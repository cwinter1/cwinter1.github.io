Concept 1 — Network Telemetry Hierarchy

Network detection requires a different data source than endpoint detection. Where Sysmon captures what a process does, network telemetry captures what crosses the wire. The three primary network data sources for a SOC:

PCAP (Packet Capture): full packet capture stores every byte of network traffic. Complete fidelity — you can reconstruct sessions, extract files, replay traffic. Cost: 1 Gbps of traffic generates roughly 450 GB/hour of PCAP. Typically retained for 24–72 hours due to storage cost.

Flow data (NetFlow/IPFIX/sFlow): summarized per-connection metadata — source IP, dest IP, source port, dest port, byte count, packet count, duration. No payload content. Typical retention: 30–90 days. Used for beaconing detection, lateral movement detection, volumetric analysis.

Application-layer logs (Zeek/Bro logs): Zeek parses protocols and extracts connection metadata, DNS queries, HTTP headers, SSL certificates, file hashes. Richer than flow data, cheaper than PCAP. Zeek generates per-protocol log files: conn.log, dns.log, http.log, ssl.log, files.log.

Detection strategy: use Zeek logs as the primary detection source (rich, indexed, queryable). Use PCAP for forensic investigation after an alert fires. Use flow data for trend analysis and lateral movement hunting over long time windows.

Data engineering analogy: PCAP = raw event stream with full payload (Kafka with message content retained). Flow data = aggregated metrics (Kafka → aggregation pipeline → metrics store). Zeek logs = structured ETL output (Kafka → Flink parsing → enriched event store).

from dataclasses import dataclass
from typing import Optional

@dataclass
class ZeekConnLog:
    ts: float               # epoch timestamp
    uid: str                # unique connection ID
    id_orig_h: str          # source IP
    id_orig_p: int          # source port
    id_resp_h: str          # dest IP
    id_resp_p: int          # dest port
    proto: str              # tcp/udp/icmp
    service: Optional[str]  # application protocol (http, dns, ssl)
    duration: Optional[float]   # seconds
    orig_bytes: Optional[int]   # bytes sent by originator
    resp_bytes: Optional[int]   # bytes sent by responder
    conn_state: str         # connection state code
    local_orig: bool        # originator is local
    local_resp: bool        # responder is local

    def is_outbound(self) -> bool:
        return self.local_orig and not self.local_resp

    def bytes_ratio(self) -> Optional[float]:
        if self.resp_bytes and self.orig_bytes and self.orig_bytes > 0:
            return round(self.resp_bytes / self.orig_bytes, 3)
        return None

from dataclasses import dataclass
from typing import List

CONN_STATE_DESCRIPTIONS = {
    "SF":   "Normal establish + close",
    "S0":   "SYN only — no response (scan/filtered)",
    "S1":   "SYN + SYN-ACK — no data transferred",
    "REJ":  "Connection rejected (RST received)",
    "RSTO": "Originator reset connection",
    "RSTOS0": "Originator sent SYN then RST",
    "RSTR": "Responder reset the connection",
    "SH":   "SYN + FIN — no data (half-open)",
    "OTH":  "Mid-session capture (asymmetric)",
}

def categorize_connection(conn: "ZeekConnLog") -> List[str]:
    labels = []
    state_desc = CONN_STATE_DESCRIPTIONS.get(conn.conn_state, "Unknown")
    labels.append(f"STATE:{conn.conn_state}({state_desc})")

    if conn.conn_state == "S0":
        labels.append("SCAN_CANDIDATE")
    if conn.duration and conn.duration > 3600:
        labels.append("LONG_LIVED_CONNECTION")
    if conn.orig_bytes is not None and conn.resp_bytes is not None:
        if conn.orig_bytes < 200 and conn.resp_bytes > 10_000:
            labels.append("ASYMMETRIC_BYTES:possible_C2_beacon")
        if conn.orig_bytes > 50_000_000:
            labels.append("HIGH_UPLOAD:possible_exfiltration")
    return labels

Concept 3 — DNS Log Analysis


dns.log is the second most important Zeek log for detection. DNS is used by nearly every C2 framework (DNS tunneling, DGA domains), and it is the first observable artifact when malware phones home. Every outbound connection to an external IP starts with a DNS query.


Key dns.log fields:


    

  • query: the domain name being resolved
    • 

  • qtype_name: query type (A, AAAA, TXT, MX) — TXT queries to external domains are often used for C2 commands
    • 

  • rcode_name: response code (NOERROR, NXDOMAIN, SERVFAIL) — high NXDOMAIN rate = DGA activity
    • 

  • answers: list of resolved IP addresses
    • 

  • TTL: low TTL values (< 60 seconds) indicate fast-flux DNS (botnet infrastructure)
    • 

  • rejected: True if the query was rejected by a DNS filter
    • 



Detection patterns from DNS:


    

  • DGA (Domain Generation Algorithm): high entropy domain names that resolve to NXDOMAIN — malware cycling through auto-generated domains looking for active C2
    • 

  • DNS tunneling: large TXT record queries, unusually long subdomain labels (data encoded in subdomain)
    • 

  • Fast-flux: TTL < 30 seconds + multiple A record answers
    • 

  • Typosquatting: domains similar to legitimate domains (leveled by edit distance)
    • 



Example:


import math
from dataclasses import dataclass
from typing import List, Optional

@dataclass
class ZeekDNSLog:
    ts: float
    uid: str
    id_orig_h: str
    query: str
    qtype_name: str
    rcode_name: str
    answers: List[str]
    ttl: Optional[float]

def shannon_entropy(s: str) -> float:
    if not s:
        return 0.0
    freq = {c: s.count(c) / len(s) for c in set(s)}
    return -sum(p * math.log2(p) for p in freq.values())

def analyze_dns_query(log: ZeekDNSLog) -> List[str]:
    indicators = []
    domain = log.query.lower()

    if log.rcode_name == "NXDOMAIN":
        indicators.append("NXDOMAIN")

    entropy = shannon_entropy(domain.split(".")[0])
    if entropy > 3.5:
        indicators.append(f"HIGH_ENTROPY_DOMAIN:{entropy:.2f}")

    if log.qtype_name == "TXT":
        indicators.append("TXT_QUERY:possible_C2_channel")

    if log.ttl and log.ttl < 30:
        indicators.append(f"LOW_TTL:{log.ttl}s:fast_flux")

    subdomain_part = ".".join(domain.split(".")[:-2]) if len(domain.split(".")) > 2 else ""
    if len(subdomain_part) > 40:
        indicators.append(f"LONG_SUBDOMAIN:{len(subdomain_part)}chars:possible_tunneling")

    return indicators

    ZeekDNSLog(1710499200.0, "D001", "10.0.1.42", "xkjhqwzplmvb.com",           "A",   "NXDOMAIN", [],                  None),
    ZeekDNSLog(1710499201.0, "D002", "10.0.1.42", "google.com",                  "A",   "NOERROR",  ["142.250.80.46"],    300.0),
    ZeekDNSLog(1710499202.0, "D003", "10.0.1.42", "data.c2.evil.com",            "TXT", "NOERROR",  ["aGVsbG8gd29ybGQ="], 5.0),

LLM Integration


Topic: LLMs can classify domain names as malicious or benign by reasoning about lexical features (length, entropy, character distribution) without needing a threat intelligence lookup.
Threat: LLM-powered DNS filtering that blocks domains based on LLM classification introduces false positives for legitimate but unusual domain names (brand new TLDs, IDN domains, short cryptic domains used by legitimate services).
Opportunity: Use an LLM as a second-pass triage tool for high-entropy DNS queries — it can cross-reference the domain against known legitimate patterns and explain its reasoning.

Concept 1 — Beaconing Patterns


Command-and-control (C2) malware typically "beacons" — makes periodic outbound connections to a C2 server to check for commands. The beacon is a short HTTP or DNS request sent on a regular schedule (e.g., every 60 seconds) with a small amount of jitter to avoid exact periodicity detection.


Beacon characteristics:


    

  • Periodicity: connections at regular intervals (e.g., every 60 ± 10 seconds)
    • 

  • Consistent destination: same IP/domain, same port
    • 

  • Small payload: check-in beacon is typically < 200 bytes outbound
    • 

  • Long duration: a compromised host may beacon for days or weeks
    • 

  • Jitter: attacker adds random delay (typically ±20% of interval) to defeat exact-interval detection
    • 



Detection approach: calculate the statistical distribution of inter-arrival times between connections to the same destination. A beacon produces a narrow inter-arrival time distribution (low variance around the mean interval). Legitimate web browsing produces a wide, irregular distribution.


Metrics used:


    

  • Mean inter-arrival time (μ): the likely beacon interval
    • 

  • Standard deviation (σ): low σ = consistent interval = beacon
    • 

  • Coefficient of variation (CV = σ/μ): scale-independent regularity metric; CV < 0.3 is suspicious
    • 



Example:


import statistics
from dataclasses import dataclass
from typing import List, Tuple

@dataclass
class ConnectionRecord:
    source_ip: str
    dest_ip: str
    dest_port: int
    timestamp: float    # epoch seconds
    orig_bytes: int
    resp_bytes: int

def compute_beacon_score(connections: List[ConnectionRecord]) -> dict:
    if len(connections) < 5:
        return {"verdict": "INSUFFICIENT_DATA", "count": len(connections)}

    timestamps = sorted(c.timestamp for c in connections)
    intervals = [timestamps[i+1] - timestamps[i] for i in range(len(timestamps)-1)]

    mean_interval = statistics.mean(intervals)
    if mean_interval == 0:
        return {"verdict": "BURST", "count": len(connections)}

    stdev = statistics.stdev(intervals) if len(intervals) > 1 else 0
    cv = stdev / mean_interval

    mean_bytes = statistics.mean(c.orig_bytes for c in connections)

    return {
        "source_ip":      connections[0].source_ip,
        "dest_ip":        connections[0].dest_ip,
        "dest_port":      connections[0].dest_port,
        "connection_count": len(connections),
        "mean_interval_s": round(mean_interval, 1),
        "stdev_s":         round(stdev, 1),
        "cv":              round(cv, 3),
        "mean_bytes_out":  round(mean_bytes, 0),
        "verdict":        "BEACON" if cv < 0.3 and len(connections) >= 10 else "IRREGULAR",
    }

import random
random.seed(42)

base_time = 1710499200.0
beacon_interval = 60.0

    ConnectionRecord(
        "10.0.1.42", "185.220.101.5", 443,

        orig_bytes=random.randint(50, 150),
        resp_bytes=random.randint(100, 300),
    )
    for i in range(20)
]

print(f"Verdict: {result['verdict']}")
print(f"Interval: {result['mean_interval_s']}s ± {result['stdev_s']}s (CV={result['cv']})")
print(f"Connections: {result['connection_count']} over {result['mean_interval_s'] * result['connection_count'] / 60:.1f} min")

Concept 2 — Jitter Analysis and Seasonality


Simple CV-based beaconing detection fails against low-jitter beacons (always ±0.5%) and against legitimate services that happen to poll regularly (Windows Update, antivirus definition updates, NTP). Advanced beacon detection adds:


Seasonality filtering: legitimate periodic connections (NTP port 123, Windows Update, DNS heartbeats) are allowlisted by port or destination domain. If the destination is a known CDN or a Microsoft IP range, the connection is excluded before beacon scoring.


Jitter distribution analysis: true beacons have jitter concentrated around the mean (Gaussian-like). Legitimate periodic traffic often has bimodal distributions (e.g., a service that polls at :00 and :30 of each minute).


Autocorrelation: calculate the autocorrelation of the timestamp series at lag-1. Strong positive autocorrelation (ρ > 0.7) indicates a self-similar pattern — the interval at time T predicts the interval at time T+1, which is characteristic of jitter-based beacons.


Example:


import statistics
from typing import List

ALLOWLISTED_PORTS = {53, 123, 80, 443}
ALLOWLISTED_DEST_PREFIXES = ("8.8.8.8", "8.8.4.4", "13.107.", "20.190.", "204.79.")

def should_allowlist(dest_ip: str, dest_port: int) -> bool:
    if dest_port in ALLOWLISTED_PORTS:
        return True
    return any(dest_ip.startswith(prefix) for prefix in ALLOWLISTED_DEST_PREFIXES)

def autocorrelation_lag1(intervals: List[float]) -> float:
    if len(intervals) < 3:
        return 0.0
    n = len(intervals)
    mean = statistics.mean(intervals)
    variance = statistics.variance(intervals)
    if variance == 0:
        return 1.0
    covariance = sum((intervals[i] - mean) * (intervals[i+1] - mean) for i in range(n-1)) / (n - 1)
    return round(covariance / variance, 3)

def enhanced_beacon_score(connections: List["ConnectionRecord"]) -> dict:
    if not connections:
        return {}

    dest_ip = connections[0].dest_ip
    dest_port = connections[0].dest_port

    if should_allowlist(dest_ip, dest_port):
        return {"verdict": "ALLOWLISTED", "dest": dest_ip, "port": dest_port}

    if len(connections) < 5:
        return {"verdict": "INSUFFICIENT_DATA"}

    timestamps = sorted(c.timestamp for c in connections)
    intervals = [timestamps[i+1] - timestamps[i] for i in range(len(timestamps)-1)]
    mean_i = statistics.mean(intervals)
    cv = statistics.stdev(intervals) / mean_i if mean_i > 0 else 999
    acf = autocorrelation_lag1(intervals)

    beacon_score = 0
    if cv < 0.30:
        beacon_score += 3
    elif cv < 0.50:
        beacon_score += 1

    if acf > 0.70:
        beacon_score += 2

    if statistics.mean(c.orig_bytes for c in connections) < 300:
        beacon_score += 1

    verdict = "BEACON" if beacon_score >= 4 else ("SUSPICIOUS" if beacon_score >= 2 else "CLEAN")

    return {
        "dest": dest_ip, "port": dest_port,
        "count": len(connections),
        "cv": round(cv, 3), "acf_lag1": acf,
        "beacon_score": beacon_score, "verdict": verdict,
    }

# Test the allowlist
print(f"Google DNS allowlisted: {should_allowlist('8.8.8.8', 53)}")
print(f"Unknown IP port 443: {should_allowlist('185.220.101.5', 443)}")

Concept 3 — Lateral Movement Detection via Network


Lateral movement leaves network signatures that differ from normal user traffic. Key patterns:


    

  • SMB scanning: short-duration connections to port 445 across many internal IPs from a single source — indicates automated enumeration
    • 

  • WMI remote execution: connections from a workstation to port 135 (RPC endpoint mapper) then an ephemeral high port on another internal host
    • 

  • Pass-the-Hash / Pass-the-Ticket: SMB authentication to multiple hosts in rapid succession from a single source, often at unusual hours
    • 

  • RDP brute force: multiple connection attempts to port 3389 with REJ or failed state from a single source
    • 



Detection strategy for lateral movement: look for a single internal source connecting to many internal destinations on administrative ports (445, 135, 3389, 5985) within a short time window.


Example:


from collections import defaultdict
from datetime import datetime
from typing import List, Dict

def detect_lateral_movement(
    connections: List["ZeekConnLogSimple"],
    time_window_seconds: float = 300,
    min_unique_targets: int = 5,
    admin_ports: set = None,
) -> List[dict]:
    if admin_ports is None:
        admin_ports = {445, 135, 139, 3389, 5985, 5986, 22}

    source_to_targets: Dict[str, set] = defaultdict(set)
    source_first_seen: Dict[str, float] = {}

    for conn in connections:
        if not (conn.local_orig and conn.local_resp):
            continue
        if conn.id_resp_p not in admin_ports:
            continue

        src = conn.id_orig_h
        if src not in source_first_seen:
            source_first_seen[src] = conn.ts
        if conn.ts - source_first_seen[src] <= time_window_seconds:
            source_to_targets[src].add((conn.id_resp_h, conn.id_resp_p))

    alerts = []
    for src, targets in source_to_targets.items():
        unique_hosts = len({t[0] for t in targets})
        if unique_hosts >= min_unique_targets:
            alerts.append({
                "source_ip": src,
                "unique_target_hosts": unique_hosts,
                "connections": len(targets),
                "ports_used": sorted({t[1] for t in targets}),
                "verdict": "LATERAL_MOVEMENT_CANDIDATE",
            })
    return alerts

    ts: float
    uid: str
    id_orig_h: str
    id_resp_h: str
    id_orig_p: int
    id_resp_p: int
    proto: str
    service: str
    duration: float
    orig_bytes: int
    resp_bytes: int
    conn_state: str
    local_orig: bool = True
    local_resp: bool = False

    for i in range(10)
]

alerts = detect_lateral_movement(lateral_conns)
for alert in alerts:
    print(f"ALERT: {alert['source_ip']} → {alert['unique_target_hosts']} hosts via ports {alert['ports_used']}")

Concept 1 — Suricata Rule Structure


Suricata is an open-source network IDS/IPS that performs deep packet inspection and matches traffic against a rule library. Where Zeek extracts metadata, Suricata inspects payload content and matches signatures in real time — the network equivalent of YARA for endpoint files.


Suricata rule anatomy:


alert tcp $HOME_NET any -> $EXTERNAL_NET 443 (msg:"Cobalt Strike Beacon HTTPS"; flow:established,to_server; content:"GET"; http_method; content:"/jquery-3.3.1.min.js"; http_uri; threshold:type both,track by_src,count 3,seconds 60; classtype:trojan-activity; sid:9001001; rev:1;)

Components:


    

  • Action: alert (log), drop (IPS mode), reject, pass
    • 

  • Protocol: tcp, udp, icmp, http, dns, tls
    • 

  • Source/Dest: $HOME_NET, $EXTERNAL_NET, specific IP, any
    • 

  • Port: specific port, port group, any
    • 

  • Options: everything in parentheses — msg, content, pcre, threshold, classtype, sid
    • 



Key option keywords:


    

  • content: exact byte match — e.g., content:"evil.exe"
    • 

  • pcre: Perl-compatible regex — e.g., pcre:"/[A-Z0-9]{32}\.php/i"
    • 

  • flow: direction (established, to_server, to_client)
    • 

  • http_uri, http_header, http_client_body: apply match to specific HTTP layer
    • 

  • threshold: alert suppression — fire once per source per N seconds
    • 

  • sid: unique rule ID (5000000+ for local rules)
    • 



Example:


from dataclasses import dataclass
from typing import Optional

@dataclass
class SuricataRule:
    action: str
    proto: str
    src: str
    src_port: str
    direction: str
    dst: str
    dst_port: str
    msg: str
    content: Optional[str]
    pcre: Optional[str]
    flow: Optional[str]
    classtype: str
    sid: int
    rev: int = 1

    def to_rule_string(self) -> str:
        options = [f'msg:"{self.msg}"']
        if self.flow:
            options.append(f"flow:{self.flow}")
        if self.content:
            options.append(f'content:"{self.content}"')
        if self.pcre:
            options.append(f"pcre:{self.pcre}")
        options += [
            f"classtype:{self.classtype}",
            f"sid:{self.sid}",
            f"rev:{self.rev}",
        ]
        opts_str = "; ".join(options) + ";"
        return (
            f"{self.action} {self.proto} {self.src} {self.src_port} "
            f"{self.direction} {self.dst} {self.dst_port} ({opts_str})"
        )

    action="alert", proto="dns",
    src="$HOME_NET", src_port="any",
    direction="->", dst="any", dst_port="53",
    msg="DNS Query for High-Entropy Domain",
    content=None,
    pcre='"/^[a-z0-9]{12,}\\.(?:com|net|org)$/i"',
    flow=None,
    classtype="trojan-activity",
    sid=9001002,
)

Concept 2 — Network Sigma Rules


Sigma supports a network_connection log source category that maps to Zeek conn.log fields. Network Sigma rules can be deployed to SIEM platforms that ingest Zeek logs (Elastic, Splunk, Sentinel) using the same Sigma toolchain as endpoint rules.


A network Sigma rule targeting beaconing looks for the pattern: high connection count to a single external destination within a time window. Most SIEM platforms support this via aggregate functions (KQL's summarize, SPL's stats count).


Network Sigma limitations compared to Suricata:


    

  • No payload inspection — you cannot match HTTP body content or TLS SNI in a Sigma rule targeting conn.log (you need Zeek http.log or ssl.log)
    • 

  • Relies on metadata only — connection count, byte volumes, duration
    • 

  • No real-time blocking capability — Sigma produces alerts, not drops
    • 



Use Suricata for real-time signature matching and inline blocking. Use Sigma for behavioral detection over aggregated metadata over longer time windows.

Concept 3 — Threat Intelligence Integration with Network Logs


Network log analysis becomes significantly more powerful when enriched with threat intelligence (TI). An IP address appearing in conn.log means little in isolation; the same IP flagged as a known C2 server in a TI feed is an immediate high-priority alert.


TI enrichment workflow for network logs:


    

  1. Extract all external destination IPs from conn.log
    2. 

  2. Look up each IP against TI feeds (VirusTotal, AbuseIPDB, Shodan, AlienVault OTX)
    3. 

  3. Tag each connection with TI hits: confidence score, threat categories, reported malware families
    4. 

  4. Correlate TI-tagged connections with user accounts and hostnames
    5. 

  5. Auto-escalate connections with TI confidence ≥ 80 to Tier 1 analyst queue
    6. 



TI feed limitations: false positives exist (IP reputation can lag — an IP cleaned up but still listed as malicious); TI misses novel infrastructure (zero-day C2 servers never seen before). TI enrichment is a signal multiplier, not a standalone detection.

Concept 1 — JA3 TLS Fingerprinting


JA3 is a method for creating a fingerprint of a TLS client based on the SSL/TLS ClientHello message fields: SSL version, ciphers, extensions, elliptic curves, and elliptic curve formats. The fingerprint is an MD5 hash of these fields. Because different applications (Chrome, PowerShell, Cobalt Strike) use different TLS parameters, JA3 fingerprints can distinguish C2 tools from legitimate browser traffic even when the destination IP and domain are unknown.


JA3S is the server-side version — a fingerprint of the ServerHello response. A (JA3, JA3S) pair uniquely identifies a specific C2 framework communicating with its specific C2 server.


Known malicious JA3 fingerprints are published in threat intelligence databases. Zeek's ssl.log includes the ja3 and ja3s fields when using the JA3 script package.


Use case: a new IP appears in conn.log — no TI hit. But the JA3 fingerprint matches the known Cobalt Strike default JA3 hash. The IP has been active less than 24 hours and is not yet in any TI feed — JA3 catches it early.


Example:


import hashlib
from dataclasses import dataclass
from typing import List, Optional

    "51c64c77e60f3980eea90869b68c58a8": "CobaltStrike",
    "6734f37431670b3ab4292b8f60f29984": "Metasploit",
    "a0e9f5d64349fb13191bc781f81f42e1": "Emotet",
}

@dataclass
class ZeekSSLLog:
    ts: float
    uid: str
    id_orig_h: str
    id_resp_h: str
    id_resp_p: int
    server_name: str     # SNI — the domain being accessed
    ja3: Optional[str]   # client fingerprint
    ja3s: Optional[str]  # server fingerprint
    issuer: Optional[str]
    subject: Optional[str]
    validation_status: str

    def tls_alert(self) -> Optional[str]:
        if self.ja3 and self.ja3 in KNOWN_MALICIOUS_JA3:
            return f"JA3_MATCH:{KNOWN_MALICIOUS_JA3[self.ja3]}"
        if self.validation_status not in ("ok", ""):
            return f"CERT_INVALID:{self.validation_status}"
        if self.server_name.endswith((".ru", ".cn", ".onion")):
            return f"SUSPICIOUS_SNI_TLD:{self.server_name}"
        return None

def compute_ja3(
    ssl_version: int,
    ciphers: List[int],
    extensions: List[int],
    elliptic_curves: List[int],
    elliptic_curve_formats: List[int],
) -> str:
    raw = ",".join([
        str(ssl_version),
        "-".join(str(c) for c in ciphers),
        "-".join(str(e) for e in extensions),
        "-".join(str(c) for c in elliptic_curves),
        "-".join(str(f) for f in elliptic_curve_formats),
    ])
    return hashlib.md5(raw.encode()).hexdigest()

)

Concept 2 — HTTP Log Detection


Zeek's http.log records every HTTP transaction: method, URI, user-agent, referrer, response code, response body size. HTTP is the most common C2 protocol because it traverses almost every firewall and blends with legitimate web traffic.


Key http.log fields for detection:






Field
Detection Pattern






user_agent
Known malicious UA strings; no UA (curl/wget); UA doesn't match browser version




uri
Long random-looking URIs; URIs with Base64 patterns; known C2 URI templates




request_body_len
Large POST body on a non-upload endpoint (data exfiltration)




resp_body_len
Very small responses to POST requests (C2 command acknowledgment)




method
PUT/DELETE to non-API endpoints; HEAD beaconing




status_code
200 to all requests regardless of URI content (C2 server always returns 200)






Common C2 HTTP patterns:


    

  • GET /juliet-golf.php: random-looking URI that maps to a C2 tasking endpoint
    • 

  • Cookie: SESSIONID=aGVsbG8gd29ybGQ=: Base64-encoded C2 data in cookie headers
    • 

  • User-Agent: Mozilla/4.0 (compatible; MSIE 6.0): outdated IE UA used by old malware families
    •

from dataclasses import dataclass
from typing import List, Optional
import re
import base64

@dataclass
class ZeekHTTPLog:
    ts: float
    uid: str
    id_orig_h: str
    id_resp_h: str
    method: str
    host: str
    uri: str
    user_agent: str
    request_body_len: int
    resp_body_len: int
    status_code: int
    referrer: Optional[str] = None

SUSPICIOUS_UA_PATTERNS = [
    r"MSIE [456]\.",                       # very outdated IE
    r"^python-requests/",                  # automated requests library
    r"^Go-http-client/",                   # Go default HTTP client
    r"^curl/",                             # command-line tool
    r"^Wget/",                             # wget
]

def analyze_http_log(log: ZeekHTTPLog) -> List[str]:
    indicators = []
    ua = log.user_agent

    for pattern in SUSPICIOUS_UA_PATTERNS:
        if re.search(pattern, ua, re.IGNORECASE):
            indicators.append(f"SUSPICIOUS_UA:{pattern}")
            break

    uri_entropy_score = sum(1 for c in log.uri if c not in "-_./abcdefghijklmnopqrstuvwxyz0123456789") / max(len(log.uri), 1)
    if uri_entropy_score > 0.3:
        indicators.append(f"HIGH_ENTROPY_URI")

    if log.method == "POST" and log.request_body_len > 100_000:
        indicators.append(f"LARGE_POST_BODY:{log.request_body_len}B:possible_exfil")

    if log.method == "POST" and log.resp_body_len < 50:
        indicators.append("SMALL_POST_RESPONSE:possible_C2_ack")

    return indicators

Concept 3 — File Extraction and Hash Detection


Zeek's files.log records metadata about files transferred over observed protocols (HTTP, SMB, FTP, SMTP). Each file transfer generates a record with: file hash (MD5, SHA1, SHA256), MIME type, filename, source/destination IPs, and the protocol used for transfer.


File hash detection workflow:


    

  1. Extract SHA256 hashes from files.log in real time
    2. 

  2. Look up each hash against threat intelligence (VirusTotal, internal YARA scan results)
    3. 

  3. Alert on known-malicious hashes
    4. 

  4. Alert on high-risk MIME types delivered from external sources (.exe, .dll, .ps1, .hta, .vbs from outside the corporate perimeter)
    5. 



Legitimate and malicious deliveries look identical at the network level unless you inspect the file content. A .exe delivered via HTTPS from download.microsoft.com is legitimate; the same .exe delivered from a newly-registered domain is highly suspicious.

Concept 1 — Parsing Zeek Logs with Python


Zeek log files are TSV (tab-separated values) with a JSON header describing the fields and types. Parsing them in Python is straightforward with pandas but requires handling Zeek's special values: - (null), (empty) (empty string), and the header format.


Zeek conn.log TSV format:


#separator \x09
#set_separator ,
#empty_field (empty)
#unset_field -
#fields ts uid id.orig_h id.orig_p id.resp_h id.resp_p proto service duration orig_bytes resp_bytes conn_state
#types time string addr port addr port enum string interval count count string
1710499200.123456	CaBcDe1234567	10.0.1.42	54321	185.220.101.5	443	tcp	ssl	120.3	1024	128	SF

The #fields line defines column names; #types defines data types. Lines starting with # are header/metadata lines to be skipped when reading as data.


Example:


import pandas as pd
from io import StringIO

SAMPLE_CONN_LOG = """#separator \\x09
#set_separator ,
#empty_field (empty)
#unset_field -
#fields ts\tuid\tid.orig_h\tid.orig_p\tid.resp_h\tid.resp_p\tproto\tservice\tduration\torig_bytes\tresp_bytes\tconn_state
#types time\tstring\taddr\tport\taddr\tport\tenum\tstring\tinterval\tcount\tcount\tstring
1710499200.0\tC001\t10.0.1.42\t54321\t185.220.101.5\t443\ttcp\tssl\t120.3\t128\t512\tSF
1710499260.0\tC002\t10.0.1.42\t54322\t185.220.101.5\t443\ttcp\tssl\t118.7\t130\t508\tSF
1710499320.0\tC003\t10.0.1.42\t54323\t185.220.101.5\t443\ttcp\tssl\t121.1\t126\t515\tSF
1710499380.0\tC004\t10.0.1.42\t54324\t185.220.101.5\t443\ttcp\tssl\t119.5\t128\t510\tSF
1710499440.0\tC005\t10.0.1.42\t54325\t185.220.101.5\t443\ttcp\tssl\t120.0\t129\t512\tSF
"""

def parse_zeek_conn_log(log_content: str) -> pd.DataFrame:
    lines = log_content.strip().splitlines()
    fields_line = next(l for l in lines if l.startswith("#fields"))
    columns = fields_line.replace("#fields\t", "").split("\t")
    data_lines = [l for l in lines if not l.startswith("#")]
    df = pd.read_csv(StringIO("\n".join(data_lines)), sep="\t", names=columns, na_values=["-", "(empty)"])
    df["ts"] = pd.to_numeric(df["ts"])
    for col in ["orig_bytes", "resp_bytes", "id.orig_p", "id.resp_p"]:
        if col in df.columns:
            df[col] = pd.to_numeric(df[col], errors="coerce")
    return df

df = parse_zeek_conn_log(SAMPLE_CONN_LOG)
print(df[["ts", "id.orig_h", "id.resp_h", "id.resp_p", "orig_bytes", "resp_bytes"]].to_string())

Concept 2 — Beacon Scoring with Pandas


Pandas is well-suited for beacon detection: groupby aggregates connections per (source, destination, port) tuple; diff calculates inter-arrival times; describe provides the statistical summary for scoring.


The beacon scoring pipeline:


    

  1. Filter to outbound SF connections only
    2. 

  2. Group by (id.orig_h, id.resp_h, id.resp_p)
    3. 

  3. Sort each group by ts
    4. 

  4. Calculate interval = ts.diff()
    5. 

  5. Aggregate: mean_interval, std_interval, cv, count, mean_bytes
    6. 

  6. Filter: count >= 10 AND cv < 0.35
    7. 

  7. Score: combine CV, count, and byte size into a single beacon confidence score
    8. 



Example:


import pandas as pd
import numpy as np

def beacon_scan_pandas(df: pd.DataFrame, min_connections: int = 10, cv_threshold: float = 0.35) -> pd.DataFrame:
    outbound = df[
        (df.get("is_outbound", True) == True) &
        (df["conn_state"] == "SF")
    ].copy()

    outbound = outbound.sort_values("ts")

    def group_stats(group: pd.DataFrame) -> pd.Series:
        intervals = group["ts"].diff().dropna()
        if len(intervals) < max(min_connections - 1, 4):
            return pd.Series(dtype=float)
        mean_i = intervals.mean()
        if mean_i == 0:
            return pd.Series(dtype=float)
        cv = intervals.std() / mean_i
        return pd.Series({
            "connection_count": len(group),
            "mean_interval_s":  round(mean_i, 1),
            "std_interval_s":   round(intervals.std(), 1),
            "cv":               round(cv, 3),
            "mean_orig_bytes":  group["orig_bytes"].mean(),
            "time_span_s":      group["ts"].max() - group["ts"].min(),
        })

    stats = outbound.groupby(
        ["id.orig_h", "id.resp_h", "id.resp_p"],
        group_keys=False,
    ).apply(group_stats).dropna()

    if stats.empty:
        return pd.DataFrame()

    beacons = stats[
        (stats["cv"] < cv_threshold) &
        (stats["connection_count"] >= min_connections)
    ].copy()

    beacons["beacon_score"] = (
        (1 - beacons["cv"]) * 0.5 +
        (beacons["connection_count"].clip(upper=50) / 50) * 0.3 +
        (1 / (1 + beacons["mean_orig_bytes"] / 1000)) * 0.2
    ).round(3)

    return beacons.sort_values("beacon_score", ascending=False)

Concept 3 — Full Beaconing Detector Module


The Royal Road deliverable for W14 combines log parsing, beacon scoring, and alert output into a standalone Python module. The module reads a Zeek conn.log file, runs beacon scoring, and outputs alerts as JSON.


Integration with the detection pipeline:


    

  • Alerts from this module feed into the same alert queue as Sigma rules (alert schema matches W09 output)
    • 

  • The module is called by the CI pipeline on sample log files as a smoke test
    • 

  • Output JSON can be ingested into a SIEM as custom detection output
    • 



Example:


import json
import argparse
from pathlib import Path
from datetime import datetime

def run_beacon_detector(
    log_path: str,
    output_path: str,
    min_connections: int = 10,
    cv_threshold: float = 0.35,
    local_net: str = "10.",
) -> dict:
    from io import StringIO
    import pandas as pd

    content = Path(log_path).read_text(encoding="utf-8") if Path(log_path).exists() else log_path

    df = parse_zeek_conn_log(content)
    df["is_outbound"] = (
        df["id.orig_h"].str.startswith(local_net) &
        ~df["id.resp_h"].str.startswith(local_net)
    )

    results = beacon_scan_pandas(df, min_connections=min_connections, cv_threshold=cv_threshold)

    alerts = []
    if not results.empty:
        for idx, row in results.reset_index().iterrows():
            alerts.append({
                "alert_id":         f"BEACON-{idx+1:04d}",
                "rule":             "zeek_beaconing_detector",
                "technique":        "T1071.001",
                "source_ip":        row["id.orig_h"],
                "dest_ip":          row["id.resp_h"],
                "dest_port":        int(row["id.resp_p"]),
                "connection_count": int(row["connection_count"]),
                "mean_interval_s":  row["mean_interval_s"],
                "cv":               row["cv"],
                "beacon_score":     row["beacon_score"],
                "severity":         "HIGH" if row["beacon_score"] > 0.7 else "MEDIUM",
                "generated_at":     datetime.utcnow().isoformat() + "Z",
            })

    output = {"alert_count": len(alerts), "alerts": alerts}
    Path(output_path).write_text(json.dumps(output, indent=2), encoding="utf-8")
    return output

LLM Integration


Topic: LLMs can generate narrative threat reports from raw beacon detection output, translating JSON alert fields into incident documentation suitable for ticket systems and compliance reporting.
Threat: A SOC that over-automates beacon reporting via LLM may auto-close alerts for low-scoring beacons (score=0.55) that are genuinely malicious but well-configured to evade detection thresholds.
Opportunity: Use an LLM to suggest follow-up investigation steps tailored to the specific beacon parameters (interval, byte size, destination) that would either confirm or dismiss the alert.
