Concept 1 — KQL Syntax and the Pipe Model

Kusto Query Language (KQL) is Microsoft's query language used in Azure Monitor, Microsoft Sentinel, and Defender. It uses a left-to-right pipe model: data flows from a source table through a series of operators, each transforming the result.

TableName
| operator1 arguments
| operator2 arguments
| operator3 arguments

This is identical to a Unix shell pipeline or a pandas method chain — each step receives the output of the previous step and passes its output to the next. KQL is declarative: you describe what you want, not how to compute it.

Core operators every analyst needs:

  • where — filter rows (like SQL WHERE)
  • project — select columns (like SQL SELECT)
  • extend — add computed columns (like pandas assign)
  • summarize — aggregate (like SQL GROUP BY)
  • sort by — order results
  • top N by — return top N rows
  • join — combine two tables

Data engineering analogy: KQL is dbt + SQL combined. The pipe chain maps directly to a dbt model chain.

Example:

// KQL — Find failed logons in the last 24 hours
SecurityEvent
| where TimeGenerated > ago(24h)
| where EventID == 4625
| where AccountType == "User"
| project TimeGenerated, Account, WorkstationName, IpAddress, LogonTypeName
| sort by TimeGenerated desc

Concept 2 — where, project, extend, summarize

These four operators handle 90% of detection queries. Understanding their semantics precisely prevents common mistakes.

where filters rows. Multiple conditions in one where are ANDed. Use or explicitly. project keeps only listed columns and drops the rest. project-away drops listed columns and keeps the rest. extend adds new columns without removing existing ones — unlike project. summarize collapses rows. Every column not in the by clause must be an aggregation. The result has one row per unique combination of by columns.

Example:

// Brute force detector — accounts with > 5 failures in 10 min windows
SecurityEvent
| where EventID == 4625
| where TimeGenerated > ago(1d)
| extend TimeWindow = bin(TimeGenerated, 10m)
| summarize
    failure_count = count(),
    distinct_ips = dcount(IpAddress)
    by Account, TimeWindow
| where failure_count > 5
| sort by failure_count desc

// Python equivalent (pandas) for local testing
import pandas as pd

def brute_force_detector(df: pd.DataFrame, window: str = "10min", threshold: int = 5) -> pd.DataFrame:
    failures = df[df["EventID"] == 4625].copy()
    failures["TimeWindow"] = failures["TimeGenerated"].dt.floor(window)
    result = (
        failures.groupby(["Account", "TimeWindow"])
        .agg(failure_count=("EventID", "count"), distinct_ips=("IpAddress", "nunique"))
        .reset_index()
    )
    return result[result["failure_count"] > threshold].sort_values("failure_count", ascending=False)

Concept 3 — Time Functions and Windowing

Detection queries are almost always time-bounded. KQL time functions are first-class:

  • ago(Xh) / ago(Xd) — relative time from now
  • bin(TimeGenerated, 1h) — floor timestamp to nearest hour bucket
  • datetime(2024-03-15) — literal datetime
  • between(datetime(X) .. datetime(Y)) — time range
  • startofday(now()) — today's midnight
  • format_datetime(ts, "yyyy-MM-dd HH:mm") — format for display

Windowing with bin() is the key to time-series detection. It groups events into fixed buckets so you can count per-window and spot volume anomalies.

Example:

// Hourly logon failure counts — spot brute force timing
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4625
| summarize hourly_failures = count() by bin(TimeGenerated, 1h), Account
| where hourly_failures > 20
| sort by TimeGenerated desc

// Python equivalent
def hourly_failure_count(df: pd.DataFrame, threshold: int = 20) -> pd.DataFrame:
    df = df[df["EventID"] == 4625].copy()
    df["hour_bucket"] = df["TimeGenerated"].dt.floor("h")
    result = (
        df.groupby(["hour_bucket", "Account"])
        .size()
        .reset_index(name="hourly_failures")
    )
    return result[result["hourly_failures"] > threshold].sort_values("TimeGenerated" if "TimeGenerated" in result.columns else "hour_bucket", ascending=False)

Concept 1 — let Statements and Query Modularity

let binds a name to a value, table, or function. It's the KQL equivalent of a CTE or a pandas variable assignment. Complex detection queries use let to define reusable sub-queries, lookups, and parameters.

let threshold = 5;
let suspicious_ips = datatable(ip:string) ["10.0.0.99", "192.168.1.200"];
let recent_failures =
    SecurityEvent
    | where EventID == 4625
    | where TimeGenerated > ago(1h);
recent_failures
| where IpAddress in (suspicious_ips)
| summarize count() by Account, IpAddress
| where count_ > threshold

let with a tabular expression creates a named intermediate result — exactly like a CTE. Multiple let statements can reference each other (as long as there are no cycles).

Example:

# Python equivalent of KQL let + join pattern
def kql_let_pattern(events_df: pd.DataFrame, suspicious_ips: list[str], threshold: int = 5) -> pd.DataFrame:
    # let recent_failures = ...
    recent_failures = events_df[
        (events_df["EventID"] == 4625) &
        (events_df["TimeGenerated"] > pd.Timestamp.now() - pd.Timedelta(hours=1))
    ]
    # where IpAddress in (suspicious_ips)
    filtered = recent_failures[recent_failures["IpAddress"].isin(suspicious_ips)]
    # summarize count() by Account, IpAddress
    result = (
        filtered.groupby(["Account", "IpAddress"])
        .size()
        .reset_index(name="count_")
    )
    return result[result["count_"] > threshold]

Concept 2 — join in KQL


KQL supports multiple join flavors. The most used in detection work:






Flavor
Behavior






inner
Keep rows where key exists in both tables (default)




leftouter
Keep all left rows; null right fields if no match




leftanti
Keep left rows with NO match in right (allowlist exclusion)




rightsemi
Keep right rows that have a match in left






The leftanti join is extremely useful for detection: "show me processes not in my known-good baseline." It's the KQL expression of allowlist-based detection.


Example:


// Find logons from accounts that have NOT logged in before (new accounts)
let known_accounts =
    SecurityEvent
    | where TimeGenerated between (ago(30d) .. ago(1d))
    | where EventID == 4624
    | summarize by Account;
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID == 4624
| join kind=leftanti known_accounts on Account
| project TimeGenerated, Account, IpAddress, WorkstationName

// Python equivalent
def new_account_logons(df: pd.DataFrame) -> pd.DataFrame:
    cutoff = pd.Timestamp.now()
    historical = df[
        (df["TimeGenerated"] < cutoff - pd.Timedelta(days=1)) &
        (df["TimeGenerated"] > cutoff - pd.Timedelta(days=30)) &
        (df["EventID"] == 4624)
    ]["Account"].unique()
    recent = df[
        (df["TimeGenerated"] > cutoff - pd.Timedelta(days=1)) &
        (df["EventID"] == 4624)
    ]
    return recent[~recent["Account"].isin(historical)]

Concept 3 — Regex and String Operations in KQL


Detection rules frequently need pattern matching — extracting substrings, matching suspicious patterns, parsing fields from unstructured strings. KQL string operators:


    

  • contains — case-insensitive substring match
    • 

  • has — word boundary match (faster than contains for whole words)
    • 

  • matches regex — full regex match
    • 

  • extract(regex, group, field) — pull a capture group from a string
    • 

  • parse — extract multiple fields by pattern
    • 

  • base64_decode_tostring() — decode base64 (catches encoded PowerShell)
    • 



Example:


// Detect encoded PowerShell
SecurityEvent
| where EventID == 4688
| where CommandLine matches regex @"-[Ee][Nn][Cc][Oo][Dd][Ee][Dd][Cc][Oo][Mm][Mm][Aa][Nn][Dd]"
| extend decoded_cmd = base64_decode_tostring(extract(@"-[Ee]nc\w*\s+([A-Za-z0-9+/=]+)", 1, CommandLine))
| project TimeGenerated, Account, CommandLine, decoded_cmd

// Python equivalent
import base64, re

def detect_encoded_powershell(df: pd.DataFrame) -> pd.DataFrame:
    pattern = re.compile(r"-[Ee][Nn][Cc][Oo][Dd][Ee][Dd][Cc][Oo][Mm][Mm][Aa][Nn][Dd]")
    b64_pattern = re.compile(r"-[Ee]nc\w*\s+([A-Za-z0-9+/=]+)", re.IGNORECASE)
    
    mask = df["CommandLine"].str.contains(pattern, regex=True, na=False)
    result = df[mask].copy()
    
    def decode_b64(cmd: str) -> str:
        m = b64_pattern.search(cmd)
        if m:
            try:
                return base64.b64decode(m.group(1)).decode("utf-16-le", errors="replace")
            except Exception:
                return "<decode_error>"
        return ""
    
    result["decoded_cmd"] = result["CommandLine"].apply(decode_b64)
    return result[["UtcTime", "User", "CommandLine", "decoded_cmd"]]

Concept 1 — SPL Fundamentals


Splunk Processing Language (SPL) is Splunk's query language. Like KQL, it uses a pipe model, but the data model is different: Splunk indexes raw text events and extracts fields at search time using regex patterns defined in props.conf and transforms.conf.


SPL syntax:


index=windows EventCode=4625
| stats count by user, src_ip
| where count > 5
| sort -count

Key differences from KQL:


    

  • index= instead of a table name (Splunk indexes, not tables)
    • 

  • EventCode not EventID (Splunk's default field name from Windows TA)
    • 

  • stats is the aggregate operator (like KQL summarize)
    • 

  • eval adds computed fields (like KQL extend)
    • 

  • Field names are case-insensitive
    • 

  • Time range set in the search UI or with earliest= / latest=
    • 



Example:


# Translate SPL to Python pandas — same conceptual operations
SPL_QUERY = """
index=windows EventCode=4625
| stats count as failure_count, dc(src_ip) as unique_ips by user
| where failure_count > 10
| sort -failure_count
"""

def spl_equivalent(df: pd.DataFrame) -> pd.DataFrame:
    # index=windows EventCode=4625
    filtered = df[(df["index"] == "windows") & (df["EventCode"] == 4625)]
    # stats count, dc(src_ip) by user
    result = filtered.groupby("user").agg(
        failure_count=("EventCode", "count"),
        unique_ips=("src_ip", "nunique")
    ).reset_index()
    # where failure_count > 10
    result = result[result["failure_count"] > 10]
    return result.sort_values("failure_count", ascending=False)

Concept 2 — SPL stats, eval, rex


The three most-used SPL commands after search:


stats — aggregate with functions: count, dc (distinct count), sum, avg, min, max, list, values, earliest, latest.


eval — compute new fields: eval risk = if(failure_count > 10, "HIGH", "LOW"). Supports regex, math, string functions.


rex — extract fields from raw text using named capture groups: rex field=CommandLine "(?i)-enc\s+(?P<encoded_payload>[A-Za-z0-9+/=]+)". Named groups become new fields.


Example:


// Risk scoring in SPL
index=windows (EventCode=4625 OR EventCode=4688)
| eval event_type=case(EventCode=4625, "failed_logon", EventCode=4688, "process_create", true(), "other")
| stats count by event_type, ComputerName
| eval risk_score=case(
    event_type="failed_logon" AND count > 20, 3,
    event_type="failed_logon" AND count > 5, 2,
    true(), 1)
| sort -risk_score

def spl_risk_score(df: pd.DataFrame) -> pd.DataFrame:
    df = df[df["EventCode"].isin([4625, 4688])].copy()
    df["event_type"] = df["EventCode"].map({4625: "failed_logon", 4688: "process_create"})
    agg = df.groupby(["event_type", "ComputerName"]).size().reset_index(name="count")
    
    def score(row):
        if row["event_type"] == "failed_logon" and row["count"] > 20:
            return 3
        if row["event_type"] == "failed_logon" and row["count"] > 5:
            return 2
        return 1
    
    agg["risk_score"] = agg.apply(score, axis=1)
    return agg.sort_values("risk_score", ascending=False)

Concept 1 — Sigma Rule Structure


Sigma is a generic YAML format for writing detection rules that compile to any SIEM query language. A Sigma rule describes what to detect; a compiler converts it to KQL, SPL, Elasticsearch DSL, or any other target.


Rule anatomy:


title: Descriptive title
id: uuid4
status: experimental | test | stable
description: What does this rule detect?
references: [links]
author: name
date: YYYY/MM/DD
tags:
  - attack.technique_id
logsource:
  category: process_creation | network_connection | etc.
  product: windows | linux | etc.
detection:
  selection:
    FieldName|modifier: value
  condition: selection
falsepositives: [known FPs]
level: informational | low | medium | high | critical

The detection section is the core. selection defines field-value conditions. condition composes them with and, or, not, 1 of, all of.


Example:

# Simulate Sigma modifier matching in Python
import re

def sigma_contains(field_value: str, pattern: str) -> bool:
    return pattern.lower() in field_value.lower()

def sigma_endswith(field_value: str, suffix: str) -> bool:
    return field_value.lower().endswith(suffix.lower())

def sigma_re(field_value: str, pattern: str) -> bool:
    return bool(re.search(pattern, field_value, re.IGNORECASE))

def apply_sigma_rule(event: dict) -> bool:
    """Simulate the Mimikatz Sigma rule detection logic."""
    image = event.get("Image", "")
    cmdline = event.get("CommandLine", "")
    
    selection_image = sigma_endswith(image, "\\mimikatz.exe")
    selection_cmdline = any(
        sigma_contains(cmdline, kw)
        for kw in ["sekurlsa::logonpasswords", "lsadump::sam", "privilege::debug"]
    )
    return selection_image or selection_cmdline

events = [
    {"Image": "C:\\Tools\\mimikatz.exe", "CommandLine": "mimikatz.exe"},
    {"Image": "C:\\Windows\\cmd.exe", "CommandLine": "privilege::debug"},
    {"Image": "C:\\Windows\\explorer.exe", "CommandLine": "ls"},
]
for e in events:
    print(apply_sigma_rule(e), e["CommandLine"])

Concept 3 — Sigma to KQL Compilation


The Sigma compiler (pySigma) converts rules to target query languages. Understanding the compilation output helps you debug rules and verify correctness.


A Sigma process_creation rule with logsource.product: windows compiles to:


    

  • Sentinel/KQL: queries the DeviceProcessEvents or SecurityEvent table
    • 

  • Splunk SPL: queries index=windows with Windows TA field names
    • 

  • Elasticsearch: generates a DSL query against ECS-mapped indices
    • 



The compilation maps:


    

  • Sigma field CommandLine → KQL field ProcessCommandLine (DeviceProcessEvents) or CommandLine (SecurityEvent)
    • 

  • Sigma field Image → KQL field FolderPath or NewProcessName
    • 

  • Sigma contains modifier → KQL has or contains operator
    • 



Example:


# Manual Sigma → KQL translation function (simplified)
SIGMA_TO_KQL_FIELDS = {
    "CommandLine": "CommandLine",
    "Image": "NewProcessName",
    "ParentImage": "ParentProcessName",
    "User": "Account",
}

def sigma_selection_to_kql(selection: dict) -> str:
    conditions = []
    for field_spec, values in selection.items():
        if "|" in field_spec:
            field, modifier = field_spec.split("|", 1)
        else:
            field, modifier = field_spec, "equals"
        
        kql_field = SIGMA_TO_KQL_FIELDS.get(field, field)
        
        if isinstance(values, list):
            if modifier == "contains":
                parts = [f'{kql_field} contains "{v}"' for v in values]
                conditions.append("(" + " or ".join(parts) + ")")
            elif modifier == "endswith":
                parts = [f'{kql_field} endswith "{v}"' for v in values]
                conditions.append("(" + " or ".join(parts) + ")")
        else:
            conditions.append(f'{kql_field} == "{values}"')
    
    return " and ".join(conditions)

selection = {
    "CommandLine|contains": ["sekurlsa::logonpasswords", "privilege::debug"],
}
print(sigma_selection_to_kql(selection))

Concept 1 — Sentinel Analytics Rules


In Microsoft Sentinel, detections run as Analytics Rules. Each rule has:


    

  • A KQL query that runs on a schedule
    • 

  • A time window (how far back to look)
    • 

  • An evaluation frequency (how often to run)
    • 

  • An entity mapping (which fields map to IP, Account, Host entities)
    • 

  • An alert threshold (minimum results to fire)
    • 

  • A severity level and MITRE ATT&CK tactic/technique mapping
    • 



Rule types:


    

  • Scheduled — KQL query runs on a schedule; most common
    • 

  • NRT (Near-Real-Time) — runs every minute with 5-min lookback; low latency
    • 

  • Fusion — ML-based correlation across multiple signals
    • 

  • Anomaly — built-in ML; no KQL required
    • 



For the Royal Road this week, the deliverable is 3 Scheduled rules deployed (or exported as ARM templates if no Sentinel workspace is available).


Example:


# Sentinel rule definition as Python dict (maps to ARM template)
def build_sentinel_rule(
    display_name: str,
    kql_query: str,
    severity: str,
    tactics: list[str],
    techniques: list[str],
    frequency_minutes: int = 60,
    lookback_hours: int = 24,
) -> dict:
    return {
        "kind": "Scheduled",
        "properties": {
            "displayName": display_name,
            "description": f"Detection rule: {display_name}",
            "severity": severity,
            "enabled": True,
            "query": kql_query,
            "queryFrequency": f"PT{frequency_minutes}M",
            "queryPeriod": f"PT{lookback_hours}H",
            "triggerOperator": "GreaterThan",
            "triggerThreshold": 0,
            "tactics": tactics,
            "techniques": techniques,
            "suppressionEnabled": False,
        }
    }

Concept 3 — Alert Tuning and False Positive Management


A deployed detection that fires constantly on false positives gets ignored — alert fatigue kills detection programs. Tuning is the process of adding exclusions to reduce noise without removing true positive coverage.


Tuning strategies:


    

  1. Allowlist exclusion (where Account !in (known_service_accounts))
    2. 

  2. Network scope restriction (where IpAddress startswith "10.")
    3. 

  3. Time-based exclusion (where dayofweek(TimeGenerated) != 0 — exclude weekends)
    4. 

  4. Threshold adjustment — raise minimum count to reduce noise
    5. 

  5. Context enrichment — join against asset inventory to exclude known-safe hosts
    6. 



Each tuning exception must be documented: why it was added, when to review it, what attack scenario it could mask.


Example:


TUNING_LOG = [
    {
        "rule_id": "rule-001",
        "exclusion": "Account in ('svc_deploy', 'svc_backup')",
        "reason": "Deployment pipeline uses encoded PowerShell legitimately",
        "added": "2024-03-15",
        "review_date": "2024-09-15",
        "risk": "Attacker compromising svc_deploy would evade rule",
    },
]

def add_tuning_exception(rule_kql: str, exclusion_clause: str, log_entry: dict) -> str:
    """Append a where exclusion clause and log the tuning decision."""
    tuned_kql = rule_kql + f"\n| where not ({exclusion_clause})"
    TUNING_LOG.append(log_entry)
    return tuned_kql

tuned = add_tuning_exception(
    "SecurityEvent | where EventID == 4688",
    "Account in ('svc_deploy')",
    {"rule_id": "rule-001", "exclusion": "Account in ('svc_deploy')", "reason": "CI/CD pipeline"}
)
print(tuned)
