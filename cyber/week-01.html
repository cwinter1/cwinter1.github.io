Concept 1 — The OSI Model: Layers as Pipeline Stages

The OSI model describes how data travels from an application on one machine to an application on another. It has 7 layers, each responsible for one job. Think of it like a data pipeline: raw bytes at the bottom, business-meaningful messages at the top, with transformation happening at every layer in between.

The 4 layers you will interact with daily as a detection engineer:

  • Layer 3 (Network) — IP addresses, routing. Analogous to the table/partition that holds your data.
  • Layer 4 (Transport) — TCP/UDP ports, connections. Analogous to the query that selects specific rows from that table.
  • Layer 6/7 (Application) — HTTP, DNS, TLS. The actual payload — what the connection is doing.

A firewall operates at Layer 3/4 (block this IP, block this port). An IDS operates at Layer 7 (inspect the actual content of the request).

Example:

When your browser loads https://example.com:

Layer 7 (Application):  HTTP GET request
Layer 6 (Presentation): TLS encryption wraps the HTTP
Layer 4 (Transport):    TCP segment, destination port 443
Layer 3 (Network):      IP packet, destination IP 93.184.216.34
Layer 2 (Data Link):    Ethernet frame with MAC addresses
Layer 1 (Physical):     Electrical signals on the wire

Each layer adds a header when sending (encapsulation).
Each layer strips its header when receiving (decapsulation).

Exercise: Open a terminal and run: traceroute google.com (Linux/Mac) or tracert google.com (Windows). Each line is one router hop at Layer 3. Count the hops and note the IP addresses.

Expected output: 10–20 lines, each showing a hop number, latency (ms), and an IP address or hostname.

Concept 2 — TCP vs UDP: Reliable vs Fast

TCP is the delivery service that requires a signature — it confirms every packet arrived and retransmits lost ones. UDP is a flyer dropped in the mailbox — sent once, no confirmation.

Data engineering analogy: TCP is like a transactional database write (ACID — confirmed delivery). UDP is like a fire-and-forget Kafka producer with no acks.

Why it matters for detection:

  • Most attacks use TCP (HTTP, HTTPS, SSH, SMB) because they need reliable data transfer.
  • DNS uses UDP by default (small queries, fast). DNS over large UDP or DNS using TCP is a red flag — possibly DNS tunneling.
  • Attackers who use UDP for C2 often rely on custom protocols precisely because UDP is less inspected.

The TCP three-way handshake (SYN → SYN-ACK → ACK) is the "connection established" event. A flood of SYN packets with no follow-up ACK = SYN flood denial-of-service attack.

Example:

# Capture TCP SYN packets on your local machine (requires root/admin)
# On Linux:
sudo tcpdump -i eth0 "tcp[tcpflags] & tcp-syn != 0" -c 10

# What you see:
# 10:23:41 IP 192.168.1.5.54321 > 142.250.80.46.443: Flags [S]
# The [S] flag = SYN (connection initiation)
# If you only see [S] and never [S.] (SYN-ACK) back, the host may be down or filtered

Exercise: In Wireshark, open a capture on your active network interface. Filter with tcp.flags.syn == 1 && tcp.flags.ack == 0. Browse to any website. Identify the SYN packets your browser sends.

Expected output: Wireshark rows showing your machine's IP as source, destination port 443 or 80, Flags column showing [SYN].

Concept 3 — Ports and Services: The Address Within the Address

An IP address identifies a machine. A port identifies the service on that machine. Think of it like a BigQuery dataset (the machine) versus a table name (the port) — both are needed to reach the data.

Well-known ports every detection engineer memorizes:

Port Protocol Normal use Detection note
22 SSH Remote admin Brute force, tunneling
53 DNS Name resolution Tunneling, DGA
80 HTTP Web Unencrypted C2, malware download
443 HTTPS Secure web Encrypted C2 (most common)
445 SMB Windows file sharing Ransomware, lateral movement
3389 RDP Remote desktop Brute force, ransomware entry
4444 — Nothing legitimate Metasploit default listener

Connections to uncommon ports (e.g., 8443, 4444, 31337) or on protocols that don't match (e.g., HTTP traffic on port 8080 identified as something else by DPI) are detection-worthy.

Example:

# On Linux — show all active TCP connections with ports
ss -tnp

# Output:
# State    Recv-Q  Send-Q  Local Address:Port   Peer Address:Port
# ESTAB    0       0       192.168.1.5:54210    142.250.80.46:443
# ESTAB    0       0       192.168.1.5:54221    52.114.128.10:443
# LISTEN   0       128     0.0.0.0:22           0.0.0.0:*

Exercise: Run ss -tnp (Linux) or netstat -ano (Windows) on your machine. Find all ESTABLISHED connections. For each connection, look up the destination port in the table above. Note any port that is not 80 or 443.

Expected output: A list of active connections. At minimum you should see connections to port 443. Any connection to port 445 (SMB) externally would be suspicious on a home machine.

Concept 1 — IP Addresses: Public vs Private

An IPv4 address is 32 bits written as four octets (e.g., 192.168.1.100). Think of it like a row in a BigQuery table: the network part is the partition key (which network), the host part is the row ID (which machine).

Private IP ranges (RFC 1918) — these addresses are not routable on the public internet:

  • 10.0.0.0/8 — large corporate networks
  • 172.16.0.0/12 — medium networks
  • 192.168.0.0/16 — home and small office networks

Detection relevance: If you see traffic from a 10.x.x.x source in your perimeter firewall logs, that traffic is already inside your network — it skipped your internet-facing controls. That is always worth investigating.

Example:

import ipaddress

def is_private(ip_str: str) -> bool:
    return ipaddress.ip_address(ip_str).is_private

test_ips = [
    "192.168.1.100",   # private — internal host
    "10.0.0.55",       # private — internal host
    "8.8.8.8",         # public — Google DNS
    "203.0.113.5",     # public — external host
]

for ip in test_ips:
    print(f"{ip:20s}  private={is_private(ip)}")

Concept 2 — CIDR and Subnets: Filtering by Network Range


CIDR notation (e.g., 192.168.1.0/24) defines a network range. The /24 means the first 24 bits are the network part — leaving 8 bits for hosts (256 addresses, 254 usable).


Data engineering analogy: CIDR is a WHERE clause on an IP range. WHERE ip BETWEEN '192.168.1.0' AND '192.168.1.255' is the same as checking membership in 192.168.1.0/24. The Python ipaddress module does this natively.


In detection, you often need to:


    

  • Check if a source IP belongs to a known-good corporate subnet (allowlist)
    • 

  • Flag traffic to/from known-bad CIDR blocks (blocklist)
    • 

  • Identify traffic crossing subnet boundaries (lateral movement indicator)
    • 



Example:


import ipaddress

corporate_subnets = [
    ipaddress.ip_network("10.10.0.0/16"),    # HQ network
    ipaddress.ip_network("10.20.0.0/16"),    # Branch network
]

def is_corporate(ip_str: str) -> bool:
    addr = ipaddress.ip_address(ip_str)
    return any(addr in net for net in corporate_subnets)

test_ips = ["10.10.5.22", "10.20.100.3", "185.220.101.5"]
for ip in test_ips:
    label = "CORPORATE" if is_corporate(ip) else "EXTERNAL"
    print(f"{ip:20s}  {label}")

Concept 3 — Routing and NAT: Why You Rarely See Real Source IPs


When a packet leaves a corporate network, NAT (Network Address Translation) rewrites the source IP from the internal private address to the public IP of the gateway. This means your perimeter firewall logs show the router's public IP as the source of all outbound traffic — not the individual workstation.


This creates a fundamental detection gap: if you only have perimeter logs, you cannot see which internal host made a suspicious connection. You need internal network logs (east-west traffic) or endpoint logs (EDR, Sysmon) to correlate the internal source.


Think of it like a data warehouse where all rows from a source system are stamped with the ETL job ID instead of the original transaction ID — you lose granularity unless you also capture the source system's own logs.


Example:


Scenario: Workstation 10.10.5.22 connects to malicious IP 185.220.101.5

What perimeter firewall sees:
  Source IP:  203.0.113.10 (company's public IP — the NAT gateway)
  Dest IP:    185.220.101.5
  Dest Port:  443

What you CANNOT determine from firewall logs alone:
  - Which internal workstation made the connection
  - What process on that workstation initiated it

What you CAN determine from internal DNS + proxy logs:
  - 10.10.5.22 resolved bad-domain.com → 185.220.101.5 at 10:23:40
  - 10.10.5.22 made an HTTPS connection to 185.220.101.5 at 10:23:41

Concept 1 — How DNS Works: The Query Chain


DNS translates human-readable domain names (google.com) into IP addresses (142.250.80.46). Think of it like a BigQuery lookup table JOIN — you have a name, you need the underlying address to route your query.


The resolution chain:


    

  1. Your machine checks its local cache
    2. 

  2. Asks the local resolver (usually your router or corporate DNS server)
    3. 

  3. The resolver asks a Root nameserver (knows where .com lives)
    4. 

  4. Then the TLD nameserver (knows where google.com lives)
    5. 

  5. Then Google's authoritative nameserver (returns the actual IP)
    6. 



Why DNS is gold for detection:


    

  • Every connection starts with a DNS query (usually)
    • 

  • DNS logs show you what domains a machine is trying to reach — even before a connection is established
    • 

  • DNS queries happen in plaintext on port 53 UDP — easy to inspect and log
    • 

  • Malware almost always makes DNS queries — it needs to find its C2 server
    • 



Example:


# Perform a manual DNS lookup and see all records
dig google.com ANY

# See the full resolution chain (who answered what)
dig +trace google.com

# Query a specific DNS server directly
dig @8.8.8.8 google.com A

# Check if a domain has a bad reputation by querying a DNS blocklist
# NXDOMAIN response = not listed, any IP response = listed
dig malware-domain.com.zen.spamhaus.org A

Exercise:

Concept 2 — DNS as an Attack Vector: Tunneling and DGA


Two critical DNS attack patterns every detection engineer must recognize:


DNS Tunneling: Encoding data inside DNS query names to exfiltrate data or establish C2 over port 53 (which is almost always allowed through firewalls). The domain query looks like aGVsbG8gd29ybGQ.evil.com — the subdomain is base64-encoded data.


Data engineering analogy: DNS tunneling is like hiding a full CSV file inside a column that's supposed to only contain a short string. The column passes schema validation (it's still a string) but the content is completely different from what's expected.


DGA (Domain Generation Algorithm): Malware generates hundreds of random-looking domain names daily from a seed algorithm. The attacker registers a few of them. The malware queries all of them until it finds one that resolves. This makes blocklisting nearly impossible — you can't blocklist what you don't know in advance.


Example:


import re
from collections import Counter

# Simple heuristic: high-entropy subdomains suggest DNS tunneling
def subdomain_entropy(domain: str) -> float:
    import math
    subdomain = domain.split(".")[0]  # take the leftmost label
    freq = Counter(subdomain)
    length = len(subdomain)
    return -sum((c/length) * math.log2(c/length) for c in freq.values())

domains = [
    "www.google.com",               # normal
    "mail.company.com",             # normal
    "aGVsbG8gd29ybGQ.evil.com",    # base64 tunnel
    "xkj29fmqpwz.malware.net",     # DGA-like
]

for d in domains:
    entropy = subdomain_entropy(d)
    flag = "SUSPICIOUS" if entropy > 3.5 else "normal"
    print(f"{d:40s}  entropy={entropy:.2f}  {flag}")

import pandas as pd

# Simulated DNS log data
dns_logs = pd.DataFrame({
    "timestamp": ["2024-01-15 10:00:01", "2024-01-15 10:00:31",
                  "2024-01-15 10:01:01", "2024-01-15 10:01:31",
                  "2024-01-15 10:02:01"],
    "client_ip":  ["10.10.5.22"] * 5,
    "query":      ["evil-c2.net", "evil-c2.net", "evil-c2.net",
                   "evil-c2.net", "evil-c2.net"],
    "rcode":      ["NOERROR"] * 5,
})

# Detect beaconing: same domain, same host, regular intervals
dns_logs["timestamp"] = pd.to_datetime(dns_logs["timestamp"])
dns_logs["interval"] = dns_logs.groupby(["client_ip","query"])["timestamp"].diff().dt.seconds

print(dns_logs[["client_ip","query","interval"]])
print(f"\nMean interval: {dns_logs['interval'].mean():.0f}s — consistent beaconing pattern")

Concept 1 — HTTP Request and Response Structure


HTTP is the language browsers and servers use to communicate. As a detection engineer you need to read raw HTTP traffic the same way you read a log file — every field is a potential indicator.


An HTTP request has:


    

  • Method: GET (fetch), POST (send data), PUT, DELETE
    • 

  • URL path: what resource is being requested
    • 

  • Host header: which domain (crucial — one IP can serve many domains)
    • 

  • User-Agent: what client software is making the request (easily spoofed by malware)
    • 

  • Body: data sent with POST requests (login forms, file uploads, C2 check-ins)
    • 



Data engineering analogy: An HTTP request is like a function call with named parameters. The URL is the function name. The headers are keyword arguments. The body is the data payload.


Example:


POST /c2/checkin HTTP/1.1
Host: evil-c2.net
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Content-Type: application/json
Content-Length: 87

{"hostname":"WORKSTATION-05","user":"jsmith","pid":4821,"interval":30}

Detection notes:
- POST to /c2/checkin — path contains "c2" literally (rare in legitimate apps)
- User-Agent looks like a browser but the path is not a browser request
- JSON body contains hostname/user/pid — classic implant beacon structure
- interval:30 — the malware is telling the server to expect check-ins every 30 seconds

Concept 2 — TLS: Encryption That Still Leaks Metadata


TLS encrypts the HTTP body and headers — the content of the request is hidden. But TLS itself leaves observable metadata:


    

  • SNI (Server Name Indication): the domain name sent in plaintext during TLS handshake, before encryption — visible in logs even for HTTPS traffic
    • 

  • Certificate: the server's certificate contains the domain name, issuer, and validity period — self-signed certs are suspicious
    • 

  • JA3 fingerprint: a hash of the TLS handshake parameters (cipher suites, extensions, elliptic curves). Different clients produce different JA3 hashes — malware often has a unique JA3 even when using port 443
    • 

  • Certificate transparency logs: all publicly-issued certificates are logged — you can search for domains issued in the last 24 hours to find attacker infrastructure
    • 



Data engineering analogy: TLS is like encrypting a Parquet file — the contents are hidden, but the file metadata (schema, created_by, row count) is still readable in the file footer.


Example:


# Extract SNI from a PCAP without decrypting the traffic
tshark -r capture.pcap -Y "tls.handshake.type == 1" \
  -T fields -e ip.src -e ip.dst -e tls.handshake.extensions_server_name

# Output:
# 10.10.5.22    185.220.101.5    evil-c2.net
# 10.10.5.22    142.250.80.46    www.google.com

# Even though traffic is encrypted, SNI reveals the destination domain

Concept 3 — User-Agent Strings and HTTP Anomalies


The User-Agent header identifies the client software. Browsers send long, standardized User-Agent strings. Malware often:


    

  • Uses a hardcoded fake browser User-Agent (detectable by mismatch with other headers)
    • 

  • Uses an empty or minimal User-Agent
    • 

  • Uses a consistent, unique string across all C2 beacons
    • 



Detection approach — flag these HTTP anomalies:


    

  • POST requests with no Referer header (browsers almost always include one for user-initiated POSTs)
    • 

  • Requests where the User-Agent says "Chrome" but the Accept-Language or Accept-Encoding headers are missing (browsers always send these)
    • 

  • Regular interval POSTs to the same URL (beaconing)
    • 

  • Very consistent byte sizes across multiple requests (C2 heartbeat with fixed payload)
    • 



Example:


import re
from collections import Counter

proxy_logs = [
    {"ua": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36", "has_accept": True},
    {"ua": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36", "has_accept": False},
    {"ua": "python-requests/2.28.0", "has_accept": False},
    {"ua": "", "has_accept": False},
]

for log in proxy_logs:
    is_browser_ua = "Mozilla" in log["ua"] or "AppleWebKit" in log["ua"]
    suspicious = is_browser_ua and not log["has_accept"]
    print(f"UA: {log['ua'][:50]:50s}  suspicious={suspicious}")

Concept 1 — Capturing Traffic: Wireshark and tcpdump


A PCAP (packet capture) file contains the raw bytes of every packet that passed through a network interface during a capture window. Think of it like a raw event log before any transformation — the ground truth.


Wireshark is the GUI tool: visual, color-coded, easy to apply display filters and follow streams.
tcpdump is the CLI tool: fast, scriptable, used for capturing on remote servers where you have no GUI.


Both use the same underlying libpcap library and produce the same PCAP file format.


As a detection engineer, you use PCAPs to:


    

  • Validate that a detection rule fires correctly on real traffic
    • 

  • Investigate alerts by examining the raw traffic around the event time
    • 

  • Build example data for writing and testing new detection rules
    • 



Example:


# tcpdump — capture 100 packets on interface eth0, save to file
sudo tcpdump -i eth0 -c 100 -w capture.pcap

# tcpdump — capture only HTTP traffic (port 80) to a specific host
sudo tcpdump -i eth0 host 185.220.101.5 and port 80 -w suspicious.pcap

# tcpdump — capture DNS queries only
sudo tcpdump -i eth0 port 53 -w dns.pcap

# Read a PCAP file and display in human-readable format
tcpdump -r capture.pcap -n

# Display packet contents in ASCII (useful for spotting plaintext C2)
tcpdump -r capture.pcap -A -n

Concept 2 — Wireshark Filters: Finding the Signal in the Noise


Wireshark has two filter systems: capture filters (BPF syntax, applied during capture) and display filters (Wireshark syntax, applied after capture). Display filters are more powerful and are what you use for analysis.


Data engineering analogy: Capture filters are like partitioning your data lake — you only write certain data at ingestion time. Display filters are like WHERE clauses on already-captured data.


Essential display filters for detection work:


# Show only DNS queries
dns

# Show only HTTP POST requests
http.request.method == "POST"

# Show traffic to/from a specific IP
ip.addr == 185.220.101.5

# Show TCP SYN packets (connection attempts)
tcp.flags.syn == 1 and tcp.flags.ack == 0

# Show packets with a specific string in the payload
frame contains "password"

# Show TLS with specific SNI
tls.handshake.extensions_server_name contains "evil"

# Show large DNS queries (possible tunneling)
dns and frame.len > 512

Example:


Scenario: You have a 10,000-packet PCAP from a suspected compromised host.

Step 1: Apply filter  ip.src == 10.10.5.22
  → reduces to ~3,000 packets (traffic from the suspicious host)

Step 2: Apply filter  ip.src == 10.10.5.22 and not ip.dst == 192.168.1.1
  → excludes gateway traffic (gateway is the router) → ~800 packets

Step 3: Apply filter  ip.src == 10.10.5.22 and http
  → shows only HTTP → 45 packets, all POSTing to the same URL every 30 seconds

Conclusion: confirmed beaconing pattern

Concept 3 — Python PCAP Parsing with scapy


Wireshark is great for interactive analysis, but automating analysis of hundreds of PCAPs requires scripting. The scapy library reads PCAP files and exposes each packet as a Python object you can filter, aggregate, and write to CSV — exactly like working with rows in a DataFrame.


Example:


from scapy.all import rdpcap, IP, TCP, UDP, DNS, DNSQR

packets = rdpcap("capture.pcap")

results = []
for pkt in packets:
    if IP in pkt:
        row = {
            "src_ip":   pkt[IP].src,
            "dst_ip":   pkt[IP].dst,
            "protocol": "TCP" if TCP in pkt else "UDP" if UDP in pkt else "OTHER",
            "src_port": pkt[TCP].sport if TCP in pkt else (pkt[UDP].sport if UDP in pkt else None),
            "dst_port": pkt[TCP].dport if TCP in pkt else (pkt[UDP].dport if UDP in pkt else None),
        }
        results.append(row)

import csv
with open("parsed_packets.csv", "w", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=results[0].keys())
    writer.writeheader()
    writer.writerows(results)

print(f"Parsed {len(results)} IP packets → parsed_packets.csv")
