Concept 1 — Threat Modeling vs. Vulnerability Assessment

Vulnerability assessment answers: "what weaknesses exist in our systems?" Threat modeling answers: "what attacks are most likely against our specific environment, and which should we detect first?"

Detection engineering starts with threat modeling because you cannot write rules for everything. A 500-technique ATT&CK matrix with no prioritization produces a backlog that never gets finished. Threat modeling narrows the field to the techniques most relevant to your industry, adversary profile, and asset inventory.

The STRIDE model (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) maps cleanly to ATT&CK tactics: Spoofing → Initial Access / Defense Evasion, Tampering → Persistence / Impact, Repudiation → Defense Evasion (log clearing), Information Disclosure → Collection / Exfiltration, DoS → Impact, Elevation of Privilege → Privilege Escalation.

Data engineering analogy: threat modeling is the requirements-gathering phase before building a pipeline. You would not build ingestion infrastructure for every possible data source — you prioritize based on business value. Detection is the same: prioritize based on attacker likelihood and business impact.

Example:

from dataclasses import dataclass, field
from typing import List

@dataclass
class ThreatModel:
    environment: str
    industry: str
    crown_jewels: List[str]          # high-value assets
    primary_adversary_profiles: List[str]  # e.g. ["ransomware", "APT", "insider"]
    relevant_techniques: List[str] = field(default_factory=list)

    def summarize(self) -> str:
        return (
            f"Environment: {self.environment} | Industry: {self.industry}\n"
            f"Crown jewels: {', '.join(self.crown_jewels)}\n"
            f"Adversary profiles: {', '.join(self.primary_adversary_profiles)}\n"
            f"Relevant techniques: {len(self.relevant_techniques)}"
        )

model = ThreatModel(
    environment="corporate Windows AD + Azure",
    industry="financial services",
    crown_jewels=["Active Directory", "payment processing DB", "customer PII store"],
    primary_adversary_profiles=["ransomware", "APT financial", "insider threat"],
    relevant_techniques=["T1078", "T1003", "T1486", "T1071", "T1021"],
)
print(model.summarize())

Concept 2 — Asset-Centric Prioritization


Not all assets carry equal detection value. A domain controller compromise enables full network takeover; a developer workstation compromise is serious but limited. Prioritizing detection coverage by asset criticality ensures that the highest-value targets get the deepest rule coverage first.


Asset tiers:


    

  • Tier 1 (Crown Jewel): domain controllers, PKI servers, payment systems, prod databases — detect everything
    • 

  • Tier 2 (Critical): jump hosts, build servers, admin workstations — detect lateral movement and privilege escalation
    • 

  • Tier 3 (Standard): end-user workstations — detect initial access and execution
    • 



Each detection rule should be tagged with the asset tiers it covers. A rule that only fires on Tier 3 assets is lower priority to develop than one covering Tier 1 assets.


Data engineering analogy: SLA tiers in a data pipeline — Tier 1 tables have real-time monitoring and PagerDuty alerts; Tier 3 tables have daily checks and email reports. Same concept applied to detection coverage.


Example:


from enum import IntEnum
from dataclasses import dataclass
from typing import List

class AssetTier(IntEnum):
    CROWN_JEWEL = 1
    CRITICAL = 2
    STANDARD = 3

@dataclass
class Asset:
    name: str
    tier: AssetTier
    detection_techniques: List[str] = None

    def __post_init__(self):
        if self.detection_techniques is None:
            self.detection_techniques = []

    def coverage_required(self) -> str:
        requirements = {
            AssetTier.CROWN_JEWEL: "full ATT&CK coverage + behavioral baselines",
            AssetTier.CRITICAL: "lateral movement + privilege escalation coverage",
            AssetTier.STANDARD: "initial access + execution coverage",
        }
        return requirements[self.tier]

assets = [
    Asset("dc01.corp.local", AssetTier.CROWN_JEWEL),
    Asset("jump-host-01", AssetTier.CRITICAL),
    Asset("dev-workstation-42", AssetTier.STANDARD),
]

for asset in assets:
    print(f"{asset.name} (Tier {asset.tier.value}): {asset.coverage_required()}")

Concept 3 — Detection Requirements Document


A detection requirements document (DRD) defines what a detection must do before implementation begins. Writing the DRD prevents scope creep, ensures the right log sources are available, and provides a pass/fail acceptance test when the rule is reviewed.


Minimum DRD fields:


    

  • Technique: ATT&CK technique ID and name
    • 

  • Scenario: specific attacker behavior being detected (not the general technique)
    • 

  • Trigger condition: what exact event combination fires the alert
    • 

  • Log source required: what logs must be ingested (Sysmon event 1, Windows Security 4624, etc.)
    • 

  • False positive expected: known benign events that match
    • 

  • Acceptance test: how to verify the rule fires on a known-malicious sample
    • 



Data engineering analogy: a DRD is the same as a data contract — it specifies schema, SLA, and acceptance criteria before the pipeline is built.


Example:


from dataclasses import dataclass
from typing import List

@dataclass
class DetectionRequirement:
    rule_id: str
    technique_id: str
    technique_name: str
    scenario: str
    trigger_condition: str
    log_sources: List[str]
    false_positives: List[str]
    acceptance_test: str
    tier_coverage: List[int]  # which asset tiers this covers

    def to_markdown(self) -> str:
        tiers = ", ".join(f"Tier {t}" for t in self.tier_coverage)
        fps = "\n".join(f"  - {fp}" for fp in self.false_positives)
        sources = ", ".join(self.log_sources)
        return f"""## {self.rule_id}: {self.technique_name} ({self.technique_id})
**Scenario:** {self.scenario}
**Trigger:** {self.trigger_condition}
**Log sources:** {sources}
**False positives:**
{fps}
**Acceptance test:** {self.acceptance_test}
**Asset coverage:** {tiers}"""

drd = DetectionRequirement(
    rule_id="DRD-001",
    technique_id="T1059.001",
    technique_name="PowerShell Execution",
    scenario="Encoded PowerShell command executed from non-admin context",
    trigger_condition="Process: powershell.exe with CommandLine containing '-enc' or '-EncodedCommand'",
    log_sources=["Sysmon Event ID 1", "Windows Security 4688"],
    false_positives=["IT admin scripts", "Software deployment tools (SCCM, Intune)"],
    acceptance_test="Run 'powershell -enc aQBlAHgA' on test host; alert must fire within 30 seconds",
    tier_coverage=[1, 2, 3],
)
print(drd.to_markdown())

Concept 1 — Coverage Matrix Construction


An ATT&CK coverage matrix maps your existing detection rules to the techniques they cover. It reveals which techniques have no coverage (gaps), which have one rule (single point of failure), and which have multiple overlapping rules (robust coverage).


Coverage levels per technique:


    

  • 0 — No coverage: no rule exists; attacker executes technique undetected
    • 

  • 1 — Partial: a rule exists but only covers one sub-technique or one log source
    • 

  • 2 — Good: rule covers the main scenario with validated false positive tuning
    • 

  • 3 — Robust: multiple rules from different data sources; behavioral + signature coverage
    • 



Building the matrix requires two inputs: a list of your deployed rules (with technique tags) and the full ATT&CK technique list for your scope. The gap is every technique in the full list not covered by any deployed rule.


Example:


from dataclasses import dataclass
from typing import List, Dict
from collections import defaultdict

@dataclass
class DeployedRule:
    rule_id: str
    title: str
    techniques: List[str]   # ATT&CK technique IDs
    data_sources: List[str]
    status: str             # "production" | "experimental" | "disabled"

def build_coverage_matrix(
    rules: List[DeployedRule],
    technique_scope: List[str],
) -> Dict[str, dict]:
    coverage: Dict[str, dict] = {}
    technique_to_rules: Dict[str, List[str]] = defaultdict(list)

    for rule in rules:
        if rule.status == "production":
            for technique in rule.techniques:
                technique_to_rules[technique].append(rule.rule_id)

    for technique in technique_scope:
        rule_ids = technique_to_rules.get(technique, [])
        count = len(rule_ids)
        coverage[technique] = {
            "rule_count": count,
            "rules": rule_ids,
            "level": 0 if count == 0 else (1 if count == 1 else (2 if count == 2 else 3)),
        }
    return coverage

rules = [
    DeployedRule("SIG-001", "PowerShell Encoded Command", ["T1059.001"], ["Sysmon"], "production"),
    DeployedRule("SIG-002", "LSASS Access", ["T1003.001"], ["Sysmon"], "production"),
    DeployedRule("SIG-003", "Scheduled Task Creation", ["T1053.005"], ["Windows Security"], "production"),
    DeployedRule("BEH-001", "Rare Process Execution", ["T1059.001", "T1204.002"], ["Sysmon"], "production"),
]

scope = ["T1059.001", "T1003.001", "T1053.005", "T1078", "T1021.001", "T1204.002"]
matrix = build_coverage_matrix(rules, scope)

for technique, data in matrix.items():
    print(f"{technique}: level={data['level']} | rules={data['rules'] or 'NONE'}")

Concept 2 — Gap Analysis Methodology


A gap analysis compares your current coverage matrix against a target coverage model. The target model defines what coverage level you need for each technique based on your threat model.


Gap analysis steps:


    

  1. Define target coverage level per technique (from your threat model and asset tiers)
    2. 

  2. Subtract actual coverage from target coverage to get the gap score
    3. 

  3. Sort by gap score descending — the top of the list is your detection backlog
    4. 

  4. For each gap, estimate effort (hours) to close it based on log source availability
    5. 



Gap scoring formula:


gap_score = (target_level - actual_level) × asset_tier_weight

Where asset_tier_weight = 3 for Tier 1, 2 for Tier 2, 1 for Tier 3.


A Tier 1 technique with zero coverage targeting target level 3 scores (3-0) × 3 = 9 — highest urgency.


Example:


from dataclasses import dataclass
from typing import Dict

@dataclass
class TechniqueTarget:
    technique_id: str
    target_level: int
    asset_tier: int

def gap_analysis(
    coverage_matrix: Dict[str, dict],
    targets: list[TechniqueTarget],
) -> list[dict]:
    gaps = []
    tier_weights = {1: 3, 2: 2, 3: 1}

    for target in targets:
        tid = target.technique_id
        actual = coverage_matrix.get(tid, {}).get("level", 0)
        gap = target.target_level - actual
        if gap > 0:
            weight = tier_weights.get(target.asset_tier, 1)
            gaps.append({
                "technique": tid,
                "actual_level": actual,
                "target_level": target.target_level,
                "gap": gap,
                "asset_tier": target.asset_tier,
                "gap_score": gap * weight,
            })

    return sorted(gaps, key=lambda x: x["gap_score"], reverse=True)

targets = [
    TechniqueTarget("T1059.001", target_level=3, asset_tier=1),
    TechniqueTarget("T1003.001", target_level=3, asset_tier=1),
    TechniqueTarget("T1053.005", target_level=2, asset_tier=2),
    TechniqueTarget("T1078",     target_level=3, asset_tier=1),
    TechniqueTarget("T1021.001", target_level=2, asset_tier=2),
    TechniqueTarget("T1204.002", target_level=2, asset_tier=3),
]

# Use the coverage_matrix from Concept 1 (rebuild inline here for standalone execution)
from collections import defaultdict
coverage_matrix_example = {
    "T1059.001": {"level": 3},
    "T1003.001": {"level": 1},
    "T1053.005": {"level": 1},
    "T1078":     {"level": 0},
    "T1021.001": {"level": 0},
    "T1204.002": {"level": 1},
}

gaps = gap_analysis(coverage_matrix_example, targets)
for g in gaps:
    print(f"{g['technique']}: gap={g['gap']} | score={g['gap_score']} | tier={g['asset_tier']}")

Concept 3 — Navigator Layer JSON


The ATT&CK Navigator is the standard tool for visualizing coverage. It reads a JSON layer file where each technique has a score and an optional color. You can generate Navigator layers programmatically from your coverage matrix.


A Navigator layer JSON has this structure:


{
  "name": "Coverage Layer",
  "versions": {"attack": "14", "navigator": "4.9"},
  "domain": "enterprise-attack",
  "techniques": [
    {"techniqueID": "T1059.001", "score": 3, "color": "#00ff00"},
    {"techniqueID": "T1078",     "score": 0, "color": "#ff0000"}
  ]
}

Score colors: 0 = red (no coverage), 1 = orange, 2 = yellow, 3 = green. This gives SOC leadership an at-a-glance coverage picture during monthly reviews.


Example:


import json
from typing import Dict

SCORE_COLORS = {
    0: "#ff4444",   # red — no coverage
    1: "#ff9900",   # orange — partial
    2: "#ffee00",   # yellow — good
    3: "#66cc44",   # green — robust
}

def generate_navigator_layer(
    coverage_matrix: Dict[str, dict],
    layer_name: str = "Detection Coverage",
) -> dict:
    techniques = []
    for technique_id, data in coverage_matrix.items():
        level = data.get("level", 0)
        techniques.append({
            "techniqueID": technique_id,
            "score": level,
            "color": SCORE_COLORS[level],
            "comment": f"Rules: {len(data.get('rules', []))}",
            "enabled": True,
        })

    return {
        "name": layer_name,
        "versions": {"attack": "14", "navigator": "4.9"},
        "domain": "enterprise-attack",
        "description": f"Auto-generated coverage layer: {len(techniques)} techniques",
        "techniques": techniques,
        "gradient": {"colors": ["#ff4444", "#66cc44"], "minValue": 0, "maxValue": 3},
    }

coverage_sample = {
    "T1059.001": {"level": 3, "rules": ["SIG-001", "BEH-001"]},
    "T1003.001": {"level": 1, "rules": ["SIG-002"]},
    "T1078":     {"level": 0, "rules": []},
}

layer = generate_navigator_layer(coverage_sample, "SOC Coverage — Q2 2024")
print(json.dumps(layer, indent=2))

Concept 1 — Detection Backlog as a Product Backlog


Detection engineering teams that work without a structured backlog ship rules reactively — after incidents — rather than proactively covering known threats. Treating the detection backlog like a software product backlog (with priority scores, story points, acceptance criteria, and sprint assignments) brings the same velocity improvements that engineering teams get from Agile.


Each backlog item is a detection requirement (from W12 Day 1) plus:


    

  • Priority score: calculated from gap analysis (Day 2 Concept 2)
    • 

  • Effort estimate: hours to write, test, tune, and deploy the rule
    • 

  • Status: backlog / in-progress / review / deployed / tuning
    • 

  • Sprint: which sprint it is assigned to (if using 2-week cycles)
    • 

  • Dependencies: log sources that must be available before work can start
    • 



Data engineering analogy: a data platform backlog has pipeline requests with business value estimates and engineering effort. Detection backlog items are the same structure — value (risk reduction) vs. cost (engineering hours).


Example:


from dataclasses import dataclass, field
from typing import Optional
from enum import Enum

class BacklogStatus(str, Enum):
    BACKLOG = "backlog"
    IN_PROGRESS = "in_progress"
    REVIEW = "review"
    DEPLOYED = "deployed"
    TUNING = "tuning"

@dataclass
class BacklogItem:
    item_id: str
    technique_id: str
    title: str
    priority_score: float       # from gap analysis gap_score
    effort_hours: int
    status: BacklogStatus = BacklogStatus.BACKLOG
    sprint: Optional[int] = None
    log_source_available: bool = True
    assignee: Optional[str] = None

    def roi_score(self) -> float:
        """Risk reduction per engineering hour."""
        return round(self.priority_score / max(self.effort_hours, 1), 3)

backlog = [
    BacklogItem("DET-012", "T1078",     "Valid Account Detection — AD",  9, 16),
    BacklogItem("DET-013", "T1003.001", "LSASS Dump — Behavioral",       6, 12),
    BacklogItem("DET-014", "T1021.001", "Lateral Movement via RDP",       4,  8),
    BacklogItem("DET-015", "T1204.002", "User Execution Malicious File",  1,  8),
]

sorted_backlog = sorted(backlog, key=lambda x: x.roi_score(), reverse=True)
for item in sorted_backlog:
    print(f"{item.item_id} | {item.technique_id} | ROI={item.roi_score()} | {item.effort_hours}h")

Concept 2 — MoSCoW Prioritization for Detections


MoSCoW (Must Have / Should Have / Could Have / Won't Have) is a simple qualitative prioritization framework. It complements the quantitative gap score by adding business context: regulatory requirements force certain detections into "Must Have" regardless of ROI score.


Detection MoSCoW mapping:


    

  • Must Have: regulatory compliance (PCI-DSS requires detecting T1078 account abuse), active incident response requirements, Tier 1 asset coverage
    • 

  • Should Have: high gap score techniques not covered by compliance requirements
    • 

  • Could Have: medium gap score, coverage improvement from L1 to L2
    • 

  • Won't Have (this sprint): Tier 3-only techniques with low gap scores, log source not yet available
    • 



Combining MoSCoW with ROI score: Must-Have items go to sprint 1 regardless of ROI. Within each MoSCoW bucket, order by ROI score.


Example:


from dataclasses import dataclass
from enum import Enum
from typing import List

class MoSCoW(str, Enum):
    MUST = "Must Have"
    SHOULD = "Should Have"
    COULD = "Could Have"
    WONT = "Won't Have"

@dataclass
class PrioritizedItem:
    item_id: str
    technique_id: str
    title: str
    moscow: MoSCoW
    roi_score: float

def prioritize_by_moscow(items: List[PrioritizedItem]) -> dict:
    result = {bucket: [] for bucket in MoSCoW}
    for item in items:
        result[item.moscow].append(item)
    for bucket in result:
        result[bucket].sort(key=lambda x: x.roi_score, reverse=True)
    return result

items = [
    PrioritizedItem("DET-012", "T1078",     "Valid Account",        MoSCoW.MUST,   0.562),
    PrioritizedItem("DET-013", "T1003.001", "LSASS Dump",           MoSCoW.MUST,   0.500),
    PrioritizedItem("DET-014", "T1021.001", "RDP Lateral Movement", MoSCoW.SHOULD, 0.500),
    PrioritizedItem("DET-015", "T1204.002", "User Exec File",       MoSCoW.COULD,  0.125),
    PrioritizedItem("DET-016", "T1566.001", "Spearphishing Link",   MoSCoW.SHOULD, 0.350),
]

prioritized = prioritize_by_moscow(items)
for bucket, bucket_items in prioritized.items():
    print(f"\n{bucket.value}:")
    for i in bucket_items:
        print(f"  {i.item_id}: {i.title} (ROI={i.roi_score})")

Concept 3 — Dependency Tracking for Detection Work


Detection work has dependencies that stall progress when not tracked explicitly. The three most common blockers:


    

  1. Log source not available: a Sigma rule is written, but the log source was never configured — the rule cannot be tested or deployed
    2. 

  2. Infrastructure dependency: a new SIEM workspace needs to be provisioned before queries can be deployed
    3. 

  3. Baseline dependency: a behavioral detection requires 30 days of baseline data before it can fire
    4. 



Tracking dependencies on each backlog item prevents sprint planning failures where 40% of sprint items are immediately blocked. The dependency check runs before sprint planning: blocked items are automatically pushed to a future sprint after their dependency resolves.


Example:


from dataclasses import dataclass, field
from typing import List, Optional

@dataclass
class Dependency:
    dep_id: str
    description: str
    resolved: bool = False
    blocker_type: str = "log_source"  # "log_source" | "infrastructure" | "baseline"

@dataclass
class BacklogItemWithDeps:
    item_id: str
    technique_id: str
    title: str
    roi_score: float
    dependencies: List[Dependency] = field(default_factory=list)

    def is_blocked(self) -> bool:
        return any(not dep.resolved for dep in self.dependencies)

    def blocking_deps(self) -> List[str]:
        return [dep.description for dep in self.dependencies if not dep.resolved]

items = [
    BacklogItemWithDeps(
        "DET-012", "T1078", "Valid Account Detection", roi_score=0.562,

Concept 1 — Signal-to-Noise Ratio and Alert Fidelity


A detection rule that fires constantly with mostly false positives is worse than no rule: it trains analysts to ignore alerts, creates alert fatigue, and masks real detections in the noise. Signal-to-noise ratio (SNR) measures the proportion of true positive alerts vs. total alerts for a given rule.


SNR = true_positives / (true_positives + false_positives)

Target SNR thresholds:


    

  • Production rule: SNR ≥ 0.80 (at most 1 in 5 alerts is a false positive)
    • 

  • Experimental rule: SNR ≥ 0.50 acceptable during tuning
    • 

  • Below 0.20: rule must be disabled or fundamentally redesigned
    • 



Alert volume also matters independently: a rule with SNR=0.90 that fires 1,000 times per day still generates 100 false positives daily. Alert volume × SNR = analyst workload.


Data engineering analogy: SNR is the same as data quality score — precision and recall applied to a detection pipeline instead of a ML model.


Example:


from dataclasses import dataclass
from typing import List

@dataclass
class RuleMetrics:
    rule_id: str
    title: str
    true_positives: int
    false_positives: int
    total_alerts_30d: int

    def snr(self) -> float:
        total = self.true_positives + self.false_positives
        if total == 0:
            return 0.0
        return round(self.true_positives / total, 3)

    def daily_fp_volume(self) -> float:
        return round(self.false_positives / 30, 1)

    def status(self) -> str:
        s = self.snr()
        if s >= 0.80:
            return "PRODUCTION"
        elif s >= 0.50:
            return "TUNING"
        else:
            return "DISABLE"

rules = [
    RuleMetrics("SIG-001", "PowerShell Encoded",    tp=45, fp=5,   total_alerts_30d=50),
    RuleMetrics("SIG-003", "Scheduled Task",        tp=12, fp=88,  total_alerts_30d=100),
    RuleMetrics("BEH-001", "Rare Process Exec",     tp=8,  fp=2,   total_alerts_30d=10),
]

for r in rules:
    print(f"{r.rule_id}: SNR={r.snr()} | daily FPs={r.daily_fp_volume()} | {r.status()}")

Concept 2 — Mean Time to Detect (MTTD) and Mean Time to Respond (MTTR)


MTTD measures the average time between an attacker beginning a technique and the first alert firing. MTTR measures from alert creation to incident containment. These are the two most important SOC KPIs tracked by leadership and reported to compliance auditors.


MTTD has two components:


    

  • Detection latency: time between the malicious event and the alert firing (a rule running every 15 minutes has a minimum 15-minute detection latency)
    • 

  • Triage latency: time between alert creation and an analyst beginning investigation
    • 



Reducing MTTD: run high-fidelity critical rules in real-time (streaming) rather than on a schedule; ensure Tier 1 alerts bypass the queue and go directly to an analyst.


Data engineering analogy: MTTD is pipeline SLA latency. A batch pipeline running every 4 hours has a maximum data freshness SLA of 4 hours. Real-time streaming pipelines bring SLA to seconds — but at higher cost.


Example:


from dataclasses import dataclass
from datetime import datetime, timedelta
from typing import List

@dataclass
class IncidentTimeline:
    incident_id: str
    attack_start: datetime
    first_alert: datetime
    analyst_begin: datetime
    contained: datetime

    def mttd_minutes(self) -> float:
        return (self.first_alert - self.attack_start).total_seconds() / 60

    def triage_lag_minutes(self) -> float:
        return (self.analyst_begin - self.first_alert).total_seconds() / 60

    def mttr_minutes(self) -> float:
        return (self.contained - self.attack_start).total_seconds() / 60

Concept 3 — Detection Coverage Score


A coverage score is a single number that summarizes the quality of your detection program for a given time period. It combines breadth (how many techniques covered) and depth (coverage level) into a normalized 0–100 score for executive reporting.


coverage_score = Σ(actual_level / max_level × technique_weight) / Σ(technique_weights) × 100

Where technique_weight = asset_tier_weight × technique_prevalence_weight. A Tier 1 technique with high attacker prevalence has the highest weight.


A coverage score above 70 indicates a mature detection program. Below 40 indicates reactive-only detection. Tracking the score monthly shows program improvement or regression.


Example:


from dataclasses import dataclass
from typing import List, Dict

MAX_COVERAGE_LEVEL = 3

@dataclass
class WeightedTechnique:
    technique_id: str
    asset_tier_weight: int   # 3=T1, 2=T2, 1=T3
    prevalence_weight: int   # 1–5 (5 = commonly exploited in wild)
    actual_level: int        # 0–3

    def weight(self) -> float:
        return self.asset_tier_weight * self.prevalence_weight

    def contribution(self) -> float:
        return (self.actual_level / MAX_COVERAGE_LEVEL) * self.weight()

def coverage_score(techniques: List[WeightedTechnique]) -> float:
    total_possible = sum(t.weight() for t in techniques)
    achieved = sum(t.contribution() for t in techniques)
    return round((achieved / total_possible) * 100, 1) if total_possible > 0 else 0.0

techniques = [
    WeightedTechnique("T1059.001", asset_tier_weight=3, prevalence_weight=5, actual_level=3),
    WeightedTechnique("T1003.001", asset_tier_weight=3, prevalence_weight=5, actual_level=1),
    WeightedTechnique("T1078",     asset_tier_weight=3, prevalence_weight=4, actual_level=0),
    WeightedTechnique("T1053.005", asset_tier_weight=2, prevalence_weight=3, actual_level=1),
    WeightedTechnique("T1021.001", asset_tier_weight=2, prevalence_weight=4, actual_level=0),
    WeightedTechnique("T1204.002", asset_tier_weight=1, prevalence_weight=3, actual_level=1),
]

score = coverage_score(techniques)
print(f"Detection Coverage Score: {score}/100")

Concept 1 — Building a Coverage Dashboard in Python


A coverage dashboard aggregates all metrics computed in Days 2–4 into a single report: matrix coverage levels, gap scores, SNR by rule, MTTD/MTTR trends, coverage score. The dashboard is a Python script that reads your rule repository and generates a markdown report file.


The output format for a detection program dashboard:


    

  1. Executive summary: coverage score, MTTD, MTTR
    2. 

  2. Coverage matrix: technique-by-technique table
    3. 

  3. Gap report: prioritized backlog with effort estimates
    4. 

  4. Rule health: SNR and alert volume per deployed rule
    5. 

  5. Trend line: coverage score month-over-month
    6. 



A Python-generated markdown report can be committed to the rules repository alongside the Sigma rules, making coverage reporting part of the CI pipeline (automatically regenerated on every merge).

from typing import List, Dict
from datetime import date

@dataclass
class DashboardData:
    report_date: date
    coverage_score: float
    mean_mttd_minutes: float
    mean_mttr_minutes: float
    techniques: List[dict]   # each: {id, level, rule_count}
    rules: List[dict]        # each: {id, title, snr, daily_fp}
    top_gaps: List[dict]     # each: {technique, gap_score, effort_hours}

def render_markdown_report(data: DashboardData) -> str:
    lines = [
        f"# Detection Coverage Report — {data.report_date}",
        "",
        "## Executive Summary",
        f"| Metric | Value |",
        f"|--------|-------|",
        f"| Coverage Score | {data.coverage_score}/100 |",
        f"| Mean MTTD | {data.mean_mttd_minutes:.1f} min |",
        f"| Mean MTTR | {data.mean_mttr_minutes:.1f} min |",
        "",
        "## Coverage Matrix",
        "| Technique | Level | Rules |",
        "|-----------|-------|-------|",
    ]
    for t in data.techniques:
        bar = "█" * t["level"] + "░" * (3 - t["level"])
        lines.append(f"| {t['id']} | {bar} ({t['level']}/3) | {t['rule_count']} |")

    lines += [
        "",
        "## Top Gaps (Prioritized Backlog)",
        "| Technique | Gap Score | Est. Hours |",
        "|-----------|-----------|------------|",
    ]
    for g in data.top_gaps:
        lines.append(f"| {g['technique']} | {g['gap_score']} | {g['effort_hours']}h |")

    lines += [
        "",
        "## Rule Health",
        "| Rule ID | Title | SNR | Daily FPs |",
        "|---------|-------|-----|-----------|",
    ]
    for r in data.rules:
        health = "GOOD" if r["snr"] >= 0.80 else ("TUNE" if r["snr"] >= 0.50 else "DISABLE")
        lines.append(f"| {r['id']} | {r['title']} | {r['snr']} ({health}) | {r['daily_fp']} |")

    return "\n".join(lines)

Concept 2 — Automated Gap Report Generation


The gap report is the most actionable output of the coverage process. It answers the question a detection engineering manager needs every sprint: "what should the team work on next and why?" Automating gap report generation from the rules repository eliminates manual tracking and ensures the report is always current.


Gap report automation pipeline:


    

  1. Read all Sigma rules from the rules/ directory
    2. 

  2. Parse technique IDs from each rule's tags field
    3. 

  3. Aggregate into a coverage matrix (same as Day 2 Concept 1)
    4. 

  4. Run gap analysis against target model
    5. 

  5. Write GAP_REPORT.md to the repository root
    6. 



This pipeline runs as a GitHub Actions job on every PR merge to the main branch, keeping the gap report fresh without any manual steps.


Example:


import os
from pathlib import Path
from typing import List, Dict
from datetime import date

def extract_technique_from_tag(tag: str) -> str | None:
    """Convert 'attack.t1059_001' → 'T1059.001'"""
    if not tag.startswith("attack.t"):
        return None
    raw = tag.replace("attack.t", "T").replace("_", ".")
    parts = raw.split(".")
    if len(parts) == 2:
        return f"T{parts[0][1:]}.{parts[1]}"
    return raw

def parse_sigma_tags(rule_text: str) -> List[str]:
    """Extract technique IDs from a Sigma rule YAML string."""
    techniques = []
    in_tags = False
    for line in rule_text.splitlines():
        stripped = line.strip()
        if stripped == "tags:":
            in_tags = True
            continue
        if in_tags:
            if stripped.startswith("- "):
                tag = stripped[2:]
                tech = extract_technique_from_tag(tag)
                if tech:
                    techniques.append(tech)
            elif not stripped.startswith("-") and ":" in stripped:
                break
    return techniques

sample_rule_yaml = """
title: PowerShell Encoded Command
tags:
    - attack.execution
    - attack.t1059_001
logsource:
    category: process_creation
detection:
    selection:
        CommandLine|contains: '-enc'
    condition: selection
"""

techniques = parse_sigma_tags(sample_rule_yaml)
print(f"Extracted techniques: {techniques}")

def generate_gap_report_from_rules_dir(
    rules_dir: str,
    target_techniques: List[str],
    output_path: str,
) -> int:
    """Parse all .yml files in rules_dir, build matrix, write GAP_REPORT.md."""
    covered: Dict[str, int] = {}
    rules_path = Path(rules_dir)

    if rules_path.exists():
        for rule_file in rules_path.glob("**/*.yml"):
            text = rule_file.read_text(encoding="utf-8")
            for tech in parse_sigma_tags(text):
                covered[tech] = covered.get(tech, 0) + 1

    gaps = [t for t in target_techniques if t not in covered or covered[t] == 0]

    lines = [
        f"# Detection Gap Report — {date.today()}",
        f"",
        f"Techniques in scope: {len(target_techniques)}",
        f"Techniques with coverage: {len(target_techniques) - len(gaps)}",
        f"Gaps (no coverage): {len(gaps)}",
        "",
        "## Uncovered Techniques",
        "| Technique | Status |",
        "|-----------|--------|",
    ]
    for t in sorted(gaps):
        lines.append(f"| {t} | NO COVERAGE |")

    Path(output_path).write_text("\n".join(lines), encoding="utf-8")
    return len(gaps)

gap_count = generate_gap_report_from_rules_dir(
    rules_dir="rules/",
    target_techniques=["T1059.001", "T1003.001", "T1078", "T1021.001", "T1053.005"],
    output_path="GAP_REPORT.md",
)
print(f"Gap report written. {gap_count} uncovered techniques.")

Concept 3 — Stakeholder Reporting and Communication


Detection engineers own technical execution; stakeholders own budget, headcount, and risk acceptance. Translating coverage metrics into business risk language is a critical skill that separates a detection engineer from a detection engineering leader.


Stakeholder communication principles:


    

  1. Lead with risk, not technique IDs: "An attacker who steals valid credentials (T1078) is undetectable for an average of 45 minutes" is more actionable than "T1078 gap score = 9"
    2. 

  2. Quantify the gap in business terms: if mean dwell time for ransomware is 14 days without detection, and your coverage closes that to 2 days, you can estimate the cost reduction
    3. 

  3. One ask per report: each report should have a single, specific action requested of the stakeholder — not a list of ten problems
    4. 



The three-section stakeholder report structure:


    

  1. Status: where we are (coverage score, MTTD, MTTR)
    2. 

  2. Risk: what the gaps mean in business terms (specific attack scenario + estimated dwell time)
    3. 

  3. Ask: one concrete decision or resource request
    4.
