Concept 1 — What ATT&CK Is and Why It Matters

MITRE ATT&CK (Adversarial Tactics, Techniques, and Common Knowledge) is a publicly maintained knowledge base of real-world attacker behavior. It organizes over 600 techniques into 14 tactics — the "why" behind each action. Every technique is documented with: how it works, which threat actors use it, how to detect it, and how to mitigate it.

Before ATT&CK, detection teams wrote rules based on isolated indicators (block this IP, block this hash). ATT&CK shifted the field to behavior-based detection: instead of blocking a specific tool, detect the behavior (e.g., "process injecting into another process") that works against any tool implementing that technique.

Data engineering analogy: ATT&CK is like a data quality rule catalog. Instead of writing a one-off check for each dataset, you categorize quality issues (completeness, accuracy, timeliness) and apply a systematic framework. ATT&CK does the same for attacker behavior — categorize the technique, then build detection coverage systematically.

The 14 tactics in order (roughly matching the attack lifecycle):

  1. Reconnaissance, 2. Resource Development, 3. Initial Access, 4. Execution,
  2. Persistence, 6. Privilege Escalation, 7. Defense Evasion, 8. Credential Access,
  3. Discovery, 10. Lateral Movement, 11. Collection, 12. Command and Control,
  4. Exfiltration, 14. Impact

Example:

Tactic:    Execution (TA0002)
Technique: Command and Scripting Interpreter (T1059)
Sub-technique: PowerShell (T1059.001)

What it means:
  Attacker runs PowerShell to execute their payload.

Real-world example:
  PowerShell used to download and run Cobalt Strike beacon:
  powershell.exe -nop -w hidden -enc <base64_payload>

Detection idea:
  Sysmon Event ID 1 (Process Create):
    Image contains powershell.exe
    CommandLine contains -EncodedCommand or -enc
    ParentImage is NOT a known management tool (mmc.exe, etc.)

Concept 2 — Tactics vs Techniques vs Sub-Techniques

The ATT&CK hierarchy has three levels:

  • Tactic — the goal (WHY). Example: Credential Access. The attacker wants to obtain usernames and passwords.
  • Technique — the method (HOW). Example: T1003 OS Credential Dumping. The attacker dumps credentials from the operating system.
  • Sub-technique — the specific implementation. Example: T1003.001 LSASS Memory. The attacker specifically reads from the lsass.exe process.

This hierarchy matters for detection design. A detection rule targeting a sub-technique is highly specific (low false positives, but misses variants). A detection rule targeting the technique or tactic is broader (more coverage, potentially higher false positives).

Data engineering analogy: tactics are like data quality dimensions (accuracy, completeness, timeliness). Techniques are like specific quality categories (duplicate records, null values, stale data). Sub-techniques are like specific checks (null in column X, duplicate on key Y). You need rules at multiple levels — specific rules for high-confidence alerts, broad rules for hypothesis generation.

Example:

Tactic:         Credential Access (TA0006)
  Technique:    OS Credential Dumping (T1003)
    Sub-tech:   LSASS Memory (T1003.001)  ← Mimikatz sekurlsa
    Sub-tech:   Security Account Manager (T1003.002)  ← reg save / VSS
    Sub-tech:   NTDS (T1003.003)  ← ntdsutil, VSS on DC
    Sub-tech:   LSA Secrets (T1003.004)  ← reg query HKLM\SECURITY
    Sub-tech:   DCSync (T1003.006)  ← fake DC replication via drsuapi

  Technique:    Brute Force (T1110)
    Sub-tech:   Password Spraying (T1110.003)  ← W04 Day 1 Concept 3
    Sub-tech:   Credential Stuffing (T1110.004)

# Detection at technique level: any of these triggers "Credential Access"
# Detection at sub-technique level: only the specific behavior triggers the alert

Concept 3 — Detection Coverage: What You Can and Cannot See

Not every ATT&CK technique is detectable from every log source. A technique like T1140 (Deobfuscate/Decode Files) leaves traces in PowerShell Script Block Logging (if enabled) but not in network logs. T1071.001 (HTTP C2) is visible in web proxy logs but not in Windows Security logs.

Coverage mapping is the practice of: for each ATT&CK technique you care about, documenting which data sources you have, which log sources those map to, and whether your current rules cover the technique. The gaps are your detection backlog.

Example:

Concept 1 — ATT&CK Navigator: The Coverage Map Tool

ATT&CK Navigator (mitre-attack.github.io/attack-navigator) is a web app that lets you create color-coded heat maps over the ATT&CK matrix. You use it to:

  • Visualize which techniques your detection rules cover
  • Map a threat actor's known techniques to see your coverage against that specific adversary
  • Share coverage maps with stakeholders as a prioritized improvement plan

You interact with Navigator by uploading a "layer" — a JSON file that assigns scores and colors to techniques. A score of 1 (green) means you have a detection. A score of 0 (red) means no coverage. You can layer multiple views: one for your detections, one for a threat actor, and compare.

Data engineering analogy: ATT&CK Navigator is like a dbt docs coverage report or a Great Expectations validation report — a visual dashboard showing which parts of the system are tested (covered) and which are not. The layer JSON file is the data behind the visualization, exactly like a test results JSON that feeds a CI/CD dashboard.

Example:

    "techniques": [
        {
            "techniqueID": "T1059.001",
            "score": 1,
            "color": "#4caf50",
            "comment": "Covered by Sysmon EID 1 + PowerShell EID 4104"
        },
        {
            "techniqueID": "T1003.001",

Concept 3 — Building the Navigator Layer JSON (Royal Road)


The W05 Royal Road is a Python script that reads a coverage CSV and outputs a valid ATT&CK Navigator layer JSON file. This is the foundation of the coverage dashboard built in W12.


Example:


# coverage.csv format:
# technique_id,covered,data_source,notes
# T1059.001,1,Sysmon EID 1,PowerShell detection via process creation
# T1003.001,1,Sysmon EID 10,lsass access detection
# T1071.001,0,,No proxy deployed

import csv
import json
from pathlib import Path

LAYER_TEMPLATE = {
    "name": "",
    "versions": {"attack": "14", "navigator": "4.9.1", "layer": "4.5"},
    "domain": "enterprise-attack",
    "description": "",
    "techniques": [],
    "gradient": {"colors": ["#f44336", "#ff9800", "#4caf50"], "minValue": 0, "maxValue": 1},
    "legendItems": [
        {"label": "Covered",     "color": "#4caf50"},
        {"label": "Partial",     "color": "#ff9800"},
        {"label": "No coverage", "color": "#f44336"},
    ]
}

def csv_to_navigator(csv_path: str, layer_name: str, out_path: str) -> dict:
    layer = {**LAYER_TEMPLATE, "name": layer_name}
    techniques = []
    with open(csv_path) as f:
        for row in csv.DictReader(f):
            score = int(row.get("covered", 0))
            color = "#4caf50" if score == 1 else "#f44336"
            techniques.append({
                "techniqueID": row["technique_id"],
                "score": score,
                "color": color,
                "comment": row.get("notes", ""),
            })
    layer["techniques"] = techniques
    Path(out_path).write_text(json.dumps(layer, indent=2))
    return layer

Concept 1 — Mapping Existing Rules to ATT&CK


The first step in building a detection program is understanding what you already have. Every existing alert or SIEM rule should be tagged with the ATT&CK technique it detects. This creates an inventory: "we have 47 rules, covering 23 unique techniques across 8 tactics."


Most SIEM rules are written without ATT&CK tags. Retroactively tagging them reveals: duplication (3 rules for the same technique), coverage gaps, and tactic-level blind spots.


Data engineering analogy: this is like a data lineage audit. You trace every dashboard metric back to its source table. Some metrics come from three different tables (duplication). Some business questions have no source table at all (gaps). The audit map drives prioritization.


Example:


# Existing SIEM rules inventory (before ATT&CK tagging):
rules = [
    {"rule_id": "R001", "name": "PowerShell encoded command",    "tags": []},
    {"rule_id": "R002", "name": "LSASS access by non-system",    "tags": []},
    {"rule_id": "R003", "name": "Net.exe domain group query",     "tags": []},
    {"rule_id": "R004", "name": "Failed logon spike",             "tags": []},
    {"rule_id": "R005", "name": "Scheduled task created via schtasks", "tags": []},
]

# After tagging:
tagged_rules = [
    {"rule_id": "R001", "name": "PowerShell encoded command",    "tags": ["T1059.001"]},
    {"rule_id": "R002", "name": "LSASS access by non-system",    "tags": ["T1003.001"]},
    {"rule_id": "R003", "name": "Net.exe domain group query",     "tags": ["T1069.002"]},
    {"rule_id": "R004", "name": "Failed logon spike",             "tags": ["T1110.003", "T1110.001"]},
    {"rule_id": "R005", "name": "Scheduled task created",         "tags": ["T1053.005"]},
]

# Compute coverage:
all_covered = {t for r in tagged_rules for t in r["tags"]}
print(f"Unique techniques covered: {len(all_covered)}")
# → Unique techniques covered: 5

Concept 2 — Prioritizing the Detection Backlog


You cannot build detections for all 600+ ATT&CK techniques simultaneously. Prioritization uses three inputs:


    

  1. Threat intelligence — which techniques are used by adversaries targeting your sector?
    2. 

  2. Data availability — which techniques can you detect with your current log sources?
    3. 

  3. Risk — what is the business impact if the technique succeeds without detection?
    4. 



A simple scoring formula: priority_score = (threat_relevance × data_availability × impact) / effort


Data engineering analogy: this is the same prioritization framework used for data quality fixes. You focus first on quality issues that affect high-value datasets (impact), that you actually have data to detect (availability), and where you have had incidents before (threat relevance).


Example:


# Detection backlog prioritization:
backlog = [
    {
        "technique_id": "T1078",
        "name": "Valid Accounts",
        "threat_relevance": 9,   # APT34 uses this heavily
        "data_available": 8,     # Azure AD logs available
        "impact": 9,             # Full account takeover
        "effort": 3,             # Moderate to build
    },
    {
        "technique_id": "T1071.004",
        "name": "DNS C2",
        "threat_relevance": 7,
        "data_available": 4,     # DNS logs not centralized
        "impact": 8,
        "effort": 7,             # Hard — need DNS parser
    },
]

for item in backlog:
    score = (item["threat_relevance"] * item["data_available"] * item["impact"]) / item["effort"]
    item["priority_score"] = round(score, 1)

# Sort by priority:
backlog.sort(key=lambda x: x["priority_score"], reverse=True)
for item in backlog:
    print(f"{item['technique_id']}: {item['priority_score']} — {item['name']}")
# → T1078: 216.0 — Valid Accounts  (high priority)
# → T1071.004: 32.0 — DNS C2       (low priority until DNS logs available)

Concept 3 — Sigma Rules as ATT&CK-Tagged Detections


A Sigma rule is a vendor-neutral detection rule format. It describes what to detect in YAML, independent of any specific SIEM. The sigma-cli tool compiles Sigma rules into KQL (for Sentinel), SPL (for Splunk), or Elasticsearch queries. Every Sigma rule includes ATT&CK technique IDs in its tags — this is how Sigma and ATT&CK connect.


Data engineering analogy: Sigma rules are like dbt tests written in a portable format. Just as dbt tests can be compiled to run against multiple SQL engines (Snowflake, BigQuery, DuckDB), Sigma rules compile to multiple SIEM query languages. The rule logic is written once; the target engine is specified at compile time.


Example:


# sigma/rules/windows/process_creation/proc_creation_powershell_encoded.yml
title: PowerShell Encoded Command Execution
status: stable
description: Detects PowerShell execution with -EncodedCommand parameter — commonly used to hide payload content
author: Detection Team
date: 2024/01/15
tags:
    - attack.execution
    - attack.t1059.001
logsource:
    category: process_creation
    product: windows
detection:
    selection:
        Image|endswith: '\powershell.exe'
        CommandLine|contains:
            - '-EncodedCommand'
            - '-enc '
            - '-ec '
    condition: selection
falsepositives:
    - Legitimate administrative scripts using encoding for special characters
level: medium

Concept 1 — The Attack Chain: Mapping an Intrusion to ATT&CK


Real attacks use multiple techniques in sequence. Mapping an intrusion to ATT&CK after the fact turns a confusing series of events into a structured narrative. Each event in the timeline corresponds to one ATT&CK technique — a detective process that reveals both what happened and what you missed.


Data engineering analogy: mapping an incident to ATT&CK is like root-cause analysis on a failed pipeline run. You start with the symptom (data quality issue) and trace backwards through the execution graph until you find the root cause (broken transformation, missing source data). ATT&CK gives you the vocabulary to describe each step in the attack "pipeline" precisely.


Example:


Incident Timeline → ATT&CK Mapping:

2024-01-15 08:45  User bob receives phishing email with malicious attachment
  → T1566.001 (Spearphishing Attachment)

2024-01-15 08:51  bob opens attachment → macro runs PowerShell
  → T1204.002 (Malicious File) + T1059.001 (PowerShell)

2024-01-15 08:52  PowerShell downloads and runs beacon from C2 server
  → T1105 (Ingress Tool Transfer) + T1071.001 (HTTP C2)

2024-01-15 09:03  Beacon runs whoami, net group, arp -a, systeminfo
  → T1033 (System Owner/User Discovery)
  → T1069.002 (Domain Groups Discovery)
  → T1016 (System Network Configuration Discovery)

2024-01-15 09:15  Lateral movement to finance server via Pass-the-Hash
  → T1550.002 (Pass the Hash)

2024-01-15 10:30  Attacker archives financial data to encrypted ZIP
  → T1560.001 (Archive via Utility)

2024-01-15 10:45  ZIP exfiltrated via HTTPS to cloud storage provider
  → T1567.002 (Exfiltration to Cloud Storage)

Concept 2 — Emulation Plans: Testing Your Detections


ATT&CK Evaluations and MITRE's Center for Threat-Informed Defense publish attacker emulation plans — step-by-step scripts that simulate a specific threat actor's behavior on a test system. Running an emulation plan against your environment tells you whether your detections fire correctly before a real attacker tests them for you.


Free tools for emulation:


    

  • Atomic Red Team (atomicredteam.io) — one YAML file per ATT&CK technique, each with a safe test command
    • 

  • Caldera (caldera.mitre.org) — automated multi-step emulation engine
    • 



Data engineering analogy: emulation plans are integration tests for your detection pipeline. Just as you run a test ETL job with synthetic data to verify your pipeline produces the correct output, you run an emulation test to verify your detection rules fire when the technique occurs.


Example:


# Atomic Red Team — running test for T1059.001 PowerShell:
# (on a test Windows machine — never on production)

# Install:
Install-Module -Name invoke-atomicredteam
Import-Module invoke-atomicredteam

# List available tests for T1059.001:
Invoke-AtomicTest T1059.001 -ShowDetailsBrief

# Run test 1 (PowerShell encoded command):
Invoke-AtomicTest T1059.001 -TestNumbers 1

# Check if your Sysmon + SIEM rule fired:
# Event Viewer → Windows PowerShell → Operational → look for EID 4104

Concept 3 — Purple Teaming: Offense and Defense Working Together


Purple teaming is the practice of running attacker simulations (red team) while the defense (blue team) watches in real time to tune detections. The red team executes a technique; the blue team watches the logs; if the detection does not fire, they tune the rule together.


Unlike traditional red team (attacker vs. defender, no collaboration), purple team exercises maximize detection coverage improvement per hour of effort.


Example:


Purple Team Exercise Structure:

Step 1: Select technique
  → T1547.001 (Registry Run Keys / Startup Folder — persistence)

Step 2: Red team executes (on a test VM):
  reg add "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v "Test" /d "C:\Temp\test.exe" /f

Step 3: Blue team observes:
  → Sysmon EID 13 (Registry Value Set) fires?
  → If yes: alert details correct? (TargetObject, Details, Image all accurate?)
  → If no: why not? Is the Sysmon config missing registry monitoring? Is the rule wrong?

Step 4: Tune:
  → Add missing Sysmon filter
  → Update Sigma rule to catch this variant
  → Re-run the test — does it fire now?

Step 5: Document:
  → Technique covered, data source, rule version, test date
  → Add to coverage CSV (feeds Navigator layer)

Concept 1 — Reading ATT&CK STIX Data Programmatically


ATT&CK publishes its data as STIX 2.0 JSON at github.com/mitre/cti. The enterprise-attack.json file contains all techniques, tactics, groups, and software. Parsing it lets you build tools that automatically look up technique metadata without manual lookups.


Data engineering analogy: the ATT&CK STIX file is like a dimension table dump from a reference data API. You download it once, parse it into a local lookup dict, and JOIN it against your operational data (coverage CSV, incident logs) to enrich with metadata.


Example:


import json
from pathlib import Path

def load_attack_stix(path: str) -> dict[str, dict]:
    with open(path) as f:
        bundle = json.load(f)
    techniques = {}
    for obj in bundle.get("objects", []):
        if obj.get("type") != "attack-pattern":
            continue
        ext_refs = obj.get("external_references", [])
        tech_id = next(
            (r["external_id"] for r in ext_refs if r.get("source_name") == "mitre-attack"),
            None
        )
        if not tech_id:
            continue
        kill_chain = obj.get("kill_chain_phases", [])
        tactic = kill_chain[0]["phase_name"] if kill_chain else "unknown"
        techniques[tech_id] = {
            "id":          tech_id,
            "name":        obj.get("name", ""),
            "tactic":      tactic,
            "description": obj.get("description", "")[:200],
            "deprecated":  obj.get("x_mitre_deprecated", False),
        }
    return techniques

Concept 2 — Generating the Navigator Layer from Coverage Data


Combining the coverage CSV, the ATT&CK STIX metadata, and the Navigator layer format from Day 2 Concept 3 into a single CLI script produces the W05 Royal Road artifact.


Example:


# pipeline/w05_coverage_map.py

import csv
import json
import argparse
from pathlib import Path

def load_coverage(csv_path: str) -> list[dict]:
    with open(csv_path) as f:
        return list(csv.DictReader(f))

def build_layer(coverage: list[dict], name: str) -> dict:
    techniques = []
    for row in coverage:
        score = int(row.get("covered", 0))
        techniques.append({
            "techniqueID": row["technique_id"],
            "score":   score,
            "color":   "#4caf50" if score == 1 else "#f44336",
            "comment": row.get("notes", ""),
        })
    return {
        "name":       name,
        "versions":   {"attack": "14", "navigator": "4.9.1", "layer": "4.5"},
        "domain":     "enterprise-attack",
        "techniques": techniques,
        "gradient":   {"colors": ["#f44336", "#4caf50"], "minValue": 0, "maxValue": 1},
    }

if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--coverage", required=True)
    ap.add_argument("--name",     default="My Coverage")
    ap.add_argument("--output",   default="coverage_layer.json")
    args = ap.parse_args()

    cov = load_coverage(args.coverage)
    layer = build_layer(cov, args.name)
    Path(args.output).write_text(json.dumps(layer, indent=2))
    covered = sum(1 for r in cov if int(r.get("covered", 0)) == 1)
    print(f"Coverage: {covered}/{len(cov)} techniques → {args.output}")

Concept 3 — Threat Actor Coverage: How Well Do You Cover APT34?


The final piece of the Royal Road: compare your coverage layer against a threat actor's known technique list. This generates a "readiness score" against a specific adversary — a metric that maps directly to security program maturity.


Example:


APT34_TECHNIQUES = [
    "T1566.001", "T1059.001", "T1078", "T1071.001",
    "T1105", "T1003.001", "T1070.004", "T1041",
    "T1053.005", "T1082", "T1016", "T1033",
]

def apt_coverage(coverage_csv: str, apt_techniques: list[str]) -> dict:
    with open(coverage_csv) as f:
        rows = {r["technique_id"]: int(r.get("covered", 0))
                for r in csv.DictReader(f)}
    covered   = [t for t in apt_techniques if rows.get(t, 0) == 1]
    uncovered = [t for t in apt_techniques if rows.get(t, 0) == 0]
    return {
        "actor":        "APT34",
        "total":        len(apt_techniques),
        "covered":      len(covered),
        "uncovered":    uncovered,
        "coverage_pct": round(len(covered) / len(apt_techniques) * 100, 1),
    }

result = apt_coverage("coverage.csv", APT34_TECHNIQUES)
print(f"APT34 readiness: {result['coverage_pct']}% ({result['covered']}/{result['total']})")
print(f"Gaps: {result['uncovered']}")
