Concept 1 — What Detection-as-Code Means

Detection-as-Code (DaC) applies software engineering practices to detection rules: version control, code review, automated testing, and deployment pipelines. Instead of writing KQL directly in the Sentinel UI and forgetting it, you manage rules in a Git repository with the same discipline as application code.

Core principles:

  1. All rules live in version control — Git is the source of truth, not the SIEM UI
  2. Rules are reviewed before merging — pull request with peer review catches logic errors
  3. CI validates every change — automated tests run on every commit
  4. Deployment is automated — no manual clicking in the SIEM portal
  5. Changes are auditable — git log shows who changed what and why

Data engineering analogy: DaC is exactly what dbt does for SQL transformations. dbt put SQL models into Git with tests and CI. DaC does the same for detection rules. The mental model is identical.

Example:

from dataclasses import dataclass

@dataclass
class SigmaRuleMeta:
    title: str
    id: str
    status: str              # experimental | test | stable
    severity: str            # informational | low | medium | high | critical
    tactics: list[str]
    techniques: list[str]
    
    def is_valid(self) -> list[str]:
        errors = []
        valid_statuses = {"experimental", "test", "stable"}
        valid_severities = {"informational", "low", "medium", "high", "critical"}
        if self.status not in valid_statuses:
            errors.append(f"Invalid status: {self.status}")
        if self.severity not in valid_severities:
            errors.append(f"Invalid severity: {self.severity}")
        if not self.techniques:
            errors.append("At least one ATT&CK technique required")
        return errors

Concept 2 — Git Workflow for Detection Rules


Detection rules follow the same Git branching model as application code. The key difference is that a bad merge can create a detection gap (missed attack) or alert fatigue (noise storm) — both have real security consequences.


Standard workflow:


    

  1. Create a branch: git checkout -b detection/T1059.001-powershell-encoded
    2. 

  2. Write the Sigma rule YAML
    3. 

  3. Run local validation: sigma check rule.yml
    4. 

  4. Open a pull request
    5. 

  5. CI runs automatically: lint + test + compile to KQL
    6. 

  6. Peer review (second analyst reads the rule logic)
    7. 

  7. Merge → auto-deploy to Sentinel
    8. 



Commit message conventions for detection rules:


    

  • feat(detection): add T1059.001 PowerShell encoded command rule
    • 

  • fix(detection): tune brute force threshold from 5 to 10 to reduce FP
    • 

  • chore(detection): deprecate legacy rule replaced by T1003.001-v2
    •

import subprocess

def run_git_command(args: list[str]) -> tuple[int, str]:
    result = subprocess.run(["git"] + args, capture_output=True, text=True)
    return result.returncode, result.stdout.strip()

def get_changed_rule_files() -> list[str]:
    """Return list of Sigma YAML files changed in the current branch vs main."""
    _, diff_output = run_git_command(["diff", "--name-only", "main", "HEAD"])
    changed = [
        line for line in diff_output.splitlines()
        if line.startswith("rules/") and line.endswith(".yml")
    ]
    return changed

# Simulate pySigma compilation without the library installed
import yaml
import re

def compile_sigma_to_kql_simple(rule_yaml: str) -> str:
    """
    Minimal Sigma → KQL compiler for process_creation rules.
    Handles contains and endswith modifiers only.
    """
    rule = yaml.safe_load(rule_yaml)
    detection = rule.get("detection", {})
    conditions = []
    
    for sel_name, sel_body in detection.items():
        if sel_name == "condition":
            continue
        if not isinstance(sel_body, dict):
            continue
        for field_spec, values in sel_body.items():
            field, _, modifier = field_spec.partition("|")
            kql_field = {"CommandLine": "CommandLine", "Image": "NewProcessName"}.get(field, field)
            vals = values if isinstance(values, list) else [values]
            if modifier == "contains":
                parts = [f'{kql_field} contains "{v}"' for v in vals]
                conditions.append("(" + " or ".join(parts) + ")")
            elif modifier == "endswith":
                parts = [f'{kql_field} endswith "{v}"' for v in vals]
                conditions.append("(" + " or ".join(parts) + ")")
    
    where_clause = " or ".join(conditions) if conditions else "true"
    return f"SecurityEvent\n| where EventID == 4688\n| where {where_clause}"

sigma_rule = """
title: Test Rule
detection:
  selection:
    CommandLine|contains:
      - mimikatz
      - sekurlsa
  condition: selection
"""
print(compile_sigma_to_kql_simple(sigma_rule))

Concept 1 — Why Detection Rules Need Tests


A detection rule without tests is a guess. Tests verify:


    

  1. True positive coverage — the rule fires when the attack occurs
    2. 

  2. False negative prevention — the rule fires on all relevant attack variants
    3. 

  3. False positive rate — the rule does NOT fire on known-good activity
    4. 

  4. Field existence — all referenced fields exist in the log source schema
    5. 



In software terms: true positive = feature works; false negative = regression; false positive = spurious alert.


Detection tests are analogous to unit tests for a function: you provide known input (a log event), assert the expected output (alert fired or not), and run them automatically on every change.


Example:


import unittest
from dataclasses import dataclass
from typing import Callable

@dataclass
class DetectionTestCase:
    name: str
    event: dict
    should_fire: bool
    description: str

def test_detection_rule(
    rule_fn: Callable[[dict], bool],
    test_cases: list[DetectionTestCase],
) -> dict:
    results = {"pass": 0, "fail": 0, "failures": []}
    for tc in test_cases:
        fired = rule_fn(tc.event)
        if fired == tc.should_fire:
            results["pass"] += 1
        else:
            results["fail"] += 1
            results["failures"].append({
                "test": tc.name,
                "expected": tc.should_fire,
                "got": fired,
                "description": tc.description,
            })
    return results

Concept 2 — Atomic Red Team and Test Data Generation


Atomic Red Team (by Red Canary) is a library of small, focused attack simulations mapped to ATT&CK techniques. Each atomic test produces specific log events that a detection rule should catch.


For testing detection rules locally (without running actual attacks), you generate synthetic log events that match what Atomic Red Team would produce. This is called test event generation or rule unit testing.


The pattern:


    

  1. Look up the ATT&CK technique
    2. 

  2. Find the Atomic Red Team test for it
    3. 

  3. Extract the command/action that produces the log event
    4. 

  4. Create a synthetic log record matching that command
    5. 

  5. Assert your rule fires on it
    6.

Concept 3 — Coverage Matrix: Which Attacks Can You Detect?


A coverage matrix answers: for each ATT&CK technique in scope, do you have a detection rule? This is the gap analysis view that drives your detection backlog.


The matrix has three states per technique:


    

  • Covered — you have a rule, it's tested, it's deployed
    • 

  • Partial — you have a rule but it covers only some variants
    • 

  • Gap — no rule exists
    • 



Coverage matrices are maintained as data (YAML or JSON) and rendered visually in ATT&CK Navigator (a browser-based tool that accepts JSON layer files). The W05 Royal Road built a Navigator layer; this week you extend it with detection status.


Example:

def coverage_summary(coverage: list[TechniqueCoVerage]) -> dict:
    from collections import Counter
    counts = Counter(c.status for c in coverage)
    total = len(coverage)
    return {
        "total": total,
        "covered": counts.get("covered", 0),
        "partial": counts.get("partial", 0),
        "gap": counts.get("gap", 0),
        "coverage_pct": round(counts.get("covered", 0) / total * 100, 1),
    }

Concept 1 — GitHub Actions Workflow Structure


GitHub Actions runs automated workflows triggered by repository events (push, pull_request, schedule). Each workflow is a YAML file in .github/workflows/. For detection-as-code, the standard triggers are:


    

  • on: pull_request — validate every proposed rule change before merge
    • 

  • on: push: branches: [main] — deploy validated rules after merge
    • 

  • on: schedule — weekly regression tests against live data
    • 



Workflow anatomy:


on: [trigger]
jobs:
  job-name:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: python scripts/validate_rules.py

Jobs run in parallel by default. Steps within a job run sequentially. Use needs: [job-name] to create job dependencies.


Example:


# .github/workflows/detect-ci.yml
name: Detection Rule CI

on:

      - "rules/**"

Concept 2 — The Rule Validation Script


The CI pipeline runs a Python validation script that checks every Sigma rule for structural and content quality. This is the automated gate that prevents bad rules from reaching production.


Checks to implement:


    

  1. Valid YAML — can be parsed
    2. 

  2. Required fields — title, id (UUID), status, detection, logsource, level, tags
    3. 

  3. UUID format — id is a valid UUID4
    4. 

  4. ATT&CK tag — at least one tag matching attack.t\d{4} pattern
    5. 

  5. Status whitelist — one of: experimental, test, stable
    6. 

  6. Severity whitelist — one of: informational, low, medium, high, critical
    7. 

  7. Detection not empty — detection.condition exists and is non-empty
    8. 

  8. No placeholders — title/description do not contain "TODO" or "FIXME"
    9. 



Example:


import yaml
import re
import uuid
from pathlib import Path

REQUIRED_FIELDS = ["title", "id", "status", "description", "logsource", "detection", "level"]
VALID_STATUSES = {"experimental", "test", "stable"}
VALID_SEVERITIES = {"informational", "low", "medium", "high", "critical"}

def validate_sigma_rule(rule_path: str) -> list[str]:
    errors = []
    try:
        with open(rule_path) as f:
            rule = yaml.safe_load(f)
    except yaml.YAMLError as e:
        return [f"Invalid YAML: {e}"]
    
    for field in REQUIRED_FIELDS:
        if field not in rule:
            errors.append(f"Missing required field: {field}")
    
    if "id" in rule:
        try:
            uuid.UUID(str(rule["id"]))
        except ValueError:
            errors.append(f"Invalid UUID: {rule['id']}")
    
    if "status" in rule and rule["status"] not in VALID_STATUSES:
        errors.append(f"Invalid status: {rule['status']}")
    
    if "level" in rule and rule["level"] not in VALID_SEVERITIES:
        errors.append(f"Invalid level: {rule['level']}")
    
    tags = rule.get("tags", [])
    has_attack_tag = any(re.match(r"attack\.t\d{4}", t) for t in tags)
    if not has_attack_tag:
        errors.append("No ATT&CK technique tag found (expected attack.tNNNN)")
    
    return errors

Concept 1 — Rule Lifecycle States


Detection rules have a lifecycle analogous to software releases. A new rule starts as experimental, moves to test after validation, and becomes stable after sustained production operation with acceptable FP rates.






State
Meaning
CI behavior






experimental
Just written, logic untested
Compile + lint; skip deployment




test
Tested on sample data; may have FPs
Compile + lint + deploy to staging




stable
30+ days in production, FP rate < 1%
Compile + lint + deploy to production




deprecated
Superseded or no longer relevant
Excluded from deployment; kept for audit






Promotion between states requires a PR with evidence: for experimental → test, attach test results; for test → stable, attach 30-day FP report.


Example:


from enum import Enum

class RuleStatus(str, Enum):
    EXPERIMENTAL = "experimental"
    TEST = "test"
    STABLE = "stable"
    DEPRECATED = "deprecated"

DEPLOYMENT_TARGETS = {
    RuleStatus.EXPERIMENTAL: [],           # do not deploy
    RuleStatus.TEST: ["staging"],          # staging only
    RuleStatus.STABLE: ["staging", "prod"],# both
    RuleStatus.DEPRECATED: [],             # do not deploy
}

def get_deployment_targets(status: RuleStatus) -> list[str]:
    return DEPLOYMENT_TARGETS[status]

def promote_rule(rule: dict, new_status: RuleStatus, evidence: str) -> dict:
    allowed_promotions = {
        RuleStatus.EXPERIMENTAL: {RuleStatus.TEST},
        RuleStatus.TEST: {RuleStatus.STABLE, RuleStatus.DEPRECATED},
        RuleStatus.STABLE: {RuleStatus.DEPRECATED},
    }
    current = RuleStatus(rule["status"])
    if new_status not in allowed_promotions.get(current, set()):
        raise ValueError(f"Cannot promote from {current} to {new_status}")
    return {**rule, "status": new_status.value, "promotion_evidence": evidence}

Concept 2 — Documentation Standards for Detection Rules


A detection rule without documentation is a maintenance liability. Documentation requirements:


    

  1. description — one sentence: what does this rule detect?
    2. 

  2. references — at least one URL (ATT&CK technique page, blog post, vendor advisory)
    3. 

  3. falsepositives — explicit list (minimum 2 scenarios); "None" is not acceptable for high/critical rules
    4. 

  4. author — who wrote it and when
    5. 

  5. modified — when it was last changed
    6. 

  6. related — IDs of rules that complement this one
    7. 



For detection rules, the description should answer: "What attacker action generates this alert?" not "What fields does this query check?"


Example:


DOCUMENTATION_REQUIREMENTS = {
    "informational": {"references": 0, "falsepositives_min": 0},
    "low":           {"references": 1, "falsepositives_min": 1},
    "medium":        {"references": 1, "falsepositives_min": 2},
    "high":          {"references": 2, "falsepositives_min": 2},
    "critical":      {"references": 2, "falsepositives_min": 3},
}

def validate_documentation(rule: dict) -> list[str]:
    errors = []
    level = rule.get("level", "informational")
    reqs = DOCUMENTATION_REQUIREMENTS.get(level, {})
    
    refs = rule.get("references", [])
    if len(refs) < reqs.get("references", 0):
        errors.append(f"Level '{level}' requires {reqs['references']} references; found {len(refs)}")
    
    fps = rule.get("falsepositives", [])
    if len(fps) < reqs.get("falsepositives_min", 0):
        errors.append(f"Level '{level}' requires {reqs['falsepositives_min']} false positive entries; found {len(fps)}")
    
    if not rule.get("description", "").strip():
        errors.append("Description is required and must be non-empty")
    
    return errors

Example:


from datetime import datetime, timedelta

def compute_detection_metrics(rules: list[dict], alerts: list[dict]) -> dict:
    total_rules = len(rules)
    stable = sum(1 for r in rules if r.get("status") == "stable")
    
    today = datetime.now()
    stale_cutoff = today - timedelta(days=90)
    stale = [
        r for r in rules
        if datetime.strptime(r.get("date", "2020/01/01"), "%Y/%m/%d") < stale_cutoff
        and r.get("status") == "stable"
    ]
    
    total_alerts = len(alerts)
    fp_alerts = sum(1 for a in alerts if a.get("outcome") == "false_positive")
    fp_rate = round(fp_alerts / total_alerts * 100, 1) if total_alerts else 0.0
    
    return {
        "total_rules": total_rules,
        "stable_rules": stable,
        "coverage_pct": round(stable / max(total_rules, 1) * 100, 1),
        "stale_rule_count": len(stale),
        "false_positive_rate_pct": fp_rate,
    }

Concept 1 — Pipeline Architecture


The full Detection-as-Code CI pipeline has four stages:


Stage 1: Validate
  ├── YAML syntax check
  ├── Required field presence
  ├── UUID format
  ├── ATT&CK tag
  └── Documentation standards

Stage 2: Test
  ├── Load test cases (from tests/ directory)
  ├── Run detection function against each test event
  ├── Assert true positives fire
  └── Assert false positives do not fire

Stage 3: Compile
  ├── Sigma → KQL (for Sentinel)
  ├── Sigma → SPL (for Splunk)
  └── Store compiled output as artifacts

Stage 4: Deploy (main branch only)
  ├── Staging: all test + stable rules
  └── Production: stable rules only

The pipeline fails fast: if Stage 1 fails, Stage 2 does not run.


Example:


from dataclasses import dataclass, field

@dataclass
class PipelineResult:
    stage: str
    passed: bool
    errors: list[str] = field(default_factory=list)
    artifacts: dict = field(default_factory=dict)

def run_pipeline(rules_dict: dict[str, str], test_cases: dict[str, list]) -> list[PipelineResult]:
    results = []
    
    # Stage 1: Validate
    val_errors = {}
    for name, content in rules_dict.items():
        errs = validate_sigma_rule_from_string(content)
        if errs:
            val_errors[name] = errs
    
    stage1 = PipelineResult("validate", passed=not val_errors, errors=[f"{k}: {v}" for k, v in val_errors.items()])
    results.append(stage1)
    if not stage1.passed:
        return results  # fail fast
    
    # Stage 2: Test (simplified)
    stage2 = PipelineResult("test", passed=True)
    results.append(stage2)
    
    # Stage 3: Compile
    compiled = {name: compile_sigma_to_kql_simple(content) for name, content in rules_dict.items()}
    stage3 = PipelineResult("compile", passed=True, artifacts={"kql_queries": compiled})
    results.append(stage3)
    
    return results

Concept 2 — Artifact Management


CI pipelines produce artifacts (compiled KQL files, test reports, coverage maps) that are stored and used by downstream stages or for historical reference. GitHub Actions artifact storage keeps these for 90 days by default.


For detection engineering artifacts:


    

  • compiled/kql/ — KQL files ready for Sentinel
    • 

  • reports/test_results.json — which tests passed/failed
    • 

  • reports/coverage.json — ATT&CK coverage map with current status
    • 

  • arm_templates/ — ARM JSON for deployment
    • 



The pipeline script writes these files and the workflow YAML specifies them as artifacts to upload.


Example:


import json
from pathlib import Path
from datetime import datetime

def write_pipeline_artifacts(
    compiled_rules: dict[str, str],
    test_results: dict,
    coverage: list[dict],
    output_dir: str,
) -> list[str]:
    base = Path(output_dir)
    written = []
    
    kql_dir = base / "compiled" / "kql"
    kql_dir.mkdir(parents=True, exist_ok=True)
    for name, kql in compiled_rules.items():
        p = kql_dir / f"{name.replace('.yml', '.kql')}"
        p.write_text(kql)
        written.append(str(p))
    
    reports_dir = base / "reports"
    reports_dir.mkdir(exist_ok=True)
    
    test_report_path = reports_dir / "test_results.json"
    test_report_path.write_text(json.dumps({
        "generated": datetime.now().isoformat(),
        **test_results
    }, indent=2))
    written.append(str(test_report_path))
    
    coverage_path = reports_dir / "coverage.json"
    coverage_path.write_text(json.dumps(coverage, indent=2))
    written.append(str(coverage_path))
    
    return written

def get_pipeline_config(project_root: str) -> dict:
    root = Path(project_root)
    return {
        "rules_dir": str(root / "detections" / "rules"),
        "tests_dir": str(root / "detections" / "tests"),
        "dataset_path": str(root / "detection_dataset" / "sysmon_detections.parquet"),

        "navigator_layer": str(root / "coverage" / "attck_layer.json"),
        "output_dir": str(root / "ci_artifacts"),
    }

def main(project_root: str) -> None:
    config = get_pipeline_config(project_root)
    
    # 1. Discover rules
    rule_files = list(Path(config["rules_dir"]).glob("**/*.yml"))
    print(f"Found {len(rule_files)} rule files")
    
    # 2. Validate
    all_valid = True
    for rf in rule_files:
        errors = validate_sigma_rule(str(rf))
        if errors:

        else:
            print(f"PASS {rf.name}")
    
    if not all_valid:
        raise SystemExit("Validation failed — fix rule errors before proceeding")
    
    print("All rules valid. Pipeline complete.")
