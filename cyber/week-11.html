Concept 1 — Signature vs. Behavioral Detection

Signature detection matches known bad indicators: file hashes, IP addresses, domain names. Behavioral detection identifies patterns of activity that deviate from a baseline regardless of specific indicators. Behavioral detection catches unknown threats; signature detection is faster and more precise for known threats.

The spectrum:

  • Signature: Image endswith '\mimikatz.exe' — catches mimikatz by name
  • Behavioral: rare process spawning cmd.exe, running from temp dir, making network connections — catches any credential dumping tool that mimics mimikatz behavior without using the same name

A signature that attackers bypass by renaming a binary stops working instantly. A behavioral rule based on what the process does survives the rename.

Data engineering analogy: signature detection is a lookup against a known-bad table. Behavioral detection is an anomaly score calculated from distributions and baselines — the same shift from exact-match queries to statistical thresholds you see in data quality monitoring.

Example:

import pandas as pd

# Signature approach — fails on renamed tool
def detect_by_signature(df: pd.DataFrame) -> pd.DataFrame:
    return df[df["process_name"] == "mimikatz.exe"]

# Behavioral approach — survives rename
def detect_by_behavior(df: pd.DataFrame) -> pd.DataFrame:
    suspicious = df[
        # high integrity process
        (df["IntegrityLevel"] == "High") &
        # spawned by office or script host
        (df["parent_name"].isin(["winword.exe", "powershell.exe", "wscript.exe"])) &
        # makes network connection (if net_connections column available)
        (df.get("outbound_connections", pd.Series(0)) > 0) &
        # runs from suspicious path
        (df["Image"].str.lower().str.contains(r"\\temp\\|\\appdata\\", regex=True))
    ]
    return suspicious

Concept 2 — Establishing a Process Baseline


Behavioral detection requires a normal baseline. Without knowing what "normal" looks like, you can't define "abnormal." A process baseline answers: which processes run, on which hosts, how often, launched by which parents?


Baseline construction:


    

  1. Collect 7–30 days of Sysmon EventID 1 (ProcessCreate) data
    2. 

  2. For each (host, process_name, parent_name) triple, count occurrences
    3. 

  3. Processes appearing on fewer than N% of hosts or fewer than M times are "rare"
    4. 

  4. Rarity is contextual: schtasks.exe running at midnight is normal; running 50 times in 1 hour from PowerShell is not
    5. 



Example:


def build_process_baseline(df: pd.DataFrame, lookback_days: int = 7) -> pd.DataFrame:
    """
    Build a frequency baseline for (process_name, parent_name) pairs.
    Returns baseline with occurrence counts and host coverage.
    """
    cutoff = df["UtcTime"].max() - pd.Timedelta(days=lookback_days)
    baseline_df = df[df["UtcTime"] < cutoff].copy()
    
    baseline = (
        baseline_df.groupby(["process_name", "parent_name"])
        .agg(
            total_occurrences=("process_name", "count"),
            unique_hosts=("User", "nunique"),   # proxy for host diversity
        )
        .reset_index()
    )
    baseline["occurrence_rank"] = baseline["total_occurrences"].rank(pct=True)
    return baseline.sort_values("occurrence_rank")

def flag_rare_processes(df: pd.DataFrame, baseline: pd.DataFrame, rarity_pct: float = 0.05) -> pd.DataFrame:
    """Flag processes in the rare tail (below rarity_pct percentile of occurrence)."""
    rare_pairs = baseline[baseline["occurrence_rank"] <= rarity_pct][["process_name", "parent_name"]]
    merged = df.merge(rare_pairs, on=["process_name", "parent_name"], how="inner")
    return merged

Concept 3 — Rare Process Detection Algorithm


The rare process detector works by comparing current activity against the baseline and flagging processes that:


    

  1. Are in the rare tail of the baseline distribution, OR
    2. 

  2. Were never seen in the baseline at all (new process), OR
    3. 

  3. Have a significantly higher frequency today than their baseline average
    4. 



This is the Pareto principle applied to security: 80% of attacks use processes that appear in the rarest 5% of your baseline.


Example:


from datetime import datetime, timedelta

def rare_process_detector(
    historical_df: pd.DataFrame,
    current_df: pd.DataFrame,
    rarity_threshold: float = 0.05,
    new_process_flag: bool = True,
) -> pd.DataFrame:
    """
    Detect rare and new processes in current_df relative to historical_df.
    Returns flagged records with a 'detection_reason' column.
    """
    baseline = build_process_baseline(historical_df)
    rare_threshold_count = baseline["total_occurrences"].quantile(rarity_threshold)
    
    rare_set = set(
        baseline[baseline["total_occurrences"] <= rare_threshold_count]["process_name"].tolist()
    )
    known_processes = set(baseline["process_name"].tolist())
    
    flags = []
    for _, row in current_df.iterrows():
        pname = row["process_name"]
        if pname not in known_processes:
            flags.append({**row.to_dict(), "detection_reason": "new_process_never_seen"})
        elif pname in rare_set:
            flags.append({**row.to_dict(), "detection_reason": "rare_process_in_baseline"})
    
    return pd.DataFrame(flags) if flags else pd.DataFrame(columns=list(current_df.columns) + ["detection_reason"])

Concept 1 — Stacking: Finding Low-Frequency Events


Stacking is a threat hunting technique that aggregates events by a key attribute and counts them, then sorts ascending to surface the rarest values. The insight: most attacks are low-frequency by definition — an attacker running a tool once stands out from a baseline of thousands of routine events.


Stack everything: process names, parent-child pairs, command lines, destination ports, user-agent strings, DNS domains. The rarest items in each stack are hunting leads.


Example:


// KQL — Stack process names, sort by rarity
SecurityEvent
| where EventID == 4688
| where TimeGenerated > ago(7d)
| summarize process_count = count(), unique_hosts = dcount(Computer) by NewProcessName
| sort by process_count asc
| take 20

def stack_by_field(df: pd.DataFrame, field: str, top_n: int = 20) -> pd.DataFrame:
    """Stack events by a field, return the rarest N values."""
    result = (
        df.groupby(field)
        .agg(
            event_count=(field, "count"),
            unique_users=("User", "nunique") if "User" in df.columns else (field, "count"),
        )
        .reset_index()
        .sort_values("event_count")
        .head(top_n)
    )
    return result

# Stack parent-child process pairs
def stack_parent_child(df: pd.DataFrame, top_n: int = 20) -> pd.DataFrame:
    df["pair"] = df["parent_name"] + " → " + df["process_name"]
    return stack_by_field(df, "pair", top_n)

Concept 2 — Temporal Correlation


Temporal correlation detects sequences of events that occur within a time window. A single 4625 (failed logon) is noise. Ten 4625 events followed by a 4624 (success) within 5 minutes is a successful brute force.


Patterns to correlate:


    

  • Failed logons → success (brute force succeeding)
    • 

  • Process create → network connect → DNS query (malware C2 setup)
    • 

  • File create → process create from same path (dropper + execution)
    • 

  • Account create → group add → logon (new admin account lateral movement)
    • 



Example:


def correlate_brute_force_success(df: pd.DataFrame, window_minutes: int = 5) -> pd.DataFrame:
    """
    Find accounts where: >= 5 failed logons followed by a success within N minutes.
    """
    failures = df[df["EventID"] == 4625][["TimeGenerated", "Account", "IpAddress"]].copy()
    successes = df[df["EventID"] == 4624][["TimeGenerated", "Account", "IpAddress"]].copy()
    
    alerts = []
    for account in failures["Account"].unique():
        acct_failures = failures[failures["Account"] == account].sort_values("TimeGenerated")
        acct_successes = successes[successes["Account"] == account]
        
        for _, success_row in acct_successes.iterrows():
            window_start = success_row["TimeGenerated"] - pd.Timedelta(minutes=window_minutes)
            prior_failures = acct_failures[
                (acct_failures["TimeGenerated"] >= window_start) &
                (acct_failures["TimeGenerated"] < success_row["TimeGenerated"])
            ]
            if len(prior_failures) >= 5:
                alerts.append({
                    "account": account,
                    "success_time": success_row["TimeGenerated"],
                    "failure_count": len(prior_failures),
                    "source_ip": success_row["IpAddress"],
                })
    return pd.DataFrame(alerts)

Concept 3 — Entity-Based Correlation


Entity-based correlation pivots on an entity (user, host, IP) and aggregates all suspicious activity for that entity across event types. A single event rarely tells a full story; multiple low-severity events targeting the same entity compose into a high-confidence alert.


Risk scoring: assign point values to individual events, sum by entity over a time window, alert when the entity exceeds a threshold.


Example:


RISK_WEIGHTS = {
    "failed_logon": 1,
    "successful_logon_from_new_ip": 5,
    "rare_process_execution": 3,
    "process_from_temp": 2,
    "encoded_powershell": 4,
    "outbound_to_rare_domain": 3,
}

def entity_risk_score(events_by_entity: dict[str, list[str]]) -> dict[str, int]:
    """
    events_by_entity: {entity_name: [list of event_type strings]}
    Returns {entity_name: total_risk_score}
    """
    scores = {}
    for entity, event_types in events_by_entity.items():
        score = sum(RISK_WEIGHTS.get(et, 0) for et in event_types)
        scores[entity] = score
    return dict(sorted(scores.items(), key=lambda x: x[1], reverse=True))

    "svc_backup": ["successful_logon_from_new_ip"],
    "admin": ["failed_logon"],
}

Concept 1 — The Hunting Loop


Threat hunting is the proactive search for threats that have evaded existing detection rules. The process is hypothesis-driven: you start with a threat model or CTI (from W07), form a hypothesis about attacker behavior, then search for evidence.


The hunting loop:


    

  1. Form hypothesis — "Attackers using PowerShell download cradles to stage payloads"
    2. 

  2. Identify observables — what log events would this produce?
    3. 

  3. Write the hunt query — KQL/SPL/pandas to find the pattern
    4. 

  4. Investigate results — review hits manually, determine true/false positive
    5. 

  5. Convert to detection — if the hypothesis holds, write a Sigma rule for continuous monitoring
    6. 

  6. Document findings — even negative hunts are valuable (confirms no evidence of technique)
    7. 



Data engineering analogy: hunting is exploratory analysis (pandas, notebooks, ad-hoc SQL). Detection rules are the productionized version (scheduled queries, CI pipeline, Sentinel).


Example:


# Hypothesis: attackers use certutil to download payloads
# Observable: certutil.exe with -urlcache or -decode flags

def hunt_certutil_download(df: pd.DataFrame) -> pd.DataFrame:
    certutil = df[df["process_name"] == "certutil.exe"].copy()
    download_flags = certutil["CommandLine"].str.lower().str.contains(
        r"-urlcache|-decode|-encode", regex=True, na=False
    )
    return certutil[download_flags][
        ["UtcTime", "User", "CommandLine", "parent_name", "Image"]
    ].sort_values("UtcTime")

def hunt_lolbin_network(df: pd.DataFrame, lolbins: list[str]) -> pd.DataFrame:
    """Find LOLBins (living-off-the-land binaries) making network connections."""
    lolbin_events = df[df["process_name"].isin(lolbins)]
    return lolbin_events[
        lolbin_events.get("has_network_connection", pd.Series(False, index=lolbin_events.index))
    ]

Concept 2 — Data-Driven Hunting with Frequency Analysis


Not all hunts start with a hypothesis. Frequency analysis generates hunting leads by surfacing statistically unusual patterns in the data — you let the data tell you what's strange, then investigate.


Techniques:


    

  • Command line clustering — group similar command lines; outlier clusters contain unusual executions
    • 

  • Edit distance — processes with names similar to system processes (svchost.exe → svchost0.exe)
    • 

  • Port/protocol rarity — connections on unusual ports
    • 

  • User-host affinity — users logging into hosts they've never accessed before
    • 



Example:


def typosquatting_detector(df: pd.DataFrame, system_processes: list[str]) -> pd.DataFrame:
    """
    Detect process names that are similar to (but not exactly) known system processes.
    Uses simple edit distance: flag processes within Levenshtein distance 1 or 2.
    """
    def levenshtein(s1: str, s2: str) -> int:
        if len(s1) < len(s2):
            return levenshtein(s2, s1)
        if not s2:
            return len(s1)
        prev = list(range(len(s2) + 1))
        for i, c1 in enumerate(s1):
            curr = [i + 1]
            for j, c2 in enumerate(s2):
                curr.append(min(prev[j+1]+1, curr[j]+1, prev[j]+(c1 != c2)))
            prev = curr
        return prev[-1]
    
    suspects = []
    for _, row in df.drop_duplicates("process_name").iterrows():
        pname = row["process_name"].lower()
        for sys_proc in system_processes:
            if pname != sys_proc and levenshtein(pname, sys_proc) <= 2:
                suspects.append({**row.to_dict(), "similar_to": sys_proc, "edit_distance": levenshtein(pname, sys_proc)})
                break
    return pd.DataFrame(suspects)

SYSTEM_PROCS = ["svchost.exe", "lsass.exe", "explorer.exe", "services.exe", "winlogon.exe"]

Concept 3 — Documenting Hunt Findings


Hunts must be documented even when negative. A documented negative hunt is evidence that a technique was searched for and not found — valuable for security posture reporting. A positive hunt finding documents the attack chain that was missed and becomes the basis for a new detection rule.


Hunt documentation format:


Hunt ID: HUNT-2024-003
Hypothesis: PowerShell download cradle via IEX + Net.WebClient
Date: 2024-03-15
Analyst: [name]
Data sources: Sysmon EventID 1, 3 (30 days)
Hunt query: [KQL or Python function]
Results: 3 hits found
Classification: True Positive (confirmed via IR)
Outcome: New Sigma rule created: rules/execution/powershell_iex_download.yml

Example:


from dataclasses import dataclass, field
from datetime import date

@dataclass
class HuntReport:
    hunt_id: str
    hypothesis: str
    hunt_date: date
    analyst: str
    data_sources: list[str]
    query_description: str
    result_count: int
    classification: str    # "true_positive" | "false_positive" | "negative" | "inconclusive"
    outcome: str
    related_techniques: list[str] = field(default_factory=list)
    rule_created: str = ""

    def to_markdown(self) -> str:
        tp_label = "TP" if self.classification == "true_positive" else self.classification.upper()
        lines = [
            f"## {self.hunt_id} — {self.hypothesis}",
            f"**Date**: {self.hunt_date} | **Analyst**: {self.analyst} | **Result**: {tp_label}",
            f"**Data sources**: {', '.join(self.data_sources)}",
            f"**Hits**: {self.result_count}",
            f"**Outcome**: {self.outcome}",
        ]
        if self.rule_created:
            lines.append(f"**Rule**: `{self.rule_created}`")
        return "\n".join(lines)

Concept 1 — KQL Query Optimization


KQL queries on production SIEM data run against billions of rows. Poorly written queries time out or consume excessive resources. Optimization principles:


    

  1. Filter early — put where TimeGenerated > ago(24h) first; this is the most powerful filter
    2. 

  2. Use has not contains — has matches word boundaries and is faster for whole words
    3. 

  3. Avoid regex when string operators suffice — contains is faster than matches regex for simple patterns
    4. 

  4. Use in for multiple values — where EventID in (4624, 4625, 4688) is faster than three separate or conditions
    5. 

  5. Reduce columns early — project after where, before join, to reduce data volume
    6. 

  6. Limit join right-side size — join to small lookup tables, not large event tables
    7. 

  7. Use materialize() — for repeated sub-queries, let t = materialize(...) caches the result
    8. 



Example:


# Python analogy: pandas optimization patterns that mirror KQL optimization

# SLOW: filter after join
def slow_query(df_events: pd.DataFrame, df_users: pd.DataFrame) -> pd.DataFrame:
    merged = df_events.merge(df_users, on="Account")
    return merged[merged["EventID"] == 4624]

# FAST: filter before join
def fast_query(df_events: pd.DataFrame, df_users: pd.DataFrame) -> pd.DataFrame:
    filtered = df_events[df_events["EventID"] == 4624]   # filter first
    return filtered.merge(df_users, on="Account")         # join smaller dataset

# SLOW: regex when not needed
def slow_contains(df: pd.DataFrame) -> pd.DataFrame:
    return df[df["CommandLine"].str.contains(r"powershell", regex=True, na=False)]

# FAST: str.contains with regex=False
def fast_contains(df: pd.DataFrame) -> pd.DataFrame:
    return df[df["CommandLine"].str.contains("powershell", regex=False, na=False)]

Concept 2 — Window Functions in KQL


Window functions compute values over a sliding or expanding window of rows, ordered by time. They're essential for detection patterns that depend on context around an event.


KQL window functions:


    

  • prev(field) — value of field in the previous row (same partition)
    • 

  • next(field) — value of field in the next row
    • 

  • row_number() — sequential row number within partition
    • 

  • series_stats() — compute statistics over a time series array
    • 

  • make_list() + mvexpand — aggregate then expand arrays
    • 



Partitioning by Account or Computer with order by TimeGenerated enables per-entity analysis.


Example:


// Detect rapid account hopping: same IP logging in as multiple accounts
SecurityEvent
| where EventID == 4624
| where TimeGenerated > ago(1h)
| sort by IpAddress, TimeGenerated asc
| extend prev_account = prev(Account, 1, "")
| where Account != prev_account and IpAddress == prev(IpAddress, 1, "")
| summarize unique_accounts = dcount(Account), account_list = make_list(Account) by IpAddress
| where unique_accounts > 3

def detect_account_hopping(df: pd.DataFrame, window_hours: int = 1, threshold: int = 3) -> pd.DataFrame:
    """Find IPs that authenticated as multiple different accounts within the window."""
    cutoff = df["TimeGenerated"].max() - pd.Timedelta(hours=window_hours)
    recent = df[(df["EventID"] == 4624) & (df["TimeGenerated"] >= cutoff)]
    
    result = (
        recent.groupby("IpAddress")
        .agg(unique_accounts=("Account", "nunique"), account_list=("Account", list))
        .reset_index()
    )
    return result[result["unique_accounts"] > threshold].sort_values("unique_accounts", ascending=False)

Concept 3 — Aggregation Patterns for Detection


Advanced detection queries use multi-level aggregation: first aggregate individual events into summaries, then aggregate summaries into alert candidates.


Patterns:


    

  • Count-based threshold: count() by Account | where count_ > 10
    • 

  • Ratio-based: failed/(failed+success) > 0.8 in a window = credential stuffing
    • 

  • Spread-based: distinct destinations > N = scanning
    • 

  • Sequence-based: requires explicit ordering and lag/lead joins
    • 



Example:


def logon_ratio_analysis(df: pd.DataFrame, window_hours: int = 1) -> pd.DataFrame:
    """
    Compute failure ratio per account per hour.
    High failure ratio with at least one success = likely successful brute force.
    """
    cutoff = df["TimeGenerated"].max() - pd.Timedelta(hours=window_hours)
    recent = df[df["TimeGenerated"] >= cutoff & df["EventID"].isin([4624, 4625])].copy()
    recent["hour"] = recent["TimeGenerated"].dt.floor("h")
    
    agg = recent.groupby(["Account", "hour", "EventID"]).size().unstack(fill_value=0).reset_index()
    agg.columns.name = None
    agg = agg.rename(columns={4624: "success_count", 4625: "failure_count"})
    
    total = agg["success_count"] + agg["failure_count"]
    agg["failure_ratio"] = agg["failure_count"] / total.replace(0, 1)
    
    return agg[
        (agg["failure_ratio"] > 0.8) & (agg["failure_count"] > 5) & (agg["success_count"] > 0)
    ].sort_values("failure_ratio", ascending=False)

Concept 1 — Designing the Full Detector


The W11 Royal Road builds a complete rare process behavioral detector. The design brings together:

import json
import pickle
from pathlib import Path

class RareProcessDetector:
    def __init__(self, rarity_threshold: float = 0.05):
        self.rarity_threshold = rarity_threshold
        self.baseline: pd.DataFrame = pd.DataFrame()
        self.known_processes: set[str] = set()
    
    def train(self, df: pd.DataFrame) -> None:
        self.baseline = build_process_baseline(df)
        self.known_processes = set(self.baseline["process_name"].tolist())
        rare_cutoff = self.baseline["total_occurrences"].quantile(self.rarity_threshold)
        self.rare_processes = set(
            self.baseline[self.baseline["total_occurrences"] <= rare_cutoff]["process_name"].tolist()
        )
    
    def detect(self, current_df: pd.DataFrame) -> pd.DataFrame:
        if self.baseline.empty:
            raise RuntimeError("Detector not trained. Call train() first.")
        return rare_process_detector(self.baseline, current_df, self.rarity_threshold)
    
    def save(self, path: str) -> None:
        with open(path, "wb") as f:
            pickle.dump(self, f)
    
    @classmethod
    def load(cls, path: str) -> "RareProcessDetector":
        with open(path, "rb") as f:
            return pickle.load(f)

def generate_sigma_stub_from_alert(alert: dict) -> str:
    """Generate a Sigma rule skeleton from a rare process alert."""
    import yaml
    import uuid
    
    process = alert.get("process_name", "unknown.exe")
    technique = alert.get("mitre_technique", "T1059")
    
    rule = {
        "title": f"Rare Process Execution - {process}",
        "id": str(uuid.uuid4()),
        "status": "experimental",
        "description": f"Detects execution of {process}, identified as rare via behavioral baseline analysis.",
        "references": [f"https://attack.mitre.org/techniques/{technique}/"],
        "author": "Detection Pipeline (auto-generated)",
        "date": "2024/03/15",
        "tags": [f"attack.{technique.lower().replace('.', '_')}"],
        "logsource": {"category": "process_creation", "product": "windows"},
        "detection": {
            "selection": {
                "Image|endswith": f"\\{process}",
            },
            "condition": "selection",
        },
        "falsepositives": ["Security testing", "Unknown — requires analyst review"],
        "level": "medium",
    }
    return yaml.dump(rule, default_flow_style=False)

def run_full_integration(
    dataset_path: str,
    ioc_db_path: str,
    rules_output_dir: str,
) -> dict:
    """Full pipeline: detect → enrich → generate stubs."""
    df = pd.read_parquet(dataset_path)
    
    detector = RareProcessDetector(rarity_threshold=0.05)
    split = int(len(df) * 0.8)
    detector.train(df.iloc[:split])
    alerts_df = detector.detect(df.iloc[split:])
    
    if alerts_df.empty:
        return {"alerts": 0, "stubs_generated": 0}
    
    alerts = [enrich_alert(row.to_dict()) for _, row in alerts_df.iterrows()]
    
    stubs = []
    output = Path(rules_output_dir)
    output.mkdir(exist_ok=True)
    for alert in alerts[:5]:  # cap at 5 to avoid flooding the rule backlog
        stub = generate_sigma_stub_from_alert(alert)
        stub_path = output / f"auto_{alert['process_name'].replace('.', '_')}.yml"
        stub_path.write_text(stub)
        stubs.append(str(stub_path))
    
    return {"alerts": len(alerts), "stubs_generated": len(stubs), "stub_files": stubs}
