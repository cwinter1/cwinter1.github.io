Concept 1 — How Passwords Are Stored: Hashing, Salting, and Why It Matters

Passwords are never stored as plaintext in any properly designed system. Instead, a one-way hash function transforms the password into a fixed-length string. You cannot reverse the hash to get the original password — you can only verify by hashing a candidate and comparing. A salt (random per-user string) is added before hashing to prevent precomputed dictionary attacks.

Data engineering analogy: a password hash is like a deterministic aggregation — given the same input you always get the same output, but you cannot reconstruct the input from the output. A salt is like adding a unique surrogate key prefix before hashing a natural key — two rows with identical natural keys get different hashes, so you cannot build a reverse lookup table.

Modern secure algorithms:

  • bcrypt — designed to be slow; configurable work factor; widely used
  • Argon2 — winner of Password Hashing Competition; memory-hard; current best practice
  • PBKDF2 — NIST-approved; used by Django, many enterprise systems
  • SHA-256 / MD5 — fast hash functions. Fast = bad for passwords. MD5 is broken. SHA-256 alone (without iterations) is insecure for passwords.

Example:

import hashlib
import os
import bcrypt

# BAD: MD5 without salt — precomputed rainbow tables break this instantly
password = "hunter2"
bad_hash = hashlib.md5(password.encode()).hexdigest()
print(bad_hash)
# → 2ab96390c7dbe3439de74d0c9b0b1767
# Every "hunter2" in every database has this same hash → rainbow table attack

# GOOD: bcrypt with auto-generated salt
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
print(hashed)
# → b'$2b$12$LQv3c1yqBWVHxkd0LHAkCOYz6TtxMQJqhN8/LewdBPj0iy21mGqKC'
# $2b$ = bcrypt, $12$ = 12 rounds (work factor), next 22 chars = salt, rest = hash

# Verify:
is_valid = bcrypt.checkpw(password.encode(), hashed)
print(is_valid)  # True

Concept 2 — Credential Dumping: What Attackers Extract and From Where


Once an attacker has code execution on a Windows machine, their next goal is usually to collect credentials. They target three sources:


    

  1. LSASS process memory — Windows caches credentials (NTLM hashes, Kerberos tickets) in lsass.exe for single sign-on. Mimikatz dumps this.
    2. 

  2. SAM database — local account hashes stored in C:\Windows\System32\config\SAM (locked while Windows runs — attackers use Volume Shadow Copies to read it)
    3. 

  3. NTDS.dit — the Active Directory database file on Domain Controllers. Contains every domain account's hash.
    4. 



Detection: Windows Event ID 4656 (object access to SAM), Event ID 4663 (NTDS.dit access), Sysmon Event ID 10 (process access to lsass.exe).


Data engineering analogy: this is like an attacker who gains access to your dbt project and reads the profiles.yml file (which contains database credentials), then uses those credentials to dump your entire data warehouse. LSASS is your in-memory credential cache — equivalent to reading database connection objects from a running Python process's heap.

Concept 3 — Password Attacks: Brute Force, Spraying, and Stuffing


Three distinct attack patterns, each with different detection signatures:


    

  • Brute force — try every password against one account. High volume against one username. Triggers account lockout. Detectable by: many 4625 events for the same TargetUserName.
    • 

  • Password spray — try one (or a few) common passwords against many accounts. Low volume per account — avoids lockout. Detectable by: 4625 events for many different TargetUserNames from the same source in a short window.
    • 

  • Credential stuffing — use username:password pairs leaked from other breaches. Medium volume. Detectable by: 4625 events where the TargetUserName matches a known leaked credential list.
    • 



Data engineering analogy: brute force is like running a full table scan with no WHERE clause — high I/O, easily noticed. Password spray is like a carefully sampled query designed to stay under the cost threshold — low per-row cost but wide coverage. Credential stuffing is like a targeted lookup with a pre-built index — efficient and targeted.


Example:


import pandas as pd
from datetime import timedelta

# Sample of Event ID 4625 (failed logons):
events = pd.DataFrame([
    {"time": "2024-01-15 09:00:01", "user": "alice", "src_ip": "10.0.99.1"},
    {"time": "2024-01-15 09:00:03", "user": "bob",   "src_ip": "10.0.99.1"},
    {"time": "2024-01-15 09:00:05", "user": "carol", "src_ip": "10.0.99.1"},
    {"time": "2024-01-15 09:00:07", "user": "dave",  "src_ip": "10.0.99.1"},
    {"time": "2024-01-15 09:00:09", "user": "eve",   "src_ip": "10.0.99.1"},
    {"time": "2024-01-15 09:00:11", "user": "frank", "src_ip": "10.0.99.1"},
])
events["time"] = pd.to_datetime(events["time"])

# Password spray detection: 1 source IP, many usernames, short window
spray = (events.groupby("src_ip")
               .apply(lambda g: g.set_index("time")
                                 .resample("1min")["user"].nunique())
               .reset_index())
spray.columns = ["src_ip", "window", "unique_users"]
print(spray[spray["unique_users"] >= 5])
# → 10.0.99.1 sprayed 6 unique accounts in 1 minute

Concept 1 — MFA Factors and TOTP


Multi-factor authentication requires proof of identity from at least two categories:


    

  • Something you know — password, PIN
    • 

  • Something you have — phone (TOTP app), hardware token (YubiKey)
    • 

  • Something you are — fingerprint, face scan
    • 



TOTP (Time-based One-Time Password) is the standard behind Google Authenticator, Authy, and Microsoft Authenticator. It generates a 6-digit code that changes every 30 seconds. The code is HOTP(secret, floor(current_time / 30)) — a HMAC-SHA1 of the shared secret and the current 30-second window.


Data engineering analogy: TOTP is like a time-partitioned signing key. The key used to sign a request is only valid for the current 30-second partition. An attacker who intercepts the token cannot reuse it after 30 seconds — the equivalent of a signed S3 URL with a 30-second expiry.


Example:


import hmac
import hashlib
import time
import struct
import base64

def totp(secret_b32: str, digits: int = 6, window: int = 30) -> str:
    secret = base64.b32decode(secret_b32.upper())
    counter = int(time.time()) // window
    msg = struct.pack(">Q", counter)
    h = hmac.new(secret, msg, hashlib.sha1).digest()
    offset = h[-1] & 0x0F
    code = struct.unpack(">I", h[offset:offset+4])[0] & 0x7FFFFFFF
    return str(code % (10 ** digits)).zfill(digits)

# TOTP shared secret (from QR code during enrollment):
secret = "JBSWY3DPEHPK3PXP"
print(totp(secret))
# → "123456" (changes every 30 seconds)

Concept 2 — OAuth2 and JWT: How Modern Apps Delegate Authentication


OAuth2 is the protocol that powers "Sign in with Google" and API authorization. A JWT (JSON Web Token) is the token format commonly used to carry identity and permissions. Understanding this is essential because JWT vulnerabilities and OAuth misconfigurations are top attack targets.


OAuth2 authorization code flow:


    

  1. User clicks "Sign in with Google"
    2. 

  2. App redirects user to Google with client_id, redirect_uri, scope
    3. 

  3. User authenticates with Google
    4. 

  4. Google redirects back with an authorization code
    5. 

  5. App exchanges code for access_token (and optionally id_token) — server to server
    6. 

  6. App uses access_token to call Google APIs
    7. 



JWT structure: header.payload.signature — all base64-encoded. The signature proves the token was issued by the trusted authority. The payload contains claims: sub (subject), exp (expiry), iss (issuer), scope (permissions).


Data engineering analogy: an OAuth2 access token is like a time-limited, scope-restricted IAM token (AWS STS AssumeRole response). The token grants access to specific resources for a limited time without exposing the underlying credentials.


Example:


import base64
import json

def decode_jwt_payload(token: str) -> dict:
    parts = token.split(".")
    if len(parts) != 3:
        raise ValueError("Invalid JWT format")
    # Add padding for base64 decode
    payload_b64 = parts[1] + "=" * (-len(parts[1]) % 4)
    payload_bytes = base64.urlsafe_b64decode(payload_b64)
    return json.loads(payload_bytes)

# Sample JWT (do NOT verify — just inspect the payload):
token = (
    "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9"
    ".eyJzdWIiOiJ1c2VyQGV4YW1wbGUuY29tIiwic2NvcGUiOiJyZWFkOnJlcG9zIiwiZXhwIjoxNzA1MzE4MDAwfQ"
    ".SIGNATURE_OMITTED"
)
payload = decode_jwt_payload(token)
print(payload)
# → {'sub': 'user@example.com', 'scope': 'read:repos', 'exp': 1705318000}

Concept 3 — OAuth2 Attack Patterns: Token Theft and Open Redirects


Common OAuth2 attacks:


    

  • Token theft — steal the access_token from browser storage, network traffic, or logs. Tokens in application logs are a common leak.
    • 

  • Open redirect — the redirect_uri parameter is not strictly validated; attacker changes it to their server to receive the authorization code
    • 

  • CSRF on the callback — the state parameter prevents cross-site request forgery on the OAuth callback; if omitted, an attacker can inject a code
    • 

  • Refresh token abuse — refresh tokens are long-lived; stealing one gives persistent access
    • 



Detection: look for access_token values appearing in HTTP access logs or proxy logs (tokens should never be in URLs — they belong in headers). Alert on OAuth flows where the redirect_uri does not match the registered value.


Example:


import re

# Tokens in URLs (a severe security mistake — they appear in web server access logs):
log_lines = [
    '10.0.1.5 - - [15/Jan/2024] "GET /api/data HTTP/1.1" 200 -',
    '10.0.1.5 - - [15/Jan/2024] "GET /callback?code=auth_code_here&state=abc HTTP/1.1" 302 -',
    '10.0.1.5 - - [15/Jan/2024] "GET /api/resource?access_token=eyJhbGciOi... HTTP/1.1" 200 -',
    '10.0.99.1 - - [15/Jan/2024] "GET /oauth/callback?redirect_uri=http://evil.com HTTP/1.1" 302 -',
]

def find_token_leaks(logs: list[str]) -> list[str]:
    token_pattern = re.compile(r"access_token=([A-Za-z0-9._-]{20,})")
    redirect_pattern = re.compile(r"redirect_uri=([^\s&]+)")
    ALLOWED_REDIRECTS = {"http://app.example.com/callback"}
    flagged = []
    for line in logs:
        if token_pattern.search(line):
            flagged.append(f"TOKEN IN URL: {line[:80]}")
        m = redirect_pattern.search(line)
        if m and m.group(1) not in ALLOWED_REDIRECTS:
            flagged.append(f"OPEN REDIRECT: {line[:80]}")
    return flagged

print(find_token_leaks(log_lines))

Concept 2 — Service Principals and Managed Identities


In Azure, applications authenticate as service principals (like service accounts in Linux) or managed identities. Service principals have client credentials (client ID + secret or certificate). Managed identities are automatically managed by Azure — no credential to steal.


Attack surface: a service principal secret (client secret) is essentially a password for an application identity. If it is hard-coded in code, stored in source control, or leaked in logs, an attacker can authenticate as the application. The application's Azure RBAC role determines the blast radius.


Data engineering analogy: a service principal with Contributor role on a subscription is like a data pipeline service account with bq.admin rights — it can read, write, and delete any dataset. Credential theft of this service principal is equivalent to leaking an all-access BigQuery service account key.


Example:


# Using Azure CLI to list service principals:

# Check what roles a service principal has:
az role assignment list --assignee <appId> --all -o table

# Generate a new client secret (for rotation):

Concept 3 — Conditional Access and Zero Trust


Conditional Access is Azure AD's policy engine: it evaluates every authentication attempt against a set of conditions (user, device, location, risk score) and grants or blocks access — or requires MFA — based on policy. This is the enforcement layer of Zero Trust.


Zero Trust principle: "never trust, always verify." No user or device is trusted by default, even inside the corporate network. Every access request is evaluated against policy.


Detection engineer perspective: Conditional Access policy failures (sign-ins that were blocked by CA) are high-signal events. Attempts to bypass CA (e.g., legacy authentication protocols that CA cannot intercept) are a critical detection target.


Example:

Concept 1 — Why Raw Log Events Are Not Enough


A raw log event tells you what happened technically: "IP 10.0.1.99 authenticated as user ID 1234 at 09:00." But the question you need to answer is: "Is this normal?" To answer that, you need context: Who is user 1234? What department? What is their typical login time? Is 10.0.1.99 their registered device?


Identity enrichment adds this context to every event by joining against an identity reference dataset. After enrichment, the same event becomes: "Alice (Finance, Chicago, normally authenticates 08:00-17:00 from her registered laptop 10.0.1.22) authenticated from 10.0.1.99 at 09:00." Now the alert writes itself.


Data engineering analogy: this is a standard dimensional JOIN. Your log event is a fact table row. Your identity dataset is a dimension table. JOIN ON user_id enriches every fact with the dimension attributes. This is the same pattern as enriching sales transactions with product and customer dimension tables in a star schema.


Example:


import pandas as pd

# Fact: log events

    {"time": "2024-01-15 09:00:00", "user_id": "alice",    "src_ip": "10.0.1.99", "event": "login_success"},
    {"time": "2024-01-15 09:05:00", "user_id": "bob",      "src_ip": "10.0.2.55", "event": "file_access"},

Concept 2 — Building the Identity Reference Dataset


In practice, the identity reference dataset is built by pulling from HR systems, Active Directory, Azure AD, and IT asset management. For the detection pipeline, you need at minimum: user ID, department, manager, typical working hours, registered device IPs, and account type (human / service).


Data engineering analogy: this is exactly like building an SCD Type 1 or Type 2 dimension table in dbt. The source is an HR API or LDAP export; you run a daily refresh; you track changes (hire, termination, role change) that affect access risk.

import json

IDENTITY_SCHEMA = {

    "department":       str,

Concept 3 — The Royal Road: Putting Identity Enrichment Into the Pipeline


The W04 Royal Road artifact adds an identity enrichment JOIN to the unified pipeline built in W02 and W03. Every event — whether from Windows EVTX or Linux syslog — gets enriched with user department, admin status, and normal hours before hitting any detection rule.


This mirrors how production SIEM enrichment works: raw events are enriched at ingest time so detection rules can reference context fields directly, without requiring a secondary lookup at query time.


Example:


# pipeline/w04_enrich.py — identity enrichment layer
import json
import pandas as pd
from pathlib import Path

def load_events(paths: list[str]) -> pd.DataFrame:
    rows = []
    for p in paths:
        with open(p) as f:
            for line in f:
                rows.append(json.loads(line))
    df = pd.DataFrame(rows)
    df["time"] = pd.to_datetime(df.get("time", pd.Series()), errors="coerce", utc=True)
    return df

def enrich_with_identity(df: pd.DataFrame, identity_db: dict) -> pd.DataFrame:
    def get_attr(user_id, attr, default=None):
        record = identity_db.get(str(user_id), {})
        return record.get(attr, default)

    for col in ["department", "account_type", "is_admin", "normal_hours_utc", "is_active"]:
        # Try to find the user field — different log sources use different field names
        user_col = next((c for c in df.columns
                         if c.lower() in ("user", "user_id", "targetusername", "username")), None)
        if user_col:
            df[col] = df[user_col].map(lambda u: get_attr(u, col))
    return df

Concept 1 — Kerberoasting Detection


Kerberoasting is a technique where an attacker requests service tickets (TGS) for accounts with Service Principal Names (SPNs). The service ticket is encrypted with the service account's password hash. The attacker takes the ticket offline and cracks it — no network noise during the crack phase.


Detection is based on Event ID 4769 (Service Ticket Request) with two specific conditions:


    

  1. Ticket encryption type = 0x17 (RC4-HMAC) — modern Kerberos uses AES; RC4 requests are legacy or deliberate downgrade
    2. 

  2. Multiple 4769 events from the same source in a short window requesting tickets for multiple different service accounts
    3. 



Example:


events = [
    {"time": "09:00:01", "event_id": "4769", "user": "alice", "service": "MSSQLSvc/db01", "enc_type": "0x12", "src_ip": "10.0.1.15"},
    {"time": "09:00:03", "event_id": "4769", "user": "alice", "service": "HTTP/web01",    "enc_type": "0x17", "src_ip": "10.0.1.15"},
    {"time": "09:00:05", "event_id": "4769", "user": "alice", "service": "HOST/srv01",    "enc_type": "0x17", "src_ip": "10.0.1.15"},
    {"time": "09:00:07", "event_id": "4769", "user": "alice", "service": "MSSQLSvc/db02", "enc_type": "0x17", "src_ip": "10.0.1.15"},
]

def detect_kerberoasting(events: list[dict], threshold: int = 3) -> list[dict]:
    from collections import defaultdict
    rc4_by_src: dict[str, list] = defaultdict(list)
    for e in events:
        if e.get("event_id") == "4769" and e.get("enc_type") == "0x17":
            rc4_by_src[e["src_ip"]].append(e)
    return [
        {"src_ip": ip, "count": len(evts), "services": [e["service"] for e in evts]}
        for ip, evts in rc4_by_src.items()
        if len(evts) >= threshold
    ]

print(detect_kerberoasting(events))
# → [{"src_ip": "10.0.1.15", "count": 3, "services": ["HTTP/web01", "HOST/srv01", "MSSQLSvc/db02"]}]

Concept 2 — AS-REP Roasting and Pre-Authentication Disabled Accounts


AS-REP Roasting targets accounts with "Do not require Kerberos preauthentication" enabled. Normally, Kerberos requires the client to prove it knows the password before issuing a TGT. With preauthentication disabled, the KDC responds with an AS-REP encrypted with the user's password hash — without any proof the requester knows the password.


An attacker can request this AS-REP for any vulnerable account without any credentials at all, then crack it offline.


Detection: Event ID 4768 where PreAuthType = 0 (preauthentication not required).


Example:
