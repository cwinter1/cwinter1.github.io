Concept 1 — Portfolio as a System, Not a Collection

A portfolio that passes a technical screen at an Israeli security company is not a list of file names — it is a demonstrable system. The hiring engineer will clone the repo, run a script, and expect to see output. If anything requires a cloud credential or live SIEM to run, the reviewer will close the terminal and move on.

The capstone portfolio has four non-negotiable properties: everything runs locally (simulation mode), every component has a README that says exactly what command to run, the repo passes a lint/validate CI check on every push, and the Royal Road artifacts from W01–W22 are connected into a single end-to-end flow.

Concept 2 — End-to-End Pipeline Wiring


The portfolio components from W01–W22 were built independently. The capstone connects them: PCAP parser → beaconing detector → RAG enrichment → final alert report. The output of each component is the input of the next. This is the same pattern as a data engineering ETL pipeline — which you already know how to build.


The key new skill is writing a pipeline_runner.py that orchestrates the full flow, handles component failures gracefully, and produces a single output file that a reviewer can inspect.


Example:


import subprocess
import sys
import json
from dataclasses import dataclass
from pathlib import Path

@dataclass
class PipelineStep:
    name: str
    command: list[str]
    output_path: str
    required: bool = True

def run_step(step: PipelineStep) -> tuple[bool, str]:
    result = subprocess.run(
        step.command,
        capture_output=True,
        text=True,
    )
    if result.returncode != 0:
        return False, result.stderr.strip()
    if not Path(step.output_path).exists():
        return False, f"Output file not created: {step.output_path}"
    return True, f"Output: {step.output_path}"

PIPELINE_STEPS = [
    PipelineStep(
        "PCAP Ingestion",
        ["python", "ingestion/pcap_parser.py", "--input", "samples/sample.pcap", "--output", "data/connections.csv"],
        "data/connections.csv",
    ),
    PipelineStep(
        "Beaconing Detection",
        ["python", "detection/beaconing_detector.py", "--input", "data/connections.csv", "--output", "data/beacons.json"],
        "data/beacons.json",
    ),
    PipelineStep(
        "RAG Enrichment",
        ["python", "enrichment/pipeline.py", "--input", "data/beacons.json", "--output", "data/enriched_alerts.json"],
        "data/enriched_alerts.json",
    ),
]

def run_pipeline(steps: list[PipelineStep]) -> dict:
    results = []
    for step in steps:
        success, message = run_step(step)
        results.append({"step": step.name, "success": success, "message": message})
        if not success and step.required:
            print(f"FAILED: {step.name} — {message}")
            break
        status = "OK" if success else "SKIP"
        print(f"[{status}] {step.name}: {message}")
    return {"steps": results, "passed": sum(1 for r in results if r["success"])}

# Example call (simulation — does not actually run subprocesses in this exercise)

Concept 3 — GitHub Actions CI for the Portfolio


A portfolio repository with a green CI badge is visually compelling and technically credible. The CI workflow runs on every push: it validates Sigma rules, runs Python syntax checks with ruff, and executes the pipeline in simulation mode. If the badge is green, the reviewer knows the code is not just demo-ware.


This extends the GitHub Actions pattern from W10 into the security domain. The workflow is nearly identical — only the commands differ.


Example:


# .github/workflows/portfolio_ci.yml
name: Portfolio CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  validate:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Lint with ruff
        run: ruff check . --select E,F,W

      - name: Validate Sigma rules
        run: |
          pip install sigma-cli
          sigma-cli validate rules/sigma/*.yml

      - name: Run pipeline simulation
        run: python pipeline_runner.py --simulation
        env:
          SIMULATION_MODE: "true"

      - name: Check output artifacts exist
        run: |
          test -f data/enriched_alerts.json && echo "enriched_alerts.json OK"
          test -f data/anomalies.csv        && echo "anomalies.csv OK"

LLM Integration


Topic: LLM-generated portfolio README from code metadata.
Threat: Auto-generated READMEs from LLMs often include plausible but fabricated claims ("Processes 10M events/second") that a reviewer will attempt to verify and immediately distrust. Every claim in your portfolio README must be reproducible.
Opportunity: Feed your PORTFOLIO_COMPONENTS list and CI_STEPS to an LLM and ask it to draft a README section that is verifiable — every performance claim tied to a specific test, every feature tied to a specific file. The LLM draft removes the blank-page problem; you verify every sentence before committing.

Concept 1 — Production Sigma Rule Quality Standards


A Sigma rule submitted to an employer or open-source rule set will be reviewed against the same checklist as production code: correct MITRE mapping, meaningful description, tuned FP filter, proper logsource definition. Rules that fail these checks are rejected regardless of whether the detection logic is correct.


This concept walks through the review checklist using the three rules built in W13 as the base.


Example:


from dataclasses import dataclass

@dataclass
class SigmaRuleMetadata:
    title: str
    id: str           # UUID format
    status: str       # test | experimental | stable
    description: str
    references: list[str]
    author: str
    date: str         # YYYY-MM-DD
    tags: list[str]   # mitre tags e.g. "attack.t1059.001"
    logsource_category: str
    logsource_product: str
    detection_keywords: list[str]  # simplified; real rules have condition logic
    falsepositives: list[str]
    level: str        # informational | low | medium | high | critical

    def quality_issues(self) -> list[str]:
        issues = []
        if len(self.description) < 30:
            issues.append("description too short — explain what the rule detects and why")
        if not self.tags:
            issues.append("no MITRE ATT&CK tags — add attack.tNNNN")
        if not self.falsepositives:
            issues.append("no falsepositives entry — add at least one known FP scenario")
        if self.status == "stable" and not self.references:
            issues.append("stable rules require at least one reference URL")
        if self.level not in {"informational", "low", "medium", "high", "critical"}:
            issues.append(f"invalid level: {self.level}")
        return issues

powershell_rule = SigmaRuleMetadata(
    title="PowerShell Encoded Command Execution",
    id="a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    status="test",
    description="Detects PowerShell execution with encoded command flag, commonly used to obfuscate malicious scripts",
    references=["https://attack.mitre.org/techniques/T1059/001/"],
    author="Chris Winter",
    date="2026-05-05",
    tags=["attack.execution", "attack.t1059.001"],
    logsource_category="process_creation",
    logsource_product="windows",
    detection_keywords=["-EncodedCommand", "-enc ", "-e "],
    falsepositives=["Legitimate admin scripts using encoded commands for cross-platform compatibility"],
    level="high",
)

issues = powershell_rule.quality_issues()
print(f"Rule: {powershell_rule.title}")

Concept 2 — Detection Coverage Dashboard


The coverage dashboard from W12 showed which ATT&CK techniques are covered by Sigma rules. The capstone version extends this to three layers: rules that exist, rules that have been tested in CI, and rules that have fired at least once against a log sample. A rule that exists but has never been tested or fired is technically "coverage" but practically dead weight.


Example:


from dataclasses import dataclass
from enum import Enum

class RuleMaturity(Enum):
    EXISTS      = "exists"       # rule file exists and validates
    TESTED      = "tested"       # rule ran against log sample, produced expected match
    PRODUCTION  = "production"   # rule deployed, fired at least once in real/simulated data

@dataclass
class CoverageEntry:
    technique_id: str
    technique_name: str
    rule_file: str | None
    maturity: RuleMaturity | None  # None = GAP
    last_fired: str | None         # ISO date or None

    def is_gap(self) -> bool:
        return self.maturity is None

    def maturity_score(self) -> int:
        scores = {None: 0, RuleMaturity.EXISTS: 1, RuleMaturity.TESTED: 2, RuleMaturity.PRODUCTION: 3}
        return scores[self.maturity]

COVERAGE = [
    CoverageEntry("T1059.001", "PowerShell",           "rules/sigma/powershell_encoded.yml", RuleMaturity.TESTED,      "2026-05-01"),
    CoverageEntry("T1071.001", "Web Protocols C2",      "rules/sigma/c2_beaconing.yml",       RuleMaturity.PRODUCTION,  "2026-05-04"),
    CoverageEntry("T1003.001", "LSASS Memory Dump",     "rules/sigma/lsass_dump.yml",         RuleMaturity.EXISTS,      None),
    CoverageEntry("T1078",     "Valid Accounts",         None,                                 None,                     None),
    CoverageEntry("T1566.001", "Spearphishing Attach",  None,                                 None,                     None),
]

def coverage_stats(entries: list[CoverageEntry]) -> dict:
    total = len(entries)
    gaps = sum(1 for e in entries if e.is_gap())
    by_maturity = {}
    for e in entries:
        key = e.maturity.value if e.maturity else "GAP"
        by_maturity[key] = by_maturity.get(key, 0) + 1
    coverage_pct = (total - gaps) / total * 100 if total > 0 else 0.0
    return {"total": total, "gaps": gaps, "coverage_pct": coverage_pct, "by_maturity": by_maturity}

stats = coverage_stats(COVERAGE)
print(f"Coverage: {stats['coverage_pct']:.0f}% ({stats['total'] - stats['gaps']}/{stats['total']} techniques)")
print(f"By maturity: {stats['by_maturity']}")

Concept 3 — YARA Rule Integration


YARA rules from W18 scan file content for malware signatures. The capstone connects YARA into the pipeline: when the RAG enrichment pipeline returns a verdict of ESCALATE, a YARA scan runs on any associated file artifacts. This is the same pattern as a data quality gate — a downstream check that only activates when the upstream signal crosses a threshold.


Example:


from dataclasses import dataclass

@dataclass
class YaraRule:
    rule_name: str
    description: str
    tags: list[str]
    strings: dict[str, str]  # name → pattern
    condition: str

    def to_yara_text(self) -> str:
        tag_str = " ".join(self.tags)
        strings_block = "\n".join(
            f"        ${name} = {pattern}"
            for name, pattern in self.strings.items()
        )
        return f"""rule {self.rule_name} : {tag_str}
{{
    meta:
        description = "{self.description}"
    strings:
{strings_block}
    condition:
        {self.condition}
}}"""

YARA_RULES = [
    YaraRule(
        rule_name="Cobalt_Strike_Beacon_Shellcode",
        description="Detects Cobalt Strike beacon shellcode by MZ header position and config marker",
        tags=["APT", "CobaltStrike", "Shellcode"],
        strings={
            "mz_header":    '"MZ"',
            "config_marker": '{ FC 48 83 E4 F0 }',
            "sleep_mask":    '"sleeptime"',
        },
        condition="$mz_header at 0 and ($config_marker or $sleep_mask)",
    ),
    YaraRule(
        rule_name="Mimikatz_Strings",
        description="Detects Mimikatz credential dumping tool by embedded strings",
        tags=["CredentialDumping", "Mimikatz"],
        strings={
            "sekurlsa":  '"sekurlsa"',
            "wdigest":   '"wdigest"',
            "kerberos":  '"kerberos"',
        },
        condition="2 of ($sekurlsa, $wdigest, $kerberos)",
    ),
]

for rule in YARA_RULES:

LLM Integration


Topic: LLM-assisted detection rule review — using a code review prompt to catch quality issues in Sigma and YARA rules.
Threat: An attacker who has access to the LLM review tool could submit a malformed rule that the LLM rates as "high quality" due to plausible-sounding metadata — while the detection condition silently never matches anything. LLM review is a supplement to, not a replacement for, testing against real log samples.

Concept 1 — Connecting ML Output to Detection Rules


The Isolation Forest anomaly detector from W19 produces a scored CSV. The capstone step converts anomalous scores into actionable alerts that feed the RAG enrichment pipeline. This connection — ML score → alert → enrichment → verdict — is the architecture that modern detection platforms are moving toward.


The key design decision: at what threshold does an anomaly score become an alert? Set it too low and every event becomes an alert; too high and real attacks slip through. This is the precision-recall trade-off applied to detection engineering.


Example:


from dataclasses import dataclass

@dataclass
class AnomalyEvent:
    event_id: str
    timestamp: str
    process_name: str
    parent_process: str
    command_line: str
    anomaly_score: float    # Isolation Forest: < -0.1 = anomalous, lower = more anomalous

@dataclass
class AlertThresholdConfig:
    low_threshold: float    = -0.10   # informational
    medium_threshold: float = -0.25   # medium priority
    high_threshold: float   = -0.50   # high priority — feeds enrichment pipeline

    def classify(self, score: float) -> str:
        if score <= self.high_threshold:
            return "HIGH"
        if score <= self.medium_threshold:
            return "MEDIUM"
        if score <= self.low_threshold:
            return "LOW"
        return "NORMAL"

def events_to_alerts(events: list[AnomalyEvent], config: AlertThresholdConfig) -> list[dict]:
    alerts = []
    for e in events:
        level = config.classify(e.anomaly_score)
        if level == "NORMAL":
            continue
        alerts.append({
            "alert_id":      f"ML-{e.event_id}",
            "severity":      level,
            "source":        "isolation_forest",
            "timestamp":     e.timestamp,
            "process":       e.process_name,
            "parent":        e.parent_process,
            "command_line":  e.command_line,
            "anomaly_score": e.anomaly_score,
            "send_to_enrichment": level == "HIGH",
        })
    return alerts

sample_events = [
    AnomalyEvent("evt-001", "2026-05-05T09:00:00Z", "powershell.exe", "winword.exe",  "powershell -enc abc123", -0.62),
    AnomalyEvent("evt-002", "2026-05-05T09:01:00Z", "cmd.exe",        "explorer.exe", "cmd /c whoami",           -0.18),
    AnomalyEvent("evt-003", "2026-05-05T09:02:00Z", "notepad.exe",    "explorer.exe", "notepad.exe report.txt",   0.05),
]

config = AlertThresholdConfig()
alerts = events_to_alerts(sample_events, config)

from dataclasses import dataclass

@dataclass
class TriageSummary:
    alert_id: str
    verdict: str          # ESCALATE / MONITOR / CLOSE_FP
    confidence: float
    primary_evidence: str
    investigation_steps: list[str]
    explanation: str
    model_used: str
    context_chunks_used: int

@dataclass
class IncidentReport:
    report_id: str
    generated_at: str
    escalated_alerts: list[TriageSummary]
    monitor_alerts: list[TriageSummary]
    closed_alerts: list[TriageSummary]

    def summary_stats(self) -> dict:
        total = len(self.escalated_alerts) + len(self.monitor_alerts) + len(self.closed_alerts)
        return {
            "total": total,
            "escalated": len(self.escalated_alerts),
            "monitor": len(self.monitor_alerts),
            "closed": len(self.closed_alerts),
        }

    def to_markdown(self) -> str:
        stats = self.summary_stats()
        lines = [
            f"# Incident Report {self.report_id}",
            f"Generated: {self.generated_at}",
            "",
            "## Summary",
            f"Total alerts processed: {stats['total']}",
            f"- Escalated: {stats['escalated']}",
            f"- Monitor: {stats['monitor']}",
            f"- Closed (FP): {stats['closed']}",
            "",
        ]
        if self.escalated_alerts:
            lines.append("## Escalated Alerts")
            for alert in self.escalated_alerts:
                lines.append(f"### {alert.alert_id} (confidence: {alert.confidence:.0%})")
                lines.append(f"**Evidence:** {alert.primary_evidence}")
                lines.append(f"**Explanation:** {alert.explanation}")
                lines.append("**Next steps:**")
                for step in alert.investigation_steps:
                    lines.append(f"- {step}")
                lines.append("")
        return "\n".join(lines)

    return sorted(registry, key=lambda m: m.version)[-1]

def model_changelog(registry: list[ModelVersion]) -> list[str]:
    lines = []
    sorted_registry = sorted(registry, key=lambda m: m.version)

        lines.append(f"v{m.version} ({m.trained_on}){f1_delta}: {m.notes}")
    return lines

Concept 1 — The Hiring Manager's 90-Second Test


An Israeli security hiring manager reviewing a candidate GitHub profile has approximately 90 seconds before moving to the next candidate. In that window they look at three things: the root-level README (what is this?), one script chosen at random (can this person code?), and the CI badge (does it run?). Everything else is secondary.


The 90-second test defines what must be true about the portfolio before sending it to any employer: README loads fast with a one-paragraph description and a working example command, every script has a if __name__ == "__main__" block that demonstrates it with hardcoded sample data, and the CI badge is green.

from dataclasses import dataclass

@dataclass
class PortfolioReadinessCheck:
    check_name: str
    passes: bool
    blocker: bool  # if True, must fix before applying
    note: str

def run_readiness_checks(repo_path: str) -> list[PortfolioReadinessCheck]:
    from pathlib import Path
    root = Path(repo_path)
    checks = []

    # Check 1: Root README exists
    readme_exists = (root / "README.md").exists()
    checks.append(PortfolioReadinessCheck(
        "Root README.md exists", readme_exists, True,
        "" if readme_exists else "Create README.md at repo root"
    ))

    # Check 2: CI workflow file exists
    ci_exists = (root / ".github" / "workflows").exists()
    checks.append(PortfolioReadinessCheck(
        "CI workflow defined", ci_exists, True,
        "" if ci_exists else "Create .github/workflows/portfolio_ci.yml"
    ))

    # Check 3: requirements.txt exists
    req_exists = (root / "requirements.txt").exists()
    checks.append(PortfolioReadinessCheck(
        "requirements.txt present", req_exists, True,
        "" if req_exists else "Add requirements.txt with pinned versions"
    ))

    # Check 4: At least one Sigma rule
    sigma_rules = list((root / "rules" / "sigma").glob("*.yml")) if (root / "rules" / "sigma").exists() else []
    checks.append(PortfolioReadinessCheck(
        "Sigma rules present", len(sigma_rules) >= 3, False,
        "" if len(sigma_rules) >= 3 else f"Only {len(sigma_rules)} Sigma rules — target is 3+"
    ))

    return checks

def readiness_summary(checks: list[PortfolioReadinessCheck]) -> str:
    blockers = [c for c in checks if c.blocker and not c.passes]
    warnings = [c for c in checks if not c.blocker and not c.passes]
    if not blockers:
        verdict = "READY TO APPLY"
    else:
        verdict = f"NOT READY — {len(blockers)} blocker(s)"
    lines = [verdict]
    for b in blockers:
        lines.append(f"  [BLOCKER] {b.check_name}: {b.note}")
    for w in warnings:
        lines.append(f"  [WARN]    {b.check_name}: {b.note}")
    return "\n".join(lines)

Concept 2 — Israeli Cybersecurity Market Context for 2026


The Israeli security job market in 2026 has specific structural features that affect how you position yourself. Understanding these features lets you target the right companies with the right framing rather than spraying identical applications.


Three dominant patterns: MSSPs (CyberProof, Sygnia, Cympire, CYREBRO) hire Detection Engineers who can handle multiple client environments simultaneously — tool-agnostic proficiency matters more than deep vendor specialization. Product companies (Cybereason, Claroty, Armis, Ermetic) hire engineers who can build detection logic at platform scale — the ML and pipeline background is the differentiator. Pure startups (many, always in flux) want engineers who can own the detection stack end-to-end with minimal guidance.


Example:

Concept 3 — Sustained Learning After the 24 Weeks


The detection engineering field evolves faster than any 24-week curriculum can track. Sustaining skills after the curriculum means subscribing to the right signal sources, running one lab exercise per week, and contributing to open-source rule sets. This is the difference between a one-time effort and a career trajectory.


Example:


from dataclasses import dataclass

@dataclass
class LearningSignal:
    name: str

    url_hint: str     # keyword, not a live URL

        "1-2 scenarios per week",
        "SOC analyst simulation with real SIEM data — builds practical alert triage speed",
    ),
]

def weekly_learning_plan(sources: list[LearningSignal], hours_per_week: int) -> list[LearningSignal]:
    priority = {"lab": 1, "repo": 2, "newsletter": 3, "blog": 4}
    sorted_sources = sorted(sources, key=lambda s: priority.get(s.type, 5))
    allocated = []
    remaining = hours_per_week
    hours_per_source = {"lab": 2, "repo": 1, "newsletter": 0.5, "blog": 0.5}
    for s in sorted_sources:
        cost = hours_per_source.get(s.type, 1)
        if remaining >= cost:
            allocated.append(s)
            remaining -= cost
    return allocated

plan = weekly_learning_plan(SUSTAINED_LEARNING_SOURCES, hours_per_week=5)
print("Weekly learning plan (5 hours):")
for s in plan:
    print(f"  [{s.type}] {s.name} — {s.frequency}")
