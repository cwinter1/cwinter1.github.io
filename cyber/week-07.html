Concept 1 — The Intelligence Pyramid: Data, Information, Intelligence

Raw security data (a firewall log, a PCAP, a hash) becomes information when it has context (this hash was found on a known-compromised host), and becomes intelligence when it drives a decision (block this hash, hunt for related indicators, update this Sigma rule). The pyramid: Data → Information → Intelligence → Decision.

The three levels of CTI mirror a data platform's architecture. Tactical intelligence (IOCs — IP addresses, domains, hashes, URLs) is like raw event tables: high volume, short shelf-life, queryable. Operational intelligence (TTPs, actor campaigns, attack patterns) is like a processed mart: lower volume, higher value, longer validity. Strategic intelligence (geopolitical context, threat actor motivations, long-term trends) is like an executive dashboard: low volume, very long validity, informs organizational risk posture.

This distinction matters because IOC-only threat intelligence is a treadmill — attackers rotate IPs and domains in hours. TTP-based detection is durable because changing techniques is expensive.

from dataclasses import dataclass, field

from enum import Enum

class IOCType(Enum):
    IP = "ip"
    DOMAIN = "domain"
    SHA256 = "sha256"
    MD5 = "md5"
    URL = "url"
    EMAIL = "email"

class TLPLevel(Enum):
    WHITE = "white"    # public distribution
    GREEN = "green"    # community distribution
    AMBER = "amber"    # organization-only
    RED = "red"        # named recipients only

@dataclass
class IOC:
    value: str
    ioc_type: IOCType
    tlp: TLPLevel
    source: str
    confidence: int          # 0-100
    first_seen: str
    last_seen: str
    tags: list[str] = field(default_factory=list)
    related_actor: str = ""
    related_campaign: str = ""
    expiry_days: int = 30    # IOC shelf life

    def is_expired(self) -> bool:
        last = datetime.fromisoformat(self.last_seen)
        age = (datetime.now() - last).days
        return age > self.expiry_days

    def intel_level(self) -> str:
        if self.related_actor and self.related_campaign:
            return "operational"
        if self.related_actor:
            return "tactical-enriched"
        return "tactical"

Concept 2 — IOC Types and Their Shelf Life


Different IOC types have very different shelf lives — how long they remain valid indicators of compromise. An IP address used as C2 might be rotated within 24 hours. A domain might persist for days to weeks. A file hash (SHA-256) is permanent unless the attacker recompiles. A TTP (e.g., using certutil for download) may persist for years.


The Pyramid of Pain (David Bianco) quantifies this: blocking hash values is trivial for the attacker to bypass (recompile), blocking TTPs is painful (requires redesigning the attack). This hierarchy should drive where you invest detection engineering effort.

# Validate IOC format before inserting into the database
IP_RE = re.compile(
    r"^(?:(?:25[0-5]|2[0-4]\d|[01]?\d\d?)\.){3}(?:25[0-5]|2[0-4]\d|[01]?\d\d?)$"
)
DOMAIN_RE = re.compile(
    r"^(?:[a-zA-Z0-9](?:[a-zA-Z0-9\-]{0,61}[a-zA-Z0-9])?\.)+[a-zA-Z]{2,}$"
)
SHA256_RE = re.compile(r"^[a-fA-F0-9]{64}$")
MD5_RE = re.compile(r"^[a-fA-F0-9]{32}$")

VALIDATORS = {
    IOCType.IP: IP_RE,
    IOCType.DOMAIN: DOMAIN_RE,
    IOCType.SHA256: SHA256_RE,
    IOCType.MD5: MD5_RE,
}

EXPIRY_DEFAULTS = {
    IOCType.IP: 7,
    IOCType.DOMAIN: 30,
    IOCType.SHA256: 365,
    IOCType.MD5: 365,
    IOCType.URL: 14,
    IOCType.EMAIL: 30,
}

def validate_ioc(value: str, ioc_type: IOCType) -> tuple[bool, str]:
    validator = VALIDATORS.get(ioc_type)
    if validator is None:
        return True, ""  # URL and EMAIL — accept without strict validation for now
    if not validator.match(value.strip()):
        return False, f"value '{value}' does not match expected format for {ioc_type.value}"
    return True, ""

def default_expiry(ioc_type: IOCType) -> int:
    return EXPIRY_DEFAULTS.get(ioc_type, 30)

test_values = [
    ("185.220.101.45", IOCType.IP),
    ("256.1.2.3", IOCType.IP),
    ("evil-domain.com", IOCType.DOMAIN),
    ("abc123xyz", IOCType.SHA256),
    ("a" * 64, IOCType.SHA256),
]

for value, ioc_type in test_values:
    valid, error = validate_ioc(value, ioc_type)
    expiry = default_expiry(ioc_type)
    status = f"valid (expiry: {expiry}d)" if valid else f"INVALID: {error}"

Concept 3 — STIX 2.1 and Threat Intelligence Sharing Standards


STIX (Structured Threat Information eXpression) 2.1 is the JSON-based standard for sharing threat intelligence. TAXII (Trusted Automated eXchange of Intelligence Information) is the transport protocol. STIX defines object types: indicator (IOC with a pattern), threat-actor, campaign, attack-pattern (maps to ATT&CK technique), relationship (links objects), malware, tool, course-of-action.


A STIX indicator looks like: [domain-name:value = 'evil.com'] — using a pattern language that can express complex conditions. Most CTI platforms (MISP, OpenCTI, Anomali) export STIX 2.1 bundles that you consume programmatically.


From a data engineering perspective: STIX is a normalized schema for threat objects, just as your data warehouse has dimension tables for customers and products. Parsing STIX bundles is equivalent to loading a vendor-provided dimension table.

        },
        {
            "type": "relationship",
            "id": "relationship--rel1",
            "relationship_type": "uses",
            "source_ref": "threat-actor--apt34",
            "target_ref": "indicator--ioc1",
        },
        {
            "type": "attack-pattern",
            "id": "attack-pattern--t1566",
            "name": "Phishing",
            "external_references": [{"source_name": "mitre-attack", "external_id": "T1566"}],
        },
    ],
}

def parse_stix_bundle(bundle: dict) -> dict:
    """Extract actors, indicators, and relationships from a STIX bundle."""
    actors = {}
    indicators = {}
    relationships = []

    for obj in bundle.get("objects", []):
        obj_type = obj.get("type")
        if obj_type == "threat-actor":
            actors[obj["id"]] = obj
        elif obj_type == "indicator":
            indicators[obj["id"]] = obj
        elif obj_type == "relationship":
            relationships.append(obj)

    return {"actors": actors, "indicators": indicators, "relationships": relationships}

result = parse_stix_bundle(STIX_BUNDLE)
print(f"Actors: {len(result['actors'])}")
print(f"Indicators: {len(result['indicators'])}")
print(f"Relationships: {len(result['relationships'])}")

# Link actors to their indicators
for rel in result["relationships"]:
    if rel["relationship_type"] == "uses":
        actor = result["actors"].get(rel["source_ref"])
        ioc = result["indicators"].get(rel["target_ref"])
        if actor and ioc:
            print(f"  {actor['name']} uses {ioc['name']}: {ioc['pattern']}")

Concept 1 — Threat Actor Taxonomy: Nation-State, Cybercrime, Hacktivist


Not all attackers are the same. Categorizing threat actors by motivation changes your defensive priorities, detection focus, and response posture.


Nation-state actors (APT groups): long dwell time (months to years), sophisticated TTPs, persistent access, espionage or sabotage. Resources: government-funded. Examples with Israeli relevance: APT34/OilRig (Iranian, targets Israeli and MENA finance/government/telecom), APT33 (Iranian energy and aerospace), Lazarus Group (North Korean, financial theft + espionage).


Cybercrime groups: financially motivated, ransomware-as-a-service, credential theft, business email compromise. Faster tempo, more noise. Examples: Scattered Spider, BlackCat/ALPHV, LockBit.


Hacktivists: politically motivated, often target public-facing services for DDoS or defacement. Relevant in Israeli context: groups like Anonymous Sudan, Killnet — target public infrastructure during geopolitical events.

Concept 2 — APT34 Deep Dive: Techniques, Tools, and Israeli Context


APT34 (OilRig / Helix Kitten) is an Iranian state-sponsored group that has been active since at least 2014. It targets government and critical infrastructure in the Middle East and North Africa — with Israel a primary target given geopolitical tensions. The group uses custom malware families (POWRUNER, BONDUPDATER, RDAT, DNSpionage) alongside built-in LOLBins.


Key operational patterns: spearphishing lures related to regional business themes (logistics, finance), use of legitimate cloud services (OneDrive, Dropbox) for C2, DNS tunneling for data exfiltration, and custom PowerShell droppers. Long dwell time — once in, they persist quietly for months harvesting data.


From a defender's standpoint in an Israeli tech company: you should specifically hunt for APT34-linked IOCs, monitor for DNS tunneling patterns (characteristic of RDAT malware), watch for Office macros spawning PowerShell, and track any authentication from IP ranges associated with Iranian infrastructure.

Concept 3 — Threat Feeds: AlienVault OTX, MISP, VirusTotal, and Free Sources


Threat intelligence feeds provide machine-readable IOCs you can ingest, normalize, and act on. Free sources: AlienVault OTX (Open Threat Exchange — pulse-based, community-driven, REST API), abuse.ch (malware hash, URL, and SSL cert feeds), CIRCL MISP (open-source threat sharing platform), EmergingThreats (Snort/Suricata rule feeds), CISA AIS (US government IOCs).


Feed quality matters. Evaluate: freshness (when was this IOC last seen?), confidence (how was it verified?), false positive rate (how often does blocking this indicator break legitimate traffic?), coverage (does this feed cover the threat actors relevant to your sector?).


For Israeli organizations: the Israel National Cyber Directorate (INCD) publishes advisories and IOCs. IsaacCS (Israeli cybersecurity org) and ClearSky (Israeli CTI vendor) publish APT research specifically covering Iranian and Palestinian threat actors.

def fetch_otx_pulse_iocs(pulse_id: str, api_key: str) -> list[dict]:
    """
    Fetch IOCs from an AlienVault OTX pulse.
    In production: GET https://otx.alienvault.com/api/v1/pulses/{pulse_id}/indicators
    Simulated here for offline use.
    """
    # Simulated OTX API response structure
    simulated_response = {
        "results": [
            {"type": "domain", "indicator": "malicious-domain.ru",
             "description": "APT34 C2", "created": "2024-04-01T00:00:00"},
            {"type": "IPv4", "indicator": "185.220.101.45",
             "description": "APT34 C2 server", "created": "2024-04-02T00:00:00"},
            {"type": "FileHash-SHA256",
             "indicator": "a" * 64,
             "description": "POWRUNER dropper", "created": "2024-04-03T00:00:00"},
        ]

    TYPE_MAP = {
        "domain": IOCType.DOMAIN,
        "IPv4": IOCType.IP,
        "FileHash-SHA256": IOCType.SHA256,
        "FileHash-MD5": IOCType.MD5,
        "URL": IOCType.URL,
    }

    iocs = []
    for result in simulated_response["results"]:
        ioc_type = TYPE_MAP.get(result["type"])
        if ioc_type:

                "type": ioc_type.value,
                "source": f"OTX:{pulse_id}",
                "description": result.get("description", ""),
                "first_seen": result["created"],
                "confidence": 70,
            })
    return iocs

Concept 1 — IOC Database Schema Design


An IOC database is a normalized store for threat indicators and their context. The schema mirrors a star schema from data warehousing: a central iocs fact table with dimension tables for sources, actors, and campaigns. This allows you to answer questions like "which actors are associated with this IP?" and "how many IOCs from this feed are still active?"


Key design decisions: use TEXT for IOC values (not VARCHAR with fixed length — URLs can be long), store hashes as TEXT (not BINARY — readability matters), add a normalized_value column that stores the canonical form (lowercase domain, uppercase hash). Index on normalized_value for fast lookups during log enrichment joins.


Example:


import sqlite3
from datetime import datetime

def create_ioc_database(db_path: str) -> sqlite3.Connection:
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row
    cur = conn.cursor()

    cur.executescript("""
        CREATE TABLE IF NOT EXISTS sources (
            source_id INTEGER PRIMARY KEY AUTOINCREMENT,
            name TEXT NOT NULL UNIQUE,
            url TEXT,
            tlp TEXT DEFAULT 'GREEN',
            reliability_score INTEGER DEFAULT 70,
            last_fetched TEXT
        );

        CREATE TABLE IF NOT EXISTS actors (
            actor_id INTEGER PRIMARY KEY AUTOINCREMENT,
            name TEXT NOT NULL UNIQUE,
            aliases TEXT,           -- JSON array stored as TEXT
            nation TEXT,
            motivation TEXT
        );

        CREATE TABLE IF NOT EXISTS iocs (
            ioc_id INTEGER PRIMARY KEY AUTOINCREMENT,
            value TEXT NOT NULL,
            normalized_value TEXT NOT NULL,
            ioc_type TEXT NOT NULL,
            source_id INTEGER REFERENCES sources(source_id),
            actor_id INTEGER REFERENCES actors(actor_id),
            confidence INTEGER DEFAULT 50,
            first_seen TEXT NOT NULL,
            last_seen TEXT NOT NULL,
            expiry_date TEXT,
            tags TEXT,              -- JSON array stored as TEXT
            is_active INTEGER DEFAULT 1,
            created_at TEXT DEFAULT (datetime('now'))
        );

        CREATE INDEX IF NOT EXISTS idx_iocs_normalized ON iocs(normalized_value);
        CREATE INDEX IF NOT EXISTS idx_iocs_type ON iocs(ioc_type);
        CREATE INDEX IF NOT EXISTS idx_iocs_active ON iocs(is_active);
    """)
    conn.commit()
    return conn

def insert_source(conn: sqlite3.Connection, name: str, url: str = "",
                  tlp: str = "GREEN") -> int:
    cur = conn.cursor()
    cur.execute(
        "INSERT OR IGNORE INTO sources (name, url, tlp) VALUES (?, ?, ?)",
        (name, url, tlp)
    )
    conn.commit()
    cur.execute("SELECT source_id FROM sources WHERE name = ?", (name,))
    return cur.fetchone()[0]

conn = create_ioc_database(":memory:")
source_id = insert_source(conn, "AlienVault OTX", "https://otx.alienvault.com")
print(f"Source ID: {source_id}")
print("IOC database schema created successfully")
conn.close()

Concept 2 — Batch Feed Ingestion Pipeline


A real CTI pipeline ingests multiple feeds on a schedule, normalizes them into the standard schema, deduplicates, and marks expired IOCs as inactive. The pipeline should be idempotent: running it twice with the same feed produces the same database state.


This is identical to a data engineering incremental load pattern: fetch new data, upsert (update if exists, insert if new), expire records not seen in the latest feed snapshot. The is_active flag replaces hard-deletes — you want to keep historical IOC data for retrospective threat hunting.


Example:


import json
from datetime import datetime, timedelta

def expire_old_iocs(conn: sqlite3.Connection, max_age_days: int = 90) -> int:
    """Mark IOCs not seen recently as inactive."""
    cutoff = (datetime.now() - timedelta(days=max_age_days)).isoformat()
    cur = conn.cursor()
    cur.execute("""
        UPDATE iocs
        SET is_active = 0
        WHERE last_seen < ?
        AND is_active = 1
    """, (cutoff,))
    conn.commit()
    return cur.rowcount

def ingest_feed(conn: sqlite3.Connection, feed_data: list[dict],
                source_name: str) -> dict:
    """
    Ingest a normalized feed into the IOC database.
    Returns stats: inserted, updated, skipped.
    """
    source_id = insert_source(conn, source_name)
    stats = {"inserted": 0, "updated": 0, "skipped": 0}

    for record in feed_data:
        try:
            result = insert_ioc(
                conn=conn,
                value=record["value"],
                ioc_type=record["type"],
                source_id=source_id,
                actor_id=None,
                confidence=record.get("confidence", 50),
                first_seen=record.get("first_seen", datetime.now().isoformat()),
                last_seen=record.get("last_seen", datetime.now().isoformat()),
                tags=record.get("tags", []),
            )
            if result["action"] == "inserted":
                stats["inserted"] += 1
            else:
                stats["updated"] += 1
        except Exception:
            stats["skipped"] += 1

    return stats

Concept 3 — Enrichment Queries: Joining IOCs to Log Events


The value of an IOC database is realized when you join it against live or historical log data. In SQL terms: SELECT * FROM log_events JOIN iocs ON log_events.dst_ip = iocs.normalized_value WHERE iocs.is_active = 1. This is identical to identity enrichment from W04 — same JOIN pattern, different dimension table.


Enrichment also works retroactively: when you add a new IOC, run it against historical logs going back 30–90 days to find past compromise. This retroactive hunting is one of the highest-value CTI use cases — discovering that an attacker was present before you knew about the IOC.


Example:


def enrich_logs_with_iocs(conn: sqlite3.Connection,
                           log_events: list[dict],
                           lookback_fields: list[tuple[str, str]]) -> list[dict]:
    """
    Enrich log events with IOC matches.
    lookback_fields: list of (log_field_name, ioc_type) to check
    Returns: log events with 'ioc_hits' key added (empty list if no match)
    """
    cur = conn.cursor()
    enriched = []

    for event in log_events:
        hits = []
        for log_field, ioc_type in lookback_fields:
            value = event.get(log_field, "")
            if not value:
                continue
            normalized = value.lower().strip()
            cur.execute("""
                SELECT ioc_id, value, ioc_type, confidence, tags
                FROM iocs
                WHERE normalized_value = ?
                AND ioc_type = ?
                AND is_active = 1
            """, (normalized, ioc_type))
            rows = cur.fetchall()
            for row in rows:
                hits.append({
                    "matched_field": log_field,
                    "matched_value": value,
                    "ioc_type": row["ioc_type"],
                    "confidence": row["confidence"],
                    "tags": json.loads(row["tags"]) if row["tags"] else [],
                })
        enriched.append({**event, "ioc_hits": hits, "is_threat": len(hits) > 0})

    return enriched

print("Alert trigger: event.is_threat = True → SIEM alert or SOAR playbook")

Concept 1 — The Diamond Model of Intrusion Analysis


The Diamond Model (Caltagirone, Pendergast, Betz 2013) describes every adversarial event as four linked vertices: Adversary (who attacked), Capability (tools/techniques used), Infrastructure (IPs, domains, C2 servers), and Victim (what was targeted). The model defines relationships between vertices and allows analysts to pivot from any known vertex to discover others.


If you know the infrastructure (C2 IP), you can find other campaigns using the same IP (pivot to capability and adversary). If you know the capability (specific malware family), you find all victims and infrastructure. This pivoting logic drives threat hunting: start with what you know, expand systematically.


In data engineering terms: this is a graph traversal problem. The Diamond Model is a graph where nodes are adversary/capability/infrastructure/victim objects and edges are "uses/targets" relationships.


Example:


from dataclasses import dataclass, field

@dataclass
class DiamondEvent:
    event_id: str
    adversary: str          # actor name or "unknown"
    capability: str         # malware family, tool, or TTP
    infrastructure: str     # C2 IP or domain
    victim: str             # organization or asset
    timestamp: str
    confidence: int         # 0-100
    meta_features: dict = field(default_factory=dict)  # business, political, military, diplomatic

EVENTS = [
    DiamondEvent("evt1", "APT34", "POWRUNER", "185.220.101.45",
                 "FinanceCorp_IL", "2024-03-15", 85,
                 {"sector": "finance", "country": "Israel"}),
    DiamondEvent("evt2", "APT34", "BONDUPDATER", "185.220.101.45",
                 "TelecomCo_AE", "2024-03-20", 80,
                 {"sector": "telecom", "country": "UAE"}),
    DiamondEvent("evt3", "unknown", "POWRUNER", "94.177.123.138",
                 "GovAgency_SA", "2024-04-01", 60,
                 {"sector": "government", "country": "Saudi Arabia"}),
]

def pivot_by_infrastructure(events: list[DiamondEvent], ip: str) -> list[DiamondEvent]:
    """Find all events sharing the same C2 infrastructure."""
    return [e for e in events if e.infrastructure == ip]

def pivot_by_capability(events: list[DiamondEvent], capability: str) -> list[DiamondEvent]:
    """Find all events using the same malware/tool."""
    return [e for e in events if capability.lower() in e.capability.lower()]

def cluster_by_adversary(events: list[DiamondEvent]) -> dict[str, list[DiamondEvent]]:
    """Group events by attributed adversary."""
    clusters = {}
    for event in events:
        clusters.setdefault(event.adversary, []).append(event)
    return clusters

# Pivot: same IP as evt1 → find related campaigns

print(f"Infrastructure pivot on 185.220.101.45: {len(related)} events")
for e in related:
    print(f"  {e.event_id}: {e.adversary} used {e.capability} against {e.victim}")

# Capability pivot: POWRUNER across all campaigns
powruner_use = pivot_by_capability(EVENTS, "POWRUNER")
print(f"\nCapability pivot on POWRUNER: {len(powruner_use)} events")

Concept 2 — Hunt Hypothesis Framework


Threat hunting is proactive search for adversary activity that has not triggered any alerts. A hypothesis is a testable statement: "APT34 may have used DNS tunneling to exfiltrate data from our environment in the last 30 days." A hypothesis should be: specific (not "look for malware"), testable (maps to a query or data source), falsifiable (you know what a positive and negative result look like).


The hypothesis-to-query pipeline: hypothesis → identify data source → write detection query → baseline normal activity → define anomaly threshold → review results → document findings → if positive: escalate incident; if negative: document as hunted and move on.


Good hypothesis sources: current threat intelligence (APT34 uses DNS tunneling — do we have DNS logs?), known TTPs of threat actors relevant to your sector, recent security reports, ATT&CK data sources (what logs are needed to detect technique X?), and your own alert coverage gaps from the W05 coverage matrix.


Example:

Concept 1 — Feed Consumer Architecture


A production CTI feed consumer runs on a schedule (daily or hourly), fetches from multiple sources, normalizes to a common schema, deduplicates, stores in the IOC database, and produces a delta report (new IOCs since last run, expired IOCs, IOCs with updated confidence). It is a mini-ETL pipeline where the source systems are threat feeds and the destination is the IOC database.


The architecture mirrors a data engineering incremental load: extract (fetch from APIs), transform (normalize, validate, deduplicate), load (upsert into SQLite with conflict resolution). The key operational metric: freshness lag — how old are your current IOCs relative to the threat?


Example:


import sqlite3
import json
from datetime import datetime

class CTIFeedConsumer:
    def __init__(self, db_path: str):
        self.conn = create_ioc_database(db_path)
        self.run_stats = {
            "run_time": datetime.now().isoformat(),
            "feeds_processed": 0,
            "iocs_inserted": 0,
            "iocs_updated": 0,
            "iocs_expired": 0,
        }

    def add_feed(self, name: str, url: str, tlp: str = "GREEN") -> int:
        return insert_source(self.conn, name, url, tlp)

    def ingest(self, feed_data: list[dict], source_name: str) -> dict:
        result = ingest_feed(self.conn, feed_data, source_name)
        self.run_stats["iocs_inserted"] += result.get("inserted", 0)
        self.run_stats["iocs_updated"] += result.get("updated", 0)
        self.run_stats["feeds_processed"] += 1
        return result

    def expire(self, max_age_days: int = 30) -> int:
        count = expire_old_iocs(self.conn, max_age_days)
        self.run_stats["iocs_expired"] = count
        return count

    def summary(self) -> dict:
        cur = self.conn.cursor()
        cur.execute("SELECT COUNT(*) FROM iocs WHERE is_active = 1")
        active = cur.fetchone()[0]
        cur.execute("SELECT COUNT(*) FROM iocs WHERE is_active = 0")
        expired = cur.fetchone()[0]
        return {
            **self.run_stats,
            "total_active_iocs": active,
            "total_expired_iocs": expired,
        }

    def close(self):
        self.conn.close()

Concept 2 — IOC Lookup Integration with the Log Pipeline


The IOC database becomes useful when it is joined to the log enrichment pipeline from W04. The complete chain: raw logs → normalize (W01–W03) → identity enrichment (W04) → IOC enrichment (W07) → output as annotated events. Each event now carries both identity context and threat intelligence context.


This forms the foundation of a basic detection pipeline: if ioc_hits is non-empty, the event is a candidate alert. The confidence of the IOC and the sensitivity of the log source (LSASS access vs. HTTP request) determine the alert severity.


Example:


def build_enriched_pipeline(
    log_events: list[dict],
    identity_data: dict,        # from W04: {user_id → identity dict}
    ioc_conn: sqlite3.Connection,
    ioc_fields: list[tuple[str, str]],  # [(log_field, ioc_type), ...]
) -> list[dict]:
    """
    Full W01–W07 enrichment pipeline:
    1. Identity enrichment (W04 pattern)
    2. IOC enrichment (W07)
    3. Severity scoring
    """
    enriched = []
    for event in log_events:
        result = dict(event)

        # Step 1: Identity enrichment
        user_id = event.get("user_id", "")
        if user_id in identity_data:
            identity = identity_data[user_id]
            result["department"] = identity.get("department", "unknown")
            result["is_admin"] = identity.get("is_admin", False)
            result["account_type"] = identity.get("account_type", "human")

        # Step 2: IOC enrichment
        ioc_hits = []
        cur = ioc_conn.cursor()
        for log_field, ioc_type in ioc_fields:
            value = event.get(log_field, "")
            if not value:
                continue
            cur.execute(
                "SELECT confidence, tags FROM iocs WHERE normalized_value = ? AND ioc_type = ? AND is_active = 1",
                (str(value).lower().strip(), ioc_type)
            )
            row = cur.fetchone()
            if row:
                ioc_hits.append({
                    "field": log_field, "value": value,
                    "confidence": row[0], "tags": row[1]
                })

        result["ioc_hits"] = ioc_hits
        result["threat_score"] = max((h["confidence"] for h in ioc_hits), default=0)
        result["is_threat"] = len(ioc_hits) > 0
        enriched.append(result)

    return sorted(enriched, key=lambda x: x["threat_score"], reverse=True)

print("Full enrichment pipeline: identity (W04) + IOC (W07) = annotated events with threat score")

Concept 3 — Royal Road Deliverable: pipeline/w07_cti_consumer.py


The complete W07 Royal Road artifact integrates everything from this week: the IOC dataclass with validation, the SQLite schema, the feed ingest pipeline with upsert logic, the enrichment query, and a CLI that accepts a feed JSON file and a log events JSON file, enriches the logs, and writes alerts to a JSON output file.


The script is a standalone command-line tool: python w07_cti_consumer.py --feed feed.json --logs events.json --db ioc.db --output alerts.json. It follows the same CLI pattern as w04_enrich.py, extending the pipeline chain.


Example:


#!/usr/bin/env python3
"""
w07_cti_consumer.py — CTI feed consumer and log enrichment pipeline.

Usage:
    python w07_cti_consumer.py --feed feed.json --logs events.json --db ioc.db --output alerts.json
"""
import argparse
import json
import sqlite3
import sys
import uuid
from pathlib import Path
from datetime import datetime

def parse_args() -> argparse.Namespace:
    p = argparse.ArgumentParser(description="CTI feed consumer and log enrichment")
    p.add_argument("--feed", type=Path, required=True, help="JSON feed file")
    p.add_argument("--logs", type=Path, required=True, help="JSON log events file")
    p.add_argument("--db", type=Path, default=Path("pipeline/ioc.db"), help="SQLite DB path")
    p.add_argument("--output", type=Path, required=True, help="JSON output alerts file")
    p.add_argument("--threshold", type=int, default=70, help="Alert threshold (0-100)")
    return p.parse_args()

def main():
    args = parse_args()

    # 1. Initialize/open IOC database
    conn = create_ioc_database(str(args.db))

    # 2. Ingest feed
    with args.feed.open() as f:
        feed_data = json.load(f)
    source_id = insert_source(conn, "cli_feed")
    stats = ingest_feed(conn, feed_data, "cli_feed")
    print(f"Feed ingested: {stats}", file=sys.stderr)

    # 3. Load log events
    with args.logs.open() as f:
        log_events = json.load(f)

    # 4. Enrich and generate alerts
    ioc_fields = [("dst_domain", "domain"), ("dst_ip", "ip"), ("file_hash", "sha256")]
    enriched = build_enriched_pipeline(log_events, {}, conn, ioc_fields)

    alerts = []
    for event in enriched:
        alert = generate_alert(event, threshold=args.threshold)
        if alert:
            alerts.append(alert)

    # 5. Write output
    with args.output.open("w") as f:
        json.dump(alerts, f, indent=2)
    print(f"Wrote {len(alerts)} alerts to {args.output}", file=sys.stderr)
    conn.close()

if __name__ == "__main__":
    main()
