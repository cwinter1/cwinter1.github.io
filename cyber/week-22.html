Concept 1 — The Analyst Knowledge Problem

A junior SOC analyst looking at an alert for the first time faces an information access problem: the alert contains a technique ID, a hostname, and some raw telemetry. To make a triage decision, they need context that lives in three places: (1) institutional knowledge ("this host is the CI/CD server, PowerShell on it is expected"), (2) threat intelligence ("this technique was used by APT33 against Israeli financial sector last quarter"), and (3) past incidents ("we saw this exact pattern 10 days ago on a different host"). A senior analyst has this context in their head. A junior analyst needs to search 4 different systems manually.

RAG (Retrieval-Augmented Generation) solves this by storing that context in a vector database and retrieving the most relevant chunks at query time before passing them to an LLM for synthesis. The LLM does not need to "know" the answers — it only needs to reason over the retrieved chunks. This is important for security because hallucinated threat intel is worse than no answer.

Data engineering analogy: RAG is a lookup join on the LLM's reasoning step. Instead of letting the model generate from weights alone, you JOIN the model's context against a curated knowledge base before it generates the answer — the same reason you enrich a Kafka event with a reference table before writing to the data warehouse.

Example:

from dataclasses import dataclass, field
import hashlib


@dataclass
class KnowledgeChunk:
    chunk_id: str
    source: str            # "runbook", "threat_intel", "incident_history", "asset_inventory"
    content: str
    tags: list[str] = field(default_factory=list)
    technique_ids: list[str] = field(default_factory=list)

    @classmethod
    def from_text(cls, source: str, content: str, tags: list[str] = None,
                  technique_ids: list[str] = None) -> "KnowledgeChunk":
        chunk_id = hashlib.sha256(f"{source}:{content}".encode()).hexdigest()[:12]
        return cls(
            chunk_id=chunk_id,
            source=source,
            content=content,
            tags=tags or [],
            technique_ids=technique_ids or [],
        )

    def word_count(self) -> int:
        return len(self.content.split())

Concept 2 — Embeddings and Semantic Similarity


An embedding is a fixed-size vector of floating-point numbers that encodes the semantic meaning of a text. Two texts that mean similar things will have vectors that are close together in the embedding space (high cosine similarity). This is what allows a vector database to retrieve "T1071.001 triage steps" even when the query says "how do I handle C2 beaconing alerts".


In production, embeddings are computed by a model (OpenAI text-embedding-3-small, Anthropic embeddings, or open-source models like sentence-transformers). For this course, we simulate embeddings using keyword-based overlap scoring — which is conceptually equivalent for understanding the retrieval mechanism, without the API dependency.


Cosine similarity between two vectors A and B is: (A · B) / (|A| × |B|). In the keyword simulation, we represent each chunk as a set of keywords and compute Jaccard similarity (intersection / union) as a stand-in.


Example:


import re
from dataclasses import dataclass


STOPWORDS = {"the", "a", "an", "is", "are", "was", "were", "for", "of", "to", "in",
             "on", "at", "by", "with", "this", "that", "be", "it", "from", "as",
             "or", "and", "if", "has", "have", "had"}


def tokenize(text: str) -> set[str]:
    tokens = re.findall(r"[a-z0-9_\.\-]+", text.lower())
    return {t for t in tokens if t not in STOPWORDS and len(t) > 2}


def jaccard_similarity(set_a: set[str], set_b: set[str]) -> float:
    if not set_a and not set_b:
        return 0.0
    intersection = len(set_a & set_b)
    union = len(set_a | set_b)
    return intersection / union


@dataclass
class RetrievalResult:
    chunk: KnowledgeChunk
    score: float


def retrieve_top_k(query: str, kb: list[KnowledgeChunk], k: int = 3) -> list[RetrievalResult]:
    query_tokens = tokenize(query)
    scored = []
    for chunk in kb:
        chunk_tokens = tokenize(chunk.content + " " + " ".join(chunk.tags + chunk.technique_ids))
        score = jaccard_similarity(query_tokens, chunk_tokens)
        scored.append(RetrievalResult(chunk=chunk, score=score))
    scored.sort(key=lambda r: r.score, reverse=True)
    return scored[:k]

Concept 3 — The RAG Context Window


When the LLM generates a triage summary, it receives: the system prompt, the alert data, and the retrieved chunks. The total must fit within the context window. Context budget planning is a design constraint, not a nice-to-have.


Typical budget for an alert enrichment call:


    

  • System prompt: ~500 tokens
    • 

  • Alert data: ~300 tokens
    • 

  • Retrieved chunks (top-3 at 200 tokens each): ~600 tokens
    • 

  • Reserve for output: 500 tokens
    • 

  • Total: ~1,900 tokens per alert call
    • 



With claude-sonnet-4-6 at 200K token context, a single alert is trivially small. The constraint appears when you batch alerts: 1,000 alerts per hour × 1,900 tokens = 1.9M tokens/hour. At $3/1M input tokens, that is $5.70/hour for input alone. At scale, chunking strategy (how many tokens per chunk, how many chunks retrieved) directly affects cost.


Example:


from dataclasses import dataclass


TOKENS_PER_WORD_APPROX = 1.33


def estimate_tokens(text: str) -> int:
    return int(len(text.split()) * TOKENS_PER_WORD_APPROX)


@dataclass
class ContextBudget:
    total_window: int
    system_prompt_tokens: int
    alert_tokens: int
    output_reserve: int

    def available_for_retrieval(self) -> int:
        return self.total_window - self.system_prompt_tokens - self.alert_tokens - self.output_reserve

    def max_chunks(self, avg_chunk_tokens: int) -> int:
        return max(0, self.available_for_retrieval() // avg_chunk_tokens)

    def utilization(self, retrieved_chunks: list[KnowledgeChunk]) -> dict:
        retrieval_tokens = sum(estimate_tokens(c.content) for c in retrieved_chunks)
        total_used = self.system_prompt_tokens + self.alert_tokens + retrieval_tokens
        return {
            "system_prompt": self.system_prompt_tokens,
            "alert": self.alert_tokens,
            "retrieval": retrieval_tokens,
            "total_used": total_used,
            "remaining": self.total_window - total_used - self.output_reserve,
            "utilization_pct": total_used / self.total_window,
        }


SYSTEM_PROMPT = """You are a SOC triage assistant. Using the provided context, generate a structured
triage summary for the alert. Include: verdict (ESCALATE/MONITOR/CLOSE_FP), confidence (0.0-1.0),
key evidence used, and the next 3 investigation steps for the analyst."""

budget = ContextBudget(
    total_window=200_000,
    system_prompt_tokens=estimate_tokens(SYSTEM_PROMPT),
    alert_tokens=300,
    output_reserve=500,
)

retrieved = [r.chunk for r in retrieve_top_k("T1071.001 beaconing alert", KNOWLEDGE_BASE, k=3)]
util = budget.utilization(retrieved)

print(f"Available for retrieval: {budget.available_for_retrieval():,} tokens")
print(f"Max chunks (avg 150 tokens): {budget.max_chunks(150)}")
print(f"\nContext utilization:")
for k, v in util.items():
    if isinstance(v, float):
        print(f"  {k}: {v:.1%}")
    else:
        print(f"  {k}: {v:,}")

Concept 1 — ChromaDB Basics (Simulated)


ChromaDB is an open-source vector database designed for Python applications. It stores documents alongside their embeddings and provides similarity search in a single API call. For this course we simulate ChromaDB's interface without requiring the library — allowing the full pipeline to run in any Python environment.


The ChromaDB API surface we care about:


    

  • client.create_collection(name) → collection object
    • 

  • collection.add(documents=[], metadatas=[], ids=[]) → stores chunks
    • 

  • collection.query(query_texts=[], n_results=k) → returns top-k similar chunks with distances
    • 



Distance in ChromaDB uses cosine distance (1 - cosine_similarity), so lower distance = more relevant. Our simulation uses 1 - Jaccard similarity as the distance metric.


Example:


from dataclasses import dataclass, field
from typing import Any


@dataclass
class SimulatedCollection:
    name: str
    _documents: list[str] = field(default_factory=list)
    _metadatas: list[dict] = field(default_factory=list)
    _ids: list[str] = field(default_factory=list)

    def add(self, documents: list[str], metadatas: list[dict], ids: list[str]) -> None:
        if len(documents) != len(ids):
            raise ValueError("documents and ids must have the same length")
        self._documents.extend(documents)
        self._metadatas.extend(metadatas)
        self._ids.extend(ids)

    def query(self, query_texts: list[str], n_results: int = 3) -> dict[str, list]:
        all_results: dict[str, list] = {"documents": [], "metadatas": [], "distances": [], "ids": []}

        for query_text in query_texts:
            q_tokens = tokenize(query_text)
            scored: list[tuple[float, int]] = []
            for i, doc in enumerate(self._documents):
                doc_tokens = tokenize(doc)
                similarity = jaccard_similarity(q_tokens, doc_tokens)
                distance = 1.0 - similarity
                scored.append((distance, i))
            scored.sort(key=lambda x: x[0])
            top = scored[:n_results]

            all_results["documents"].append([self._documents[i] for _, i in top])
            all_results["metadatas"].append([self._metadatas[i] for _, i in top])
            all_results["distances"].append([d for d, _ in top])
            all_results["ids"].append([self._ids[i] for _, i in top])

        return all_results

    def count(self) -> int:
        return len(self._ids)


class SimulatedChromaClient:
    def __init__(self):
        self._collections: dict[str, SimulatedCollection] = {}

    def create_collection(self, name: str) -> SimulatedCollection:
        if name in self._collections:
            return self._collections[name]
        col = SimulatedCollection(name=name)
        self._collections[name] = col
        return col

    def get_collection(self, name: str) -> SimulatedCollection:
        if name not in self._collections:
            raise KeyError(f"Collection '{name}' does not exist")
        return self._collections[name]

Concept 2 — Ingesting the Knowledge Base


A production SOC knowledge base has multiple source types: runbooks (structured Markdown), threat intelligence reports (PDF or JSON), incident history (SIEM exports), asset inventory (CMDB exports). Each source requires a different ingest adapter that normalizes the content into KnowledgeChunk format before loading into the vector store.


Chunking strategy: documents longer than ~300 words should be split into overlapping chunks (50-word overlap prevents context loss at chunk boundaries). Short entries (asset inventory rows, IOC records) can be stored as single chunks. The chunk size directly affects retrieval quality — too large and irrelevant content dilutes the similarity score; too small and a single chunk lacks enough context for the LLM to reason from.


Example:


from dataclasses import dataclass


def split_into_chunks(text: str, max_words: int = 150, overlap_words: int = 30) -> list[str]:
    words = text.split()
    if len(words) <= max_words:
        return [text]
    chunks: list[str] = []
    step = max_words - overlap_words
    for start in range(0, len(words), step):
        chunk_words = words[start:start + max_words]
        chunks.append(" ".join(chunk_words))
        if start + max_words >= len(words):
            break
    return chunks


@dataclass
class IngestStats:
    source: str
    raw_documents: int
    chunks_produced: int
    avg_words_per_chunk: float

    def __str__(self) -> str:
        return (f"IngestStats(source={self.source}, raw_docs={self.raw_documents}, "
                f"chunks={self.chunks_produced}, avg_words={self.avg_words_per_chunk:.0f})")


def ingest_runbook(runbook_text: str, source_tag: str,
                   technique_ids: list[str] = None) -> tuple[list[KnowledgeChunk], IngestStats]:
    raw_chunks = split_into_chunks(runbook_text, max_words=150, overlap_words=25)
    result: list[KnowledgeChunk] = []
    for i, chunk_text in enumerate(raw_chunks):
        chunk = KnowledgeChunk.from_text(
            source=source_tag,
            content=chunk_text,
            tags=["runbook", f"chunk_{i}"],
            technique_ids=technique_ids or [],
        )
        result.append(chunk)
    stats = IngestStats(
        source=source_tag,
        raw_documents=1,
        chunks_produced=len(result),
        avg_words_per_chunk=sum(c.word_count() for c in result) / max(1, len(result)),
    )
    return result, stats

Concept 3 — Querying and Result Ranking


Retrieved chunks must be ranked and filtered before being sent to the LLM. Two reasons: (1) a chunk with very low similarity (distance > 0.9) is probably noise and will confuse the LLM more than help it; (2) duplicate or near-duplicate chunks from the same source waste context window budget.


Post-retrieval filtering steps:


    

  1. Distance threshold: drop any chunk with distance > MAX_DISTANCE (typically 0.85 for Jaccard-based simulation, lower for real embeddings)
    2. 

  2. Source deduplication: if two chunks have the same source and high overlap, keep only the higher-ranked one
    3. 

  3. Relevance explanation: for each retained chunk, record which query terms it matched — this becomes part of the audit trail for the LLM's decision
    4. 



Example:


MAX_DISTANCE = 0.90


def filter_retrieved_results(
    results: dict[str, list],
    query_index: int = 0,
    max_distance: float = MAX_DISTANCE,
) -> list[tuple[str, dict, float]]:
    docs = results["documents"][query_index]
    metas = results["metadatas"][query_index]
    distances = results["distances"][query_index]
    ids = results["ids"][query_index]

    filtered: list[tuple[str, dict, float]] = []
    seen_sources: set[str] = set()

    for doc, meta, dist, chunk_id in zip(docs, metas, distances, ids):
        if dist > max_distance:
            continue
        source = meta.get("source", "unknown")
        if source in seen_sources:
            continue
        seen_sources.add(source)
        filtered.append((doc, meta, dist))

    return filtered


def format_context_for_llm(filtered: list[tuple[str, dict, float]]) -> str:
    sections: list[str] = []
    for i, (doc, meta, dist) in enumerate(filtered, 1):
        source = meta.get("source", "unknown")
        sections.append(f"[Context {i} | source: {source} | relevance: {1-dist:.2f}]\n{doc}")
    return "\n\n---\n\n".join(sections)


test_results = collection.query(query_texts=["PowerShell execution macro parent T1059"], n_results=4)

print(f"Retrieved: {len(test_results['documents'][0])}  After filtering: {len(filtered)}")
print("\nFormatted context block:")

Concept 1 — Structured Output for Triage Summaries


An LLM that produces free-form text for triage is unusable in production. An analyst cannot parse a paragraph when they are working an incident under time pressure. The LLM output must be structured — a JSON object with defined fields that a downstream system can read programmatically.


Structured output patterns (from W10): use a system prompt that constrains the output format, provide a JSON schema as part of the prompt, and parse the response with validation. If the LLM returns malformed JSON, retry once with an explicit correction prompt before falling back to a default low-confidence verdict.


For alert enrichment, the triage summary schema must include: verdict, confidence, primary evidence used (which chunks were decisive), investigation steps, and a human-readable explanation. The explanation is the one free-text field — everything else is typed.

Concept 2 — Retry and Fallback Logic


LLM calls fail. The model returns malformed JSON, the API times out, or the confidence is too low to act on. A production RAG enrichment pipeline must handle each of these cases without losing the alert.


Retry strategy for LLM calls:


    

  1. First attempt: full context (retrieved chunks + alert)
    2. 

  2. If JSON parse fails: retry with correction prompt ("Your previous response was not valid JSON. Try again.")
    3. 

  3. If confidence < 0.50: retry with expanded context (fetch more chunks, increase n_results)
    4. 

  4. If all retries fail: emit a MANUAL_REVIEW verdict with all raw enrichment data attached — never silently drop
    5. 



This is the same retry-with-backoff pattern from W3 (API reliability), applied to LLM calls.


Example:


import time
from dataclasses import dataclass


@dataclass
class LLMCallResult:
    success: bool
    summary: TriageSummary | None
    attempts: int
    failure_reason: str = ""


def call_llm_with_retry(
    alert: dict,
    context_block: str,
    max_attempts: int = 3,
    min_confidence: float = 0.50,
) -> LLMCallResult:
    alert_id = alert.get("alert_id", "unknown")

    for attempt in range(1, max_attempts + 1):
        try:
            prompt = build_triage_prompt(alert, context_block)
            summary = simulate_llm_triage(prompt, alert_id)

            if summary.confidence < min_confidence:
                if attempt < max_attempts:
                    continue  # retry with broader context
                # Final attempt still low confidence
                summary.verdict = "MONITOR"
                summary.investigation_steps.insert(0, "Manual review required — low model confidence")

            return LLMCallResult(success=True, summary=summary, attempts=attempt)

        except Exception as e:
            if attempt == max_attempts:
                fallback = TriageSummary(
                    alert_id=alert_id,
                    verdict="MONITOR",
                    confidence=0.0,
                    primary_evidence=[],
                    investigation_steps=["Manual review required — all LLM attempts failed"],
                    explanation=f"Enrichment failed after {max_attempts} attempts: {e}",
                    model_used="fallback",
                    context_chunks_used=0,
                )
                return LLMCallResult(success=False, summary=fallback,
                                     attempts=attempt, failure_reason=str(e))
            time.sleep(0.1 * attempt)

    return LLMCallResult(success=False, summary=None, attempts=max_attempts, failure_reason="max retries")


result = call_llm_with_retry(alert_data, context_block)
print(f"Success: {result.success}  Attempts: {result.attempts}")
if result.summary:
    print(f"Verdict: {result.summary.verdict}  Confidence: {result.summary.confidence:.0%}")

Concept 3 — Audit Trail for LLM Decisions


Every LLM-generated triage decision must be auditable. An analyst reviewing the decision three weeks later must be able to answer: what context did the model see, what did it produce, which analyst reviewed it, and was it correct?


The audit record must be immutable — once written, it cannot be modified. In practice this means append-only storage (a log file, a write-once S3 bucket, or a database table with no UPDATE permissions for the enrichment service account). The record must include the full prompt (or a hash if privacy-sensitive), the full response, and the final human-confirmed verdict.

Concept 2 — Streaming Output for Real-Time SOC


For a real-time SOC dashboard, waiting for the full LLM response before displaying anything creates latency. Streaming output shows the analyst the triage reasoning as it is generated — they can start reading the explanation while the model is still generating the investigation steps.


Streaming is an LLM API feature: instead of returning the full response in one HTTP body, the API sends server-sent events (SSE) with partial response chunks. In Python, this is stream=True on the Anthropic client, which returns a context manager that yields MessageStreamEvent objects.


For our simulation, we implement streaming by yielding characters one at a time from the pre-built response string — same concept, no API required.


Example:


import time
from typing import Generator


def simulate_streaming_llm(prompt: str, alert_id: str) -> Generator[str, None, None]:
    summary = simulate_llm_triage(prompt, alert_id)
    full_response = summary.to_json()
    # Simulate streaming: yield one character at a time with tiny delay
    for char in full_response:
        yield char
        time.sleep(0.001)  # 1ms per character simulates ~500 tokens/sec


def consume_stream(stream: Generator[str, None, None], display_live: bool = False) -> str:
    buffer = ""
    for chunk in stream:
        buffer += chunk
        if display_live:
            print(chunk, end="", flush=True)
    return buffer


def streaming_pipeline_step(alert_dict: dict, context_block: str) -> str:
    prompt = build_triage_prompt(alert_dict, alert_dict.get("alert_id", ""))
    stream = simulate_streaming_llm(prompt, alert_dict.get("alert_id", ""))
    complete_response = consume_stream(stream, display_live=False)
    return complete_response


response_text = streaming_pipeline_step(alert_data, context_block)
print(f"Streamed {len(response_text)} characters")
print(f"Valid JSON: ", end="")
try:
    json.loads(response_text)
    print("yes")

    print(f"no — {e}")

Concept 1 — Pipeline Monitoring and Observability


A production enrichment pipeline must emit metrics that the SOC team can monitor. The three critical metrics: (1) pipeline success rate (fraction of alerts successfully enriched), (2) model decision distribution (what fraction of verdicts are ESCALATE vs. MONITOR vs. CLOSE_FP), (3) mean latency per alert.


Decision distribution drift is the most important signal: if the model's ESCALATE rate jumps from 12% to 40% overnight, either the threat landscape changed dramatically or the model is misconfigured. Either way, a human needs to investigate.


Example:

    success_count: int = 0
    failure_count: int = 0
    verdict_counts: dict[str, int] = field(default_factory=lambda: defaultdict(int))
    latency_ms_list: list[float] = field(default_factory=list)

    def record(self, output: PipelineOutput, verdict: str | None) -> None:
        self.total_alerts += 1
        if output.success:
            self.success_count += 1
            if verdict:
                self.verdict_counts[verdict] += 1
        else:
            self.failure_count += 1
        self.latency_ms_list.append(output.pipeline_latency_ms)

    def success_rate(self) -> float:
        return self.success_count / max(1, self.total_alerts)

    def p95_latency_ms(self) -> float:
        if not self.latency_ms_list:
            return 0.0
        sorted_lat = sorted(self.latency_ms_list)
        idx = int(len(sorted_lat) * 0.95)
        return sorted_lat[min(idx, len(sorted_lat) - 1)]

    def verdict_distribution(self) -> dict[str, float]:
        total = sum(self.verdict_counts.values())
        if total == 0:
            return {}
        return {k: v / total for k, v in self.verdict_counts.items()}

    def drift_detected(self, baseline_escalation_rate: float, threshold: float = 0.20) -> bool:
        current = self.verdict_distribution().get("ESCALATE", 0.0)
        return abs(current - baseline_escalation_rate) > threshold

    def to_json(self) -> str:
        return json.dumps({
            "window_start": self.window_start,
            "window_end": self.window_end,
            "total_alerts": self.total_alerts,
            "success_rate": self.success_rate(),
            "p95_latency_ms": self.p95_latency_ms(),
            "verdict_distribution": self.verdict_distribution(),
        }, indent=2)


metrics = PipelineMetrics(
    window_start=datetime.now(timezone.utc).isoformat(),
    window_end=datetime.now(timezone.utc).isoformat(),
)

sample_outputs = [

Concept 2 — Knowledge Base Maintenance


A RAG knowledge base degrades without maintenance. Old runbooks become stale when procedures change. Threat intel about TTPs from three years ago may no longer reflect current actor behavior. Incident history from before a major network redesign may mislead the LLM about which hosts are high-risk.


Maintenance operations: (1) TTL-based expiry — each chunk has a valid_until date; the pipeline skips expired chunks; (2) usage tracking — chunks that are never retrieved in 90 days are candidates for deletion; (3) conflict detection — if two chunks contradict each other (one says host X is safe, another says X is compromised), flag for human review.


Example:


from dataclasses import dataclass, field
from datetime import date, timedelta


@dataclass
class ManagedChunk(KnowledgeChunk):
    created_date: str = ""
    valid_until: str = ""   # ISO date string, "" = never expires
    retrieval_count: int = 0
    last_retrieved: str = ""

    def is_expired(self, as_of: date = None) -> bool:
        if not self.valid_until:
            return False
        check_date = as_of or date.today()
        return date.fromisoformat(self.valid_until) < check_date

    def is_stale(self, no_retrieval_days: int = 90, as_of: date = None) -> bool:
        if not self.last_retrieved:
            # Never retrieved — stale if older than threshold
            if not self.created_date:
                return False
            check_date = as_of or date.today()
            created = date.fromisoformat(self.created_date)
            return (check_date - created).days > no_retrieval_days
        check_date = as_of or date.today()
        last = date.fromisoformat(self.last_retrieved)
        return (check_date - last).days > no_retrieval_days


def audit_knowledge_base(chunks: list[ManagedChunk], as_of: date = None) -> dict:
    as_of = as_of or date.today()
    expired = [c for c in chunks if c.is_expired(as_of)]
    stale = [c for c in chunks if not c.is_expired(as_of) and c.is_stale(as_of=as_of)]
    active = [c for c in chunks if not c.is_expired(as_of) and not c.is_stale(as_of=as_of)]
    return {
        "total": len(chunks),
        "active": len(active),
        "expired_ids": [c.chunk_id for c in expired],
        "stale_ids": [c.chunk_id for c in stale],
    }

Concept 3 — End-to-End Coverage Map


The final deliverable for Phase 6 is a coverage map that shows which detection gaps the AI/LLM pipeline addresses and which remain. This closes out the detection coverage thread started in W12 (coverage dashboard) and continued in W19 (ML anomaly coverage).


For the LLM enrichment pipeline specifically, coverage means: which alert types are enriched with relevant context (good retrieval), which are enriched but the model hallucinates (low confidence output), and which receive no context (knowledge base gap).


Example:


from dataclasses import dataclass
from enum import Enum


class EnrichmentCoverage(Enum):

def print_coverage_summary(coverage_map: list[EnrichmentCoverageEntry]) -> None:
    from collections import Counter
    counts = Counter(e.coverage.value for e in coverage_map)
    total_in_scope = sum(1 for e in coverage_map if e.coverage != EnrichmentCoverage.EXCLUDED)
    full = counts.get("full", 0)
    print(f"Enrichment Coverage Summary")
    print(f"{'='*40}")
    print(f"In scope:  {total_in_scope} techniques")
    print(f"Full:      {full} ({full/max(1,total_in_scope):.0%})")
    print(f"Partial:   {counts.get('partial', 0)}")
    print(f"Gap:       {counts.get('gap', 0)}")
    print(f"Excluded:  {counts.get('excluded', 0)}")
    print()
    for entry in coverage_map:
        icon = {"full": "+", "partial": "~", "gap": "!", "excluded": "-"}[entry.coverage.value]
        conf = f"conf={entry.avg_model_confidence:.0%}" if entry.avg_model_confidence else "no data"
