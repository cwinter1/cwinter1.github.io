 CONCEPT 1 — NAVIGATION & FILE OPERATIONS
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Every pipeline runs on a Linux server. You need to navigate directories,
 find files, and move data between folders from the terminal.

 Think of it this way:
 ─────────────────────
 A file system is a building with rooms inside rooms. The terminal is your
 set of legs — pwd tells you which room you are standing in, ls reads the
 contents of the room, and cd walks you through a doorway into the next
 room. pathlib is Python's printed floor plan of that same building, letting
 you describe any room by address and open doors without leaving your script.

 Key points:
 ───────────
 1. Always use pathlib.Path in Python code instead of string concatenation.
    Path(dir) / 'subdir' constructs correct paths on Windows and Linux
    without manual slash handling.
 2. Never call shutil.rmtree without first confirming the path is what you
    intend. There is no recycle bin on a Linux server.
 3. Use mkdir(parents=True, exist_ok=True) in every pipeline setup step
    so the script is idempotent — safe to run more than once.
 4. Knowing bash commands matters even as a Python developer: you read
    cron logs, diagnose stuck jobs, and write deployment scripts all from
    the terminal.

 Essential commands and their Python equivalents:
   bash: pwd                  Python: os.getcwd()
   bash: ls -la               Python: list(Path(dir).iterdir())
   bash: mkdir -p dir         Python: Path(dir).mkdir(parents=True, exist_ok=True)
   bash: cp src dst           Python: shutil.copy(src, dst)
   bash: mv src dst           Python: Path(src).rename(dst)
   bash: rm file              Python: Path(file).unlink()
   bash: rm -rf dir           Python: shutil.rmtree(dir)

 On Windows: bash commands run in Git Bash or WSL.
 In Python scripts: use os and pathlib — they work on every platform.
 Knowing both is essential: you write Python locally, deploy to Linux.

EXAMPLE ──────────────────────────────────────────────────────
import os
import shutil
from pathlib import Path

# pwd equivalent
print('Current dir:', os.getcwd())

# mkdir equivalent — create nested directories
workspace = Path('demo_workspace')
(workspace / 'raw' / 'csv').mkdir(parents=True, exist_ok=True)
(workspace / 'processed').mkdir(parents=True, exist_ok=True)
print('Subdirs created:', [str(p) for p in workspace.rglob('*') if p.is_dir()])

# Create a sample file, then copy and rename it
sample = workspace / 'raw' / 'csv' / 'sales.csv'
sample.write_text('date,amount\n2024-01-01,500\n2024-01-02,600\n')
shutil.copy(sample, workspace / 'processed' / 'sales_backup.csv')   # cp
(workspace / 'processed' / 'sales_backup.csv').rename(              # mv
    workspace / 'processed' / 'sales_final.csv')

# ls equivalent — list files with sizes
print('\nFiles in processed/:')
for f in (workspace / 'processed').iterdir():
    print(f'  {f.name}  ({f.stat().st_size} bytes)')

shutil.rmtree(workspace)
print('\nWorkspace removed.')

 CONCEPT 2 — ENVIRONMENT VARIABLES
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Environment variables pass configuration to scripts without hardcoding
 values. Every pipeline uses them for: database passwords, API keys,
 environment names (dev/staging/prod).

 Think of it this way:
 ─────────────────────
 An environment variable is a sticky note on the server's fridge.
 The script reads it when it starts up. You change the note to switch
 between dev and prod — the script code stays identical.

 Key points:
 ───────────
 1. Always use os.environ.get('KEY', 'default') over os.environ['KEY']
    — the bracket form raises KeyError and crashes the pipeline.
 2. Never hardcode credentials in Python files. Anyone with read access
    to the repo gets the password.
 3. Add .env to .gitignore before the first commit. After it is committed
    once, deleting it does not remove it from git history.
 4. Validate all required env vars at the top of the script — fail fast
    with a clear error rather than crashing 5 minutes into a pipeline run.

   bash: export DB_HOST=localhost    — set for the current shell session
   bash: echo $DB_HOST              — read it back
   bash: python script.py           — script inherits the shell environment

 In Python:
   os.environ['KEY']           — read, raises KeyError if missing
   os.environ.get('KEY')       — read, returns None if missing
   os.environ.get('KEY', 'x')  — read with a default fallback

 Never hardcode credentials in Python files.
 Never commit .env files to git — add .env to .gitignore.

EXAMPLE ──────────────────────────────────────────────────────
import os

# Set variables for this process
os.environ['PIPELINE_ENV'] = 'staging'
os.environ['DB_PORT']      = '5432'

# Three ways to read an env var
env_name = os.environ['PIPELINE_ENV']           # KeyError if missing
db_port  = os.environ.get('DB_PORT', '5432')    # fallback default
api_key  = os.environ.get('API_KEY', '')        # empty string default

print(f'Environment : {env_name}')
print(f'DB port     : {db_port}')
print(f'API key set : {bool(api_key)}')

# Validate required variables before the pipeline starts
def validate_env(required):
    missing = [v for v in required if not os.environ.get(v)]
    if missing:
        raise EnvironmentError(f'Missing required env vars: {missing}')
    print('All required env vars present.')

validate_env(['PIPELINE_ENV', 'DB_PORT'])

try:
    validate_env(['PIPELINE_ENV', 'SECRET_TOKEN'])
except EnvironmentError as e:
    print(f'Config error: {e}')

 CONCEPT 3 — RUNNING PYTHON SCRIPTS FROM THE TERMINAL
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Data pipelines run as scripts, not notebooks. You launch them from
 the terminal and pass arguments to control their behaviour.

 Think of it this way:
 ─────────────────────
 A script is a function called from the shell. The --flags are its
 arguments. The exit code is its return value — 0 means success, anything
 else means failure. The calling process (Airflow, cron, CI) checks that
 return value to decide what to do next.

 Key points:
 ───────────
 1. Use argparse, not sys.argv directly. argparse gives you --help,
    type conversion, and required/optional validation for free.
 2. Always call sys.exit(0) on success and sys.exit(1) on failure.
    Schedulers like Airflow rely on exit codes to mark tasks as passed
    or failed.
 3. Chain scripts with && — the second command only runs if the first
    exits 0. This stops a broken extract from triggering a broken load.
 4. Log both stdout and stderr with 2>&1 | tee pipeline.log so you can
    read the log later even if the terminal is closed.

   bash: python ingest.py --source orders --limit 5000
   bash: python etl.py && python validate.py   (chain: only run next on success)
   bash: python etl.py 2>&1 | tee pipeline.log  (log stdout and stderr)

 sys.argv: list where [0] is the script name, [1]+ are your arguments.

 argparse (standard library) is the right tool for parsing arguments:
   parser = argparse.ArgumentParser()
   parser.add_argument('--source', required=True)
   args = parser.parse_args()

 Exit codes signal success or failure to the calling process:
   sys.exit(0)  — success
   sys.exit(1)  — failure

EXAMPLE ──────────────────────────────────────────────────────
import argparse

# In a real script: parser.parse_args() reads sys.argv automatically.
# Here we pass a list directly so the notebook cell can demonstrate it.
def parse_pipeline_args(argv):
    parser = argparse.ArgumentParser(description='Run the ETL pipeline')
    parser.add_argument('--source',  required=True,       help='Source table')
    parser.add_argument('--limit',   type=int, default=10000)
    parser.add_argument('--dry-run', action='store_true')
    return parser.parse_args(argv)

# Simulate: python etl.py --source sales --limit 500
args = parse_pipeline_args(['--source', 'sales', '--limit', '500'])
print(f'Source  : {args.source}')
print(f'Limit   : {args.limit}')
print(f'Dry-run : {args.dry_run}')

# Simulate: python etl.py --source orders --dry-run
args2 = parse_pipeline_args(['--source', 'orders', '--dry-run'])
print(f'\nSource  : {args2.source}')
print(f'Limit   : {args2.limit}')
print(f'Dry-run : {args2.dry_run}')

 CONCEPT 4 — PIPES, FILTERING & TEXT PROCESSING
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Pipes chain commands so the output of one becomes the input of the next.

 Think of it this way:
 ─────────────────────
 A pipe is an assembly line. Each worker does one thing and passes the
 result to the next. cat reads the file. grep keeps only matching lines.
 sort orders them. uniq -c counts duplicates. No worker stores everything
 — the data flows through.

 Key points:
 ───────────
 1. | chains commands — the stdout of the left side becomes the stdin
    of the right side. Equivalent to function chaining in Python.
 2. > overwrites the output file. >> appends to it. Use >> in pipelines
    so each run adds to the log rather than deleting the previous run.
 3. 2>&1 merges stderr into stdout — captures both in the same stream.
    Essential when you want to log errors alongside normal output.
 4. Python equivalents: splitlines() splits, list comprehension filters
    (grep), sorted() sorts, Counter counts duplicates (uniq -c).

   bash: cat pipeline.log | grep ERROR | sort | uniq -c
         reads the log, keeps only ERROR lines, sorts, counts duplicates

   bash: python etl.py > output.log 2>&1   redirect stdout+stderr to file
   bash: python etl.py >> output.log        append instead of overwrite

 Python equivalents:
   str.splitlines()           split a block of text into lines
   [l for l in lines if x]   grep equivalent — filter
   sorted(lines)              sort equivalent
   collections.Counter        count duplicates

EXAMPLE ──────────────────────────────────────────────────────
from collections import Counter

LOG_TEXT = """
2024-03-01 06:00:01 INFO     Pipeline started
2024-03-01 06:00:03 INFO     Extracted 12000 rows
2024-03-01 06:00:05 WARNING  Null values found in column: region
2024-03-01 06:00:07 ERROR    DB connection timeout -- retrying
2024-03-01 06:00:10 INFO     Retry succeeded
2024-03-01 06:00:12 ERROR    Row 4521 failed schema validation
2024-03-01 06:00:14 INFO     Loaded 11998 rows
2024-03-01 06:00:15 INFO     Pipeline complete
"""

lines = [l for l in LOG_TEXT.splitlines() if l.strip()]

# grep equivalent: filter by keyword
errors   = [l for l in lines if 'ERROR'   in l]
warnings = [l for l in lines if 'WARNING' in l]
print(f'Errors ({len(errors)}):')
for l in errors: print('  ', l)
print(f'\nWarnings ({len(warnings)}):')
for l in warnings: print('  ', l)

# uniq -c equivalent: count log levels
levels = [l.split()[2] for l in lines]
print('\nLog level counts:', dict(Counter(levels)))

 CONCEPT 1 — GIT FUNDAMENTALS
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Git tracks every change to your codebase as a commit — a snapshot with
 a message, author, and timestamp. This gives you a complete history and
 the ability to roll back any mistake.

 Think of it this way:
 ─────────────────────
 A commit is a named save point in a video game. git add is the moment
 you walk to the save station and choose which items to carry forward.
 git commit is pressing save — the game records exactly where you are,
 what you have, and what you named this checkpoint. If the next level
 breaks the game, you load back to the save point and try a different path.

 Key points:
 ───────────
 1. Use conventional commit format (type(scope): description) so your
    team can scan history, generate changelogs, and filter by type.
 2. Never use git add . blindly. Stage specific files or use git add -p
    to review each chunk — committing unintended files (secrets, binaries)
    is hard to undo once pushed.
 3. git diff --staged before every commit. If the diff surprises you,
    unstage and reconsider. The commit message should match what you see.

 Core commands:
   git init            create a new repository in the current folder
   git status          show what has changed since the last commit
   git add file        stage a file (mark it for the next commit)
   git add -p          stage changes interactively, chunk by chunk
   git commit -m 'msg' save staged changes as a new commit
   git log --oneline   show the commit history, one line per commit
   git diff            show unstaged changes
   git diff --staged   show staged changes

 Conventional commit format (industry standard):
   type(scope): short description
   Examples: feat(ingest): add retry logic for API timeouts
             fix(transform): handle null region column
             chore(deps): upgrade pandas to 2.2

EXAMPLE ──────────────────────────────────────────────────────
# This example demonstrates git operations in a temporary folder.
# Run in your terminal to see real git output.
import subprocess, os, shutil, tempfile

repo = tempfile.mkdtemp(prefix='git_demo_')

def git(cmd, cwd=repo):
    result = subprocess.run(
        ['git'] + cmd.split(), cwd=cwd,
        capture_output=True, text=True
    )
    if result.stdout.strip(): print(result.stdout.strip())
    if result.returncode != 0 and result.stderr.strip():
        print('STDERR:', result.stderr.strip())

git('init')
git('config user.email ci@example.com')
git('config user.name CI')

# Create a file and make the first commit
open(os.path.join(repo, 'pipeline.py'), 'w').write('# ETL pipeline\n')
git('add pipeline.py')
git('commit -m "feat(pipeline): initial skeleton"')

# Make a change and commit
open(os.path.join(repo, 'pipeline.py'), 'w').write('# ETL pipeline\n\ndef run(): pass\n')
git('add pipeline.py')
git('commit -m "feat(pipeline): add run() stub"')

git('log --oneline')
shutil.rmtree(repo)

══════════════════════════════════════════════════════════════
 CONCEPT 2 — BRANCHING & MERGING
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Branches let you work on a feature without touching the main codebase.
 When the feature is ready, you merge it back.

 Think of it this way:
 ─────────────────────
 A branch is a photocopy of the published document. You mark it up, cross
 things out, and rewrite sections on the copy — the original stays clean.
 If the draft is good, you apply the changes to the original. If the draft
 fails, you shred the photocopy and the original is untouched.

 Key points:
 ───────────
 1. Never commit directly to main. Every change, however small, gets a
    branch. This makes code review possible and rollback trivial.
 2. Delete branches after merging. Stale branches accumulate quickly and
    obscure which work is actually in progress.
 3. Prefer fast-forward merges for feature branches — they keep history
    linear. Reserve merge commits for release integrations.

   git branch                    list all branches
   git checkout -b feature/name  create and switch to a new branch
   git checkout main             switch back to main
   git merge feature/name        merge a branch into the current branch
   git branch -d feature/name    delete a branch after merging

 Branch naming conventions:
   feature/add-retry-logic
   fix/null-region-column
   chore/upgrade-pandas

 Fast-forward merge: main has not moved since you branched — git just
 advances the pointer. No merge commit needed.

 Three-way merge: both main and your branch have new commits — git
 creates a merge commit combining both histories.

EXAMPLE ──────────────────────────────────────────────────────
import subprocess, os, shutil, tempfile

repo = tempfile.mkdtemp(prefix='branch_demo_')

def git(cmd, cwd=repo):
    r = subprocess.run(['git'] + cmd.split(), cwd=cwd,
                       capture_output=True, text=True)
    if r.stdout.strip(): print(r.stdout.strip())

git('init'); git('config user.email ci@example.com'); git('config user.name CI')
open(os.path.join(repo, 'etl.py'), 'w').write('def extract(): pass\n')
git('add etl.py'); git('commit -m "feat: initial commit"')

# Create feature branch
git('checkout -b feature/add-transform')
open(os.path.join(repo, 'etl.py'), 'a').write('def transform(): pass\n')
git('add etl.py'); git('commit -m "feat(etl): add transform stub"')

# Merge back to main
git('checkout main')
git('merge feature/add-transform')
git('log --oneline')
git('branch -d feature/add-transform')
git('branch')

shutil.rmtree(repo)

 CONCEPT 3 — REMOTE WORKFLOWS & PULL REQUESTS
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 A remote (usually GitHub) is the shared copy of the repository.
 The PR (pull request) is the review step before code reaches main.

 Think of it this way:
 ─────────────────────
 GitHub is the office whiteboard that everyone can read. Your laptop is
 your personal notepad. You draft changes on the notepad, then raise your
 hand and say "check this before I write it on the whiteboard." The team
 reviews your notes, approves them, and only then does the whiteboard
 get updated — so the shared record is always reviewed work.

 Key points:
 ───────────
 1. Push a feature branch, never main. Opening a PR from a feature branch
    makes it reviewable, revertable, and visible to the team.
 2. Write a PR description that includes what changed, why, and how to
    test it. A reviewer who cannot understand the PR quickly will approve
    it without looking closely.
 3. Use git pull --rebase instead of git pull to avoid noisy merge commits
    when syncing your local main with the remote.

   git remote add origin <url>   connect local repo to a remote
   git push -u origin main       push main branch and track remote
   git push origin feature/name  push a feature branch
   git pull                      fetch + merge remote changes
   git fetch                     fetch without merging

 PR lifecycle:
   1. Push your feature branch to GitHub
   2. Open a PR: title, description, test plan, screenshots
   3. Request reviewers — they comment, approve, or request changes
   4. Address feedback with new commits to the same branch
   5. Merge once approved (squash merge keeps history clean)
   6. Delete the feature branch

 Good PR title: feat(ingest): add exponential backoff for API retries
 Bad PR title:  fixed stuff

EXAMPLE ──────────────────────────────────────────────────────
# A PR description template — fill this in before opening a PR.
# Good descriptions save review time and prevent back-and-forth.

def build_pr_description(title, summary_points, test_steps, risk_level='low'):
    """Build a structured PR description string."""
    lines = [
        f'## {title}',
        '',
        '## Summary',
    ]
    for point in summary_points:
        lines.append(f'- {point}')
    lines += ['', '## Test plan']
    for i, step in enumerate(test_steps, 1):
        lines.append(f'- [ ] {step}')
    lines += ['', f'**Risk:** {risk_level}']
    return '\n'.join(lines)

desc = build_pr_description(
    title='feat(ingest): add exponential backoff for API retries',
    summary_points=[
        'Retries failed requests up to 3 times with 2x backoff',
        'Logs each retry attempt with status code and wait time',
    ],
    test_steps=[
        'Unit test: mock requests.get to return 429, assert retry fires',
        'Integration test: run against staging API, check logs',
    ],
    risk_level='low',
)
print(desc)

 CONCEPT 4 — CODE REVIEWS
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Code review is how teams catch bugs, share knowledge, and maintain
 standards before code reaches production.

 Think of it this way:
 ─────────────────────
 A code review is a second pair of eyes on a document before it goes to
 print. The reviewer is not a fault-finder — they are a collaborator who
 catches what the author is too close to see. A good reviewer points at
 a specific sentence and says "this sentence will confuse the reader
 because..." rather than handing back a red-marked page with no explanation.

 Key points:
 ───────────
 1. Review comments must explain the problem, not just the preferred style.
    "This will raise KeyError on missing keys" is actionable.
    "Use a dict comprehension" is not.
 2. Prefix style-only suggestions with 'nit:' so the author knows it is
    optional and does not block the merge.
 3. git blame before commenting — if a line you question was written six
    months ago for a reason, git show <hash> may explain the why before
    you ask.

 Key git commands for reviewing:
   git log --oneline --graph   visual branch history
   git diff main..feature      see all changes in a feature branch
   git blame file              who last changed each line and when
   git show <commit>           show one commit's full diff

 What a good review comment looks like:
   BAD:  'This is wrong.'
   BAD:  'Use a list comprehension here.'
   GOOD: 'This will raise KeyError if region is not in VALID_REGIONS.
          Consider using .get() with a fallback, or validate upstream.'

 A good review comment explains the PROBLEM and suggests a direction,
 not just a style preference. Use 'nit:' for minor style suggestions
 that the author can take or leave.

 CONCEPT 5 — REBASE, CHERRY-PICK & SYNCING WITH MAIN
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 The most common real-world git problem: you branch from main, work for
 several days, and teammates merge PRs into main while you are working.
 Your branch is now behind. Rebase replays your commits on top of the
 latest main so your branch looks like it was created today.

 Think of it this way:
 ─────────────────────
 Your branch is a train car you detached from the main train to do
 interior work. While you were working, the main train added new cars
 and moved forward. Rebase lifts your car off the old track position and
 re-attaches it to the front of the current train, so your changes sit
 on top of everyone else's, in a clean unbroken sequence.

 Key points:
 ───────────
 1. Rebase feature branches onto main before opening a PR. Reviewers see
    your changes against the latest code, not code from days ago.
 2. Never rebase a branch that other people have already checked out.
    Rebase rewrites commit hashes — shared branches will diverge.
 3. Use --force-with-lease, not --force, after rebasing a pushed branch.
    It fails if someone else pushed since your last fetch, so you cannot
    accidentally overwrite their work.
 4. cherry-pick is for taking one specific fix from another branch without
    merging the whole branch — useful when a teammate's bug fix is in a
    PR that is not yet merged and you need it now.

 git rebase vs git merge:
   - rebase  : rewrites history — your commits move on top of main.
               Result is a clean, linear history. Preferred for feature branches.
   - merge   : creates a merge commit combining both histories.
               Avoid merging main into a feature branch — it clutters history.

 Commands:
   git fetch origin              download remote changes, do not merge
   git rebase origin/main        replay your commits on top of latest main
   git rebase --continue         continue after resolving a conflict
   git rebase --abort            cancel — returns to pre-rebase state
   git cherry-pick <hash>        apply one specific commit onto current branch
   git push --force-with-lease   safe force push after rebase

 The diverged-branch scenario step by step:
   1. git fetch origin               — see what main looks like now
   2. git log origin/main --oneline  — confirm how far behind you are
   3. git rebase origin/main         — replay your commits on top
   4. fix conflicts if any, then git rebase --continue
   5. git push --force-with-lease    — update the remote branch

 cherry-pick: apply one commit from any branch onto your current branch.
 Useful when a teammate fixed a bug you need now, without waiting for
 their full PR to be merged.

   git cherry-pick <hash>   — the hash from git log --oneline

 After rebasing a branch you already pushed, use --force-with-lease
 instead of --force. It fails safely if someone else pushed since you
 last fetched, preventing you from overwriting their work.

EXAMPLE ──────────────────────────────────────────────────────
import subprocess, os, shutil, tempfile

repo = tempfile.mkdtemp(prefix='rebase_demo_')

def git(cmd, cwd=repo):
    r = subprocess.run(['git'] + cmd.split(), cwd=cwd,
                       capture_output=True, text=True)
    if r.stdout.strip(): print(r.stdout.strip())
    return r

git('init')
git('config user.email ci@example.com')
git('config user.name CI')

# --- initial commit on main ---
open(os.path.join(repo, 'etl.py'), 'w').write('def extract(): pass\n')
git('add etl.py')
git('commit -m "feat: initial ETL skeleton"')

# --- teammate adds a commit to main ---
open(os.path.join(repo, 'etl.py'), 'a').write('def load(): pass\n')
git('add etl.py')
git('commit -m "feat(load): add load stub"')

# --- you branch off the FIRST commit (simulate being behind) ---
git('checkout -b feature/add-transform HEAD~1')
open(os.path.join(repo, 'transform.py'), 'w').write('def transform(df): return df\n')
git('add transform.py')
git('commit -m "feat(transform): add transform function"')

print('\n--- before rebase: diverged history ---')
git('log --oneline --graph --all')

# --- sync with main via rebase ---
git('rebase main')

print('\n--- after rebase: linear history ---')
git('log --oneline --graph --all')

# --- cherry-pick: grab one specific commit from another branch ---
git('checkout main')
git('checkout -b fix/hotfix')
open(os.path.join(repo, 'etl.py'), 'a').write('def validate(): pass\n')
git('add etl.py')
git('commit -m "fix: add validate() for data quality"')

    ['git', 'rev-parse', '--short', 'HEAD'], cwd=repo,
    capture_output=True, text=True
).stdout.strip()

git('checkout feature/add-transform')
git(f'cherry-pick {hotfix_hash}')

print('\n--- after cherry-pick ---')
git('log --oneline')

shutil.rmtree(repo)

 CONCEPT 6 — SECURITY GATE: SECRETS HYGIENE (CIA: C)
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Analogy: the site foreman who checks every worker's toolbelt before
 they enter the construction zone — no classified documents, no master keys.

 The #1 source of credential leaks is git add . without checking what
 was staged. A secret that reaches GitHub is compromised immediately —
 even deleting the commit leaves the history in forks and caches.

 Production tools (conceptual — no install needed for this exercise):
 ─────────────────────────────────────────────────────────────────────
 - detect-secrets (Yelp): scans every file for high-entropy strings and
   known secret patterns before the commit is written
 - pre-commit: runs the scanner as a git hook — the commit is blocked
   if any pattern fires
 - .gitignore hygiene: .env, *.pem, credentials.json must be excluded
   before they are ever committed — deleting after is not sufficient

 Three pattern families this gate covers:
   API keys   : assignments to api_key / apikey / api-key
   Passwords  : assignments to password / passwd / pwd
   Tokens     : assignments to token / secret / access_key / credential

 Pattern form matched: keyword = "value"  or  keyword = 'value'
 where value is at least 4 characters (avoids matching empty strings).

 Cognitive story:
 ─────────────────
 The agent runs a pre-flight scan on the project directory before every
 pipeline deployment. If any secret pattern is detected in source files,
 deployment is blocked and the file + line number is reported.

EXAMPLE ──────────────────────────────────────────────────────
import re, os, tempfile, shutil

SECRET_PATTERNS = [
    r'(?i)(api[_\-]?key|password|passwd|pwd|token|secret|access[_\-]?key|credential)\s*=\s*["\'][^"\']{4,}["\']',
]

# Demo — write two files: one clean, one with a secret
demo_dir = tempfile.mkdtemp()
with open(os.path.join(demo_dir, 'config.py'), 'w', encoding='utf-8') as f:
    f.write('DEBUG = True\n')
    f.write('api_key = "sk-prod-abc123xyz"\n')
    f.write('LOG_LEVEL = "INFO"\n')
    f.write('password = "hunter2"\n')

with open(os.path.join(demo_dir, 'clean.py'), 'w', encoding='utf-8') as f:
    f.write('BATCH_SIZE = 100\n')
    f.write('SOURCE_TABLE = "orders"\n')

report = {}
for root, _, files in os.walk(demo_dir):
    for fname in files:
        if not fname.endswith(('.py', '.env', '.yaml', '.yml', '.json', '.txt')):
            continue
        fpath = os.path.join(root, fname)
        try:
            with open(fpath, encoding='utf-8') as f:
                lines = f.readlines()
        except (OSError, UnicodeDecodeError):
            continue
        hits = [i + 1 for i, line in enumerate(lines)
                if any(re.search(p, line) for p in SECRET_PATTERNS)]
        if hits:
            report[fpath] = hits

for path, line_nums in report.items():
    print(f'[SECRETS] {os.path.basename(path)}: lines {line_nums}')

shutil.rmtree(demo_dir)
