 CONCEPT 1 — TRANSFORMATIONS ARE LAZY, ACTIONS RUN
══════════════════════════════════════════════════════════════
Spark does not run anything when you call filter(), select() or withColumn().
It only records a plan. Work starts when you call an ACTION: show(), count(),
collect(), write(). This lets Spark look at the whole plan and optimize it
before touching any data.

  Transformations (lazy): select, filter, withColumn, groupBy, join, orderBy
  Actions (run now)     : show, count, collect, take, write

Why it matters: if a cell "finishes instantly" it probably only built a plan.
If a later cell is slow, that cell paid for all the earlier lazy steps.

EXAMPLE ──────────────────────────────────────────────────────
import time

rows = [("C%04d" % i, ["West", "East", "Central"][i % 3], float(100 + (i * 37) % 900)) for i in range(60000)]
claims_big = spark.createDataFrame(rows, ["claim_id", "region", "amount"])

t0 = time.time()
lazy = claims_big.filter(F.col("amount") > 500).withColumn("amount_k", F.col("amount") / 1000)
t_lazy = time.time() - t0

t0 = time.time()
n = lazy.count()
t_action = time.time() - t0

print("Transformations only returned in under 1 second:", t_lazy < 1.0)
print("Rows after the filter (action ran the plan)   :", n)
print("Type of 'lazy'                                :", type(lazy).__name__)

 CONCEPT 3 — PARTITIONS AND THE SHUFFLE (EXCHANGE)
══════════════════════════════════════════════════════════════
Spark splits data into partitions and runs one task per partition.

  Narrow transformation: each output partition needs ONE input partition
      (filter, select, withColumn). Cheap, no data moves.
  Wide transformation: output partitions need data from MANY input partitions
      (groupBy, join, orderBy, distinct). Data is moved across the network.
      This movement is called a SHUFFLE and shows up as "Exchange" in the plan.

Shuffles are the main cost in Spark jobs. Reading a plan for Exchange nodes is
the first skill of Spark tuning.

EXAMPLE ──────────────────────────────────────────────────────
import io
import re
import contextlib


def plan_text(dataframe):
    buffer = io.StringIO()
    with contextlib.redirect_stdout(buffer):
        dataframe.explain()
    return buffer.getvalue()


narrow_plan = plan_text(claims_big.filter(F.col("amount") > 500).select("claim_id"))
wide_plan = plan_text(claims_big.groupBy("region").count())

print("Partitions of claims_big:", claims_big.rdd.getNumPartitions())
print("Narrow plan has Exchange:", "Exchange" in narrow_plan)
print("Wide plan has Exchange  :", "Exchange" in wide_plan)

for line in wide_plan.splitlines():
    if "Exchange" in line:
        print("Shuffle node:", re.sub(r"#\d+|,?\s*ENSURE_REQUIREMENTS|,?\s*\[plan_id=\d+\]", "", line.strip().lstrip("+- ")))

 CONCEPT 1 — SPARK SQL AND TEMP VIEWS
══════════════════════════════════════════════════════════════
Register a DataFrame as a temporary view and you can query it with plain SQL.
Spark parses the SQL and the DataFrame code into the same logical plan, so
there is no speed difference. Pick whichever is clearer to read.

  df.createOrReplaceTempView("claims")
  spark.sql("SELECT ... FROM claims")

The view lives only in this session. It is a name for a plan, not a copy of
the data.

══════════════════════════════════════════════════════════════
 CONCEPT 2 — WINDOW FUNCTIONS
══════════════════════════════════════════════════════════════
A window function computes a value for each row using a group of related rows,
without collapsing the rows like groupBy does.

  Window.partitionBy("customer").orderBy("claim_date")

  row_number()   1, 2, 3 within each partition (no ties)
  lag("amount")  the previous row's amount in the partition
  sum("amount").over(window)  running total when the window is ordered

Typical insurance uses: latest claim per customer, days since the previous
claim, running paid total per policy. Windows need a shuffle: all rows of one
partition key must meet on one task.

EXAMPLE ──────────────────────────────────────────────────────
history = spark.createDataFrame(
    [
        ("alice", "2026-01-05", 300.0),
        ("alice", "2026-02-11", 150.0),
        ("alice", "2026-03-20", 500.0),
        ("bob", "2026-01-15", 100.0),
        ("bob", "2026-02-01", 900.0),
    ],
    ["customer", "claim_date", "amount"],
)

w_asc = Window.partitionBy("customer").orderBy("claim_date")
with_windows = (
    history.withColumn("claim_no", F.row_number().over(w_asc))
    .withColumn("prev_amount", F.lag("amount").over(w_asc))
    .withColumn("running_total", F.sum("amount").over(w_asc))
    .orderBy("customer", "claim_date")
)
with_windows.show()

══════════════════════════════════════════════════════════════
 CONCEPT 3 — JOIN STRATEGIES: BROADCAST VS SORT-MERGE
══════════════════════════════════════════════════════════════
Spark picks a physical strategy for each join:

  BroadcastHashJoin  copy the small table to every task; the big table is not
                     shuffled. Fast. Use when one side is small (lookup tables).
  SortMergeJoin      shuffle and sort BOTH sides by the join key. Scales to
                     two big tables but costs two shuffles.

You can force a broadcast with F.broadcast(small_df). Spark also broadcasts
automatically below spark.sql.autoBroadcastJoinThreshold (default 10 MB, when
it knows the table size). You confirm the choice by reading the plan.

EXAMPLE ──────────────────────────────────────────────────────
lines = spark.createDataFrame(
    [("auto", "Motor"), ("home", "Property"), ("life", "Life")],
    ["policy_type", "business_line"],
)


def join_strategy(dataframe):
    match = re.search(r"(BroadcastHashJoin|SortMergeJoin|ShuffledHashJoin)", plan_text(dataframe))
    return match.group(1) if match else "none"


forced = claims_big.join(F.broadcast(lines), "policy_type")
print("With F.broadcast hint:", join_strategy(forced))

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")
print("Broadcast switched off:", join_strategy(claims_big.join(lines, "policy_type")))

══════════════════════════════════════════════════════════════
 CONCEPT 4 — DATA SKEW AND SALTING
══════════════════════════════════════════════════════════════
A shuffle sends all rows with the same key to the same task. If one key owns
most of the rows (a default customer id, a null replaced by "UNKNOWN", one huge
broker), one task does nearly all the work while the others sit idle.

Salting spreads a hot key: add a small salt column, aggregate by (key, salt)
first, then aggregate the partial results by key. Same final answer, more
parallelism.

EXAMPLE ──────────────────────────────────────────────────────
skewed_rows = [("BIG", float(i % 100)) for i in range(40000)] + [("k%d" % (i % 20), float(i % 100)) for i in range(2000)]
skewed = spark.createDataFrame(skewed_rows, ["customer", "amount"]).withColumn("rid", F.monotonically_increasing_id())

by_key = skewed.repartition(4, "customer").withColumn("pid", F.spark_partition_id())
sizes_plain = sorted([r["count"] for r in by_key.groupBy("pid").count().collect()], reverse=True)

salted = skewed.withColumn("salt", F.pmod(F.hash("rid"), F.lit(4)))
by_salt = salted.repartition(4, "customer", "salt").withColumn("pid", F.spark_partition_id())
sizes_salt = sorted([r["count"] for r in by_salt.groupBy("pid").count().collect()], reverse=True)

print("Rows per partition, plain key  :", sizes_plain)
print("Rows per partition, salted key :", sizes_salt)

two_stage = (
    salted.groupBy("customer", "salt").agg(F.sum("amount").alias("partial"))
    .groupBy("customer").agg(F.sum("partial").alias("total"))
)
direct = skewed.groupBy("customer").agg(F.sum("amount").alias("total"))
print("Salted two-stage result equals direct result:", two_stage.orderBy("customer").collect() == direct.orderBy("customer").collect())

══════════════════════════════════════════════════════════════
 CONCEPT 1 — INSIDE A PARQUET FILE
══════════════════════════════════════════════════════════════
CSV stores row after row. To read one column you must read every byte.
Parquet stores data by COLUMN:

  file
   +-- row group 1  (a block of rows, e.g. 100,000)
   |     +-- column chunk: claim_id   (compressed, encoded)
   |     +-- column chunk: amount     (compressed, encoded)
   |     +-- statistics: min / max / null count per column chunk
   +-- row group 2 ...
   +-- footer (schema + all statistics)

Three wins for analytics:
  1. Column pruning     read only the columns the query uses
  2. Row group skipping the min/max statistics let a reader skip whole blocks
  3. Compression        similar values sit together, so they compress well

EXAMPLE ──────────────────────────────────────────────────────
rng = np.random.default_rng(42)
n_rows = 100000
claims_pdf = pd.DataFrame(
    {
        "claim_id": np.arange(n_rows),
        "region": rng.choice(["West", "East", "Central"], n_rows),
        "amount": np.sort(rng.integers(100, 100000, n_rows)),
    }

 CONCEPT 2 — PARTITIONED DATASETS AND PARTITION PRUNING
══════════════════════════════════════════════════════════════
Partitioning splits a dataset into folders by column values:

  claims/region=West/yr=2025/part-0001.parquet
  claims/region=West/yr=2026/part-0002.parquet
  claims/region=East/...

A query that filters on region lets Spark skip every other region folder
without opening a single file. That is partition pruning. You can see it in
the plan as PartitionFilters.

Good partition columns: low cardinality (tens to a few thousand values) and
used in filters (date, region). Bad: claim_id (millions of folders).

══════════════════════════════════════════════════════════════
 CONCEPT 3 — THE SMALL FILES PROBLEM
══════════════════════════════════════════════════════════════
Spark writes one file per partition per task. A job with 200 shuffle
partitions that writes 5 MB of data creates 200 tiny files. Every file costs:
a listing call, an open call, a footer read, and a task to process it. Query
time is then dominated by overhead, not by data.

Target file size for analytics: roughly 128 MB to 512 MB per file.

Fixes:
  df.coalesce(n)      shrink partitions without a full shuffle (before write)
  df.repartition(n)   even redistribution with a shuffle
  compaction jobs     rewrite many small files into few big ones (Delta
                      OPTIMIZE does this for you on day 4)

EXAMPLE ──────────────────────────────────────────────────────
def count_parquet_files(folder):
    return len([n for n in os.listdir(folder) if n.endswith(".parquet")])

 CONCEPT 1 — THE TRANSACTION LOG
══════════════════════════════════════════════════════════════
A Delta table is a folder of Parquet files PLUS a folder called _delta_log.
Every write adds one numbered JSON file to the log. The log says which Parquet
files belong to the table at each version:

  add     this Parquet file is now part of the table
  remove  this Parquet file is no longer part of the table

A reader replays the log to learn the current file list. A write becomes
visible only when its log file lands, in one atomic step. That is how Delta
gives you:
  Atomicity    a failed job leaves no half-written table
  Consistency  readers always see a whole version
  Isolation    readers keep a stable snapshot while writers work
  Durability   the log file is the commit

EXAMPLE ──────────────────────────────────────────────────────
demo_path = os.path.join(workdir, "demo")

    actions = [json.loads(line) for line in handle if line.strip()]

history = DeltaTable.forPath(spark, demo_path).history().select("version", "operation").orderBy("version")

 CONCEPT 2 — MERGE: UPDATE AND INSERT IN ONE STEP
══════════════════════════════════════════════════════════════
Plain Parquet cannot update a row. You rewrite the whole dataset. Delta gives
you MERGE (an upsert):

  when the key matches      -> update the row
  when the key is not found -> insert the row
  (optional) when matched and a condition holds -> delete

MERGE is the standard way to apply a daily batch of changed claims. Delta
rewrites only the files that contain matching rows.

EXAMPLE ──────────────────────────────────────────────────────

    .merge(changes.alias("c"), "t.claim_id = c.claim_id")
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute()
)

 CONCEPT 3 — TIME TRAVEL, DELETE AND RESTORE
══════════════════════════════════════════════════════════════
Because old Parquet files are kept (marked removed in the log, not erased),
you can read any earlier version:

  spark.read.format("delta").option("versionAsOf", 3).load(path)
  spark.read.format("delta").option("timestampAsOf", "2026-01-01").load(path)

And you can undo a mistake:

  DeltaTable.forPath(spark, path).restoreToVersion(1)

Restore is itself a new commit, so the history keeps the mistake AND the fix.
Time travel lasts only while the old files exist. VACUUM (Concept 5) deletes
them after a retention period.

 CONCEPT 5 — OPTIMIZE AND VACUUM
══════════════════════════════════════════════════════════════
Day 3 showed the small-files problem. Every append here adds at least one
file. OPTIMIZE rewrites many small files into fewer big ones, as a new commit
(readers are not disturbed).

are older than the retention period (default 7 days). After VACUUM you can
NOT time travel to versions older than the retention window. Never set
retention to zero on a production table.

An Iceberg catalog is the service that knows where each table's current

import os

import pyarrow as pa
from pyiceberg.catalog.sql import SqlCatalog
from pyiceberg.partitioning import PartitionField, PartitionSpec
from pyiceberg.schema import Schema
from pyiceberg.transforms import DayTransform
from pyiceberg.types import DateType, DoubleType, NestedField, StringType

workdir = tempfile.mkdtemp(prefix="w20_d5_")
catalog = SqlCatalog("local", uri=f"sqlite:///{workdir}/catalog.db", warehouse=f"file://{workdir}/warehouse")
catalog.create_namespace("db")

claims_schema = Schema(
    NestedField(1, "claim_id", StringType(), required=False),
    NestedField(2, "claim_date", DateType(), required=False),
    NestedField(3, "amount", DoubleType(), required=False),
)
arrow_schema = pa.schema([("claim_id", pa.string()), ("claim_date", pa.date32()), ("amount", pa.float64())])
by_day = PartitionSpec(PartitionField(source_id=2, field_id=1000, transform=DayTransform(), name="claim_date_day"))


def batch(rows):
    return pa.Table.from_pylist(
        [{"claim_id": a, "claim_date": b, "amount": c} for a, b, c in rows], schema=arrow_schema
    )


def make_table(name, partitioned=False):
    # three commits: 2 rows on Jan 5, 1 row on Jan 6, 1 row on Jan 7
    spec = by_day if partitioned else PartitionSpec()

 CONCEPT 1 — ICEBERG'S METADATA TREE
══════════════════════════════════════════════════════════════
Delta keeps a flat log of commits. Iceberg keeps a TREE of metadata:

stays fast on huge tables and on object stores where listing is slow.

 CONCEPT 2 — SILVER: TYPE, VALIDATE, DEDUPLICATE, QUARANTINE
══════════════════════════════════════════════════════════════
Silver does four things:
  1. Types   amount_raw -> double, claim_date_raw -> date
  2. Rules   one reason per failing row (the order matters and is documented)
  3. Dedupe  keep the LATEST version of each claim_id (window + row_number)
  4. Quarantine  failing rows are written to their own table with the reason,
                 so a data steward can fix the source and replay

Never drop bad rows silently. A row that vanishes between layers is the
hardest bug to find, because every later total is simply a little low.

EXAMPLE ──────────────────────────────────────────────────────
def classify(bronze_frame):
    return (
        bronze_frame
        .withColumn("amount", F.expr("try_cast(regexp_replace(amount_raw, ',', '') AS DOUBLE)"))
        .withColumn("claim_date", F.expr("try_to_date(claim_date_raw, 'yyyy-MM-dd')"))
        .withColumn(
            "reason",
            F.when(F.col("claim_id").isNull(), "missing_claim_id")
            .when(F.col("amount").isNull() | (F.col("amount") <= 0), "bad_amount")
            .when(F.col("claim_date").isNull(), "bad_date")
            .otherwise("valid"),
        )
    )


def build_silver(bronze_path, silver_path, quarantine_path):
    classified = classify(load(bronze_path))
    latest = Window.partitionBy("claim_id").orderBy(F.col("ingested_at").desc(), F.col("_loaded_at").desc())
    silver = (
        classified.filter("reason = 'valid'")
        .withColumn("rn", F.row_number().over(latest))
        .filter("rn = 1")
        .select("claim_id", "region", "amount", "claim_date", "ingested_at")
    )
    quarantine = classified.filter("reason != 'valid'").select(*RAW_COLS, "_batch_id", "reason")
    silver.write.format("delta").mode("overwrite").save(silver_path)
    quarantine.write.format("delta").mode("overwrite").save(quarantine_path)

reconciliation check costs one small query and catches the silent-loss bugs

def reconcile(bronze_path, silver_path, quarantine_path):
    bronze_n = load(bronze_path).count()
    silver_n = load(silver_path).count()
    quarantine_n = load(quarantine_path).count()
    valid_n = classify(load(bronze_path)).filter("reason = 'valid'").count()
    duplicates_n = valid_n - silver_n
    ok = bronze_n == silver_n + quarantine_n + duplicates_n
    return {"bronze": bronze_n, "silver": silver_n, "quarantine": quarantine_n, "duplicates": duplicates_n, "ok": ok}

 reconciliation between layers and a safe retry.
 End result: a gold table finance can query, and proof that no row was lost.

 ARCHITECTURE DECISION
 ─────────────────────
 Choosing between: rebuild silver from bronze each run vs incremental MERGE into silver.
