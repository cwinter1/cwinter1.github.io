 CONCEPT 2 — A DEPLOYMENT FOR THE FASTAPI IMAGE
══════════════════════════════════════════════════════════════
A production-ready Deployment has four things beyond "run this image":
  readinessProbe   traffic is sent only when /health answers
  livenessProbe    a stuck process is restarted
  resources        requests (what the scheduler reserves) and limits (the ceiling)
  securityContext  do not run as root
Pin a version tag. ":latest" makes rollbacks and audits impossible.

EXAMPLE ──────────────────────────────────────────────────────
def make_deployment(name, image, replicas, port):
    return {
        "apiVersion": "apps/v1",
        "kind": "Deployment",
        "metadata": {"name": name, "labels": {"app": name}},
        "spec": {
            "replicas": replicas,
            "selector": {"matchLabels": {"app": name}},
            "template": {
                "metadata": {"labels": {"app": name}},
                "spec": {
                    "securityContext": {"runAsNonRoot": True},
                    "containers": [
                        {
                            "name": name,
                            "image": image,
                            "ports": [{"containerPort": port}],
                            "readinessProbe": {"httpGet": {"path": "/health", "port": port}, "periodSeconds": 5},
                            "livenessProbe": {"httpGet": {"path": "/health", "port": port}, "periodSeconds": 10},
                            "resources": {
                                "requests": {"cpu": "250m", "memory": "256Mi"},
                                "limits": {"cpu": "500m", "memory": "512Mi"},
                            },
                        }
                    ],
                },
            },
        },
    }

 CONCEPT 3 — JOBS AND CRONJOBS FOR DATA WORK
══════════════════════════════════════════════════════════════
A Deployment keeps something running. Data pipelines run and FINISH, so they
use a Job (run to completion) or a CronJob (a Job on a schedule).

  restartPolicy      must be Never or OnFailure for a Job
  backoffLimit       how many times to retry a failed pod before giving up
  concurrencyPolicy  Forbid stops a slow run from overlapping the next one
                     (two writers on the same table is how you get duplicates)
  activeDeadlineSeconds  kill a run that hangs

The container runs the same command you would run locally, for example the
W20 lakehouse job: python -m claims_lakehouse.run --batch 2026-04-20

EXAMPLE ──────────────────────────────────────────────────────
def make_job(name, image, command, backoff_limit=3):
    return {
        "apiVersion": "batch/v1",
        "kind": "Job",
        "metadata": {"name": name},
        "spec": {
            "backoffLimit": backoff_limit,
            "template": {
                "spec": {
                    "restartPolicy": "Never",
                    "containers": [{"name": name, "image": image, "command": command}],
                }
            },
        },
    }


job = make_job("load-claims", "claims-lakehouse:1.0.0", ["python", "-m", "claims_lakehouse.run"])
print(job["spec"]["backoffLimit"], job["spec"]["template"]["spec"]["restartPolicy"])

══════════════════════════════════════════════════════════════
 CONCEPT 4 — WHAT THE SCHEDULER SEES: REQUESTS AND LIMITS
══════════════════════════════════════════════════════════════
The scheduler places a pod on a node that has enough UNRESERVED capacity for its
requests. The kubelet enforces the limits: exceed the memory limit and the
container is killed (OOMKilled, tomorrow's lesson). Exceed the CPU limit and it is
only slowed down.

Units: cpu "250m" = 0.25 core, "1" = 1 core. memory "256Mi" = 256 mebibytes,
"1Gi" = 1024 Mi. A small parser lets you check a manifest against a node
before applying it.

EXAMPLE ──────────────────────────────────────────────────────
def cpu_cores(text):
    text = str(text)
    return int(text[:-1]) / 1000 if text.endswith("m") else float(text)


def memory_mi(text):
    text = str(text)
    if text.endswith("Gi"):
        return float(text[:-2]) * 1024
    if text.endswith("Mi"):
        return float(text[:-2])
    raise ValueError("unsupported unit: " + text)


print(cpu_cores("250m"), cpu_cores("2"), memory_mi("256Mi"), memory_mi("1Gi"))

══════════════════════════════════════════════════════════════
 CONCEPT 1 — THE DEBUGGING LOOP
══════════════════════════════════════════════════════════════
Always the same four commands, in this order:
  kubectl get pods                       what is the status?
  kubectl describe pod <name>            what do the EVENTS say? (bottom of output)
  kubectl logs <name> --previous         what did the crashed container print?
  kubectl get pod <name> -o json         exact reason and exit code

The status fields that matter:
  waiting.reason                CrashLoopBackOff, ImagePullBackOff, ErrImagePull
  lastState.terminated.reason   OOMKilled, Error, Completed
  lastState.terminated.exitCode 137 = killed (usually OOM), 1 = app error
  conditions[PodScheduled]      False + Unschedulable = no node has room

 CONCEPT 4 — BACK-OFF: WHY A BROKEN POD "SLOWS DOWN"
══════════════════════════════════════════════════════════════
After each failed start the kubelet waits before the next one. The wait starts
at 10 seconds, doubles every time, and is capped at 300 seconds (5 minutes).
That is why a broken pod looks busy at first and then seems to do nothing.
After you fix the manifest, delete the pod to skip the wait.

EXAMPLE ──────────────────────────────────────────────────────
def backoff_delay(restart_number):
    return min(10 * 2 ** (restart_number - 1), 300)


print([backoff_delay(n) for n in range(1, 4)])

══════════════════════════════════════════════════════════════
 CONCEPT 1 — KUBERNETESPODOPERATOR
══════════════════════════════════════════════════════════════
Airflow decides WHEN and in what ORDER. Kubernetes decides WHERE and with
what resources. The operator creates a pod, streams its logs into the Airflow
task log, waits, and marks the task by the pod's exit code. The pod image holds
the code, so Airflow itself stays free of heavy dependencies.

A real task looks like this (needs the cncf.kubernetes provider, shown as text):

  from airflow.providers.cncf.kubernetes.operators.pod import KubernetesPodOperator
  load = KubernetesPodOperator(
      task_id="load_claims",
      name="load-claims",
      image="claims-lakehouse:1.0.0",
      cmds=["python", "-m", "claims_lakehouse.run"],
      get_logs=True,
      container_resources={"limits": {"memory": "1Gi"}},
  )

Because the DAG file is just Python text, a generator can write it and a test
can check it without running Airflow.

EXAMPLE ──────────────────────────────────────────────────────
def make_dag_source(dag_id, schedule, tasks):
    """tasks: list of (task_id, image, command_list). Tasks run in the order given."""
    lines = [
        "from airflow import DAG",
        "from airflow.providers.cncf.kubernetes.operators.pod import KubernetesPodOperator",
        "import datetime",
        "",
        f"with DAG({dag_id!r}, schedule={schedule!r}, start_date=datetime.datetime(2026, 1, 1), catchup=False) as dag:",
    ]
    for task_id, image, command in tasks:
        lines.append(
            f"    {task_id} = KubernetesPodOperator(task_id={task_id!r}, name={task_id.replace('_', '-')!r}, "
            f"image={image!r}, cmds={command!r}, get_logs=True)"
        )
    ids = [t[0] for t in tasks]
    lines.append("    " + " >> ".join(ids))
    return "\n".join(lines) + "\n"


example_source = make_dag_source("claims_nightly", "0 2 * * *", [("load_claims", "claims-lakehouse:1.0.0", ["python", "-m", "run"])])

══════════════════════════════════════════════════════════════

  --conf spark.executor.memory / cores        size of each executor

 CONCEPT 1 — THE WORKFLOW AND STATE
══════════════════════════════════════════════════════════════
You DECLARE what should exist in .tf files. Terraform compares that to its STATE
(a JSON file recording what it created) and to reality, then works out the steps.

  terraform init      download providers (the plugins that talk to an API)
  terraform plan      show what would change. Changes nothing.
  terraform apply     make the change (asks for approval unless -auto-approve)
  terraform destroy   remove everything in the state

The plan is the safety net. In CI the plan is posted on the pull request, and
apply runs only after a human approves it (W21_D6).

State is the part people get wrong. It maps each resource address in your code
(local_file.claims) to the real object. Lose the state and Terraform forgets what
it owns. Edit infrastructure by hand and the next plan shows DRIFT.

EXAMPLE ──────────────────────────────────────────────────────
def terraform(*args, cwd):
    """Run terraform in cwd and return its output. Skips cleanly if it is not installed."""
    if shutil.which("terraform") is None:
        return "skipped: terraform not installed"
    done = subprocess.run(["terraform", *args, "-no-color"], cwd=cwd, capture_output=True, text=True, timeout=300)
    return done.stdout + done.stderr

    add, change, destroy = (int(x) for x in match.groups())

 CONCEPT 2 — NEEDS, STAGES AND PARALLELISM
══════════════════════════════════════════════════════════════
Jobs without `needs` start together. A job with `needs` waits for those jobs and
is skipped if any of them fails. Grouping jobs into layers shows the shortest
possible pipeline: every job runs as soon as its needs are done.

EXAMPLE ──────────────────────────────────────────────────────
def stages(needs):
    remaining = {job: set(deps) for job, deps in needs.items()}
    done = set()
    layers = []
    while remaining:
        ready = sorted(job for job, deps in remaining.items() if deps <= done)
        if not ready:
            raise ValueError("cycle in needs")
        layers.append(ready)
        done.update(ready)
        for job in ready:
            del remaining[job]
    return layers


print(stages({"a": [], "b": ["a"]}))

def make_job(name, image, command, limits, backoff_limit=3):
    return {
        "apiVersion": "batch/v1",
        "kind": "Job",
        "metadata": {"name": name},
        "spec": {
            "backoffLimit": backoff_limit,
            "template": {
                "spec": {
                    "restartPolicy": "Never",
                    "containers": [{"name": name, "image": image, "command": command, "resources": {"limits": limits}}],
                }
            },
        },
    }


def lint_job(job):
    spec = job["spec"]["template"]["spec"]

def parse_plan(text):
    match = re.search(r"Plan: (\d+) to add, (\d+) to change, (\d+) to destroy", text)
    if match is None:
        return {"add": 0, "change": 0, "destroy": 0}
    add, change, destroy = (int(x) for x in match.groups())
    return {"add": add, "change": change, "destroy": destroy}
