  CREATE TABLE table_name (
      column_name datatype CONSTRAINT,
      ...
  );
Constraints: PRIMARY KEY, NOT NULL, UNIQUE, DEFAULT value

 CONCEPT 2 — INSERT, SELECT, WHERE, ORDER BY
══════════════════════════════════════════════════════════════
INSERT adds rows to a table.
SELECT retrieves rows from a table.

INSERT syntax:
  INSERT INTO table_name (col1, col2) VALUES (val1, val2);
Always use ? placeholders for values — NEVER build SQL strings with f-strings.
(f-string SQL is vulnerable to SQL injection attacks)

SELECT syntax:
  SELECT col1, col2 FROM table_name;
  SELECT * FROM table_name WHERE condition;
  SELECT * FROM table_name ORDER BY col DESC;
  SELECT * FROM table_name WHERE col = ? -- use ? for parameters

fetchall()  -- return all matching rows as a list of tuples
fetchone()  -- return the first matching row
fetchmany(n)-- return the next n rows

 CONCEPT 4 — SQL SAFETY: PARAMETERIZED QUERIES
══════════════════════════════════════════════════════════════
 ROYAL ROAD STANDARD — W6
 Never build SQL strings with f-strings or string concatenation.
 Always use ? placeholders and pass values separately.
 This prevents SQL injection — one of the most common and destructive attacks.

 SQL injection: when a user-supplied value contains SQL syntax that the
 database executes as a command. Example attack value:
   "'; DROP TABLE employees; --"
 If you used an f-string, this would delete your table.

 Parameterized queries prevent this because the database driver treats
 the value as a literal string — never as SQL code.

 WRONG (vulnerable):
   query = f"SELECT * FROM users WHERE name = '{name}'"   # never do this

 RIGHT (safe):
   cur.execute("SELECT * FROM users WHERE name = ?", (name,))

 EXAMPLE ──────────────────────────────────────────────────────
import sqlite3

conn = sqlite3.connect(":memory:")
cur = conn.cursor()
cur.execute("CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT, price REAL)")
cur.executemany("INSERT INTO products VALUES (?,?,?)", [
    (1, "Laptop",   4500.0),
    (2, "Monitor",  350.0),
    (3, "Keyboard", 89.0),
])
conn.commit()


# SAFE: parameterized query — value is never interpreted as SQL
def search_by_name(name):
    cur.execute("SELECT id, name, price FROM products WHERE name = ?", (name,))
    return cur.fetchall()


def update_price(product_id, new_price):
    cur.execute("UPDATE products SET price = ? WHERE id = ?", (new_price, product_id))
    conn.commit()
    return cur.rowcount


# Normal use
print(search_by_name("Laptop"))      # [(1, 'Laptop', 4500.0)]

# SQL injection attempt — treated as a literal string, returns nothing
attack = "' OR '1'='1"
result = search_by_name(attack)
print(f"Injection attempt returned: {result}")    # [] — database is safe

# Verify the table is untouched
cur.execute("SELECT COUNT(*) FROM products")
print(f"Products in table: {cur.fetchone()[0]}")  # 3

conn.close()

 CONCEPT 6 — TESTING YOUR PARAMETERIZED QUERY CONTRACT
══════════════════════════════════════════════════════════════

 Shift-Left Testing applied to SQL: verify that your query functions
 are actually parameterized — not just functionally correct on valid input.

 Two assertions a safe SQL function must satisfy:
   1. Returns correct data on valid input
   2. Returns empty results (not all rows) on a SQL injection attempt

 The second check is what separates a test from a smoke test.
 An f-string query also passes check 1 — only check 2 catches the vulnerability.

 Also assert that the table is intact after an injection attempt:
   cur.execute("SELECT COUNT(*) FROM table")
   assert cur.fetchone()[0] == expected_count

EXAMPLE ──────────────────────────────────────────────────────
import sqlite3

# Fresh in-memory database for this test block
conn_ex = sqlite3.connect(":memory:")
cur_ex  = conn_ex.cursor()
cur_ex.execute("CREATE TABLE items (id INTEGER PRIMARY KEY, name TEXT, category TEXT)")
cur_ex.executemany("INSERT INTO items VALUES (?,?,?)", [
    (1, "Laptop",   "Electronics"),
    (2, "Monitor",  "Electronics"),
    (3, "Desk",     "Furniture"),
])
conn_ex.commit()


def find_by_category(conn, category):
    c = conn.cursor()
    c.execute("SELECT id, name FROM items WHERE category = ?", (category,))
    return c.fetchall()


# 1. Assert valid input returns correct rows
result = find_by_category(conn_ex, "Electronics")
assert len(result) == 2,             "Electronics must return exactly 2 rows"
assert result[0][1] == "Laptop",     "first Electronics item must be Laptop"

# 2. Assert injection attempt returns zero rows (not all 3)
attack = "' OR '1'='1"
injected = find_by_category(conn_ex, attack)
assert len(injected) == 0,           "injection attack must return 0 rows, not all rows"

# 3. Assert table is untouched after injection attempt
cur_ex.execute("SELECT COUNT(*) FROM items")
assert cur_ex.fetchone()[0] == 3,    "injection must not alter or destroy the table"

conn_ex.close()
print("Parameterized query contract: all assertions passed.")

 CONCEPT 1 — PRIMARY KEYS, FOREIGN KEYS, RELATIONSHIPS
══════════════════════════════════════════════════════════════
A relational database stores data in multiple related tables.
Tables are linked through key columns.

PRIMARY KEY:
  - Uniquely identifies each row in a table
  - Cannot be NULL
  - Usually an auto-incrementing integer (AUTOINCREMENT)
  - Each table has exactly one primary key

FOREIGN KEY:
  - A column in one table that references the PRIMARY KEY of another table
  - Enforces referential integrity: you cannot add a foreign key value
    that does not exist in the referenced table
  - Creates a parent-child relationship between tables

RELATIONSHIP TYPES:
  One-to-Many (most common):
    One customer can have MANY orders
    customer_id is the PK in customers,
    and a FK in orders

  Many-to-Many:
    An order can contain MANY products, a product can be on MANY orders
    Resolved with a junction table: order_items(order_id, product_id)

ENABLING FOREIGN KEYS IN SQLite:
  SQLite does NOT enforce FKs by default.
  You must run: PRAGMA foreign_keys = ON;
  in each connection where you want enforcement.

 CONCEPT 4 — SMART SCHEMA AGENT: STAGE 1 — SCHEMA INTROSPECTION
══════════════════════════════════════════════════════════════
 CUMULATIVE PROJECT — This agent grows every week through W11.
 By Week 11 it will be a production NL→Governed SQL system.

 Stage 1 — Foundation: the agent reads the database structure dynamically.
 It never hardcodes table names or column lists. It discovers them at runtime
 using SQLite's built-in sqlite_master table and PRAGMA table_info().

 Why this matters: a production agent works against any schema, not just
 one you wrote yourself. Schema introspection is how it learns the contract.

 sqlite_master: the catalog table that lists all tables, views, and indexes.
 PRAGMA table_info(table): returns one row per column — name, type, PK flag.

 EXAMPLE ──────────────────────────────────────────────────────
import sqlite3


class SmartSchemaAgent:
    """
    A governed database agent. Grows each week (W6-W11).
    Stage 1 — reads the database schema dynamically.
    """

    def __init__(self, conn: sqlite3.Connection):
        self.conn = conn
        self.cur  = conn.cursor()

    def get_schema(self) -> dict:
        """Return {table: [{"name", "type", "nullable", "pk"}]} for all tables."""
        self.cur.execute(
            "SELECT name FROM sqlite_master WHERE type='table' ORDER BY name"
        )
        tables = [r[0] for r in self.cur.fetchall() if r[0] != "audit_log"]
        schema = {}
        for table in tables:
            self.cur.execute(f"PRAGMA table_info({table})")
            schema[table] = [
                {"name": r[1], "type": r[2], "nullable": not r[3], "pk": bool(r[5])}
                for r in self.cur.fetchall()
            ]
        return schema

    def describe_table(self, table_name: str) -> str:
        """Return a human-readable column listing for a table."""
        schema = self.get_schema()
        if table_name not in schema:
            return f"Table '{table_name}' not found."
        lines = [f"Table: {table_name}"]
        for col in schema[table_name]:
            flags = (" [PK]" if col["pk"] else "") + (" NOT NULL" if not col["nullable"] else "")
            lines.append(f"  {col['name']}: {col['type']}{flags}")
        return "\n".join(lines)

    def column_exists(self, table: str, column: str) -> bool:
        """Return True if column exists in the table."""
        schema = self.get_schema()
        return table in schema and any(c["name"] == column for c in schema[table])

 CONCEPT 5 — STAR SCHEMA & DIMENSIONAL MODELLING
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 A star schema organises data into one central fact table surrounded
 by dimension tables. It is the standard design for analytical databases
 (OLAP), data warehouses, and dbt mart models.

 Fact table   : stores measurable events (one row per sale, one per click)
                contains foreign keys to dimensions + numeric measures
 Dimension    : describes context (who, what, where, when)
                e.g. dim_customer, dim_product, dim_date
 Surrogate key: a synthetic integer ID (not the source system's ID)
                stable even if the source data changes

 Why not keep everything in one flat table?
   - Dimensions change (customer address, product price) — star schema
     lets you update one place and all queries reflect it
   - Aggregations across dimensions are fast with simple JOINs
   - dbt, BigQuery, and Power BI all assume this structure

 Note: SCD Type 2 (tracking historical dimension changes) is covered
 in W14_D2 (dbt Snapshots).

 CONCEPT 6 — FAN-OUT TRAP
══════════════════════════════════════════════════════════════
 Joining two fact tables at different grain multiplies rows and
 inflates aggregated measures. This is the fan-out trap.

 Grain: the level of detail one row represents.
   fact_sales   : one row per transaction  (grain = sale)
   fact_targets : one row per rep per month (grain = rep + month)

 When you JOIN them on rep_id only (ignoring month), every sale
 row matches every target row for that rep. With N sales per rep
 and M target rows per rep, the JOIN produces N x M rows.
 SUM(revenue) gets multiplied by M — the fan-out multiplier.

 Diagnosis:
   SELECT COUNT(*) before and after the JOIN — if the count is
   higher than the row count of the finer-grain table, you have a fan-out.

 Fix: pre-aggregate the coarser table to the finer grain in a CTE
 before joining.

 Production rule: define the grain of every query in one sentence
 before writing the JOIN ("one row per rep", "one row per sale").

 EXAMPLE ──────────────────────────────────────────────────────
import sqlite3

conn6 = sqlite3.connect(":memory:")
conn6.executescript("""
    CREATE TABLE fact_sales (
        sale_id INTEGER PRIMARY KEY,
        rep_id  INTEGER,
        revenue REAL
    );
    CREATE TABLE fact_targets (
        target_id INTEGER PRIMARY KEY,
        rep_id    INTEGER,
        month     TEXT,
        target    REAL
    );
""")
conn6.executemany("INSERT INTO fact_sales VALUES (?,?,?)", [
    (1, 1, 1200.0),
    (2, 1, 1800.0),
    (3, 2, 1500.0),
    (4, 2,  500.0),
])
# 3 monthly target rows per rep — different grain from fact_sales
conn6.executemany("INSERT INTO fact_targets VALUES (?,?,?,?)", [
    (1, 1, "2024-01", 5000.0),
    (2, 1, "2024-02", 5000.0),
    (3, 1, "2024-03", 5000.0),
    (4, 2, "2024-01", 6000.0),
    (5, 2, "2024-02", 6000.0),
    (6, 2, "2024-03", 6000.0),
])

# WRONG: each sale row joins to all 3 target rows for that rep
wrong = conn6.execute("""
    SELECT SUM(s.revenue) AS total_revenue, COUNT(*) AS row_count
    FROM   fact_sales s
    JOIN   fact_targets t ON s.rep_id = t.rep_id
""").fetchone()

# CORRECT: pre-aggregate sales to rep grain in a CTE, then join
correct_rows = conn6.execute("""
    WITH sales_by_rep AS (
        SELECT rep_id, SUM(revenue) AS rep_revenue
        FROM   fact_sales
        GROUP BY rep_id
    )
    SELECT SUM(sr.rep_revenue) AS total_revenue, COUNT(*) AS row_count
    FROM   sales_by_rep sr
    JOIN   fact_targets t ON sr.rep_id = t.rep_id
    GROUP BY sr.rep_id, sr.rep_revenue
""").fetchall()
correct_revenue = sum(r[0] for r in correct_rows)
correct_count   = sum(r[1] for r in correct_rows)

print(f"WRONG total revenue (fan-out): ${wrong[0]:,.2f}  ({wrong[1]} rows)")
print(f"CORRECT total revenue:         ${correct_revenue:,.2f}  ({correct_count} rows)")
print(f"Fan-out multiplier: {wrong[0] / correct_revenue:.1f}x")

 CONCEPT 7 — SCD TYPE 2 (SLOWLY CHANGING DIMENSIONS)
══════════════════════════════════════════════════════════════
 Dimension values change over time: a customer's tier changes,
 a product's price changes. SCD Type 2 preserves full history
 by adding new rows instead of overwriting the old value.

 SCD Type 1 — overwrite: no history kept. Wrong for analytics.
 SCD Type 2 — add a new row with three version metadata columns:
   effective_date : date this version became active
   expiry_date    : date this version was retired ('9999-12-31' = still current)
   is_current     : 1 = active row, 0 = historical row

 When an attribute changes (customer tier Gold -> Silver):
   1. UPDATE old row:  SET expiry_date = today, is_current = 0
   2. INSERT new row:  effective_date = today, expiry_date = '9999-12-31', is_current = 1

 To query the historical state on a given event_date:
   WHERE effective_date <= event_date AND expiry_date > event_date

 Note: dbt Snapshots automate this pattern using
 strategy: timestamp (or check). Covered in W14_D2.

 EXAMPLE ──────────────────────────────────────────────────────

 CONCEPT 1 — INNER JOIN AND LEFT JOIN
══════════════════════════════════════════════════════════════
JOIN combines rows from two tables based on a matching key column.

INNER JOIN:
  Returns ONLY rows where the key exists in BOTH tables.
  Customers with no orders are excluded.

LEFT JOIN:
  Returns ALL rows from the LEFT table.
  If no match in the right table, right-side columns are NULL.
  Useful for finding customers with no orders, products with no sales, etc.

Syntax:
  SELECT a.col, b.col
  FROM   left_table a
  JOIN   right_table b ON a.key = b.key       -- INNER JOIN (default)
  LEFT JOIN other_table c ON a.key = c.key    -- LEFT JOIN

 CONCEPT 2 — GROUP BY + HAVING, AGGREGATE FUNCTIONS
══════════════════════════════════════════════════════════════
GROUP BY partitions rows into groups by column value.
Aggregate functions run on each group: COUNT, SUM, AVG, MAX, MIN.

HAVING is like WHERE but runs AFTER grouping -- it filters groups, not rows.
Use WHERE to filter rows before grouping.
Use HAVING to filter based on aggregate values.

Syntax:
  SELECT col, COUNT(*), SUM(amount)
  FROM   table
  WHERE  condition            -- filter rows first
  GROUP BY col
  HAVING COUNT(*) > 3         -- then filter groups
  ORDER BY SUM(amount) DESC;
EXAMPLE ──────────────────────────────────────────────────────

 CONCEPT 3 — SUBQUERIES (SELECT INSIDE SELECT)
══════════════════════════════════════════════════════════════
A subquery is a SELECT statement embedded inside another SQL statement.
It can appear in:
  - WHERE clause  (filter based on a computed value)
  - FROM clause   (treat the result as a temporary table)
  - SELECT clause (compute a value per row)

Types:
  Scalar subquery: returns a single value
  Row subquery:    returns a single row
  Table subquery:  returns multiple rows (used with IN, EXISTS, etc.)
EXAMPLE ──────────────────────────────────────────────────────
Find customers who have spent MORE than the average customer total


print("\n=== SUBQUERY: Above-Average Spenders ===")
cur.execute("""
    SELECT
        c.name,
        c.tier,
        ROUND(SUM(o.total_amount), 2) AS total_spent
    FROM   customers c
    JOIN   orders o ON c.customer_id = o.customer_id
    WHERE  o.status = 'completed'

        -- subquery: compute average total spend across all customers
        SELECT AVG(customer_total)
        FROM (
            SELECT customer_id, SUM(total_amount) AS customer_total
            FROM   orders
            WHERE  status = 'completed'
            GROUP BY customer_id
        )
    )
    ORDER BY total_spent DESC
""")

 CONCEPT 5 — COHORT RETENTION
══════════════════════════════════════════════════════════════

 A cohort is a group of users who took a first action in the same time period.
 Retention measures what percentage of a cohort is still active N days later.

 D1 retention  = % of cohort active on day 1 after registration
 D7 retention  = % of cohort active at least once in the first 7 days
 D30 retention = % of cohort active at least once in the first 30 days

 SQL pattern (SQLite with julianday for date math):

   WITH cohorts AS (
     SELECT user_id, MIN(event_date) AS cohort_date
     FROM events GROUP BY user_id
   )
   SELECT
     cohort_date,
     COUNT(DISTINCT c.user_id) AS cohort_size,
     COUNT(DISTINCT CASE
       WHEN julianday(e.event_date) - julianday(c.cohort_date) >= 6
       THEN c.user_id END) * 100.0
     / COUNT(DISTINCT c.user_id) AS d7_retention_pct
   FROM cohorts c
   JOIN events e ON c.user_id = e.user_id
   GROUP BY c.cohort_date

 The CASE WHEN inside COUNT(DISTINCT) counts only users who had an event
 at least N days after their registration date.

 CONCEPT 6 — ISLAND / CONSECUTIVE STREAK PATTERN
══════════════════════════════════════════════════════════════

 Problem: find users with N or more consecutive active days.

 The trick uses ROW_NUMBER() to create a sequence counter.
 For truly consecutive days: day - row_number produces the same constant.
 Rows sharing that constant form one "island" (consecutive group).

   WITH numbered AS (
     SELECT user_id, day,
            date(day, '-' || ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day) || ' days') AS grp
     FROM daily_logins
   ),
   streaks AS (
     SELECT user_id, grp, COUNT(*) AS streak_len,
            MIN(day) AS start_day, MAX(day) AS end_day
     FROM numbered GROUP BY user_id, grp
   )
   SELECT * FROM streaks WHERE streak_len >= 7

 Why it works: if days are consecutive, each day is 1 more than the previous,
 and row_number also increments by 1 -- so their difference is constant.
 Any gap in days breaks the constant and starts a new island.

EXAMPLE ──────────────────────────────────────────────────────
import sqlite3

conn6 = sqlite3.connect(":memory:")
cur6  = conn6.cursor()

cur6.execute("CREATE TABLE daily_logins (user_id INTEGER, day TEXT)")
cur6.executemany("INSERT INTO daily_logins VALUES (?,?)", [
    (1, "2024-01-01"), (1, "2024-01-02"), (1, "2024-01-03"),
    (1, "2024-01-04"), (1, "2024-01-05"), (1, "2024-01-06"), (1, "2024-01-07"),
    (2, "2024-01-03"), (2, "2024-01-04"),
    (3, "2024-01-08"), (3, "2024-01-09"), (3, "2024-01-10"),
    (3, "2024-01-11"), (3, "2024-01-12"), (3, "2024-01-13"),
])
conn6.commit()

# The island trick: day - row_number = constant for consecutive days
rows = cur6.execute("""
    WITH numbered AS (
        SELECT user_id, day,
               date(day, '-' || (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day)) || ' days') AS grp
        FROM daily_logins
    ),
    streaks AS (
        SELECT user_id, grp,
               COUNT(*)  AS streak_len,
               MIN(day)  AS start_day,
               MAX(day)  AS end_day
        FROM numbered
        GROUP BY user_id, grp
    )
    SELECT user_id, start_day, end_day, streak_len
    FROM streaks
    WHERE streak_len >= 5
    ORDER BY streak_len DESC
""").fetchall()

print(f"{'user_id':<8} | {'start':<12} | {'end':<12} | streak")
print("-" * 45)
for uid, start, end, length in rows:
    print(f"{uid:<8} | {start:<12} | {end:<12} | {length}")

if rows:
    top = rows[0]
    print(f"\nLongest streak: {top[3]} days (user {top[0]})")

 CONCEPT 7 — MERGE / UPSERT (INSERT OR REPLACE)
══════════════════════════════════════════════════════════════

 MERGE combines INSERT + UPDATE + DELETE into one statement.
 Use case: daily pipeline loads a staging table; target must reflect current state.

 ANSI SQL MERGE syntax (not supported in SQLite):
   MERGE INTO target USING staging ON target.id = staging.id
   WHEN MATCHED     THEN UPDATE SET ...
   WHEN NOT MATCHED THEN INSERT ...

 SQLite equivalent -- INSERT OR REPLACE:
   INSERT OR REPLACE INTO target (id, name, amount)
   SELECT id, name, amount FROM staging

 Idempotency guard (ON CONFLICT DO UPDATE):
   INSERT INTO target (id, name, salary, updated_at)
   SELECT id, name, salary, updated_at FROM staging
   ON CONFLICT(id) DO UPDATE SET
       name       = excluded.name,
       salary     = excluded.salary,
       updated_at = excluded.updated_at
   WHERE excluded.updated_at > target.updated_at   -- only overwrite if newer

 The WHERE guard prevents overwriting a newer row with an older staging record.
 Running the same MERGE twice produces the same result (idempotent).

EXAMPLE ──────────────────────────────────────────────────────
import sqlite3

conn7 = sqlite3.connect(":memory:")
cur7  = conn7.cursor()

cur7.execute("""
    CREATE TABLE employees (
        employee_id INTEGER PRIMARY KEY,
        name        TEXT NOT NULL,
        department  TEXT NOT NULL,
        salary      INTEGER NOT NULL,
        updated_at  TEXT DEFAULT (date('now'))
    )
""")
cur7.execute("""
    CREATE TABLE staging (
        employee_id INTEGER PRIMARY KEY,
        name        TEXT NOT NULL,
        department  TEXT NOT NULL,
        salary      INTEGER NOT NULL
    )
""")
conn7.commit()

    (1, "Alice",   "Engineering", 95000),

    (3, "Carol",   "Engineering", 88000),

 CONCEPT 8 — SECURITY GATE: SQL INJECTION + DDL GUARD  (CIA: I)
══════════════════════════════════════════════════════════════

 Analogy: the bank vault guard who checks credentials before opening the safe
 and refuses any request that does not match the pre-approved transaction list.

 Two attack vectors to block at the Python layer before any query reaches the DB:

 1. SQL Injection — strings injected into a query to bypass logic or extract data.
    Common patterns: UNION (data exfiltration), -- and /* (comment stripping),
    SLEEP / BENCHMARK (timing attacks to infer structure without output).
    Defence: scan query text for known patterns; raise before execution.

 2. Unauthorized DDL — DROP, ALTER, CREATE, TRUNCATE destroy or modify schema.
    Only admin-role callers should ever run DDL.
    Defence: role check at the Python gate, not inside the database.

 Why this matters: even with parameterized queries (W6 Royal Road Standard),
 a developer might still construct a DDL string from user input.
 The gate is a second line of defence that logs and blocks bad queries.

 libraries: re (stdlib only -- no sqlparse needed for this pattern)

EXAMPLE ──────────────────────────────────────────────────────
import re

INJECTION_PATTERNS = ["UNION", "--", "/*", "SLEEP", "BENCHMARK"]
DDL_KEYWORDS       = ["DROP", "ALTER", "CREATE", "TRUNCATE"]

class SQLInjectionError(Exception):
    pass

class UnauthorizedDDLError(Exception):
    pass

def sql_security_gate(query: str, role: str) -> dict:
    q = query.strip().upper()
    for pattern in INJECTION_PATTERNS:
        if pattern in q:
            raise SQLInjectionError(f"Blocked pattern detected: {pattern!r}")
    for kw in DDL_KEYWORDS:
        if q.startswith(kw):
            if role != "admin":
                raise UnauthorizedDDLError(
                    f"Role {role!r} is not permitted to run DDL ({kw})"
                )
            return {"status": "PASS", "query_type": "DDL"}
    query_type = "SELECT" if q.startswith("SELECT") else "DML"
    return {"status": "PASS", "query_type": query_type}

print(sql_security_gate("SELECT id, name FROM employees WHERE id = 1", role="reader"))
try:
    sql_security_gate("SELECT id FROM users UNION SELECT password FROM admins", role="reader")
except SQLInjectionError as e:
    print(f"SQLInjectionError: {e}")
try:
    sql_security_gate("DROP TABLE employees", role="writer")
except UnauthorizedDDLError as e:
    print(f"UnauthorizedDDLError: {e}")
print(sql_security_gate("DROP TABLE staging_temp", role="admin"))

 CONCEPT 2 — READING DATA INTO A pandas DATAFRAME USING pd.read_sql()
══════════════════════════════════════════════════════════════
pd.read_sql() is the standard way to move SQL query results into pandas.
It works with any DBAPI2-compatible connection (pyodbc, sqlite3, sqlalchemy).

Syntax:
  df = pd.read_sql("SELECT ...", conn)
  df = pd.read_sql("SELECT ... WHERE col = ?", conn, params=("value",))

Advantages over manual cursor loops:
  - Automatically reads column names as DataFrame column headers
  - Handles NULL -> NaN conversion
  - Returns a fully functional DataFrame ready for analysis
  - Supports chunking large result sets with chunksize parameter

 CONCEPT 1 — SQL QUERY PLANS
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 The database optimizer decides HOW to execute every query. You can
 inspect its plan to see whether it will scan the whole table or
 use an index to jump directly to matching rows.

 SQLite: EXPLAIN QUERY PLAN SELECT ...
   SCAN table      — reads every row (slow on large tables)
   SEARCH table USING INDEX ...  — fast lookup via index

 When to worry:
   SCAN on a table with >100k rows and a WHERE filter = time to add an index

EXAMPLE ──────────────────────────────────────────────────────
import sqlite3

# Build a 5000-row orders table
conn = sqlite3.connect(':memory:')
conn.execute("""
    CREATE TABLE orders (
        order_id   INTEGER PRIMARY KEY,
        customer   TEXT,
        region     TEXT,
        amount     REAL,
        status     TEXT
    )
""")
import random, string
random.seed(42)
regions  = ['North', 'South', 'East', 'West']
statuses = ['open', 'closed', 'pending']
rows = [
    (i, f'CUST-{i % 300:04d}', random.choice(regions),
     round(random.uniform(10, 5000), 2), random.choice(statuses))
    for i in range(1, 5001)
]
conn.executemany('INSERT INTO orders VALUES (?,?,?,?,?)', rows)

# EXPLAIN QUERY PLAN — before index
print('Before index:')
for row in conn.execute('EXPLAIN QUERY PLAN SELECT * FROM orders WHERE region = ?', ('North',)):
    print(' ', row)

# Add an index on region
conn.execute('CREATE INDEX idx_orders_region ON orders(region)')

# EXPLAIN QUERY PLAN — after index
print('\nAfter index:')
for row in conn.execute('EXPLAIN QUERY PLAN SELECT * FROM orders WHERE region = ?', ('North',)):
    print(' ', row)
conn.close()

 CONCEPT 2 — INDEX STRATEGIES
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 An index is a sorted copy of one or more columns, stored separately.
 It speeds up lookups at the cost of extra storage and slower writes.

 When to add an index:
   - Column appears in WHERE or JOIN ON clauses frequently
   - Table has more than ~10k rows
   - Query runs more often than data is inserted/updated

 When NOT to index:
   - Write-heavy tables (every INSERT must also update the index)
   - Low-cardinality columns with few distinct values (e.g. boolean)
   - Small tables — a full scan is cheaper than an index lookup

 Composite index: CREATE INDEX name ON table(col_a, col_b)
   Useful when you filter on both columns together.
   Column ORDER matters: put the most selective column first.

EXAMPLE ──────────────────────────────────────────────────────
import sqlite3, time

        event_id   INTEGER PRIMARY KEY,

        created_at TEXT

    t = time.perf_counter()
    rows = conn.execute(sql, params).fetchall()

 CONCEPT 3 — PANDAS MEMORY OPTIMIZATION
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 Pandas uses 64-bit types by default even when 8-bit or 16-bit would do.
 On large datasets this wastes 4-8x the memory needed.

 Strategies:
   df.memory_usage(deep=True)    see actual memory per column
   .astype('int8')               downcast integer (range: -128 to 127)
   .astype('int32')              downcast for most IDs and counts
   .astype('float32')            downcast float (loses some precision)
   .astype('category')           strings with few unique values — huge win
   pd.read_csv(..., chunksize=N) read large files in chunks

 Rule of thumb: apply category to any TEXT column with < 5% unique values.

EXAMPLE ──────────────────────────────────────────────────────
import pandas as pd
import numpy as np

np.random.seed(42)
n = 100_000

df = pd.DataFrame({
    'sale_id':    np.random.randint(1, 999999, n),      # int64 by default
    'amount':     np.random.uniform(10, 5000, n),        # float64 by default
    'quantity':   np.random.randint(1, 100, n),          # int64 by default
    'region':     np.random.choice(['North','South','East','West'], n),  # object
    'status':     np.random.choice(['open','closed','pending'], n),       # object
})

before_mb = df.memory_usage(deep=True).sum() / 1_048_576
print(f'Before: {before_mb:.2f} MB')
print(df.dtypes)

# Optimize
df['sale_id']  = df['sale_id'].astype('int32')
df['amount']   = df['amount'].astype('float32')
df['quantity'] = df['quantity'].astype('int8')
df['region']   = df['region'].astype('category')
df['status']   = df['status'].astype('category')

after_mb = df.memory_usage(deep=True).sum() / 1_048_576
print(f'\nAfter:  {after_mb:.2f} MB')
print(f'Reduction: {(1 - after_mb/before_mb)*100:.0f}%')

 CONCEPT 4 — VECTORIZATION VS .apply()
══════════════════════════════════════════════════════════════
══════════════════════════════════════════════════════════════

 .apply(func) runs a Python loop over every row or cell — it is slow
 because it bypasses NumPy's compiled C code.

 Vectorized operations work on the entire column at once using C code:
   df['a'] + df['b']              element-wise add (fast)
   df['col'].str.upper()          string vectorization
   np.where(condition, val, other) conditional assignment
   df['col'].map(lookup_dict)     dictionary lookup (faster than lambda)

 Rule: if you can express it as a column operation, do not use .apply().
 Use .apply() only when the logic genuinely cannot be vectorized.

EXAMPLE ──────────────────────────────────────────────────────
import pandas as pd
import numpy as np
import time

np.random.seed(42)
n = 200_000
df = pd.DataFrame({
    'price':    np.random.uniform(10, 1000, n),
    'quantity': np.random.randint(1, 50, n),
    'discount': np.random.uniform(0, 0.3, n),
    'region':   np.random.choice(['North','South','East','West'], n),
})

# Slow: apply with a lambda
t0 = time.perf_counter()
df['revenue_slow'] = df.apply(
    lambda r: r['price'] * r['quantity'] * (1 - r['discount']), axis=1)
slow_ms = (time.perf_counter() - t0) * 1000

# Fast: vectorized
t0 = time.perf_counter()
df['revenue_fast'] = df['price'] * df['quantity'] * (1 - df['discount'])
fast_ms = (time.perf_counter() - t0) * 1000

print(f'apply:       {slow_ms:.1f} ms')
print(f'vectorized:  {fast_ms:.1f} ms')
print(f'Speedup:     {slow_ms/fast_ms:.1f}x')

# np.where for conditional column
df['tier'] = np.where(df['revenue_fast'] > 10000, 'high', 'standard')
print(df['tier'].value_counts().to_dict())
