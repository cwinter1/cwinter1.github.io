Concept 1 — A LOAN-APPLICATION-RECORD Copybook, Turned Into colspecs

A mainframe loan-origination system does not export JSON or CSV — it exports a fixed-width extract whose only real documentation is the COBOL copybook that defines the record's byte layout. The mechanics of turning that copybook into pandas.read_fwf's colspecs argument — walking each elementary PIC clause and accumulating byte offsets — are reused directly from Week 13 Day 1/2 rather than rebuilt: same LayoutField shape, same colspecs_from_layout derivation, applied here to a mortgage-specific record instead of Week 13's banking-account one.

Example:

# Reusing LayoutField / colspecs_from_layout from Week 13 Day 1 Concept 2 and
# Day 2 Concept 1, applied to a new copybook for this week's loan extract.
import dataclasses
import re

@dataclasses.dataclass
class LayoutField:
    level: int
    name: str
    pic: str  # None for group items (no PIC clause)

def pic_length(pic):
    if pic is None:
        return 0
    if pic.startswith("X("):
        return int(pic[2:-1])
    m = re.match(r"^9\((\d+)\)(?:V9\((\d+)\)|V(9+))?$", pic)
    if not m:
        raise ValueError(f"unhandled PIC clause: {pic}")
    int_digits = int(m.group(1))
    if m.group(2) is not None:
        dec_digits = int(m.group(2))
    elif m.group(3) is not None:
        dec_digits = len(m.group(3))
    else:
        dec_digits = 0
    return int_digits + dec_digits

def layout_offsets(fields):
    offset = 0
    out = []
    for f in fields:
        if f.pic is None:
            continue
        length = pic_length(f.pic)
        out.append((f.name, offset, offset + length, length))
        offset += length
    return out, offset

def colspecs_from_layout(fields):
    offsets, lrecl = layout_offsets(fields)
    names = [n for n, _s, _e, _l in offsets]
    colspecs = [(s, e) for _n, s, e, _l in offsets]
    return names, colspecs, lrecl

#    05 LOAN-ID           PIC X(10).

Concept 2 — RECFM=FB Deblocking and pandas.read_fwf


The loan extract, like Week 13's, is RECFM=FB — fixed-block, no line terminator anywhere in
the file. A record boundary is purely a byte count: after LRECL bytes the next record starts,
with nothing to search for, so the very first parsing step is confirming the raw stream's total
length is an exact multiple of LRECL before trusting any field offset downstream.


Example:


# Reusing validate_and_deblock from Week 13 Day 2 Concept 2, applied to the
# LOAN-APPLICATION-RECORD layout built in Concept 1 above.
import io
import pandas as pd

def make_loan_record(loan_id, ssn, name, amount_cents, state, app_date, status):
    amount_str = str(amount_cents).zfill(11)  # 9(9)V99 = 11 digit positions
    row = (loan_id.ljust(10) + ssn.ljust(9) + name.ljust(30) + amount_str
           + state.ljust(2) + app_date.ljust(8) + status.ljust(1) + "".ljust(6))
    assert len(row) == LOAN_LRECL, f"record is {len(row)} bytes, expected {LOAN_LRECL}"
    return row

records = [
    make_loan_record("LN0000001", "123456789", "MARIA GONZALEZ", 45000000, "TX", "20260115", "A"),
    make_loan_record("LN0000002", "234567890", "JAMES OKAFOR", 32500000, "CA", "20260118", "P"),
    make_loan_record("LN0000003", "345678901", "WEI CHEN", 61000000, "NY", "20260122", "A"),
]
raw_fb_stream = "".join(records)
print(f"raw FB stream length: {len(raw_fb_stream)} bytes, no separators present")

def validate_and_deblock(raw_stream, lrecl):
    if len(raw_stream) % lrecl != 0:
        raise ValueError(
            f"stream length {len(raw_stream)} is not a multiple of LRECL {lrecl} "
            "-- truncated or misconfigured extract, refuse to guess record boundaries"
        )
    return [raw_stream[i:i + lrecl] for i in range(0, len(raw_stream), lrecl)]

deblocked = validate_and_deblock(raw_fb_stream, LOAN_LRECL)
print(f"deblocked into {len(deblocked)} records of {LOAN_LRECL} bytes each")

buf = io.StringIO("\n".join(deblocked))
df = pd.read_fwf(buf, colspecs=loan_colspecs, names=loan_names, dtype=str, keep_default_na=False)
print(df.to_string(index=False))

Concept 3 — EBCDIC-to-UTF-8 Transcode, Trailing-Space Padding, and LOW-VALUES


A real mainframe extract is not ASCII text — it is EBCDIC bytes, and each field must be
transcoded with bytes.decode("cp037") (or cp500) before it means anything as a string. Two
more raw-byte realities show up at the same step. PIC X(n) fields are always padded with
trailing EBCDIC spaces (0x40) out to their declared length, so decoding without trimming that
padding leaves every alphanumeric field carrying invisible trailing whitespace. And a field that
was never populated on a mainframe — a draft record whose downstream fields have not been keyed
yet — is not written as EBCDIC spaces at all, it is written as LOW-VALUES: every byte 0x00.
Decoding a LOW-VALUES field as text does not raise an error, it silently returns a string of
NUL characters, which is exactly the kind of corrupted-looking value item 1 of this track's
known-issues log warns against trusting without checking — the fix is detecting LOW-VALUES
before decoding and treating it as an explicit missing-value sentinel, not as text.


Example:


def is_low_values(raw_bytes):
    """LOW-VALUES: every byte 0x00 -- a field the mainframe never populated,
    not EBCDIC-encoded text of any kind."""
    return all(b == 0x00 for b in raw_bytes)

def decode_field(raw_bytes, codepage="cp037"):
    if is_low_values(raw_bytes):
        return None
    return raw_bytes.decode(codepage).rstrip()  # trim trailing EBCDIC-space padding

populated_name = "MARIA GONZALEZ".ljust(30).encode("cp037")
draft_name = bytes(30)  # LOW-VALUES: uninitialized on a draft (not-yet-keyed) application

print(f"populated BORROWER-NAME decodes as: {decode_field(populated_name)!r}")
print(f"all-LOW-VALUES BORROWER-NAME decodes as: {decode_field(draft_name)!r}")

loan_id_ebcdic = "LN0000004".ljust(10).encode("cp037")
print(f"LOAN-ID field raw bytes (cp037): {loan_id_ebcdic.hex()}")
print(f"LOAN-ID decoded and trimmed: {decode_field(loan_id_ebcdic)!r}")

Concept 4 — A Landing-Zone Manifest, Reconciled Against the Extract's Own Trailer Record


A real mainframe batch extract does not end after its last data record — it ends with a
trailer record, a summary row the source system writes with its own idea of how many records
it sent and what they should sum to (here, a total loan amount). The landing zone's job before
anything downstream touches the file is reconciling what was actually parsed against what the
trailer claims, because a truncated transfer (a network blip mid-copy, a job that died partway)
produces a file that still parses cleanly record-by-record — validate_and_deblock from Concept
2 would not catch it if the truncation happened to land on a clean LRECL boundary — and only a
trailer-vs-parsed reconciliation surfaces the gap.


Example:


import dataclasses

@dataclasses.dataclass
class LandingManifest:
    file_name: str
    record_count: int
    control_total_amount_cents: int
    trailer_record_count: int
    trailer_control_total_cents: int

    def reconcile(self):
        count_ok = self.record_count == self.trailer_record_count
        total_ok = self.control_total_amount_cents == self.trailer_control_total_cents
        return count_ok and total_ok

def build_manifest(file_name, parsed_amounts_cents, trailer_count, trailer_total_cents):
    return LandingManifest(
        file_name=file_name,
        record_count=len(parsed_amounts_cents),
        control_total_amount_cents=sum(parsed_amounts_cents),
        trailer_record_count=trailer_count,
        trailer_control_total_cents=trailer_total_cents,
    )

amounts = [45000000, 32500000, 61000000]  # from Concept 2's three parsed loan records
good_manifest = build_manifest(
    "LOAN_EXTRACT_20260301.DAT", amounts, trailer_count=3, trailer_total_cents=sum(amounts)
)
print(f"manifest reconciles (matches trailer): {good_manifest.reconcile()}")

bad_manifest = build_manifest(
    "LOAN_EXTRACT_20260302.DAT", amounts, trailer_count=4, trailer_total_cents=sum(amounts)
)
print(f"manifest reconciles (truncated extract, trailer says 4 records): {bad_manifest.reconcile()}")
print(f"  parsed {bad_manifest.record_count} records, trailer declared {bad_manifest.trailer_record_count}")

BFSI Reality Check — Day 1


Legacy: The copybook is the only real documentation of a mainframe loan-origination record's
shape — there is no schema registry, no OpenAPI spec, nothing but a .cpy file the mainframe
team maintains (or, worse, a .cpy file nobody has updated in three years while the actual
record layout has drifted). Every downstream concept this week depends on colspecs derived
correctly from that one document.


Compliance: A loan-application extract carries SSNs and loan amounts — regulated PII and
financial data from the moment the raw bytes land, before any masking or access control has been
applied. The landing zone's manifest is also the first audit artifact a regulator would ask for:
proof of exactly how many records entered the pipeline and what they summed to, checked against
the source system's own trailer record, not a number the pipeline computed and trusted on faith.


What breaks in production: A copybook is updated to widen LOAN-AMOUNT by one digit (a
larger jumbo-loan product line launches) and the extraction pipeline's colspecs table is not
regenerated — every field after LOAN-AMOUNT silently shifts by one byte, and PROPERTY-STATE
starts reading a slice of APP-DATE instead. The manifest's control-total reconciliation is the
one check in this pipeline that would actually catch this immediately (the sum of a shifted,
garbled LOAN-AMOUNT column will not match the trailer's real total), rather than it surfacing
three weeks later as underwriting decisions made against the wrong state code.

Concept 1 — Ruled-Table Extraction Into Structured Rows, Not Flattened Text


An appraisal report's comparable-sales grid is exactly the kind of content a naive text
extractor destroys — reading it as a flat wall of text loses which sale price belongs to
which comp address. unstructured's real partition_pdf(..., infer_table_structure=True)
solves this by detecting the ruled grid and returning each Table element's
metadata.text_as_html as real cells, but — the same finding Week 08 made and confirmed
again for this week — unstructured still fails to install cleanly in this sandbox
(langdetect's setup.py breaks under this environment's setuptools). pdfplumber's
extract_tables() does the identical structural job — finding the grid's vector lines and
reading the text bounded by each cell — and installs and runs cleanly here, so it stands in
for the genuinely-executable core of this concept while partition_pdf itself stays REAL
MODE reference syntax.


Example:


# Reusing the build_table_pdf/extract_tables pattern from Week 08 Day 2 Concept 1,
# applied to an appraisal comparable-sales grid instead of a claims loss run.
import io
from reportlab.pdfgen import canvas
from reportlab.lib.pagesizes import letter
import pdfplumber

def build_comp_grid_pdf(rows, col_widths):
    buf = io.BytesIO()
    c = canvas.Canvas(buf, pagesize=letter)
    width, height = letter
    row_height = 22
    x0 = 60
    y0 = height - 90
    n_rows = len(rows)
    xs = [x0]
    for w in col_widths:
        xs.append(xs[-1] + w)
    table_width = sum(col_widths)
    c.setLineWidth(0.75)
    for xline in xs:
        c.line(xline, y0, xline, y0 - row_height * n_rows)
    for r in range(n_rows + 1):
        yline = y0 - row_height * r
        c.line(x0, yline, x0 + table_width, yline)
    c.setFont("Helvetica-Bold", 9)
    for j, cell in enumerate(rows[0]):
        c.drawString(xs[j] + 3, y0 - 15, cell)
    c.setFont("Helvetica", 9)
    for r, row in enumerate(rows[1:], start=1):
        for j, cell in enumerate(row):
            c.drawString(xs[j] + 3, y0 - row_height * r - 15, cell)
    c.showPage()
    c.save()
    buf.seek(0)
    return buf

comp_rows = [
    ["Comp #", "Address", "Sale Price", "Sale Date"],
    ["1", "412 Elm St", "$468,000", "2026-01-10"],
    ["2", "88 Birch Ave", "$451,500", "2025-12-02"],
    ["3", "230 Maple Dr", "$472,900", "2026-01-22"],
]
comp_pdf = build_comp_grid_pdf(comp_rows, col_widths=[45, 110, 75, 80])
with pdfplumber.open(comp_pdf) as pdf:
    tables = pdf.pages[0].extract_tables()
print(f"tables found: {len(tables)}")
for row in tables[0]:
    print(row)

Concept 2 — Routing an Image-Only Page to OCR Instead of Direct Extraction


A loan file mixes digitally generated pages (the appraisal report itself, born as a PDF) with
scanned or faxed pages (a pay stub a borrower photographed and uploaded). The two look
identical to a human; a digitally generated page has a real text layer, and a scanned page is
purely pixels — extract_text() on a scanned page returns an empty or near-empty string, not
an error. Counting extractable characters per page is the cheapest correct routing signal:
below a small threshold, the page has no text layer at all and must go through OCR instead of
direct extraction.


Example:


# Reusing needs_ocr from Week 08 Day 3 Concept 1, applied to a mixed loan
# file (digital appraisal page, scanned pay-stub page) instead of claim forms.
import io
from reportlab.pdfgen import canvas
from reportlab.lib.pagesizes import letter
from reportlab.lib.utils import ImageReader
from PIL import Image, ImageDraw
import pdfplumber

def render_text_as_image(text_lines, size=(620, 160)):
    """Render text into a raster image -- the way a scanned or

Concept 3 — Per-Word OCR Confidence as the Quarantine Signal


Once a page is routed to OCR, pytesseract.image_to_data(...)'s real output carries a
per-word confidence score (0-100) alongside each recognized word — the routing signal for
whether to accept the OCR result or send the page to a quarantine queue for a human to key in
by hand. Two independent thresholds matter for a pay stub: a low average confidence across
the page catches broadly poor scan quality, while a single very-low-confidence word — even on
an otherwise clean page — can be exactly the gross-pay figure underwriting will compute
debt-to-income ratio from, and that one field must not be silently wrong.


Example:


# Reusing route_ocr_result from Week 08 Day 3 Concept 3, applied to pay-stub
# OCR words instead of claim-form words.
import dataclasses

@dataclasses.dataclass
class OcrWord:
    text: str
    confidence: float

def route_ocr_result(words, mean_floor=75.0, hard_floor=40.0):
    """Quarantine instead of silently accepting a partial OCR result."""
    if not words:
        return "quarantine", "no words recognized"
    confidences = [w.confidence for w in words]
    mean_conf = sum(confidences) / len(confidences)
    min_conf = min(confidences)
    if min_conf < hard_floor:
        return "quarantine", f"a word scored {min_conf:.0f} (< hard floor {hard_floor:.0f})"
    if mean_conf < mean_floor:
        return "quarantine", f"mean confidence {mean_conf:.1f} (< floor {mean_floor:.1f})"
    return "accept", f"mean confidence {mean_conf:.1f}"

Concept 4 — A Quarantine Queue, Not a Silent Drop


Concepts 2 and 3 each make a per-page routing decision in isolation; a real ingestion pipeline
needs to make that decision for every page of every document and record the ones it could not
trust, rather than either raising an unhandled exception (which stops the whole batch) or
silently omitting the page (which produces an underwriting file that looks complete but is
missing exactly the field a human needed to check by hand). A quarantine queue is the third
option: route each page, and for anything that fails the confidence floors, log a structured
entry a human reviewer can act on instead of the pipeline either crashing or lying by omission.


Example:


import dataclasses

@dataclasses.dataclass
class QuarantineEntry:
    doc_id: str
    page_no: int
    reason: str

class QuarantineQueue:
    def __init__(self):
        self._entries = []

    def add(self, doc_id, page_no, reason):
        self._entries.append(QuarantineEntry(doc_id, page_no, reason))

    def __len__(self):
        return len(self._entries)

    def for_doc(self, doc_id):
        return [e for e in self._entries if e.doc_id == doc_id]

def triage_page(doc_id, page_no, extractable_chars, ocr_words, queue,
                 min_chars=20, mean_floor=75.0, hard_floor=40.0):
    """One page's routing decision: enough text -> direct extraction;
    otherwise OCR, and OCR below the confidence floors -> quarantine
    instead of a silently-dropped or silently-wrong field."""
    if extractable_chars >= min_chars:
        return "direct_extraction"
    decision, reason = route_ocr_result(ocr_words, mean_floor=mean_floor, hard_floor=hard_floor)
    if decision == "quarantine":
        queue.add(doc_id, page_no, reason)
        return "quarantine"
    return "ocr_accepted"

queue = QuarantineQueue()
pages_to_triage = [
    ("LN0000001", 1, 56, []),
    ("LN0000001", 2, 0, pay_stub_pages["paystub_clean"]),
    ("LN0000002", 1, 0, pay_stub_pages["paystub_smudged_amount"]),
    ("LN0000002", 2, 0, pay_stub_pages["paystub_faded_fax"]),
]
for doc_id, page_no, chars, words in pages_to_triage:
    outcome = triage_page(doc_id, page_no, chars, words, queue)
    print(f"{doc_id} page {page_no}: {outcome}")

print(f"\nquarantine queue length: {len(queue)}")
for entry in queue.for_doc("LN0000002"):
    print(f"  LN0000002 page {entry.page_no}: {entry.reason}")

Legacy: A loan file's supporting documents rarely arrive in one clean format — an appraisal
comes back from the appraiser as a born-digital PDF, a pay stub arrives as a borrower's phone
photo, a bank statement might be a fax forwarded from a branch. The same document type can even
show up both ways across different borrowers, so the pipeline cannot assume format from the
document type alone; it has to detect it per page, the way Concept 2's needs_ocr does.


Compliance: A quarantined page is not a failure to hide — it is the honest record that a
specific field (a gross-pay figure, an appraised value) could not be trusted automatically, and
an underwriting decision made from an unreviewed low-confidence OCR read is exactly the kind of
gap a fair-lending audit would flag. The quarantine queue's entries, tied to doc_id/page_no,
are themselves an artifact worth keeping: proof a human reviewed the specific pages that needed
review, not just that the pipeline "ran."


What breaks in production: A borrower uploads a pay stub as a heavily compressed JPEG
screenshot of a screenshot; OCR confidence comes back mediocre but not quite below the floor —
mean_floor=75.0 accepts a 76.2 read that gets the gross-pay figure's last digit wrong. No
threshold catches every error; the floors bound the rate of unreviewed bad reads, they do not
eliminate it, which is why Day 5's retrieval baseline still needs citations back to the exact
source page (Concept 3, Day 3) rather than treating any accepted OCR text as ground truth.

Concept 1 — Splitting a Loan File on Its Own Document-Type Sections


A single mortgage loan file is not one document, it is a bundle: income verification,
appraisal, credit report, title search — each written by a different party, in a different
voice, about a different fact pattern. Splitting on the loan file's own ALL-CAPS section
headers (the way each source document is conventionally labeled when it lands, digitally or
after Day 2's parsing) gives every chunk boundary a document-type boundary already drawn by
the file itself — never a chunk that straddles an income-verification sentence and an
appraisal sentence.


Example:


# Reusing split_on_headings from Week 09 Day 2 Concept 1, applied to a
# mortgage loan file's own document-type sections instead of an insurance
# policy's coverage/exclusions sections.
import re

def split_on_headings(text, heading_pattern=r"^[A-Z][A-Z0-9 /&\-]{3,60}$"):
    lines = text.split("\n")
    sections = []
    current_heading = None
    current_body = []
    for line in lines:
        stripped = line.strip()
        if stripped and re.match(heading_pattern, stripped):
            if current_heading is not None:
                sections.append((current_heading, "\n".join(current_body).strip()))
            current_heading = stripped
            current_body = []
        else:
            current_body.append(line)
    if current_heading is not None:
        sections.append((current_heading, "\n".join(current_body).strip()))
    return sections

Concept 2 — Metadata Schema: loan_id, doc_type, page_no, effective_date


A chunk's text alone cannot answer "which loan, which document type, which page, as of when."
build_chunk_record attaches exactly those four fields to every chunk, and derives chunk_id
as a content hash — but which fields go INTO that hash is a real design decision, not a detail:
only fields present in the hash input make two otherwise-identical chunks distinct. Leaving
page_no out of the hash (as this concept deliberately does, to make the consequence visible)
means the same section text re-appearing at a different page number collides on chunk_id — a
real risk if the same clause is repeated verbatim across an amended and original document.


Example:


# Reusing the build_chunk_record content-hash pattern from Week 09 Day 4
# Concept 1, restructured around this week's own metadata schema
# (loan_id/doc_type/page_no/effective_date) instead of an insurance
# policy's parent_doc_id/section_path.
import hashlib

DOC_TYPE_BY_HEADING = {
    "INCOME VERIFICATION": "income",
    "APPRAISAL SUMMARY": "appraisal",
    "CREDIT REPORT SUMMARY": "credit",
    "TITLE SEARCH SUMMARY": "title",
}

def build_chunk_record(text, loan_id, doc_type, page_no, effective_date, chunk_index):
    chunk_id = hashlib.sha256(
        f"{loan_id}:{doc_type}:{chunk_index}:{effective_date}:{text}".encode()
    ).hexdigest()[:16]
    return {
        "chunk_id": chunk_id,
        "loan_id": loan_id,
        "doc_type": doc_type,
        "page_no": page_no,
        "effective_date": effective_date,
        "chunk_index": chunk_index,
        "text": text,
    }

Concept 3 — Parent-Child Links From Chunk Back to Source Page


Every chunk needs a way back to the exact page it came from — not for storage bookkeeping, but
because Day 5's retrieval demo has to answer "cited source page," and that answer only exists if
each chunk carries a real, resolvable pointer to its parent page's own record. cite_chunk
looks that pointer up by the same (loan_id, doc_type, page_no) key build_chunk_record
already attaches to every chunk, and returns an explicit "unavailable" result rather than
guessing when the key does not resolve to anything stored.


Example:


import dataclasses

@dataclasses.dataclass
class SourcePage:
    loan_id: str
    doc_type: str
    page_no: int
    full_text: str

pages = {
    (r["loan_id"], r["doc_type"], r["page_no"]): SourcePage(
        r["loan_id"], r["doc_type"], r["page_no"], r["text"]
    )
    for r in chunks
}

def cite_chunk(chunk_record, pages_index):
    key = (chunk_record["loan_id"], chunk_record["doc_type"], chunk_record["page_no"])
    page = pages_index.get(key)
    if page is None:
        return f"[citation unavailable: {key}]"
    return f"loan {page.loan_id}, {page.doc_type} section, page {page.page_no}"

for record in chunks:
    print(f"chunk {record['chunk_id']} cites: {cite_chunk(record, pages)}")

Concept 4 — A Chunk Audit Table, Reconciling Chunks Per Source Document


Chunking can fail silently in a way that looks identical to a loan with no title issues to
report: zero chunks. If Day 2's parsing quarantined the title-search page instead of extracting
it, the chunker simply never sees any title-section text and produces zero doc_type="title"
chunks — indistinguishable, from the chunk store alone, from a title report that was parsed
fine and just had a short, unremarkable summary. A chunk audit table, built the same way Day 1's
manifest reconciled parsed records against a trailer's declared count, makes that failure
visible: for every expected doc_type, a chunk count of zero is flagged, not silently accepted.


Example:


from collections import Counter

def build_chunk_audit(chunks, expected_doc_types):
    counts = Counter(c["doc_type"] for c in chunks)
    rows = []
    for doc_type in expected_doc_types:
        n = counts.get(doc_type, 0)
        rows.append({"doc_type": doc_type, "chunk_count": n, "status": "ok" if n > 0 else "MISSING"})
    return rows

expected = ["income", "appraisal", "credit", "title"]
audit = build_chunk_audit(chunks, expected)
for row in audit:
    print(f"{row['doc_type']:<10} chunks={row['chunk_count']}  status={row['status']}")

chunks_missing_title = [c for c in chunks if c["doc_type"] != "title"]
audit2 = build_chunk_audit(chunks_missing_title, expected)
print()
for row in audit2:
    print(f"{row['doc_type']:<10} chunks={row['chunk_count']}  status={row['status']}")

Legacy: A loan file's four document types were never authored to be read together — the

one.

collapses into one giant undifferentiated block. The audit's status="ok" at chunk_count=1
looks identical whether that one chunk is a clean single-section report or a garbled merge of
everything; a production version needs a per-doc_type expected-range check, not just a
nonzero check, to catch that class of degradation.

Concept 1 — Batch Embedding With Bounded Concurrency and Retry-With-Backoff


Embedding every chunk from a loan file one call at a time, sequentially, wastes the time a real
embedding API spends waiting on I/O rather than compute — but firing every chunk's call at once
with no limit can overwhelm the API's own rate limits. Bounded concurrency (a fixed-size worker
pool) gets the overlap without the flood, and because any individual call can fail transiently,
each one needs its own retry-with-backoff rather than letting one flaky call fail the whole
batch.


Example:


# Reusing the trigram/zlib.crc32 deterministic embedding stand-in from
# Week 05 Day 2 Concept 1, applied to loan-chunk text instead of claim text.
import time
import zlib
import numpy as np
from concurrent.futures import ThreadPoolExecutor

DIM = 32

def trigrams(text):
    t = "  " + text.lower() + "  "
    return [t[i:i+3] for i in range(len(t) - 2)]

def embed(text, dim=DIM):
    vec = np.zeros(dim)
    for gram in trigrams(text):
        seed = zlib.crc32(gram.encode("utf-8"))
        rng = np.random.default_rng(seed)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

class FlakyEmbeddingCalls:
    """Deterministic stand-in for a real embedding API that fails the
    first N calls for a given text before succeeding -- no real
    randomness, so this reproduces identically across repeated runs."""
    def __init__(self, fail_first_n_calls_for=None):
        self.fail_first_n_calls_for = fail_first_n_calls_for or {}
        self._call_counts = {}

    def call(self, text):
        n = self._call_counts.get(text, 0)
        self._call_counts[text] = n + 1
        fail_count = self.fail_first_n_calls_for.get(text, 0)
        if n < fail_count:
            raise ConnectionError(f"embedding API transient failure (attempt {n + 1})")
        return embed(text)

def embed_with_retry(client, text, max_attempts=4, base_delay=0.0):
    for attempt in range(1, max_attempts + 1):
        try:
            return client.call(text)
        except ConnectionError:
            if attempt == max_attempts:
                raise
            time.sleep(base_delay)  # real backoff: base_delay * 2 ** (attempt - 1)
    raise RuntimeError("unreachable")

def embed_batch(texts, client, max_workers=4):
    """Bounded-concurrency batch embedding: at most max_workers texts in
    flight at once, each with its own retry-with-backoff."""
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        return list(pool.map(lambda t: embed_with_retry(client, t), texts))

texts = [
    "Gross monthly income $9,700.00 based on two pay stubs.",
    "Subject property appraised at $468,000 using three comparable sales.",
    "Tri-merge credit report shows a FICO score of 742.",
    "Preliminary title report shows clear title, no liens of record.",
]
client = FlakyEmbeddingCalls(fail_first_n_calls_for={texts[1]: 2, texts[3]: 1})
vectors = embed_batch(texts, client, max_workers=2)
print(f"embedded {len(vectors)} texts, each dim={len(vectors[0])}")
for t, calls in client._call_counts.items():
    print(f"  '{t[:40]}...' took {calls} call(s)")

Concept 2 — HNSW m/ef_construction for This Corpus, ef_search at Query Time


This sandbox turns out to have a genuine local PostgreSQL 16 instance (found while writing this
week — see the Metadata table above), and apt-get install postgresql-16-pgvector installs the
real pgvector 0.6.0 server extension cleanly. The sizing question from Week 02 Day 2 — HNSW
below a row-count threshold, IVFFlat at or above it — still applies to decide m, but this
week that decision drives a real CREATE INDEX ... USING hnsw against a real table, not just an
estimate. hnsw.ef_search is a session-level setting read at query time, not baked into the
index: a higher value trades query latency for a more thorough graph traversal.


Example:


# Reusing the HNSW-vs-IVFFlat sizing heuristic from Week 02 Day 2 Concept 1;
# unlike Week 02, this week has a genuine local Postgres+pgvector instance
# to build the index against for real (see the week's Metadata table).
import hashlib
import psycopg2
from pgvector.psycopg2 import register_vector

def index_build_plan(rows, dim, m, hnsw_row_threshold=5_000_000):
    if rows < hnsw_row_threshold:
        est_mem_gb = (rows * dim * 4 * 2) / 1e9  # HNSW ~2x raw vector bytes
        return {"index_type": "hnsw", "m": m, "estimated_mem_gb": round(est_mem_gb, 6)}
    lists = int(rows / 1000) if rows <= 1_000_000 else int(rows ** 0.5)
    return {"index_type": "ivfflat", "lists": lists}

CORPUS_ROWS = 4  # this week's demo corpus; a real underwriting index is far larger
plan = index_build_plan(CORPUS_ROWS, dim=DIM, m=16)
print(f"index build plan for {CORPUS_ROWS} rows: {plan}")

conn = psycopg2.connect(host="127.0.0.1", dbname="postgres", user="postgres", password="postgres")
conn.autocommit = True  # every statement commits immediately -- no idle-in-
                         # transaction session left holding a lock behind it,

                         # the SAME live server on a repeated execution.
register_vector(conn)

Concept 3 — Idempotent Upsert Keyed on Content Hash


Re-running an ingestion pipeline over the same loan file — after a crash, a retry, a scheduled
re-sync — must not duplicate rows for chunks that have not actually changed. content_hash
(the SHA-256 of the chunk's own text, already used as part of Day 3's chunk_id) is the key an
upsert checks: INSERT ... ON CONFLICT (chunk_id) DO UPDATE only actually writes when the
incoming content hash differs from what is already stored, so a re-run over unchanged content
is a genuine no-op at the storage layer, not merely "doesn't error."


Example:


def upsert_chunk(cur, chunk_id, loan_id, doc_type, text, vec):
    content_hash = hashlib.sha256(text.encode()).hexdigest()[:16]
    cur.execute(
        """
        INSERT INTO loan_chunk_vectors (chunk_id, loan_id, doc_type, content_hash, text, embedding)
        VALUES (%s, %s, %s, %s, %s, %s)
        ON CONFLICT (chunk_id) DO UPDATE SET
            content_hash = EXCLUDED.content_hash,
            text = EXCLUDED.text,
            embedding = EXCLUDED.embedding
        WHERE loan_chunk_vectors.content_hash IS DISTINCT FROM EXCLUDED.content_hash
        RETURNING (xmax = 0) AS was_insert;
        """,
        (chunk_id, loan_id, doc_type, content_hash, text, vec),
    )
    row = cur.fetchone()
    return "inserted" if row and row[0] else ("updated" if row else "unchanged")

cur.execute("SELECT count(*) FROM loan_chunk_vectors;")
print(f"rows before re-run: {cur.fetchone()[0]}")

outcome_same_text = upsert_chunk(cur, "CH000", "LN0000001", "income", texts[0], vectors[0])
conn.commit()
print(f"re-upserting CH000 with IDENTICAL text: {outcome_same_text}")

new_income_text = "Gross monthly income $9,850.00 after a raise, per updated pay stubs."
new_vec = embed(new_income_text)
outcome_changed_text = upsert_chunk(cur, "CH000", "LN0000001", "income", new_income_text, new_vec)
conn.commit()
print(f"re-upserting CH000 with CHANGED text: {outcome_changed_text}")

cur.execute("SELECT count(*) FROM loan_chunk_vectors;")
print(f"rows after both re-runs (should still be {len(texts)}, upsert never duplicates): {cur.fetchone()[0]}")

Concept 4 — Incremental Re-Embed When a Document Version Is Replaced


A loan file's appraisal is sometimes revised — a second review adjusts the value, a corrected
credit pull replaces an earlier one. The chunk's identity (chunk_id, same loan_id/doc_type
slot) stays the same across that revision; only its content changes. Concept 3's upsert already
handles this correctly by construction — a changed content_hash triggers a real write — this
concept makes the version-replacement case explicit by reading the prior text back before
re-embedding, so the change is auditable rather than just silently applied.


Example:


def reembed_document_version(cur, chunk_id, loan_id, doc_type, new_text, new_effective_date):
    """A replaced document version keeps the same chunk_id but genuinely
    new text -- read the old text back first so the version change is
    auditable, then let the upsert (Concept 3) do the real re-embed."""
    cur.execute("SELECT text FROM loan_chunk_vectors WHERE chunk_id = %s;", (chunk_id,))
    row = cur.fetchone()
    old_text = row[0] if row else None
    new_vec = embed(new_text)
    outcome = upsert_chunk(cur, chunk_id, loan_id, doc_type, new_text, new_vec)
    return old_text, outcome

old_text, outcome = reembed_document_version(
    cur, "CH001", "LN0000001", "appraisal",
    "Revised appraisal, second review: subject property now appraised at $471,000.",
    new_effective_date="2026-02-01",
)
conn.commit()
print(f"appraisal chunk before revision: {old_text!r}")
print(f"re-embed outcome: {outcome}")
cur.execute("SELECT text FROM loan_chunk_vectors WHERE chunk_id = %s;", ("CH001",))
print(f"appraisal chunk after revision:  {cur.fetchone()[0]!r}")

BFSI Reality Check — Day 4


Legacy: A production BFSI vector store rarely gets to assume a clean initial load — it
inherits documents that arrive in waves as a loan progresses through underwriting (initial
application, then appraisal, then a revised appraisal, then a corrected credit pull weeks
later), and every one of those waves has to land through the same idempotent upsert path, never
a special-cased "first load" script that only gets tested once.


Compliance: The content_hash-gated upsert is also an audit control: a chunk whose stored
content_hash never changes is provable evidence nothing about that fact was silently altered
between two points in time, which matters when an underwriting decision several weeks later is
challenged and someone needs to confirm the appraised value the model saw was the one actually
on file, not a since-corrected figure retroactively applied without a trace.


What breaks in production: ON CONFLICT (chunk_id) protects against exact-key collisions,
but Day 3's own finding stands: page_no is not part of chunk_id's hash, so a chunk whose
underlying page shifts (Day 1's copybook-drift scenario, Day 2's re-OCR after a quarantine
review) can upsert into the wrong existing row if its chunk_id happens to still match on
loan_id/doc_type/chunk_index/effective_date alone. The idempotent-upsert guarantee this
concept demonstrates is only as strong as the key it's keyed on.

Concept 1 — Hybrid BM25 + Vector So Exact Loan Numbers Still Resolve


A dense-embedding-only retriever is trained to place semantically similar text near each
other — an exact identifier like LN0000002 is not a semantic concept, and Week 05 Day 2
already measured this failure directly for insurance policy numbers. The same failure shows up
here: a query naming a specific loan's appraisal can retrieve the WRONG loan's chunk under
vector search alone, because "appraised value" and a generic loan-shaped identifier both read
as similar text regardless of which specific loan number is present. BM25's exact-token
matching (Week 05 Day 1) resolves the identifier correctly where the embedding alone does not;
RRF fusion (Week 05 Day 3) combines both signals without needing either system's raw scores to
be comparable.

def tokenize(text):
    return re.findall(r"[a-z0-9]+(?:-[a-z0-9]+)*", text.lower())

# loan_id is folded into the indexed text, the way a real chunk's metadata
# header would be prepended before embedding/indexing (Day 3's contextual
# header pattern, reused from Week 09 Day 4 Concept 2).
docs_text = [c["text"] + " loan " + c["loan_id"] for c in CORPUS]
tokens = [tokenize(d) for d in docs_text]
N = len(CORPUS)
doc_lens = np.array([len(t) for t in tokens])
avgdl = doc_lens.mean()
df = {}
for t in tokens:
    for w in set(t):
        df[w] = df.get(w, 0) + 1

def idf(term):
    n = df.get(term, 0)
    return np.log(1 + (N - n + 0.5) / (n + 0.5))

def bm25_score(query_terms, doc_tokens, doc_len, k1=1.5, b=0.75):
    counts = {}
    for w in doc_tokens:
        counts[w] = counts.get(w, 0) + 1
    score = 0.0
    for term in query_terms:
        if term not in counts:
            continue
        f = counts[term]
        num = f * (k1 + 1)
        denom = f + k1 * (1 - b + b * doc_len / avgdl)
        score += idf(term) * (num / denom)
    return score

def bm25_rank(query_text):
    q = tokenize(query_text)
    scores = np.array([bm25_score(q, t, doc_lens[i]) for i, t in enumerate(tokens)])
    return scores, np.argsort(-scores)

DIM = 32

def trigrams(text):
    t = "  " + text.lower() + "  "
    return [t[i:i+3] for i in range(len(t) - 2)]

def embed(text, dim=DIM):
    vec = np.zeros(dim)
    for gram in trigrams(text):
        seed = zlib.crc32(gram.encode("utf-8"))
        rng = np.random.default_rng(seed)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

doc_vecs = np.array([embed(d) for d in docs_text])

def vector_rank(query_text):
    q = embed(query_text)
    scores = doc_vecs @ q
    return scores, np.argsort(-scores)

def ranks_of(scores):
    order = np.argsort(-scores)
    r = np.zeros(len(scores), dtype=int)
    for pos, doc in enumerate(order):
        r[doc] = pos + 1
    return r

def hybrid_rrf_rank(query_text, k=60):
    bm25_scores, _ = bm25_rank(query_text)
    vec_scores, _ = vector_rank(query_text)
    bm25_r = ranks_of(bm25_scores)
    vec_r = ranks_of(vec_scores)
    rrf = 1.0 / (k + bm25_r) + 1.0 / (k + vec_r)
    return rrf, np.argsort(-rrf)

query = "what is the appraised value for LN0000002"
_, bm25_order = bm25_rank(query)
_, vec_order = vector_rank(query)
_, hybrid_order = hybrid_rrf_rank(query)

def describe(order):
    return [(int(i), CORPUS[i]["loan_id"], CORPUS[i]["doc_type"]) for i in order[:3]]

print(f"query: {query!r}")
print("bm25   top-3:", describe(bm25_order))
print("vector top-3:", describe(vec_order))
print("hybrid top-3:", describe(hybrid_order))

Concept 2 — BGE Reranker as the Second Stage


The first stage's job (Concept 1) is recall — get every plausibly relevant chunk into a
manageable candidate set. The second stage's job is precision — re-score that small candidate
set with a model that can afford to look at the query and each candidate together, rather than
independently. bge-reranker-v2-m3's real checkpoint download is blocked in this sandbox
(Week 25's own confirmed finding: httpx.ProxyError: 403 Forbidden against
huggingface.co), so this reuses Week 25's MiniCrossEncoder stand-in, which reproduces the
real CrossEncoder.predict(pairs, batch_size=...) batching contract without needing the
blocked download.


Example:


# Reusing MiniCrossEncoder from Week 25 Day 2 Concept 1 verbatim.
class MiniCrossEncoder:
    def __init__(self, max_length=512):
        self.max_length = max_length
        self.truncated_count = 0

    def _score_pair(self, query, doc):
        q_toks = query.lower().split()
        d_toks = doc.lower().split()
        if len(d_toks) > self.max_length:
            d_toks = d_toks[:self.max_length]
            self.truncated_count += 1
        overlap = len(set(q_toks) & set(d_toks))
        return overlap / (len(set(q_toks)) or 1)

    def predict(self, pairs, batch_size=8, show_progress_bar=False):
        scores = []
        batch_count = 0
        for start in range(0, len(pairs), batch_size):
            batch = pairs[start:start + batch_size]
            batch_count += 1
            scores.extend(self._score_pair(q, d) for q, d in batch)
        return scores, batch_count

def rerank(query, candidate_indices, model, top_k=3):
    pairs = [(query, CORPUS[i]["text"]) for i in candidate_indices]
    scores, _ = model.predict(pairs, batch_size=4)
    order = np.argsort(-np.array(scores))
    return [candidate_indices[i] for i in order[:top_k]]

Concept 3 — A 30-Question Underwriting Query Set, Frozen as the Baseline


A retrieval system's quality claim is only real if it is measured against a fixed query set
with known-correct answers, the same way Week 26 required a golden set before trusting any
eval number. This concept builds that set programmatically — 4 document types x 2 loans x 4
question templates per type gives 32 candidate questions, frozen to the first 30 — with each
question's single correct chunk recorded, then measures recall@3 and MRR (both reused
from Week 05 Day 5 Concept 2) for three systems: BM25 alone, hybrid RRF, and hybrid plus
reranking. This is the frozen baseline Week 29's eval gate will compare future changes
against.


Example:


# Reusing mrr()/recall_at_k() from Week 05 Day 5 Concept 2.
def mrr(order, rel):
    for i, doc in enumerate(order):
        if rel.get(int(doc), 0) > 0:
            return 1.0 / (i + 1)
    return 0.0

def recall_at_k(order, rel, k):
    relevant = set(rel.keys())
    if not relevant:
        return 0.0
    return len(set(int(x) for x in order[:k]) & relevant) / len(relevant)

def evaluate_system(query_set, rank_fn, k=3):
    recalls, rrs = [], []
    for q in query_set:
        order = rank_fn(q["text"])
        rel = {q["relevant_idx"]: 1}
        recalls.append(recall_at_k(order, rel, k))

    return {"recall": round(float(np.mean(recalls)), 4), "mrr": round(float(np.mean(rrs)), 4)}

BFSI Reality Check — Day 5


Legacy: An underwriter's real question is almost never phrased as a clean, complete
sentence with the loan number spelled out — it is closer to a half-remembered fragment typed
into a search box, or a verbal question relayed through a call. The 30-question set's
templated phrasing is a reasonable first baseline, not a claim that real underwriter queries
look this tidy; Week 29's eval gate is the place a wider, messier query set would need to grow
into.


Compliance: The frozen baseline recorded here (recall@3/MRR per system) is itself a
compliance artifact, not just an engineering one — it is the documented evidence that this
retrieval stack was measured against a real, versioned query set before any underwriting
decision was ever built on top of it. A future regression (a re-indexed corpus, a swapped
embedding model) has something concrete to be checked against, the same discipline Week 27
wired into CI for this track's earlier RAG systems.


What breaks in production: This week's corpus is eight chunks from two loans; a real
underwriting index holds millions of chunks across hundreds of thousands of loans, and both
BM25's idf weighting and the reranker's candidate pool assumptions behave differently at
that scale — a top6 reranking window that comfortably covers "the right answer is probably
in here" on eight documents is almost certainly too narrow once every loan's four document
types multiply out across a real portfolio. Week 29 will need to revisit the candidate-pool
size, not just re-run this exact pipeline at scale unchanged.




Architecture Decision — Week 28


Choosing between: batch ingestion of the legacy loan export vs. streaming it record-by-record
as the mainframe writes it; and, separately, quarantine-and-continue vs. best-effort parsing for
document pages that fail Day 2's confidence floors.


Batch vs. streaming ingestion. The mainframe loan-origination system this week's Day 1 models
produces a RECFM=FB extract as a single, complete nightly file with its own trailer record —
there is no per-record stream to tap into even if streaming were preferred; the source system's
own export boundary is the file. Batch ingestion (read the whole file, validate the trailer's
control total against what was actually parsed, then load) fits that boundary exactly: Day 1's
LandingManifest reconciliation is a whole-file operation by construction, and it can only run
once the complete file has landed — a streaming pipeline that started emitting parsed records
before the trailer arrived would have nothing to reconcile against until the stream's very last
message, at which point any per-record decision already made downstream cannot be un-made
cheaply. Rule of thumb: batch when the source system's own natural unit of delivery is a
complete file with an end-of-file control record (a nightly mainframe extract, a daily bureau
file); move to streaming (Week 30's Kafka-based customer-query intake is the contrasting case in
this same phase) only when the source itself is genuinely a continuous, boundary-free stream of
individual events with no equivalent trailer to reconcile against.


Quarantine-and-continue vs. best-effort parsing. Day 2's OCR confidence floors route a page
either to acceptance or to a quarantine queue — never to a best-effort "accept it anyway, flag it
as low-confidence" middle path that keeps the pipeline's output looking complete. That choice
costs real throughput: every quarantined page is a document an underwriter's file is missing
until a human keys it in by hand, and Day 2's own "what breaks in production" note already shows
the floors do not catch every bad read, only the worst ones. The alternative — accepting every
OCR result and merely tagging low-confidence ones with a score — would keep the pipeline moving,
but it pushes the actual trust decision onto whatever reads the tag downstream, and Day 4's
content-hash-keyed upsert has no way to represent "this field is provisionally uncertain," only
"this field's content changed or it didn't." Rule of thumb: quarantine-and-continue when a
wrong value in the specific field at stake (an appraised value, a gross-pay figure) would
propagate into a financial decision with no further human check between the parse and the
decision — exactly mortgage underwriting's shape; best-effort-with-a-confidence-tag is the right
call only when a downstream consumer genuinely will check that tag before acting on the field,
which this week's pipeline does not yet build (Week 29's guardrail/decision layer is where that
check would have to live if this track later wanted to relax the quarantine gate).
