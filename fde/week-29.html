Concept 1 — A Typed StateGraph With Retrieve, Extract, Verify, and Decide Nodes

A loan file's path from "just retrieved" to "ready for a decision" is the same four-stage shape every underwriting workflow follows, whether it is a human analyst's checklist or an automated pipeline: pull the relevant documents, pull the numbers out of them, confirm nothing required is missing, then hand off to a decision. StateGraph (Week 19 Day 1) turns that into an explicit, typed contract instead of an implicit sequence of function calls — and, unlike Week 19's TypedDict state, this week's state is a real Pydantic BaseModel, so a node returning a field with the wrong type raises immediately at construction rather than silently propagating.

Example:

# Reusing StateGraph/START/END assembly pattern from Week 19 Day 1 Concepts 1
# and 4, with UnderwritingState now a Pydantic BaseModel instead of a
# TypedDict, and Week 28 Day 5 Concept 1's CORPUS (the frozen retrieval
# baseline) as the source of truth for which chunks exist per loan.
import re
from typing import Optional
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END

CORPUS = [
    {"loan_id": "LN0000001", "doc_type": "income", "page_no": 1,
     "text": "Borrower Maria Gonzalez, employed by Acme Logistics Inc. Gross monthly income $9,700.00 based on the most recent two pay stubs and a signed verification-of-employment letter."},
    {"loan_id": "LN0000001", "doc_type": "appraisal", "page_no": 2,
     "text": "Subject property at 412 Elm St appraised at $468,000 using three comparable sales within one mile, sold within the last six months. Appraiser: R. Fine, license #APR-4021."},
    {"loan_id": "LN0000001", "doc_type": "credit", "page_no": 3,
     "text": "Tri-merge credit report shows a FICO score of 742. Two open revolving accounts, one auto loan in good standing, no delinquencies in the last 24 months."},
    {"loan_id": "LN0000001", "doc_type": "title", "page_no": 4,
     "text": "Preliminary title report shows clear title, no liens or encumbrances of record. One prior deed of trust from 2018 fully reconveyed as of 2023."},
    {"loan_id": "LN0000002", "doc_type": "income", "page_no": 1,
     "text": "Borrower James Okafor, self-employed, owner of Okafor Consulting LLC. Two years of tax returns and a CPA-prepared profit and loss statement showing average monthly income of $8,100.00 over the trailing 24 months."},
    {"loan_id": "LN0000002", "doc_type": "appraisal", "page_no": 2,
     "text": "Subject property at 88 Birch Ave appraised at $451,500. Appraiser noted a detached garage adds functional utility but no measurable value adjustment versus the comparable set."},
    {"loan_id": "LN0000002", "doc_type": "credit", "page_no": 3,
     "text": "Tri-merge credit report shows a FICO score of 701. One 30-day-late payment on a retail credit card 14 months ago, otherwise a clean payment history across four trade lines."},
    {"loan_id": "LN0000002", "doc_type": "title", "page_no": 4,
     "text": "Title search shows one active HOA lien of $340 for unpaid dues, to be paid off at closing from seller proceeds per the purchase contract's title cure provision."},
]
REQUIRED_DOC_TYPES = ["income", "appraisal", "credit", "title"]


class UnderwritingState(BaseModel):
    loan_id: str
    retrieved_doc_types: list[str] = Field(default_factory=list)
    missing_doc_types: list[str] = Field(default_factory=list)
    extracted: dict = Field(default_factory=dict)
    verified: bool = False
    decision: Optional[str] = None
    notes: list[str] = Field(default_factory=list)


def retrieve_node(state: UnderwritingState):
    chunks = [c for c in CORPUS if c["loan_id"] == state.loan_id]
    doc_types = sorted({c["doc_type"] for c in chunks})
    return {"retrieved_doc_types": doc_types,
            "notes": state.notes + [f"retrieved {len(chunks)} chunks: {doc_types}"]}


def extract_node(state: UnderwritingState):
    extracted = {}
    for c in CORPUS:
        if c["loan_id"] != state.loan_id:
            continue
        if c["doc_type"] == "income":
            m = re.search(r"income of \$([\d,]+\.\d{2})|income \$([\d,]+\.\d{2})", c["text"])
            if m:
                extracted["monthly_income"] = float((m.group(1) or m.group(2)).replace(",", ""))
        elif c["doc_type"] == "appraisal":
            m = re.search(r"appraised at \$([\d,]+)", c["text"])
            if m:
                extracted["appraised_value"] = float(m.group(1).replace(",", ""))
        elif c["doc_type"] == "credit":
            m = re.search(r"FICO score of (\d+)", c["text"])
            if m:
                extracted["fico_score"] = int(m.group(1))
    return {"extracted": extracted, "notes": state.notes + [f"extracted fields: {sorted(extracted)}"]}


def verify_node(state: UnderwritingState):
    missing = [d for d in REQUIRED_DOC_TYPES if d not in state.retrieved_doc_types]
    return {"missing_doc_types": missing, "verified": len(missing) == 0,
            "notes": state.notes + [f"verify: missing={missing}"]}


def decide_node(state: UnderwritingState):
    return {"decision": "proceed_to_decision", "notes": state.notes + ["routed to decision layer"]}


g = StateGraph(UnderwritingState)
g.add_node("retrieve", retrieve_node)
g.add_node("extract", extract_node)
g.add_node("verify", verify_node)
g.add_node("decide", decide_node)
g.add_edge(START, "retrieve")
g.add_edge("retrieve", "extract")
g.add_edge("extract", "verify")
g.add_edge("verify", "decide")
g.add_edge("decide", END)
graph = g.compile()

result1 = graph.invoke(UnderwritingState(loan_id="LN0000001"))
result2 = graph.invoke(UnderwritingState(loan_id="LN0000002"))
print(f"LN0000001 extracted: {result1['extracted']}")
print(f"LN0000001 missing_doc_types: {result1['missing_doc_types']}  decision: {result1['decision']}")
print(f"LN0000002 extracted: {result2['extracted']}")
print(f"LN0000002 missing_doc_types: {result2['missing_doc_types']}  decision: {result2['decision']}")

Concept 2 — SqliteSaver Checkpointing So a Stalled Loan Resumes, Not Restarts


A real extraction step calls out to something that can genuinely time out — a document
OCR/extraction microservice, a rate-limited API. When that happens mid-run, a stateless
pipeline restarts from retrieve, redoing work that already succeeded; a checkpointed
StateGraph resumes from exactly the node that was about to run, with everything before it
already durably saved. Reusing Week 19 Day 2 Concept 2's SqliteSaver setup verbatim: a real
on-disk file, not an in-memory dict, so this is demonstrated across a genuine dropped-and-
reopened Python process, not merely asserted.


Example:


# Reusing SqliteSaver setup from Week 19 Day 2 Concept 2 verbatim.
import os
import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

FAIL_ON_FIRST_CALL = {"tripped": False}

def flaky_extract_node(state: UnderwritingState):
    """Same as extract_node, but simulates a transient failure (a downstream
    document-extraction service timing out) on the first call for this
    thread only."""
    if not FAIL_ON_FIRST_CALL["tripped"]:
        FAIL_ON_FIRST_CALL["tripped"] = True
        raise RuntimeError("extraction service timeout (simulated transient failure)")
    return extract_node(state)

g2 = StateGraph(UnderwritingState)
g2.add_node("retrieve", retrieve_node)
g2.add_node("extract", flaky_extract_node)
g2.add_node("verify", verify_node)
g2.add_node("decide", decide_node)
g2.add_edge(START, "retrieve")
g2.add_edge("retrieve", "extract")
g2.add_edge("extract", "verify")
g2.add_edge("verify", "decide")
g2.add_edge("decide", END)

if os.path.exists("loan_checkpoints.db"):
    os.remove("loan_checkpoints.db")
conn = sqlite3.connect("loan_checkpoints.db", check_same_thread=False)
checkpointer = SqliteSaver(conn)
checkpointer.setup()
graph_a = g2.compile(checkpointer=checkpointer)
config = {"configurable": {"thread_id": "loan-LN0000001"}}

try:
    graph_a.invoke(UnderwritingState(loan_id="LN0000001"), config=config)
    print("first invoke: no exception (unexpected)")
except RuntimeError as e:
    print(f"first invoke raised: {e}")

state_after_crash = graph_a.get_state(config)
print(f"checkpoint after crash has retrieved_doc_types: {state_after_crash.values.get('retrieved_doc_types')}")
print(f"checkpoint after crash has extracted: {state_after_crash.values.get('extracted')}")
print(f"next node to run: {state_after_crash.next}")

# Simulate a real process restart: drop every in-memory object, reopen the
# SAME on-disk file from scratch.
del graph_a, checkpointer, conn
conn2 = sqlite3.connect("loan_checkpoints.db", check_same_thread=False)
checkpointer2 = SqliteSaver(conn2)
graph_b = g2.compile(checkpointer=checkpointer2)

result = graph_b.invoke(None, config=config)
print(f"resumed decision: {result['decision']}")
print(f"resumed extracted: {result['extracted']}")

Concept 3 — Conditional Edges Routing Back for a Missing-Document Loop


add_conditional_edges (Week 19 Day 1 Concept 4) is what turns Concept 1's straight-through
verify -> decide edge into a genuine loop: when verify finds a required document type
missing, the graph routes back to retrieve instead of proceeding, on the theory that the
missing document may have landed since the last attempt. That loop needs a hard cap — an
unconditional retry-forever would hang on a loan that is genuinely, permanently missing a
document — so a bounded retry_count routes to a distinct await_documents terminal node
once the cap is hit, landing the loan in a human document-request queue rather than looping
silently forever.


Example:


MAX_RETRIEVE_RETRIES = 2


class LoopState(BaseModel):
    loan_id: str
    retrieved_doc_types: list[str] = Field(default_factory=list)
    missing_doc_types: list[str] = Field(default_factory=list)
    extracted: dict = Field(default_factory=dict)
    verified: bool = False
    decision: Optional[str] = None
    retry_count: int = 0
    notes: list[str] = Field(default_factory=list)


def retrieve_node_loop(state: LoopState):
    chunks = [c for c in CORPUS if c["loan_id"] == state.loan_id]
    doc_types = sorted({c["doc_type"] for c in chunks})
    return {"retrieved_doc_types": doc_types,
            "notes": state.notes + [f"retrieve attempt {state.retry_count}: found {doc_types}"]}


def extract_node_loop(state: LoopState):
    return extract_node(state)  # reusing extract_node from Concept 1 unchanged


def verify_node_loop(state: LoopState):
    missing = [d for d in REQUIRED_DOC_TYPES if d not in state.retrieved_doc_types]
    return {"missing_doc_types": missing, "verified": len(missing) == 0,
            "notes": state.notes + [f"verify attempt {state.retry_count}: missing={missing}"]}


def bump_retry_node(state: LoopState):
    return {"retry_count": state.retry_count + 1}


def decide_node_loop(state: LoopState):
    return {"decision": "proceed_to_decision"}


def awaiting_documents_node(state: LoopState):
    return {"decision": "awaiting_documents",
            "notes": state.notes + [f"exceeded {MAX_RETRIEVE_RETRIES} retrieve retries, still missing "
                                     f"{state.missing_doc_types} -- routed to human document-request queue"]}


def route_after_verify(state: LoopState):
    if not state.missing_doc_types:
        return "decide"
    if state.retry_count < MAX_RETRIEVE_RETRIES:
        return "retry"
    return "await_documents"


g3 = StateGraph(LoopState)
g3.add_node("retrieve", retrieve_node_loop)
g3.add_node("extract", extract_node_loop)
g3.add_node("verify", verify_node_loop)
g3.add_node("bump_retry", bump_retry_node)
g3.add_node("decide", decide_node_loop)
g3.add_node("await_documents", awaiting_documents_node)
g3.add_edge(START, "retrieve")
g3.add_edge("retrieve", "extract")
g3.add_edge("extract", "verify")
g3.add_conditional_edges("verify", route_after_verify,
                          {"decide": "decide", "retry": "bump_retry", "await_documents": "await_documents"})
g3.add_edge("bump_retry", "retrieve")
g3.add_edge("decide", END)
g3.add_edge("await_documents", END)
graph3 = g3.compile()

complete_result = graph3.invoke(LoopState(loan_id="LN0000001"))
print(f"LN0000001 (complete file) decision: {complete_result['decision']}  "
      f"retry_count: {complete_result['retry_count']}")

stuck_result = graph3.invoke(LoopState(loan_id="LN0000099"))
print(f"LN0000099 (no documents on file) decision: {stuck_result['decision']}  "
      f"retry_count: {stuck_result['retry_count']}")
print(f"LN0000099 last note: {stuck_result['notes'][-1]}")

BFSI Reality Check — Day 1


Legacy: Week 28's ingestion pipeline lands documents in batches (a nightly mainframe
extract, a scanned-document drop), which means "the title search hasn't arrived yet" is a
completely ordinary, expected state for a loan file mid-process, not an edge case — this
day's retry-and-loop-back structure is built for that as the normal path, not a rare failure.


Compliance: notes accumulating across every node (rather than being overwritten) gives
an auditor the full sequence of what the workflow actually did for a given loan — every
retrieve attempt, every verify outcome, exactly which retry finally supplied the missing
document — the same audit-trail property Week 19 Day 1's operator.add reducer established,
now applied to a workflow whose outcome directly affects a lending decision.


What breaks in production: MAX_RETRIEVE_RETRIES=2 here is tuned to a toy corpus with an
instantly-available static list — a real document-request queue takes hours or days for a
human to fulfill, so a production version of this loop needs bump_retry to route through an
actual wait (a scheduled re-check, not a synchronous retry in the same invocation), or the
graph will exhaust its retry cap and land every genuinely slow-to-arrive document in
await_documents regardless of whether it was ever really stuck.

Concept 1 — A Custom PatternRecognizer for SSN, Account, and Loan Numbers


An underwriter's note is exactly the kind of free text Week 14 built Presidio recognizers
for — except this week's identifiers have their own shapes: a dashed SSN, this track's
LN\d{7} loan-id format (Week 28's own loan_id field), and an internal account number.
Reusing Week 14 Day 2 Concept 1's Pattern/PatternRecognizer construction verbatim, just
retargeted to these three shapes under one custom entity type.


Example:


# Reusing PatternRecognizer/Pattern construction from Week 14 Day 2 Concept 1
# verbatim, retargeted to this week's SSN/loan-id/account-number shapes.
from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
from presidio_analyzer.nlp_engine import NlpEngineProvider

provider = NlpEngineProvider(nlp_configuration={
    "nlp_engine_name": "spacy",
    "models": [{"lang_code": "en", "model_name": "en_core_web_sm"}],
})
analyzer = AnalyzerEngine(nlp_engine=provider.create_engine())

ssn_pattern = Pattern(name="ssn_dashed", regex=r"\b\d{3}-\d{2}-\d{4}\b", score=0.9)
loan_id_pattern = Pattern(name="loan_id", regex=r"\bLN\d{7}\b", score=0.9)
account_pattern = Pattern(name="account_number", regex=r"\bACCT-\d{8}\b", score=0.9)

underwriting_recognizer = PatternRecognizer(
    supported_entity="UNDERWRITING_ID",
    name="underwriting_recognizer",
    patterns=[ssn_pattern, loan_id_pattern, account_pattern],
)
analyzer.registry.add_recognizer(underwriting_recognizer)

loan_note = (
    "Underwriter note: borrower Maria Gonzalez (SSN 512-34-8765) applied for loan LN0000001, "
    "linked deposit account ACCT-88214410. Co-signer James Okafor (SSN 601-22-9931) is listed "
    "on loan LN0000002."
)

results = analyzer.analyze(text=loan_note, language="en",
                            entities=["UNDERWRITING_ID", "PERSON"])
for r in sorted(results, key=lambda r: r.start):
    print(f"  {r.entity_type:<18}score={r.score:.2f}  {loan_note[r.start:r.end]!r}")
print(f"total matches: {len(results)}")

Concept 2 — Reversible Tokenization: Masking Before the LLM, Re-identifying After


Presidio's detection alone is only half the job — before any of this note reaches an LLM
call (Day 3's decision narrative), every UNDERWRITING_ID span needs to be masked in a way
that can be reversed AFTER the call, so the final decision record can be re-identified for
the actual loan file without the LLM itself ever seeing the plaintext SSN or account number.
Reusing Week 14 Day 3 Concept 2's AnonymizerEngine/DeanonymizeEngine encrypt/decrypt
pattern verbatim — genuine AES encryption, not a reversible-looking placeholder.

Legacy: An underwriter's freeform notes field is exactly the kind of unstructured legacy
text this whole capstone is built around — nobody typed those notes expecting an LLM pipeline
to read them, so the PII patterns have to be discovered and codified after the fact (Concept

Compliance: Reversible tokenization (Concept 2) is what makes it possible to send loan

promise trustworthy rather than theater.


What breaks in production: Concept 4's own finding is the whole point of this Reality
Check: a regex-based self-check rail has blind spots for any paraphrase its author didn't

only as strong as the LLM answering them — a real deployment needs the prompt-injection test
suite to keep growing with every new bypass discovered in production, not to be written once
and trusted forever.

def build_chunk_id(loan_id, doc_type, page_no, text):
    return hashlib.sha256(f"{loan_id}:{doc_type}:{page_no}:{text}".encode()).hexdigest()[:16]

for c in CORPUS:
    c["chunk_id"] = build_chunk_id(c["loan_id"], c["doc_type"], c["page_no"], c["text"])

CHUNKS_BY_LOAN_TYPE = {(c["loan_id"], c["doc_type"]): c for c in CORPUS}


class Citation(BaseModel):
    chunk_id: str
    doc_type: str
    page_no: int


class CitedField(BaseModel):
    value: float
    citation: Citation


class UnderwritingDecision(BaseModel):
    loan_id: str
    monthly_income: CitedField
    appraised_value: CitedField
    fico_score: CitedField

    "income": (r"income of \$([\d,]+\.\d{2})|income \$([\d,]+\.\d{2})", "monthly_income"),
    "appraisal": (r"appraised at \$([\d,]+)", "appraised_value"),
    "credit": (r"FICO score of (\d+)", "fico_score"),
}

        fields[field_name] = CitedField(
            value=value,
            citation=Citation(chunk_id=chunk["chunk_id"], doc_type=doc_type, page_no=chunk["page_no"]),
        )
    return UnderwritingDecision(loan_id=loan_id, **fields)

Concept 2 — Deterministic DTI/LTV, Compared Against the LLM's Own Narrative


DTI (debt-to-income) and LTV (loan-to-value) are plain arithmetic — dividing two numbers this
pipeline already has cited, exact values for. There is no reason to ask an LLM to compute
them, and every reason not to: computing them in Python and then checking whether the LLM's
own narrative text agrees is a genuine grounding check, not a courtesy. The narrative
generation itself is this week's one real REAL MODE boundary (no live LLM API in this
sandbox) — narrative_for below is a disclosed stand-in that deliberately introduces one
genuine numeric slip, so the comparison has something real to catch, the same honest-failure
convention Week 28 Day 5 used for its retrieval baseline.


Example:

UnderwritingDecision has no field that can represent "unknown" for monthly_income — every

Concept 4 — Rejecting Any Field Asserted Without a Citation


Concepts 1-3 build citations by construction — every CitedField this pipeline produces
already has one, because build_decision only ever reads a value out of a chunk it also has
the chunk_id for. A real LLM-based extraction call is not so well-behaved: it can assert a
value with no citation, a citation to a chunk_id that was never actually retrieved
(a hallucinated reference), or a citation to a real chunk that belongs to the WRONG loan.
validate_llm_claims is the gate that catches all three before any of them reach a decision
record.


Example:


# Reusing CORPUS/CHUNKS_BY_LOAN_TYPE from Concept 1.
VALID_CHUNK_IDS = {c["chunk_id"] for c in CORPUS}


class UngroundedFieldError(ValueError):
    pass


def validate_llm_claims(loan_id, raw_claims):
    validated = {}
    for claim in raw_claims:
        field_name = claim["field"]
        chunk_id = claim.get("chunk_id")
        if not chunk_id:
            raise UngroundedFieldError(f"field {field_name!r} has no citation at all")
        if chunk_id not in VALID_CHUNK_IDS:
            raise UngroundedFieldError(
                f"field {field_name!r} cites chunk_id {chunk_id!r}, which was never retrieved "
                f"for this pipeline run"
            )
        matching_chunk = next(c for c in CORPUS if c["chunk_id"] == chunk_id)
        if matching_chunk["loan_id"] != loan_id:
            raise UngroundedFieldError(
                f"field {field_name!r} cites a chunk belonging to loan "
                f"{matching_chunk['loan_id']!r}, not {loan_id!r}"
            )
        validated[field_name] = claim["value"]
    return validated

Legacy: LOAN_APPLICATIONS' loan_amount/monthly_debt facts trace back to Week 28 Day

def bm25_score(query_terms, doc_tokens, doc_len, k1=1.5, b=0.75):
    counts = {}
    for w in doc_tokens:
        counts[w] = counts.get(w, 0) + 1
    score = 0.0
    for term in query_terms:
        if term not in counts:
            continue
        f = counts[term]
        num = f * (k1 + 1)
        denom = f + k1 * (1 - b + b * doc_len / avgdl)
        score += idf(term) * (num / denom)
    return score

    q = tokenize(query_text)
    scores = np.array([bm25_score(q, t, doc_lens[i]) for i, t in enumerate(tokens)])
    return scores, np.argsort(-scores)

def trigrams(text):
    t = "  " + text.lower() + "  "
    return [t[i:i+3] for i in range(len(t) - 2)]

def embed(text, dim=DIM):
    vec = np.zeros(dim)
    for gram in trigrams(text):
        seed = zlib.crc32(gram.encode("utf-8"))
        rng = np.random.default_rng(seed)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

def vector_rank(query_text):
    q = embed(query_text)
    scores = doc_vecs @ q
    return scores, np.argsort(-scores)

    order = np.argsort(-scores)
    r = np.zeros(len(scores), dtype=int)
    for pos, doc in enumerate(order):
        r[doc] = pos + 1
    return r

    bm25_scores, _ = bm25_rank(query_text)
    vec_scores, _ = vector_rank(query_text)
    bm25_r = ranks_of(bm25_scores)
    vec_r = ranks_of(vec_scores)
    rrf = 1.0 / (k + bm25_r) + 1.0 / (k + vec_r)

Concept 2 — The Gate: Absolute Floors Plus Baseline-Regression Checks


Reusing Week 27 Day 3 Concept 1's evaluate_gate/EvalGateError/composite_score pattern
verbatim: an absolute floor catches a metric that is simply too low to ship, and a separate
baseline-regression check catches a metric that clears the floor but has quietly gotten worse
than a recorded prior run — exactly the two-layer gate Week 27 built to stop a regression an
absolute-floor-only check would wave through.


Example:


# Reusing evaluate_gate/EvalGateError/composite_score from Week 27 Day 3
# Concept 1 verbatim, retargeted to this week's faithfulness/context_precision
# pair.
class EvalGateError(ValueError):
    pass

EVAL_CONFIG = {
    "weights": {"faithfulness": 0.5, "context_precision": 0.5},
    "thresholds": {"composite_min": 0.45, "faithfulness_min": 0.5},
    "baseline": {"faithfulness": 0.90, "context_precision": 0.30},
    "max_regression": {"faithfulness": 0.05, "context_precision": 0.05},
}

def composite_score(metrics, config):
    weights = config["weights"]
    return round(sum(metrics[m] * w for m, w in weights.items()), 4)

def evaluate_gate(metrics, config):
    faithfulness_floor = config["thresholds"]["faithfulness_min"]
    if metrics["faithfulness"] < faithfulness_floor:
        raise EvalGateError(f"faithfulness {metrics['faithfulness']} below absolute floor {faithfulness_floor}")

    composite = composite_score(metrics, config)
    composite_floor = config["thresholds"]["composite_min"]
    if composite < composite_floor:
        raise EvalGateError(f"composite {composite} below absolute floor {composite_floor}")

    for metric_name, baseline_value in config["baseline"].items():
        current = metrics[metric_name]
        drop = round(baseline_value - current, 4)
        max_drop = config["max_regression"][metric_name]
        if drop > max_drop:
            raise EvalGateError(
                f"{metric_name} dropped {drop} vs. baseline {baseline_value} "
                f"(current {current}), exceeding max allowed drop {max_drop}"
            )
    return composite

current_metrics = {"faithfulness": mean_faithfulness, "context_precision": mean_precision}
try:
    score = evaluate_gate(current_metrics, EVAL_CONFIG)
    print(f"gate PASS  composite={score}")
except EvalGateError as e:
    print(f"gate FAIL  {e}")

regressed_metrics = {"faithfulness": 0.70, "context_precision": mean_precision}
try:
    score = evaluate_gate(regressed_metrics, EVAL_CONFIG)
    print(f"regressed gate PASS  composite={score}")
except EvalGateError as e:

Concept 4 — Triage: Splitting Retrieval Misses From Generation Errors


Concept 3's 1.0 accuracy assumed the correct chunk was already found — a real pipeline has
to actually retrieve it first. This concept runs the FULL retrieve-then-extract path (the
pipeline's own top-1 hybrid_rrf_rank result, not a direct lookup) and classifies every wrong
final answer as either a RETRIEVAL miss (the correct chunk wasn't even the top-1 result) or a
GENERATION error (the correct chunk was retrieved, but extraction from it still produced the
wrong value) — the two failure modes need completely different fixes, so a single "wrong"
bucket would hide which part of the pipeline actually needs work.


Example:


retrieval_misses = []
generation_errors = []
correct_end_to_end = []

for case in field_cases:
    _, order = hybrid_rrf_rank(case["query"])
    top1_idx = int(order[0])
    retrieval_hit = top1_idx == case["relevant_idx"]

    if not retrieval_hit:
        retrieval_misses.append(case)
        continue

    field_name, extracted_value = extract_field(case["loan_id"], case["doc_type"])
    if abs(extracted_value - case["expected_value"]) < 0.01:
        correct_end_to_end.append(case)
    else:
        generation_errors.append(case)

print(f"total field-bearing cases: {len(field_cases)}")
print(f"correct end-to-end: {len(correct_end_to_end)}")
print(f"retrieval misses (wrong chunk retrieved at top-1): {len(retrieval_misses)}")
print(f"generation errors (right chunk, wrong extracted value): {len(generation_errors)}")

Reusing Week 16 Day 3 Concept 2's OpenLineageClient/ConsoleTransport/emit_stage_run
context-manager pattern verbatim, wired around all five of this pipeline's real stages instead

Example:


# Reusing OpenLineageClient/ConsoleTransport/RunEvent/emit_stage_run pattern
# from Week 16 Day 3 Concept 2 verbatim, retargeted to this pipeline's five
# real stages instead of Week 16's parse/chunk pair. ConsoleTransport logs
# through Python's logging module to stderr, never Python's own stdout --
# nothing it prints is part of this block's captured/diffed output.
import contextlib
import datetime
import logging

from openlineage.client import OpenLineageClient
from openlineage.client.transport.console import ConsoleConfig, ConsoleTransport
from openlineage.client.run import Job, Run, RunEvent, RunState
from openlineage.client.uuid import generate_new_uuid

logging.basicConfig(level=logging.INFO, format="%(message)s")
client = OpenLineageClient(transport=ConsoleTransport(ConsoleConfig()))


@contextlib.contextmanager
def emit_stage_run(job_namespace, job_name, producer="fde-underwriting-pipeline"):
    run_id = str(generate_new_uuid())
    run, job = Run(runId=run_id), Job(namespace=job_namespace, name=job_name)
    client.emit(RunEvent(
        eventType=RunState.START,
        eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
        run=run, job=job, producer=producer,
    ))
    try:
        yield run_id
    except Exception:
        client.emit(RunEvent(
            eventType=RunState.FAIL,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))
        raise
    else:
        client.emit(RunEvent(
            eventType=RunState.COMPLETE,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))


PIPELINE_NAMESPACE = "fde.underwriting"
run_ids = []

def run_pipeline_stage(stage_name, fn, *args):
    with emit_stage_run(PIPELINE_NAMESPACE, stage_name) as run_id:
        result = fn(*args)
        run_ids.append((stage_name, run_id))
        return result

    return f"parsed documents for {loan_id}"

Concept 3 — A Human-Review Queue Fed by Abstains and Low-Confidence Decisions


Day 3's AbstainedDecision type and a below-threshold confidence signal both need somewhere
to land that a human actually checks — this concept builds that queue directly: every abstain
becomes a high-priority entry, every low-confidence decision (here, a FICO score below a
threshold) becomes medium-priority, and a normal, confident decision never enters the queue at
all.


Example:


from pydantic import BaseModel

GROUND_TRUTH = {
    "LN0000001": {"monthly_income": 9700.0, "appraised_value": 468000.0, "fico_score": 742.0},
    "LN0000002": {"monthly_income": 8100.0, "appraised_value": 451500.0, "fico_score": 701.0},
}

    loan_id: str
    reason: str
    priority: str


def evaluate_loan(loan_id):

Architecture Decision — Week 29


Choosing between: auto-deciding a loan outright vs. always routing every decision through a
human reviewer; and, separately, how much of this week's own eval gate (Day 4) should block a
release outright vs. only alert.


Auto-decide vs. always-human-review. This week's decision layer deliberately does neither
extreme. A pipeline that auto-decides every loan with no human in the loop treats Day 3's
grounding machinery — citations, deterministic DTI/LTV, the abstain path — as sufficient
authorization to act on a lending decision, which it is not: Day 4's own triage found a real
24/48 retrieval-miss rate at top-1 on a corpus far smaller and cleaner than production will
ever be, and a wrong-but-confident decision in mortgage underwriting has real financial and
fair-lending consequences no amount of citation-checking alone fully closes out. A pipeline that
instead routes every single loan to a human reviewer regardless of confidence wastes the entire
point of building this system — an underwriter re-verifying every citation on every loan by
hand gets none of Day 1-4's actual leverage. Day 5's review queue is the deliberate middle
path: evaluate_loan's abstain and low-confidence signals are exactly the cases this pipeline
has genuine reason to distrust itself on, and only those go to a human — a confident, fully
cited, grounded decision (Day 3's UnderwritingDecision, not AbstainedDecision) ships without
waiting on a person. Rule of thumb: auto-decide only the slice of cases a concrete,
measured signal (an abstain, a below-threshold confidence score, a citation-validation
failure) says the pipeline itself has no reason to doubt; route everything else — by default,
not by exception — to a human, and treat "route to human" as the SAFE default a case has to
earn its way out of, not something a case has to earn its way into.


How much of the eval gate blocks release vs. only alerts. Day 4's evaluate_gate raises
EvalGateError on both an absolute-floor breach and a baseline-regression breach — but not
every metric deserves the same response. faithfulness dropping below its absolute floor
means the pipeline is asserting things its own retrieved evidence does not support, which is
exactly the failure mode Day 3's whole citation-validation layer exists to prevent — that
blocks release outright, no exceptions, the same hard-stop Week 27's own gate enforced.
context_precision regressing past its baseline tolerance is different: it is a real signal
something changed for the worse, but Day 4's own Concept 1 showed this metric's natural ceiling
on a small corpus is itself low and corpus-size-dependent — a context_precision regression on
its own, with faithfulness and per-field decision accuracy both still healthy, is closer to
"investigate before the next release" than "stop this one." Rule of thumb: block release on
any metric whose failure means the pipeline's own OUTPUT can no longer be trusted
(faithfulness, per-field decision accuracy against ground truth, the citation-validation gate
itself); alert-but-don't-block on a metric that measures pipeline HEALTH but where a human
still checks every low-confidence case anyway (Day 5's own review queue is already the backstop
for exactly that class of miss) — the review queue and the release gate are two different
control points for two different kinds of risk, and conflating them into one on/off switch
