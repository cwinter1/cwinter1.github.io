Concept 1 — A Masked Production Copy Is Still In Scope

"We masked it" is not the same claim as "it is out of regulatory scope." Masking hides a column at display time; it does nothing about the other columns sitting next to it. If a record still carries a 5-digit ZIP code, an exact birth date, and a sex flag, those three fields alone are often enough to re-identify a specific person even after the account number and name are gone — a fact from the re-identification literature (Sweeney's 1997 finding on U.S. voter records, using the same three quasi-identifiers), not a hypothetical.

The fix is not "mask more columns," it is generalizing the columns you keep until no combination of them singles out one person. That is a different operation from masking, and it is the one that actually moves data out of scope.

Example:

from faker import Faker
from collections import Counter

Faker.seed(11)
f = Faker()

n = 2000
records = []
for _ in range(n):
    zipcode = f.zipcode()
    dob = f.date_of_birth(minimum_age=18, maximum_age=90)
    sex = f.random_element(['M', 'F'])
    records.append({
        'zip5': zipcode,
        'zip1': zipcode[0],
        'birth_date': dob,
        'birth_decade': (dob.year // 10) * 10,
        'sex': sex,
    })

def unique_fraction(recs, keys):
    combos = Counter(tuple(r[k] for k in keys) for r in recs)
    singleton = sum(1 for c in combos.values() if c == 1)
    return singleton / len(recs), len(combos)

fine_frac, fine_combos = unique_fraction(records, ['zip5', 'birth_date', 'sex'])
coarse_frac, coarse_combos = unique_fraction(records, ['zip1', 'birth_decade', 'sex'])
print(f'n = {n}')
print(f'fine   (zip5 + exact birth date + sex)    : {fine_combos} distinct combos, {fine_frac:.3f} of records uniquely identified')
print(f'coarse (zip 1st digit + birth decade + sex): {coarse_combos} distinct combos, {coarse_frac:.3f} of records uniquely identified')

Concept 2 — PCI-DSS Scope Reduction Is a Practical Driver, Not a Slogan


PCI-DSS Requirement 3.4.1 (v4.0; numbered 3.3 under the earlier v3.2.1 standard) sets a
display rule: when a primary account number (PAN) is shown, no more than the first six
and last four digits may appear. That is the rule behind
every receipt printed as 4716 20** **** 0028. It is easy to mistake that display rule for
a scope-reduction technique, and they are not the same thing: the full PAN still exists in
storage behind the mask, so the system storing it is still in PCI-DSS scope. Actual scope
reduction means the real PAN is never present at all — tokenized at the point of capture, or
in this case, never generated as a real number in the first place because the environment
is fully synthetic.


Example:


from faker import Faker

Faker.seed(31)
f = Faker()

def pci_display_mask(pan):
    return pan[:6] + ('*' * (len(pan) - 10)) + pan[-4:]

pans = [f.credit_card_number(card_type='visa16') for _ in range(3)]
for pan in pans:
    print(f'{pan}  ->  display-masked: {pci_display_mask(pan)}')

Concept 3 — Synthetic, Anonymized and Pseudonymized Are Three Different Things


These three words get used interchangeably in casual conversation and mean genuinely
different things under GDPR and in practice:


    

  • Pseudonymized data replaces an identifier with a token generated from it — typically
a keyed hash — so the same input always produces the same token (joins across tables
still work) but the mapping requires a key to reverse. GDPR still treats this as personal
data, because it is reversible given the key.
    • 

  • Anonymized data has identifiers generalized or removed until no reasonable means of
re-identification remains — no key exists that undoes it, because the specific values
were never kept.
    • 

  • Synthetic data has no per-record link to any real individual at all — it was
generated fresh, and there is nothing to re-identify because nothing behind it ever
existed.
    • 



Only the third is genuinely outside GDPR's scope from the start. The first still requires
protecting a key; the second requires a real generalization/suppression process applied
correctly (Concept 1's failure mode is exactly what happens when it's applied poorly).


Example:


import hashlib, hmac
from faker import Faker

Faker.seed(21)
f = Faker()

# Stand-in for a real-shaped source record -- a hand-built example dict used
# only to demonstrate the three transforms, never real customer data.
real_like_record = {
    'customer_id': 'CUST-00458231',
    'zip5': '30301',
    'birth_date': '1982-04-17',
}

SECRET_KEY = b'dev-only-demo-key-never-a-real-secret'

def pseudonymize(customer_id, key=SECRET_KEY):
    return hmac.new(key, customer_id.encode(), hashlib.sha256).hexdigest()[:16]

def anonymize(record):
    return {
        'zip_prefix': record['zip5'][:1],
        'birth_decade': int(record['birth_date'][:4]) // 10 * 10,
    }

def synthesize():
    return {
        'customer_id': f.bothify('CUST-########'),
        'zip5': f.zipcode(),
        'birth_date': f.date_of_birth(minimum_age=18, maximum_age=90).isoformat(),
    }

pseudo_id = pseudonymize(real_like_record['customer_id'])
pseudo_id_again = pseudonymize(real_like_record['customer_id'])
anon = anonymize(real_like_record)
synth = synthesize()

print('pseudonymized id (stable across calls):', pseudo_id, pseudo_id == pseudo_id_again)
print('anonymized       :', anon)
print('synthetic        :', synth)

BFSI Reality Check — Day 1


Legacy angle: A half-migrated AWS estate usually means the on-prem system is the
system of record and the cloud side is read replicas or a data lake fed by nightly batch —
so "just point dev at a copy" often means copying an on-prem extract into a cloud dev
account, which can itself be a cross-border data movement question depending on where that
dev account's region actually is.


Compliance angle: GDPR's territorial scope and most local data-residency rules care
about where personal data physically sits and who can access it, not about the labels a
team uses internally. "It's just a dev environment" is not a legal argument; a masked
column next to unmasked quasi-identifiers is not anonymization; and the burden of proving
data is genuinely out of scope sits with the team that moved it, not with the regulator.


What breaks in production: A "temporary" masked-prod-copy dev database that was
supposed to be deleted after one migration project outlives the project by years, because
nobody owned turning it off. Synthetic data sidesteps this entirely — there is no
production copy to forget about, because one was never made.

Concept 1 — Faker.seed() for a Reproducible Corpus


Faker.seed() is a classmethod that seeds the shared random generator every Faker()
instance draws from. Call it once before generating anything, and the exact same sequence
of fake values comes out every time the script runs — on this machine, on a teammate's
machine, in CI next month. That reproducibility is what makes a synthetic dataset a
genuine test fixture rather than a moving target: a regression test that asserts against
specific synthetic values only works if those values are stable across runs.


Example:


from faker import Faker

Faker.seed(42)
f1 = Faker()
run1 = [f1.name() for _ in range(3)]

Faker.seed(42)
f2 = Faker()
run2 = [f2.name() for _ in range(3)]

print('run1:', run1)
print('run2:', run2)
print('identical:', run1 == run2)

Concept 3 — A Custom BaseProvider for Policy and Claim Numbers


Faker has no idea what a policy number looks like at your company, because there's no
universal standard — each insurer invents its own scheme. That's what BaseProvider is
for: subclass it, add methods, register it with add_provider, and the new methods behave
exactly like Faker's built-in ones (same self.random_element / self.numerify helpers,
same seeding behavior).


This provider gives policy and claim numbers a real check-digit shape using the Luhn
algorithm — the same checksum credit card numbers use — computed by hand here since it's a
handful of lines of arithmetic, not a library call.


Example:


from faker import Faker
from faker.providers import BaseProvider

def luhn_check_digit(digits_str):
    digits = [int(d) for d in digits_str]
    total = 0
    for i, d in enumerate(reversed(digits)):
        if i % 2 == 0:
            d = d * 2
            if d > 9:
                d -= 9
        total += d
    return (10 - (total % 10)) % 10

class BFSIProvider(BaseProvider):
    _product_codes = ['AUT', 'HOM', 'LIF', 'PCM']

    def policy_number(self):
        product = self.random_element(self._product_codes)
        seq = self.numerify('#######')
        check = luhn_check_digit(seq)
        return f'POL-{product}-{seq}{check}'

    def claim_id(self, policy_year=None):
        year = policy_year or self.random_int(min=2019, max=2026)
        seq = self.numerify('########')
        check = luhn_check_digit(seq)
        return f'CLM-{year}-{seq}{check}'

Faker.seed(100)
f = Faker()
f.add_provider(BFSIProvider)
for _ in range(4):
    print(f.policy_number(), '|', f.claim_id())

Concept 4 — fake.unique and Its Exhaustion Failure


fake.unique.<method>() wraps any provider method so it retries until it gets a value it
hasn't returned before in this run, then remembers it. That's exactly what a primary key
column needs. It is not infinite, though: it tracks every value it has already handed out
for that method, and once the underlying value space is exhausted, it raises
UniquenessException rather than looping forever or silently returning a duplicate.


Example:


from faker import Faker
from faker.exceptions import UniquenessException

f = Faker()
Faker.seed(5)
seen = []
try:
    for i in range(5):
        seen.append(f.unique.random_int(min=1, max=3))
except UniquenessException as e:
    print('generated before failure:', seen)
    print('raised:', type(e).__name__, '-', e)

BFSI Reality Check — Day 2


Legacy angle: A real core banking export rarely has one IBAN format — a bank with
UK, German and Israeli operations has three different national account-number shapes in
the same "account_number" column, historically, because each entity onboarded onto the
core platform separately. A synthetic generator that only ever produces one locale's shape
is easier to build and a worse test fixture; it won't catch a parser that only handles
22-character IBANs when a real extract also has 34-character ones from another country.


Compliance angle: A policy or claim number with a real check-digit shape is not
decorative. Downstream validation code — a form that rejects a mistyped policy number
before it reaches a human — is part of the actual data-quality control chain a regulator
expects, and synthetic test data that skips the check digit means that validation code path
never gets exercised in dev or CI.


What breaks in production: A synthetic ID generator with no unique wrapper produces a
collision once in a while, silently, because the collision odds look tiny for any one
insert but a batch load of a million rows makes tiny odds routine. The failure surfaces
much later as a primary-key constraint violation deep in a load job, not at generation time
where the actual bug is.

Concept 1 — Fixed-Width Fields, Padded and Positional


A mainframe batch extract usually has no delimiters at all — no commas, no pipes. Every
field lives at a fixed byte offset, defined by a copybook the receiving system has to know
in advance. Text fields are padded with trailing spaces to reach their width; numeric
fields are padded with leading zeros. Get the offsets wrong and you don't get an error, you
get a value silently sliced from the wrong field.


Example:


from faker import Faker

Faker.seed(50)
f = Faker()

def fixed_width_record(customer_id, surname, amount_cents):
    return (
        customer_id.ljust(12)
        + surname.ljust(20)
        + str(amount_cents).rjust(10, '0')
    )

names = [f.last_name() for _ in range(3)]
for i, surname in enumerate(names):
    rec = fixed_width_record(f'CUST{i:08d}', surname, 12550 + i)
    print(repr(rec), len(rec))

Concept 2 — Uppercase-Only, Truncated Text Fields


Legacy mainframe text fields are frequently uppercase-only — a convention carried forward
from the EBCDIC era long after the hardware reason for it stopped mattering — and hard
-truncated at a fixed width with no warning and no ellipsis. A synthetic surname generator
that always produces short, cleanly-cased names never exercises the code path that handles
a truncated, all-caps MONTGOMERY where the real surname was Montgomery-Blake.


Example:


def legacy_surname(surname, width=10):
    return surname.upper()[:width]

surnames = ['Nightingale', 'Fitzgerald-Owusu', 'Li', "O'Sullivan"]
for s in surnames:
    print(f'{s!r:25} -> {legacy_surname(s)!r}')

Concept 3 — Julian Dates and All-9s Sentinels


Many COBOL copybooks store dates as YYYYDDD — a 4-digit year plus a zero-padded
day-of-year, not month/day — a compact format that predates the storage being cheap enough
to bother with a more readable one. Open dates (a claim with no close date yet) are commonly
represented with an all-9s sentinel value rather than a null, because the field's storage
format has no concept of null — it's a fixed-width numeric slot that must always hold
something.


Example:


import datetime
from faker import Faker

Faker.seed(70)
f = Faker()

def to_julian(d):
    return f'{d.year}{d.timetuple().tm_yday:03d}'

SENTINEL_OPEN_CLAIM = '9999999'

dates = [f.date_between(start_date=datetime.date(2023, 1, 1), end_date=datetime.date(2025, 12, 31)) for _ in range(3)]
for d in dates:
    print(d.isoformat(), '->', to_julian(d))
print('open claim close_date field:', SENTINEL_OPEN_CLAIM)

Concept 4 — Header and Trailer Records with a Control Count


A legacy batch extract is rarely just the detail rows. It's bracketed by a header record
(run date, record count) and a trailer record (the same count again, sometimes with a
checksum). The count exists so the receiving system can detect a truncated transfer without
opening the file's business content at all — if the trailer's count doesn't match the
number of detail rows actually present, something failed in transit and the whole file is
rejected before any row is loaded.


Example:


import datetime

def build_extract(detail_records, run_date):
    header = 'HDR' + run_date.strftime('%Y%m%d') + str(len(detail_records)).rjust(8, '0')
    trailer = 'TRL' + str(len(detail_records)).rjust(8, '0')

Concept 2 — Varying Seed Facts to Avoid Template Collapse


A template with fixed seed facts produces the same output every time — obviously useless as
a dataset of more than one row. The fix does not require an LLM at all: pull each seed fact
independently from a pool of plausible values, and the combinatorics alone produce enough
distinct narratives that a downstream model training or testing against them won't overfit
to one sentence shape.


Example:


import random

rng = random.Random(200)

PERILS = ['water damage', 'wind damage', 'fire', 'theft', 'vandalism']
ROOMS = ['kitchen', 'master bedroom', 'garage', 'basement', 'living room']
CAUSES = ['a burst supply pipe', 'a fallen tree limb', 'a faulty space heater',
          'a forced rear door', 'an unattended candle']

TEMPLATE = 'Insured reported {peril} in the {room}, caused by {cause}. Claimant was on-site at the time.'

def generate_narrative(seed_facts):
    return TEMPLATE.format(**seed_facts)

def fixed_facts_narrative():
    return generate_narrative({'peril': PERILS[0], 'room': ROOMS[0], 'cause': CAUSES[0]})

def varied_facts_narrative():
    return generate_narrative({
        'peril': rng.choice(PERILS),
        'room': rng.choice(ROOMS),
        'cause': rng.choice(CAUSES),
    })

fixed_batch = [fixed_facts_narrative() for _ in range(8)]
varied_batch = [varied_facts_narrative() for _ in range(8)]

print('fixed seed facts  -- distinct narratives:', len(set(fixed_batch)), '/', len(fixed_batch))
print('varied seed facts -- distinct narratives:', len(set(varied_batch)), '/', len(varied_batch))

Concept 3 — Near-Duplicate Detection with MinHash


Varying seed facts reduces exact duplicates but does not catch near-duplicates — two
narratives that differ by one word yet describe the same underlying content. Comparing
every pair of documents' exact word-shingle sets (Jaccard similarity) is the precise answer
but gets expensive at scale; MinHash approximates the same Jaccard similarity from a small
fixed-size signature per document, so comparing two documents costs comparing two short
vectors instead of two large sets. Built from scratch here with hashlib, no external
library needed for the size of corpus this week deals with.


Example:


import hashlib

def shingles(text, k=3):
    words = text.lower().split()
    return set(tuple(words[i:i+k]) for i in range(len(words) - k + 1))

def minhash_signature(shingle_set, num_hashes=64):
    sig = []
    for i in range(num_hashes):
        best = None
        for sh in shingle_set:
            h = int(hashlib.sha256((str(i) + '|' + ' '.join(sh)).encode()).hexdigest(), 16)
            if best is None or h < best:
                best = h
        sig.append(best)
    return sig

def signature_similarity(sig_a, sig_b):
    matches = sum(1 for a, b in zip(sig_a, sig_b) if a == b)
    return matches / len(sig_a)

texts = [
    'Insured reported water damage in the kitchen, caused by a burst supply pipe.',
    'Insured reported water damage in the kitchen caused by a burst supply pipe.',
    'Insured reported fire in the garage, caused by a faulty space heater.',
]
sigs = [minhash_signature(shingles(t), num_hashes=64) for t in texts]
for i in range(len(texts)):
    for j in range(i + 1, len(texts)):
        est = signature_similarity(sigs[i], sigs[j])
        print(f'({i},{j}) minhash-estimated jaccard={est:.3f}')

Concept 4 — Injecting Realistic Typos, Abbreviations and Jargon


Real free-text fields typed by claims adjusters and call-center agents under time pressure
are not clean prose — they're full of abbreviations (cust, bc, approx) and the
occasional transposed-letter typo. A downstream NLP pipeline (a parser, a classifier, an
LLM prompt template) that only ever sees grammatically clean synthetic text will not have
been exercised against the noise it will actually face in production.


Example:


import random

ABBREVIATIONS = {
    'because': 'bc', 'approximately': 'approx', 'customer': 'cust',
    'policy': 'pol', 'immediately': 'immed',
}

def inject_typo(word, rng):
    if len(word) < 4:
        return word
    i = rng.randrange(1, len(word) - 1)
    return word[:i] + word[i + 1] + word[i] + word[i + 2:]

def roughen_text(text, rng, typo_rate=0.15, abbrev_rate=0.5):
    words = text.split()
    out = []
    for w in words:
        bare = w.strip('.,').lower()
        if bare in ABBREVIATIONS and rng.random() < abbrev_rate:
            out.append(ABBREVIATIONS[bare] + w[len(bare):])
        elif rng.random() < typo_rate:
            out.append(inject_typo(w, rng))
        else:
            out.append(w)
    return ' '.join(out)

clean = 'The customer contacted us immediately because approximately half the roof was damaged, per policy terms.'
rough = roughen_text(clean, random.Random(300))
print('clean:', clean)
print('rough:', rough)

Concept 1 — Matching Marginal Statistics Against Real Aggregates Only


Data residency rules mean a synthetic-data team is often handed aggregate statistics from
a real portfolio — mean, median, a few percentiles — and never the underlying records
themselves. That's actually enough to calibrate a generator and check its fidelity, as long
as the check is honest about what it's comparing: the generator's own summary statistics
against the target summary statistics, never claiming to validate against individual real
records it was never allowed to see.


Example:


import numpy as np

rng = np.random.default_rng(400)

# Real aggregate targets a compliance team is allowed to hand over -- summary
# statistics only, never individual records. Illustrative published-style
# figures for a property-claims portfolio.
REAL_TARGETS = {'mean': 8500.0, 'median': 6200.0, 'p95': 32000.0}
FIDELITY_THRESHOLD = 0.15

def synthetic_claim_amounts(n, mu=8.6, sigma=1.0):
    return rng.lognormal(mean=mu, sigma=sigma, size=n)

def pct_error(synth, real):
    return abs(synth - real) / real

amounts = synthetic_claim_amounts(20_000)
synthetic_stats = {
    'mean': float(np.mean(amounts)),
    'median': float(np.median(amounts)),
    'p95': float(np.percentile(amounts, 95)),
}

for stat, target in REAL_TARGETS.items():
    synth_val = synthetic_stats[stat]
    err = pct_error(synth_val, target)
    status = 'PASS' if err < FIDELITY_THRESHOLD else 'FAIL'
    print(f'{stat:>7}: synthetic={synth_val:10.2f}  real target={target:10.2f}  pct_error={err:.3f}  {status}')

Concept 2 — Uniqueness Checks on Quasi-Identifier Combinations


Day 1 Concept 1 showed this technique on a customer-record shape; the same check belongs on
the claims dataset itself before it ships anywhere, because claims data carries its own
quasi-identifiers (location, claim type, loss year) that can combine into a re-identifying
fingerprint even with no name or account number in sight.


Example:


from faker import Faker
from collections import Counter

Faker.seed(500)
f = Faker()

n = 3000
claims = []
for _ in range(n):
    zipcode = f.zipcode()
    claims.append({
        'zip3': zipcode[:3],
        'claim_type': f.random_element(['auto', 'home', 'life', 'pcm']),
        'loss_year': f.random_int(min=2021, max=2026),
    })

def uniqueness_rate(records, keys):
    combos = Counter(tuple(r[k] for k in keys) for r in records)
    singleton = sum(1 for c in combos.values() if c == 1)
    return singleton / len(records)

rate = uniqueness_rate(claims, ['zip3', 'claim_type', 'loss_year'])
print(f'n={n}  unique-combo rate on (zip3, claim_type, loss_year): {rate:.3f}')

Concept 3 — An Automated Test That No Real PII Pattern Survives


Every generation step in this week was designed to avoid real PII by construction, but
"designed to" is not "verified to." The last line of defense is a pattern-based scanner run
over the finished dataset as an actual automated test, checking for the shapes real PII
takes (an SSN-formatted string, an email address, a handful of card-network BIN prefixes
that must never appear on a supposedly-synthetic PAN) regardless of how it got there —
whether from a copy-pasted example, a template that accidentally embedded a placeholder, or
a bug elsewhere in the pipeline.


Example:


import re

SSN_PATTERN = re.compile(r'\b\d{3}-\d{2}-\d{4}\b')
EMAIL_PATTERN = re.compile(r'\b[\w.+-]+@[\w-]+\.[\w.-]+\b')
# Illustrative reserved/well-known test BIN prefixes that must never appear on
# a synthetic PAN -- in a real check this list comes from the card networks'
# actual published test ranges, not invented digits.
FORBIDDEN_BIN_PREFIXES = ('400000', '424242')

def scan_for_pii_leaks(records):
    findings = []
    for i, rec in enumerate(records):
        text = ' '.join(str(v) for v in rec.values())
        if SSN_PATTERN.search(text):
            findings.append((i, 'ssn_pattern'))
        if EMAIL_PATTERN.search(text):
            findings.append((i, 'email_pattern'))
        for prefix in FORBIDDEN_BIN_PREFIXES:
            if any(str(v).startswith(prefix) for v in rec.values()):
                findings.append((i, f'forbidden_bin:{prefix}'))
    return findings

clean_batch = [
    {'pan': '4716202183220028', 'note': 'auto claim, no injury'},
    {'pan': '5432109876543210', 'note': 'home claim, water damage'},
]
dirty_batch = [
    {'pan': '4716202183220028', 'note': 'ssn on file 512-33-8890'},
    {'pan': '4242424242424242', 'note': 'clean note'},
]

print('clean batch findings:', scan_for_pii_leaks(clean_batch))
print('dirty batch findings:', scan_for_pii_leaks(dirty_batch))
assert scan_for_pii_leaks(clean_batch) == []
print('assertion passed: clean batch has zero PII-pattern findings')

Concept 4 — Documenting the Fidelity Gaps You Knowingly Accept


No synthetic generator matches every real correlation, and pretending otherwise is worse
than admitting it plainly. A short, structured "known gaps" report shipped alongside the
generator — what correlations it doesn't model, what patterns it can't produce — turns an
implicit limitation into something a downstream consumer can actually plan around, instead
of discovering the gap the hard way when a model trained on the synthetic data fails to
generalize to real seasonal or geographic patterns.


Example:


def fidelity_gap_report(known_gaps):
    for g in known_gaps:
        if 'field' not in g or 'gap' not in g:
            raise ValueError(f'incomplete gap entry, missing field/gap key: {g}')
    return {'known_gaps': known_gaps, 'gap_count': len(known_gaps)}

gaps = [
    {'field': 'claim_amount x geography', 'gap': 'no correlation modeled; real coastal ZIPs see higher wind-peril severity, synthetic data does not'},
    {'field': 'claim_amount x season', 'gap': 'no seasonality modeled; real Q1 sees more freeze-related water claims'},
    {'field': 'fraud_flag', 'gap': 'not modeled at all; synthetic data has no adversarial fraud patterns to detect against'},
]
report = fidelity_gap_report(gaps)
print(report)

BFSI Reality Check — Day 5


Legacy angle: The "real aggregate statistics" a synthetic-data team gets handed often
come from a report a data-warehouse team runs by hand once a quarter off the legacy
platform, not a live query — so the fidelity target itself can be months stale, and a
generator calibrated against it is calibrated against a snapshot, not the current
portfolio.


Compliance angle: A fidelity check and a re-identification check answer two different
questions, and a real review needs both answered, not one standing in for the other: "does
this synthetic data look statistically realistic" (Concept 1) is not the same claim as
"can this synthetic data be reverse-engineered to a real individual" (Concept 2) — the
second question is the one a privacy impact assessment actually asks, and passing the
first says nothing about the second.


What breaks in production: A model trained entirely on synthetic data quietly encodes
that data's own fidelity gaps as if they were true facts about the real world — a fraud
classifier trained on synthetic data with no fraud patterns modeled (Concept 4's third gap)
learns nothing useful about fraud at all, and the failure is invisible until it's deployed
against real fraud it was never shown anything resembling.




Architecture Decision — Week 10


Choosing between: Faker-only structured generation vs. LLM-assisted free-text
generation vs. using a masked copy of real production data.


Rule of thumb: use Faker (plus a custom BaseProvider for domain-specific fields) for
every structured column — it's fast, free, fully reproducible under a seed, and there is
categorically no real individual behind any value it produces. Reach for an LLM only for
the free-text layer templates can't cover — narrative variety and register that a
finite template set collapses into repetition on (Day 4) — and always pair it with
near-duplicate detection, since an LLM given the same constrained prompt repeatedly will
itself collapse toward similar phrasing without an explicit diversity check. Never reach
for a masked copy of real production data as the default path: masking reduces what's
displayed, not what's in scope (Day 1), and the one property a masked-prod-copy has that
synthetic data doesn't — genuine correlational realism — has to be earned back
deliberately by calibrating the generator against real aggregate statistics (Day 5,
Concept 1) and admitting in writing what correlations it still doesn't capture (Day 5,
Concept 4). A masked production copy is the right call only when a specific validated
fidelity requirement cannot be met any other way, and even then it stays subject to every
data-residency and access control that applied to the original data, because scope
reduction never actually happened.
