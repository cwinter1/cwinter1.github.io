Concept 1 — A Wide Net, Then a Narrow One

A single-stage retriever has to pick one operating point: retrieve few candidates and risk missing the answer, or retrieve many and hand the generator a pile of mostly-irrelevant context. Two-stage retrieval refuses that trade-off by splitting it across two models with different jobs. Stage one is recall-oriented: cheap enough to run over the WHOLE corpus, tuned to cast a wide net at top_n (typically 50-100 candidates in production, a smaller top_n here to fit this week's small demo corpus), accepting noise in exchange for rarely missing the true answer. Stage two is precision-oriented: expensive per item, so it only ever runs over stage one's short candidate list, and its job is to find the single best answer inside that list and put it at rank 1, at a narrow top_k of 3-5. Week 24's retrieve() — a bag-of-words cosine retriever standing in for a real embedding index, the same stand-in pattern that week used throughout — is reused here unchanged as the first stage; the second stage below is new to this week.

    ("DOC-10", "Fire and smoke damage: direct fire damage and resulting smoke damage to the dwelling and personal property are covered under the base property policy with no separate sublimit."),
]

def bow(text):
    toks = tokenize(text)
    return {t: toks.count(t) for t in toks if t in VOCAB}

def cosine(v1, v2):
    common = set(v1) & set(v2)
    dot = sum(v1[t] * v2[t] for t in common)
    n1 = math.sqrt(sum(x * x for x in v1.values())) or 1.0
    n2 = math.sqrt(sum(x * x for x in v2.values())) or 1.0
    return dot / (n1 * n2)

def retrieve(query_text, k=3, corpus=CORPUS):
    qv = bow(query_text)
    scored = [(doc_id, cosine(qv, bow(text))) for doc_id, text in corpus]
    scored.sort(key=lambda x: -x[1])
    return scored[:k]

def first_stage(query_text, top_n=6, corpus=CORPUS):
    return retrieve(query_text, k=top_n, corpus=corpus)

# The second stage is a JOINT scorer -- it looks at the query and the candidate document
# TOGETHER (unigram overlap plus bigram/exact-phrase overlap), something a bag-of-words
# cosine similarity (which scores query and document independently) cannot see.
doc_lookup = {doc_id: text for doc_id, text in CORPUS}

def cross_encode(query_text, doc_text):
    q_toks = tokenize(query_text)
    d_toks = tokenize(doc_text)
    q_bigrams = set(zip(q_toks, q_toks[1:]))
    d_bigrams = set(zip(d_toks, d_toks[1:]))
    unigram_overlap = len(set(q_toks) & set(d_toks))
    bigram_overlap = len(q_bigrams & d_bigrams)
    return unigram_overlap + 3 * bigram_overlap

def second_stage(query_text, candidate_ids, top_k=3):
    scored = [(cid, cross_encode(query_text, doc_lookup[cid])) for cid in candidate_ids]
    scored.sort(key=lambda x: -x[1])
    return scored[:top_k]

query = "water came up through the drain into my basement do I have coverage"
narrow = [d for d, _ in first_stage(query, top_n=3)]
wide = [d for d, _ in first_stage(query, top_n=8)]
print("first-stage top_n=3:", narrow)
print("first-stage top_n=8:", wide)
final = second_stage(query, wide, top_k=3)
print("second-stage top_k=3 reranked from the top_n=8 pool:", [d for d, _ in final])

Concept 2 — Bi-Encoder vs. Cross-Encoder Scoring Mechanics


The reason two stages exist, in one sentence: a bi-encoder encodes the query and each
document INDEPENDENTLY into fixed vectors, so every document's vector can be computed once,
cached, and reused across every future query — that caching is exactly what makes an ANN
index over millions of documents feasible. A cross-encoder encodes the query and a document
TOGETHER as one joint input, which lets it model interactions a bi-encoder's independent
vectors structurally cannot (this concept's Example already showed one: bigram/phrase
overlap between the query and the document) — but the joint encoding can never be
precomputed or cached, because it depends on both the specific query and the specific
document together. Score N documents against M different queries and a bi-encoder does
N encode calls total (each document once, ever); a cross-encoder does N x M calls,
because every new query needs its own pass over every candidate.


Example:


# Reusing CORPUS, bow, cross_encode from Concept 1

doc_vector_cache = {}
bienc_doc_encode_calls = 0

def bienc_encode_doc(doc_id, text):
    global bienc_doc_encode_calls
    if doc_id not in doc_vector_cache:
        doc_vector_cache[doc_id] = bow(text)
        bienc_doc_encode_calls += 1
    return doc_vector_cache[doc_id]

queries = [
    "does my plan pay to fix a wind damaged roof",
    "water came up through the drain into my basement do I have coverage",
    "can I still get money back",
]

for q in queries:
    for doc_id, text in CORPUS:
        bienc_encode_doc(doc_id, text)
print(f"bi-encoder doc-encode calls across {len(queries)} queries over {len(CORPUS)} docs: {bienc_doc_encode_calls}")

crossenc_pair_calls = 0
for q in queries:
    for doc_id, text in CORPUS:
        cross_encode(q, text)
        crossenc_pair_calls += 1
print(f"cross-encoder pair-scoring calls for the same workload: {crossenc_pair_calls}")
print(f"cross-encoder does {crossenc_pair_calls // bienc_doc_encode_calls}x the encode work of the bi-encoder here")

Every document is encoded exactly once by the bi-encoder regardless of how many queries
come in — the cache absorbs all repeat lookups, which is why a bi-encoder index scales to
millions of documents and constant-time-ish query latency. The cross-encoder pays for every
single query-document pair, with zero possible caching, because there is no such thing as
"the vector for DOC-6" under a cross-encoder — only "the joint score of DOC-6 against
THIS query." That asymmetry is why the cross-encoder only ever runs over a short candidate
list, never the whole corpus.

Concept 3 — Where the Extra Recall Actually Comes From


It is tempting to credit the reranker with "finding" documents the first stage missed, but
a reranker can only rerank what is already IN its candidate list — it cannot retrieve a
document the first stage never surfaced. All of the recall gain in a two-stage system comes
from widening top_n in the first stage; all of the precision gain comes from the
reranker's ability to put the single right answer at rank 1 once it is in that list. Proving
this means measuring recall@top_n (does the relevant document appear ANYWHERE in the
first top_n results) as top_n widens, independent of reranking entirely.


Example:


# Reusing first_stage, CORPUS from Concept 1

labeled_queries = [
    ("water came up through the drain into my basement do I have coverage", "DOC-6"),
    ("does my plan pay to fix a wind damaged roof", "DOC-7"),
    ("is mold from a leaky pipe covered", "DOC-8"),
    ("what extra liability protection is above my home and auto limits", "DOC-9"),

def recall_at_n(query_text, relevant_id, top_n):
    ids = [d for d, _ in first_stage(query_text, top_n=top_n)]
    return 1.0 if relevant_id in ids else 0.0

for top_n in (1, 3, 5, 8, 13):

    print(f"top_n={top_n:>2}  recall={sum(scores)/len(scores):.3f}  hits={scores}")

Concept 4 — End-to-End Latency Budget Allocation


The two stages have very different cost shapes per candidate. A first-stage ANN lookup over
a whole vector index costs roughly the same regardless of how many results you ask it to
return (top_n=10 and top_n=100 are both a single index query) — its cost is dominated by
embedding the query itself, not by top_n. The reranker's cost, by contrast, scales
LINEARLY with top_n, because Concept 2 already showed it must score every single
candidate individually with no caching. A latency budget has to account for both shapes, not
just eyeball a top_n number that "sounds reasonable."


Example:


def latency_budget(ann_lookup_ms, per_pair_rerank_ms, top_n, embed_query_ms=8.0):
    first_stage_ms = embed_query_ms + ann_lookup_ms
    second_stage_ms = per_pair_rerank_ms * top_n
    total_ms = first_stage_ms + second_stage_ms
    return {
        "first_stage_ms": round(first_stage_ms, 2),
        "second_stage_ms": round(second_stage_ms, 2),
        "total_ms": round(total_ms, 2),
        "second_stage_share": round(second_stage_ms / total_ms, 3),
    }

budget_target_ms = 300.0
for top_n in (10, 25, 50, 100):
    b = latency_budget(ann_lookup_ms=15.0, per_pair_rerank_ms=4.0, top_n=top_n)
    fits = b["total_ms"] <= budget_target_ms
    print(f"top_n={top_n:>3}  first_stage={b['first_stage_ms']:>6}ms  "
          f"second_stage={b['second_stage_ms']:>6}ms  total={b['total_ms']:>7}ms  "
          f"second_stage_share={b['second_stage_share']:.1%}  fits_{budget_target_ms:.0f}ms_budget={fits}")

BFSI Reality Check — Day 1


Legacy angle: a claims or underwriting knowledge base built up over a decade of policy
revisions is exactly the shape a first-stage retriever is weakest against — near-duplicate
clauses across policy versions, superseded riders never removed from the index — so top_n
needs to be wide enough to survive that noise, not just wide enough for a clean demo corpus.


Compliance angle: the reranker's score is the last thing that decided what context the
generator saw before answering a policyholder or adjuster — an audit trail that logs only
the final answer, with no record of the first-stage candidate list or the reranker's scores
over it, cannot explain why a specific clause was surfaced instead of a nearly-identical one
one policy version earlier.


What breaks in production: a top_n tuned once against today's corpus size silently
stops being "wide enough" as the corpus grows — Concept 3's recall@top_n curve is a
snapshot of ONE corpus at ONE point in time, and the same methodology (not the same number)
needs to be re-run whenever the underlying document set changes meaningfully, the same
warning Week 24's own bake-off closed on.

Example:


class MiniCrossEncoder:
    """Stand-in for sentence_transformers.CrossEncoder -- same predict(pairs,
    batch_size=...) contract, hand-rolled because the real checkpoint download is
    blocked in this sandbox (httpx.ProxyError: 403 against huggingface.co, confirmed
    directly). Demonstrates the real batching and truncation MECHANICS, not the real
    model's relevance judgments."""

    def __init__(self, max_length=512):
        self.max_length = max_length
        self.truncated_count = 0

    def _score_pair(self, query, doc):
        q_toks = query.lower().split()
        d_toks = doc.lower().split()
        if len(d_toks) > self.max_length:
            d_toks = d_toks[:self.max_length]
            self.truncated_count += 1
        overlap = len(set(q_toks) & set(d_toks))
        return overlap / (len(set(q_toks)) or 1)

    def predict(self, pairs, batch_size=8, show_progress_bar=False):
        scores = []
        batch_count = 0
        for start in range(0, len(pairs), batch_size):
            batch = pairs[start:start + batch_size]
            batch_count += 1
            scores.extend(self._score_pair(q, d) for q, d in batch)
        return scores, batch_count

model = MiniCrossEncoder(max_length=512)

]

Concept 2 — 512-Token Truncation Effects on Long Policy Chunks


A real cross-encoder has a hard input-length ceiling (512 tokens is bge-reranker-v2-m3's
default) — anything past that is silently dropped before scoring, not summarized or
compressed. A short policy clause is unaffected, but a long policy chunk (a multi-page
coverage section pasted in whole, rather than pre-split) can lose exactly the sentence that
actually answers the question if that sentence happens to sit past the cutoff — a common
shape for a policy document that opens with boilerplate definitions before reaching the
specific coverage language a claim actually turns on.

Concept 3 — CPU Throughput and the batch_size Knob


This sandbox has no GPU, so only CPU throughput can be measured directly here; a real GPU
deployment of bge-reranker-v2-m3 is documented (not measured in this sandbox) to reach
roughly one to two orders of magnitude higher pairs-per-second than the same model on CPU,
which is the actual production argument for a GPU box once query volume grows past what a
CPU reranker can absorb inside its latency budget. What genuinely runs here: batch_size
controls the NUMBER of batching-overhead calls for a fixed pair count, real and measured,
independent of whichever device does the actual math inside each batch. Wall-clock
milliseconds are not compared exactly below (they vary run to run, per known-issues.md item

Concept 4 — The On-Prem Argument When Claim Text Cannot Leave the Bank


A hosted reranking API (Day 3) sends the query and every candidate document's full text
across the network to a third party on every single request — for a claims adjuster's note
containing a policyholder's name, address, and injury description, or a commercial loan
file with covenant terms, that is a data-egress decision a BFSI compliance program has to
approve BEFORE the first production call, not discover after the fact in a vendor audit. A
self-hosted reranker (this day's whole subject) never sends document text anywhere outside
infrastructure the bank already controls — the cost is operational (hosting the model,
maintaining the GPU or CPU capacity, keeping the checkpoint current), not a data-residency
review. Which one is correct is a real, checkable decision, not a vibe.


Example:

Legacy angle: a self-hosted reranker still needs somewhere to run, and a bank's

methodology and exactly why it has to be run per document-length bucket, not just overall.

Concept 1 — The Cohere Rerank Endpoint's Real Call Shape


Cohere's Rerank endpoint takes a query, a flat list of documents, and a top_n, and
returns a ranked list of (index, relevance_score) pairs referencing positions in the
original documents list — the caller does the actual work of mapping indices back to
document IDs. cohere is not installed in this sandbox and no API key is configured, so
the real call below is shown as reference syntax only, in a plain (non-executable) fence,
never claimed as run:


import cohere
co = cohere.ClientV2(api_key="...")
response = co.rerank(
    model="rerank-english-v3.0",
    query=query,
    documents=documents,   # list[str]
    top_n=top_n,
)
for result in response.results:
    print(result.index, result.relevance_score)

What is built and run for real below is a local mock client that returns objects matching
that same response shape (.results, each with .index and .relevance_score) — the
response-parsing code a production integration actually depends on gets genuinely
exercised, even though the relevance judgments themselves are a deterministic
lexical-overlap stand-in, not the live endpoint's own scoring.


Example:


from dataclasses import dataclass

@dataclass
class RerankResult:
    index: int
    relevance_score: float

class MockCohereClient:
    """Matches cohere.ClientV2().rerank()'s real response shape -- deterministic
    lexical-overlap scoring stands in for the live model's judgment."""
    def rerank(self, model, query, documents, top_n):
        q_toks = set(query.lower().split())
        scored = []
        for i, doc in enumerate(documents):
            d_toks = set(doc.lower().split())
            overlap = len(q_toks & d_toks)
            scored.append((i, overlap / (len(q_toks) or 1)))
        scored.sort(key=lambda x: -x[1])
        results = [RerankResult(index=i, relevance_score=round(s, 4)) for i, s in scored[:top_n]]
        return type("RerankResponse", (), {"results": results})()

co = MockCohereClient()
documents = [
    "Wind and hail roof damage: shingle damage from a wind or hail storm is covered under the standard property policy.",
    "Grace period for premium payment: coverage stays active for 31 days past the due date before the policy lapses.",

]

A hosted rerank endpoint truncates each document to a fixed maximum length before scoring
it — a real, documented limit, not a suggestion — and a long commercial loan file (a full
credit agreement pasted in as one chunk, boilerplate definitions first) can lose the exact
covenant clause a question turns on if that clause sits past the cutoff, the same failure
shape Day 2 Concept 2 already measured for a self-hosted cross-encoder's max_length.

def truncate_for_rerank(doc_text, max_tokens):
    toks = doc_text.split()
    truncated = len(toks) > max_tokens

def lexical_relevance(query, doc_text):
    q_toks = set(query.lower().split())
    d_toks = set(doc_text.lower().split())
    return round(len(q_toks & d_toks) / (len(q_toks) or 1), 3)

Concept 4 — Circuit Breaker: Degrading to First-Stage-Only on Timeout


A hosted reranker is one more network hop that can be slow or down, and a claims or
servicing chat cannot simply hang or error out because a third-party rerank call timed
out — it should degrade gracefully to the first stage's own ranking, which is worse but
still usable, rather than fail the whole request. A circuit breaker tracks consecutive
failures, trips OPEN once a threshold is hit (skip the reranker entirely, return
first-stage results, fail fast instead of waiting out every future timeout), and probes
HALF_OPEN after a cooldown to check whether the reranker has recovered.


Example:


class RerankerCircuitBreaker:
    def __init__(self, failure_threshold=3, cooldown_calls=2):
        self.failure_threshold = failure_threshold
        self.cooldown_calls = cooldown_calls
        self.state = "CLOSED"
        self.consecutive_failures = 0
        self.calls_since_open = 0

    def call(self, rerank_fn, first_stage_ids, timeout_ok):
        if self.state == "OPEN":
            self.calls_since_open += 1
            if self.calls_since_open >= self.cooldown_calls:
                self.state = "HALF_OPEN"
            else:
                return first_stage_ids, "degraded_first_stage_only", self.state

        if not timeout_ok:
            self.consecutive_failures += 1
            if self.state == "HALF_OPEN":
                self.state = "OPEN"
                self.calls_since_open = 0
            elif self.consecutive_failures >= self.failure_threshold:
                self.state = "OPEN"
                self.calls_since_open = 0
            return first_stage_ids, "degraded_first_stage_only", self.state

        self.consecutive_failures = 0
        if self.state == "HALF_OPEN":
            self.state = "CLOSED"
        result = rerank_fn(first_stage_ids)
        return result, "reranked", self.state


def fake_rerank(ids):
    return list(reversed(ids))

breaker = RerankerCircuitBreaker(failure_threshold=3, cooldown_calls=2)
call_outcomes = [True, True, False, False, False, False, False, True, True, True]
for i, ok in enumerate(call_outcomes, start=1):
    ids, mode, state = breaker.call(fake_rerank, ["a", "b", "c"], timeout_ok=ok)
    print(f"call {i:>2} timeout_ok={ok!s:<5} state_after={state:<10} mode={mode:<24} result={ids}")

Concept 1 — p50/p95/p99 Latency With and Without the Reranker


An average latency number hides the shape that actually matters for a user-facing SLA: a
reranker adds a fixed-ish cost to the common case (p50) but a much larger, disproportionate
cost to the tail (p95/p99), because a handful of requests always hit slow paths (a cold
cache, a larger candidate batch, a retry). Percentiles need to be computed correctly, not
approximated by eye — the standard linear-interpolation method between the two nearest
ranks is used below.


Example:


def percentile(sorted_values, p):
    if not sorted_values:
        return 0.0
    k = (len(sorted_values) - 1) * (p / 100.0)
    f = int(k)
    c = min(f + 1, len(sorted_values) - 1)
    if f == c:
        return sorted_values[f]
    return sorted_values[f] + (sorted_values[c] - sorted_values[f]) * (k - f)

Concept 2 — Cost Per 1k Queries: Hosted vs. Self-Hosted GPU-Hours


A hosted reranker charges per query (a fixed marginal cost, no matter the volume); a
self-hosted GPU reranker has a largely FIXED monthly cost (the box, on whether or not it is
busy) that gets cheaper per query the more volume you push through it. The two cost curves
cross at some break-even query volume, and which side of that crossing a given workload
falls on is a real, computable answer — not a rule of thumb about which is "obviously"
cheaper.

Concept 3 — Caching Scores Keyed on (query_hash, doc_id) With TTL


A rerank score for a given query-document pair does not change between two requests that
ask the exact same question against the exact same candidate list within a short window —
caching that score avoids paying for the reranker twice. The cache key has to be the PAIR,
not just the query (two different candidate documents for the same query need different
cached scores), and needs a TTL — an unbounded cache would serve a stale score forever even
after the underlying document changed.


Example:


import hashlib

class RerankScoreCache:
    def __init__(self, ttl_calls=3):
        self.ttl_calls = ttl_calls
        self.store = {}  # (query_hash, doc_id) -> (score, expires_at_call)
        self.call_counter = 0
        self.hits = 0
        self.misses = 0

    def _key(self, query, doc_id):
        query_hash = hashlib.sha256(query.encode()).hexdigest()[:12]
        return (query_hash, doc_id)

    def get_or_compute(self, query, doc_id, compute_fn):
        self.call_counter += 1
        key = self._key(query, doc_id)
        cached = self.store.get(key)
        if cached is not None and cached[1] > self.call_counter:
            self.hits += 1
            return cached[0], True
        self.misses += 1
        score = compute_fn(query, doc_id)
        self.store[key] = (score, self.call_counter + self.ttl_calls)
        return score, False

cache = RerankScoreCache(ttl_calls=3)

def fake_score(query, doc_id):
    return round(len(query) / (len(doc_id) + 1), 3)

Concept 4 — When Reranking Does Not Earn Its Cost


Every concept so far assumed reranking was worth running at all. Two shapes of request
make that assumption false: a single-candidate result (there is nothing to reorder — the
first stage already returned exactly one document, correct or not), and an exact-ID lookup
(the query itself IS a policy/claim/loan number, not a natural-language question a
cross-encoder's semantic scoring adds any value to). Both cases should skip the reranker
entirely — every millisecond and dollar spent reranking them is pure waste.


Example:


import re

    return True, f"{len(candidate_ids)} candidates need ranking"

Concept 1 — nDCG@10 and MRR Before and After Reranking


recall@k (used throughout Week 24 and Day 1-3 of this week) only asks whether the
relevant document is SOMEWHERE in the top k — it cannot tell a ranking with the right
answer at rank 1 apart from one with it buried at rank 8. Normalized Discounted Cumulative
Gain (nDCG@10) and Mean Reciprocal Rank (MRR) both reward rank position directly: MRR
is 1/rank of the first relevant hit, and nDCG discounts a relevant document's
contribution logarithmically the further down the ranking it sits, normalized against the
best possible ordering. Both are computed below over graded (not binary) relevance grades —
Concept 2 explains why the grading matters — reusing Day 1's first_stage/second_stage
as the before/after ranking pair.


Example:


import math
# Reusing first_stage, second_stage, CORPUS, doc_lookup from Day 1

def dcg_at_k(ranked_ids, relevance_grades, k=10):
    total = 0.0
    for i, doc_id in enumerate(ranked_ids[:k], start=1):
        rel = relevance_grades.get(doc_id, 0)
        if rel > 0:
            total += (2 ** rel - 1) / math.log2(i + 1)
    return total

def ndcg_at_k(ranked_ids, relevance_grades, k=10):
    dcg = dcg_at_k(ranked_ids, relevance_grades, k)
    ideal_order = sorted(relevance_grades.items(), key=lambda x: -x[1])
    ideal_ids = [d for d, r in ideal_order if r > 0]
    idcg = dcg_at_k(ideal_ids, relevance_grades, k)
    return round(dcg / idcg, 4) if idcg > 0 else 0.0

def mrr(ranked_ids, relevance_grades):
    for i, doc_id in enumerate(ranked_ids, start=1):
        if relevance_grades.get(doc_id, 0) > 0:
            return round(1.0 / i, 4)
    return 0.0

# graded relevance: 0=irrelevant, 1=tangential, 2=relevant, 3=exact answer
labeled = [
    {"query": "water came up through the drain into my basement do I have coverage",
     "grades": {"DOC-6": 3, "DOC-9": 1}},
    {"query": "does my plan pay to fix a wind damaged roof",
     "grades": {"DOC-7": 3, "DOC-10": 1}},
    {"query": "is mold from a leaky pipe covered",
     "grades": {"DOC-8": 3, "DOC-6": 1}},
]

for item in labeled:

    ndcg_after = ndcg_at_k(reranked_ids, grades, k=10)
    mrr_before = mrr(first_ids, grades)
    mrr_after = mrr(reranked_ids, grades)
    print(f"{q[:40]:<42} nDCG@10 {ndcg_before:.3f}->{ndcg_after:.3f}  MRR {mrr_before:.3f}->{mrr_after:.3f}")

Concept 2 — Graded Relevance on a 0-3 Scale, Not Binary


Binary relevance (a document is either relevant or it isn't) throws away information a
reranker's whole job depends on: whether the top result is the EXACT clause that answers
the question, or merely a related one that mentions the same topic without actually
answering it. A 0-3 graded scale (0=irrelevant, 1=tangentially related, 2=relevant but not
the best answer, 3=the exact answer) lets nDCG distinguish two rankings that binary
recall@1 would score identically.


Example:

Concept 3 — Per-Query-Type Regression Detection


A single averaged metric across an entire labeled set can hide a real regression that only
hits one query shape — a reranker change that improves easy queries while quietly breaking
phrase-sensitive ones can still show a flat or even improved OVERALL average. Breaking the
labeled set down by query type and comparing a candidate reranker against a baseline PER
TYPE catches what an aggregate number would miss.


Example:


# Reusing tokenize from Day 1, ndcg_at_k from Concept 1

def cross_encode_v1(query_text, doc_text):
    q_toks = tokenize(query_text)
    d_toks = tokenize(doc_text)
    q_bigrams = set(zip(q_toks, q_toks[1:]))
    d_bigrams = set(zip(d_toks, d_toks[1:]))
    unigram_overlap = len(set(q_toks) & set(d_toks))
    bigram_overlap = len(q_bigrams & d_bigrams)
    return unigram_overlap + 3 * bigram_overlap

def cross_encode_v2_unigram_only(query_text, doc_text):
    q_toks = tokenize(query_text)
    d_toks = tokenize(doc_text)
    return len(set(q_toks) & set(d_toks))

def rerank_with(score_fn, query_text, candidate_ids, doc_lookup_local):
    scored = [(cid, score_fn(query_text, doc_lookup_local[cid])) for cid in candidate_ids]
    scored.sort(key=lambda x: -x[1])
    return [c for c, _ in scored]

def detect_regressions(baseline, candidate, threshold=0.02):
    regressions = []
    for qtype, base_score in baseline.items():
        new_score = candidate.get(qtype, 0.0)
        if new_score < base_score - threshold:

    return regressions

Concept 4 — Freezing the Winning Reranker and top_n as a Versioned Config Artifact


A bake-off's result is only useful in production if the WINNING configuration — which
reranker, what top_n/top_k, and the measured numbers that justified picking it — is
captured as a concrete, versioned artifact a deployment can reference, not left as a
conclusion in a markdown file someone has to remember to re-read. Freezing it as a
serializable config object makes the decision auditable and gives a future regression check
(re-running this same harness) something exact to compare against.


Example:


import json
from dataclasses import dataclass, asdict

@dataclass(frozen=True)
class RerankerConfig:
    config_version: str
    reranker_name: str
    top_n: int
    top_k: int
    mean_ndcg_at_10: float
    mean_mrr: float
    frozen_reason: str

def freeze_winning_config(candidates_evaluated, chosen_name, top_n, top_k, mean_ndcg, mean_mrr):
    version = f"rerank-cfg-{len(candidates_evaluated):02d}"
    reason = f"beat {len(candidates_evaluated) - 1} other candidate(s) on mean nDCG@10 across the full labeled set"
    return RerankerConfig(
        config_version=version,
        reranker_name=chosen_name,
        top_n=top_n,
        top_k=top_k,
        mean_ndcg_at_10=mean_ndcg,
        mean_mrr=mean_mrr,
        frozen_reason=reason,
    )

candidates_evaluated = ["cross_encode_v1", "cross_encode_v2_unigram_only", "no_reranker_baseline"]
winning_config = freeze_winning_config(candidates_evaluated, "cross_encode_v1", top_n=50, top_k=5, mean_ndcg=0.972, mean_mrr=0.944)
config_json = json.dumps(asdict(winning_config), indent=2, sort_keys=True)
print(config_json)

reloaded = RerankerConfig(**json.loads(config_json))
print("round-trips cleanly:", reloaded == winning_config)

BFSI Reality Check — Day 5


Legacy angle: a labeled set built once against today's policy corpus goes stale the
moment new products or clause language ship — the same warning Day 1 and Week 24 both
closed on, restated here as a concrete operational requirement: the regression harness
needs a re-labeling cadence tied to corpus/product changes, not a one-time build.


Compliance angle: the frozen config artifact (Concept 4) IS the audit trail for "why
this reranker, why this top_n" that a model-risk-management review will eventually ask
for — capturing it as a real artifact at decision time is far cheaper than reconstructing
the reasoning from memory or old chat logs during an audit months later.


What breaks in production: a regression check run once at deployment time and never
again is a false sense of safety — the whole point of Concept 3's methodology is that it
has to re-run on every reranker or prompt/model change, the same way a unit test suite
protects against a code regression, not as a one-time acceptance gate that is satisfied and
forgotten.




Architecture Decision — Week 25


Choosing between: no reranking, first-stage-only (skip this week's whole subject, trust
the bi-encoder retriever's own ranking) vs. self-hosted cross-encoder reranking
(bge-reranker-v2-m3 through CrossEncoder, Day 2) vs. hosted reranking via Cohere
(Day 3, with the circuit breaker built to degrade safely).


Rule of thumb: default to no reranking for exact-ID lookups and single-candidate
results — Day 4 Concept 4 already proved these cases pay full reranking cost for zero
benefit, and that check should run BEFORE any reranker call, not after. For everything
else, default to self-hosted the moment claim notes, loan files, or any other
customer-identifying text would otherwise leave the bank's own infrastructure on every
single request (Day 2 Concept 4's data-residency argument) — that constraint is a hard
compliance blocker, not a cost tradeoff to be weighed against convenience. Move to
hosted only when no such constraint applies AND in-house GPU capacity genuinely is not
available (Day 2 Concept 4's has_gpu_capacity branch) or query volume sits below Day 4
Concept 2's measured break-even point (roughly 100k-1M monthly queries in this week's
illustrative pricing, real numbers to be re-measured against actual vendor rates before
being trusted) — below that volume, hosted's per-query pricing beats an always-on GPU box's
fixed cost.


The actual failure case for the chosen default (self-hosted-when-data-residency-requires-
it, hosted-otherwise) is Day 5's own: neither choice is validated by picking the "obviously
right" option once and trusting it forever. bge-reranker-v2-m3 truncates at 512 tokens
silently (Day 2 Concept 2); a stripped-down reranker regresses specifically on
phrase-sensitive queries while a flat average metric hides it entirely (Day 5 Concept 3); a
circuit breaker tuned against the wrong latency assumption trips on ordinary variance (Day
3's own closing warning). Day 5's regression harness — a labeled set with graded relevance,
nDCG@10/MRR computed per query type, re-run on every reranker or config change, with the
winning configuration frozen as a versioned artifact rather than trusted from memory — is
the actual deliverable this week builds toward, not any single reranker choice. Whichever
reranker a given deployment picks, it is only a safe default for as long as that harness
keeps confirming it, not because it was the right answer once.
