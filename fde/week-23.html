Concept 1 — Cost Per Claim Processed, Not Cost Per Thousand Tokens

A dashboard that reports "$0.004 per 1,000 tokens" tells a BFSI operations lead nothing they can act on — nobody budgets a claims department in tokens. The number that actually matters is the fully-loaded cost of processing ONE claim end to end, across every LLM call that claim's run made, at whatever model tier each call used. Reporting cost-per-1k-tokens alongside cost-per-claim can even be actively misleading: an escalated claim that made two calls (a cheap triage pass, then an expensive full-agent pass) can show a SMALLER cost-per-1k-tokens figure than a simple one-call claim, purely because its later call had a larger token count to average against — even though its total dollar cost per claim is far higher.

Example:

import dataclasses

@dataclasses.dataclass
class ModelPricing:
    name: str
    input_per_1k: float
    output_per_1k: float

PRICING = {
    "claims-triage-mini": ModelPricing("claims-triage-mini", 0.00025, 0.00125),
    "claims-agent-v3.2": ModelPricing("claims-agent-v3.2", 0.003, 0.015),
}

def call_cost_usd(model_name, input_tokens, output_tokens):
    p = PRICING[model_name]
    return (input_tokens / 1000) * p.input_per_1k + (output_tokens / 1000) * p.output_per_1k

@dataclasses.dataclass
class ClaimRun:
    claim_id: str
    calls: list  # list of (model_name, input_tokens, output_tokens)

def cost_per_claim(run):
    return sum(call_cost_usd(m, i, o) for m, i, o in run.calls)

def cost_per_1k_tokens_view(run):
    total_tokens = sum(i + o for _, i, o in run.calls)
    total_cost = cost_per_claim(run)
    if total_tokens == 0:
        return 0.0
    return (total_cost / total_tokens) * 1000

simple_claim = ClaimRun("CLM-88213", calls=[("claims-triage-mini", 800, 120)])
escalated_claim = ClaimRun("CLM-88214", calls=[
    ("claims-triage-mini", 800, 60),
    ("claims-agent-v3.2", 4200, 900),
])

for run in [simple_claim, escalated_claim]:
    print(f"{run.claim_id}: cost_per_claim=${cost_per_claim(run):.4f}  cost_per_1k_tokens=${cost_per_1k_tokens_view(run):.4f}")

spans — gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens,
gen_ai.system — so cost and usage data from any provider lands in the same shape a
tracing backend already knows how to query, instead of every team inventing its own field

attribute SHAPE and the attribution fields a BFSI deployment adds alongside it

Concept 3 — Local Tokenizer Counts vs. Billed Usage, and Where They Diverge


A pre-flight budget check needs a token estimate before the call ever happens, so it has
to be computed locally with no network round trip. But a local estimate is never exactly
what the provider bills — BPE tokenization splits on sub-word boundaries that don't line
up with word boundaries, especially for the exact strings a BFSI prompt is full of: policy
numbers, currency figures, dates. This sandbox cannot demonstrate the gap against a REAL
BPE tokenizer: tiktoken imports cleanly, but tiktoken.get_encoding("cl100k_base")
fetches its vocabulary file from openaipublic.blob.core.windows.net, and this sandbox's
egress proxy rejects that host —


requests.exceptions.ProxyError: ... Tunnel connection failed: 403 Forbidden ...
openaipublic.blob.core.windows.net

— confirmed directly, the same gap known-issues.md item 9 already found for this exact
package. The estimate below is therefore a genuine, hand-rolled word-count heuristic
(roughly 1.3 tokens per English word, the same approximation this track's own Curriculum
content already uses), not a stand-in FOR tiktoken pretending to be it — and the
billed_actual figures are values a real provider usage response would report, used here
to demonstrate the divergence math, not measured by a live call.


Example:


def local_token_estimate(text):
    """A cheap, no-network approximation -- ~1.3 tokens per word for English
    prose. This is not what a provider bills; it's what a service can
    compute locally before a call to budget and pre-flight check."""
    return int(len(text.split()) * 1.3)

def divergence_pct(local_estimate, billed_actual):
    if billed_actual == 0:
        return 0.0
    return (billed_actual - local_estimate) / billed_actual * 100

# billed_actual values stand in for a provider's real usage response
# (gen_ai.usage.input_tokens on the response span) -- genuinely different
# from the word-count heuristic because BPE boundaries don't match word
# boundaries, especially for policy numbers and currency figures.
sample_texts = [
    ("plain_prose", "Please confirm the customer's mailing address on file."),
    ("claim_reference", "Claim CLM-88213 policy POL-445920 balance $12,450.75 as of 2026-09-18."),
]
billed_actual = {"plain_prose": 12, "claim_reference": 34}

for label, text in sample_texts:
    local = local_token_estimate(text)
    billed = billed_actual[label]
    print(f"{label}: local_estimate={local} billed_actual={billed} divergence={divergence_pct(local, billed):.1f}%")

Concept 4 — Splitting Spend by Tenant, Use Case, and Pipeline Stage Before Optimizing Anything


Optimizing before you know where the money is going is how a team ends up caching the
cheap path and leaving the expensive one untouched. The same gen_ai.* attribution fields
Concept 2 attached to every span make it possible to answer "which tenant, which use
case, which pipeline stage" BEFORE reaching for prompt caching, model routing, or batching
— grouping the exact same span data by different attribute keys is the whole mechanism,
no new instrumentation required.


Example:


import collections

def aggregate_spend(spans_list, group_by):
    totals = collections.defaultdict(float)
    for s in spans_list:
        key = tuple(s.attributes[k] for k in group_by)
        totals[key] += span_cost_usd(s)
    return dict(totals)

by_tenant = aggregate_spend(spans, ["tenant.id"])
by_tenant_stage = aggregate_spend(spans, ["tenant.id", "pipeline.stage"])

print("by tenant:")
for k, v in sorted(by_tenant.items()):
    print(f"  {k[0]}: ${v:.4f}")
print("by tenant + stage:")
for k, v in sorted(by_tenant_stage.items()):
    print(f"  {k}: ${v:.4f}")

BFSI Reality Check — Day 1


Legacy angle: a claims platform built before LLM calls existed has no claim_id on
any of its existing cost-tracking tables — attribution has to be bolted on by tagging
every span at call time (tenant.id, use_case, pipeline.stage) rather than joined in
after the fact from a system that was never designed to carry it.


Compliance angle: per-tenant cost attribution is not just a FinOps convenience in a
multi-tenant BFSI platform — it is the same data a tenant-level billing dispute or an
internal chargeback audit needs, so the attribution fields have to be trustworthy enough
to stand behind in that context, not an approximate label added as an afterthought.


What breaks in production: a local token estimate used as a hard pre-flight gate
(reject anything over a threshold before sending) will reject requests the provider would
have accepted, and admit requests the provider bills far more for than expected, purely
from the local/billed divergence Concept 3 measured — a production budget gate needs
either a wide safety margin around the local estimate or a real tokenizer library, not the
bare word-count heuristic used here for its no-network property alone.

Concept 1 — Cache Breakpoints and the TTL They Carry


A provider's prompt cache is opt-in per block: a request marks specific content with a
cache_control breakpoint, and only content up to and including that marker becomes
eligible for a cache hit on a later request. Each breakpoint carries its own TTL — how
long the cached prefix stays warm before it has to be rewritten. Content the agent
generates fresh every turn (the actual user message) is never marked; only genuinely
static content — a system prompt, a tool schema, a policy document — is a breakpoint
candidate. This sandbox cannot make a real cache-control call to a live provider, but the
decision of WHICH blocks to mark and what TTL to give them is genuine, checkable logic
here regardless.


Example:


import dataclasses

@dataclasses.dataclass
class CacheBreakpoint:
    block_label: str
    ttl_seconds: int

@dataclasses.dataclass
class PromptBlock:
    label: str
    content: str
    cache_control: CacheBreakpoint | None = None

def mark_cache_breakpoint(block, ttl_seconds=300):
    # Real Anthropic API shape (REAL MODE reference, not executed here):
    #   {"type": "text", "text": block.content,
    #    "cache_control": {"type": "ephemeral", "ttl": "5m"}}
    return dataclasses.replace(block, cache_control=CacheBreakpoint(block.label, ttl_seconds))

system_block = PromptBlock("system_policy", "You are a claims assistant. Follow policy PL-100. " * 40)
tool_block = PromptBlock("tool_schema", "Available tools: get_policy_balance, renew_policy. " * 20)
per_request_block = PromptBlock("user_turn", "What is the balance on POL-445920?")

system_block = mark_cache_breakpoint(system_block, ttl_seconds=300)
tool_block = mark_cache_breakpoint(tool_block, ttl_seconds=300)
# per_request_block deliberately NOT marked -- it changes every call

for b in [system_block, tool_block, per_request_block]:
    cached = "cached" if b.cache_control else "not cached"
    ttl = f"ttl={b.cache_control.ttl_seconds}s" if b.cache_control else ""
    print(f"{b.label:15s} {cached:12s} {ttl}")

Concept 2 — Ordering Static Content Ahead of Per-Request Content


A provider's cache matches on the prompt's PREFIX, byte for byte, starting from the very
first token. If per-request content (today's user message, a live balance figure) sits
anywhere before the static system/tool/policy content, the prefix is never byte-stable
across two requests, and every request becomes a cache miss regardless of how many
breakpoints are marked. The fix is purely an ordering rule: static content always comes
first, in the same order, every time; dynamic content always comes last.


Example:


def assemble_prompt(static_blocks, dynamic_blocks):
    # Static, cacheable content MUST come first and in a stable order --
    # any per-request content before it (even a single differing byte)
    # invalidates the cache for everything that follows it.
    return static_blocks + dynamic_blocks

def prompt_prefix_bytes(blocks, up_to):
    return "".join(b.content for b in blocks[:up_to]).encode("utf-8")

correct_order = assemble_prompt([system_block, tool_block], [per_request_block])
wrong_order = assemble_prompt([per_request_block, system_block], [tool_block])

# Two different requests sharing the same static content, correct order:
per_request_block_b = PromptBlock("user_turn", "What is the balance on POL-990112?")
correct_order_b = assemble_prompt([system_block, tool_block], [per_request_block_b])

prefix_a = prompt_prefix_bytes(correct_order, up_to=2)
prefix_b = prompt_prefix_bytes(correct_order_b, up_to=2)
print(f"correct order: prefix identical across requests = {prefix_a == prefix_b}")

wrong_order_b = assemble_prompt([per_request_block_b, system_block], [tool_block])
wrong_prefix_a = prompt_prefix_bytes(wrong_order, up_to=1)
wrong_prefix_b = prompt_prefix_bytes(wrong_order_b, up_to=1)
print(f"wrong order (dynamic first): prefix identical across requests = {wrong_prefix_a == wrong_prefix_b}")

Concept 3 — Minimum Cacheable Prefix Length and the Write/Read Price Asymmetry


Providers set a minimum token count below which a prefix isn't cache-eligible at all — a
short system prompt is simply too small to bother caching. Above that floor, caching still
isn't free: the FIRST request that populates the cache pays a WRITE premium (more than an
uncached call would cost), and only SUBSEQUENT requests that hit the warm cache get the
steep READ discount. A cache only pays for itself once enough hit-priced requests have
run to offset that one write premium.


Example:


MIN_CACHEABLE_TOKENS = 1024  # provider-documented floor below which caching isn't offered

def estimate_tokens(text):
    return int(len(text.split()) * 1.3)

def cache_write_cost(tokens, input_price_per_1k):
    # Real providers charge a WRITE premium (Anthropic: 1.25x base for a
    # 5-minute TTL) -- the first call that populates the cache costs MORE
    # than an uncached call would.
    return (tokens / 1000) * input_price_per_1k * 1.25

def cache_read_cost(tokens, input_price_per_1k):
    # A cache HIT is billed at a steep discount (Anthropic: 0.1x base).
    return (tokens / 1000) * input_price_per_1k * 0.1

def cache_eligible(prefix_text):
    return estimate_tokens(prefix_text) >= MIN_CACHEABLE_TOKENS

short_prefix = "You are a claims assistant."
long_prefix = ("You are a claims assistant. Follow policy PL-100 for every claim over "
               "$1,000. " * 65)

for label, prefix in [("short_prefix", short_prefix), ("long_prefix", long_prefix)]:
    tokens = estimate_tokens(prefix)
    print(f"{label}: tokens={tokens} cache_eligible={cache_eligible(prefix)}")

INPUT_PRICE_PER_1K = 0.003
tokens = estimate_tokens(long_prefix)
write_cost = cache_write_cost(tokens, INPUT_PRICE_PER_1K)
read_cost = cache_read_cost(tokens, INPUT_PRICE_PER_1K)
uncached_cost = (tokens / 1000) * INPUT_PRICE_PER_1K
print(f"tokens={tokens}  write=${write_cost:.5f}  read=${read_cost:.5f}  uncached=${uncached_cost:.5f}")
print(f"break-even: cache pays off after {write_cost / (uncached_cost - read_cost):.2f} cache-hit calls")

Concept 4 — Cache-Hit Rate as a Deploy-Gating Metric


A cache that never actually hits is worse than useless — it pays the write premium on
every request with none of the read-discount payoff, usually because a recent deploy
broke prefix stability (Concept 2) without anyone noticing until the bill arrived. Tracking
hit rate as a first-class metric, and gating a deploy on it directly, catches that
regression before it reaches production traffic at scale, the same way a quality
regression gate would.


Example:


import hashlib

@dataclasses.dataclass
class CacheStats:
    hits: int = 0
    misses: int = 0

    @property
    def hit_rate(self):
        total = self.hits + self.misses
        return self.hits / total if total else 0.0

class PrefixCacheSimulator:
    """An in-memory stand-in for a provider's real prompt cache -- tracks
    hit/miss by the byte-identical static prefix, the same mechanism a real
    cache keys on."""

    def __init__(self):
        self._store = {}  # prefix_hash -> expiry_time
        self.stats = CacheStats()

    def _hash(self, prefix_bytes):
        return hashlib.sha256(prefix_bytes).hexdigest()

    def request(self, prefix_bytes, ttl_seconds, now):
        key = self._hash(prefix_bytes)
        expiry = self._store.get(key)
        if expiry is not None and now < expiry:
            self.stats.hits += 1
            hit = True
        else:
            self.stats.misses += 1
            hit = False
        self._store[key] = now + ttl_seconds
        return hit

Concept 1 — Embedding-Similarity Cache With a Tuned Threshold and Per-Tenant Namespaces


Day 2's prefix cache only hits on a byte-identical prompt. Most repeated questions are
NOT byte-identical — "What is my current balance?" and "What amount do I currently owe?"
mean the same thing but share almost no bytes. A semantic cache instead embeds the
question and looks up the nearest PREVIOUSLY-ANSWERED question by cosine similarity,
returning that cached answer only above a tuned similarity threshold. This sandbox has no
live embedding API, so fake_embed below is a genuine, deterministic, keyword-bucket
stand-in (not a real model) — it is enough to demonstrate real threshold-tuning behavior
(paraphrases cluster near 1.0, unrelated questions near 0.0), which is the actual subject
here, without needing a live model. Namespacing the cache BY TENANT (a separate entry list
per tenant, never searched across tenants) keeps one tenant's cached answers — which may
reflect tenant-specific policy terms — from ever leaking into another tenant's response.


Example:


import dataclasses
import math

def cosine_similarity(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    if norm_a == 0 or norm_b == 0:
        return 0.0
    return dot / (norm_a * norm_b)

def fake_embed(text):
    """Deterministic stand-in for a real embedding model (this sandbox has
    no live embedding API). Buckets the text into a small set of hand-picked
    semantic axes based on keyword presence, so paraphrases of the SAME
    question land close together and different questions land far apart --
    enough to demonstrate threshold-tuning behavior genuinely, without a
    live model."""
    axes = ["balance", "renew", "claim_status", "password"]
    keywords = {
        "balance": ["balance", "owe", "amount due"],
        "renew": ["renew", "renewal", "expir"],
        "claim_status": ["claim", "status"],
        "password": ["password", "login", "reset"],
    }
    vec = []
    lowered = text.lower()
    for axis in axes:
        score = sum(1.0 for kw in keywords[axis] if kw in lowered)
        vec.append(score)
    if sum(vec) == 0:
        vec = [0.1, 0.1, 0.1, 0.1]
    return vec

@dataclasses.dataclass
class SemanticCacheEntry:
    tenant: str
    question_embedding: list
    answer: str
    written_at: float
    ttl_seconds: float

class SemanticCache:
    def __init__(self, similarity_threshold=0.90):
        self.similarity_threshold = similarity_threshold
        self._entries = {}  # tenant -> list[SemanticCacheEntry]

    def lookup(self, tenant, question, now):
        emb = fake_embed(question)
        best = None
        best_sim = 0.0
        for entry in self._entries.get(tenant, []):
            if now >= entry.written_at + entry.ttl_seconds:
                continue
            sim = cosine_similarity(emb, entry.question_embedding)
            if sim > best_sim:
                best_sim, best = sim, entry
        if best is not None and best_sim >= self.similarity_threshold:
            return best.answer, best_sim
        return None, best_sim

    def store(self, tenant, question, answer, now, ttl_seconds=3600):
        emb = fake_embed(question)
        self._entries.setdefault(tenant, []).append(
            SemanticCacheEntry(tenant, emb, answer, now, ttl_seconds)
        )

Concept 2 — Invalidation and TTL When a Policy Document Is Re-Versioned Mid-Day


A TTL alone is not enough for a semantic cache backing policy-dependent answers: a claims
policy document can be re-versioned in the middle of a business day, and every cached
answer that was generated under the OLD version is now potentially wrong, regardless of
how much of its TTL window remains. The fix is tagging every cache entry with the source
document version it was answered under, and invalidating by that tag directly the moment
a re-version happens — not waiting for TTL expiry to catch up.


Example:


def invalidate_by_source_version(cache_obj, tenant, source_doc, old_version, new_version):
    # A real deployment tags each cache entry with the policy-doc version it
    # was answered under; re-versioning invalidates every entry tagged with
    # the OLD version for that tenant, regardless of its TTL.
    entries = cache_obj._entries.get(tenant, [])
    kept = [e for e in entries if getattr(e, "source_version", new_version) != old_version]
    removed = len(entries) - len(kept)
    cache_obj._entries[tenant] = kept
    return removed

Concept 3 — When Caching Is Unsafe Because the Answer Depends on Live State


Not every question is safe to answer from a cache no matter how well it matches semantically.
"What is my current balance?" and "Do I have an open claim?" have a DIFFERENT correct answer
every time they're asked, even worded identically, because the answer depends on account
state that changes independently of the question. Caching these anyway would silently
serve a stale balance or a stale claim status — worse than a slow answer, a WRONG one.
The fix is a keyword/intent classifier that routes live-state-dependent questions around
the cache entirely, straight to a live lookup, before the cache is ever consulted.


Example:


LIVE_STATE_KEYWORDS = ("balance", "open claim", "claim status", "current amount", "owe")

def is_cache_safe(question):
    lowered = question.lower()
    return not any(kw in lowered for kw in LIVE_STATE_KEYWORDS)

def cached_lookup_or_live(cache_obj, tenant, question, now, live_answer_fn):
    if not is_cache_safe(question):
        return live_answer_fn(question), "live_required"
    answer, sim = cache_obj.lookup(tenant, question, now)
    if answer is not None:
        return answer, "cache_hit"
    live_result = live_answer_fn(question)
    cache_obj.store(tenant, question, live_result, now)
    return live_result, "cache_miss_stored"

Concept 4 — Trimming Retrieved Context Through Reranking Instead of Enlarging the Window


A common but wasteful reflex when a RAG answer looks weak is to raise the retrieval
top_k or the model's context window — more context, more tokens, more cost, with no
guarantee the extra chunks are actually relevant. Reranking the ALREADY-retrieved chunks
by relevance and trimming to a fixed token budget gets the opposite effect: the same or
better answer quality (only the genuinely relevant chunks make the cut) at a bounded,
predictable cost, regardless of how many chunks the initial retrieval step returned.


Example:


@dataclasses.dataclass
class RetrievedChunk:
    chunk_id: str
    text: str
    relevance_score: float

def rerank_and_trim(chunks, token_budget, tokens_per_chunk=150):
    ranked = sorted(chunks, key=lambda c: c.relevance_score, reverse=True)
    kept = []
    used = 0
    for c in ranked:
        if used + tokens_per_chunk > token_budget:
            continue
        kept.append(c)
        used += tokens_per_chunk
    return kept, used

    RetrievedChunk("c4", "Appendix C: unrelated vendor contact list.", 0.12),

Concept 1 — A Cheap Triage Model With Escalation Triggered by Low Verifier Confidence


Sending every request to the most capable (and most expensive) model is the default that
costs the most and needs the least engineering. A tiered cascade sends everything to a
cheap, fast triage pass FIRST, and only escalates to the expensive model when the cheap
pass's own confidence in its classification is too low to trust — not based on the
question's topic, but on how CONFIDENT the classifier itself is in its own answer. This
sandbox has no live triage model, so triage_classify below is a genuine, deterministic
keyword scorer standing in for one — its confidence values are hand-set to demonstrate
real escalation behavior (high confidence on clear cases, low on ambiguous ones), the
same mechanism a real classifier's own logit-derived confidence would drive.


Example:

class TriageResult:
    label: str
    confidence: float

def triage_classify(text):

    trigger escalation."""

Concept 4 — Constrained Output Schemas and Stop Sequences to Cut Output Tokens Directly


Output tokens are typically billed at a HIGHER per-1k rate than input tokens (5x is
common), so trimming a verbose free-text answer down to exactly the fields the caller
actually needs cuts cost disproportionately to how little text is removed. Constraining
the model's output to a JSON schema (or cutting generation early with a stop sequence) is
a direct, structural fix — not a prompting nudge to "be concise" that the model may or may
not follow.


Example:

An honest, genuinely executable proxy for confidence is self-consistency: sample the
classifier several times and use the winning label's VOTE FRACTION, an empirical
frequency, rather than trusting any single call's self-reported figure. The stand-in
below hand-sets each message's sample outcomes the same deliberate way Concept 1's
triage_classify hand-sets its confidence — tight agreement on a clear case, real split
on an ambiguous one:

def simulate_n_samples(text):
    """Stand-in for calling a classifier N times at temperature>0 and
    collecting each sample's label. Hand-set per input to demonstrate
    real self-consistency behavior (tight agreement on a clear case,
    split on an ambiguous one)."""
    lowered = text.lower()
    if "duplicate charge" in lowered or "refund" in lowered:
        return ["billing_dispute"] * 5
    if "balance" in lowered:
        return ["balance_inquiry"] * 4 + ["general"] * 1
    if "unusual" in lowered or "not sure" in lowered or "complicated" in lowered:
        return ["unclear", "general", "unclear", "billing_dispute", "unclear"]
    return ["general"] * 3 + ["balance_inquiry"] * 2

def vote_fraction_confidence(samples):
    counts = {}
    for s in samples:
        counts[s] = counts.get(s, 0) + 1
    winner = max(counts, key=counts.get)
    return winner, counts[winner] / len(samples)

def route_with_sampled_confidence(text, floor=ESCALATION_CONFIDENCE_FLOOR):
    label, fraction = vote_fraction_confidence(simulate_n_samples(text))
    route = "escalate_to_full_model" if fraction < floor else "cheap_tier_handles_it"
    return route, label, fraction

at all. None of these tools hand you calibration for free — they hand you an honest number
to calibrate, which is a different and smaller claim than "the model's own confidence."
(A newer category of vendor-native "typed decision" model claiming to return a calibrated
probability directly emerged in 2026; worth watching, but with no production BFSI track
record yet, not a tool to anchor a design on.)

Concept 1 — Per-Tenant Token Budgets and Quota Enforcement


A cost governance system that only REPORTS spend after the fact can tell you a tenant blew
through their budget, but not stop it from happening. Enforcing a hard daily token budget
per tenant — consumed as requests come in, rejected once exhausted — turns "we noticed the
overspend in yesterday's report" into "the 47th request today was blocked before it ever
reached the model," the same shift from detection to prevention this track's guardrail and
circuit-breaker content has made in earlier weeks.


Example:


import dataclasses

class QuotaExceededError(Exception):
    pass

@dataclasses.dataclass
class TenantQuota:
    tenant: str
    daily_token_budget: int
    tokens_used_today: int = 0

    def remaining(self):
        return max(0, self.daily_token_budget - self.tokens_used_today)

    def consume(self, tokens):
        if self.tokens_used_today + tokens > self.daily_token_budget:
            raise QuotaExceededError(
                f"{self.tenant}: request needs {tokens} tokens but only "
                f"{self.remaining()} remain of {self.daily_token_budget} daily budget"
            )
        self.tokens_used_today += tokens
        return self.tokens_used_today

quotas = {
    "tenant-acme": TenantQuota("tenant-acme", daily_token_budget=10000),
    "tenant-globex": TenantQuota("tenant-globex", daily_token_budget=2000),
}

requests = [
    ("tenant-acme", 3000),
    ("tenant-globex", 1500),
    ("tenant-globex", 800),  # this should exceed globex's remaining 500
]

for tenant, tokens in requests:
    q = quotas[tenant]
    try:
        used = q.consume(tokens)
        print(f"{tenant}: consumed {tokens} tokens, used_today={used}, remaining={q.remaining()}")
    except QuotaExceededError as e:

Concept 2 — Canary Rollout on a Model Swap, Cost and Quality Compared Side by Side


Swapping to a cheaper model tier without measuring both sides of the tradeoff is how a
"cost optimization" quietly becomes a quality regression nobody notices until customers
complain. A canary rollout — the same deterministic hash-bucketing this track's own
Curriculum content already uses for prompt canaries — routes a small percentage of real
traffic to the candidate model and compares its cost AND quality against the stable
baseline side by side, on the same real traffic mix, before deciding whether to promote
it.


Example:


import hashlib

@dataclasses.dataclass
class CanaryResult:
    variant: str
    cost_usd: float
    quality_score: float

def canary_bucket(request_id, canary_pct=10):
    bucket = int(hashlib.md5(str(request_id).encode()).hexdigest(), 16) % 100
    return "canary" if bucket < canary_pct else "stable"

def run_canary_comparison(request_ids, stable_cost, stable_quality, canary_cost, canary_quality, canary_pct=10):
    results = []
    for rid in request_ids:
        variant = canary_bucket(rid, canary_pct)
        if variant == "canary":
            results.append(CanaryResult(variant, canary_cost, canary_quality))
        else:
            results.append(CanaryResult(variant, stable_cost, stable_quality))
    return results

request_ids = [f"req-{i}" for i in range(50)]
results = run_canary_comparison(
    request_ids,
    stable_cost=0.012, stable_quality=0.91,
    canary_cost=0.007, canary_quality=0.89,
    canary_pct=10,
)
canary_results = [r for r in results if r.variant == "canary"]
stable_results = [r for r in results if r.variant == "stable"]
print(f"canary_count={len(canary_results)}  stable_count={len(stable_results)}")
avg_canary_cost = sum(r.cost_usd for r in canary_results) / len(canary_results)
avg_stable_cost = sum(r.cost_usd for r in stable_results) / len(stable_results)
print(f"avg_canary_cost=${avg_canary_cost:.4f}  avg_stable_cost=${avg_stable_cost:.4f}")
print(f"canary_quality={canary_results[0].quality_score}  stable_quality={stable_results[0].quality_score}")

Concept 4 — Treating a Cost Regression as a Failing Release Gate Alongside a Quality Regression


A quality regression already blocks a release in a mature ML pipeline. A cost regression
of the same magnitude — a new model version that costs 24% more per claim for no quality
gain — deserves the identical treatment: a hard gate that raises and blocks the release,
not a dashboard number someone might notice later. Gating on BOTH dimensions together also
catches the case neither alone would: a candidate that's cheaper AND meaningfully worse in
quality still fails, because a quality floor exists independent of what the cost trend
looks like.


Example:


@dataclasses.dataclass
class ReleaseCandidate:
    version: str
    cost_per_claim: float
    quality_score: float

BASELINE = ReleaseCandidate("v3.1-baseline", cost_per_claim=0.0210, quality_score=0.92)

class ReleaseGateError(Exception):
    pass

def evaluate_release_gate(candidate, baseline=BASELINE, max_cost_increase_pct=15.0, max_quality_drop=0.02):
    cost_increase_pct = (candidate.cost_per_claim - baseline.cost_per_claim) / baseline.cost_per_claim * 100
    quality_drop = baseline.quality_score - candidate.quality_score
    failures = []
    if cost_increase_pct > max_cost_increase_pct:
        failures.append(f"cost regression: +{cost_increase_pct:.1f}% (limit {max_cost_increase_pct}%)")
    if quality_drop > max_quality_drop:
        failures.append(f"quality regression: -{quality_drop:.4f} (limit {max_quality_drop})")
    if failures:
        raise ReleaseGateError(f"{candidate.version} BLOCKED: " + "; ".join(failures))
    return {"version": candidate.version, "cost_increase_pct": round(cost_increase_pct, 1), "quality_drop": round(quality_drop, 4)}

candidates = [
    ReleaseCandidate("v3.2-cheaper", cost_per_claim=0.0195, quality_score=0.915),
    ReleaseCandidate("v3.2-cost-regression", cost_per_claim=0.0260, quality_score=0.925),
    ReleaseCandidate("v3.2-quality-regression", cost_per_claim=0.0205, quality_score=0.88),
]

for c in candidates:
    try:
        result = evaluate_release_gate(c)
        print(f"{c.version}: PASS  {result}")
    except ReleaseGateError as e:
        print(f"{c.version}: {e}")

BFSI Reality Check — Day 5


Legacy angle: a per-tenant quota is only as trustworthy as the token-counting it's
built on — Day 1's own local-estimate-vs-billed divergence means a quota enforced purely
on local estimates can both wrongly block a tenant still under their REAL budget and
wrongly admit one already over it, unless the enforcement point reconciles against actual
billed usage on some regular cadence, not just the pre-flight estimate.


Compliance angle: ReleaseGateError's hard block on a 24% cost regression is exactly
the kind of automated control a FinOps or model-risk review expects to see evidenced, not
just asserted — a real deployment would want this gate's pass/fail history retained
alongside the model version it evaluated, the same audit-trail instinct Week 22 built for
tool calls applied here to releases.


What breaks in production: TenantQuota.tokens_used_today resets only if something
external calls a reset at day boundary — a quota object with no such reset simply never
gives a tenant their daily allowance back, silently blocking every request from a tenant
whose quota window never actually rolled over, a bug that looks identical to a genuine
sustained overspend until someone checks the reset logic specifically.




Architecture Decision — Week 23


Choosing between: aggressive caching and routing (semantic caching with a permissive
similarity threshold, an escalation-confidence floor tuned low so most traffic stays on
the cheap tier, and constrained output schemas applied everywhere by default) vs.
conservative, correctness-first spend (caching restricted to content proven
live-state-independent per Day 3 Concept 3, a high escalation floor that sends more
traffic to the expensive tier, and free-text output left alone unless a schema is already
part of the product's contract).


Rule of thumb: default to conservative, correctness-first spend for any request whose
answer could plausibly depend on account state that changes between cache writes (a
balance, an open claim's status, anything Day 3's is_cache_safe would flag) or whose
escalation miss carries real cost (an ambiguous claims-liability question routed to the
cheap tier and answered wrong). Move to aggressive caching and routing only for
traffic that is provably safe to optimize: genuinely static reference content (policy
text, FAQ-shaped questions), requests whose triage confidence is measurably reliable
against a real historical accuracy check (not just a threshold picked once and left
alone), and batchable, non-interactive work where Day 4's asynchronous discount applies
with no user waiting on the other end.


This is not a track-wide, set-once choice — it is the same PER-REQUEST-CLASS decision
Week 22's Architecture Decision made for write-tool blast radius, applied here to spend
instead of writes. A new use case defaults to conservative (full-price, uncached, always
escalated to the capable model) until its own traffic has a measured track record — real
cache-hit rates, real triage accuracy, real canary comparisons per Day 5 Concept 2 —
that earns it a deliberate, evidenced move toward the cheaper path. Every one of those
moves is then protected the same way Day 5 Concept 4 protects a model swap: a cost
regression is a release-blocking defect, not a metric to note and move past, precisely
because "optimized last quarter" is not evidence that this quarter's traffic mix, prompt
content, or provider pricing hasn't quietly made the optimization wrong.
