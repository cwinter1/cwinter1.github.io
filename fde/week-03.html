Concept 1 — Four Worker Roles and Three Dependencies

pgvector is one process. Milvus is a cluster of specialised roles, and reading its architecture is mostly a matter of noticing that each role owns one verb.

  • Proxy — the stateless front door. Clients connect here. It validates requests, routes them, and reduces the per-node result sets into the single top-k you asked for. Being stateless, it is the easy thing to scale horizontally.
  • Query node — serves searches. It loads sealed segments and their indexes into memory, and separately subscribes to the write stream so it can also serve data too recent to have been sealed.
  • Data node — consumes the write log, accumulates incoming rows, and flushes them to object storage as immutable sealed segments. It also executes compaction.
  • Index node — builds index files over sealed segments and writes those files back to object storage.

Behind those sit three dependencies Milvus does not implement itself: etcd for metadata and coordination, a log broker (Pulsar or Kafka; a local embedded broker in the standalone image) as the write-ahead log, and object storage (MinIO or S3) for segment and index files. A set of coordinator services assigns work to the workers; recent Milvus versions let you run them as one mixed coordinator process rather than four.

The write path is worth committing to memory, because every later concept this week is a consequence of it: client to proxy, proxy appends to the log broker, data node consumes the log and builds a growing segment, flush turns that into a sealed segment in object storage, index node indexes it, query node loads it.

Example:

# REAL MODE -- requires a running Milvus instance. Not executed in this sandbox.
from pymilvus import connections, utility

connections.connect(alias="default", host="milvus.internal", port="19530")

print("server version :", utility.get_server_version())
print("collections    :", utility.list_collections())

# The query nodes' own view of what they are currently serving.
for seg in utility.get_query_segment_info("claim_notes"):
    print(seg)

Concept 2 — Growing Segments and Sealed Segments

A segment is Milvus's unit of storage and of work. Segments come in two states, and the distinction drives both freshness and latency.

A growing segment is still accepting writes. It lives in memory, it is not indexed, and a query node searches it by brute-force scan. A sealed segment is immutable, flushed to object storage, and indexed. Sealing is triggered by policy — most visibly a size threshold (dataCoord.segment.maxSize, expressed in MB and commonly 512 by default, though you should read it from your own deployment's config rather than trusting a number in a document), and also by lifetime and idle-time policies.

This is why a freshly-written row can be found immediately but slightly more expensively: it is being scanned, not indexed. It is also why a collection under heavy write load with sealing misconfigured develops large unindexed growing segments and mysteriously slow searches.

Example:

# Plain Python -- this one runs anywhere. Sealed-segment arithmetic.
dim, bytes_per = 1024, 4
vector_bytes = dim * bytes_per
segment_max_mb = 512
vectors_per_segment = (segment_max_mb * 1024**2) // vector_bytes
print(f"bytes per vector          : {vector_bytes:,}")
print(f"vectors per 512 MB segment: {vectors_per_segment:,}")

for n in (1_000_000, 20_000_000, 200_000_000):
    segs = -(-n // vectors_per_segment)
    print(f"{n:>12,} vectors -> {segs:>6,} sealed segments")

Concept 3 — Deletes Are Tombstones, and Compaction Is the Reaper


Milvus does not delete in place. A delete writes a record marking the entity gone; searches
then filter it out at query time. The row's vector is still sitting in its sealed segment,
still occupying memory on every query node that has loaded it, until a compaction run
rewrites the segment without it.


An upsert is the same story told twice, since it is a delete followed by an insert. A
collection under steady correction traffic — which is exactly what a claims system is —
accumulates dead weight that shows up as memory pressure long before anyone thinks to look
at deletion volume.


This should feel familiar rather than exotic: it is the same design as Postgres dead tuples
and VACUUM, which is a useful anchor for anyone arriving from Week 02.


Example:


# REAL MODE -- requires a running Milvus instance. Not executed in this sandbox.
from pymilvus import Collection

claims = Collection("claim_notes")

# Soft delete: writes a delete record, does not reclaim space.
claims.delete(expr="claim_id in [880412, 880417, 880431]")

# Compaction is what actually reclaims it.
job = claims.compact()
print("compaction state:", claims.get_compaction_state())

Concept 4 — Compute-Storage Separation Pays Off at Reindex Time


Milvus keeps segments and index files in object storage, not on the query node's local disk.
Query nodes hold a loaded copy in memory. That separation sounds like an abstract design
virtue right up until you have to change an index parameter, at which point it becomes the
whole argument.


Changing M on an HNSW index means a rebuild, not a reconfigure — Week 01 established this
and it stays true here. Because the segments live in object storage independently of any
serving node, an index node can build the new index files by reading from object storage
without touching the copy the query nodes are currently serving from. The switchover then
becomes a load operation rather than a data migration.


Contrast that with the pgvector case from Week 02, where the index lives in the same
instance that is serving queries, and a REINDEX competes for the same buffers, the same
CPU and the same disk as production traffic.


Example:


# REAL MODE -- requires a running Milvus instance. Not executed in this sandbox.
from pymilvus import Collection

claims = Collection("claim_notes")

# Rebuild under a new graph degree. The build reads segments from object storage.
claims.release()                       # free query-node memory first
claims.drop_index()
claims.create_index(
    field_name="embedding",
    index_params={
        "index_type": "HNSW",
        "metric_type": "COSINE",
        "params": {"M": 32, "efConstruction": 256},
    },
)
claims.load()                          # reload, now serving the new index
print(claims.index().params)

BFSI Reality Check — Day 1


Legacy angle: Milvus's three dependencies are three more things your on-prem platform
team has to own. etcd, a Kafka or Pulsar cluster and a MinIO deployment are each a
production system with its own upgrade path, backup story and on-call rota. In a bank where
Kafka is already run by a different team on a different change calendar, "we need a topic"
is not a config line, it is a quarter.


Compliance angle: Soft deletes collide directly with erasure obligations. If a customer
exercises a deletion right, a delete record that leaves the vector physically resident for
an indeterminate period until compaction runs is difficult to describe as erasure. The
defensible position is an explicit compaction step tied to the erasure workflow, with the
completion recorded — not a background process nobody schedules.


What breaks in production: Growing segments that never seal. Someone tunes the sealing
policy for a bulk-load window, the workload changes to steady trickle-writes, and segments
sit growing and unindexed. Nothing errors. Search latency simply climbs as an increasing
share of every query is served by brute-force scan over the unsealed portion.

Concept 1 — Field Schema and the Partition Key


A Milvus collection is declared, not inferred: a primary key, one or more vector fields with
fixed dimension, and scalar fields for anything you want to filter on. So far this is a
table definition.


The interesting field is the partition key. Mark one scalar field (INT64 or VARCHAR) with
is_partition_key=True and Milvus hashes its value to route each entity into one of
num_partitions physical partitions, defaulting to 16. A search that filters on that field
can then be restricted to the relevant partition rather than scanning all of them.


This is the multi-tenancy primitive. For a broker platform holding many carriers' claims in
one collection, carrier_id as the partition key gives you tenant isolation without
managing partitions by hand. Two constraints worth knowing before you design around it: one
partition key per collection, and the pruning only happens if the query actually filters on
that field — a query without it fans out across every partition.


Example:


# REAL MODE -- requires a running Milvus instance. Not executed in this sandbox.
from pymilvus import CollectionSchema, FieldSchema, DataType, Collection

fields = [
    FieldSchema("claim_id",    DataType.INT64,       is_primary=True, auto_id=False),
    FieldSchema("carrier_id",  DataType.VARCHAR,     max_length=32, is_partition_key=True),
    FieldSchema("policy_type", DataType.VARCHAR,     max_length=32),
    FieldSchema("claim_date",  DataType.INT64),      # epoch seconds, filterable
    FieldSchema("embedding",   DataType.FLOAT_VECTOR, dim=1024),
]
schema = CollectionSchema(fields, description="claim notes, partitioned by carrier")

claims = Collection("claim_notes", schema=schema, num_partitions=32)
print(claims.schema)

Concept 2 — load_collection Is the Real Capacity Limit


Milvus will happily ingest more data than it can search. Data lives in object storage;
searching it requires it to be loaded into query-node memory first. load_collection
(or load_partitions for a subset) is what does that, and available query-node RAM is
therefore the true capacity ceiling — not disk, not object-storage cost.


replica_number multiplies that cost directly. Two in-memory replicas of a collection
occupy twice the memory across the cluster, which is the price of surviving a query node
failure without losing searchability.


Example:


# Plain Python -- this one runs anywhere. Resident memory for a loaded collection.
def resident_gib(n, dim, bytes_per=4, graph_m=16, replicas=1):
    vectors = n * dim * bytes_per
    graph = n * graph_m * 2 * 4          # HNSW edges, ~2M ids at layer 0, 4-byte ids
    return (vectors + graph) * replicas / 1024**3

for n in (2_000_000, 20_000_000):
    for r in (1, 2, 3):
        print(f"{n:>11,} vectors  replicas={r}  resident ~{resident_gib(n,1024,replicas=r):7.2f} GiB")

budget = 64
n = 20_000_000
print(f"query-node RAM budget {budget} GiB, corpus {n:,} @1024d float32")
print(f"  one replica needs      : {resident_gib(n,1024):.2f} GiB")
print(f"  query nodes to hold it : {-(-resident_gib(n,1024)//budget):.0f} (before any replica)")

Concept 3 — Four Consistency Levels and What GuaranteeTs Does


Milvus offers four consistency levels, and they are all the same mechanism with one number
changed. Every search request carries a guarantee timestamp. Each query node tracks a
service timestamp reflecting how far through the write stream it has consumed. Before
executing, the node waits until its service timestamp reaches the request's guarantee
timestamp. The level just decides what the guarantee timestamp is set to.


    

  • Strong — set to the current system timestamp. The node waits for everything written
before the request to become visible. Correct, and the slowest.
    • 

  • Bounded — set to the current timestamp minus a tolerance (the graceful-time setting).
Recent writes within that window may be missed. This is the default in current versions;
confirm against your own deployment.
    • 

  • Session — set to this client's own last write. You always read your own writes, with
no guarantee about anyone else's.
    • 

  • Eventually — set to the minimum. No waiting at all, lowest latency, weakest guarantee.
    • 



The level can be set on the collection and overridden per request, which matters because a
single application usually needs more than one. Framed as a BFSI question: an adjuster
searching for duplicates of the claim they just filed needs Session at minimum. A monthly
portfolio analytics sweep is fine on Eventually. A fraud check that must not miss a
transaction written seconds ago wants Strong, and should pay for it.


Example:


# REAL MODE -- requires a running Milvus instance. Not executed in this sandbox.
from pymilvus import Collection

claims = Collection("claim_notes")

# Per-request override: the adjuster must see the claim they just wrote.
hits = claims.search(
    data=[query_vector],
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"ef": 64}},
    limit=10,
    expr='carrier_id == "IL-CARRIER-04" and policy_type == "MOTOR"',
    output_fields=["claim_id", "policy_type"],
    consistency_level="Session",
)
for hit in hits[0]:
    print(hit.id, hit.distance, hit.entity.get("policy_type"))

Concept 4 — IVF_FLAT vs HNSW, Chosen Per Vector Field


Milvus indexes are declared per vector field, so the choice is made per collection rather
than globally. Two index types cover most of the ground.


IVF_FLAT clusters the vectors with k-means into nlist buckets and stores the full
vectors inside them. At search time nprobe decides how many buckets to examine. It builds
quickly, its memory footprint is essentially the raw vectors plus centroids, and its recall
is tuned entirely by nprobe.


HNSW builds the layered proximity graph from Week 01, parameterised by M and
efConstruction, searched with ef. It costs more memory — the graph edges are real, as the
Concept 2 arithmetic showed — and considerably more build time, and it generally gives a
better latency-versus-recall curve at query time.


The practical rule: HNSW where query latency is the binding constraint and the corpus fits
in memory with its graph; IVF_FLAT where build time or memory is binding, or where the
collection is rebuilt often enough that build cost dominates. Week 04 tunes both properly.


Example:


# REAL MODE -- requires a running Milvus instance. Not executed in this sandbox.
hnsw = {
    "index_type": "HNSW",
    "metric_type": "COSINE",
    "params": {"M": 16, "efConstruction": 200},
}
ivf_flat = {
    "index_type": "IVF_FLAT",
    "metric_type": "COSINE",
    "params": {"nlist": 4096},
}

claims.create_index(field_name="embedding", index_params=hnsw)
print(claims.index().params)

# Search params differ per index type: HNSW takes ef, IVF_FLAT takes nprobe.
hnsw_search = {"metric_type": "COSINE", "params": {"ef": 64}}
ivf_search  = {"metric_type": "COSINE", "params": {"nprobe": 16}}

BFSI Reality Check — Day 2


Legacy angle: The partition key wants a clean tenant identifier, and legacy cores rarely
have one. Carrier identity is often implied by a branch code range, or by which nightly file
the row arrived in, and the same carrier can appear under two identifiers after an
acquisition. Deriving a stable partition key is an upstream data-modelling job that has to
finish before the collection schema is fixed, because changing the partition key means
recreating the collection.


Compliance angle: Consistency level is an auditable property of a control. If a sanctions
or fraud screen runs at Bounded consistency, there is a defined window in which a
just-written record is invisible to it, and that window is a control gap you would rather
document deliberately than have an auditor discover. Record the level per query path
alongside the rest of the retrieval configuration.


What breaks in production: The collection is loaded during a quiet migration, everything
is fast, and nobody records that load was ever called. Months later a restart brings the
cluster back with the collection released, searches fail or return nothing, and the runbook
does not mention loading because the person who ran it did so interactively.

Concept 1 — Payload Indexes Are Not Optional


Qdrant attaches arbitrary JSON — the payload — to each point, and lets you filter on it.
Filtering works without any index; it just works by checking the condition against points as
they are considered, which is fine at small scale and quietly terrible at large scale.


A payload index on a field changes that from a check into a lookup, and it is what makes
the query planner's cardinality estimate possible at all (Concept 3 depends on this). Index
types are per field and typed: keyword for categorical strings like policy_type,
integer, float, bool, datetime for ranges like claim_date, geo, text for
full-text conditions, and uuid.


The rule is simple and worth stating flatly: if you filter on a field in production, index
it. The cost is memory and a small write-path overhead; the alternative is a filter that
degrades as the collection grows.


Example:


# REAL MODE -- requires a running Qdrant instance. Not executed in this sandbox.
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://qdrant.internal:6333")

client.create_collection(
    collection_name="claims",
    vectors_config=models.VectorParams(size=1024, distance=models.Distance.COSINE),
)

client.create_payload_index(
    collection_name="claims",
    field_name="policy_type",
    field_schema=models.PayloadSchemaType.KEYWORD,
)
client.create_payload_index(
    collection_name="claims",
    field_name="claim_date",
    field_schema=models.PayloadSchemaType.DATETIME,
)

print(client.get_collection("claims"))

Concept 2 — must, should and must_not


Qdrant's filter language is three clause lists, and they map onto boolean logic directly:


    

  • must — every condition has to hold. This is AND.
    • 

  • should — at least one has to hold. This is OR. If a filter contains only should
clauses, at least one of them must match for a point to qualify.
    • 

  • must_not — none may hold. This is NOT.
    • 



Conditions are built from FieldCondition with a matcher: MatchValue for exact equality,
MatchAny for set membership, Range for numeric bounds, DatetimeRange for dates. They
nest — a Filter can itself appear inside a clause list — which is how you express anything
resembling (A OR B) AND NOT C.


Example:


# REAL MODE -- requires a running Qdrant instance. Not executed in this sandbox.
from qdrant_client import models

# Motor or property claims, filed since 2026-01-01, excluding closed and fraudulent ones.
claim_filter = models.Filter(
    must=[
        models.FieldCondition(
            key="claim_date",
            range=models.DatetimeRange(gte="2026-01-01T00:00:00Z"),
        ),
    ],
    should=[
        models.FieldCondition(key="policy_type", match=models.MatchValue(value="MOTOR")),
        models.FieldCondition(key="policy_type", match=models.MatchValue(value="PROPERTY")),
    ],
    must_not=[
        models.FieldCondition(key="status", match=models.MatchAny(any=["CLOSED", "FRAUD"])),
    ],
)

hits = client.query_points(
    collection_name="claims",
    query=query_vector,
    query_filter=claim_filter,
    limit=10,
    with_payload=True,
).points

for point in hits:
    print(point.id, point.score, point.payload.get("policy_type"))

Concept 3 — Filterable HNSW: payload_m and full_scan_threshold


Here is the problem a dedicated vector store solves that Week 02 had to work around. Filter a
graph index hard enough and the graph stops working: traversal moves between neighbours, and
if almost every neighbour fails the filter, the walk has nowhere to go and recall collapses.
Week 02 met this as the pre-filter versus post-filter dilemma.


Qdrant's answer has two parts. First, the query planner uses payload indexes to estimate the
cardinality of the filter before choosing a strategy. If the filtered subset is small, it
prefers a filtered full scan over just those points, which is exact and cheap at that size.
If the subset is large, it uses graph traversal with the filter applied during the walk.
full_scan_threshold in hnsw_config is the knob that sets where that switch happens; it is
expressed in KB, so it is a size threshold rather than a point count.


Second, payload_m builds additional payload-aware links into the graph. Where m is the
ordinary edge count per node, payload_m governs extra links constructed for payload values,
so that a filtered traversal still has somewhere to go. This is what makes per-tenant
subgraphs viable, and it is the direct structural answer to the recall collapse above.


Example:


# Plain Python -- this one runs anywhere. Filter selectivity against a size threshold.
dim = 1024
raw = dim * 4
n = 8_000_000
print("Filter selectivity vs a filtered-full-scan decision, corpus 8,000,000")
for name, sel in [("policy_type=MOTOR", 0.34),
                  ("claim_date in last 7d", 0.004),
                  ("branch=IL-042", 0.00012)]:
    hits = int(n * sel)
    kb = hits * raw / 1024
    print(f"  {name:<24} sel={sel:<8} -> {hits:>9,} points, {kb:>12,.0f} KB of vectors")

Concept 4 — Scalar and Binary Quantization


Quantization shrinks vectors by storing them at lower precision. Qdrant offers scalar
quantization (typically float32 to int8), binary quantization (one bit per dimension), and
product quantization. The compression is not subtle.


Both scalar and binary quantization are designed to be used with rescoring: search the
compressed representation to get a candidate set cheaply, then re-rank those candidates
against the original full-precision vectors. oversampling widens the candidate set to feed
that re-rank. This is how you recover most of the accuracy the compression cost you, and it
is why quantization is usually a better first move than dropping dimensions.


Binary quantization is aggressive and works best on high-dimensional embeddings from models
whose vectors tolerate it. It is not a universal setting, and it needs measuring on your own
corpus against a full-precision baseline — the Week 01 recall harness is exactly the tool.


Example:


# Plain Python -- this one runs anywhere. Per-vector footprint by representation.
dim = 1024
raw = dim * 4
print("Quantization footprint per vector, dim=1024")
print(f"  float32 : {raw:>6,} bytes  (1.0x)")
print(f"  int8 SQ : {dim:>6,} bytes  ({raw/dim:.0f}x smaller)")
print(f"  binary  : {dim//8:>6,} bytes  ({raw/(dim/8):.0f}x smaller)")

BFSI Reality Check — Day 3


Legacy angle: Payload fields inherit legacy encodings wholesale. policy_type off a
mainframe extract is a two-character code, not "MOTOR", and the same logical product carries
different codes across systems merged in an acquisition. A keyword index over an
un-normalised code space produces filters that silently miss whole populations, which looks
like a relevance problem and is actually a data-modelling one.


Compliance angle: Quantization changes which records are retrieved. For a retrieval path
feeding a regulated decision, that is a model-affecting change and belongs under the same
change control as swapping the embedding model — declared, measured against a baseline, and
recorded, per the accuracy-declaration expectations Week 01 met in its own Day 5.


What breaks in production: A filter on a field nobody indexed. It works in test against
50,000 points, ships, and degrades continuously as the collection grows, because the planner
has no cardinality estimate and cannot choose a sensible strategy. There is no error at any
point — only a latency graph that trends the wrong way for months.

Concept 1 — RAM Per Million Vectors Is the Sizing Driver


Every deployment conversation this week reduces to one number: how much memory a million
vectors need once loaded and indexed. Get that right and sharding, replication and node
count all follow arithmetically. Get it wrong and no amount of cluster topology rescues you.


Example:


# Plain Python -- this one runs anywhere. Corpus footprint and per-shard split.
n, dim = 20_000_000, 1024
per_vec = dim * 4 + 16 * 2 * 4        # vector bytes + HNSW edge bytes
total = n * per_vec / 1024**3
print(f"corpus {n:,} @{dim}d  ->  {total:.1f} GiB of vectors+graph (one copy)")

for shards in (3, 6, 12):
    print(f"shard_number={shards:<3} -> {total/shards:6.2f} GiB per shard")

Concept 2 — shard_number and replication_factor


The two parameters answer two different questions, and conflating them is the classic sizing
error.


shard_number divides a collection's data across nodes. It is a capacity decision: it
determines whether the collection fits at all, and how much of it any one node must hold. In
Qdrant it is fixed at collection creation for the default sharding method, so it is a
decision made against a growth forecast rather than today's row count.


replication_factor keeps N copies of each shard on different nodes. It is an
availability decision: with a factor of 1 a node loss takes part of the collection offline;
with 2 you survive one loss; with 3 you survive two. It multiplies total storage exactly.


Qdrant additionally exposes write_consistency_factor, governing how many replicas must
acknowledge a write — the same trade Milvus expresses through consistency levels, made at
the write side rather than the read side.


Example:


# Plain Python -- this one runs anywhere. Node count and failure tolerance.
total = 78.7                           # GiB, one copy, from Concept 1
node_ram = 64
for rf in (1, 2, 3):
    stored = total * rf
    nodes = -(-stored // node_ram)
    print(f"replication_factor={rf}  stored={stored:7.1f} GiB  "
          f"nodes@{node_ram}GiB>={nodes:.0f}  tolerates {rf-1} node loss")

Concept 3 — Single-Node Compose Versus a Three-Node Cluster


Both systems run single-node from Docker, and both single-node deployments are misleading in
the same way: they work perfectly and teach you nothing about the failure modes you will
actually meet.


Qdrant's single node is genuinely a single container. Milvus standalone is a compose file
with three services, because even standalone Milvus needs its etcd, its object storage and
its embedded log broker — which is itself the honest preview of the operational cost.


The gap between single-node and cluster is where the real work is: coordinating replica
placement, handling a node rejoining with stale data, and — most often overlooked — the fact
that a single-node deployment has no replication_factor worth setting, so nothing in your
development environment ever exercises the replication paths that production depends on.


Example:

      - ./qdrant_storage:/qdrant/storage

BFSI Reality Check — Day 4


Legacy angle: On-prem means the node count is set by a procurement cycle, not by a
config value. The Concept 2 arithmetic is the input to a capital request that will be
answered in months, and the corpus will have grown by then. Size against the forecast rather
than today's row count, because the cost of being one node short is a quarter, not an
afternoon.


Compliance angle: Data residency is what removes the managed-service escape hatch
entirely. When claims data must stay in-country and on infrastructure you control, "move to
a hosted vector service" is not a fallback available to you at any price, and the sizing
arithmetic has to close on hardware you actually own. This constraint deserves its own axis
in the Day 5 decision, and it gets one.


What breaks in production: replication_factor=1 in an environment everyone describes
as highly available. A node is lost during a routine patch, part of the collection goes
unsearchable, and the retrieval layer starts returning thin result sets rather than errors —
which downstream consumers cannot distinguish from a genuinely small result.

Concept 1 — The Four Axes That Actually Decide


Most vector-database comparisons are benchmark tables, and benchmark tables are close to
useless for this decision, because the thing that sinks a choice is almost never queries per
second. Four axes carry the actual weight.


    

  • Corpus size — does it fit one machine's memory, now and on the growth forecast? Day 2's
78.68 GiB is what this axis is really asking about.
    • 

  • Ops headcount — who runs it at 03:00? Milvus's three dependencies from Day 1 are three
more systems that a two-person team does not have the capacity to own.
    • 

  • Transactional-join need — do you need the vector search result joined to authoritative
policy or customer state in one consistent read? Postgres does this natively; a separate
vector store makes it two systems and a consistency problem you now own.
    • 

  • Self-host and data residency — is a managed service available to you at all? Day 4's
compliance angle makes this a hard constraint rather than a preference for many BFSI
workloads.
    • 



Writing them down with explicit weights is the discipline. The weights are where the
judgement lives, and leaving them implicit is how a comparison table smuggles in a
conclusion.


Example:


# Plain Python -- this one runs anywhere. The axes, weighted explicitly.
axes = {
    "corpus size":            0.30,
    "ops headcount":          0.30,
    "transactional joins":    0.25,
    "self-host / residency":  0.15,
}
assert abs(sum(axes.values()) - 1.0) < 1e-9, "weights must sum to 1"
for axis, w in axes.items():
    print(f"{axis:<24} {w:.2f}")

Concept 2 — Scoring the Three Candidates


Score each candidate 1 to 5 on each axis, multiply by the weights, and read the total. The
point of doing it numerically is not precision — it is that disagreements become locatable.
When two engineers disagree about the outcome, the matrix shows whether they disagree about a
score or about a weight, and those are very different arguments.


Example:


# Plain Python -- this one runs anywhere. Two weightings, same scores.
axes_a = {"corpus size":0.30, "ops headcount":0.30,
          "transactional joins":0.25, "self-host / residency":0.15}
axes_b = {"corpus size":0.50, "ops headcount":0.30,
          "transactional joins":0.05, "self-host / residency":0.15}
scores = {
 "pgvector":{"corpus size":2,"ops headcount":5,"transactional joins":5,"self-host / residency":5},
 "Milvus":  {"corpus size":5,"ops headcount":2,"transactional joins":1,"self-host / residency":4},
 "Qdrant":  {"corpus size":4,"ops headcount":4,"transactional joins":1,"self-host / residency":5},
}
def total(axes, c):
    return sum(scores[c][a] * w for a, w in axes.items())

for label, axes in (("A: small team, joins matter", axes_a),
                    ("B: corpus dominates, joins do not", axes_b)):
    t = {c: total(axes, c) for c in scores}
    print(label)
    for c in scores:
        print(f"   {c:<10} {t[c]:.2f}")
    print(f"   winner -> {max(t, key=t.get)}")
    print()

genuinely "stay where Week 02 left you". That is the most common correct answer, and the one
a vector-database comparison is least likely to give you.

Concept 3 — Migration Cost If the Choice Is Wrong


Every ADR should carry the cost of being wrong, because that cost is what determines how much
analysis is worth doing up front. For a vector store the migration has two components, and
they differ by two orders of magnitude.


Example:

print(f"  index build               : {n/index_build_per_sec/3600:8.1f} h")
print(f"  dual-write window         : the sum, "
      f"{n/embed_per_sec/3600 + n/index_build_per_sec/3600:.1f} h, plus verification")

print("If vectors are retained, re-embedding drops out:")
print(f"  index build only          : {n/index_build_per_sec/3600:8.1f} h")

The gap between 4.6 hours and 0.2 hours is the entire argument for one specific engineering

are trying to leave, you are re-running your embedding pipeline over the whole corpus.

comparison, which is why it belongs in the ADR as a mitigation rather than in a runbook as an
afterthought.

BFSI Reality Check — Day 5


Legacy angle: The decision is rarely made on a blank slate. There is an existing Postgres
that the core system already writes to, an existing Kafka owned by another team, and an
existing procurement relationship that makes one vendor dramatically easier to buy than
another. Those are real inputs, and an ADR that pretends the choice was made purely on
technical merit will not survive contact with the people who have to approve it.


Compliance angle: An ADR is a governance artifact, not an engineering note. Under EU AI
Act Article 11 documentation duties, the retrieval component of a high-risk system needs its
design decisions recorded with their rationale — which is exactly what the weighting in
Concept 2 provides, and exactly what a bare comparison table does not. Record the weights,
not just the winner.


What breaks in production: The decision is made once, correctly, for a 2M-vector corpus,
and never revisited. Three years later the corpus is 30M, the weights that produced the
answer no longer describe reality, and nobody re-runs the matrix because the ADR reads as
settled. Put the crossover number from the Concept 2 exercise into a monitored metric and the
ADR becomes reviewable rather than archaeological.




Architecture Decision — Week 03


Choosing between: pgvector, Milvus and Qdrant as the vector store for a BFSI retrieval
workload, scored on corpus size, ops headcount, transactional-join need, and
self-host/data-residency constraints.


Rule of thumb: stay on pgvector while the corpus fits comfortably in one machine's
memory with its index — in practice into the low millions of vectors — and especially where
the retrieval result must be joined transactionally to authoritative policy or customer
state, since that join is free in Postgres and becomes a distributed consistency problem the
moment the vectors live elsewhere. Move to Qdrant when filtering is the binding
constraint rather than raw scale: its filterable HNSW, payload indexes and cardinality-driven
planner solve the high-selectivity filtering problem directly, and it carries markedly less
operational surface than Milvus for a small team. Move to Milvus when the corpus genuinely
exceeds what one machine can hold — the 78.68 GiB single-replica figure from Day 2 is the
concrete form of this — and you have the platform headcount to run etcd, a log broker and
object storage as production systems, since those three dependencies, not Milvus itself, are
what the decision actually commits you to. Where data residency forbids a managed service,
score self-hosting operability as a hard constraint rather than a preference, because it
removes the escape hatch every other option quietly assumes. Above all, record the weights
alongside the choice: the Day 5 matrix produced pgvector as the winner at one weighting and
Qdrant at another from identical scores, so an ADR that states a winner without stating its
weights has documented a conclusion while omitting the entire argument.
