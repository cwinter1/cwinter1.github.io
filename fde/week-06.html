Concept 1 — Partition Count Is the Ceiling on Embedder Parallelism

A Kafka topic's partitions are the unit of parallelism for a consumer group: each partition is assigned to exactly one consumer in the group at a time. That means the number of partitions is a hard ceiling — adding an eleventh consumer to a ten-partition topic buys you nothing, because there is no eleventh partition to hand it.

For a claim-embedding pipeline this is not an abstract limit. If embedding one batch takes 800ms and each active consumer processes one batch at a time, the whole pipeline's throughput is active_consumers x (batch_size / embed_latency) — capped the moment active_consumers hits the partition count, no matter how many more consumer processes you add.

Example:

def assign_partitions(num_partitions, num_consumers):
    """Kafka's default range/round-robin style assignment: partitions split as
    evenly as possible, extra consumers beyond partition count sit idle."""
    assignment = {c: [] for c in range(num_consumers)}
    for p in range(num_partitions):
        assignment[p % num_consumers].append(p)
    return assignment

def throughput_records_per_sec(num_partitions, num_consumers, batch_size, embed_latency_s):
    """Each active consumer processes one batch at a time; idle consumers add nothing."""
    active_consumers = min(num_partitions, num_consumers)
    per_consumer_rps = batch_size / embed_latency_s
    return active_consumers * per_consumer_rps

for num_consumers in (4, 8, 12, 24):
    num_partitions = 12
    assignment = assign_partitions(num_partitions, num_consumers)
    idle = sum(1 for c, parts in assignment.items() if not parts)
    rps = throughput_records_per_sec(num_partitions, num_consumers, batch_size=50, embed_latency_s=0.8)
    print(f"consumers={num_consumers:>3}  partitions=12  idle_consumers={idle:>2}  "
          f"throughput={rps:8.1f} rec/s")

Concept 2 — Keying by claim_id Buys Per-Entity Ordering and Costs You Skew


Kafka guarantees order only within a partition. Keyed messages with the same key always
land on the same partition (the default partitioner hashes the key), so keying every
event for a claim by its claim_id guarantees that claim's own events arrive in order —
opened, then updated, then closed, never out of sequence. That guarantee is per-key, not
per-topic; two different claims' events can interleave freely across partitions.


The cost is that the same hash-to-one-partition property that buys ordering also means a
disproportionately busy key sends disproportionate volume to one partition, permanently.
Uniformly-distributed keys spread evenly by the law of large numbers; a small number of
unusually active claims do not average out, because every one of their events shares the
same fixed destination.


Example:


import hashlib
import random
from collections import Counter

def partition_for_key(key, num_partitions):
    """Stand-in for Kafka's default partitioner (murmur2 mod partition count,
    not in stdlib) -- same class of skew behaviour regardless of hash choice."""
    digest = hashlib.md5(key.encode()).digest()
    return int.from_bytes(digest[:4], "big") % num_partitions

num_partitions = 8
num_claims = 5_000
rng = random.Random(6)
claim_ids = [f"CLM-{i:07d}" for i in range(num_claims)]

# Every event for a claim carries the SAME key -> same partition every time.
uniform_events_per_claim = {c: rng.randint(1, 3) for c in claim_ids}

# 2% of claims (litigation, large commercial losses) generate 40x the typical
# event volume -- reopens, adjuster notes, subrogation updates.

skewed_events_per_claim = {
    c: rng.randint(60, 120) if c in hot_claims else rng.randint(1, 3)
    for c in claim_ids

def partition_event_totals(events_per_claim):
    totals = Counter()
    for claim_id, n_events in events_per_claim.items():
        totals[partition_for_key(claim_id, num_partitions)] += n_events
    return totals

Concept 3 — Redpanda: Raft Per Partition, No ZooKeeper, Same Client API


Redpanda is a Kafka-API-compatible broker written from scratch in C++, without
ZooKeeper and without a separate KRaft-style controller quorum. Each partition runs its
own Raft consensus group directly, and the broker speaks the same wire protocol Kafka
clients already use — a producer or consumer written against confluent_kafka (or any
other Kafka client library) does not know, or need to know, which broker it is talking
to.


What changes is entirely on the operations side: no ZooKeeper cluster to run and
patch, one binary instead of Kafka-plus-ZooKeeper-plus-(optionally)-Schema-Registry, and
a different set of tuning knobs at the broker/cluster layer. None of that touches the
producer/consumer configuration this week spends most of its time on — acks,
enable.idempotence, linger.ms, max.poll.interval.ms mean exactly the same thing
against either broker.

Concept 4 — Retention vs Log Compaction for an Embed Feed


A Kafka topic can be cleaned up two ways. Retention deletes records after a time or
size limit regardless of key — appropriate for an append-only audit feed where every
event matters and none should be silently collapsed. Compaction instead keeps only
the latest record per key forever (subject to a cleaner running periodically), discarding
every earlier value for that key.


A "current status of this claim" feed is exactly what compaction is for: a consumer
rebuilding "where does every claim currently stand" only ever needs the latest record per
claim_id, and replaying a compacted topic costs one pass over the number of distinct
keys, not the number of events ever written. An append-only "every status change that
ever happened" audit trail needs retention instead, because compaction would destroy the
history that trail exists to keep.


Example:


import random

def compact(events):
    """Log compaction: keep only the latest value per key. Mirrors what a
    compacted Kafka topic converges to after the cleaner runs (offsets are
    not preserved -- only the payload)."""
    latest = {}
    for key, value in events:
        latest[key] = value
    return list(latest.items())

rng = random.Random(11)
num_claims = 2_000
num_status_updates = 20_000
statuses = ["OPEN", "IN_REVIEW", "PENDING_DOCS", "APPROVED", "DENIED", "CLOSED"]
events = [(f"CLM-{rng.randrange(num_claims):06d}", rng.choice(statuses))
          for _ in range(num_status_updates)]

compacted = compact(events)
print(f"raw event log entries      : {len(events):>7,}")
print(f"compacted (latest per key) : {len(compacted):>7,}")
print(f"replay volume reduction    : {(1 - len(compacted) / len(events)) * 100:6.1f}%")
print(f"raw replay reads           : {len(events):>7,} records")
print(f"compacted replay reads     : {len(compacted):>7,} records")

BFSI Reality Check — Day 1


Legacy angle: The event that should trigger re-embedding — "this claim's adjuster
notes changed" — often has no native change feed on a legacy policy administration
system. It arrives as a nightly batch extract diffed against yesterday's extract, turned
into synthetic "claim updated" events after the fact. The partition-count and keying
decisions in this section assume a real-time source; plan for a batch-to-stream adapter
sitting in front of it instead.


Compliance angle: Keying by claim_id is also a data-minimization boundary. If the
same topic carries claims for multiple lines of business or multiple legal entities under
one insurance group, the partition assignment must not become a de facto way to infer
which entity a claim belongs to from which partition it lands on — keep that mapping out
of anything an external consumer group can observe.


What breaks in production: A well-meaning "let's add more consumers for
resilience" change adds consumers past the partition count. Nothing errors. The extra
consumers sit idle, throughput does not improve, and the on-call engineer spends an hour
looking for the bottleneck in the wrong place before checking partition count.

acks='all' is a durability guarantee: the write is acknowledged only once every
in-sync replica has it, so a broker failure after the ack cannot lose the record.
enable.idempotence=True is a completely separate no-duplicate-on-producer-retry
guarantee: the broker tracks a producer id plus per-partition sequence numbers, so if the
producer retries a send whose ack was lost in transit, the broker recognizes the retry
and discards the duplicate instead of writing it twice. Durability says nothing about
duplicates; dedup-on-retry says nothing about durability. Idempotence only means what it
claims under three preconditions: acks=all (the broker in fact rejects an idempotent
producer configured otherwise), retries > 0 (zero retries means there is nothing to
deduplicate), and max.in.flight.requests.per.connection <= 5 (the broker's
sequence-number tracking window is bounded).


The runnable version below is the config validator that enforces exactly those
preconditions, so the muddled combinations fail loudly instead of silently running with a
guarantee that was never actually in effect.


Example:


def validate_idempotent_producer_config(cfg):
    problems = []
    idempotent = cfg.get("enable.idempotence", False)
    acks = cfg.get("acks")
    retries = cfg.get("retries", 0)
    max_in_flight = cfg.get("max.in.flight.requests.per.connection", 5)

    if idempotent and acks != "all":
        problems.append("enable.idempotence=true requires acks='all'")
    if idempotent and retries == 0:
        problems.append("enable.idempotence=true with retries=0 is vacuous")
    if idempotent and max_in_flight > 5:
        problems.append(f"max.in.flight.requests.per.connection={max_in_flight} exceeds 5")
    if acks == "all" and not idempotent:
        problems.append("acks='all' without idempotence is durable but not dedup-safe")
    return problems

cfg = {"enable.idempotence": True, "acks": "all", "retries": 3,
       "max.in.flight.requests.per.connection": 5}
print(validate_idempotent_producer_config(cfg))

Concept 2 — linger.ms and batch.size Are the Throughput Dial


A producer does not send one network request per record. It buffers records per
partition into a batch and ships the batch when either linger.ms elapses since the
first record in it arrived, or the batch fills to batch.size bytes — whichever happens
first. linger.ms=0 (the default) still batches opportunistically under load, but adds
no deliberate delay; raising it trades a small amount of added latency for meaningfully
fewer, larger requests.


Example:


def requests_per_second(event_rate, linger_ms, batch_size, avg_record_bytes):
    time_trigger_batch = event_rate * (linger_ms / 1000)
    size_trigger_batch = batch_size / avg_record_bytes
    effective_batch = min(time_trigger_batch, size_trigger_batch) if time_trigger_batch > 0 else size_trigger_batch
    effective_batch = max(effective_batch, 1)
    return event_rate / effective_batch, effective_batch

avg_record_bytes = 512
batch_size = 16_384
for linger_ms in (0, 5, 20, 50, 100):

    print(f"linger.ms={linger_ms:>4}  eff.batch={eff_batch:>6.1f}  requests/sec={rps:>7.1f}")

Concept 3 — Schema Registry Under BACKWARD Compatibility


A schema registry (Confluent's, Apicurio's, or Redpanda's built-in one) enforces a
compatibility mode before it will register a new schema version. Under BACKWARD
compatibility — the usual default and the right one for an embed feed, since it protects
existing consumers reading new data — a consumer built against the new schema must be
able to read data written under the old schema. That constrains what a schema change
is allowed to do: adding a field is fine only if it has a default (an old record that
never had the field falls back to the default); adding a field with no default breaks
BACKWARD compatibility, because an old record genuinely has nothing there. Removing a
field is allowed (the new reader simply never looks for it). Changing a field's type is
a break unless the old and new types are on the registry's short list of promotable
pairs (e.g. int to long).


Example:


def check_backward_compatible(old_schema, new_schema):
    breaks = []
    old_fields = old_schema["fields"]
    new_fields = new_schema["fields"]
    for name, new_field in new_fields.items():
        if name not in old_fields:
            if new_field.get("default") is None and new_field.get("required", True):
                breaks.append(f"added required field '{name}' with no default")
        else:
            if old_fields[name]["type"] != new_field["type"]:
                breaks.append(f"changed type of '{name}': {old_fields[name]['type']} -> {new_field['type']}")
    return breaks

produce() is asynchronous: it appends to an internal buffer and returns immediately.
The delivery callback that confirms success or failure only fires when the library's
background thread actually sends the batch — which flush() forces, and a bare process
exit does not wait for. A process that produces records and exits without calling
flush() can lose everything still sitting in the buffer, with no error raised anywhere,
because from the buffer's point of view the write was never attempted.


Example:


class FakeProducer:
    """Models confluent_kafka.Producer's async buffering: produce() queues,
    only flush() drains it and fires delivery callbacks."""
    def __init__(self):
        self.queue = []
    def produce(self, value, on_delivery):
        self.queue.append((value, on_delivery))
    def flush(self, timeout=None):
        remaining = list(self.queue)
        self.queue.clear()
        for value, callback in remaining:
            if callback:
                callback(None, value)
        return len(remaining)

def run_producer_session(num_events, call_flush):
    producer = FakeProducer()
    delivered = []
    def on_delivery(err, msg):
        if err is None:
            delivered.append(msg)
    for i in range(num_events):
        producer.produce(f"claim-event-{i}", on_delivery=on_delivery)
    if call_flush:

Concept 1 — Commit After the Upsert, Not Before


An offset commit tells the broker "everything up to and including this offset has been
processed" — a promise the next consumer to take over this partition after a restart or
rebalance takes at face value: it resumes from committed_offset + 1. Whether that
promise is actually true depends entirely on when the commit happens relative to the
work.


enable.auto.commit=True commits on its own timer, based on what has been fetched,
with no knowledge of whether the corresponding vector-index upsert has actually
succeeded. A consumer typically fetches ahead of where it has finished processing —
that pipelining is normal and desirable — so an auto-commit can advance the committed
offset past work that has not actually landed in the index yet. If the process crashes
in that window, those records are skipped forever on restart: genuine data loss. A
manual commit() called only after a batch of upserts has actually succeeded can never
commit past real, completed work — but because it commits in batches rather than after
every single record, a crash between commits causes some already-upserted records to be
reprocessed: a duplicate, not a loss.


Example:

Concept 3 — Cooperative-Sticky Rebalance and max.poll.interval.ms


Two different timeouts guard consumer liveness, and conflating them is the single most
common cause of a mystery rebalance loop. session.timeout.ms is heartbeat
liveness: heartbeats are sent from a background thread independent of whatever the
application thread is doing, so it fires only when the process or its network is
genuinely gone — a slow embedding call does not stop heartbeats and does not trip this
timeout. max.poll.interval.ms is progress liveness on the application thread
itself: it fires when the consumer has not called poll() again within that window,
which is exactly what happens when a micro-batch of embedding-API calls takes too long
between polls. When it fires, the consumer proactively leaves the group, its partitions
get reassigned, and any offsets for the in-flight batch were never committed — so
another consumer re-reads them. Batch too large, interval exceeded, rebalance, work
redone, still too large, rebalance again: a loop with no error message that ever says
"your batch is too big".


partition.assignment.strategy=cooperative-sticky softens the damage a rebalance does,
whatever triggers it: the older "eager" strategies revoke every partition from every
consumer and reassign from scratch (stop-the-world), while cooperative-sticky revokes
and reassigns incrementally, letting unaffected consumers keep working through the
rebalance instead of all pausing at once.


Example:


def max_safe_records_per_poll(max_poll_interval_ms, per_record_embed_latency_ms, safety_factor=0.7):

Concept 4 — Consumer Lag Is the Pipeline's SLI


Consumer lag — how many records behind the latest offset a consumer group sits — is the
single most direct measure of whether an ingestion pipeline is keeping up. But the
absolute number alone cannot distinguish a pipeline that just absorbed a burst and is
draining normally from one that is steadily falling further behind: both can show the
identical lag value at the moment you check.


The number that actually tells you something is the derivative — lag's rate of
change between consecutive samples, sometimes called the burn rate. A negative burn
rate means the pipeline is catching up regardless of how high the absolute number is
right now; a positive and growing burn rate means it is falling behind and heading
toward an outage even if the current lag still looks survivable.


Example:


def burn_rate(lag_samples, interval_seconds):
    return [(lag_samples[i] - lag_samples[i - 1]) / interval_seconds
            for i in range(1, len(lag_samples))]

sample_interval_s = 60
recovering_samples = [70_000, 65_000, 59_000, 55_000, 50_000]
degrading_samples  = [30_000, 36_000, 41_000, 46_000, 50_000]

                       ("degrading  (was 30k)", degrading_samples)):
    rates = burn_rate(samples, sample_interval_s)
    print(f"{label}: current lag={samples[-1]}  latest burn rate={rates[-1]:+.1f} rec/s  "
          f"{'DEGRADING' if rates[-1] > 0 else 'draining'}")

Concept 1 — Size- and Time-Triggered Micro-Batching


Calling an embedding API once per record is wasteful — most embedding APIs charge a
fixed per-request overhead on top of the actual compute, and batching amortizes it. But
waiting to accumulate a full batch under low traffic adds latency nobody asked for. A
MicroBatcher flushes on whichever limit is hit first: max_size records buffered, or
max_age_ms since the oldest buffered record arrived — the same two-trigger pattern Day
2 used for producer batching, applied on the consuming side instead.


Example:


class MicroBatcher:
    def __init__(self, max_size, max_age_ms):
        self.max_size = max_size
        self.max_age_ms = max_age_ms
        self.buffer = []
        self.buffer_started_at = None

    def add(self, record, now):
        if not self.buffer:
            self.buffer_started_at = now
        self.buffer.append(record)
        if len(self.buffer) >= self.max_size:
            return "size"
        if (now - self.buffer_started_at) * 1000 >= self.max_age_ms:
            return "age"
        return None

    def flush(self):
        batch, self.buffer, self.buffer_started_at = self.buffer, [], None
        return batch

    [(f"CLM-{i:04d}", 0.15 + (i - 15) * 0.08) for i in range(15, 20)] +
    [(f"CLM-{i:04d}", 0.55 + (i - 20) * 0.01) for i in range(20, 40)]
)
batcher = MicroBatcher(max_size=10, max_age_ms=150)
for claim_id, t in arrivals:
    trigger = batcher.add(claim_id, now=t)
    if trigger:
        batch = batcher.flush()
        print(f"t={t:5.2f}s  flush trigger={trigger:<5}  batch_size={len(batch):>2}")

Concept 2 — Bounded Concurrency via a Semaphore


Sending every record in a micro-batch to the embedding API at once is not free
concurrency — it is an unbounded burst against a service that has its own rate limit,
and enough concurrent requests will get you throttled or worse. An asyncio.Semaphore
caps how many requests are in flight simultaneously without capping how many records
the batch contains; asyncio.gather still processes the whole batch, just never more
than the semaphore's limit at once.


Example:


import asyncio

async def embed_and_upsert(claim_id, semaphore, in_flight_counter, peak_tracker):
    async with semaphore:
        in_flight_counter[0] += 1
        peak_tracker[0] = max(peak_tracker[0], in_flight_counter[0])
        await asyncio.sleep(0.05)   # stand-in for an embedding API call
        in_flight_counter[0] -= 1
        return claim_id

async def run_batch(claim_ids, concurrency_limit):
    semaphore = asyncio.Semaphore(concurrency_limit)
    in_flight_counter, peak_tracker = [0], [0]
    results = await asyncio.gather(
        *(embed_and_upsert(cid, semaphore, in_flight_counter, peak_tracker) for cid in claim_ids)
    )
    return results, peak_tracker[0]

async def main():
    claim_ids = [f"CLM-{i:04d}" for i in range(50)]
    for limit in (5, 10, 50):
        results, peak = await run_batch(claim_ids, concurrency_limit=limit)
        assert peak <= limit
        print(f"concurrency_limit={limit:>3}  measured_peak_in_flight={peak:>3}  processed={len(results)}")

asyncio.run(main())

Concept 3 — Backpressure: Pause the Partition, Never Drop the Record

LOW_WATERMARK = 100

paused_partitions = set()

    global queue_depth
    queue_depth += len(records)
    if queue_depth >= HIGH_WATERMARK:
        tps = [TopicPartition(r.topic(), r.partition()) for r in records]
        consumer.pause(tps)
        paused_partitions.update((tp.topic, tp.partition) for tp in tps)

def on_queue_drained_to(new_depth):
    global queue_depth
    queue_depth = new_depth
    if queue_depth <= LOW_WATERMARK and paused_partitions:
        tps = [TopicPartition(topic, partition) for topic, partition in paused_partitions]
        consumer.resume(tps)
        paused_partitions.clear()

Concept 4 — Content-Hash Keys Make the Upsert Idempotent


Day 3 established that manual-commit-after-batch is at-least-once, not exactly-once: a
crash can cause some records to be reprocessed. The fix is not to chase exactly-once
delivery (expensive and, across a Kafka-to-vector-store boundary, not really available)
but to make redelivery harmless at the write itself. Deriving the vector store's point
id as a deterministic hash of (claim_id, text, model_id) means the same input always
produces the same id, so upserting it twice is a no-op from the reader's perspective —
at-least-once delivery becomes effectively-once in the index, even though Kafka itself
never stopped being at-least-once.


model_id has to be part of the hash, not an afterthought: if a model upgrade re-embeds
the same claim text, that is a genuinely different vector and needs a different point,
or the new embedding silently overwrites the old one under a shared id with no record
that a swap happened.


Example:


import hashlib

def point_id(claim_id, text, model_id):
    payload = f"{claim_id}|{text}|{model_id}".encode("utf-8")
    return hashlib.sha256(payload).hexdigest()

Concept 1 — Retry Topic With Backoff vs Blocking the Partition Head


Kafka processes each partition strictly in order. If a consumer retries a failed record
in a loop right where it sits — blocking the partition head — every good record behind
it in that same partition waits for the entire retry-then-fail sequence to finish, even
though none of them had anything to do with the failure. A retry topic breaks this
coupling: a failed record is republished to a separate topic (often several, one per
backoff tier) and the main partition's head moves on immediately, so good records are
never held hostage by one bad one.


The retry itself should back off exponentially with jitter — a fixed or unjittered delay
means every consumer that failed on the same broker blip retries in lockstep and
recreates the exact overload that caused the failure in the first place.


Example:


import random

def backoff_schedule(base_ms, max_ms, attempts, rng):
    return [rng.uniform(0, min(max_ms, base_ms * (2 ** attempt))) for attempt in range(attempts)]

rng = random.Random(42)
schedule = backoff_schedule(base_ms=200, max_ms=30_000, attempts=6, rng=rng)
print("retry delays (ms):", [round(d) for d in schedule])
print("cumulative wait before giving up (s):", round(sum(schedule) / 1000, 1))

def head_of_line_cost(num_records, poison_pill_index, retry_delays_ms):
    retry_total_ms = sum(retry_delays_ms)
    records_behind = num_records - poison_pill_index - 1
    return records_behind, records_behind * retry_total_ms

behind, extra_wait_ms = head_of_line_cost(200, 50, schedule)
print(f"good records delayed behind the poison pill: {behind}")
print(f"extra wait imposed on the partition's tail: {extra_wait_ms / 1000:.1f}s total")

Concept 2 — The DLQ Envelope Carries Offset, Headers and Error


A record that exhausts its retries needs to land somewhere a human or an automated
remediation job can act on it — and doing anything useful with it later (debug it,
replay it once the bug is fixed, or just count how many of a given error type occurred)
requires more than the raw payload. The envelope wrapping a dead-lettered record should
carry everything needed to find it again (original topic, partition, offset, key,
timestamp), everything the record's own metadata said (propagated headers), and the
failure itself (error type, message, attempt count, first-seen and failed-at
timestamps).


Example:


import json, datetime

def build_dlq_envelope(original_message, error, attempt_count, first_seen_at):
    return {
        "original_topic": original_message["topic"],
        "original_partition": original_message["partition"],
        "original_offset": original_message["offset"],
        "original_key": original_message["key"],
        "original_timestamp": original_message["timestamp"],
        "propagated_headers": original_message["headers"],
        "error_type": type(error).__name__,
        "error_message": str(error),
        "attempt_count": attempt_count,
        "first_seen_at": first_seen_at,
        "failed_at": datetime.datetime.now(datetime.timezone.utc).isoformat(),
    }

    "topic": "claim-events", "partition": 3, "offset": 918273, "key": "CLM-0004821",

Concept 3 — Poison-Pill Isolation After N Attempts


Not every failure deserves a retry. A transient error — a timeout, a rate limit, a
temporarily unavailable dependency — is worth retrying, because the same input might
succeed a moment later. A terminal error — a schema validation failure, a malformed
payload that will never parse — will fail identically on every retry, and retrying it
only delays the DLQ landing while wasting attempts. The routing decision reads an
attempt counter carried in the record's own headers (set and incremented by the retry
topic infrastructure itself) alongside the error's classification, and sends the record
to the retry topic while attempts remain and the error is retryable, or straight to the
DLQ otherwise.


Example:


RETRYABLE_ERRORS = {"ConnectionError", "TimeoutError", "RateLimitError", "ServiceUnavailable"}
TERMINAL_ERRORS = {"ValueError", "SchemaValidationError", "PermissionError"}
MAX_ATTEMPTS = 3

def route_after_failure(error_type, attempt_count):
    if error_type in TERMINAL_ERRORS:
        return "dlq", f"{error_type} is not retryable -- straight to DLQ"
    if error_type in RETRYABLE_ERRORS:
        if attempt_count < MAX_ATTEMPTS:
            return "retry_topic", f"attempt {attempt_count + 1} of {MAX_ATTEMPTS}"
        return "dlq", f"exhausted {MAX_ATTEMPTS} attempts -- poison pill"
    return "dlq", f"unclassified error type '{error_type}' -- treat as terminal by default"

cases = [
    {"error_type": "TimeoutError", "attempt_count": 0},
    {"error_type": "TimeoutError", "attempt_count": 3},
    {"error_type": "ValueError", "attempt_count": 0},
    {"error_type": "WeirdCustomError", "attempt_count": 0},
]
for case in cases:
    destination, reason = route_after_failure(**case)
    print(f"error={case['error_type']:<18} attempt={case['attempt_count']}  -> {destination:<11}  ({reason})")

Once a bug is fixed (say, a bad deploy that truncated adjuster-note text before
embedding), the records affected while it was live need to be reprocessed. assign()
plus seek() gives manual control over exactly which offsets to re-read, independent of
the consumer group's normal committed-offset bookkeeping. Doing this safely has exactly
one precondition, and it is the same one Day 4 built: the upsert must be idempotent. If
it is, replaying a range that includes already-good records is a harmless no-op for
those records; if it is not, the replay creates duplicate points for everything in the
range, good and bad alike.


Example:


def build_replay_plan(partition_offset_ranges, idempotent_upsert):
    plan = []
    total = 0
    for partition, (start, end) in partition_offset_ranges.items():
        count = end - start + 1
        total += count
        plan.append({"partition": partition, "seek_to_offset": start,
                     "replay_through_offset": end, "expected_record_count": count})
    precondition = (
        "safe: upserts are keyed by a content hash, so re-processing already-good "
        "records is a no-op" if idempotent_upsert else
        "UNSAFE: upserts are not idempotent -- replaying will create duplicates"
    )
    return {"plan": plan, "total_expected_records": total,
            "safe_to_replay": idempotent_upsert, "precondition": precondition}

affected_ranges = {0: (140_200, 141_875), 1: (139_950, 141_600), 2: (140_500, 142_003)}
result = build_replay_plan(affected_ranges, idempotent_upsert=True)
for entry in result["plan"]:
    print(f"partition {entry['partition']}: seek to {entry['seek_to_offset']}, "
          f"replay through {entry['replay_through_offset']} "
          f"({entry['expected_record_count']} records)")
print(f"total expected records: {result['total_expected_records']}")
print(f"precondition: {result['precondition']}")

BFSI Reality Check — Day 5


Legacy angle: A poison pill is frequently not a malformed message at all but a
perfectly valid one that encodes a legacy quirk nobody modeled — a claim amount field
carrying a mainframe-era sentinel value like 999999999 for "unknown," which a schema
validator correctly rejects as out of range. The DLQ envelope's job in that case is
surfacing the pattern fast enough that someone adds a translation rule, not endlessly
retrying a record that will never parse.


Compliance angle: A DLQ is itself a store of claim data sitting outside the normal
access-control and retention policy applied to the main topic, and it is easy to forget
that when it was created purely as an engineering safety net. Whatever retention and
access rules apply to claim-events apply to its DLQ too — a common gap an audit finds
is a DLQ topic with no retention policy at all, quietly accumulating claim payloads
forever.


What breaks in production: A replay run against a pipeline nobody confirmed was
idempotent, because the person running it assumed "we fixed the bug, so replaying is
obviously fine." The replay succeeds, throughput looks normal, and the actual damage —
duplicated points inflating a downstream similarity count — surfaces days later in a
completely different investigation.




Architecture Decision — Week 06


Choosing between: embed-on-consume, one record at a time, per message vs.
micro-batched embedding with paused-partition backpressure (Day 4's MicroBatcher plus
consumer.pause()/resume()).


Rule of thumb: use single-record-per-message embedding while the embedding API's
rate limit and per-call latency comfortably clear the event rate with room to spare, and
while the pipeline's lag SLO has no real burn-rate risk at current volume — the simpler
code path is worth keeping until it measurably cannot keep up. Move to micro-batching
plus backpressure once any of three things happen: the embedding API bills or throttles
per request rather than per token, so amortizing overhead across a batch materially
changes cost or throughput; max.poll.interval.ms starts constraining how much work a
single poll cycle can safely do, which micro-batching lets you control independently of
raw event rate; or lag's burn rate goes positive under normal (non-incident) load,
meaning per-record processing genuinely cannot clear the volume regardless of tuning.
Having adopted micro-batching, the watermark thresholds in the backpressure controller
are not a set-once decision — they have to move with max.poll.records and the measured
embedding latency, the same way ef_search in Week 01 turned out to be a monitored
production knob rather than a launch-day constant.
