Concept 1 — Retrieval Failure vs. Generation Failure

A RAG pipeline has exactly two places to go wrong, and they call for completely different fixes: the retriever can fail to surface the document that actually answers the question (no metric downstream of retrieval can recover from this — the generator never saw the right text), or retrieval can succeed while the generator still produces a wrong or unsupported answer from a context that DID contain the right material. Picking a metric before knowing which failure mode you are chasing is backwards — context_recall/context_precision (Day 2) diagnose the first, faithfulness/answer_relevancy (Day 2) diagnose the second, and conflating them (blaming the generator for a retrieval miss, or vice versa) sends an engineering fix to the wrong stage of the pipeline. This reuses Week 24's retrieve() and CORPUS unchanged as the retrieval stage under test.

Example:

import math

    return text.lower().replace(",", " ").replace(".", " ").split()

    "liability", "bodily", "injury", "property", "umbrella", "excess", "earthquake",
}

def bow(text):
    toks = tokenize(text)
    return {t: toks.count(t) for t in toks if t in VOCAB}

def cosine(v1, v2):
    common = set(v1) & set(v2)
    dot = sum(v1[t] * v2[t] for t in common)
    n1 = math.sqrt(sum(x * x for x in v1.values())) or 1.0
    n2 = math.sqrt(sum(x * x for x in v2.values())) or 1.0
    return dot / (n1 * n2)

Concept 2 — Golden Set Records: Question, Ground Truth, Reference Contexts


A golden-set record is not just a question-and-answer pair — it also needs to name WHICH
document(s) the answer should come from, so a later regression check can tell "the answer
changed because retrieval changed" apart from "the answer changed because the generator
changed" even before running the full pipeline. Storing this as a dataclass (not a loose
dict, per this track's Week 1 Royal Road habit carried through the whole Curriculum/
track) makes a record's required fields explicit and lets a linter catch a record built
without one.

Concept 3 — Annotation Guidelines for Policy-Language Ambiguity


Insurance policy text is written with deliberate hedges ("may", "at the company's
discretion", "subject to underwriting") that a single annotator can read past without
noticing — and a golden-set record built from a hedge, presented as a flat fact, teaches the
evaluation harness to penalize an honestly-hedged model answer as if it were wrong. A cheap
guardrail: scan every candidate ground-truth answer for known ambiguity markers before it
enters the golden set, and route any hit to a second annotator rather than accepting the
first annotator's read silently.


Example:


AMBIGUITY_MARKERS = {
    "may", "at the company's discretion", "subject to underwriting", "generally",
    "typically", "in most cases", "reasonable", "as applicable", "without limitation",
}

def flag_ambiguous_ground_truth(ground_truth_answer):
    lowered = ground_truth_answer.lower()
    hits = sorted(m for m in AMBIGUITY_MARKERS if m in lowered)
    return hits

review_queue = []
candidates = [
    "The grace period is 31 days from the due date.",
    "Claims may be approved at the company's discretion depending on the circumstances.",
    "Mold remediation is covered up to a sublimit, subject to underwriting review of the source of water damage.",
]
for text in candidates:
    hits = flag_ambiguous_ground_truth(text)
    status = "NEEDS SECOND ANNOTATOR" if hits else "single-annotator OK"
    print(f"{status:<24} markers={hits}  text={text[:50]!r}")
    if hits:
        review_queue.append(text)

print(f"flagged for review: {len(review_queue)}/{len(candidates)}")

Concept 4 — A 50-Question Synthetic Seed Set With No Real PII


A golden set needs enough coverage to catch a regression in any one part of the pipeline,
but hand-writing 50 distinct questions is slow and error-prone to keep unique. Generating
them from a small template x topic grid is faster, guarantees no duplicate question text,
and — because every question is built from a fixed vocabulary describing generic policy
topics rather than any real customer's data — never has a chance to contain PII in the
first place. The PII check below runs anyway, not because template generation could
plausibly leak anything, but because it is the same check a REAL ingested question set
would need, and running it here proves the check itself works before it is trusted on real
input.


Example:


import re

DOC_IDS = ["DOC-1", "DOC-2", "DOC-3", "DOC-4", "DOC-5", "DOC-6", "DOC-7", "DOC-8",
           "DOC-9", "DOC-10", "DOC-A", "DOC-B", "DOC-C"]

TEMPLATES = [
    "What does {topic} cover?",
    "How long is the {topic} period?",
    "Is {topic} covered under my policy?",
    "What is excluded from {topic}?",
]
TOPICS = [
    "the free look", "reinstatement", "beneficiary changes", "deductible waivers",
    "auto glass repair", "roadside assistance", "rental reimbursement",
    "sump pump backup", "wind and hail roof", "mold remediation",
    "umbrella liability", "fire and smoke damage", "the grace period",
]

def build_seed_set(n):
    records = []
    i = 0
    while len(records) < n:
        template = TEMPLATES[i % len(TEMPLATES)]
        topic = TOPICS[i % len(TOPICS)]
        doc_id = DOC_IDS[i % len(DOC_IDS)]
        records.append({
            "id": f"Q-{i + 1:03d}",
            "question": template.format(topic=topic),
            "source_doc": doc_id,
        })
        i += 1
    return records

PII_PATTERNS = [
    re.compile(r"\b\d{3}-\d{2}-\d{4}\b"),        # SSN-shaped
    re.compile(r"\b\d{9,16}\b"),                  # account/card-number-shaped
    re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b"),  # email
]

def contains_pii(text):
    return any(p.search(text) for p in PII_PATTERNS)

seed_set = build_seed_set(50)
print(f"seed set size: {len(seed_set)}")
print(f"unique question texts: {len(set(r['question'] for r in seed_set))}")
pii_hits = [r for r in seed_set if contains_pii(r['question'])]
print(f"records containing PII-shaped text: {len(pii_hits)}")
print("sample:", seed_set[0], seed_set[-1])

Concept 1 — What Faithfulness, Answer Relevancy, Context Precision, and Context Recall Each Measure


ragas's four RAG metrics split cleanly along Concept 1's retrieval/generation line from
Day 1. context_precision and context_recall grade retrieval: precision asks what
fraction of what was retrieved was actually relevant (noise in the retrieved set costs
precision even if the right document is also there), recall asks whether everything the
ground-truth answer needed was retrieved at all (a real answer can require content spread
across more than one document). faithfulness and answer_relevancy grade generation once
retrieval is fixed: faithfulness asks what fraction of the generated answer's own content is
actually supported by the retrieved context (an unfaithful answer is a hallucination even if
it happens to be correct), answer_relevancy asks what fraction of the question the answer
actually addresses (a faithful answer can still dodge the question that was asked).


Example:


# Reusing retrieve, doc_lookup, CORPUS from Day 1 Concept 1

STOPWORDS = {"the", "a", "an", "is", "was", "were", "are", "of", "to", "in",
             "on", "for", "and", "or", "by", "with", "this", "that", "what",
             "how", "did", "do", "does", "it", "its", "my", "your"}

def content_words(text):
    words = text.lower().replace(",", "").replace(".", "").replace("?", "").split()
    return {w for w in words if w not in STOPWORDS}

def faithfulness_score(answer, context):
    a_words = content_words(answer)
    c_words = content_words(context)
    if not a_words:
        return 0.0
    return len(a_words & c_words) / len(a_words)

def answer_relevancy_score(question, answer):
    q_words = content_words(question)
    a_words = content_words(answer)
    if not q_words:
        return 0.0
    return len(q_words & a_words) / len(q_words)

def context_precision(retrieved_ids, relevant_ids):
    if not retrieved_ids:
        return 0.0
    relevant_set = set(relevant_ids)
    hits = sum(1 for cid in retrieved_ids if cid in relevant_set)
    return hits / len(retrieved_ids)

def context_recall(ground_truth_answer, retrieved_context_texts):
    gt_words = content_words(ground_truth_answer)
    if not gt_words:
        return 0.0
    covered = set()
    for text in retrieved_context_texts:
        covered |= content_words(text)
    return len(gt_words & covered) / len(gt_words)

question = "How many days do I have to reinstate a lapsed policy?"
relevant_id = "DOC-2"
ground_truth = "90 days from the date of lapse, with all past-due premium paid."
answer = "You have 90 days from the date of lapse to reinstate, as long as past-due premium is paid."

retrieved = [d for d, _ in retrieve(question, k=3)]
retrieved_texts = [doc_lookup[d] for d in retrieved]

f = faithfulness_score(answer, " ".join(retrieved_texts))
r = answer_relevancy_score(question, answer)
cp = context_precision(retrieved, [relevant_id])
cr = context_recall(ground_truth, retrieved_texts)

print(f"retrieved: {retrieved}")
print(f"faithfulness={f:.2f}  answer_relevancy={r:.2f}  context_precision={cp:.2f}  context_recall={cr:.2f}")

Concept 3 — Choosing and Pinning the Judge LLM


Every one of Concept 1-2's metrics needs a judge to decide "does this content word count as
support" in the real ragas library — a real LLM call, not the word-overlap stand-in used
here. Which model, which version, and at what decoding temperature all change the score a
real judge returns for the identical input, so a judge configuration that is not written
down and versioned makes a metric drift unexplainably between two runs that were both,
supposedly, evaluating "the same" pipeline. Pinning it as a validated config — not a loose
string passed at the call site — makes drift traceable: a score change either comes from the
pipeline changing or from the judge config changing, and the config's own version field says
which.


Example:


from dataclasses import dataclass

APPROVED_JUDGE_MODELS = {"claude-sonnet-5", "gpt-4o-mini", "claude-haiku-4"}

@dataclass
class JudgeConfig:
    model: str
    version: str
    temperature: float
    pinned_at: str  # ISO date the config was frozen, for the audit trail

class JudgeConfigError(ValueError):
    pass

def validate_judge_config(config):
    if config.model not in APPROVED_JUDGE_MODELS:
        raise JudgeConfigError(f"model {config.model!r} is not on the approved judge list")
    if config.temperature != 0:
        raise JudgeConfigError(
            f"temperature={config.temperature} is non-deterministic; judge configs must pin temperature=0"
        )
    if not config.version:
        raise JudgeConfigError("model version must be pinned, not left as 'latest'")
    return True

]

        validate_judge_config(cfg)

Concept 4 — Quantifying Metric Variance Across Repeated Identical Runs


A judge LLM called at a nonzero decoding temperature scores the exact same
(question, answer, context) triple slightly differently on repeated calls, purely from
sampling noise — a well-documented property of temperature-based decoding, not something
this sandbox needs a live API to demonstrate the SHAPE of. simulated_judge_score below
stands in for that real behavior deterministically: a temperature-scaled random offset,
seeded so this block's own output is reproducible on every run. Comparing temperature=0
against a nonzero temperature shows exactly why Concept 3 pins temperature=0 for a judge
whose scores need to be trusted run to run.


Example:


import random
import statistics

def simulated_judge_score(base_score, temperature, rng):
    noise = rng.uniform(-temperature, temperature)
    return max(0.0, min(1.0, round(base_score + noise, 4)))

def run_n_times(base_score, temperature, n, seed):
    rng = random.Random(seed)
    return [simulated_judge_score(base_score, temperature, rng) for _ in range(n)]

base_score = 0.75
for temperature in [0.0, 0.15]:
    scores = run_n_times(base_score, temperature, n=8, seed=42)
    spread = round(max(scores) - min(scores), 4)
    stdev = round(statistics.pstdev(scores), 4)
    print(f"temperature={temperature}  scores={scores}")
    print(f"  spread={spread}  stdev={stdev}")

Concept 1 — The RAG Triad: Groundedness, Context Relevance, Answer Relevance


TruLens frames RAG evaluation as a triangle with the question, the retrieved context, and
the generated answer at its three corners, and a score for each of the three EDGES:
groundedness checks the answer-to-context edge (is the answer actually supported by what was
retrieved — the same axis ragas's faithfulness measures, under TruLens's own name),
context relevance checks the question-to-context edge (did retrieval fetch something that
actually relates to the question — the same axis as context_precision), and answer
relevance checks the question-to-answer edge (does the answer actually address the question
— the same axis as answer_relevancy). Different library, same triangle.


Example:


# Reusing retrieve, doc_lookup from Day 1 Concept 1

STOPWORDS = {"the", "a", "an", "is", "was", "were", "are", "of", "to", "in",
             "on", "for", "and", "or", "by", "with", "this", "that", "what",
             "how", "did", "do", "does", "it", "its", "my", "your"}

def content_words(text):
    words = text.lower().replace(",", "").replace(".", "").replace("?", "").split()
    return {w for w in words if w not in STOPWORDS}

def groundedness_score(answer, context):
    a_words = content_words(answer)
    c_words = content_words(context)
    if not a_words:
        return 0.0
    return round(len(a_words & c_words) / len(a_words), 4)

def context_relevance_score(question, context):
    q_words = content_words(question)
    c_words = content_words(context)
    if not q_words:
        return 0.0
    return round(len(q_words & c_words) / len(q_words), 4)

def answer_relevance_score(question, answer):
    q_words = content_words(question)
    a_words = content_words(answer)
    if not q_words:
        return 0.0
    return round(len(q_words & a_words) / len(q_words), 4)

question = "How many days do I have to reinstate a lapsed policy?"
context = doc_lookup["DOC-2"]
answer = "You have 90 days from the date of lapse to reinstate, as long as past-due premium is paid."

g = groundedness_score(answer, context)
cr = context_relevance_score(question, context)
ar = answer_relevance_score(question, answer)
print(f"groundedness={g}  context_relevance={cr}  answer_relevance={ar}")

Concept 1 — Rubric-Based Scoring vs. a Vague Quality Ask


"Rate this answer 1-5" gives a judge nothing to anchor a score to beyond its own guess at
what "good" means, and a real judge under that prompt reliably falls back to surface signals
like length and topical overlap — this concept's deterministic stand-in makes that failure
mode concrete rather than asserting it. An explicit rubric names what each score tier
actually requires, so a judge working from it has something checkable to point to, not a
vibe.


Example:


from pydantic import BaseModel, Field

class JudgeScore(BaseModel):
    score: int = Field(ge=1, le=5)
    reasoning: str

RUBRIC = """
Score 5: directly and completely answers the question with the specific figure or fact asked for.
Score 4: answers the question correctly but omits a minor supporting detail.
Score 3: partially relevant but missing the specific figure or fact asked for.
Score 2: on-topic but does not actually answer what was asked.
Score 1: does not address the question at all.
"""

def judge_vague(question, answer):
    # Deterministic stand-in for a real judge call with a vague ask ("rate this answer").
    # Anchored only to "does it look long and on-topic," never checking for the SPECIFIC
    # fact the question needed.
    overlap = len(set(question.lower().split()) & set(answer.lower().split()))
    if len(answer) > 60 and overlap >= 1:
        return {"score": 5, "reasoning": "Looks thorough and on-topic."}
    return {"score": 2, "reasoning": "Seems short or off-topic."}

def judge_with_rubric(question, answer, required_fact):
    # Deterministic stand-in for a real judge call given RUBRIC as its system prompt --
    # explicitly checks for the fact the rubric's score-5 tier requires.
    if required_fact.lower() in answer.lower():
        return {"score": 5, "reasoning": f"States the required fact: {required_fact!r}."}
    overlap = len(set(question.lower().split()) & set(answer.lower().split()))
    if overlap >= 2:
        return {"score": 3, "reasoning": f"On-topic but missing the required fact: {required_fact!r}."}
    return {"score": 1, "reasoning": "Does not address the question."}

question = "How many days do I have to reinstate a lapsed policy?"
long_but_wrong_answer = "Reinstating a lapsed policy is an important process that policyholders should understand well before it becomes necessary to use it."
correct_answer = "You have 90 days from the date of lapse to reinstate."
required_fact = "90 days"

for label, answer in [("long_but_wrong", long_but_wrong_answer), ("correct", correct_answer)]:
    vague = JudgeScore(**judge_vague(question, answer))
    rubric = JudgeScore(**judge_with_rubric(question, answer, required_fact))
    print(f"{label}: vague_score={vague.score}  rubric_score={rubric.score}  rubric_reasoning={rubric.reasoning}")

Concept 2 — Position Bias and Verbosity Bias in Pairwise Judging


A pairwise judge ("which of these two answers is better") has two well-documented failure
modes distinct from a single-answer rubric judge's: verbosity bias (a longer answer scores
higher independent of correctness) and position bias (on a genuine tie, whichever answer was
shown FIRST tends to win). Both are real, published findings about LLM judges, not invented
for this lesson — the stand-in below encodes them explicitly so the debiasing technique in
the second half is provably doing something.


Example:


def naive_pairwise_judge(answer_first, answer_second):
    # Deterministic stand-in encoding both documented biases: verbosity (longer wins) and,
    # on a tie, position (first-shown wins).
    len_first, len_second = len(answer_first), len(answer_second)
    if len_first > len_second:
        return "first"
    if len_second > len_first:
        return "second"
    return "first"

answer_a = "Coverage stays active for 31 days past the due date."
answer_b = "Your policy will not lapse for nonpayment until 31 days have passed since the due date, giving you time to catch up."

print("order (A, B):", naive_pairwise_judge(answer_a, answer_b))
print("order (B, A):", naive_pairwise_judge(answer_b, answer_a))

identical_a = "Coverage is active for 31 days."
identical_b = "Coverage is active for 31 days."
print("identical, order (A, B):", naive_pairwise_judge(identical_a, identical_b))
print("identical, order (B, A):", naive_pairwise_judge(identical_b, identical_a))

def position_bias_corrected_judge(answer_a, answer_b):
    """Run the judge in BOTH orders and only declare a winner if both orders agree --
    the standard debiasing technique for a pairwise judge's position bias."""
    verdict_forward = naive_pairwise_judge(answer_a, answer_b)
    verdict_backward = naive_pairwise_judge(answer_b, answer_a)
    forward_winner = "a" if verdict_forward == "first" else "b"
    backward_winner = "b" if verdict_backward == "first" else "a"
    if forward_winner == backward_winner:
        return forward_winner
    return "tie (position-dependent disagreement)"

print("corrected(A vs B, different lengths):", position_bias_corrected_judge(answer_a, answer_b))
print("corrected(A vs A, identical):", position_bias_corrected_judge(identical_a, identical_b))

Concept 3 — Agreement With Human Labels via Cohen's Kappa


Raw agreement rate ("the judge matched the human 80% of the time") overstates how good a
judge is whenever the underlying label set is imbalanced — a judge that always guesses the
majority label gets a high raw agreement rate for free, without ever actually discriminating
between cases. Cohen's kappa corrects for exactly this: it measures agreement ABOVE what each
rater's own label distribution would produce by chance alone.


Example:


from collections import Counter

def cohens_kappa(judge_labels, human_labels):
    n = len(judge_labels)
    assert n == len(human_labels) and n > 0
    observed_agreement = sum(1 for j, h in zip(judge_labels, human_labels) if j == h) / n

    judge_counts = Counter(judge_labels)
    human_counts = Counter(human_labels)
    labels = set(judge_counts) | set(human_counts)
    expected_agreement = sum(
        (judge_counts.get(l, 0) / n) * (human_counts.get(l, 0) / n) for l in labels
    )

    if expected_agreement == 1.0:
        return 1.0
    return round((observed_agreement - expected_agreement) / (1 - expected_agreement), 4)

judge_labels = ["PASS", "PASS", "FAIL", "PASS", "FAIL", "PASS", "PASS", "FAIL", "PASS", "FAIL"]
human_labels = ["PASS", "PASS", "FAIL", "FAIL", "FAIL", "PASS", "PASS", "FAIL", "PASS", "PASS"]

agreement_rate = sum(1 for j, h in zip(judge_labels, human_labels) if j == h) / len(judge_labels)
kappa = cohens_kappa(judge_labels, human_labels)
print(f"raw agreement: {agreement_rate:.2f}  Cohen's kappa: {kappa}")

always_pass_labels = ["PASS"] * 10
always_pass_agreement = sum(1 for j, h in zip(always_pass_labels, human_labels) if j == h) / len(human_labels)
always_pass_kappa = cohens_kappa(always_pass_labels, human_labels)
print(f"always-PASS judge: raw agreement: {always_pass_agreement:.2f}  Cohen's kappa: {always_pass_kappa}")

Concept 4 — Cheap-Judge Screening With Strong-Judge Escalation on Disagreement


Running an expensive, high-quality judge on every single evaluation case is wasteful when
most cases are unambiguous — a cheap, fast judge can screen the easy cases (a clean pass with
the exact fact present) and only escalate the genuinely uncertain ones to a slower, more
capable judge, which is the same cheap-then-strong cascade Week 23 built for cost routing,
applied here to judging instead of generation.


Example:


def cheap_judge(question, answer, required_fact):
    # Fast, cheap: pure keyword presence, no nuance.
    return 5 if required_fact.lower() in answer.lower() else 1

def strong_judge(question, answer, required_fact):
    # Slower, more expensive: partial credit for on-topic-but-incomplete answers.
    if required_fact.lower() in answer.lower():
        return 5
    overlap = len(set(question.lower().split()) & set(answer.lower().split()))
    if overlap >= 2:
        return 3
    return 1

UNCERTAIN_BAND = {1, 2, 3, 4}  # anything short of a clean 5 gets a second opinion

def cascaded_judge(cases):
    results = []
    escalated = 0
    for question, answer, required_fact in cases:
        cheap_score = cheap_judge(question, answer, required_fact)
        if cheap_score in UNCERTAIN_BAND:
            escalated += 1
            final_score = strong_judge(question, answer, required_fact)
            source = "strong (escalated)"
        else:
            final_score = cheap_score
            source = "cheap"
        results.append((question[:35], final_score, source))
    return results, escalated

cases = [
    ("How many days to reinstate a lapsed policy?", "You have 90 days from the date of lapse.", "90 days"),
    ("How many days to reinstate a lapsed policy?", "Reinstatement is possible if you contact us promptly.", "90 days"),
    ("Is my deductible waived for a first claim?", "Yes, the deductible is waived for the first claim filed.", "waived"),
]
results, escalated = cascaded_judge(cases)
for question, score, source in results:
    print(f"{question:<38} score={score}  source={source}")
print(f"escalated to strong judge: {escalated}/{len(cases)}")

BFSI Reality Check — Day 4


Legacy angle: a cheap-judge/strong-judge cascade (Concept 4) is the same tiered-review
pattern a claims department already runs on human adjusters — most claims get a fast,
junior-adjuster pass, and only the genuinely ambiguous ones escalate to a senior reviewer;
applying it to LLM judging is a direct transfer, not a new idea borrowed from ML research.


Compliance angle: Concept 3's kappa-against-human-labels check is the actual evidence an
internal model-risk review wants before an automated judge is allowed to gate a deployment
unsupervised — "the judge agrees with our human reviewers at kappa=0.58, measured on N
labeled cases" is auditable; "we eyeballed a few outputs and they looked fine" is not.


What breaks in production: Concept 1's vague-ask failure mode is the most common real
mistake in a first eval harness — "rate this response 1-10" is the intuitive first thing to
write, and it is precisely the prompt shape that silently rewards a long, confident,
wrong answer over a short, correct one; catching this requires actually checking judge output
against known-correct cases (as this concept did), not just eyeballing that the judge
"seems reasonable."

Concept 1 — pytest-Parameterized Eval Cases Over the Golden Set


pytest.mark.parametrize turns each golden-set record from Day 1 into its own test case,
run and reported individually — a failure names exactly which question regressed, not just
"the eval suite failed." The test module below is written to a real temp file and run with
a real pytest.main() call, not simulated; a small pytest plugin collects pass/fail
counts programmatically instead of parsing pytest's own printed summary line, since that
line's timing text ("3 passed in 0.05s") genuinely varies run to run and would make this
block's output undocumentable.


Example:


import os, tempfile, textwrap, io, contextlib
import pytest

# The test module below embeds retrieve()/CORPUS directly (a condensed copy of Day 1
# Concept 1's own logic) rather than importing them from an outer module -- this file has
# no installable package structure of its own for a real `from myapp.retrieval import
# retrieve` to target, so the self-contained version is the one that is honestly runnable
# as a genuine, standalone pytest.main() call, not simulated.
RETRIEVAL_SOURCE = textwrap.dedent("""
    import math

    def tokenize(text):
        return text.lower().replace(",", " ").replace(".", " ").split()

    VOCAB = {"reinstate", "reinstatement", "lapse", "lapsed", "days", "grace", "period",
             "premium", "mold", "water", "damage", "covered", "beneficiary", "claim"}

    def bow(text):
        toks = tokenize(text)
        return {t: toks.count(t) for t in toks if t in VOCAB}

    def cosine(v1, v2):
        common = set(v1) & set(v2)
        dot = sum(v1[t] * v2[t] for t in common)
        n1 = math.sqrt(sum(x * x for x in v1.values())) or 1.0
        n2 = math.sqrt(sum(x * x for x in v2.values())) or 1.0
        return dot / (n1 * n2)

    CORPUS = [
        ("DOC-2", "Reinstatement after lapse: a lapsed policy can be reinstated within 90 days of lapse if all past-due premium is paid, without new underwriting."),
        ("DOC-5", "Grace period for premium payment: coverage stays active for 31 days past the due date before the policy lapses for nonpayment."),
        ("DOC-8", "Mold remediation: mold caused by a covered water damage event is covered up to a sublimit; mold from long term neglect is excluded."),
        ("DOC-3", "Beneficiary changes: the policyholder may change the named beneficiary at any time before a claim is filed, using the standard change-of-beneficiary form."),
    ]

    def retrieve(query_text, k=3, corpus=CORPUS):
        qv = bow(query_text)
        scored = [(doc_id, cosine(qv, bow(text))) for doc_id, text in corpus]
        scored.sort(key=lambda x: -x[1])
        return scored[:k]
""")

TEST_BODY = textwrap.dedent("""
    GOLDEN_CASES = [
        ("How many days do I have to reinstate a lapsed policy?", "DOC-2"),
        ("Is mold damage covered under my property policy?", "DOC-8"),
        ("What is the grace period for premium payment?", "DOC-5"),
    ]

    import pytest

    @pytest.mark.parametrize("question,relevant_doc_id", GOLDEN_CASES)
    def test_retrieval_finds_relevant_doc(question, relevant_doc_id):
        retrieved_ids = [d for d, _ in retrieve(question, k=3)]
        assert relevant_doc_id in retrieved_ids
""")

test_dir = tempfile.mkdtemp()
test_path = os.path.join(test_dir, "test_golden_retrieval.py")
with open(test_path, "w") as f:

class ResultCollector:
    def __init__(self):
        self.passed = 0
        self.failed = 0

    def pytest_runtest_logreport(self, report):
        if report.when != "call":
            return
        if report.passed:
            self.passed += 1
        elif report.failed:
            self.failed += 1

collector = ResultCollector()
with contextlib.redirect_stdout(io.StringIO()):
    # --import-mode=importlib: without it, pytest identifies a collected test file by
    # basename alone, and a SECOND generated file also named test_golden_retrieval.py

    # raises a real "import file mismatch" collection error against the first one still
    # cached in sys.modules -- confirmed directly, not a hypothetical.
    exit_code = pytest.main(["-q", "--import-mode=importlib", test_path], plugins=[collector])

print(f"passed: {collector.passed}  failed: {collector.failed}  exit_code: {exit_code}")

Concept 2 — Deterministic Seeding and Cached Retrieval Fixtures


A regression suite re-runs the exact same golden questions on every CI trigger, often many
times a day — without caching, that is redundant retrieval work for input that never
changes, and worse, it opens the door to a score drifting between two runs of "the same"
suite purely from something incidental (a smoke test sampling a different random subset
each time) rather than a real system change. functools.lru_cache makes repeat lookups of
the identical question free, and a seeded random.Random makes a sampled subset of the
golden set identical across runs — together, a score can only move because the pipeline
under test moved, which is the entire point of a regression check.


Example:


from functools import lru_cache
import random

# Reusing retrieve from Day 1 Concept 1, aliased here so the cache wrapper's own name
# stays free for the cached version
_raw_retrieve = retrieve

call_count = {"n": 0}

@lru_cache(maxsize=256)
def cached_retrieve(question, k=3):
    call_count["n"] += 1
    return tuple(_raw_retrieve(question, k=k))

q = "How many days do I have to reinstate a lapsed policy?"
r1 = cached_retrieve(q, k=3)
r2 = cached_retrieve(q, k=3)
r3 = cached_retrieve(q, k=3)
print(f"result 1 == result 2 == result 3: {r1 == r2 == r3}")
print(f"underlying retrieve() actually called: {call_count['n']} time(s) for 3 lookups")

other_q = "Is mold damage covered under my property policy?"
for _ in range(5):
    cached_retrieve(other_q, k=3)
print(f"underlying retrieve() called: {call_count['n']} time(s) total (2 distinct questions, 8 lookups)")

def sample_golden_subset(golden_questions, n, seed):
    rng = random.Random(seed)
    return sorted(rng.sample(golden_questions, n))

golden_pool = [
    "How many days do I have to reinstate a lapsed policy?",

    "What is the grace period for premium payment?",
    "Is my deductible waived if this is my first claim?",

sample_1 = sample_golden_subset(golden_pool, n=3, seed=7)
sample_2 = sample_golden_subset(golden_pool, n=3, seed=7)
print(f"same seed -> same smoke-test sample: {sample_1 == sample_2}")
print(sample_1)

Concept 3 — A JSON Scorecard Artifact Written Per Run


A score printed to a terminal and never saved is worthless to next week's run — a scorecard
written as a real JSON file on disk is a durable artifact another process (a CI step, a
dashboard, Day 5's own config-driven gate in Concept 4) can read back later, and the same
shape every run produces makes runs directly comparable. run_id here is derived
deterministically from the run's own question set (a hash, not a wall-clock timestamp) so
this block's output stays reproducible under --repeat.


Example:


import json, os, hashlib, tempfile

# Reusing retrieve, doc_lookup from Day 1 Concept 1, faithfulness_score from Day 2 Concept 1

def build_scorecard(cases):
    rows = []
    for question, relevant_id, answer in cases:
        retrieved = [d for d, _ in retrieve(question, k=3)]
        context = doc_lookup[retrieved[0]] if retrieved else ""
        rows.append({
            "question": question,
            "retrieved_top": retrieved[0] if retrieved else None,
            "relevant_doc_id": relevant_id,
            "retrieval_correct": relevant_id in retrieved,
            "faithfulness": round(faithfulness_score(answer, context), 4),
        })
    run_key = "|".join(r["question"] for r in rows)
    run_id = hashlib.sha256(run_key.encode()).hexdigest()[:12]
    return {"run_id": run_id, "case_count": len(rows), "cases": rows}

cases = [
    ("How many days do I have to reinstate a lapsed policy?", "DOC-2",

Concept 4 — Thresholds and Metric Weights in a Version-Controlled Config File


Hard-coding "faithfulness must be above 0.3" inside the test function that checks it makes
the threshold invisible to anyone reviewing the eval policy itself, and any change to it is
indistinguishable from a change to the test logic in a code review's diff. Pulling weights
and thresholds into a small, version-controlled config file — genuinely written to and read
back from disk here, the same as Week_23_D5's budget/threshold config pattern — makes the
eval POLICY a reviewable, diffable artifact separate from the harness code that enforces it.


Example:


import json, os, tempfile

EVAL_CONFIG = {
    "weights": {"faithfulness": 0.4, "context_precision": 0.3, "context_recall": 0.3},
    "thresholds": {"composite_min": 0.55, "faithfulness_min": 0.3},
}

config_path = os.path.join(tempfile.gettempdir(), "w26_eval_config.json")
with open(config_path, "w") as f:
    json.dump(EVAL_CONFIG, f, indent=2, sort_keys=True)

with open(config_path) as f:
    config = json.load(f)

class EvalGateError(ValueError):
    pass

def composite_score(metrics, config):
    weights = config["weights"]
    return round(sum(metrics[m] * w for m, w in weights.items()), 4)

def evaluate_gate(metrics, config):
    composite = composite_score(metrics, config)
    faithfulness_floor = config["thresholds"]["faithfulness_min"]
    if metrics["faithfulness"] < faithfulness_floor:
        raise EvalGateError(
            f"faithfulness {metrics['faithfulness']} below floor {faithfulness_floor}"
        )
    composite_floor = config["thresholds"]["composite_min"]
    if composite < composite_floor:
        raise EvalGateError(f"composite {composite} below floor {composite_floor}")
    return composite

healthy_metrics = {"faithfulness": 0.62, "context_precision": 0.55, "context_recall": 0.71}
regressed_metrics = {"faithfulness": 0.20, "context_precision": 0.55, "context_recall": 0.71}

for label, metrics in [("healthy", healthy_metrics), ("regressed", regressed_metrics)]:
    try:
        score = evaluate_gate(metrics, config)
        print(f"{label}: PASS  composite={score}")
    except EvalGateError as e:
        print(f"{label}: FAIL  {e}")

composite is even checked — evaluate_gate deliberately checks the individual floor first,
because a bad enough score on ONE metric should fail the gate outright even if the other two
metrics are strong enough to pull a blended composite number above its own threshold.

BFSI Reality Check — Day 5


Legacy angle: the same config-driven gate pattern (Concept 4) is what should sit in
front of any legacy-sourced pipeline change too, not just an LLM's — a schema-drift fix in
Week 18's catalog code deserves the identical "does this regress the numbers we already
trust" gate this week built for RAG, not a special exemption because the change touches old
infrastructure instead of a model.


Compliance angle: the JSON scorecard (Concept 3) plus the config file (Concept 4)
together ARE the audit trail a model-risk review asks for: every run's actual scores,
against a dated, version-controlled statement of what "pass" meant at the time that run
happened — reconstructing either one after the fact from memory or a Slack thread is not an
acceptable substitute.


What breaks in production: a harness that only ever gets run manually, by hand, before
a release is not a regression check, it is a one-time spot-check with extra steps — the
whole value of Concept 1's pytest shape is that it plugs into the exact same CI trigger
every other test in the repo already uses, which is where Week 27 picks this up next.




Architecture Decision — Week 26


Choosing between: hand-rolled, word-overlap metric functions (this week's Day 1-2/5
default, genuinely portable and dependency-free) vs. ragas's real, LLM-judged metrics
(the industry-standard library, but confirmed unable to import in this specific environment
because of a real dependency conflict with langchain 1.4.1) vs. TruLens's
instrumentation-plus-dashboard approach (genuinely working here, real per-record
drill-down and a persistent query-able database, at the cost of wiring an actual LangChain
chain through a real recorder).


Rule of thumb: default to the hand-rolled metric for anything that has to run
everywhere, cheaply, on every commit — Day 5's pytest suite, Day 1's golden-set validation,
any check that needs to be fast and free of a live LLM call. Move to ragas (once its
own dependency stack is reconciled with whatever else a given deployment needs — the
conflict found this week is specific to this sandbox's exact langchain pin, not a
permanent property of the library) when a team needs the industry-standard, LLM-judged
metrics for a periodic, budgeted evaluation run, not every commit — the same
cheap-then-strong logic Day 4's judge cascade already argued for judging individually applies
at the metric-library level too. Move to TruLens specifically when per-record
drill-down and a persistent, query-able history of every eval run (Day 3 Concept 4) matter
more than the metric computation itself — a team debugging WHY a score dropped needs exactly
what TruChain's recorded Record objects give them, which a bare metric number never will.


The actual failure case for any of the three, proven across this week rather than assumed: a
metric — hand-rolled, ragas, or TruLens — is only as trustworthy as the golden set it is
measured against (Day 1), the judge configuration behind it if an LLM is involved (Day 2
Concept 3, Day 4), and the gate that decides what a regression actually is (Day 5 Concept 4).
Picking the "best" library and skipping those three is how a team ships an evaluation
harness that LOOKS rigorous and catches nothing — this week's real, repeated gotchas
(ragas's import conflict, TruLens's TP.submit bug and singleton TruSession, a vague
judge prompt scoring a wrong answer higher than a right one) are each exactly the kind of
thing a harness with the discipline this week built — golden-set quality checks, judge
variance measurement, human-agreement kappa, and a version-controlled gate — is designed to
survive discovering, rather than being invalidated by.
