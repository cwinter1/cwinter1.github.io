Concept 1 — Similarity Search Is a Matrix Multiply

A vector search is not a lookup. There is no key to match on. You have a query vector and a pile of stored vectors, and you score the query against every stored vector, then keep the best few.

For cosine similarity the score between query q and stored vector v is dot(q, v) / (||q|| * ||v||). Run that over every row of a matrix and you have brute-force k-nearest-neighbour search. Vectorised, the whole scoring pass is one matrix-vector product — which is why NumPy does this far faster than a Python loop even though the asymptotic cost is identical.

Data engineering analogy: this is a full table scan with a computed column in the ORDER BY. No index is involved yet. That framing matters, because every later week is about building the index that lets you stop scanning.

Example:

import numpy as np

claim_notes = [
    "Water damage to kitchen ceiling from upstairs pipe burst",
    "Rear-end collision at intersection, minor bumper damage",
    "Theft of laptop and jewelry from vehicle",
]
# Stand-in embeddings. A real system gets these from an embedding model.
rng = np.random.default_rng(0)
vectors = rng.normal(size=(3, 8))
query = rng.normal(size=8)

# Vectorised cosine: one matrix-vector product, then divide by the norms.
scores = (vectors @ query) / (np.linalg.norm(vectors, axis=1) * np.linalg.norm(query))
for i, s in enumerate(scores):
    print(f"{i}  {s: .4f}  {claim_notes[i]}")

environments. First, the gap is far smaller than the "vectorise everything" folklore

interpreter overhead, not the arithmetic. Second, that discarded first call matters: on a
cold kernel the same measurement came out at 352 ms for the loop against 2342 ms
vectorised, i.e. the vectorised version measured 6x slower, because the BLAS library
pays a one-time dynamic-architecture dispatch cost on its first big call. If you skip the
warm-up you will measure that startup cost and conclude the wrong thing. This is a general
benchmarking hazard, not a NumPy quirk, and Day 5 returns to it.




Concept 2 — Top-k Without a Full Sort


Sorting every score to take the top 5 is wasted work: np.argsort is O(n log n) over the
whole array when you only need the k best. np.argpartition is O(n) — it partially orders
the array so that position k splits "at least as good" from "worse", without ordering
either side. You then sort only those k.


At n = 3 this is irrelevant. At n = 10 million it is the difference between sorting ten
million floats per query and touching each one once.


Example:


import numpy as np

rng = np.random.default_rng(1)
scores = rng.normal(size=1_000_000)
k = 5

# Partition puts the k largest anywhere in the last k slots, unordered.
top_k_unordered = np.argpartition(scores, -k)[-k:]
# Then order just those k.
top_k = top_k_unordered[np.argsort(-scores[top_k_unordered])]

print("indices:", top_k)
print("scores :", np.round(scores[top_k], 4))

Concept 3 — The Cost Model That Forces an Index


Brute-force search costs O(n · d) multiply-adds per query: one pass over n vectors, d
dimensions each. Put real numbers in it.


A bank with ten million historical transaction memos, embedded at 1024 dimensions, needs
about 1.024e10 multiply-adds for a single query. That is not a rounding error you can
optimise away with better Python — it is roughly a second of pure arithmetic per query on
a single core, before you have touched the network or the database.


The exactness you buy with that cost is real, though, and worth naming: brute force
returns the true nearest neighbours, always. That is an audit property, not a performance
one, and it is occasionally the reason to keep it.


Example:


n, d = 10_000_000, 1024
mults = n * d
bytes_f32 = n * d * 4

print(f"multiply-adds per query : {mults:.3e}")
print(f"corpus size (float32)   : {bytes_f32 / 1024**3:.1f} GiB")
print(f"corpus size (float16)   : {bytes_f32 / 2 / 1024**3:.1f} GiB")

BFSI Reality Check — Day 1


Legacy angle: The ten-million-memo corpus in Concept 3 does not arrive as a tidy
Parquet file. It arrives as a nightly fixed-width extract off the core banking platform,
and the memo field is a 40-character truncated column that has been overloaded for two
decades. Sizing your index against the row count is easy; discovering the text is
truncated, uppercase and full of branch-specific abbreviations is the real Week 1 of a
real engagement.


Compliance angle: Exact brute-force search has one property an approximate index does
not: it is reproducible and explainable without qualification. If a regulator asks why a
particular historical claim was surfaced as similar, "we compared against every record and
these scored highest" is a complete answer. Keep that in mind before assuming the fastest
option is automatically the right one for a regulated decision path.


What breaks in production: Loading the whole corpus into a NumPy array works on your
laptop with a sample and dies on the real volume. A 10M x 1024 float32 matrix is about 39
GiB resident — more RAM than most on-prem application servers are given. The failure is
not slow search; it is the process being killed during load.

Concept 1 — Three Metrics and What Each Measures


Three operators dominate vector search, and vector databases expose all three:


    

  • Cosine similarity measures the angle between vectors and ignores their length.
Higher is more similar, bounded in [-1, 1].
    • 

  • Euclidean (L2) distance measures straight-line distance and is sensitive to length.
Lower is more similar, bounded in [0, inf).
    • 

  • Inner product (dot product) is unbounded and rewards both alignment and magnitude.
    • 



For text embeddings, cosine is the usual default, because the length of an embedding
vector often varies with incidental things — document length, model quirks — rather than
with meaning. But "usual default" is not "always correct", which Concept 3 gets to.


Example:


import numpy as np

rng = np.random.default_rng(2)
v = rng.normal(size=(4, 8))
q = rng.normal(size=8)

cos = (v @ q) / (np.linalg.norm(v, axis=1) * np.linalg.norm(q))
l2 = np.linalg.norm(v - q, axis=1)
ip = v @ q

for i in range(4):
    print(f"{i}  cos={cos[i]: .4f}  l2={l2[i]: .4f}  ip={ip[i]: .4f}")
print("best by cosine:", int(np.argmax(cos)))
print("best by l2    :", int(np.argmin(l2)))
print("best by ip    :", int(np.argmax(ip)))

Concept 2 — Normalization Collapses the Difference


Here is the fact that resolves most of the metric debate. For unit-length vectors:


||a - b||^2 = 2 - 2 * cos(a, b)

Squared L2 distance is a strictly decreasing function of cosine similarity. That means for
normalized vectors, cosine and L2 produce identical rankings. Not similar rankings —
identical. The same holds for inner product, since with ||a|| = ||b|| = 1 the inner
product is the cosine.


This matters practically because most production embedding models emit L2-normalized
vectors by default. So the metric argument you will read online is largely moot for the
models you will actually use, and the real decision becomes a cost question: cosine
requires computing norms per comparison, inner product does not. That is why vector
databases document inner product as the faster choice for pre-normalized data.


Example:


import numpy as np

rng = np.random.default_rng(3)
v = rng.normal(size=(6, 8))
q = rng.normal(size=8)
v = v / np.linalg.norm(v, axis=1, keepdims=True)   # normalize
q = q / np.linalg.norm(q)

cos_rank = np.argsort(-(v @ q))
l2_rank = np.argsort(np.linalg.norm(v - q, axis=1))

print("cosine ranking:", cos_rank.tolist())
print("l2 ranking    :", l2_rank.tolist())
print("identical     :", cos_rank.tolist() == l2_rank.tolist())

Concept 3 — Match the Metric to the Model, Not to Taste


The metric is not a free choice. An embedding model is trained with a particular similarity
function in its objective, and its vector space is shaped around that function. Using a
different metric at query time is not guaranteed to be wrong, but it is unvalidated —
you are measuring the space in a way its training never optimised for.


The practical rule: read the model card, use the metric the model documents, and normalize
if the model expects normalized input. Then keep the choice in configuration, not scattered
across call sites, because changing it later means rebuilding every index that was built
under the old operator class.


Example:


# The choice belongs in one config object, not inline at each call site.
INDEX_CONFIG = {
    "model_id": "example-embedding-model-v2",
    "dim": 1024,
    "normalize": True,          # per the model card
    "metric": "inner_product",  # valid because vectors are pre-normalized
}

def score(vectors, query, cfg=INDEX_CONFIG):
    if cfg["normalize"]:
        return vectors @ query          # cosine, since both sides are unit length
    norms = __import__("numpy").linalg.norm(vectors, axis=1)
    return (vectors @ query) / (norms * __import__("numpy").linalg.norm(query))

print(INDEX_CONFIG["metric"], "with normalize =", INDEX_CONFIG["normalize"])

Legacy angle: Claim notes off a legacy core are wildly uneven in length: a 12-character

Compliance angle: Changing the metric changes which records are retrieved, which
changes what a model sees, which under EU AI Act Article 11 documentation duties is a
change worth recording. Treat the metric as a versioned property of the index, not a
tuning knob someone can adjust in a console.


What breaks in production: Mixing normalized and unnormalized vectors in one
collection. It fails silently — no error, just quietly wrong rankings for the subset that
was written under the other convention. This is why normalize belongs in the same config
object as model_id and dim.

Concept 1 — Storage Is the First Real Constraint


Before latency, before recall, there is RAM. Most vector indexes want to be resident in
memory, and the arithmetic is unforgiving:


bytes = n_vectors x dimensions x bytes_per_component

One million vectors at 1024 dimensions in float32 is about 4.1 GB (3.8 GiB) of raw vectors
— before the index structure, which adds its own overhead on top. Halving to float16 halves
that, at some accuracy cost. This single calculation decides more architectures than any
benchmark does.


Example:


def corpus_bytes(n, dim, bytes_per=4):
    return n * dim * bytes_per

for n in (100_000, 1_000_000, 10_000_000):
    f32 = corpus_bytes(n, 1024, 4)
    f16 = corpus_bytes(n, 1024, 2)
    print(f"{n:>10,} vectors  float32={f32/1024**3:6.2f} GiB  float16={f16/1024**3:6.2f} GiB")

Concept 2 — Distances Concentrate as Dimension Grows


In high dimensions, the distances from a query to all points in a random cloud become
increasingly similar to one another. The ratio between the nearest and farthest distance
tends toward 1. This is the practical face of the "curse of dimensionality", and it has a
direct consequence: the contrast your search relies on gets weaker as d grows, all else
equal.


Real embeddings are not uniform random clouds — they have structure, which is precisely why
search works at all at 768 or 1536 dimensions. But the effect is real enough that it
explains why naive high-dimensional indexing degrades, and why measuring recall on your own
data matters more than trusting a dimension count.


Example:


import numpy as np

rng = np.random.default_rng(4)
for d in (2, 16, 128, 1024):
    pts = rng.normal(size=(2000, d))
    q = rng.normal(size=d)
    dists = np.linalg.norm(pts - q, axis=1)
    print(f"d={d:>5}  min={dists.min():8.3f}  max={dists.max():8.3f}  "
          f"max/min={dists.max()/dists.min():.3f}")

0.05, falling toward the baseline as noise grows.


That two-way comparison is the actual lesson, and it is easy to get backwards. Structure
alone does not restore contrast — a query landing nowhere near any cluster sees a
tightly-concentrated wall of distances regardless of how well-clustered the data is. What
restores contrast is structure plus a query that lands inside it. That is exactly the
real case: an embedded query about water damage lands near the water-damage cluster, which
is why search works on real embeddings at 1024 dimensions and does not work on uniform
noise.




Concept 3 — Reducing Dimensions Moves Recall


Cutting dimensions is tempting: it shrinks storage and speeds every comparison. It also
changes the geometry your recall depends on, and the loss is not uniform — it usually hurts
hardest on the near-duplicate pairs you most wanted to find.


The rule is not "never reduce" but "never reduce blind". Any dimension reduction, whether
PCA, a smaller model, or a model's own Matryoshka-style truncation, is a change that has
to be measured on your own query set against the full-dimension baseline, exactly like an
index parameter change.


Example:


import numpy as np

rng = np.random.default_rng(5)
full = rng.normal(size=(500, 256))
full /= np.linalg.norm(full, axis=1, keepdims=True)
q = full[0]

# Truncate to the first 64 dims and re-normalize -- the cheapest possible reduction.
trunc = full[:, :64]
trunc = trunc / np.linalg.norm(trunc, axis=1, keepdims=True)

top_full = np.argsort(-(full @ q))[:10]
top_trunc = np.argsort(-(trunc @ q[:64] / np.linalg.norm(q[:64])))[:10]
overlap = len(set(top_full.tolist()) & set(top_trunc.tolist()))
print(f"top-10 overlap after 4x truncation: {overlap}/10")

usable. The transferable lesson is the method — sweep and measure against a full-dimension
baseline — not this particular curve.

remain in-country and on-premises, so the storage math has to close on hardware you
actually control.


What breaks in production: Someone swaps in a model with a different dimension and the
index silently accepts vectors of the wrong width, or rejects them at write time deep in a
batch job at 02:00. Assert dimension at the ingestion boundary, not at the database.

Concept 1 — A Layered Proximity Graph


HNSW (Hierarchical Navigable Small World) is the index behind most production vector
databases. The structure: every vector is a node in a graph, connected to some of its
near neighbours. Nodes are assigned to layers with exponentially decreasing probability, so
the top layer is very sparse and the bottom layer contains everything.


The sparse upper layers act as long-range links across the space; the dense bottom layer
gives fine-grained local resolution. If you know skip lists, the layer assignment is the
same idea applied to a graph rather than a linked list.


Malkov and Yashunin's original paper characterises the search as scaling logarithmically
with the number of elements. That is the property that makes it worth building.


Example:


import numpy as np

# Layer assignment: geometric, controlled by mL. Most nodes land only on layer 0.
rng = np.random.default_rng(6)
mL = 1 / np.log(16)          # the usual 1/ln(M) choice
levels = np.floor(-np.log(rng.random(100_000)) * mL).astype(int)

for lvl in range(levels.max() + 1):
    count = int((levels == lvl).sum())
    print(f"layer {lvl}: {count:>7,} nodes ({count/len(levels)*100:6.3f}%)")

Concept 2 — Greedy Descent Is the Whole Search


Query time is simple to describe. Start at a fixed entry point in the top layer. Move
greedily to whichever neighbour is closer to the query. When no neighbour improves, drop to
the next layer down and repeat. At the bottom layer, instead of keeping just the single
best, keep a dynamic candidate list of size ef and return the best k from it.


That ef parameter (ef_search at query time) is the recall dial: larger means more
candidates explored, better recall, more latency. It must be at least k.


Example:


import numpy as np

def greedy_step(points, neighbours, current, query):
    """One greedy hop: move to the closest neighbour, or stay if none is better."""
    best, best_d = current, np.linalg.norm(points[current] - query)
    for nb in neighbours[current]:
        d = np.linalg.norm(points[nb] - query)
        if d < best_d:
            best, best_d = nb, d
    return best, best_d

rng = np.random.default_rng(7)
points = rng.normal(size=(20, 2))
neighbours = {i: np.argsort(np.linalg.norm(points - points[i], axis=1))[1:4].tolist()
              for i in range(20)}
query = rng.normal(size=2)

cur = 0
for hop in range(10):
    nxt, d = greedy_step(points, neighbours, cur, query)
    print(f"hop {hop}: node {cur} -> {nxt}  dist={d:.4f}")
    if nxt == cur:
        print("no improving neighbour; stopped")
        break
    cur = nxt

Concept 3 — Where Approximation Loses the True Neighbour


Greedy descent can get stuck. If the true nearest neighbour is not reachable through a
chain of strictly-improving hops from where you started, you will not find it. That is the
whole source of HNSW's recall loss, and it explains the shape of the queries that fail:


    

  • Queries landing in sparse regions of the space, where local connectivity is poor.
    • 

  • True neighbours that are isolated — connected to their own cluster but weakly linked to
where the search entered.
    • 

  • Anything reachable only through a temporarily worse hop, which greedy search refuses.
    • 



Raising ef_search mitigates this by keeping more candidates in flight rather than
committing to the single best at each step. It reduces the failure rate; it does not
eliminate it.


One clarification worth holding onto, because it is commonly muddled: HNSW's logarithmic
scaling is a property of this graph-descent design. IVF-family indexes — covered
alongside HNSW in Week 04 — use a completely different cluster-then-probe approach with
different scaling behaviour. They are separate algorithm families, not two settings of one
knob.


Example:


import numpy as np

rng = np.random.default_rng(8)
points = rng.normal(size=(200, 4))
neighbours = {i: np.argsort(np.linalg.norm(points - points[i], axis=1))[1:6].tolist()
              for i in range(200)}

def greedy(entry, query):
    cur = entry
    while True:
        cand = min(neighbours[cur], key=lambda n: np.linalg.norm(points[n] - query))
        if np.linalg.norm(points[cand] - query) >= np.linalg.norm(points[cur] - query):
            return cur
        cur = cand

misses = 0
trials = 200
for t in range(trials):
    q = rng.normal(size=4)
    true_nn = int(np.argmin(np.linalg.norm(points - q, axis=1)))
    if greedy(entry=0, query=q) != true_nn:
        misses += 1
print(f"greedy-from-fixed-entry missed the true NN on {misses}/{trials} queries")

Do not read that 131/200 as HNSW's real miss rate. This toy deliberately strips out the

index with those restored reaches well over 90% recall at sane ef_search values. What
the toy isolates is the failure mechanism, not the failure rate.




BFSI Reality Check — Day 4


Legacy angle: HNSW builds are expensive and single-shot: changing M means rebuilding
the index, not reconfiguring it. On-prem, that rebuild competes for the same machine as the
nightly batch. The build window, not the build time, is usually the binding constraint.


Compliance angle: An approximate index means the answer to "did you consider every
record?" is formally no. For a screening or monitoring control where completeness is the
point — sanctions screening being the obvious one — that answer may be unacceptable, and an
exact pass is required regardless of cost. Know which of your use cases are in that
category before choosing an index.


What breaks in production: ef_search left at a library default that was tuned for a
benchmark, not your corpus. Nothing errors. Recall is simply lower than anyone believes,
and nobody finds out until someone checks a result by hand.

Concept 1 — Recall@k Against Brute-Force Ground Truth


You cannot tune what you have not measured, and for approximate search the measurement is
recall@k: of the k true nearest neighbours, how many did the index actually return?


The ground truth comes from brute force. That is the one place the expensive exact search
earns its cost unambiguously — run it once, offline, over a fixed query set, and keep the
results as the reference every index configuration is scored against.


Example:


import numpy as np

def recall_at_k(approx_ids, true_ids, k):
    """Fraction of the true top-k that appear anywhere in the approximate top-k."""
    return len(set(approx_ids[:k]) & set(true_ids[:k])) / k

true_ids = [12, 7, 44, 3, 91]
approx_ids = [12, 44, 58, 3, 7]
print("recall@5:", recall_at_k(approx_ids, true_ids, 5))
print("recall@3:", recall_at_k(approx_ids, true_ids, 3))

Concept 2 — Report Percentiles, Never the Mean


Mean latency hides exactly the behaviour that matters. Vector search latency is
right-skewed: most queries are fast, a minority traverse far more of the graph. A p99 that
is ten times the p50 is normal, and it is the p99 that decides whether an interactive
application feels broken.


Report p50, p95 and p99. Discard warm-up runs — the first queries after an index loads pay
page-cache and allocation costs that are not representative. And keep the query workload
fixed, because comparing two configurations on two different query sets measures nothing.


Example:


import numpy as np, time

def measure(fn, queries, warmup=10):
    for q in queries[:warmup]:      # warm-up, results discarded
        fn(q)
    lat = []
    for q in queries[warmup:]:
        t0 = time.perf_counter()
        fn(q)
        lat.append((time.perf_counter() - t0) * 1000)
    lat = np.array(lat)
    return {
        "p50_ms": float(np.percentile(lat, 50)),
        "p95_ms": float(np.percentile(lat, 95)),
        "p99_ms": float(np.percentile(lat, 99)),
        "mean_ms": float(lat.mean()),
        "n": len(lat),
    }

rng = np.random.default_rng(9)
corpus = rng.normal(size=(20_000, 128))
queries = rng.normal(size=(200, 128))
search = lambda q: np.argpartition(-(corpus @ q), 10)[:10]
print(measure(search, queries))

Concept 3 — A Benchmark Harness You Can Rerun


A benchmark is only useful if a future you can rerun it unchanged. That means the query
set, the corpus, the ground truth and the config are all fixed artifacts, and the output is
a structured record rather than console output someone screenshots.


The output you want per configuration: recall@k, p50/p95/p99 latency, index build time and
resident memory. Build time and memory belong in the same record as recall, because a
configuration that wins on recall and takes eleven hours to build is not actually the
winner.


Example:


import json, platform, datetime

def benchmark_record(config, recall, latency, build_s, rss_mb):
    return {
        "timestamp": datetime.datetime.now(datetime.timezone.utc).isoformat(),
        "host": platform.node(),
        "config": config,                 # every index parameter, no defaults implied
        "recall_at_10": recall,
        "latency_ms": latency,            # the p50/p95/p99 dict from Concept 2
        "build_seconds": build_s,
        "resident_mb": rss_mb,
    }

rec = benchmark_record(
    config={"index": "hnsw", "m": 16, "ef_construction": 200, "ef_search": 64},
    recall=0.94,
    latency={"p50_ms": 1.8, "p95_ms": 6.1, "p99_ms": 11.4},
    build_s=412.0,
    rss_mb=5120,
)
print(json.dumps(rec, indent=2))

BFSI Reality Check — Day 5


Legacy angle: Benchmarking on a shared on-prem host means the nightly batch is your
noisy neighbour. A p99 measured at 21:00 and one measured at 02:00 can differ by an order
of magnitude for reasons that have nothing to do with your index. Record the wall-clock
window in the benchmark record.


Compliance angle: EU AI Act Article 15 expects declared accuracy metrics for high-risk
systems. Recall@k measured against an exact baseline is precisely the kind of declared,
reproducible metric that supports such a claim — provided the harness is versioned and the
result is an artifact, not a screenshot in a slide deck.


What breaks in production: Recall is measured once, at launch, and never again. The
corpus grows, its distribution shifts, and the ef_search that gave 94% recall on 200,000
vectors quietly gives far less on two million. Recall is a monitored metric, not a
launch-day certificate.




Architecture Decision — Week 01


Choosing between: exact brute-force k-NN vs. an approximate nearest-neighbour index
(the HNSW or IVF families).


Rule of thumb: use exact brute force while the corpus is small enough that a full scan
fits the latency budget — in practice up to roughly the low hundreds of thousands of
vectors on a single node — or whenever completeness is a control requirement rather than a
preference, sanctions and screening paths being the clearest example. Move to an ANN index
when scan latency breaches the budget, the corpus outgrows a single machine's memory, or
query volume makes per-query CPU the dominant cost. Having moved, treat recall@k as a
monitored production metric rather than a one-time acceptance test, because the point at
which an ANN configuration stops being good enough is a moving target set by corpus growth,
not a fixed property of the index.
