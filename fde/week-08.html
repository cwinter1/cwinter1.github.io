Weeks 01 through 07 assumed the input to a pipeline was already a clean vector or a well-formed database row. Real BFSI documents rarely arrive that way. A claim form is a scanned fax with a ruled table on it; a loan application is a multi-column PDF where the borrower's name sits in one column and the co-borrower's sits in the other, printed on the same line. Extracting text from that naively — reading the page purely left-to-right, top-to-bottom in one pass — does not fail loudly. It silently interleaves unrelated sentences, drops tables into a wall of unstructured text, and returns nothing at all for a page that is actually a picture of text. This week is about the specific failure modes that make PDF text extraction harder than page.extract_text(), and the two real tools — Unstructured.io and LlamaParse — built to handle them, plus the OCR fallback path underneath both.

Concept 1 — Multi-Column Layouts Break Reading Order

A PDF has no concept of "paragraph" or "column." It has positioned characters on a page, each with an (x, y) coordinate. A naive text extractor reads those characters ordered primarily by vertical position, then horizontal — which is exactly right for a single column of body text and exactly wrong for two independent columns printed side by side at the same line height. It does not error. It quietly stitches the end of one column's line onto the start of the other column's line at the same height, producing a sentence that reads as if generated by shuffling two documents together.

The fix is to detect the columns first — group text by horizontal band — and only then apply top-to-bottom ordering, independently, within each band. That two-step process (bands first, order second) is the core of what a real layout model does at much greater sophistication; this is its simplest possible version.

Example:

import io
from reportlab.pdfgen import canvas
from reportlab.lib.pagesizes import letter
import pdfplumber


def build_two_column_pdf():
    """An adjuster narrative report: two independent columns of prose at
    the same line height, the way a legacy claims system's PDF export
    often lays out a summary alongside policy metadata."""
    buf = io.BytesIO()
    c = canvas.Canvas(buf, pagesize=letter)
    width, height = letter
    c.setFont("Helvetica-Bold", 16)
    c.drawString(72, height - 72, "ADJUSTER NARRATIVE REPORT")
    left_x = 72
    right_x = width / 2 + 20
    top_y = height - 110
    left_lines = [
        "The insured vehicle was stopped at",
        "a red light on Dizengoff Street when",
        "it was struck from behind by the",
        "second vehicle at approximately 40",
        "km/h based on skid mark analysis.",
    ]
    right_lines = [
        "Policy POL-88123 was bound on",
        "2025-01-01 with a $500 deductible",
        "and comprehensive collision cover.",
        "No prior claims are on file for",
        "this policyholder in the last 5 years.",
    ]
    c.setFont("Helvetica", 11)
    for i, line in enumerate(left_lines):
        c.drawString(left_x, top_y - i * 16, line)
    for i, line in enumerate(right_lines):
        c.drawString(right_x, top_y - i * 16, line)
    c.showPage()
    c.save()
    buf.seek(0)
    return buf


def reconstruct_columns(words, page_width, num_columns=2):
    """Group words into vertical bands by x0 position first, THEN order
    each band top-to-bottom -- the layout-aware fix for a reader that
    otherwise orders purely by y and splices unrelated columns together."""
    band_width = page_width / num_columns
    columns = [[] for _ in range(num_columns)]
    for w in words:
        band = min(int(w["x0"] // band_width), num_columns - 1)
        columns[band].append(w)
    column_texts = []
    for col_words in columns:
        col_words.sort(key=lambda w: (round(w["top"]), w["x0"]))
        lines = {}
        for w in col_words:
            key = round(w["top"] / 8) * 8   # snap to line bands
            lines.setdefault(key, []).append(w)
        ordered_lines = []
        for key in sorted(lines):
            line_words = sorted(lines[key], key=lambda w: w["x0"])
            ordered_lines.append(" ".join(w["text"] for w in line_words))
        column_texts.append("\n".join(ordered_lines))
    return column_texts


pdf_buf = build_two_column_pdf()
with pdfplumber.open(pdf_buf) as pdf:
    page = pdf.pages[0]
    naive_text = page.extract_text()
    words = page.extract_words()
    page_width = page.width

print("--- naive page.extract_text() reading order ---")
print(naive_text)

columns = reconstruct_columns(words, page_width, num_columns=2)

Concept 2 — Element Types: Title, NarrativeText, Table, ListItem


Unstructured's real partition_pdf does not return a flat string. It returns a list of
typed elements — Title, NarrativeText, Table, ListItem, and a few rarer types —
each carrying its own text plus metadata (page_number, bounding-box coordinates, and
for tables, an HTML rendering of the detected structure). That typing is the whole reason
to use a real partitioning library over extract_text(): an LLM prompt built from typed
elements can treat a Title as a heading and a Table as structured data, instead of
guessing from raw text which lines are which.


REAL MODE — requires the Unstructured.io library (fails to install in this sandbox,
see this week's Metadata row):


from unstructured.partition.pdf import partition_pdf

elements = partition_pdf(
    filename="claim_form.pdf",
    strategy="hi_res",             # runs a layout-detection model
    infer_table_structure=True,    # populates Table.metadata.text_as_html
)

for el in elements:
    print(type(el).__name__, "| page", el.metadata.page_number, "|", el.text[:60])

The hand-rolled classifier below reproduces the same idea — assign each line of text a
type from font size and a leading marker character — using only what pdfplumber gives

bigger than body text; a ListItem starts with a bullet marker) is genuinely testable here

Example:


import io
import dataclasses
from reportlab.pdfgen import canvas
from reportlab.lib.pagesizes import letter
import pdfplumber


def build_form_pdf():
    buf = io.BytesIO()
    c = canvas.Canvas(buf, pagesize=letter)
    width, height = letter
    y = height - 72
    c.setFont("Helvetica-Bold", 16)
    c.drawString(72, y, "AUTO CLAIM INTAKE FORM")
    y -= 30
    c.setFont("Helvetica", 11)
    c.drawString(72, y, "The claimant reported the vehicle was parked and unattended")
    y -= 16
    c.drawString(72, y, "when the damage occurred in the apartment parking garage.")
    y -= 30
    c.setFont("Helvetica-Bold", 13)
    c.drawString(72, y, "Itemized Damage")
    y -= 20
    c.setFont("Helvetica", 11)
    for item in ["Front bumper replacement", "Headlight assembly", "Paint and labor"]:
        c.drawString(90, y, f"- {item}")
        y -= 16
    c.showPage()
    c.save()
    buf.seek(0)
    return buf


@dataclasses.dataclass
class Element:
    element_type: str
    text: str
    font_size: float
    page_number: int


def classify_line(text, font_size, body_size):
    """Font size relative to the page's dominant (body) size, plus a
    leading bullet/dash marker, stands in for the real layout model's
    Title/NarrativeText/ListItem typing."""
    stripped = text.strip()
    if stripped.startswith(("-", "*", "•")):
        return "ListItem"
    if font_size > body_size + 1.5:
        return "Title"
    return "NarrativeText"


pdf_buf = build_form_pdf()
elements = []
with pdfplumber.open(pdf_buf) as pdf:
    page = pdf.pages[0]
    chars = page.chars
    lines = {}
    for ch in chars:
        key = round(ch["top"] / 4) * 4
        lines.setdefault(key, []).append(ch)
    all_sizes = [ch["size"] for ch in chars]
    body_size = max(set(all_sizes), key=all_sizes.count)  # modal size = body text
    for key in sorted(lines):
        line_chars = sorted(lines[key], key=lambda c: c["x0"])
        text = "".join(c["text"] for c in line_chars)
        size = round(line_chars[0]["size"], 1)
        etype = classify_line(text, size, body_size)
        elements.append(Element(etype, text, size, page_number=1))

for el in elements:
    print(f"{el.element_type:<14} size={el.font_size:<5} {el.text!r}")

Concept 3 — Strategy Selection: hi_res vs fast vs ocr_only


partition_pdf's strategy parameter is not a quality dial you crank up "to be safe." It
picks a genuinely different code path: "fast" reads the PDF's own text layer directly
with no layout model at all (cheap, but blind to tables and reading order); "hi_res"
runs a real layout-detection model over a rendered image of each page to find titles,
tables, and reading order (accurate, computationally expensive); "ocr_only" skips the
text layer entirely and assumes none exists. Running every document through "hi_res"
"to be safe" is the single most common way a document-parsing pipeline's compute bill
becomes unexplainable — most digital-native, single-column documents get zero benefit
from a layout model whose whole job is untangling structure they don't have.


Example:


def choose_strategy(has_extractable_text, expects_tables, page_count):
    if not has_extractable_text:
        return "ocr_only"
    if expects_tables:
        return "hi_res"
    return "fast"


# Illustrative per-page compute time, ordered fast < hi_res < ocr_only --
# not measured against a real corpus, just the relative-cost ordering
# every parser vendor documents. Swap in real timings once you profile
# your own document mix.
STRATEGY_SECONDS_PER_PAGE = {"fast": 0.05, "hi_res": 0.9, "ocr_only": 2.4}

documents = [
    {"name": "loss_run_table.pdf", "has_extractable_text": True, "expects_tables": True, "page_count": 3},
    {"name": "policy_wording.pdf", "has_extractable_text": True, "expects_tables": False, "page_count": 40},
    {"name": "faxed_intake.pdf", "has_extractable_text": False, "expects_tables": False, "page_count": 1},
]

total_seconds = 0.0
for doc in documents:
    strategy = choose_strategy(doc["has_extractable_text"], doc["expects_tables"], doc["page_count"])
    est_seconds = doc["page_count"] * STRATEGY_SECONDS_PER_PAGE[strategy]
    total_seconds += est_seconds
    print(f"{doc['name']:<20} strategy={strategy:<8} est={est_seconds:6.2f}s "
          f"({doc['page_count']} pages)")
print(f"\ntotal estimated compute: {total_seconds:.2f}s for {len(documents)} documents")

BFSI Reality Check — Day 1


Legacy angle: A loan-origination system built in the 2000s often exports its case file
as a single PDF concatenating a digitally-generated cover sheet, a scanned signature page,
and a faxed pay stub — three different "documents" glued into one file with three
different parsing needs. choose_strategy has to run per page, not per file, or the cover
sheet's cheap "fast" path gets dragged into "ocr_only" by one scanned page at the end.


Compliance angle: metadata.page_number and coordinates on every element are not
convenience fields — they are what lets a downstream answer cite "this figure came from
page 3, this specific paragraph" rather than "somewhere in this 40-page document." Under
EU AI Act Article 13's transparency duties, a high-risk system's outputs need to be
traceable to their source; discarding coordinates at parse time makes that traceability
unrecoverable later.


What breaks in production: Every document silently defaulting to "hi_res" because
nobody set strategy explicitly. Nothing errors — the pipeline just runs ten times slower
and costs ten times more than it needs to, and the first person to notice is whoever gets
the compute bill, not whoever wrote the parsing code.

Concept 1 — Ruled-Line Table Detection


A ruled table — one drawn with actual vector lines on the page, the way an ACORD loss-run
form is laid out — is detected by finding the grid itself: the horizontal and vertical
lines that bound each cell, then reading the text that falls inside each bounded region.
This is exactly how pdfplumber.extract_tables() works, and it is the same structural
signal Unstructured's infer_table_structure=True uses internally before rendering the
result as Table.metadata.text_as_html.


Example:


import io
from reportlab.pdfgen import canvas
from reportlab.lib.pagesizes import letter
import pdfplumber


def build_table_pdf(rows, col_widths):
    """A ruled table with real grid lines -- header row plus data rows --
    drawn the way a scanned ACORD loss-run form is ruled."""
    buf = io.BytesIO()
    c = canvas.Canvas(buf, pagesize=letter)
    width, height = letter
    row_height = 24
    x0 = 72
    y0 = height - 100
    n_rows = len(rows)
    xs = [x0]
    for w in col_widths:
        xs.append(xs[-1] + w)
    table_width = sum(col_widths)
    c.setLineWidth(0.75)
    for xline in xs:
        c.line(xline, y0, xline, y0 - row_height * n_rows)
    for r in range(n_rows + 1):
        yline = y0 - row_height * r
        c.line(x0, yline, x0 + table_width, yline)
    c.setFont("Helvetica-Bold", 10)
    for j, cell in enumerate(rows[0]):
        c.drawString(xs[j] + 4, y0 - 16, cell)
    c.setFont("Helvetica", 10)
    for r, row in enumerate(rows[1:], start=1):
        for j, cell in enumerate(row):
            c.drawString(xs[j] + 4, y0 - row_height * r - 16, cell)
    c.showPage()
    c.save()
    buf.seek(0)
    return buf


rows = [
    ["Claim ID", "Loss Type", "Reserve", "Status"],
    ["CLM-1001", "Collision", "$4,200", "Open"],
    ["CLM-1002", "Theft", "$1,850", "Closed"],
    ["CLM-1003", "Water Damage", "$9,600", "Open"],
]
pdf_buf = build_table_pdf(rows, col_widths=[90, 110, 80, 80])
with pdfplumber.open(pdf_buf) as pdf:
    tables = pdf.pages[0].extract_tables()

print(f"tables found: {len(tables)}")
for row in tables[0]:
    print(row)

Concept 2 — Multi-Row Headers and Merged Cells


A ruled-line extractor has no concept of a merged cell — it only knows the grid. A header
that visually spans two columns ("CLAIM INFO" printed once, over what are really two
separate columns) comes back from extraction as one cell holding the label and one empty
cell beside it, on the row above a second header row that names the actual sub-columns.
Reconciling that into one flat, usable column name per column is a forward-fill: propagate
each non-blank top-header cell rightward until the next non-blank one, then join it with
the sub-header beneath it.


Example:


import io
from reportlab.pdfgen import canvas
from reportlab.lib.pagesizes import letter
import pdfplumber


def build_multirow_header_pdf():
    buf = io.BytesIO()
    c = canvas.Canvas(buf, pagesize=letter)
    width, height = letter
    col_widths = [70, 90, 80, 80]
    row_height = 22
    x0 = 72
    y0 = height - 100
    n_rows = 3
    xs = [x0]
    for w in col_widths:
        xs.append(xs[-1] + w)
    table_width = sum(col_widths)
    c.setLineWidth(0.75)
    for xline in xs:
        c.line(xline, y0, xline, y0 - row_height * n_rows)
    for r in range(n_rows + 1):
        yline = y0 - row_height * r
        c.line(x0, yline, x0 + table_width, yline)
    c.setFont("Helvetica-Bold", 9)
    c.drawString(xs[0] + 4, y0 - 15, "CLAIM INFO")   # spans cols 0-1
    c.drawString(xs[2] + 4, y0 - 15, "RESERVE")       # spans cols 2-3
    row2 = ["ID", "Type", "Amount", "Currency"]
    for j, cell in enumerate(row2):
        c.drawString(xs[j] + 4, y0 - row_height - 15, cell)
    c.setFont("Helvetica", 9)
    data_row = ["CLM-1001", "Collision", "4200", "USD"]
    for j, cell in enumerate(data_row):
        c.drawString(xs[j] + 4, y0 - 2 * row_height - 15, cell)
    c.showPage()
    c.save()
    buf.seek(0)
    return buf


def flatten_multirow_header(header_row1, header_row2):
    """Forward-fill the top header row across its blank (merged) cells,
    then join with the sub-header row into one flat column name per
    column."""
    filled = []
    last = ""
    for cell in header_row1:
        if cell and cell.strip():
            last = cell.strip()
        filled.append(last)
    flat = []
    for top, sub in zip(filled, header_row2):
        name = f"{top}_{sub}".strip("_").lower().replace(" ", "_")
        flat.append(name)
    return flat


pdf_buf = build_multirow_header_pdf()
with pdfplumber.open(pdf_buf) as pdf:
    table = pdf.pages[0].extract_tables()[0]

print("raw extracted rows:")
for row in table:
    print(row)

header_row1, header_row2, data_row = table
columns = flatten_multirow_header(header_row1, header_row2)
print("\nflattened columns:", columns)
record = dict(zip(columns, data_row))
print("record:", record)

Concept 3 — HTML-to-Markdown for LLM Consumption


Unstructured's Table.metadata.text_as_html is HTML — correct, unambiguous, and full of
tokens an LLM prompt does not need to spend on. A <table><tr><td> structure converts
losslessly to a GitHub-flavoured markdown table at a fraction of the character count, which
matters directly at inference time: fewer tokens per table means more tables fit in a
context window and a lower per-call cost.


Example:


from bs4 import BeautifulSoup

# Stand-in for Unstructured's own Table.metadata.text_as_html output --
# same shape: a plain <table> with <tr>/<td>, no styling.
text_as_html = """
<table>
<tr><td>Claim ID</td><td>Loss Type</td><td>Reserve</td><td>Status</td></tr>
<tr><td>CLM-1001</td><td>Collision</td><td>$4,200</td><td>Open</td></tr>
<tr><td>CLM-1002</td><td>Theft</td><td>$1,850</td><td>Closed</td></tr>
</table>
"""


def html_table_to_markdown(html):
    """Convert a simple <table> (no rowspan/colspan) to a GitHub-flavoured
    markdown table."""
    soup = BeautifulSoup(html, "html.parser")
    rows = [[td.get_text(strip=True) for td in tr.find_all("td")]
            for tr in soup.find_all("tr")]
    if not rows:
        return ""
    header, *body = rows
    lines = ["| " + " | ".join(header) + " |",
             "| " + " | ".join(["---"] * len(header)) + " |"]
    for row in body:
        lines.append("| " + " | ".join(row) + " |")
    return "\n".join(lines)


markdown = html_table_to_markdown(text_as_html)
print(markdown)
print()
print("markdown chars:", len(markdown), " html chars:", len(text_as_html))

Concept 1 — Detecting a Scanned Page


Before OCR can even be considered, the pipeline has to know a page needs it. A digitally
generated PDF page has a text layer pdfplumber (or any extractor) can read directly; a
scanned or faxed page is a picture with no text layer at all — extract_text() returns
an empty or near-empty string, not an error. Counting extractable characters per page is
the cheapest possible routing signal: below a threshold, the page has no text layer to
extract and must go through OCR instead.


Example:


import io
from reportlab.pdfgen import canvas
from reportlab.lib.pagesizes import letter
from reportlab.lib.utils import ImageReader
from PIL import Image, ImageDraw
import pdfplumber


def render_text_as_image(text_lines, size=(600, 200)):
    """Render text into a raster image -- the way a scanned claim form
    arrives: pixels only, no text layer for a PDF text extractor to find."""
    img = Image.new("L", size, color=255)
    draw = ImageDraw.Draw(img)
    y = 10
    for line in text_lines:
        draw.text((10, y), line, fill=0)
        y += 24
    return img


def build_mixed_pdf():
    """Page 1: a real digital text layer. Page 2: the same content
    rendered as a picture and dropped onto the page as an image --
    simulating a scanned document with zero extractable characters."""
    buf = io.BytesIO()
    c = canvas.Canvas(buf, pagesize=letter)
    width, height = letter
    c.setFont("Helvetica", 12)
    c.drawString(72, height - 100, "Claim CLM-2001: digital intake form, text layer present.")
    c.showPage()
    img = render_text_as_image([
        "Claim CLM-2002: faxed intake form,",
        "scanned at the branch, no text layer.",
    ])
    c.drawImage(ImageReader(img), 72, height - 300, width=300, height=100)
    c.showPage()
    c.save()
    buf.seek(0)
    return buf


def needs_ocr(page, min_chars=20):
    """Below min_chars of extractable text, the page is image-only and
    must go through the OCR path rather than direct text extraction."""
    text = page.extract_text() or ""
    return len(text.strip()) < min_chars, len(text.strip())


pdf_buf = build_mixed_pdf()

        route = "OCR fallback" if route_to_ocr else "direct text extraction"
        print(f"page {i}: extractable_chars={char_count:>3}  route -> {route}")

Concept 2 — DPI, Deskew and the Preprocessing Pipeline


Two preprocessing steps decide whether Tesseract even has a fair chance: resolution and
rotation. Below roughly 300 DPI, a typical body-text font resolves to too few pixels tall
for reliable glyph shapes — this is arithmetic, not a rule of thumb, since a point size and
a DPI directly determine a pixel height. Rotation (skew) is the second: a page scanned
even a few degrees off-level breaks the row-by-row assumption OCR engines rely on, and has
to be corrected before recognition, not after.


Example:


import numpy as np
from PIL import Image, ImageDraw

# --- Part A: DPI arithmetic ---
def px_height_for_font(point_size, dpi):
    return point_size * dpi / 72  # 72 points per inch is the PDF unit

for dpi in (150, 200, 300):
    print(f"10pt font at {dpi:>3} DPI -> {px_height_for_font(10, dpi):5.1f} px tall")

# --- Part B: skew estimation by projection profile ---
# Rotate candidate angles, sum pixel darkness per row, and pick the angle
# whose row-sum profile has the highest variance -- text rows line up
# into sharp peaks only when the image is level.
def make_text_rows_image(size=(300, 150), n_rows=6):
    img = Image.new("L", size, color=255)
    draw = ImageDraw.Draw(img)
    for r in range(n_rows):
        y = 15 + r * 20
        draw.line([(10, y), (280, y)], fill=0, width=4)
    return img


def estimate_skew_angle(img, angle_range=(-10, 10), step=0.5):
    best_angle, best_score = 0.0, -1.0
    angles = np.arange(angle_range[0], angle_range[1] + step, step)
    for angle in angles:
        rotated = img.rotate(angle, expand=False, fillcolor=255)
        rot_arr = np.array(rotated.convert("L"))
        darkness = 255 - rot_arr
        row_sums = darkness.sum(axis=1)
        score = row_sums.var()
        if score > best_score:
            best_score, best_angle = score, angle
    return best_angle


base = make_text_rows_image()
true_angle = 4.0
skewed = base.rotate(true_angle, expand=False, fillcolor=255)
estimated = estimate_skew_angle(skewed)
print(f"\ntrue skew angle applied  : {true_angle} degrees")
print(f"estimated correction angle: {estimated} degrees")

Concept 3 — Per-Word Confidence as a Routing Signal


Tesseract does not just return text — pytesseract.image_to_data(...) returns a
per-word confidence score (0-100). That score is the real routing signal for the last
decision in this pipeline: whether to accept an OCR result, or send the page to a
quarantine queue for a human to key in by hand. Two independent thresholds matter, not
one: a low average confidence across the page catches broadly poor scan quality, while a
single very-low-confidence word — even on an otherwise clean page — can be exactly the
claim amount or policy number that must not be silently wrong.


Example:


import dataclasses

# Tesseract's pytesseract.image_to_data(...) returns a per-word confidence
# (0-100, or -1 for non-text regions) alongside each recognized word. The
# numbers below stand in for that real output shape -- what matters here
# is the routing logic built on top of confidence scores, which is
# identical whether the scores come from a real Tesseract call (REAL
# MODE, no engine in this sandbox) or this stand-in list.
@dataclasses.dataclass
class OcrWord:
    text: str
    confidence: float


def route_ocr_result(words, mean_floor=75.0, hard_floor=40.0):
    """Quarantine instead of silently accepting a partial OCR result.
    Either the page average drops below mean_floor, or any single word
    falls below hard_floor -- one badly-recognized field (a claim amount)
    can poison a downstream number even when the page average looks fine."""
    if not words:
        return "quarantine", "no words recognized"
    confidences = [w.confidence for w in words]
    mean_conf = sum(confidences) / len(confidences)
    min_conf = min(confidences)
    if min_conf < hard_floor:
        return "quarantine", f"a word scored {min_conf:.0f} (< hard floor {hard_floor:.0f})"
    if mean_conf < mean_floor:
        return "quarantine", f"mean confidence {mean_conf:.1f} (< floor {mean_floor:.1f})"
    return "accept", f"mean confidence {mean_conf:.1f}"


pages = {
    "clean_scan": [OcrWord("CLM-2002", 96), OcrWord("Collision", 93), OcrWord("4200", 91)],
    "smudged_amount": [OcrWord("CLM-2003", 94), OcrWord("Collision", 90), OcrWord("42O0", 31)],
    "faded_fax": [OcrWord("CLM-2004", 68), OcrWord("Colli5ion", 61), OcrWord("42OO", 58)],
}

for page_id, words in pages.items():
    decision, reason = route_ocr_result(words)
    print(f"{page_id:<16} -> {decision:<10} ({reason})")

Legacy angle: Branch-scanned intake forms are frequently faxed rather than scanned

than the system guessing and moving on.

and never revisited. Scan quality drifts — a branch replaces its scanner, a new fax
gateway compresses harder — and a threshold that correctly quarantined 2% of pages a year
ago silently accepts far more bad reads today because nobody re-measured it against

Concept 2 — API Cost vs Local Compute


LlamaParse bills per page through a hosted API; Unstructured's hi_res strategy runs
locally, which trades a per-call cost for a fixed infrastructure cost (a server, whether or
not it is busy). At low volume, paying only for what you use tends to be cheaper. At high
enough volume, the fixed cost of running your own compute amortizes below the accumulated
per-page API cost. The crossover point is not a rule of thumb — it is arithmetic that
depends on your actual page volume and both providers' actual rates.


Example:


# Illustrative unit-cost parameters (not measured, not scraped from any
# vendor page today) -- the arithmetic is what this concept teaches;
# swap in the real published rate before using this for an actual budget.
def monthly_cost(pages_per_month, api_cost_per_page=0.003, local_pages_per_hour=1200,
                  compute_cost_per_hour=0.35, local_fixed_monthly=150.0):
    api_total = pages_per_month * api_cost_per_page
    local_hours = pages_per_month / local_pages_per_hour
    local_total = local_fixed_monthly + local_hours * compute_cost_per_hour
    return api_total, local_total


for pages in (10_000, 100_000, 1_000_000):

Concept 3 — Parser Chosen Per Document Class, Not Globally


Neither Unstructured nor LlamaParse is uniformly "the right tool." A pipeline handling
multiple document classes should choose per class: a scanned document with no text layer
needs an OCR-capable path regardless of which tool provides it; a short, table-heavy
digital document is worth the accuracy of a layout model; a long digital document with no
tables gains nothing from either and should take the cheapest path available.


Example:

    if has_ruled_table and page_count <= 5:

    return "fast"

Concept 4 — Deterministic Re-Parse and Caching


Re-parsing the same document under the same configuration should hit a cache, not
re-trigger an API call or a slow hi_res pass. The cache key has to include both the
document's content and the exact parser configuration — hashing content alone would
incorrectly return a cached "fast" result when the caller actually asked for "hi_res"
this time.


Example:


import hashlib

def cache_key(file_bytes, parser_config):
    """Hash both the document content and the exact config so a config
    change (e.g. strategy='hi_res' -> 'fast') correctly misses instead of
    returning a stale result parsed under a different strategy."""
    config_str = "&".join(f"{k}={v}" for k, v in sorted(parser_config.items()))
    digest_input = file_bytes + config_str.encode()
    return hashlib.sha256(digest_input).hexdigest()[:16]


doc_bytes = b"%PDF-1.4 example claim form bytes"
key_a = cache_key(doc_bytes, {"strategy": "hi_res", "infer_table_structure": True})
key_b = cache_key(doc_bytes, {"strategy": "fast", "infer_table_structure": True})
key_c = cache_key(doc_bytes, {"strategy": "hi_res", "infer_table_structure": True})
print(f"key (hi_res)      : {key_a}")
print(f"key (fast)        : {key_b}")
print(f"key (hi_res again): {key_c}")
print("same config -> same key:", key_a == key_c)
print("different config -> different key:", key_a != key_b)

Compliance angle: A deterministic, cached parse result is also an auditable one — the
same document under the same configuration produces the same output every time, which
matters when a regulator asks how a specific figure was extracted from a specific source
document months after the fact. A non-deterministic pipeline (a hosted API whose model
version changes underneath you) cannot make that guarantee without pinning a model
version explicitly.


What breaks in production: Choosing LlamaParse for its accuracy on complex documents
without checking whether the account's data-processing agreement actually covers the
document classes being sent to it. A parser choice made purely on quality and cost, with
the compliance constraint discovered afterward, is a rebuild, not a config change.

Concept 1 — Gold Set and Field-Level Recall/Precision


A parsing pipeline cannot be trusted on "it looked right when I checked one document." The
real check is a small hand-labeled gold set — roughly 20 documents with known-correct
field values — scored field by field: recall (did the parser surface a value at all,
whether right or wrong) and precision (of the values it did surface, how many were
exactly correct). The two numbers separate two different failure modes: a low-recall
field is being missed, a low-precision field is being extracted wrong.


Example:


gold_set = [
    {"doc": "clm_1001.pdf", "gold": {"claim_id": "CLM-1001", "reserve": "4200", "status": "Open"},
     "extracted": {"claim_id": "CLM-1001", "reserve": "4200", "status": "Open"}},
    {"doc": "clm_1002.pdf", "gold": {"claim_id": "CLM-1002", "reserve": "1850", "status": "Closed"},
     "extracted": {"claim_id": "CLM-1002", "reserve": "1850", "status": None}},   # status missed
    {"doc": "clm_1003.pdf", "gold": {"claim_id": "CLM-1003", "reserve": "9600", "status": "Open"},
     "extracted": {"claim_id": "CLM-1003", "reserve": "9600O", "status": "Open"}},  # OCR digit/letter confusion
    {"doc": "clm_1004.pdf", "gold": {"claim_id": "CLM-1004", "reserve": "3100", "status": "Open"},
     "extracted": {"claim_id": "CLM-1004", "reserve": "3100", "status": "Open"}},
]


def field_level_scores(records):
    """recall = fraction of gold values the parser surfaced at all;
    precision = fraction of surfaced (non-null) values that exactly
    match gold."""
    fields = records[0]["gold"].keys()
    scores = {}
    for field in fields:
        surfaced = correct = present_in_gold = 0
        for rec in records:
            gold_val = rec["gold"][field]
            ext_val = rec["extracted"].get(field)
            present_in_gold += 1
            if ext_val is not None:
                surfaced += 1
                if ext_val == gold_val:
                    correct += 1
        recall = surfaced / present_in_gold
        precision = correct / surfaced if surfaced else 0.0
        scores[field] = {"recall": round(recall, 3), "precision": round(precision, 3)}
    return scores


for field, s in field_level_scores(gold_set).items():
    print(f"{field:<10} recall={s['recall']:.3f}  precision={s['precision']:.3f}")

Concept 2 — Failure Taxonomy


A raw "N documents failed" count tells you nothing about what to fix. Tagging each failure
with a specific cause — rotated scan, handwriting, multi-column layout, a stamped overlay
covering text — turns a pile of failures into a prioritized backlog: if 40% of failures are
rotated_scan, the highest-leverage fix is a deskew step, not a better OCR model.


Example:


import collections

failure_log = [
    {"doc": "clm_2001.pdf", "failure": "rotated_scan"},
    {"doc": "clm_2002.pdf", "failure": "multi_column"},
    {"doc": "clm_2003.pdf", "failure": "handwriting"},
    {"doc": "clm_2004.pdf", "failure": "rotated_scan"},
    {"doc": "clm_2005.pdf", "failure": "stamped_overlay"},
    {"doc": "clm_2006.pdf", "failure": "multi_column"},
    {"doc": "clm_2007.pdf", "failure": "rotated_scan"},
]
tally = collections.Counter(f["failure"] for f in failure_log)
for failure_type, count in tally.most_common():
    print(f"{failure_type:<16} {count}")

Concept 3 — Quarantine Queue, Not Silent Partial Output


The final decision in the pipeline is the same shape as Day 3's OCR confidence routing,
applied one level up: after parsing and field extraction, a record with any missing or
clearly malformed required field goes to a quarantine queue for human review, rather than
being upserted downstream with a silent gap or a wrong value baked into it.


Example:


def quality_gate(record, required_fields=("claim_id", "reserve", "status")):
    """A record with a missing OR malformed required field is quarantined
    rather than upserted with a gap silently left in it."""
    missing = [f for f in required_fields if record["extracted"].get(f) is None]
    malformed = [f for f in required_fields
                 if record["extracted"].get(f) is not None
                 and f == "reserve" and not record["extracted"][f].isdigit()]
    if missing or malformed:
        return "quarantine", missing, malformed
    return "accept", [], []


for rec in gold_set:
    decision, missing, malformed = quality_gate(rec)
    print(f"{rec['doc']:<14} -> {decision:<10} missing={missing} malformed={malformed}")

BFSI Reality Check — Day 5


Legacy angle: Building the gold set itself is the real bottleneck against a legacy
document backlog — someone has to open 20 real scanned claim forms and key in the correct
answer by hand before any recall/precision number means anything. That labeling cost is
often the actual reason a parsing pipeline ships without a quality harness, not a lack of
awareness that one is needed.


Compliance angle: A field-level recall/precision score against a fixed gold set is
exactly the kind of declared, reproducible accuracy metric EU AI Act Article 15 expects for
a high-risk system — provided the gold set itself is versioned and the harness is rerun
whenever the underlying parser configuration changes, not measured once at launch and
never touched again.


What breaks in production: The gold set is built once, from whichever documents were
on hand at the time, and never refreshed as new document templates and scan qualities
enter the pipeline. Recall and precision measured against a stale gold set can look
perfect while the live pipeline silently degrades on document shapes the gold set never
covered.




Architecture Decision — Week 08


Choosing between: Unstructured.io (self-hosted, local compute) vs. LlamaParse (hosted
API) vs. a cloud OCR service (e.g. AWS Textract / Azure Document Intelligence), for a
claims-intake pipeline under an on-prem or data-residency constraint.


Rule of thumb: Choose Unstructured.io when documents cannot leave the institution's own
network — a data-residency requirement rules out every hosted option regardless of
accuracy or cost, and Unstructured's local hi_res strategy is the only one of the three
that runs entirely inside infrastructure you control. Choose LlamaParse when documents
can leave the network, table-heavy or unusually-formatted documents are common, and
engineering time to tune a local layout pipeline is scarcer than the per-page API cost —
its markdown-native, instruction-steerable output needs the least post-processing to reach
an LLM prompt. Choose a cloud OCR service (Textract/Document Intelligence) when the
document mix is dominated by scanned forms with well-known field layouts (a specific
insurer's ACORD template, a specific bank's loan form) and the cloud provider's
form-specific extraction features (key-value pair detection, pre-trained form models) beat
generic layout detection on exactly that template family, and the same data-residency
constraint that would block LlamaParse is already satisfied because the documents already
live in that provider's cloud region. Whichever is chosen, keep the parser choice a
per-document-class decision (Day 4 Concept 3), not a single global pick — the three tools
are not competing for one universal winner, they cover genuinely different constraints,
and a real pipeline will end up using more than one.
