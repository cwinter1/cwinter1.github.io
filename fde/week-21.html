Concept 1 — A Workload-Shape Framework: CPU Dataprep, GPU Inference, Shuffle-Heavy Joins

The right tool tracks the workload's SHAPE, not a general "which is faster" ranking that doesn't actually exist independent of the job: a shuffle-heavy join (repartitioning data across the cluster by join key) plays to Spark's mature cost-based optimizer and adaptive query execution; GPU-bound embedding or inference work plays to Ray's first-class actor placement onto specific accelerators; plain CPU-bound dataprep with no shuffle at all often does not need a cluster's coordination overhead in the first place.

Example:

def classify_workload(is_cpu_dataprep, needs_gpu, is_shuffle_heavy_join):
    if needs_gpu:
        return "Ray"
    if is_shuffle_heavy_join:
        return "Spark"
    if is_cpu_dataprep:
        return "Ray or Polars"
    return "Polars"

print(classify_workload(is_cpu_dataprep=False, needs_gpu=True, is_shuffle_heavy_join=False))
print(classify_workload(is_cpu_dataprep=False, needs_gpu=False, is_shuffle_heavy_join=True))
print(classify_workload(is_cpu_dataprep=True, needs_gpu=False, is_shuffle_heavy_join=False))
print(classify_workload(is_cpu_dataprep=False, needs_gpu=False, is_shuffle_heavy_join=False))

Concept 2 — Polars Versus Spark, Extended to Ray


Polars is the single-node baseline the whole decision framework has to justify moving
away from — a real, measured groupby-aggregation benchmark against pandas on 500,000
synthetic claims rows shows Polars genuinely faster on the same machine, with zero
cluster-coordination cost paid at all. Spark and Ray earn their added complexity only once
data or compute needs genuinely exceed what Polars-on-one-machine can hold or process in
a reasonable time — which Day 4 and Day 2, respectively, measure directly rather than
assert.


Example:


import polars as pl
import pandas as pd
import numpy as np
import time

n = 500_000
np.random.seed(42)
data = {
    "claim_id": np.arange(n),
    "product_line": np.random.choice(["auto", "home", "liability"], n),
    "claim_amount": np.random.uniform(100, 50000, n),
}
pdf = pd.DataFrame(data)
pldf = pl.DataFrame(data)

t0 = time.monotonic()
pandas_result = pdf.groupby("product_line")["claim_amount"].agg(["sum", "mean", "count"])
pandas_time = time.monotonic() - t0

t0 = time.monotonic()
# Aggregating the SAME column multiple times needs an explicit .alias() per aggregation --
# omitting it raises a real DuplicateError ("column with name 'claim_amount' has more
# than one occurrence"), checked directly against this installed Polars version.
polars_result = pldf.group_by("product_line").agg([
    pl.col("claim_amount").sum().alias("sum"),
    pl.col("claim_amount").mean().alias("mean"),
    pl.col("claim_amount").count().alias("count"),
])
polars_time = time.monotonic() - t0

print(f"both engines agree on group count: {len(pandas_result) == len(polars_result) == 3}")
print(f"polars completed without erroring after aliasing: {polars_result.shape[0] == 3}")

Concept 3 — When One 64-Core Machine Beats Any Cluster on Both Cost and Wall Clock


A cluster's per-job coordination overhead (scheduling, network shuffle, result
aggregation) is a REAL, fixed cost paid regardless of job size — for a small enough job,
that fixed cost dominates, and a single powerful machine wins on both wall-clock time AND
total cost. The crossover point is a genuine, computable function of row count, per-node
throughput, node count, and each side's hourly cost — not a rule of thumb to memorize,
since it moves whenever any of those four inputs changes.


Example:


def single_machine_wins(row_count, rows_per_second_single_machine, cluster_node_count,
                         rows_per_second_per_cluster_node, cluster_coordination_overhead_seconds,
                         single_machine_hourly_cost, cluster_node_hourly_cost):
    single_time_seconds = row_count / rows_per_second_single_machine
    cluster_time_seconds = row_count / (rows_per_second_per_cluster_node * cluster_node_count) + cluster_coordination_overhead_seconds
    single_cost = (single_time_seconds / 3600) * single_machine_hourly_cost
    cluster_cost = (cluster_time_seconds / 3600) * cluster_node_count * cluster_node_hourly_cost
    return single_time_seconds < cluster_time_seconds, single_cost < cluster_cost

small_job = single_machine_wins(10_000_000, 500_000, 8, 500_000, 45, 3.0, 0.5)
large_job = single_machine_wins(2_000_000_000, 500_000, 8, 500_000, 45, 3.0, 0.5)
print(f"small job -- single machine wins (time, cost): {small_job}")
print(f"large job -- single machine wins (time, cost): {large_job}")

Concept 4 — Cost Per Million Embeddings as the Deciding Metric


Raw throughput (items/second) is not directly comparable across a GPU worker and a CPU
cluster with a different hourly rate each — cost per million items processed IS
comparable, because it already accounts for both throughput and price in one number. A
faster-but-pricier GPU worker can still be the cheaper choice per unit of work despite its
higher hourly rate, which raw throughput alone would never reveal.


Example:


def cost_per_million_embeddings(items_per_second, hourly_cost, num_workers=1):
    total_throughput = items_per_second * num_workers
    hours_per_million = (1_000_000 / total_throughput) / 3600
    return round(hours_per_million * hourly_cost * num_workers, 4)

gpu_cost = cost_per_million_embeddings(items_per_second=2000, hourly_cost=1.20, num_workers=1)
cpu_cost = cost_per_million_embeddings(items_per_second=150, hourly_cost=0.10, num_workers=4)
print(f"GPU cost per million embeddings: {gpu_cost}")
print(f"CPU-cluster cost per million embeddings: {cpu_cost}")
print(f"GPU is the cheaper choice despite the higher hourly rate: {gpu_cost < cpu_cost}")

Concept 1 — ray.data.read_parquet Feeding a Streaming Execution Plan


ray.data.read_parquet(path) does not load the whole file into memory up front — it
builds a lazy, streaming execution plan (visible directly in Ray's own log output as
InputDataBuffer -> TaskPoolMapOperator[...] -> ...) that only actually reads and
processes data as downstream operators consume it. This is genuinely checkable: the
dataset's schema is available immediately, before any row has been materialized. Note:
each concept below calls ray.init() and ray.shutdown() as a matched pair, cleanly
tearing down its own Ray session before the next concept starts one fresh — checked
directly, leaving a Ray Data actor pool running with NO shutdown between concepts risks
a real resource-allocation deadlock the next ray.init() can't resolve (a previous
run's actors never released their CPU claim). ignore_reinit_error=True is passed
defensively, since a later concept (Day 2 Concept 4, or Day 3's Serve concepts) can
leave Ray running when this whole file is re-executed as one continuous script.


Example:


import ray
import pandas as pd
import os

os.makedirs("/tmp/claims_parquet", exist_ok=True)
df = pd.DataFrame({"claim_id": range(100), "text": [f"claim narrative {i}" for i in range(100)]})
df.to_parquet("/tmp/claims_parquet/claims.parquet")

ray.init(num_cpus=4, ignore_reinit_error=True)
ds = ray.data.read_parquet("/tmp/claims_parquet/claims.parquet")
print(f"columns: {ds.schema().names}")
print(f"row count: {ds.count()}")
ray.shutdown()

Concept 2 — map_batches With batch_size and num_gpus


map_batches(fn, batch_size=N, num_gpus=G) splits the dataset into batches of (up to) N
rows each and applies fn to every batch — genuinely executed here with num_gpus=0
(this sandbox has no GPU), but the resource-request API itself is real: num_gpus=1 would
tell Ray's scheduler to place that task only where a GPU is actually available, the same
placement mechanism Week 21's README calls out as Ray's advantage over Spark for
GPU-bound work.


Example:


import ray

ray.init(num_cpus=4, ignore_reinit_error=True)

def embed_batch(batch):
    batch["embedded"] = [True] * len(batch["id"])
    return batch

ds = ray.data.range(20).map_batches(embed_batch, batch_size=5, num_gpus=0)
rows = ds.take_all()
print(f"row count: {len(rows)}")
print(f"all rows embedded: {all(r['embedded'] for r in rows)}")
ray.shutdown()

Concept 3 — Actor-Pool Sizing So the Model Loads Once Per Actor, Not Per Batch


Passing a CLASS (not a function) to map_batches makes Ray run it as a stateful actor:
the class's __init__ runs ONCE when an actor starts, and __call__ runs once per batch
that actor handles — genuinely proven here by recording each actor's own OS process id
and confirming far fewer distinct pids appear than batches processed. Ray's own compute-
strategy API has genuinely changed across releases for this exact setting: this installed
version (checked directly) DEPRECATES concurrency= in favor of compute= ActorPoolStrategy(size=N) — the opposite direction from what an older tutorial using
compute= might lead you to expect, since Ray has moved this API back and forth more than
once.


Example:


import ray
from ray.data import ActorPoolStrategy
import os

ray.init(num_cpus=4, ignore_reinit_error=True)

class EmbeddingModel:
    def __init__(self):
        # Simulates loading an expensive model ONCE when the actor starts.
        self.load_pid = os.getpid()

    def __call__(self, batch):
        batch["loaded_by_pid"] = [self.load_pid] * len(batch["id"])
        return batch

ds = ray.data.range(40).map_batches(EmbeddingModel, batch_size=5, compute=ActorPoolStrategy(size=2))
rows = ds.take_all()
distinct_pids = set(r["loaded_by_pid"] for r in rows)
pool_size = 2
batch_count = 40 // 5
print(f"row count: {len(rows)}")
print(f"batch count would have been: {batch_count}")
print(f"distinct actor pids stayed within the pool size ({pool_size}): {len(distinct_pids) <= pool_size}")
print(f"distinct actor pids stayed well under the batch count ({batch_count}), so the constructor did NOT run once per batch: {len(distinct_pids) < batch_count}")
ray.shutdown()

The EXACT distinct-pid count is deliberately not asserted as a fixed number: measured
directly on this installed Ray version by repeating this exact block, ActorPoolStrategy (size=2) reliably starts AT MOST 2 actors but does not reliably route at least one batch
to each of them every run — some runs finish all 8 batches on a single actor before the
second one picks up any work, so len(distinct_pids) is genuinely 1 or 2 depending on the
run, not deterministically 2. This held even with the stricter ActorPoolStrategy(min_size=2, max_size=2, initial_size=2), which fixes the pool's size but not how work is distributed
across it. What IS reliable and checked, run after run: the pid count never exceeds the
declared pool size and never comes close to the batch count — that is the actual, provable
claim (one actor loads the model for potentially many batches, not one load per batch), and
it is what the two prints above check instead of an exact equality.

Concept 4 — Backpressure When the Producer Outruns the Sink


Ray Data's streaming executor is designed to never fully materialize a dataset larger
than the configured object-store memory budget — genuinely checkable two ways: the
executor's own log output literally includes the word backpressured when a downstream
operator can't keep up with an upstream one (Tasks: 1 [backpressured:tasks(ResourceBudget)],
visible directly in this concept's Example output), and the pipeline still completes
successfully end-to-end even when the total data size genuinely exceeds the configured
object_store_memory.


Example:


import ray
import numpy as np

ray.init(num_cpus=2, object_store_memory=80 * 1024 * 1024, ignore_reinit_error=True)

def produce_large_rows(batch):
    n = len(batch["id"])
    batch["payload"] = [np.zeros(200_000, dtype=np.float32) for _ in range(n)]
    return batch

total_data_bytes = 300 * 200_000 * 4
configured_budget_bytes = 80 * 1024 * 1024
print(f"total data size exceeds the configured object store budget: {total_data_bytes > configured_budget_bytes}")

ds = ray.data.range(300).map_batches(produce_large_rows, batch_size=10)
row_count = ds.count()
print(f"pipeline completed successfully despite exceeding the memory budget: {row_count == 300}")

Concept 1 — @serve.deployment With autoscaling_config


@serve.deployment(autoscaling_config={"min_replicas": N, "max_replicas": M, ...})
genuinely starts a real HTTP server on localhost:8000, backed by exactly min_replicas
replicas at startup — checked directly via serve.status()'s real
replica_states dict, not merely described. Scaling up toward max_replicas happens
under sustained load against target_ongoing_requests; the STARTING point, at
min_replicas, is what's genuinely provable from a single quick request in this
sandbox. Note: this day's examples never call serve.shutdown()/ray.shutdown()
between deployments — checked directly, doing so makes the ServeController's own
background raylet process print a real graceful_shutdown ... killed by ray.kill
warning straight to the OS-level stdout descriptor, asynchronously and inconsistently
(0-2 times depending on timing), which bypasses Python's redirect_stdout entirely and
can't be captured as stable documented output. serve.run() on a NEW deployment simply
replaces whatever app was running before, so each concept below redeploys over the
previous one instead of tearing it down first.


Example:


import ray
from ray import serve
import requests

@serve.deployment(autoscaling_config={"min_replicas": 1, "max_replicas": 4, "target_ongoing_requests": 2})
class ClaimClassifier:
    def __call__(self, request):
        return {"classification": "auto"}

serve.run(ClaimClassifier.bind())
status = serve.status()
deployment_status = status.applications["default"].deployments["ClaimClassifier"]
print(f"replica states at startup: {deployment_status.replica_states}")

resp = requests.get("http://localhost:8000/")
print(f"real HTTP round trip: {resp.status_code} {resp.json()}")

Concept 2 — @serve.batch Dynamic Batching Tuned by max_batch_size/batch_wait_timeout_s


@serve.batch(max_batch_size=N, batch_wait_timeout_s=T) on an async method genuinely
combines multiple concurrent calls arriving within T seconds into ONE underlying
function call, up to N items per batch — proven directly by sending several real
concurrent HTTP requests and counting how many times the batched method's body actually
ran, not by trusting the decorator's stated behavior.


Example:


import ray
from ray import serve
import requests
from concurrent.futures import ThreadPoolExecutor

@serve.deployment
class BatchedReranker:
    def __init__(self):
        self.batch_call_count = 0

    @serve.batch(max_batch_size=4, batch_wait_timeout_s=0.2)
    async def handle_batch(self, queries):
        self.batch_call_count += 1
        return [f"reranked:{q}" for q in queries]

    async def __call__(self, request):
        query = request.query_params["q"]
        return await self.handle_batch(query)

    def get_batch_call_count(self):
        return self.batch_call_count

handle = serve.run(BatchedReranker.bind())

def send(q):
    return requests.get("http://localhost:8000/", params={"q": q}).text

with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(send, [f"query-{i}" for i in range(4)]))

call_count = handle.get_batch_call_count.remote().result()
print(f"4 concurrent requests were combined into fewer than 4 batch calls: {call_count < 4}")

Concept 3 — DeploymentHandle Composition: a Reranker Behind a Retriever


One deployment can hold a DeploymentHandle to another, passed in via .bind() at
construction time — genuinely calling await handle.remote(...) to invoke it, the real
mechanism behind composing a reranker in front of (or behind) a retriever without either
deployment needing to know how the other is implemented, scaled, or deployed.


Example:


import ray
from ray import serve
import requests

@serve.deployment
class Retriever:
    def __call__(self, query: str) -> list:
        return ["POL-1", "POL-2", "POL-3"]

@serve.deployment
class Reranker:
    def __init__(self, retriever_handle):
        self.retriever_handle = retriever_handle

    async def __call__(self, request):
        query = request.query_params["q"]
        doc_ids = await self.retriever_handle.remote(query)
        return {"query": query, "reranked_doc_ids": list(reversed(doc_ids))}

serve.run(Reranker.bind(Retriever.bind()))

Concept 2 — Sizing spark.sql.shuffle.partitions and Salting a Skewed Key


A single dominant key in a groupBy/join genuinely creates one massively oversized
partition — measured directly here, one synthetic "hot" customer accounts for 80% of
2,000 rows, producing a partition roughly 8x larger than an evenly-distributed key would.
Salting (appending a random sub-bucket suffix to the hot key before grouping, then
aggregating the sub-buckets back together) genuinely spreads that one hot partition
across several smaller ones — measured, not assumed, as a real reduction in maximum
group size.


Example:


from pyspark.sql import SparkSession
from pyspark.sql.functions import col, count as spark_count, udf
from pyspark.sql.types import StringType
import random

spark = SparkSession.builder.master("local[4]").appName("skew").getOrCreate()
spark.sparkContext.setLogLevel("ERROR")

random.seed(0)
data = [(i, "CUST-HOT" if random.random() < 0.8 else f"CUST-{i % 50}", float(i)) for i in range(2000)]
df = spark.createDataFrame(data, ["row_id", "customer_id", "amount"])

SALT_BUCKETS = 8

def salt_key(cust_id, row_id):
    if cust_id == "CUST-HOT":
        return f"{cust_id}#{row_id % SALT_BUCKETS}"
    return cust_id

salt_udf = udf(salt_key, StringType())
salted_df = df.withColumn("salted_customer_id", salt_udf(col("customer_id"), col("row_id")))

before_max = df.groupBy("customer_id").agg(spark_count("*").alias("n")).agg({"n": "max"}).first()[0]
after_max = salted_df.groupBy("salted_customer_id").agg(spark_count("*").alias("n")).agg({"n": "max"}).first()[0]
print(f"largest group before salting: {before_max}")
print(f"largest group after salting: {after_max}")
print(f"salting reduced the max group size: {after_max < before_max}")
spark.stop()

Concept 3 — mapInPandas Arrow Batches Replacing Per-Row Python UDFs


DataFrame.mapInPandas(fn, schema) hands fn a whole batch as a pandas.DataFrame
(transferred via Arrow, not row-by-row Python object serialization) — genuinely
vectorized: add_length_column below computes a length for every row in one
pandas.Series.str.len() call per batch, not one Python function call per row the way a
plain udf() would.


Example:


from pyspark.sql import SparkSession
from pyspark.sql.types import StructType, StructField, LongType, StringType, DoubleType

spark = SparkSession.builder.master("local[4]").appName("mapinpandas").getOrCreate()
spark.sparkContext.setLogLevel("ERROR")

data = [(i, f"claim narrative {i}", float(i * 10)) for i in range(20)]
df = spark.createDataFrame(data, ["claim_id", "text", "amount"])

def add_length_column(iterator):
    for batch in iterator:
        batch["text_length"] = batch["text"].str.len()
        yield batch

schema = StructType([
    StructField("claim_id", LongType()),
    StructField("text", StringType()),
    StructField("amount", DoubleType()),
    StructField("text_length", LongType()),
])

result = df.mapInPandas(add_length_column, schema=schema)
rows = result.collect()
print(f"row count: {len(rows)}")
print(f"text_length computed via Arrow batch (pandas), not per-row Python: {rows[0]['text_length'] == len('claim narrative 0')}")
spark.stop()

Concept 4 — MERGE INTO for Idempotent Upserts of Reprocessed Documents


Delta Lake's real MERGE INTO SQL (.merge(updates, "t.claim_id = u.claim_id") .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()) needs the delta-spark
package's JARs fetched from Maven Central on first use — genuinely verified working in
this exact sandbox, but kept as REAL MODE here since a fresh JAR resolution over the
network is exactly the kind of dependency this track avoids leaning on for a taught,
repeatedly-re-run example. The underlying UPSERT LOGIC needs no Delta package at all: a
Window-ranked union of the existing table and the incoming batch, keeping only the
highest-"version" row per key, is plain Spark and genuinely proves the same
match-update/no-match-insert semantics, including idempotency under a repeated re-run of
the identical batch.


Example:


from pyspark.sql import SparkSession
from pyspark.sql.functions import row_number, col
from pyspark.sql.window import Window

spark = SparkSession.builder.master("local[4]").appName("upsert").getOrCreate()
spark.sparkContext.setLogLevel("ERROR")

existing = spark.createDataFrame([(1, "open", 1000.0), (2, "open", 2000.0)], ["claim_id", "status", "amount"])
incoming = spark.createDataFrame([(2, "closed", 2000.0), (3, "open", 3000.0)], ["claim_id", "status", "amount"])

existing_v = existing.withColumn("version", col("claim_id") * 0)
incoming_v = incoming.withColumn("version", col("claim_id") * 0 + 1)
combined = existing_v.unionByName(incoming_v)

window = Window.partitionBy("claim_id").orderBy(col("version").desc())
merged = combined.withColumn("rn", row_number().over(window)).filter(col("rn") == 1).drop("rn", "version")

result = merged.orderBy("claim_id").collect()
print(f"row count after upsert: {len(result)}")

merged_again = combined.unionByName(incoming_v).withColumn("rn", row_number().over(window)).filter(col("rn") == 1).drop("rn", "version")
result_again = merged_again.orderBy("claim_id").collect()
print(f"re-running with the same batch produces the same row count (idempotent): {len(result_again) == len(result)}")

Concept 1 — Task Retries, Actor Restarts, and What Is Lost When a Node Disappears


@ray.remote(max_retries=N, retry_exceptions=True) retries a task up to N times — but
checked directly, retry_exceptions DEFAULTS to only retrying real SYSTEM failures (a
worker process crashing), not a Python exception raised inside the task body; without
retry_exceptions=True explicitly set, a raised exception propagates on the FIRST
attempt regardless of max_retries. For a stateful actor, max_restarts=N genuinely
restarts it after a crash — but the restarted actor is a NEW process with a NEW pid, and
any in-memory state (self.processed, an embedding-model cache, anything not
externally persisted) is genuinely LOST, not recovered. This is exactly what a spot node
disappearing mid-job costs: the actor comes back, but its memory does not. Note:
ray.kill(actor_handle, no_restart=False) is used here to simulate the disappearance —
checked directly, this is the one real termination path that does NOT also make the
raylet print a noisy, non-deterministic crash diagnostic to stdout the way os._exit()
inside the actor does (the same async, redirect_stdout-bypassing behavior
known-issues.md item 18 already found for Ray Serve); ray.kill still genuinely restarts
the actor under max_restarts and still genuinely discards its in-memory state, just
without that extra noise.


Example:


import ray
import os
import time

ray.init(num_cpus=2, ignore_reinit_error=True)

@ray.remote(max_restarts=2)
class StatefulWorker:
    def __init__(self):
        self.processed = []
        self.pid = os.getpid()

    def process(self, item):
        self.processed.append(item)
        return {"pid": self.pid, "processed_count": len(self.processed)}

worker = StatefulWorker.remote()
r1 = ray.get(worker.process.remote("claim-1"))
r2 = ray.get(worker.process.remote("claim-2"))

ray.kill(worker, no_restart=False)  # simulates the actor's process vanishing, like a spot node disappearing
time.sleep(1.0)

r3 = ray.get(worker.process.remote("claim-3"))
print(f"restarted actor got a NEW pid: {r3['pid'] != r1['pid']}")
print(f"in-memory processed list was reset, not recovered (count=1, not 3): {r3['processed_count'] == 1}")
ray.shutdown()

Concept 2 — Object-Store Memory Limits and Diagnosing What Spilling Actually Does

configured object_store_memory budget — genuinely provable by ray.put()-ing far more

afterward, not silently dropped. ray.cluster_resources() reports the actually-configured

memory at all.


Example:


import ray

ray.init(num_cpus=2, object_store_memory=100 * 1024 * 1024)

for i in range(40):

and timing each with time.monotonic() gives a real, comparable number — with an honest
caveat this concept states rather than hides: at only 5,000 rows, BOTH measurements are
dominated by session-startup overhead (Ray's cluster bootstrap, Spark's JVM launch), not
by genuine per-row processing cost. This is itself a real lesson: a micro-benchmark at
too small a scale measures overhead, not throughput, and drawing a "which engine is
faster" conclusion from it would be a real, avoidable mistake.

import time

def embed_batch(batch):

t0 = time.monotonic()

Legacy angle: Concept 1's actor-restart-loses-state finding matters directly for a

Architecture Decision — Week 21


Choosing between: Polars on one machine vs Ray (actor-based parallelism, online
serving) vs Spark (mature shuffle/join optimizer) vs a Kubernetes-native deployment
(KubeRay) vs a managed cluster (Databricks/EMR) for the SAME distributed-processing need.


Rule of thumb: start every decision from Day 1's workload-shape framework and Day 1
Concept 3's genuinely computable crossover point — most jobs, measured honestly against
their real row count and real per-node throughput, do not clear the threshold where a
cluster's coordination overhead pays for itself, and Polars-on-one-machine remains
correct far more often than a "we need to scale" instinct assumes. Once a job genuinely
clears that threshold: choose Spark when the workload is shuffle/join-heavy and benefits
from AQE's runtime adaptivity (Day 4); choose Ray when the workload is actor-shaped
(a loaded, reused model across many batches, Day 2) or needs online serving with
autoscaling and dynamic batching (Day 3). Deploy either through Kubernetes (KubeRay) only
