Concept 1 — Enabling Capture, and What It Actually Creates

sys.sp_cdc_enable_table is not a flag you flip; it provisions real objects. Enabling capture on a table creates a capture instance (default name <schema>_<table>, e.g. dbo_Claim), a change table (cdc.dbo_Claim_CT), and two SQL Server Agent jobs (capture and cleanup) — which means capture requires SQL Server Agent running, not just the database engine.

A table can carry at most two capture instances at once. That limit looks like an arbitrary restriction until you need to change a captured table's schema without an outage: you enable a second instance against the new schema, let both run side by side while consumers migrate, then drop the old one. It is the schema-evolution escape hatch, not a quota to work around.

@supports_net_changes = 1 (net-change queries, one row per key instead of every intermediate change) requires the table to have a primary key, or an explicit @index_name naming a unique index to use instead.

Example:

REAL MODE — not executed here; requires a live SQL Server instance with Agent running:

EXEC sys.sp_cdc_enable_db;  -- once per database

EXEC sys.sp_cdc_enable_table
    @source_schema      = N'dbo',
    @source_name        = N'Claim',
    @role_name          = NULL,               -- NULL = no access-control gating role
    @supports_net_changes = 1,                 -- requires a PK, or @index_name below
    @capture_instance   = N'dbo_Claim';        -- default; a second instance could be
                                                -- 'dbo_Claim_v2' during a schema migration

Expected output: a call adding @index_name = N'UQ_PolicyEndorsement_Composite' alongside @supports_net_changes = 1, plus the answer that both the capture job (cdc.<capture_instance>_capture) and the cleanup job (cdc.<capture_instance>_cleanup) must be running — capture populates the change table, cleanup enforces retention, and a disabled Agent leaves capture silently producing nothing.

Concept 2 — Reading an LSN Range

Change rows are read by LSN range, not by timestamp. sys.fn_cdc_get_min_lsn('dbo_Claim') gives the oldest LSN still retained; sys.fn_cdc_get_max_lsn() gives the newest LSN captured anywhere in the database. cdc.fn_cdc_get_all_changes_dbo_Claim(@from_lsn, @to_lsn, N'all') returns every changed row in that range; N'all update old' additionally returns the before-image of every update as a separate row.

sys.fn_cdc_increment_lsn(@last_lsn) bumps a checkpoint LSN forward by the smallest possible amount, so the next range starts strictly after the last row already read instead of re-reading its boundary. sys.fn_cdc_map_time_to_lsn('smallest greater than or equal', @dt) converts a wall-clock time into a starting LSN — the one legitimate way to seed a brand-new consumer from "start capturing from now".

Example:

REAL MODE — not executed here; requires a live SQL Server instance:

DECLARE @from_lsn BINARY(10) = sys.fn_cdc_get_min_lsn('dbo_Claim');
DECLARE @to_lsn   BINARY(10) = sys.fn_cdc_get_max_lsn();

SELECT * FROM cdc.fn_cdc_get_all_changes_dbo_Claim(@from_lsn, @to_lsn, N'all update old');

-- Next cycle: never re-read the row at @to_lsn itself.
DECLARE @next_from_lsn BINARY(10) = sys.fn_cdc_increment_lsn(@to_lsn);

Expected output: for advance_checkpoint(1000, 900), the next checkpoint 1001 (the smallest valid increment); for advance_checkpoint(1000, 1500), a raised error or a "reseed_required" result rather than a silently wrong LSN — the min_lsn has already passed the point this consumer thinks it is at.

Concept 3 — __$operation and Update Semantics

Every change row carries __$operation: 1 = delete, 2 = insert, 3 = before-update image, 4 = after-update image. Queried with N'all', an update surfaces only as a single op-4 row. Queried with N'all update old', it surfaces as an op-3/op-4 pair sharing the same __$start_lsn and __$seqval — the pair is how you recover both the old and new values of an update.

The ordering key across everything is (__$start_lsn, __$seqval) — never the business modified_at column, which is stamped by application code and says nothing about capture order. __$update_mask is a bitmask over the table's columns; paired with sys.fn_cdc_is_bit_set(@column_ordinal, __$update_mask), it tells you whether a specific column actually changed in that row — the mechanism that lets an update skip a re-embed when only, say, a status flag changed and the narrative text did not.

Example:

import dataclasses

# __$operation codes: 1=delete, 2=insert, 3=before-update image, 4=after-update image.
NARRATIVE_COL_ORDINAL = 3  # ordinal of the notes/narrative column this index embeds

@dataclasses.dataclass
class CdcRow:
    start_lsn: int
    seqval: int
    operation: int
    claim_id: int
    update_mask: frozenset  # column ordinals changed in this row (set on op 3 and 4)
    narrative: str


def translate_cdc_rows(rows):
    """Ordered vector-index ops from a raw 'all update old' result set: one upsert
    per insert/after-update row (skipped if the narrative column did not change),
    one delete per delete row. A 3/4 pair collapses to a single op off the after
    image (op 4); the before image (op 3) carries no new information."""
    rows = sorted(rows, key=lambda r: (r.start_lsn, r.seqval))
    ops = []
    for row in rows:
        if row.operation == 1:
            ops.append(("delete", row.claim_id, row.start_lsn, row.seqval))
        elif row.operation == 2:
            ops.append(("upsert", row.claim_id, row.narrative, row.start_lsn, row.seqval))
        elif row.operation == 3:
            continue
        elif row.operation == 4:
            if NARRATIVE_COL_ORDINAL in row.update_mask:
                ops.append(("upsert", row.claim_id, row.narrative, row.start_lsn, row.seqval))
            else:
                ops.append(("skip-reembed", row.claim_id, row.start_lsn, row.seqval))
        else:
            raise ValueError(f"unknown __$operation code: {row.operation}")
    return ops


rows = [
    CdcRow(1000, 1, 2, 501, frozenset(), "Water damage to kitchen ceiling"),
    CdcRow(1000, 2, 1, 490, frozenset(), ""),
]
for op in translate_cdc_rows(rows):
    print(op)

Concept 4 — Retention Is a Data-Loss Clock


sys.sp_cdc_change_job @job_type = 'cleanup', @retention = 4320 sets the default: change
rows older than 3 days (4320 minutes) are deleted by the cleanup job, and
sys.fn_cdc_get_min_lsn advances past them. If a consumer has been down longer than
retention, the LSN range it needs no longer exists — not slow, gone.


The less obvious direction of the same clock: while the capture job itself lags (not
the consumer — the SQL Server Agent capture job that reads the transaction log into the
change table), the transaction log cannot truncate past the oldest change capture has not
yet processed. A stalled capture job grows the live transaction log, which is a different
outage than a stalled consumer, and both share the same root cause: something is not
keeping up with the log.


The operational rule: validate checkpoint_lsn >= min_lsn before every read, and treat a
failure as "reseed from a fresh fn_cdc_map_time_to_lsn seed", not as an error to retry.


Example:


RETENTION_MINUTES_DEFAULT = 4320  # sp_cdc_change_job's default @retention, 3 days

def validate_checkpoint(checkpoint_lsn, min_lsn):
    if checkpoint_lsn >= min_lsn:
        return "ok", 0
    return "reseed_required", min_lsn - checkpoint_lsn

def outage_hours_tolerated(retention_minutes=RETENTION_MINUTES_DEFAULT, safety_margin_minutes=60):
    return (retention_minutes - safety_margin_minutes) / 60

print(validate_checkpoint(5000, 4000))
print(f"outage tolerated at default retention: {outage_hours_tolerated():.1f} hours")

BFSI Reality Check — Day 1


Legacy angle: Enabling CDC is not your decision to make alone. The DBA team owns
sp_cdc_enable_table, the change-control window it requires, and the two-instance limit
that has to stretch across a quarterly schema-release cadence you do not control.


Compliance angle: cdc.dbo_Claim_CT is a second, full copy of every changed customer
record living inside the source database. It is in scope for the same retention and
erasure obligations as the primary table — a data-subject deletion request that only
touches dbo.Claim and misses the change table has not actually deleted the data.


What breaks in production: A weekend outage longer than the 3-day retention window is
a silent gap. Nothing errors at the time; it surfaces weeks later during a source-vs-index
reconciliation job, by which point the change rows that would explain the gap are gone.

Concept 1 — Supplemental Logging Comes First


Without supplemental logging, Oracle redo carries only the columns an UPDATE actually
changed, plus the row's ROWID — enough to redo/undo the transaction, not enough to
reconstruct a full "here is the whole row after this change" image for a downstream
consumer. ALTER DATABASE ADD SUPPLEMENTAL LOG DATA (minimal) is the baseline every CDC
setup requires; ADD SUPPLEMENTAL LOG DATA (PRIMARY KEY, UNIQUE) COLUMNS at the database
level identifies changed rows by key; ALTER TABLE claims ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS at the table level is what actually gives you full before/after row images for a
specific table.


Verify with V$DATABASE.SUPPLEMENTAL_LOG_DATA_MIN (database-level minimal logging) and
DBA_LOG_GROUPS (table-level column groups). Turning this on is a capacity decision, not
a config toggle — every logged column on every write adds to redo volume, on every
transaction, forever, not just the ones a consumer cares about.


Example:


REAL MODE — not executed here; requires a live Oracle instance:


ALTER DATABASE ADD SUPPLEMENTAL LOG DATA;
ALTER DATABASE ADD SUPPLEMENTAL LOG DATA (PRIMARY KEY, UNIQUE) COLUMNS;
ALTER TABLE claims ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;

SELECT SUPPLEMENTAL_LOG_DATA_MIN FROM V$DATABASE;
SELECT * FROM DBA_LOG_GROUPS WHERE TABLE_NAME = 'CLAIMS';

Concept 2 — LogMiner and SCN Checkpointing


DBMS_LOGMNR.ADD_LOGFILE registers archived redo logs to mine; START_LOGMNR(STARTSCN => ..., ENDSCN => ..., OPTIONS => DBMS_LOGMNR.DICT_FROM_ONLINE_CATALOG + DBMS_LOGMNR.COMMITTED_DATA_ONLY) starts the session, using the online data dictionary and
returning only committed changes. Results land in V$LOGMNR_CONTENTS, with columns SCN,
COMMIT_SCN, XID, OPERATION, SQL_REDO, SEG_NAME.


The checkpoint for the next mining run must be the highest COMMIT_SCN seen, never
the row SCN. A long transaction writes rows at SCNs that are older than the SCN at which
it actually commits and becomes visible; checkpointing on row SCN can replay rows twice or,
worse, skip a transaction whose commit is still pending. CONTINUOUS_MINE — the option
that used to let LogMiner track new redo automatically — was deprecated in 12.2 and
desupported from 19c, so a real pipeline manages its own ADD_LOGFILE calls as new
archived logs appear.


Example:


REAL MODE — not executed here; requires a live Oracle instance:


BEGIN
  DBMS_LOGMNR.ADD_LOGFILE(LOGFILENAME => '/arch/redo_001.arc', OPTIONS => DBMS_LOGMNR.NEW);
  DBMS_LOGMNR.ADD_LOGFILE(LOGFILENAME => '/arch/redo_002.arc', OPTIONS => DBMS_LOGMNR.ADDFILE);
  DBMS_LOGMNR.START_LOGMNR(
    STARTSCN => :last_checkpoint_commit_scn,
    OPTIONS  => DBMS_LOGMNR.DICT_FROM_ONLINE_CATALOG + DBMS_LOGMNR.COMMITTED_DATA_ONLY);
END;
/

SELECT SCN, COMMIT_SCN, XID, OPERATION, SEG_NAME, SQL_REDO
FROM V$LOGMNR_CONTENTS
ORDER BY COMMIT_SCN, XID;

Concept 3 — Archive-Log Retention and RAC Thread Ordering


LogMiner reads archived redo logs, not the live online logs. An RMAN backup-and-delete
policy, or Fast Recovery Area (FRA) space pressure evicting old archived logs, can delete a
log before it has been mined — the exact same class of loss as MSSQL's 3-day cleanup, just
governed by a different team's backup policy instead of a CDC retention setting.


Oracle RAC gives each instance its own redo thread. A two-node RAC cluster produces two
independent thread-1 and thread-2 archived log sequences. Mining only the logs from one
instance silently loses every change written by the other — there is no error, the miner
simply never sees rows that were never added to it. A correct pipeline adds every thread's
logs and merges the results by COMMIT_SCN across threads, and must be able to detect when
one thread's logs are simply missing from what was mined.


Example:


import dataclasses

@dataclasses.dataclass
class ThreadRow:
    thread_id: int
    commit_scn: int
    xid: str
    sql_redo: str

def merge_threads(rows_by_thread, mined_threads):
    all_rows = []
    for thread_id in mined_threads:
        all_rows.extend(rows_by_thread.get(thread_id, []))
    all_rows.sort(key=lambda r: (r.commit_scn, r.thread_id))
    return all_rows

def detect_missing_threads(expected_threads, mined_threads):
    return sorted(set(expected_threads) - set(mined_threads))

thread1 = [ThreadRow(1, 2001, "t1-A", "insert into claims values (601, ...)")]
thread2 = [ThreadRow(2, 2005, "t2-A", "insert into claims values (602, ...)")]
rows_by_thread = {1: thread1, 2: thread2}
print(merge_threads(rows_by_thread, mined_threads=[1, 2]))

Concept 4 — Mine It or Buy It: LogMiner vs GoldenGate/XStream


DBMS_LOGMNR ships with the database and costs nothing to license, but every mining
session runs on the source instance's own CPU unless the pipeline is deliberately built to
mine downstream (e.g. against a standby). XStream Out is an API that requires an
Oracle GoldenGate license — it is not a free alternative interface to the same redo data,
it is a licensed product's capture path. GoldenGate itself is a separate paid product on
top of the database license. Debezium's Oracle connector defaults to plain LogMiner and can
use XStream only where that license already exists.


This is a procurement decision with a real cost line, not a technical preference: mining
CPU on the source has a cost that scales with data volume, while a license has a cost that
does not scale with volume at all. The two costs cross at some volume, and only a written
estimate of both tells you which side of that crossing you are on.


Example:

XStream Out API call requires: an active Oracle GoldenGate license bound to the source
database, an XStream administrator user, and an outbound server configured via

Concept 1 — The High-Watermark Loop and Its Safety Lag


Polling CDC has no log to read — it queries modified_at > :last_seen on a schedule. The
lower bound is not simply the last row's timestamp; it steps back by a safety lag every
cycle (modified_at > high_watermark - safety_lag), deliberately re-reading a window of
rows that were already processed. This only works because the downstream upsert is
idempotent — Week 06's content-hash key means re-applying the same row twice is a no-op,
not a duplicate. A tuple cursor (modified_at, pk) breaks ties when two rows share the
exact same timestamp, which plain single-column timestamp comparison cannot do.


Example:


import datetime as dt

SAFETY_LAG = dt.timedelta(seconds=30)

class Source:
    def __init__(self, rows):
        self.rows = rows
    def query(self, lower, upper):
        return [(pk, ts) for pk, ts in self.rows if lower < ts <= upper]

def poll_once(source, high_watermark, now, safety_lag=SAFETY_LAG):
    """Query from (high_watermark - safety_lag) to now; the lower bound steps back
    by the safety lag every cycle, re-reading that overlap deliberately."""
    lower = high_watermark - safety_lag
    hits = source.query(lower, now)
    new_high_watermark = max([ts for _, ts in hits] + [high_watermark])
    return hits, new_high_watermark

base = dt.datetime(2026, 1, 1, 12, 0, 0)
source = Source([(1, base + dt.timedelta(seconds=5)), (2, base + dt.timedelta(seconds=40))])
hits, wm = poll_once(source, base - dt.timedelta(seconds=1), base + dt.timedelta(seconds=60))
print(hits, wm)

Concept 2 — Long-Running Transactions Commit Behind the Watermark


modified_at is stamped at write time, inside the transaction, but the row only
becomes visible to a poller at commit. A transaction that opens at T and commits at
T+8 minutes writes a timestamp of T, but a poller cannot see that row until T+8. If the
watermark has already advanced past T by the time the row becomes visible, the row is
permanently missed — not delayed, gone, because the next poll's lower bound is already
ahead of it. The safety lag has to exceed the longest transaction duration the source
sees, not just clock skew between servers. rowversion/identity columns share this exact
flaw: the value is assigned at write time, not at commit.


Example:


import random
random.seed(11)
N = 5000
durations = [round(random.expovariate(1/3) if random.random() > 0.02
                    else random.expovariate(1/240), 2) for _ in range(N)]

def count_permanently_missed(durations, safety_lag_seconds):
    return sum(1 for d in durations if d > safety_lag_seconds)

print(count_permanently_missed(durations, 30))

Concept 3 — Hard Deletes Are Invisible; Chunking Without Locking


Polling can only ever match rows against modified_at > watermark — a DELETE leaves no
row to match, so polling never observes a delete. The remedy is one of: a soft-delete
flag the application sets instead of deleting, a trigger-writing audit table, or a
scheduled key-set reconciliation comparing the full source key set against the index's key
set (this feeds directly into Week 11's monitoring). An orphaned vector left behind by an
unobserved delete keeps being retrieved as if the record still existed.


Extracting the full key set for reconciliation should not be one long table scan under a
lock: chunk it with keyset pagination (WHERE pk > :last_pk ORDER BY pk fetching a fixed
chunk size) under snapshot isolation. NOLOCK is not a substitute — under NOLOCK a page
split during the scan can cause a row to be read twice or missed entirely, the opposite of
the reliability reconciliation needs.


Example:


import random
random.seed(12)
SOURCE_TOTAL_KEYS = 50_000
source_keys = set(range(1, SOURCE_TOTAL_KEYS + 1))
index_keys = set(range(1, SOURCE_TOTAL_KEYS + 1))
deleted = set(random.sample(sorted(source_keys), 37))
source_keys -= deleted

def reconcile(source_keys, index_keys):
    return index_keys - source_keys, source_keys - index_keys

orphans, missing = reconcile(source_keys, index_keys)
print(len(orphans), orphans == deleted)

Concept 1 — The Batch Window Is a Physical Constraint


A mainframe nightly cycle — online region down at 23:30, batch jobs run overnight, the
extract lands around 04:40 — is scheduled around the business day and the batch job
dependency graph, not around your pipeline's SLA. The floor for anything downstream of that
extract is extract_landing_time + your_own_processing_time, and no engineering on the
downstream side moves the first term. This is worth stating plainly, because it is the
single most common latency-budget mistake in this space: engineering effort spent shaving
seconds off a pipeline that is fed by an extract that will not exist for another six hours.


Example:


import datetime as dt
EXTRACT_LANDS_AT = dt.time(4, 40)

def earliest_freshness(extract_lands_at, processing_minutes):
    landed = dt.datetime.combine(dt.date(2026, 1, 1), extract_lands_at)
    return (landed + dt.timedelta(minutes=processing_minutes)).time()

print(earliest_freshness(EXTRACT_LANDS_AT, 22))

Concept 2 — Writing a Staleness Budget Per Use Case


The professional deliverable this week builds toward is not a faster pipeline; it is a
written, per-use-case maximum acceptable staleness, agreed with the business, checked
against what the source can actually deliver (Concept 1's floor, or Day 3's polling floor,
or Day 1/2's CDC floor). Feasibility gets marked explicitly, in the document, rather than
discovered later when someone complains an answer was stale — "explicitly infeasible, given
this source, unless we escalate to X" is a legitimate, professional answer.


Example:


import dataclasses

Concept 3 — Catch-Up Backfill and Event-Time Merge


A catch-up backfill (reprocessing a period after an outage, or the daily nightly file
itself) must apply changes ordered by event time, not arrival order — last-writer-wins
keyed on (entity, event_time, seq). Applying in arrival order lets a chronologically
older batch record silently overwrite a chronologically newer value that a live stream
already wrote.


The nightly file is, from a streaming watermark's point of view, one enormous burst of
"late" data — every record in it arrived hours after events with similar event times were
already processed. A naive watermark policy drops anything that late as unusable, which
throws away the whole file. The fix is an allowed-lateness window: records within it
merge normally; records past it route to a side output for out-of-band reconciliation
instead of vanishing.


Example:


import dataclasses

@dataclasses.dataclass
class Event:
    entity: str
    event_time: float
    arrival_time: float
    seq: int
    value: str
    source: str

def last_writer_wins_merge(events):
    latest = {}
    for ev in sorted(events, key=lambda e: (e.entity, e.event_time, e.seq)):
        cur = latest.get(ev.entity)
        if cur is None or (ev.event_time, ev.seq) >= (cur.event_time, cur.seq):
            latest[ev.entity] = ev
    return latest

events = [Event("claim-501", 10.0, 10.001, 0, "status=OPEN", "stream"),
          Event("claim-501", 14.0, 14.001, 0, "status=CLOSED", "stream")]
print(last_writer_wins_merge(events))

Concept 1 — A Source Capability Matrix, System by System


The only honest way to set a latency target is to build a matrix, one row per source
system, of what mechanism it actually supports, what it costs, and what its floor latency
genuinely is — then derive achievable end-to-end freshness from that, never the reverse.
The matrix has to include the row where the honest entry is "nightly": pretending otherwise
does not change the mainframe's schedule, it only produces a documented promise nobody can
keep.


Example:


import dataclasses

@dataclasses.dataclass
class SourceCapability:
    name: str
    mechanism: str
    floor_latency_seconds: int
    delete_visible: bool

sources = [
    SourceCapability("MSSQL claims OLTP", "log-based CDC", 30, True),
    SourceCapability("Mainframe policy core", "nightly batch extract", 6 * 3600, False),
]

def achievable_freshness(source, downstream_seconds):
    return source.floor_latency_seconds + downstream_seconds

for s in sources:
    print(s.name, achievable_freshness(s, 15))

Concept 2 — The Cost of Forcing CDC Onto a Source That Cannot Support It


Every mechanism from Day 1-3 has a real cost when pushed past what the source can
comfortably support: aggressive polling against a busy OLTP core adds query contention on
top of the transactional workload it was already carrying; full supplemental logging on a
busy Oracle instance grows redo volume on every write, forever; MSSQL's CDC capture lag
blocks transaction-log truncation, and a log volume that fills because capture never caught
up takes down every write on the source — the CDC consumer becomes the outage, not a
symptom of one. The mainframe case is the cleanest: there is no mechanism to push past its
limits, because there is no mechanism at all besides the nightly file.


Example:


ASSUMED_QUERY_COST_MS = 8
def poll_load(interval_seconds, query_cost_ms=ASSUMED_QUERY_COST_MS):
    qps = 1 / interval_seconds
    return qps, qps * query_cost_ms

print(poll_load(5))

Concept 3 — Hybrid: Stream Where Possible, Batch Where Not, One Index


The design this week has been building toward: one vector index, fed by whichever
mechanism each source actually supports, with per-record provenance —
source_system, mechanism, event_time, ingested_at, staleness_seconds — carried on
every record. Query time then annotates or refuses a result that is older than the
requesting use case's staleness budget, instead of returning every record as if the index
were uniformly fresh. The index looking uniform is exactly the failure mode Day 4's Reality
Check named: nobody remembers a third of it is 14 hours old until an answer built on it is
wrong.


Example:


import dataclasses, datetime as dt

@dataclasses.dataclass
class UnifiedRecord:
    entity_id: str
    source_system: str
    mechanism: str
    event_time: dt.datetime
    ingested_at: dt.datetime
    staleness_seconds: float

def build_unified_record(entity_id, source_system, mechanism, event_time, ingested_at):
    return UnifiedRecord(entity_id, source_system, mechanism, event_time, ingested_at,
                          (ingested_at - event_time).total_seconds())

def freshness_gate(record, max_staleness_seconds):
    if record.staleness_seconds > max_staleness_seconds:
        return "REFUSED"
    return "OK"

now = dt.datetime(2026, 1, 2, 8, 0, 0)
rec = build_unified_record("claim-501", "mssql_claims_oltp", "cdc", now - dt.timedelta(seconds=40), now)
print(freshness_gate(rec, 60))

BFSI Reality Check — Day 5


Legacy angle: This ADR's real audience is not another data engineer — it is the DBA

Compliance angle: A declared, versioned staleness budget per use case is the evidence
artifact a regulator or auditor actually wants — proof the organisation knew how fresh its
data was allowed to be for a given decision, rather than a retroactive excuse after an

What breaks in production: The unified index looks the same at every query regardless
of which source fed a given record. Nobody remembers a third of it is 14 hours old until
someone traces a wrong answer back to a mainframe-sourced record that was already stale
when it was ingested.




Architecture Decision — Week 07


Choosing between: log-based CDC (seconds), polling micro-batch (minutes), and scheduled
batch (hours) — decided per source system, not per programme.


Rule of thumb: Pick the mechanism the source can actually support, and derive the
latency target from that choice — never the reverse. Do not set a "near real time" target
first and then go looking for a mechanism to hit it; Day 4 and Day 5 both showed what that
produces: a written promise a mainframe extract or an unwilling DBA team was never going to
keep.


Use log-based CDC where the platform team will actually enable and fund it (SQL Server
Agent running, an Oracle supplemental-logging change accepted, archive-log retention long
enough to cover realistic outages) and where delete-visibility and strict ordering
genuinely matter — sanctions-adjacent and fraud-adjacent paths, where a missed delete or an
out-of-order update is not just stale, it is wrong. Use polling with a safety lag that
provably exceeds the longest transaction the source actually produces (Day 3, Concept 2 —
measure it, do not assume it), paired with a scheduled key-set reconciliation job to catch
the hard deletes polling structurally cannot see, wherever CDC is refused rather than
merely inconvenient. Use scheduled batch, and say so plainly in the documentation as
"nightly", wherever the source only ever produces a batch — a mainframe nightly extract is
not "near real time with a long tail"; it is batch, and disguising it as anything else is
exactly the failure mode this ADR exists to prevent. Escalate to a licensed product
(GoldenGate/XStream, or an equivalent) only when a written staleness budget for a specific,
named use case proves that budget is infeasible any other way (Day 2, Concept 4's
break-even method) — never as a default first reach, because the license cost is real and
recurring whether or not the volume ever justifies it.


The deliverable of Phase 1, taken as a whole, is not a single uniformly fast pipeline — it
is one vector index carrying per-record provenance (source_system, mechanism,
event_time, ingested_at, staleness_seconds) and a written, per-use-case staleness
budget checked against what each source can actually deliver, with query-time logic that
annotates or refuses a result older than its use case allows rather than presenting the
whole index as uniformly fresh. The failure mode this entire phase exists to prevent is
Weeks 01 through 06 building a beautifully engineered streaming vector pipeline against a
source that structurally cannot feed it — HNSW tuning, hybrid search and Kafka ingestion
all optimizing the wrong end of a system whose floor was set, from day one, by a mainframe
batch window nobody asked about.
