Week 01 established that exact and approximate vector search both answer the same question: "which stored vectors are closest to this query vector." This week asks a different question first — whether vector search is even the right tool for a given query. A claims database is full of exact identifiers (POL-8842-C, CLM-2024-114858) that a dense embedding was never trained to treat as special strings, and BM25 — the decades-old lexical scoring function behind most production search engines before embeddings existed — handles exactly this case by design. This week builds BM25 from its formula, runs a stand-in dense embedder to see it fail on identifiers for real, and then fuses the two with reciprocal rank fusion, because the honest answer to "BM25 or vectors" is usually both.

Concept 1 — The BM25 Scoring Formula in NumPy

BM25 scores a document against a query as a sum over query terms, each weighted by how rare the term is across the corpus (its inverse document frequency, IDF) and how strongly the term appears in this particular document relative to the corpus's typical document length. For a term with document frequency df in a corpus of N documents, and a document of length L (tokens) containing the term f times, with corpus average length avgdl:

IDF(term) = ln(1 + (N - df + 0.5) / (df + 0.5))

BM25(term, doc) = IDF(term) * [ f * (k1 + 1) ] / [ f + k1 * (1 - b + b * L / avgdl) ]

score(query, doc) = sum over query terms of BM25(term, doc)

rank_bm25 is not installed in this environment (confirmed: pip show rank-bm25 finds nothing), so every executed block this week implements BM25 directly from this formula in NumPy — the formula is short enough that there is no real teaching loss, and it removes any ambiguity about which exact variant is running.

Example:

import re
import numpy as np

def tokenize(text):
    # Keeps letter-digit-hyphen runs (POL-8842-C) as a single token instead of
    # shredding it -- Concept 4 shows why that choice matters.
    return re.findall(r"[a-z0-9]+(?:-[a-z0-9]+)*", text.lower())

corpus = [
    "Policy POL-8842-C: water damage claim, ceiling leak from upstairs pipe burst reported by tenant",
    "Claim under policy POL-8842-C for escape of water damage to kitchen ceiling, adjuster assigned",
    "Policy POL-8842-C renewal notice, no open claims, premium payment received on schedule",
    "Policy POL-9013-A rear-end collision claim, minor bumper damage, two vehicles involved",
    "Policy POL-7754-D theft of laptop and jewelry from parked vehicle, police report filed",
    "Policy POL-6620-B fire damage to garage roof, contractor estimate attached to claim file",
]

tokens = [tokenize(d) for d in corpus]
N = len(corpus)
doc_lens = np.array([len(t) for t in tokens])
avgdl = doc_lens.mean()

df = {}
for t in tokens:
    for w in set(t):
        df[w] = df.get(w, 0) + 1

def idf(term):
    n = df.get(term, 0)
    return np.log(1 + (N - n + 0.5) / (n + 0.5))

def bm25_score(query_terms, doc_tokens, doc_len, k1=1.5, b=0.75):
    counts = {}
    for w in doc_tokens:
        counts[w] = counts.get(w, 0) + 1
    score = 0.0
    for term in query_terms:
        if term not in counts:
            continue
        f = counts[term]
        num = f * (k1 + 1)
        denom = f + k1 * (1 - b + b * doc_len / avgdl)
        score += idf(term) * (num / denom)
    return score

print(f"N={N}  avgdl={avgdl:.4f}")
for term in ("pol-8842-c", "water", "policy"):
    print(f"{term:<12} df={df.get(term, 0)}  idf={idf(term):.4f}")

query = tokenize("POL-8842-C")
for i, t in enumerate(tokens):
    s = bm25_score(query, t, doc_lens[i])
    print(f"doc {i}  bm25={s:.4f}  len={doc_lens[i]}")

Concept 2 — k1: Term-Frequency Saturation


k1 controls how much repeating a term inside a document keeps adding to its score. A term
appearing 10 times is real evidence of relevance, but it should not score 10x a single occurrence —
diminishing returns is the whole point. Low k1 saturates fast (approaching binary "present or
not"); high k1 stays close to linear in term frequency. Typical values sit in 1.2-2.0.


Example:


import numpy as np

def tf_component(f, L, avgdl, k1, b):
    return (f * (k1 + 1)) / (f + k1 * (1 - b + b * L / avgdl))

print("TF component vs term frequency f, at L = avgdl (b has no effect here):")
for k1 in (0.5, 1.2, 2.0, 100.0):
    vals = [round(tf_component(f, 15, 15, k1, 0.75), 3) for f in (1, 2, 4, 8, 16, 32)]
    print(f"  k1={k1:>5}  f=1..32 -> {vals}")

Concept 3 — b: Length Normalization


b controls how much a document's length relative to avgdl penalizes its score. b=0 disables
length normalization entirely — a 500-word document and a 5-word document with the same term
frequency score identically. b=1 applies full normalization. The BM25 default, b=0.75, is a
compromise: a longer document is expected to occasionally repeat a term without that repetition
implying only length inflation.


Example:


import numpy as np

    return (f * (k1 + 1)) / (f + k1 * (1 - b + b * L / avgdl))

    print(f"  b={b:>4}  L=5,10,15,30,60 -> {vals}")

Concept 4 — Tokenization, BM25Okapi vs BM25Plus, and Negative IDF


Two more decisions belong beside k1 and b, both with real production consequences.


Tokenization that does not shred identifiers. A naive tokenizer that splits on any non-letter
character turns POL-8842-C into three meaningless tokens (pol, 8842, c), each of which then
matches unrelated documents that merely contain the digits "8842" or the letter "c" somewhere. The
regex [a-z0-9]+(?:-[a-z0-9]+)* used all week keeps a hyphenated alphanumeric run intact as one
token.


BM25Okapi vs BM25Plus, and why IDF can go negative. The smoothed IDF this week uses,
ln(1 + (N-df+0.5)/(df+0.5)), is always non-negative. rank_bm25's BM25Okapi — the library this
environment does not have installed — instead uses the older, unsmoothed ratio
ln((N-df+0.5)/(df+0.5)). That ratio goes negative once a term appears in more than half the
corpus, because the numerator becomes smaller than the denominator. BM25Okapi floors this with an
epsilon parameter (default 0.25, multiplied by the corpus's average IDF) rather than letting a
common term's score actively subtract from a document's total — but a narrow-vocabulary claims
corpus, where a word like "policy" legitimately appears in every single document, hits this floor
routinely, not as an edge case. BM25Plus sidesteps the whole problem with a different IDF
(ln((N+1)/df), always positive) and additionally adds a delta (default 1.0) to the TF component,
so a long document with only a middling term frequency is not driven to a score near zero the way
plain BM25's length normalization can push it.


Example:


import numpy as np

def idf_smoothed(df, N):
    return np.log(1 + (N - df + 0.5) / (df + 0.5))

def idf_unsmoothed(df, N):   # rank_bm25's BM25Okapi formula, before its epsilon floor
    return np.log((N - df + 0.5) / (df + 0.5))

BFSI Reality Check — Day 1


Legacy angle: A core claims system's free-text notes field is exactly the "narrow vocabulary,
every document repeats the same words" corpus that breaks unsmoothed IDF. Words like "policy",
"claim" and "damage" appear in nearly every record because adjusters were trained to write in fixed
templates. That is precisely the corpus shape where the smoothed-vs-unsmoothed IDF choice stops being
academic.


Compliance angle: A tokenizer that shreds POL-8842-C into pol/8842/c does not just hurt
recall — it can produce spurious matches: a customer's exact-identifier lookup surfacing an unrelated
claim that happens to share the digits "8842". In a regulated workflow where "which record did this
system surface, and why" needs a clean answer, an identifier-preserving tokenizer is not a nicety.


What breaks in production: k1 and b left at library defaults tuned for web-search-style
corpora (long, varied documents) rather than short, templated claims notes. Nothing errors — scores
simply rank in a way nobody validated against this corpus's actual length distribution.

Concept 1 — The Identifier Failure, Measured


Dense embeddings are trained to place semantically similar text near each other. An exact identifier
like POL-8842-C is not a semantic concept — it is an arbitrary string, and a model has no reason to
treat it specially unless it was explicitly trained to. To see this failure without needing a real
embedding model (none is available offline in this environment), this week uses a deterministic
stand-in: character trigrams of the text, each hashed with zlib.crc32 to seed a small Gaussian
projection, summed and L2-normalized. It is not a real embedding model, but it reproduces the
property that matters here — it is sensitive to surface text, not to the meaning of an identifier as
a single unit.


Example:


import zlib
import numpy as np

corpus = [
    "Policy POL-8842-C: water damage claim, ceiling leak from upstairs pipe burst reported by tenant",
    "Claim under policy POL-8842-C for escape of water damage to kitchen ceiling, adjuster assigned",
    "Policy POL-8842-C renewal notice, no open claims, premium payment received on schedule",
    "Policy POL-9013-A rear-end collision claim, minor bumper damage, two vehicles involved",
    "Policy POL-7754-D theft of laptop and jewelry from parked vehicle, police report filed",
    "Policy POL-6620-B fire damage to garage roof, contractor estimate attached to claim file",
]

DIM = 32

def trigrams(text):
    t = "  " + text.lower() + "  "   # pad so short strings still produce a trigram
    return [t[i:i+3] for i in range(len(t) - 2)]

def embed(text, dim=DIM):
    vec = np.zeros(dim)
    for gram in trigrams(text):
        seed = zlib.crc32(gram.encode("utf-8"))
        rng = np.random.default_rng(seed)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

doc_vecs = np.array([embed(d) for d in corpus])

def cosine_rank(query_text):
    q = embed(query_text)
    scores = doc_vecs @ q
    order = np.argsort(-scores)
    print(f"query: {query_text!r}")
    for rank, i in enumerate(order):
        print(f"  rank {rank+1}  doc {i}  cos={scores[i]:.4f}  {corpus[i][:55]}")

cosine_rank("POL-8842-C")
cosine_rank("escape of water damage to a ceiling")

Concept 2 — A Nonsense Query and False Confidence


BM25 has a property worth naming explicitly: when a query shares no vocabulary with any document, it
says so, honestly, with a score of exactly zero everywhere. A dense similarity search has no such
"nothing matches" signal — cosine similarity always produces a ranked list, because it is measuring
geometric closeness, not lexical evidence, and closeness is never exactly undefined.

Concept 3 — Negation and Numeric Thresholds in Coverage Text


Bag-of-words scoring, whether BM25 or a bag-of-trigrams embedding, counts term overlap. Neither
mechanism, by construction, distinguishes "policy covers flood damage" from "policy excludes flood
damage" — both sentences share the same vocabulary. This matters specifically in coverage text, where
the entire business meaning of a clause can flip on a single word like "excludes" or a numeric
threshold like "up to $50,000".


Example:

ext_avgdl = ext_doc_lens.mean()

    for w in set(t):
        ext_df[w] = ext_df.get(w, 0) + 1

def ext_idf(term):
    n = ext_df.get(term, 0)
    return np.log(1 + (len(extended_corpus) - n + 0.5) / (n + 0.5))

def ext_bm25(query_terms, doc_tokens, doc_len, k1=1.5, b=0.75):
    counts = {}
    for w in doc_tokens:
        counts[w] = counts.get(w, 0) + 1
    score = 0.0
    for term in query_terms:
        if term not in counts:
            continue
        f = counts[term]
        num = f * (k1 + 1)
        denom = f + k1 * (1 - b + b * doc_len / ext_avgdl)
        score += ext_idf(term) * (num / denom)
    return score

query = tokenize("flood damage covered")
scores = [ext_bm25(query, t, ext_doc_lens[i]) for i, t in enumerate(extended_tokens)]
order = np.argsort(-np.array(scores))
for rank, i in enumerate(order):
    print(f"  rank {rank+1}  doc {i}  bm25={scores[i]:.4f}  {extended_corpus[i][:70]}")

Concept 1 — Why BM25 and Cosine Scores Are Not Comparable


BM25 and cosine similarity measure fundamentally different things on fundamentally different scales.
BM25 is unbounded above, exactly 0.0 for a document with no query-term overlap, and its magnitude
depends on the corpus's IDF distribution and the query's length — a BM25 score of 0.7 means something
different in a two-document toy corpus than in a ten-million-document production index. Cosine
similarity is bounded to [-1, 1] and, for real (non-adversarial) text, is rarely close to 0. Adding
or comparing these two numbers directly is arithmetic on incompatible units — it looks like a valid
operation because both are floats, but there is no meaningful sense in which "0.7 of BM25" and "0.7
of cosine" are the same amount of relevance.


Example:

Concept 2 — Reciprocal Rank Fusion


Reciprocal Rank Fusion (RRF) sidesteps the score-comparability problem by discarding scores entirely
and fusing only each system's rank for a document:


RRF(doc) = sum over systems s of 1 / (k + rank_s(doc))

with k = 60, the constant from Cormack, Clarke & Buettcher's 2009 paper introducing the method. k
is not a cutoff — every document that appears in either ranking contributes — it is a damping term
that keeps rank 1 from dominating the sum outright (1/(60+1) vs 1/(60+2) differ by much less than
1/1 vs 1/2 would).


Example:


import numpy as np

bm25_scores = np.array([0.6659, 0.6659, 0.7140, 0.0000, 0.0000, 0.0000])
cos_scores = np.array([0.5246, 0.4416, 0.4844, 0.4457, 0.5201, 0.0753])

def ranks_of(scores):
    order = np.argsort(-scores)
    r = np.zeros(len(scores), dtype=int)
    for pos, doc in enumerate(order):
        r[doc] = pos + 1   # 1-indexed rank
    return r

bm25_r = ranks_of(bm25_scores)
cos_r = ranks_of(cos_scores)
print("doc   bm25_rank  cos_rank")
for d in range(6):
    print(f"{d:>3}   {bm25_r[d]:>9}  {cos_r[d]:>8}")

K = 60
rrf = 1.0 / (K + bm25_r) + 1.0 / (K + cos_r)
print("\nRRF (k=60):")
for d in range(6):
    print(f"  doc {d}  rrf={rrf[d]:.6f}")
print("ranking:", np.argsort(-rrf).tolist())

Concept 3 — Min-Max vs Z-Score vs a Weighted Alpha Blend


Score-based fusion is not automatically wrong — it is unavoidable when a use case genuinely needs
tunable weighting between lexical and semantic signal, e.g. "trust BM25 twice as much as cosine for
this query type." The two common normalizers, min-max and z-score, both attempt to put BM25 and
cosine on the same footing before blending. Both share the same weakness: they are defined per query,
from that query's own score distribution, so one outlier score redefines the scale for everyone else
in the same result set.


Example:


import numpy as np

bm25_scores = np.array([0.6659, 0.6659, 0.7140, 0.0000, 0.0000, 0.0000])
cos_scores = np.array([0.5246, 0.4416, 0.4844, 0.4457, 0.5201, 0.0753])

def minmax(x):
    lo, hi = x.min(), x.max()
    return (x - lo) / (hi - lo) if hi > lo else np.zeros_like(x)

def zscore(x):
    mu, sigma = x.mean(), x.std()
    return (x - mu) / sigma if sigma > 0 else np.zeros_like(x)

bm25_mm, cos_mm = minmax(bm25_scores), minmax(cos_scores)
alpha = 0.5
blend_mm = alpha * bm25_mm + (1 - alpha) * cos_mm
print("min-max alpha-blend ranking:", np.argsort(-blend_mm).tolist())

bm25_z, cos_z = zscore(bm25_scores), zscore(cos_scores)
blend_z = alpha * bm25_z + (1 - alpha) * cos_z
print("z-score alpha-blend ranking:", np.argsort(-blend_z).tolist())

# Instability check: one outlier BM25 score (e.g. a rare-term exact match) on a DIFFERENT query
bm25_outlier = np.array([0.6659, 0.6659, 0.7140, 0.0, 0.0, 9.0])
print("\ndoc 2's min-max score without the outlier:", round(minmax(bm25_scores)[2], 4))
print("doc 2's min-max score with doc 5 spiking to 9.0:", round(minmax(bm25_outlier)[2], 4))

BFSI Reality Check — Day 3


Legacy angle: A core system migrating from a keyword-only search box to hybrid retrieval usually
has years of tuned relevance behavior riding on the old BM25-only ranking. RRF's rank-based fusion
tends to preserve "documents that were already top BM25 hits stay near the top" better than a score
blend does, which matters when a change in search ranking itself needs a change-control ticket.


Compliance angle: A score-blending weight (alpha) is a tunable business decision masquerading
as an engineering parameter — whoever sets alpha=0.8 favoring lexical results over semantic ones is
making a real policy choice about which claims get surfaced first. Record alpha, and any
normalization method, as a versioned configuration value, the same way Week 01 treated the embedding
metric.


What breaks in production: Comparing today's blended score against yesterday's for the "same"
query and treating the difference as a relevance signal. Min-max and z-score are recomputed fresh
from each query's own result set, so the same document's normalized score is not stable across
different queries or different corpus states — only RRF's rank-based approach is comparably stable
across runs.

Concept 3 — One CTE Returning Both Rankings for Fusion


REAL MODE — not executed (requires a live PostgreSQL instance with pg_trgm/pgvector installed; none is available in this environment):


Both the lexical and semantic candidate sets, and their rank fusion, can be expressed in a single
query — no application-side round trip needed to fetch two result sets and merge them in Python.


WITH lexical AS (
    SELECT id,
           ts_rank_cd(doc_tsv, websearch_to_tsquery('english', :query_text)) AS lex_rank
    FROM claims
    WHERE doc_tsv @@ websearch_to_tsquery('english', :query_text)
),
semantic AS (
    SELECT id,
           1 - (embedding <=> :query_embedding) AS cos_sim
    FROM claims
    ORDER BY embedding <=> :query_embedding
    LIMIT 50
),
lex_ranked AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY lex_rank DESC) AS lex_pos FROM lexical
),
sem_ranked AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY cos_sim DESC) AS sem_pos FROM semantic
)
SELECT COALESCE(l.id, s.id) AS id,
       COALESCE(1.0 / (60 + l.lex_pos), 0) + COALESCE(1.0 / (60 + s.sem_pos), 0) AS rrf_score
FROM lex_ranked l
FULL OUTER JOIN sem_ranked s ON l.id = s.id
ORDER BY rrf_score DESC
LIMIT 10;

Expected output (shape only): up to 10 rows of (id, rrf_score), ordered highest fusion score first
— a document appearing in only one of the two candidate sets still gets a score (via COALESCE's
0 for the missing side), while a document in neither CTE's result set never appears at all, unlike
the from-scratch RRF in Day 3 which ranked every document in the corpus regardless of match.


One deliberate design choice worth naming: lexical only contains rows where doc_tsv @@ query
actually matched. A document with zero lexical overlap is absent from that CTE, not present with
a rank at the bottom — which is a more accurate reflection of "no lexical evidence" than Day 3's toy,
where every document received a BM25 rank even when its score was 0.0.


The pure-Python block below simulates exactly this query's arithmetic — the same ROW_NUMBER() +
1/(k+rank) fusion, applied to plain Python dicts standing in for what the two CTEs would return —
so the fusion logic itself is checked even without a live database.

BFSI Reality Check — Day 4


Legacy angle: Many BFSI shops already run Postgres for the system of record and would need a
change-management case to introduce a dedicated search engine (Elasticsearch/OpenSearch) purely for

materially different, less mature lexical ranking function than a dedicated engine's real BM25.


Compliance angle: A single CTE that computes and returns both rankings in one query is also a
single artifact an auditor can read end-to-end to answer "how was this result ranked" — versus two
separately-tuned systems (a search engine plus a vector database) whose combined behavior lives partly
in application code that may not be captured by either system's own audit log.


What breaks in production: ts_rank_cd and cosine similarity share the same non-comparability
problem as BM25 and cosine (Day 3 Concept 1) — a team that swaps this week's RRF fusion for a raw
lex_rank + cos_sim sum inside the CTE reintroduces exactly the scale-mismatch bug this week spent
three days establishing, just inside SQL instead of Python.

Concept 1 — Graded Relevance Judgments and nDCG@10


A labeled query set needs more than a binary "relevant/not relevant" per document — a document that
is the exact right claim is worth more than one that is merely topically related. Graded relevance
(commonly 0-3) captures that, and nDCG (normalized Discounted Cumulative Gain) is the standard metric
built for graded judgments:


gain(rel)      = 2^rel - 1
DCG@k          = sum over positions i=1..k of gain(rel_i) / log2(i + 1)
nDCG@k         = DCG@k / IDCG@k     (IDCG = DCG of the ideal, relevance-sorted ordering)

The exponential gain rewards a top-graded document heavily; a linear-gain variant (gain = rel
instead of 2^rel - 1) exists in some implementations and treats grade differences more evenly — the
exponential form is what most published benchmarks use and what this week uses throughout.


Example:


import numpy as np

def dcg(order, rel, k):
    total = 0.0
    for i, doc in enumerate(order[:k]):
        gain = (2 ** rel.get(doc, 0)) - 1
        total += gain / np.log2(i + 2)   # position is i+1 (0-indexed i), discount log2(pos+1)
    return total

def ndcg_at_k(order, rel, k):
    ideal_order = sorted(rel.keys(), key=lambda d: -rel[d])
    idcg = dcg(ideal_order, rel, k)
    return dcg(order, rel, k) / idcg if idcg > 0 else 0.0

# Query "POL-8842-C": docs 0 and 1 are the fullest narrative matches (graded 3),
# doc 2 (the bare renewal notice) is a real but weaker match (graded 2).
relevance = {0: 3, 1: 3, 2: 2}

bm25_order   = [2, 0, 1, 3, 4, 5]   # from Day 1
vector_order = [0, 4, 2, 3, 1, 5]   # from Day 2 -- doc 4 (wrong policy) intrudes at rank 2
hybrid_order = [0, 2, 4, 1, 3, 5]   # from Day 3's RRF fusion

for name, order in (("bm25", bm25_order), ("vector", vector_order), ("hybrid", hybrid_order)):
    print(f"{name:<7}  nDCG@10 = {ndcg_at_k(order, relevance, 10):.4f}")

Concept 2 — MRR and Recall@50


Two simpler, complementary metrics fill gaps nDCG leaves open. MRR (Mean Reciprocal Rank) is the
mean, over queries, of 1 / rank of the first relevant result (0 if no relevant result is retrieved
at all) — it captures "how far down the list until the user sees anything useful," which matters most
for queries where any relevant hit is enough (an identifier lookup is the clearest case). Recall@k
is the fraction of all known-relevant documents that appear anywhere in the top k — it captures
completeness, which nDCG (which only rewards position, not presence) does not directly measure.


Example:


def mrr(order, rel):
    for i, doc in enumerate(order):
        if rel.get(doc, 0) > 0:
            return 1.0 / (i + 1)
    return 0.0

def recall_at_k(order, rel, k):
    relevant = set(rel.keys())
    if not relevant:
        return 0.0
    return len(set(order[:k]) & relevant) / len(relevant)

relevance = {0: 3, 1: 3, 2: 2}
bm25_order   = [2, 0, 1, 3, 4, 5]
vector_order = [0, 4, 2, 3, 1, 5]
hybrid_order = [0, 2, 4, 1, 3, 5]

for name, order in (("bm25", bm25_order), ("vector", vector_order), ("hybrid", hybrid_order)):
    print(f"{name:<7}  MRR = {mrr(order, relevance):.4f}  recall@50 = {recall_at_k(order, relevance, 50):.4f}")

size of thousands of documents, recall@50 becomes exactly the metric that would expose a system
missing relevant documents entirely rather than merely mis-ranking ones it did retrieve.

Concept 3 — Per-Query-Type Breakdown and Regression vs the Vector-Only Baseline


An aggregate metric across all queries hides exactly the pattern this week has been building toward:
identifier-lookup queries and conceptual queries fail differently, so they should be reported
separately, not blended into one mean that a strong showing on one type can mask a weakness on the
other. The regression check that actually matters before shipping a hybrid system is not "is hybrid's
aggregate score higher" — it is "is hybrid strictly no worse than the vector-only baseline it is
replacing, for every query type," since a hybrid system that trades vector-only's conceptual strength
for lexical gains elsewhere would be a regression for exactly the queries the system already handled
well.


Example:


# id_lookup: relevance {0:3, 1:3, 2:2}, orders from Day 1/2/3.
# conceptual: relevance {0:3, 1:3}, orders from Concept 1's Exercise (all three orders identical: [0,1,...]).
id_orders = {"bm25": [2, 0, 1, 3, 4, 5], "vector": [0, 4, 2, 3, 1, 5], "hybrid": [0, 2, 4, 1, 3, 5]}
concept_orders = {"bm25": [1, 0, 2, 3, 4, 5], "vector": [0, 1, 5, 4, 2, 3], "hybrid": [0, 1, 5, 4, 2, 3]}
id_rel = {0: 3, 1: 3, 2: 2}
concept_rel = {0: 3, 1: 3}

print(f"{'system':<7} {'id_lookup':>10} {'conceptual':>11} {'mean':>7}")
means = {}
for system in ("bm25", "vector", "hybrid"):
    id_score = ndcg_at_k(id_orders[system], id_rel, 10)
    concept_score = ndcg_at_k(concept_orders[system], concept_rel, 10)
    mean = (id_score + concept_score) / 2
    means[system] = mean
    print(f"{system:<7} {id_score:>10.4f} {concept_score:>11.4f} {mean:>7.4f}")

delta = means["hybrid"] - means["vector"]
print(f"\nhybrid vs vector-only baseline: {delta:+.4f}  ({'improvement' if delta > 0 else 'regression'})")

BFSI Reality Check — Day 5


Legacy angle: Building a graded relevance judgment set requires a domain expert (a claims adjuster
or underwriter) to label queries, which is real, recurring human cost — not a one-time engineering
task. A labeled set built once against today's product line goes stale as new coverage types and
exclusion wordings are added, the same way any test fixture rots against a moving system.


Compliance angle: EU AI Act Article 15's declared-accuracy-metric expectation, already raised in
Week 01, applies directly here: nDCG@10/MRR/recall@50 measured against a versioned, graded judgment
set is exactly the kind of reproducible retrieval-quality claim that supports a documented accuracy
statement for a high-risk system, provided the judgment set and the harness are both version-controlled
artifacts rather than a one-time spreadsheet.


What breaks in production: Reporting only the aggregate mean and shipping a change that improves
it. This lesson's own numbers show a hybrid config beating vector-only on aggregate nDCG@10 while
being identical to it on the conceptual query type — a real system could just as easily improve on
aggregate while quietly regressing one query type that a mean, by construction, cannot reveal without
the per-query-type breakdown Concept 3 insists on.




Architecture Decision — Week 05


Choosing between: BM25-only lexical search, vector-only dense search, and hybrid retrieval fused
by RRF (or, for a use case that genuinely needs it, a tuned score blend).


Rule of thumb: use BM25-only when the query population is dominated by exact identifiers, codes,
or short structured terms where a bag-of-words match is the actual right answer and the added
infrastructure of a vector index buys nothing — the from-scratch scoring in Day 1 is enough to ship
that, no embedding model required. Use vector-only when queries are genuinely open-ended natural
language with no meaningful identifier component and a labeled evaluation set (Day 5) confirms dense
search alone already meets the bar; this is rarely the right resting point for a claims/policy corpus
specifically because both query types coexist in the same product. Move to hybrid, fused by RRF at
k=60, as the default once real queries mix both types — Day 2's measured failure (a wrong-policy
document beating two genuine matches under cosine alone) is not a corner case for this domain, it is
the routine shape of an identifier query, and Day 5's per-query-type nDCG showed hybrid winning
specifically on that query type without losing anything on the conceptual one. Reserve a tuned
alpha-weighted score blend for the narrow case where a stakeholder has an explicit, documented
reason to trust one signal more than the other for a specific query class — and even then, treat
alpha as a versioned configuration value (Day 3's BFSI Reality Check), not a knob tuned once and
forgotten, because the min-max/z-score instability this week measured means an untracked change
elsewhere in the score distribution can silently move that blend's behavior without anyone touching
alpha itself.
