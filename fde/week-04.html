Concept 1 — M Is Graph Degree, and Levels Are Assigned by a Coin Flip

M is the maximum number of neighbours each node keeps at the graph's base layer (layer 0); mmax0, the base-layer cap, is conventionally 2*M. Every inserted node is also assigned a top layer by an exponential draw: mL = 1 / ln(M), and level = floor(-ln(U) * mL) for a uniform random U. The probability of landing at layer 1 or higher works out to 1/M — a smaller M means more nodes get long-range layers, a larger M means the hierarchy stays flatter.

This is a build-time choice. There is no "reconfigure M" operation in a real HNSW index — changing it means re-inserting every vector into a new graph, because the base layer's connectivity is baked in one insertion at a time. Naming M correctly as a rebuild parameter, not a tunable setting, matters more than the exact number chosen.

One clarification worth holding before the first line of code below: a plain "connect each vector to its M nearest neighbours" graph is not HNSW, and it can fail outright. Linking 5,000 vectors drawn from 10 well-separated clusters to their 8 nearest neighbours each, then walking that graph with a beam search from a fixed entry point, reached only 448 of the 5,000 nodes and scored recall@10 = 0.000 even with the candidate list widened to 5,000 — the entry point's cluster and the query's cluster were simply never connected. Rebuilding the same graph incrementally, one node at a time, with the neighbour-selection heuristic Concept 3 measures below, reached all 5,000 nodes and scored recall@10 = 1.000 on the same query. That heuristic — favouring diverse, long-range links over a clique of nearest neighbours — is the concrete reason "just link each vector to its M nearest" is not HNSW.

Example:

import numpy as np

rng = np.random.default_rng(10)
n = 100_000
for M in (8, 16, 32, 48):
    mL = 1 / np.log(M)
    levels = np.floor(-np.log(rng.random(n)) * mL).astype(int)
    frac_ge1 = (levels >= 1).mean()
    print(f"M={M:>3}  mL={mL:.4f}  frac(level>=1)={frac_ge1:.4f}  theory(1/M)={1/M:.4f}")

Concept 2 — What M Costs in RAM, and Why It's a Rebuild Not a Reconfigure


hnswlib documents its own per-vector memory formula: d*4 + M*2*4 bytes — the d*4 is the
float32 vector itself, M*2*4 is M neighbour ids stored as 4-byte integers on each of the
two directions the base-layer cap (mmax0 = 2*M) allows. This is additive to the raw vector
storage, not a replacement for it: HNSW does not compress vectors, it adds a graph on top of
them.


Example:


d = 1024
for M in (8, 16, 32, 48, 64):
    per_vector = d * 4 + M * 2 * 4
    total_1m_gib = per_vector * 1_000_000 / 1024**3
    print(f"M={M:>3}  bytes/vector={per_vector}  total@1M={total_1m_gib:.2f} GiB")

Concept 3 — ef_construction Buys Graph Quality With Build Time


ef_construction is the candidate-list size used while building the graph: for each new
node, the builder does a beam search of width ef_construction over the graph built so far,
then keeps the best M of those candidates (via the neighbour-selection heuristic from
Concept 1) as the new node's links. Bigger ef_construction means a better-informed
neighbour choice — and a slower build, since every insertion does more work.


The honest shape of that tradeoff: quality rises with ef_construction and then plateaus.
It does not plateau at 1.0, because the neighbour-selection heuristic deliberately trades
away some true-nearest-neighbour links in exchange for the long-range diversity that fixes
the disconnection problem from Concept 1 — a graph of pure true-nearest-neighbour links is
exactly the kind of graph that got stuck at 448/5000 reachable nodes.


This week's build_graph/search_layer pair, defined once below and reused for the rest
of the week, is the compact single-layer NSW-style implementation the note under this
concept's Expected output describes: a greedy beam search over whatever graph has been
built so far, plus the Malkov & Yashunin neighbour-selection heuristic (Algorithm 4,
simplified) that Concept 1's disconnection story depends on.


Example:


import time
import numpy as np

_dist_calls = [0]

def dist(points, i, q):
    _dist_calls[0] += 1
    return np.linalg.norm(points[i] - q)

def _greedy_search(points, graph, entry, q, ef, limit):
    """Beam search over nodes already inserted (index < limit)."""
    visited = {entry}
    result = [(dist(points, entry, q), entry)]
    frontier = list(result)
    while frontier:
        frontier.sort()
        c_dist, c = frontier.pop(0)
        result.sort()
        if len(result) >= ef and c_dist > result[-1][0]:
            break
        for nb in graph.get(c, []):
            if nb not in visited and nb < limit:
                visited.add(nb)
                nd = dist(points, nb, q)
                frontier.append((nd, nb))
                result.append((nd, nb))
        result.sort()
        if len(result) > ef:
            result = result[:ef]
    result.sort()
    return result[:ef]

def _select_neighbors_heuristic(points, candidates, M):
    """Algorithm 4, simplified: keep a candidate only if it is closer to the
    query than to every neighbour already selected -- this is what buys the
    long-range diversity Concept 1's disconnection story depends on."""
    candidates = sorted(candidates)
    selected = []
    for cd, cidx in candidates:
        if len(selected) >= M:
            break
        if all(np.linalg.norm(points[cidx] - points[sidx]) >= cd for _, sidx in selected):
            selected.append((cd, cidx))
    return [idx for _, idx in selected]

def build_graph(points, M, ef_construction):
    n = len(points)
    graph = {0: []}
    entry = 0
    for i in range(1, n):
        candidates = _greedy_search(points, graph, entry, points[i], ef_construction, limit=i)
        selected = _select_neighbors_heuristic(points, candidates, M)
        graph[i] = list(selected)
        for j in selected:
            graph[j].append(i)
            if len(graph[j]) > 2 * M:
                cands_j = [(np.linalg.norm(points[nb] - points[j]), nb) for nb in graph[j]]
                graph[j] = _select_neighbors_heuristic(points, cands_j, 2 * M)
    return graph, entry

def search_layer(points, graph, entry, query, ef):
    return _greedy_search(points, graph, entry, query, ef, limit=len(points))

rng = np.random.default_rng(11)
n, d, M = 2000, 32, 16
points = rng.normal(size=(n, d)).astype(np.float32)

dmat = np.linalg.norm(points[:, None, :] - points[None, :, :], axis=2)
np.fill_diagonal(dmat, np.inf)
true_16nn = np.argsort(dmat, axis=1)[:, :16]

for efc in (10, 20, 40, 80, 160, 320):
    t0 = time.perf_counter()
    graph, entry = build_graph(points, M=M, ef_construction=efc)
    build_s = time.perf_counter() - t0
    captured = sum(len(set(true_16nn[i]) & set(graph[i])) for i in range(n))
    total = n * 16
    print(f"ef_c={efc:>4}  true-16NN captured={captured/total:.3f}  build={build_s:.1f}s")

Implementation note, stated once and held for the rest of this week: every runnable
example in this file uses a compact incremental single-layer NSW-style graph with the
Malkov & Yashunin neighbour-selection heuristic (Algorithm 4, simplified — no
extendCandidates or keepPrunedConnections), not a full multi-layer HNSW implementation.
A full multi-layer build is too long to fit in a markdown lesson block. What is measured
here is the base-layer mechanics — degree, heuristic neighbour selection, ef_construction
and ef_search — the same mechanics a real multi-layer graph runs at every layer. The layer
hierarchy on top is what gives production HNSW its logarithmic scaling at large corpus size;
it is not reproduced here, and no recall or latency number in this file should be read as a
production HNSW benchmark.




BFSI Reality Check — Day 1


Legacy angle: An insurer's on-prem index-build window is usually the overnight batch
slot, shared with settlement runs and regulatory extract jobs. A rebuild triggered by a
tuning change to M competes for the same machine and the same window as those existing
jobs — the constraint is rarely "can this build finish", it is "does this build finish
before the settlement job needs the CPU back."


Compliance angle: Because M and ef_construction are baked into the graph at build
time, every live index has an implicit "as-built" configuration that a model card or index
change log should record — not just at launch, but at every rebuild. A regulator asking why
a claims-similarity search under-performed cannot be answered with "current config" if the
config that actually built the graph in production was a different one that has since been
changed in a ticket but never redeployed.


What breaks in production: A well-meaning engineer bumps M in a config file expecting
an immediate quality improvement, and nothing happens — because the running index was never
rebuilt against the new value. The failure is silent: the service keeps serving the old
graph under a config that claims to be the new one.

Concept 1 — ef_search Is a Candidate-List Size, Not a Result Count


ef_search controls how many candidates the query-time beam search keeps in flight at the
base layer before returning the best k. It is a floor, not a target: if ef_search < k,
the search physically cannot return k results, because the candidate list it is drawing
from is smaller than k. Every production HNSW implementation enforces (or silently clamps
to) ef_search >= k; this example removes that guard to make the failure visible.


Example:


# Reusing build_graph/search_layer defined in Day 1 Concept 3.
import numpy as np

rng = np.random.default_rng(12)
n, d, M = 2000, 32, 16
points = rng.normal(size=(n, d)).astype(np.float32)
graph, entry = build_graph(points, M=M, ef_construction=100)

query = rng.normal(size=d).astype(np.float32)
k = 10
# ef passed straight through, no max(ef, k) floor -- this is deliberately unsafe.
for ef in (2, 5, 10, 20):
    results = search_layer(points, graph, entry, query, ef=ef)[:k]
    print(f"ef_search={ef:>3}  k={k}  results returned={len(results)}")

Concept 2 — The Recall@10 Sweep, With Distance Computations as the Cost Axis


Wall-clock timing is one way to measure query cost, but it is noisy in a pure-Python
implementation. The number of distance computations a search performs is a cleaner, more
stable proxy for the work ef_search actually buys — and it is the quantity a real vector
database's own internal counters expose.


Example:


# Reusing build_graph/search_layer/dist/_dist_calls defined in Day 1 Concept 3.
import numpy as np

rng = np.random.default_rng(13)
n, d, M, efc = 3000, 32, 16, 100
points = rng.normal(size=(n, d)).astype(np.float32)
graph, entry = build_graph(points, M=M, ef_construction=efc)

n_queries = 50
queries = rng.normal(size=(n_queries, d)).astype(np.float32)
dmat = np.linalg.norm(points[None, :, :] - queries[:, None, :], axis=2)
true_top10 = np.argsort(dmat, axis=1)[:, :10]

# dist() already counts every call into _dist_calls[0] -- reset it right
# before each measured search and read it right after, ignoring whatever
# the build above already accumulated.
for ef in (10, 32, 64, 128):
    recalls, total_calls = [], 0
    for qi in range(n_queries):
        _dist_calls[0] = 0
        results = search_layer(points, graph, entry, queries[qi], ef=ef)[:10]
        got = set(i for _, i in results)
        recalls.append(len(got & set(true_top10[qi].tolist())) / 10)
        total_calls += _dist_calls[0]
    print(f"ef_search={ef:>4}  recall@10={np.mean(recalls):.3f}  "
          f"avg distance computations={total_calls / n_queries:.0f}")

Concept 3 — Latency Percentiles Under Rising ef_search


The expected story is that ef_search disproportionately taxes the tail: a minority of
hard queries pay more of the added cost than the median query does. Measuring this
carefully on the toy graph here gives a more precise, slightly different answer worth
reporting honestly rather than asserting the expected one unchecked.


Example:


# Reusing build_graph/search_layer/dist/_dist_calls defined in Day 1 Concept 3.
import numpy as np

rng = np.random.default_rng(14)
n, d, M, efc = 3000, 32, 16, 100
points = rng.normal(size=(n, d)).astype(np.float32)
graph, entry = build_graph(points, M=M, ef_construction=efc)

n_queries = 300
queries = rng.normal(size=(n_queries, d)).astype(np.float32)

for ef in (32, 128):
    costs = []
    for qi in range(n_queries):
        _dist_calls[0] = 0
        search_layer(points, graph, entry, queries[qi], ef=ef)
        costs.append(_dist_calls[0])
    costs = np.array(costs)
    p50, p95, p99 = (np.percentile(costs, q) for q in (50, 95, 99))
    print(f"ef_search={ef:>4}  p50={p50:.0f}  p95={p95:.0f}  p99={p99:.0f}  "
          f"max={costs.max():.0f}  p99/p50={p99/p50:.2f}")

assuming either direction.




BFSI Reality Check — Day 2


Legacy angle: A per-query ef_search override is the cheapest lever an on-call engineer
has at 2 a.m. — it needs no rebuild, no deploy, just a changed request parameter. Knowing
that ef_search is the query-time knob (unlike M, which needs a rebuild) is the difference
between a five-minute mitigation and an escalation.


Compliance angle: A high-stakes lookup — a sanctions-adjacent claim similarity check, for
instance — is a legitimate reason to raise ef_search for that one call path even if the
rest of the service runs a lower default, since the latency cost of a single elevated-recall
query is bounded and the completeness gain is real. Document that override as a deliberate
per-path decision, not a stray parameter someone will "clean up" later.


What breaks in production: ef_search left at whatever the client library's default
happens to be, which was tuned against a benchmark corpus, not this one. Nothing errors.
Recall is quietly lower than the number in last quarter's evaluation report, and nobody
notices until a specific claim search is manually checked and found wanting.

Concept 1 — IVF Is a Different Family, Not a Different Setting


IVF (Inverted File index) has nothing structurally in common with HNSW. It trains a k-means
coarse quantizer over the corpus, producing nlist centroids; every stored vector is
assigned to its nearest centroid's inverted list. A query first finds the nprobe closest
centroids, then does an exact (or PQ-approximated) scan of only the vectors in those lists.
There is no graph, no layers, no M, no ef_construction.


The two families do not share a parameter, and describing IVF's nlist/nprobe as
"HNSW's version of M/ef_search" is a category error that will send a reader looking for
a knob that does not exist in whichever system they are actually configuring.


Example:


hnsw_config = {"family": "HNSW", "M": 16, "ef_construction": 100, "ef_search": 64}
ivf_config = {"family": "IVF", "nlist": 224, "nprobe": 16, "quantizer": "kmeans"}

shared_keys = set(hnsw_config) & set(ivf_config)
print("HNSW config:", hnsw_config)
print("IVF config :", ivf_config)
print("keys shared between the two configs (excluding 'family'):", shared_keys - {"family"})

Concept 2 — nlist, the sqrt(N) Heuristic, and the Training-Sample Floor


nlist, the number of coarse-quantizer centroids, is a build-time parameter — it needs a
training pass before the index exists at all, exactly like M needs a graph rebuild. FAISS's
own documentation gives nlist ~ sqrt(N) as a starting point, plus a hard minimum: at least
39 * nlist training points, with 256 * nlist as its stated comfort level. Below the
minimum, k-means has too few points per intended cluster to converge meaningfully.


Example:


import numpy as np

for n in (20_000, 50_000, 500_000, 5_000_000):
    nlist_heuristic = int(round(np.sqrt(n)))
    min_train = 39 * nlist_heuristic
    comfort_train = 256 * nlist_heuristic
    print(f"n={n:>10,}  sqrt(n) nlist~={nlist_heuristic:>5}  "
          f"min_train_pts={min_train:>9,}  comfort_train_pts={comfort_train:>10,}")

Concept 3 — nprobe Tracks the nprobe/nlist Ratio, Not nprobe Alone


The clean version of "sqrt(N) is a rule of thumb" ends here: measuring nprobe in
isolation is misleading, because the same nprobe value means something completely
different depending on nlist. nprobe = 32 is nearly exhaustive at nlist = 64 (half the
lists get probed) and a thin slice at nlist = 1000 (3.2% of lists). Recall tracks the
ratio, not the raw count — and cluster imbalance (a corpus with a few dominant claim types
and many rare ones) makes that ratio even less predictable, since some lists hold far more
vectors than others.


Example:


import time
import numpy as np

def build_ivf(points, nlist, seed=1, iters=10):
    """Lloyd's-algorithm k-means coarse quantizer, Forgy (random-sample) init."""
    rng = np.random.default_rng(seed)
    n = len(points)
    idx = rng.choice(n, size=nlist, replace=False)
    centroids = points[idx].copy()
    for _ in range(iters):
        d2 = ((points[:, None, :] - centroids[None, :, :]) ** 2).sum(axis=2)
        assign = np.argmin(d2, axis=1)
        new_centroids = centroids.copy()
        for c in range(nlist):
            members = points[assign == c]
            if len(members) > 0:
                new_centroids[c] = members.mean(axis=0)
        centroids = new_centroids
    d2 = ((points[:, None, :] - centroids[None, :, :]) ** 2).sum(axis=2)
    assign = np.argmin(d2, axis=1)
    lists = {c: [] for c in range(nlist)}
    for i, c in enumerate(assign):
        lists[int(c)].append(i)
    return centroids, lists

def ivf_search(points, centroids, lists, query, nprobe, k):
    d2c = ((centroids - query) ** 2).sum(axis=1)
    probe_order = np.argsort(d2c)[:nprobe]
    cand_ids = []
    for c in probe_order:
        cand_ids.extend(lists[int(c)])
    if not cand_ids:
        return []
    cand_ids = np.array(cand_ids)
    dists = np.linalg.norm(points[cand_ids] - query, axis=1)
    order = np.argsort(dists)[:k]
    return cand_ids[order].tolist()

# Skewed claim-type corpus: a few dominant claim types, several rare ones.
rng = np.random.default_rng(20)
d = 16
cluster_sizes = [8000, 6000, 3000, 1200, 700, 500, 300, 300]  # sums to 20,000
centres = rng.normal(scale=6.0, size=(len(cluster_sizes), d))
chunks = [rng.normal(loc=centres[i], scale=1.0, size=(sz, d)) for i, sz in enumerate(cluster_sizes)]
points = np.concatenate(chunks, axis=0).astype(np.float32)
n = len(points)

n_queries = 30
queries = rng.normal(size=(n_queries, d)).astype(np.float32)
dmat = np.linalg.norm(points[None, :, :] - queries[:, None, :], axis=2)
true_top10 = np.argsort(dmat, axis=1)[:, :10]

for nlist in (64, 224, 1000):
    t0 = time.perf_counter()
    centroids, lists = build_ivf(points, nlist, seed=1)
    build_s = time.perf_counter() - t0
    sizes = np.array([len(v) for v in lists.values()])
    ratio = sizes.max() / max(sizes.min(), 1)
    for nprobe in (1, 8, 16, 32):
        recalls = []
        for qi in range(n_queries):
            got = set(ivf_search(points, centroids, lists, queries[qi], nprobe, 10))
            recalls.append(len(got & set(true_top10[qi].tolist())) / 10)
        print(f"nlist={nlist:>5}  nprobe={nprobe:>3}  recall@10={np.mean(recalls):.3f}  "
              f"list max/min={ratio:.1f}  build={build_s:.1f}s")

Legacy angle: IVF's training step needs a representative sample of the corpus before

the rare, high-value claim categories a fraud or compliance review cares most about.

Concept 1 — The Compression Arithmetic


Product Quantization splits each d-dimensional vector into m contiguous subvectors and
encodes each subvector as the index of its nearest of 2**bits per-subspace centroids. A
1024-dimension float32 vector (4096 bytes) encoded with m = 64 subvectors at 8 bits each
becomes a 64-byte code — a 64x compression, at the cost of a codebook (m * 2**bits * (d/m) * 4 bytes) that must be kept in RAM to decode or score against. Scalar quantization
(SQ8, one byte per dimension, no subspace training) is the simpler alternative worth sizing
alongside PQ, since it needs no training step at all.


Example:


d = 1024
for m, bits in ((64, 8), (32, 8), (16, 8)):
    code_bytes = m * bits / 8
    compression = (d * 4) / code_bytes
    codebook_bytes = m * (2 ** bits) * (d // m) * 4
    print(f"m={m:>3} bits={bits}  code={code_bytes:.0f} B  "
          f"compression={compression:.0f}x  codebook={codebook_bytes/1024:.1f} KiB")

sq8_bytes = d * 1
print(f"\nSQ8 for comparison: {sq8_bytes} B/vector, compression={(d*4)/sq8_bytes:.0f}x")

size relative to bits=8 — more compression, at a coarser codebook that the training-and-
measurement in Concept 2 is what actually reveals the cost of.




Concept 2 — Training a Codebook and Measuring the Loss


The arithmetic in Concept 1 says nothing about accuracy — that has to be measured by
training real per-subspace k-means codebooks and running Asymmetric Distance Computation
(ADC): for a query, build a per-subspace lookup table of distances to that subspace's
centroids, then score every stored code by summing table lookups, without ever
decompressing a stored vector.


This example runs at d = 64, not d = 1024, so codebook training finishes in a
reasonable time on a laptop — the compression ratios and the recall trend transfer, the
absolute byte counts do not (see Concept 1 for the d = 1024 arithmetic).


Example:


import numpy as np

def train_pq(train_points, m, bits, seed=1, iters=10):
    """Per-subspace k-means: one independent codebook per of the m subvectors."""
    rng = np.random.default_rng(seed)
    n, d = train_points.shape
    sub_dim = d // m
    k = 2 ** bits
    codebooks = []
    for s in range(m):
        sub = train_points[:, s * sub_dim:(s + 1) * sub_dim]
        k_eff = min(k, len(sub))
        idx = rng.choice(len(sub), size=k_eff, replace=False)
        centroids = sub[idx].copy()
        for _ in range(iters):
            d2 = ((sub[:, None, :] - centroids[None, :, :]) ** 2).sum(axis=2)
            assign = np.argmin(d2, axis=1)
            new_centroids = centroids.copy()
            for c in range(k_eff):
                members = sub[assign == c]
                if len(members) > 0:
                    new_centroids[c] = members.mean(axis=0)
            centroids = new_centroids
        codebooks.append(centroids)
    return codebooks, sub_dim

def adc_search(codebooks, full_codes, query, m, k_return):
    """Asymmetric Distance Computation: per-subspace lookup table, summed."""
    n = full_codes.shape[0]
    sub_dim = len(query) // m
    total = np.zeros(n)
    for s in range(m):
        qs = query[s * sub_dim:(s + 1) * sub_dim]
        d2 = ((codebooks[s] - qs) ** 2).sum(axis=1)
        total += d2[full_codes[:, s]]
    return np.argsort(total)[:k_return].tolist()

rng = np.random.default_rng(30)
n, d = 8000, 64
points = rng.normal(size=(n, d)).astype(np.float32)
train_points = points[:4000]  # train on a subsample, per FAISS practice

n_queries = 30
queries = rng.normal(size=(n_queries, d)).astype(np.float32)
dmat = np.linalg.norm(points[None, :, :] - queries[:, None, :], axis=2)
true_top10 = np.argsort(dmat, axis=1)[:, :10]

bits = 8
for m in (4, 8, 16):
    codebooks, _ = train_pq(train_points, m=m, bits=bits, seed=1)
    sub_dim = d // m
    full_codes = np.zeros((n, m), dtype=np.int32)
    for s in range(m):
        sub = points[:, s * sub_dim:(s + 1) * sub_dim]
        d2 = ((sub[:, None, :] - codebooks[s][None, :, :]) ** 2).sum(axis=2)
        full_codes[:, s] = np.argmin(d2, axis=1)

        top10 = adc_search(codebooks, full_codes, queries[qi], m, k_return=10)
        adc_recalls.append(len(set(top10) & set(true_top10[qi].tolist())) / 10)
    code_bytes = m * bits / 8
    print(f"m={m:>3}  code={code_bytes:.0f}B  compression={(d*4)/code_bytes:.0f}x  "
          f"ADC recall@10={np.mean(adc_recalls):.3f}")

Concept 3 — Buying Recall Back With Refine/Rerank


Raw ADC recall from Concept 2 is often too low to ship alone. The standard fix is refine
(also called rerank): retrieve a larger candidate set with the cheap PQ/ADC scan (say
top-100 instead of top-10), then compute exact distances against the full, uncompressed
vectors for just those 100 candidates, and return the true top-10 among them.


The catch, worth stating rather than glossing over: reranking requires the full,
uncompressed vectors to still exist somewhere accessible — on disk, in a separate store, or
paged in on demand. That storage requirement is exactly what PQ's compression was trying to
avoid, so a refine step is a partial, not a free, undoing of the memory saving. It usually
still nets out ahead, because the resident, hot index is the small PQ codes, and only the
cold full vectors need to exist somewhere for the (small) refine step.


Example:


# Reusing train_pq/adc_search defined in Day 4 Concept 2.
import numpy as np

rng = np.random.default_rng(30)
n, d = 8000, 64
points = rng.normal(size=(n, d)).astype(np.float32)
train_points = points[:4000]
queries = rng.normal(size=(30, d)).astype(np.float32)
dmat = np.linalg.norm(points[None, :, :] - queries[:, None, :], axis=2)
true_top10 = np.argsort(dmat, axis=1)[:, :10]

m, bits = 8, 8
codebooks, _ = train_pq(train_points, m=m, bits=bits, seed=1)

    sub = points[:, s * sub_dim:(s + 1) * sub_dim]
    d2 = ((sub[:, None, :] - codebooks[s][None, :, :]) ** 2).sum(axis=2)
    full_codes[:, s] = np.argmin(d2, axis=1)

for qi in range(30):
    cand = np.array(adc_search(codebooks, full_codes, queries[qi], m, k_return=100))
    true_d = np.linalg.norm(points[cand] - queries[qi], axis=1)
    reranked = cand[np.argsort(true_d)][:10]
    rerank_recalls.append(len(set(reranked.tolist()) & set(true_top10[qi].tolist())) / 10)
print(f"m={m}  rerank@100 recall@10 = {np.mean(rerank_recalls):.3f}")

Legacy angle: The uncompressed vectors a refine step needs still have to live somewhere
on-prem storage the compliance team already knows about — pointing refine at "wherever the

number than what produced the original decision.

to save latency during a load spike, with no corresponding recall re-measurement. The system
keeps answering; it just answers less accurately, and the gap between "still up" and "still
correct" is precisely what a launch-day recall number cannot tell you six months later.

Concept 1 — Ground Truth First, With Warm-Up Discipline


Every recall number in this file has depended on one thing: an exact brute-force ground
truth computed once, over a frozen query workload, and reused as the reference every
configuration is scored against. Comparing two configurations against two different query
sets, or against ground truth recomputed differently each time, measures noise, not the
configurations.


Example:

Concept 2 — The Recall@10 vs QPS Pareto Table, Across Both Families


A single benchmark table with recall@10 and queries-per-second side by side, across HNSW
and IVF configurations sharing one ground truth, is what lets you spot dominated
configurations — ones where another row exists with equal or better recall and higher
QPS. A dominated configuration is never the right choice regardless of taste.


Example:


# Reusing build_graph/search_layer (Day 1 Concept 3) and build_ivf/ivf_search
# (Day 3 Concept 3) defined earlier this week.
import time
import numpy as np

rng = np.random.default_rng(41)
n, d = 5000, 32
points = rng.normal(size=(n, d)).astype(np.float32)
queries = rng.normal(size=(40, d)).astype(np.float32)

def brute_force_topk(points, query, k=10):
    return np.argsort(np.linalg.norm(points - query, axis=1))[:k]
ground_truth = [set(brute_force_topk(points, q).tolist()) for q in queries]

def recall_and_qps(search_fn, warmup=5):
    for q in queries[:warmup]:
        search_fn(q)
    t0 = time.perf_counter()
    recalls = []
    for i, q in enumerate(queries[warmup:], start=warmup):
        got = set(search_fn(q))
        recalls.append(len(got & ground_truth[i]) / 10)
    elapsed = time.perf_counter() - t0
    n_measured = len(queries) - warmup
    return np.mean(recalls), n_measured / elapsed

records = []
graph, entry = build_graph(points, M=16, ef_construction=100)
for ef in (16, 32, 64, 128):
    fn = lambda q, ef=ef: [i for _, i in search_layer(points, graph, entry, q, ef=ef)[:10]]

    recall, qps = recall_and_qps(fn)
    records.append(("IVF", f"nprobe={nprobe}", recall, qps))

    print(f"{family:6} {params:16} recall@10={recall:.3f}  qps={qps:.1f}")

Concept 3 — Build Time, Resident Memory, and a Record That Refuses to Omit a Parameter


Recall and QPS without build time and memory beside them is an incomplete comparison — a
configuration that wins on both but takes eleven hours to build, or that only fits in RAM on
paper, is not actually the winner. And a benchmark record with an unstated parameter is not
reproducible: a missing default is a silent assumption, not a documented one.


Example:

        "timestamp": datetime.datetime.now(datetime.timezone.utc).isoformat(),
        "config": config,
        "recall_at_10": recall,
        "qps": qps,
        "build_seconds": build_s,
        "resident_mb": rss_mb,
    }

BFSI Reality Check — Day 5


Legacy angle: An on-prem benchmark run competes for the same hardware as everything else
scheduled that night. Two runs of the identical config, one at 21:00 and one at 02:00, can
show meaningfully different QPS for reasons that have nothing to do with the index — record
the wall-clock window alongside the numbers, the same discipline Week 01 Day 5 established.


Compliance angle: A declared recall@k figure, backed by a versioned benchmark harness and
a frozen query set, is the kind of evidence an EU AI Act Article 15 accuracy claim or an
internal model-risk review actually wants — a number nobody can reproduce because the
harness has since changed is not evidence, it is an anecdote with more decimal places.


What breaks in production: The benchmark that qualified a configuration at launch is
never rerun as the corpus grows or its distribution shifts. The Pareto table in the launch
deck is treated as a permanent fact about the index rather than a snapshot of one corpus at
one point in time — exactly the same failure mode Week 01 closed on, now with two index
families' worth of parameters that can each silently drift out of the configuration that was
actually measured.




Architecture Decision — Week 04


Choosing between: HNSW vs. IVF-PQ, for a fixed on-prem RAM budget that the corpus may or
may not fit inside.


Rule of thumb: choose HNSW when query latency at high recall dominates the decision and
the full, uncompressed corpus fits comfortably in the RAM budget the hardware procurement
cycle actually granted — Day 1's formula (d*4 + M*2*4 bytes/vector) is the number to check
against that budget before committing, not after. Choose IVF-PQ when the corpus does not fit
resident in RAM at full precision, or is projected not to within the current hardware's
lifetime, and a refine/rerank pass against a colder store of full vectors can buy back the
recall PQ's compression gives up — accepting that the refine step re-introduces a real, if
partial, storage requirement for those full vectors somewhere. Both choices carry a rebuild
cadence, not a reconfiguration cadence: HNSW's M and IVF's nlist both require a full
rebuild (and, for IVF, a fresh k-means training pass whose training-sample floor Day 3
measured) to change, so plan corpus-growth-triggered rebuilds as a scheduled operational
event, not an emergency response. And whichever family is chosen, treat its rebuild as a
training-drift risk in its own right — an IVF quantizer trained on last year's claim-type mix
degrades exactly the way any other trained model degrades against a shifted distribution,
which is a reason to monitor recall@k continuously (Week 01's closing point) rather than
treat the choice between these two families as a one-time decision.
