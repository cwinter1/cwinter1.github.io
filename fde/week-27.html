Concept 1 — A DVC-Style Pointer File Instead of Committing a Large Dataset Directly

Git tracks every version of every file it is given forever, which is fine for a golden set of a few dozen questions but stops scaling once a dataset grows into the tens of thousands of rows real production golden sets reach — every revision bloats the repository's history permanently, even after the data itself is deleted. DVC's actual answer is to commit a small pointer file (a content hash plus a size, checked into git normally) instead of the dataset itself, and store the real bytes in a separate artifact store keyed by that hash. The pointer below is a genuine, hand-built version of exactly that shape — dvc add produces a .dvc YAML file with the same three fields (path, hash, size) checked into git in the real tool; this is that same contract, executed directly rather than through the DVC CLI, which this sandbox does not have installed.

Example:

import hashlib, json, os, tempfile

def hash_file(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        h.update(f.read())
    return h.hexdigest()

def write_pointer(dataset_path, pointer_path):
    size = os.path.getsize(dataset_path)
    digest = hash_file(dataset_path)
    pointer = {
        "path": os.path.basename(dataset_path),
        "sha256": digest,
        "size_bytes": size,
        "storage": "artifact-store://fde-golden-sets/",
    }
    with open(pointer_path, "w") as f:
        json.dump(pointer, f, indent=2, sort_keys=True)
    return pointer

def verify_pointer(dataset_path, pointer_path):
    with open(pointer_path) as f:
        pointer = json.load(f)
    actual_digest = hash_file(dataset_path)
    actual_size = os.path.getsize(dataset_path)
    return (actual_digest == pointer["sha256"]) and (actual_size == pointer["size_bytes"])

tmp_dir = tempfile.mkdtemp()
dataset_path = os.path.join(tmp_dir, "golden_v1.jsonl")
with open(dataset_path, "w") as f:
    f.write('{"question": "How many days to reinstate?", "answer": "90 days"}\n')
    f.write('{"question": "What is the grace period?", "answer": "31 days"}\n')

pointer_path = dataset_path + ".pointer.json"
pointer = write_pointer(dataset_path, pointer_path)
print(f"pointer written: sha256={pointer['sha256'][:12]}...  size_bytes={pointer['size_bytes']}")
print(f"pointer verifies against real file: {verify_pointer(dataset_path, pointer_path)}")

with open(dataset_path, "a") as f:
    f.write('{"question": "Is mold covered?", "answer": "only from water damage"}\n')
print(f"pointer verifies after untracked edit: {verify_pointer(dataset_path, pointer_path)}")

Concept 2 — Synthetic-Only Golden Queries: Keeping the Repo PII-Free by Construction


A golden set that is committed to git, and later copied into every CI runner's checkout on
every pull request, is a genuinely bad place for a real customer's name, SSN, or account
number to end up — git history does not forget, and a CI log can outlive the PR that
triggered it. Week 26 Day 1's build_seed_set already generated questions from a fixed
template x topic grid specifically so nothing real could enter the set in the first place;
this concept adds the audit that should run on ANY golden-set addition regardless of how it
was authored, since a synthetic-generation process protects against nothing once someone
pastes in a real support ticket as a "realistic" example question.


Example:


import re
from dataclasses import dataclass
from typing import List

# Reusing GoldenRecord from Week 26 Day 1 Concept 2
@dataclass
class GoldenRecord:
    question: str
    ground_truth_answer: str
    reference_context_ids: List[str]
    category: str

PII_PATTERNS = [
    re.compile(r"\b\d{3}-\d{2}-\d{4}\b"),        # SSN-shaped
    re.compile(r"\b\d{9,16}\b"),                  # account/card-number-shaped
    re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b"),  # email
    re.compile(r"\b\d{5}(?:-\d{4})?\b"),          # zip-code-shaped
]
REAL_NAME_MARKERS = {"mr.", "mrs.", "ms.", "dr.", "policyholder name", "ssn", "account number"}

def contains_pii(text):
    lowered = text.lower()
    if any(m in lowered for m in REAL_NAME_MARKERS):
        return True
    return any(p.search(text) for p in PII_PATTERNS)

def audit_golden_set(records):
    flagged = []
    for rec in records:
        if contains_pii(rec.question) or contains_pii(rec.ground_truth_answer):
            flagged.append(rec.question)
    return flagged

synthetic_set = [
    GoldenRecord("How many days do I have to reinstate a lapsed policy?",
                 "90 days from the date of lapse.", ["DOC-2"], "timing"),
    GoldenRecord("Is mold damage covered under my property policy?",
                 "Only mold caused by a covered water damage event.", ["DOC-8"], "exclusion"),
]
leaked_set = [
    GoldenRecord("What is the claim status for policyholder John Smith, SSN 512-33-9981?",
                 "Claim CLM-2291045 is pending review.", ["DOC-2"], "timing"),
]

flagged_synthetic = audit_golden_set(synthetic_set)
flagged_leaked = audit_golden_set(leaked_set)
print(f"synthetic set flagged: {len(flagged_synthetic)}/{len(synthetic_set)}")
print(f"leaked-shaped set flagged: {len(flagged_leaked)}/{len(leaked_set)}")
for q in flagged_leaked:
    print(f"  BLOCKED: {q[:60]}...")

Concept 3 — A Changelog Entry Required Per Dataset Revision


A golden set's .pointer.json (Concept 1) proves a revision's bytes are exactly what CI
thinks they are, but it says nothing about WHY the bytes changed — that has to be a human
decision, recorded before the revision is trusted, not reconstructed later from git blame.
validate_revision below treats a changelog as a required gate: a dataset hash with no
matching entry is rejected outright, and an entry whose claimed add/retire counts do not
match the real diff is rejected too, so the changelog cannot silently drift out of sync with
what actually changed the way the dataset itself could without Concept 1's pointer check.


Example:


import hashlib

# Reusing dataset_hash-style content hashing from Concept 1
from dataclasses import dataclass

@dataclass
class ChangelogEntry:
    revision: str
    dataset_hash: str
    summary: str
    questions_added: int
    questions_retired: int

class ChangelogError(ValueError):
    pass

def dataset_hash_of(questions):
    key = "|".join(sorted(questions))
    return hashlib.sha256(key.encode()).hexdigest()[:12]

def validate_revision(prev_questions, new_questions, changelog):
    new_hash = dataset_hash_of(new_questions)
    entry = next((e for e in changelog if e.dataset_hash == new_hash), None)
    if entry is None:
        raise ChangelogError(
            f"dataset content hash {new_hash} has no matching changelog entry -- "
            f"every revision must be logged before it can be used"
        )
    added = len(set(new_questions) - set(prev_questions))
    retired = len(set(prev_questions) - set(new_questions))
    if entry.questions_added != added or entry.questions_retired != retired:
        raise ChangelogError(
            f"changelog entry {entry.revision} claims +{entry.questions_added}/-{entry.questions_retired} "
            f"but the real diff is +{added}/-{retired}"
        )
    return entry

v1_questions = ["grace period days", "reinstatement window"]
v2_questions = ["grace period days", "reinstatement window", "mold exclusion scope"]

changelog = [
    ChangelogEntry(
        revision="v2",
        dataset_hash=dataset_hash_of(v2_questions),
        summary="Added mold exclusion scope question after Q3 policy language update.",
        questions_added=1,
        questions_retired=0,
    ),
]

entry = validate_revision(v1_questions, v2_questions, changelog)
print(f"v2 validated against changelog: revision={entry.revision}  summary={entry.summary!r}")

v3_questions = ["grace period days", "mold exclusion scope"]  # retired reinstatement, no changelog entry
try:
    validate_revision(v2_questions, v3_questions, changelog)
    print("unexpectedly validated v3")
except ChangelogError as e:
    print(f"rejected: {e}")

Concept 4 — Two-Reviewer Approval Before a Question Is Added or Retired


A single annotator adding a golden-set question is exactly Week 26 Day 1 Concept 3's own
single-point-of-failure risk — nobody double-checks whether the new question is well-formed,
correctly labeled, or free of the ambiguity markers that concept flagged. Requiring two
DISTINCT reviewer approvals before a change merges, and rejecting a reviewer's second
approval as a duplicate rather than silently counting it twice, is the same discipline a code
review's required-approvals rule already enforces elsewhere in this repo — golden-set changes
get no exemption just because they are data, not code.


Example:


from dataclasses import dataclass, field
from typing import List

@dataclass
class ReviewRequest:
    change_id: str
    action: str  # "add" | "retire"
    question: str
    approvals: List[str] = field(default_factory=list)

class ApprovalError(ValueError):
    pass

MIN_REVIEWERS = 2

def approve(request, reviewer):
    if reviewer in request.approvals:
        raise ApprovalError(f"{reviewer} already approved {request.change_id} -- cannot double-count")
    request.approvals.append(reviewer)
    return request

def can_merge(request):
    distinct = set(request.approvals)
    if len(distinct) < MIN_REVIEWERS:
        raise ApprovalError(
            f"{request.change_id} has {len(distinct)} distinct reviewer(s), needs {MIN_REVIEWERS}"
        )
    return True

req = ReviewRequest(change_id="CH-101", action="add", question="Is flood damage from a burst pipe covered?")
approve(req, "reviewer_amir")
try:
    can_merge(req)
    print("unexpectedly merged with 1 reviewer")
except ApprovalError as e:
    print(f"blocked: {e}")

approve(req, "reviewer_dana")
print(f"{req.change_id} mergeable after 2 distinct reviewers: {can_merge(req)}")

req2 = ReviewRequest(change_id="CH-102", action="retire", question="Old wording: does the policy renew automatically?")
approve(req2, "reviewer_amir")
try:
    approve(req2, "reviewer_amir")
    print("unexpectedly allowed double approval")
except ApprovalError as e:
    print(f"rejected: {e}")

BFSI Reality Check — Day 1


Legacy angle: a golden set built against Week 13/18's mainframe-sourced corpus ages the
moment the source system's own export format changes underneath it — Concept 1's pointer file
catches the symptom (the dataset's bytes no longer match what CI expects) but Concept 3's
changelog is what tells an on-call engineer whether that was a deliberate content update or a
silent upstream break, which is the difference between merging a PR and paging someone.


Compliance angle: Concept 4's two-reviewer rule is not procedural theater for a BFSI golden
set specifically because Week 26 Day 1 Concept 3 already showed one annotator can misread a
policy's own hedged language as a flat fact — a second reviewer is the actual control that
catches that before it enters the set a regression gate will trust for months.


What breaks in production: a golden set with no changelog and no pointer file looks
identical to a well-governed one right up until someone asks "why did our recall score change
between last Tuesday and today" and there is no answer — Concepts 1 and 3 together are what
make that question answerable in minutes instead of requiring a reconstruction from memory.

Concept 1 — pull_request and workflow_dispatch Triggers on the Eval Job


An eval job needs to run automatically on every pull request that could regress the pipeline
(pull_request), and needs a manual escape hatch a reviewer can fire on demand without
opening a throwaway PR (workflow_dispatch) — for example to re-run the exact same gate
against a smaller question_count while debugging a flaky result. Both triggers coexist under
one "on": key, exactly the way regression.yml already declares pull_request alone and
ai.yml declares push+pull_request together for this repo's earlier weeks.

Concept 2 — Matrix Strategy Across Retrieval Configurations


Week 25 proved reranking earns its cost at some k values and not others — a single eval run
answers "does the CURRENT configuration still pass," not "which configuration is actually
best." A strategy.matrix job runs the same steps once per combination of named dimensions,
and exclude prunes combinations that make no sense to run at all (a reranker: none run at
a large retrieval_k that only matters once a reranker is narrowing the field). expand_matrix
below reproduces GitHub Actions' own real expansion rule: the full cartesian product of every
dimension's values, minus any row an exclude entry matches on every one of its listed keys.


Example:


import yaml
import itertools

MATRIX_YAML = """
name: FDE Eval Gate

"on":
  pull_request:
    branches: [main]

jobs:
  eval-gate:
    name: Golden Set Regression Check (${{ matrix.retrieval_k }}, reranker=${{ matrix.reranker }})
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        retrieval_k: [3, 5]
        reranker: [none, bge]
        exclude:
          - retrieval_k: 5
            reranker: none
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Run eval at this configuration
        run: |
          cd FDE_Fintech_Insurance
          python tools/run_eval.py --k ${{ matrix.retrieval_k }} --reranker ${{ matrix.reranker }}
"""

parsed = yaml.safe_load(MATRIX_YAML)
matrix = parsed["jobs"]["eval-gate"]["strategy"]["matrix"]
print(f"valid YAML: {isinstance(parsed, dict)}")
print(f"matrix dimensions: {[k for k in matrix if k != 'exclude']}")
print(f"exclude rules: {matrix.get('exclude', [])}")


def expand_matrix(matrix):
    dims = {k: v for k, v in matrix.items() if k != "exclude"}
    excludes = matrix.get("exclude", [])
    keys = list(dims.keys())
    combos = []
    for values in itertools.product(*[dims[k] for k in keys]):
        row = dict(zip(keys, values))
        if any(all(row.get(ek) == ev for ek, ev in ex.items()) for ex in excludes):
            continue
        combos.append(row)
    return combos


jobs_to_run = expand_matrix(matrix)
print(f"jobs GitHub Actions would actually run: {len(jobs_to_run)}")
for row in jobs_to_run:
    print(f"  {row}")

Concept 3 — Judge-LLM API Key via Repository Secrets

read it — ${{ secrets.JUDGE_LLM_API_KEY }} is GitHub's own substitution syntax for pulling

Concept 4 — actions/cache for the Embedding Cache


Re-embedding every golden-set question on every single PR run is real, recurring cost and
real, recurring latency for text that has not changed since the last run — actions/cache
lets a job restore a prior run's cache directory keyed by a hash of the files that actually
determine its contents, so an unrelated code change in this same PR gets a cache hit instead
of paying to re-embed unchanged questions. hashFiles() (real GitHub Actions expression
syntax) computes that hash server-side from the matched files' real content; hash_files_sim
below reproduces the same idea with hashlib directly so its result is genuinely computable
in this sandbox, and resolve_cache reproduces the exact lookup GitHub's cache action performs:
an exact key match is a HIT, a restore-keys prefix match is a PARTIAL hit (Concept 4's
restore-keys: field), and no match at all is a MISS.

def hash_files_sim(contents_by_path):
    combined = "".join(contents_by_path[p] for p in sorted(contents_by_path))
    return hashlib.sha256(combined.encode()).hexdigest()[:16]


def resolve_cache(key, cache_store):
    if key in cache_store:
        return "HIT", key
    prefix = key.rsplit("-", 1)[0] + "-"
    fallback = next((k for k in cache_store if k.startswith(prefix)), None)
    if fallback:
        return "PARTIAL (restore-keys fallback)", fallback
    return "MISS", None

Concept 1 — Absolute Per-Metric Floors Plus Delta-vs-Baseline Gates


Week 26 Day 5 Concept 4's evaluate_gate checked an absolute floor per metric plus one
composite floor — enough to catch a pipeline that is simply bad, but not enough to catch one
that used to be noticeably better and quietly got worse while staying above every absolute
number. Extending the same gate with a second, independent check — how far has each metric
dropped from a recorded baseline, not just where does it sit today — catches that second,
more common failure: nothing here is broken outright, it just isn't as good as it was
yesterday, and an absolute-floor-only gate has no way to say so.


Example:


import json

EVAL_CONFIG = {
    "weights": {"faithfulness": 0.4, "context_precision": 0.3, "context_recall": 0.3},
    "thresholds": {"composite_min": 0.55, "faithfulness_min": 0.3},
    "baseline": {"faithfulness": 0.62, "context_precision": 0.55, "context_recall": 0.71},
    "max_regression": {"faithfulness": 0.08, "context_precision": 0.08, "context_recall": 0.08},
}


class EvalGateError(ValueError):
    pass


def composite_score(metrics, config):
    weights = config["weights"]
    return round(sum(metrics[m] * w for m, w in weights.items()), 4)


def evaluate_gate(metrics, config):
    faithfulness_floor = config["thresholds"]["faithfulness_min"]
    if metrics["faithfulness"] < faithfulness_floor:
        raise EvalGateError(f"faithfulness {metrics['faithfulness']} below absolute floor {faithfulness_floor}")

    composite = composite_score(metrics, config)
    composite_floor = config["thresholds"]["composite_min"]
    if composite < composite_floor:
        raise EvalGateError(f"composite {composite} below absolute floor {composite_floor}")

    for metric_name, baseline_value in config["baseline"].items():
        current = metrics[metric_name]
        drop = round(baseline_value - current, 4)
        max_drop = config["max_regression"][metric_name]
        if drop > max_drop:
            raise EvalGateError(
                f"{metric_name} dropped {drop} vs. baseline {baseline_value} "
                f"(current {current}), exceeding max allowed drop {max_drop}"
            )

    return composite

Concept 2 — Establishing the Statistical Noise Floor From Repeated Runs


Setting max_regression in Concept 1's config to some plausible-sounding number without first
measuring how much a genuinely UNCHANGED pipeline's own score moves between two runs is how a
gate manufactures its own false alarms — Week 26 Day 2 Concept 4 showed a single score's own
sampling noise at a real judge's residual temperature; this concept measures the noise floor of
the actual quantity a delta gate compares — a BATCH AVERAGE across a repeated identical run —
and only then proposes a threshold with real headroom above it.


Example:


import random
import statistics

# Reusing simulated_judge_score/run_n_times from Week 26 Day 2 Concept 4

def simulated_judge_score(base_score, temperature, rng):
    noise = rng.uniform(-temperature, temperature)
    return max(0.0, min(1.0, round(base_score + noise, 4)))


def run_n_times(base_score, temperature, n, seed):
    rng = random.Random(seed)
    return [simulated_judge_score(base_score, temperature, rng) for _ in range(n)]


def measure_noise_floor(base_score, temperature, n_runs, n_repeats, seed):
    """Runs an n_runs-sized eval batch n_repeats times and measures how much the
    BATCH AVERAGE itself moves between repeats -- the real quantity a delta-vs-baseline
    gate should compare its own threshold against, not the single-score spread."""
    batch_averages = []
    for repeat in range(n_repeats):
        scores = run_n_times(base_score, temperature, n_runs, seed=seed + repeat)
        batch_averages.append(round(statistics.fmean(scores), 4))
    return batch_averages


def recommend_threshold(noise_floor_stdev, safety_multiplier=3):
    # A threshold set below what pure sampling noise can already produce guarantees
    # false alarms; a safety multiplier gives real signal room to still be caught.
    return round(noise_floor_stdev * safety_multiplier, 4)


base_score = 0.62
temperature = 0.05  # a small residual temperature even after pinning near 0 (Week 26 Day 2
                     # Concept 3), modeling real prompt/context-order sensitivity

batch_averages = measure_noise_floor(base_score, temperature, n_runs=8, n_repeats=6, seed=100)
noise_floor_stdev = round(statistics.pstdev(batch_averages), 4)
noise_floor_spread = round(max(batch_averages) - min(batch_averages), 4)

print(f"batch averages across 6 repeated identical runs: {batch_averages}")
print(f"noise floor: stdev={noise_floor_stdev}  spread={noise_floor_spread}")

recommended = recommend_threshold(noise_floor_stdev)
print(f"recommended max_regression threshold (3x noise floor stdev): {recommended}")

too_tight_threshold = 0.005
print(f"threshold {too_tight_threshold} would false-alarm on pure noise: {too_tight_threshold < noise_floor_spread}")
print(f"threshold {recommended} clears the observed noise spread: {recommended > noise_floor_spread}")

Concept 4 — A Documented, Logged Override Path for Genuine False Alarms


Concept 2 measured a real noise floor and Concept 1's thresholds sit above it — but no
threshold eliminates false alarms entirely, and a gate with no legitimate way past a genuine
one just trains engineers to disable the gate itself the first time it is inconvenient, which
protects nothing at all. The fix is not a backdoor — it is a narrow, auditable path: an
override needs a real justification long enough to actually explain the false alarm (not
"flaky, ignore") and a named human approver, both permanently written to the same kind of
log Concept 3's merge decision itself belongs next to.


Example:


from dataclasses import dataclass
from typing import Optional

@dataclass
class OverrideRequest:
    pr_number: int
    failing_check: str
    gate_error: str
    justification: str
    approver: Optional[str] = None
    logged_at: Optional[float] = None


class OverrideError(ValueError):
    pass

MIN_JUSTIFICATION_CHARS = 40
override_log = []


def request_override(pr_number, failing_check, gate_error, justification):
    if len(justification) < MIN_JUSTIFICATION_CHARS:
        raise OverrideError(
            f"justification is {len(justification)} chars, needs at least {MIN_JUSTIFICATION_CHARS} -- "
            f"'flaky, ignore' is not an audit trail"
        )
    return OverrideRequest(pr_number, failing_check, gate_error, justification)


def approve_override(request, approver, at):
    if approver is None:
        raise OverrideError("an override needs a named human approver, not an automated bypass")
    request.approver = approver
    request.logged_at = at
    override_log.append(request)
    return request

    request_override(1042, "Golden Set Regression Check", "faithfulness dropped 0.12 vs baseline", weak_justification)
    print("unexpectedly accepted weak justification")
except OverrideError as e:
    print(f"rejected: {e}")

    "Baseline itself was measured against a golden-set revision retired in changelog v3; "
    "re-running against the current golden set shows faithfulness=0.61, no real regression."

Concept 3 — Alerting on Sustained Decline Rather Than a Single Bad Run


Day 3 Concept 2 already measured that a single run's score moves on its own from ordinary
judge sampling noise — paging someone the first night a score dips below yesterday's number
means paging them on pure noise more often than on a real problem, and a team that gets paged
on noise stops trusting the pager. check_sustained_decline only alerts once a metric has
gotten WORSE for several consecutive nights in a row, which noise essentially never does by
chance, while a real, ongoing regression reliably does.


Example:


def check_sustained_decline(series, metric, min_consecutive_drops=3):
    """Alerts only when a metric has dropped for `min_consecutive_drops` consecutive
    nights in a row, not on any single bad run -- a one-night dip (real judge noise,
    Day 3 Concept 2) recovers on its own and should never page anyone."""
    values = [row[metric] for row in series]
    if len(values) < min_consecutive_drops + 1:
        return False, 0
    consecutive_drops = 0
    max_consecutive = 0
    for i in range(1, len(values)):
        if values[i] < values[i - 1]:
            consecutive_drops += 1
            max_consecutive = max(max_consecutive, consecutive_drops)
        else:
            consecutive_drops = 0
    return max_consecutive >= min_consecutive_drops, max_consecutive

Concept 4 — A Hard Token-Cost Cap Per Nightly Run


Concept 1's full-set nightly sweep calls a judge model on every one of 60 questions, every
night, forever — Week 23's own cost-governance discipline applies here exactly as it did
there: an unbounded loop making real per-call charges needs a hard ceiling, not a hope that
nobody ever points it at a larger question set without noticing the bill. NightlyCostTracker
stops the sweep the moment the NEXT charge would cross the cap, rather than after it — a
partial night's results, logged honestly as capped, beats an unbounded one that quietly costs
more than anyone approved.


Example:


class CostCapExceeded(RuntimeError):
    pass


COST_PER_1K_TOKENS_USD = 0.003  # judge model input+output blended rate for this pipeline


class NightlyCostTracker:
    def __init__(self, max_cost_usd):
        self.max_cost_usd = max_cost_usd
        self.spent_usd = 0.0
        self.questions_scored = 0

    def charge(self, tokens_used):
        cost = round((tokens_used / 1000) * COST_PER_1K_TOKENS_USD, 6)
        if self.spent_usd + cost > self.max_cost_usd:
            raise CostCapExceeded(
                f"charging ${cost} would bring total to ${round(self.spent_usd + cost, 4)}, "
                f"over the ${self.max_cost_usd} nightly cap -- stopping after "
                f"{self.questions_scored} of the intended question set"
            )
        self.spent_usd = round(self.spent_usd + cost, 6)
        self.questions_scored += 1
        return self.spent_usd


def run_nightly_sweep(question_tokens, max_cost_usd):
    tracker = NightlyCostTracker(max_cost_usd)
    scored = []
    capped = False
    for tokens in question_tokens:
        try:
            tracker.charge(tokens)
            scored.append(tokens)
        except CostCapExceeded as e:
            capped = True
            print(f"  STOPPED: {e}")
            break
    return tracker, capped

Concept 2 — A PR Comment Posting Metric Deltas Against the Base Branch


An artifact a reviewer has to download and open (Concept 1) is real, but it is not the FIRST
thing they see on a PR — a comment posted directly on the PR, showing exactly which metrics
moved and by how much versus the base branch, is what actually gets read before anyone clicks
into the Checks tab at all. compute_deltas and render_pr_comment below build that comment's
real content; posting it for real needs the GitHub REST API's issue-comments endpoint (a PR is
an issue, in GitHub's own API model) with a live token, shown separately as reference syntax.


Example:


def compute_deltas(base_metrics, pr_metrics):
    deltas = {}
    for name, base_value in base_metrics.items():
        current = pr_metrics[name]
        delta = round(current - base_value, 4)
        deltas[name] = {"base": base_value, "pr": current, "delta": delta}
    return deltas


def render_pr_comment(deltas, pr_number):
    lines = [f"### Eval Gate Report -- PR #{pr_number}", "", "| Metric | Base | PR | Delta |", "|---|---|---|---|"]
    for name, d in deltas.items():
        arrow = "up" if d["delta"] > 0 else ("down" if d["delta"] < 0 else "flat")
        sign = "+" if d["delta"] >= 0 else ""
        lines.append(f"| {name} | {d['base']} | {d['pr']} | {sign}{d['delta']} ({arrow}) |")
    return "\n".join(lines)

Concept 3 — A Per-Question Diff Listing Newly Failing Cases


Concept 2's aggregate deltas answer "did the average get worse" but not "worse FOR WHICH
questions" — a reviewer fixing a regression needs the second answer, not the first.
diff_per_question_results compares two runs' pass/fail verdicts question by question and
reports exactly which ones flipped in each direction, which is the same retrieval-vs-
generation-failure framing Day 1 Concept 1 built, applied here across two runs instead of
within one.


Example:


def diff_per_question_results(base_results, pr_results):
    """base_results/pr_results: {question: bool (passed)}. Returns questions that
    passed on base but fail on the PR -- the actual, actionable regression list a
    reviewer needs, not just an aggregate score that moved."""
    newly_failing = []
    newly_fixed = []
    for question, base_passed in base_results.items():
        pr_passed = pr_results.get(question)
        if base_passed and pr_passed is False:
            newly_failing.append(question)
        elif not base_passed and pr_passed is True:
            newly_fixed.append(question)
    return sorted(newly_failing), sorted(newly_fixed)


base_results = {
    "How many days to reinstate a lapsed policy?": True,
    "Is mold damage covered under my property policy?": True,
    "What is the grace period for premium payment?": False,
    "Is my deductible waived for a first claim?": True,
}
pr_results = {
    "How many days to reinstate a lapsed policy?": True,
    "Is mold damage covered under my property policy?": False,   # regressed
    "What is the grace period for premium payment?": True,       # fixed
    "Is my deductible waived for a first claim?": True,
}

newly_failing, newly_fixed = diff_per_question_results(base_results, pr_results)
print(f"newly failing ({len(newly_failing)}):")
for q in newly_failing:
    print(f"  - {q}")
print(f"newly fixed ({len(newly_fixed)}):")
for q in newly_fixed:

Concept 4 — An Eval Appendix Section Suitable for a Model Card


Everything this week built — the golden set's own version (Day 1), the gate that ran against
it (Day 3), the nightly trend (Day 4) — is exactly the evidence a model card's own evaluation
section should cite, and citing it as a static number copied in by hand goes stale the moment
the pipeline is re-evaluated. Generating the appendix directly from the same EvalAppendix
data structure the CI job already produces keeps the model card's evaluation claims honestly
tied to a specific, hashed golden-set revision and a specific run date, not a number someone
remembers from a few weeks ago.


Example:


from dataclasses import dataclass
from typing import Dict

@dataclass
class EvalAppendix:
    model_version: str
    golden_set_revision: str
    golden_set_hash: str
    metrics: Dict[str, float]
    thresholds: Dict[str, float]
    eval_date: str


def render_model_card_appendix(appendix):
    lines = [
        "## Appendix: Automated Evaluation",
        "",
        f"Model version: `{appendix.model_version}`  ",
        f"Golden set revision: `{appendix.golden_set_revision}` (content hash `{appendix.golden_set_hash}`)  ",
        f"Evaluated: {appendix.eval_date}",
        "",
        "| Metric | Score | Floor |",
        "|---|---|---|",
    ]
    for name, score in appendix.metrics.items():
        floor = appendix.thresholds.get(name, "n/a")
        status = "PASS" if floor == "n/a" or score >= floor else "FAIL"
        lines.append(f"| {name} | {score} | {floor} ({status}) |")
    lines.append("")
    lines.append(
        "Scores are produced by the automated eval gate wired into CI (Week 27); "
        "see the linked scorecard artifact for the full per-question breakdown."
    )
    return "\n".join(lines)

BFSI Reality Check — Day 5


Legacy angle: Concept 3's per-question diff is what actually lets a team separate "the RAG
pipeline regressed" from "the upstream legacy extract changed and a question's ground truth is
now stale" — both look identical as an aggregate score drop, and only the per-question list,
cross-referenced against Day 1's changelog, tells a reviewer which explanation is real.


Compliance angle: Concept 4's generated appendix is the piece that finally closes the loop
this whole week opened — a model card's evaluation claims are now provably tied to a specific,
hashed, changelog-tracked golden-set revision (Day 1) run through a documented gate (Day 3) on
a fixed schedule (Day 4), which is a materially stronger answer to a model-risk review than a
narrative paragraph written from memory.


What breaks in production: a scorecard artifact (Concept 1) nobody ever opens because the
PR comment (Concept 2) told the whole story already is not a wasted step — it is the fallback
for the one time a reviewer needs more than the comment's summary, and skipping it because "the
comment already shows the deltas" is how a team discovers, only when they actually need the
per-question detail, that the artifact was never actually being generated correctly in the
first place.




Architecture Decision — Week 27


Choosing between: a PR-blocking gate (Days 2-3's pull_request-triggered job with
absolute-floor and delta-vs-baseline checks, wired as a branch-protection required check) vs.
nightly-only monitoring (Day 4's scheduled sweep with sustained-decline alerting) vs. no
automated gate at all, human review only (what every week before this one in Phase 5 actually
shipped with).


Rule of thumb: put a check in the PR-blocking gate only once Day 3 Concept 2's noise floor has
actually been measured for it and the threshold sits comfortably above that floor — an
unmeasured threshold in a PR-blocking position does not protect the codebase, it teaches every
contributor to route around CI the first time it false-alarms on their unrelated change (Day 3
Concept 4's override path exists for the genuine exception, not as the normal path). Move a
check to nightly-only when it is too slow, too expensive, or too noisy to run on every PR but
still worth tracking as a trend — Day 4's full-set sweep and Concept 3's sustained-decline logic
exist specifically because "every PR, every metric, at full strictness" is not actually
affordable or reliable at PR-gate cadence, and pretending it is just produces Day 3's
false-alarm failure mode on a tighter clock. The one thing this week argues against outright is
the third option: an eval harness this rigorous (Weeks 26-27, golden-set governance, four real
scoring approaches, a measured noise floor, a version-controlled gate config) that only a human
remembers to consult before a release is worth almost nothing next to a $0 marginal-cost CI job
that runs it automatically on every single change — the entire value Phase 5 built across four
weeks was never the metrics themselves, it was making them impossible to skip.
