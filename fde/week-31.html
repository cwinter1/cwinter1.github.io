Concept 1 — TXN-RECORD: COMP-3 Amount, Zoned-Overpunch Balance

The nightly extract this week decodes is a TXN-RECORD copybook — a fixed-width, RECFM=FB mainframe transaction record with no line terminators, exactly Week 13's format:

01 TXN-RECORD.
   05 TXN-ID           PIC X(10).
   05 ACCOUNT-ID        PIC X(10).
   05 TXN-AMOUNT        PIC S9(9)V99 COMP-3.   -- 6 bytes packed decimal
   05 BALANCE-AFTER     PIC S9(9)V99.          -- 11 bytes zoned, sign overpunch
   05 CHANNEL           PIC X(4).
   05 TXN-TIMESTAMP     PIC X(14).             -- YYYYMMDDHHMMSS

TXN-AMOUNT reuses Week 13 Day 3 Concept 2's unpack_comp3/pack_comp3 — two decimal digits per byte in nibbles, the last nibble the sign. BALANCE-AFTER reuses Week 13 Day 3 Concept 3's unpack_zoned/pack_zoned — one digit per byte, the sign folded into the zone nibble of only the last byte (the "overpunch" this concept's YouTube search names directly). Both decoders are copied unchanged from Week 13; only the record layout around them is new.

Example:

from decimal import Decimal

# Reusing Week 13 Day 3 Concepts 2-3's unpack_comp3/pack_comp3/unpack_zoned/pack_zoned
# unchanged -- only the TXN-RECORD layout around them is new this week.
def unpack_comp3(raw, scale):
    nibbles = []
    for byte in raw:
        nibbles.append((byte >> 4) & 0xF)
        nibbles.append(byte & 0xF)
    sign_nibble = nibbles[-1]
    digit_str = "".join(str(n) for n in nibbles[:-1])
    magnitude = Decimal(digit_str)
    if scale:
        magnitude = magnitude / (Decimal(10) ** scale)
    sign = -1 if sign_nibble in (0xD, 0xB) else 1
    return sign * magnitude

def pack_comp3(value, total_digits, scale, negative_nibble=0xD, positive_nibble=0xC):
    scaled = int((abs(value) * (Decimal(10) ** scale)).to_integral_value())
    digit_str = str(scaled).zfill(total_digits)
    sign_nibble = negative_nibble if value < 0 else positive_nibble
    nibbles = [int(c) for c in digit_str] + [sign_nibble]
    if len(nibbles) % 2 != 0:
        nibbles.insert(0, 0)
    raw = bytearray()
    for i in range(0, len(nibbles), 2):
        raw.append((nibbles[i] << 4) | nibbles[i + 1])
    return bytes(raw)

def unpack_zoned(raw):
    digits = []
    sign = 1
    for i, byte in enumerate(raw):
        zone = (byte >> 4) & 0xF
        digit = byte & 0xF
        digits.append(str(digit))
        if i == len(raw) - 1 and zone in (0xD, 0xB):
            sign = -1
    return sign * int("".join(digits))

def pack_zoned(value, digits):
    scaled = abs(value)
    digit_str = str(scaled).zfill(digits)
    raw = bytearray()
    for i, ch in enumerate(digit_str):
        d = int(ch)
        is_last = (i == len(digit_str) - 1)
        zone = (0xD if value < 0 else 0xC) if is_last else 0xF
        raw.append((zone << 4) | d)
    return bytes(raw)

TXN_LRECL = 55

def make_txn_record(txn_id, account_id, amount, balance_after, channel, ts):
    amount_bytes = pack_comp3(amount, total_digits=11, scale=2)
    balance_scaled_signed = int((balance_after * 100).to_integral_value())
    balance_bytes = pack_zoned(balance_scaled_signed, digits=11)
    row = (txn_id.ljust(10).encode() + account_id.ljust(10).encode()
           + amount_bytes + balance_bytes + channel.ljust(4).encode()
           + ts.ljust(14).encode())
    assert len(row) == TXN_LRECL, f"record is {len(row)} bytes, expected {TXN_LRECL}"
    return row

def decode_txn_record(raw):
    txn_id = raw[0:10].decode().rstrip()
    account_id = raw[10:20].decode().rstrip()
    amount = unpack_comp3(raw[20:26], scale=2)
    balance = Decimal(unpack_zoned(raw[26:37])) / Decimal(100)
    channel = raw[37:41].decode().rstrip()
    ts = raw[41:55].decode()
    return dict(txn_id=txn_id, account_id=account_id, amount=amount, balance_after=balance,
                channel=channel, ts=ts)

raw = make_txn_record("TXN0000001", "ACC0000001", Decimal("1234.56"), Decimal("-500.25"),
                       "POS ", "20260301083012")
print(f"encoded record: {len(raw)} bytes")
decoded = decode_txn_record(raw)
for k, v in decoded.items():
    print(f"  {k:<14} {v}")

Concept 2 — Replaying a Batch Extract Into Kafka at Controlled Wall-Clock Speed


The nightly extract lands as one flat file with no timing information of its own beyond each
record's TXN-TIMESTAMP. Replaying it into Kafka "as if streaming" means preserving each
record's relative event-time gaps, compressed by a fixed speed_factor — a 24-hour batch
replayed at speed_factor=3600 finishes in about 24 seconds of wall clock, with every
record's relative spacing intact. This is what lets Day 5's demo run the whole nightly file
through the pipeline in seconds instead of a real day, without inventing timing that never
happened.


Example:


import datetime as dt

def parse_ts(ts):
    return dt.datetime.strptime(ts, "%Y%m%d%H%M%S")

def build_replay_schedule(records, speed_factor):
    """records: dicts with a 'ts' field (TXN-TIMESTAMP, YYYYMMDDHHMMSS). Returns
    [(record, scheduled_offset_seconds)] preserving relative event-time gaps,
    compressed by speed_factor."""
    times = [parse_ts(r["ts"]) for r in records]
    t0 = min(times)
    schedule = [(r, (t - t0).total_seconds() / speed_factor) for r, t in zip(records, times)]
    return sorted(schedule, key=lambda pair: pair[1])

records = [
    {"txn_id": "TXN0000001", "ts": "20260301000512"},
    {"txn_id": "TXN0000002", "ts": "20260301000045"},
    {"txn_id": "TXN0000003", "ts": "20260301013000"},
]
sched = build_replay_schedule(records, speed_factor=3600)
for rec, offset in sched:
    print(f"{rec['txn_id']}  event_time={rec['ts']}  scheduled_offset={offset:.2f}s")
print(f"total wall-clock replay time at 3600x speed: {sched[-1][1]:.2f}s")

Concept 3 — Event-Time vs. Ingestion-Time Skew From a Batch-Only Source


Every record in the nightly file shares the same ingestion time — the moment the batch
job dropped the extract — while their event times are scattered across the previous 24
hours. That means the skew (ingestion_time - event_time) for a single batch spans nearly a
full day: a record from the first minute after the previous drop carries the largest skew,
one from moments before this drop carries almost none. This is exactly Week 07 Day 4's
point, measured directly on this week's own data: the batch window sets a floor, not a
single number, and the floor moves with where a given record fell inside the batch.


Example:


import datetime as dt

def ingestion_skew_seconds(event_time, batch_drop_time):
    return (batch_drop_time - event_time).total_seconds()

Concept 4 — Watermark Policy for Late and Out-of-Order Records


A nightly batch, replayed into Kafka in whatever row order the extract used, is — from a
streaming watermark's point of view — one enormous burst of records that arrive out of event
order. Reusing Week 07 Day 4 Concept 3's allowed-lateness pattern: the watermark advances to
max(event_time seen so far) - allowed_lateness, and any record whose event time falls
behind the current watermark routes to a side output instead of silently corrupting an
already-advanced state.


Example:


import dataclasses
import datetime as dt

@dataclasses.dataclass
class TxnEvent:
    txn_id: str
    event_time: dt.datetime
    ingestion_time: dt.datetime

def apply_watermark(events, allowed_lateness):
    """events consumed in ARRIVAL order -- exactly what a batch replay looks
    like. watermark = max event_time seen so far - allowed_lateness."""
    watermark = None
    on_time, late = [], []
    for ev in events:
        candidate_watermark = ev.event_time - allowed_lateness
        watermark = candidate_watermark if watermark is None else max(watermark, candidate_watermark)
        if ev.event_time >= watermark:
            on_time.append(ev)
        else:
            late.append(ev)
    return on_time, late, watermark

base = dt.datetime(2026, 3, 1, 0, 0, 0)
events = [
    TxnEvent("TXN0000002", base + dt.timedelta(seconds=45), base + dt.timedelta(seconds=45)),
    TxnEvent("TXN0000001", base + dt.timedelta(seconds=312), base + dt.timedelta(seconds=312)),
    TxnEvent("TXN0000003", base + dt.timedelta(seconds=5400), base + dt.timedelta(seconds=5400)),
    # a nightly batch dump delivers this LAST in arrival order even though its
    # event_time is far behind everything already ingested
    TxnEvent("TXN0000004", base + dt.timedelta(seconds=100), base + dt.timedelta(seconds=5410)),
]
on_time, late, wm = apply_watermark(events, allowed_lateness=dt.timedelta(minutes=2))
print("on_time:", [e.txn_id for e in on_time])
print("late (side output):", [e.txn_id for e in late])
print("final watermark:", wm)

BFSI Reality Check — Day 1


Legacy angle: The copybook and the nightly batch schedule both belong to the mainframe
application and scheduler teams, not to this pipeline. A COMP-3 field's digit count or the
batch drop time changing is a change-control item on their side, not a parameter this
pipeline can tune on its own.


Compliance angle: TXN-AMOUNT and BALANCE-AFTER are regulated financial data the
instant they are decoded, in exactly the same way whether they live in a COMP-3 byte range or
a modern Postgres row — an AML case file built from a misdecoded amount is a real,
reportable-quality defect, not a display glitch.


What breaks in production: Someone tunes the watermark's allowed-lateness window down "to
alert faster" without checking how spread out a real nightly batch's event times actually are
against its single ingestion time (Concept 3's own measurement). Records from early in the
batch window silently route to the side output every single night, and nobody notices until a
reconciliation job finds transactions that never reached an alert.

Concept 1 — Composing a Text Representation and Embedding It


Reusing Week 05 Day 1 Concept 1's trigrams/embed trigram-hash stand-in unchanged (no real
embedding model is available offline in this sandbox, exactly Week 05's own note) —
retargeted from insurance-claim text to a transaction's memo, counterparty, and channel
composed into one string.


Example:


import zlib
import numpy as np

DIM = 32
def trigrams(text):
    t = "  " + text.lower() + "  "
    return [t[i:i+3] for i in range(len(t) - 2)]

def embed(text, dim=DIM):
    vec = np.zeros(dim)
    for gram in trigrams(text):
        seed = zlib.crc32(gram.encode("utf-8"))
        rng = np.random.default_rng(seed)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

def compose_txn_text(txn):
    return f"{txn['memo']} | counterparty={txn['counterparty']} | channel={txn['channel']}"

def cosine(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

grocery_a = dict(memo="POS purchase groceries", counterparty="FRESHMART 04821", channel="POS")
grocery_b = dict(memo="POS purchase groceries", counterparty="FRESHMART 04821", channel="POS")
wire_out = dict(memo="wire transfer outbound to offshore holding company",
                counterparty="OFFSHORE HOLD CO LTD", channel="WIRE")
va, vb, vw = embed(compose_txn_text(grocery_a)), embed(compose_txn_text(grocery_b)), embed(compose_txn_text(wire_out))
print(f"composed text (grocery A): {compose_txn_text(grocery_a)!r}")
print(f"cosine(grocery_a, grocery_b) = {cosine(va, vb):.4f}")
print(f"cosine(grocery_a, wire_out)  = {cosine(va, vw):.4f}")

Concept 2 — Micro-Batched Embedding Inside the Consumer


Reusing Week 06 Day 4 Concept 1's MicroBatcher unchanged — flushing on whichever of
max_size or max_age_ms fires first, the same two-trigger pattern applied here to batching
transaction records before an embedding call instead of insurance claims.


Example:


class MicroBatcher:
    def __init__(self, max_size, max_age_ms):
        self.max_size = max_size
        self.max_age_ms = max_age_ms
        self.buffer = []
        self.buffer_started_at = None

    def add(self, record, now):
        if not self.buffer:
            self.buffer_started_at = now
        self.buffer.append(record)
        if len(self.buffer) >= self.max_size:
            return "size"
        if (now - self.buffer_started_at) * 1000 >= self.max_age_ms:
            return "age"
        return None

    def flush(self):
        batch, self.buffer, self.buffer_started_at = self.buffer, [], None
        return batch

arrivals = (
    [(f"TXN{i:04d}", t * 0.01) for i, t in enumerate(range(15))] +
    [(f"TXN{i:04d}", 0.15 + (i - 15) * 0.08) for i in range(15, 20)] +
    [(f"TXN{i:04d}", 0.55 + (i - 20) * 0.01) for i in range(20, 40)]
)
batcher = MicroBatcher(max_size=10, max_age_ms=150)
for txn_id, t in arrivals:
    trigger = batcher.add(txn_id, now=t)
    if trigger:
        batch = batcher.flush()
        print(f"t={t:5.2f}s  flush trigger={trigger:<5}  batch_size={len(batch):>2}")

Concept 4 — Consumer Lag and Backpressure as the Real Health Signal


Reusing Week 06 Day 4 Concept 3's BackpressureController (pause/resume on two watermarks,
preventing flapping at one boundary) and Day 3 Concept 4's burn_rate (lag's derivative,
not its absolute value) unchanged — together, the two answer "is the embed-and-upsert
consumer keeping up" without either flapping on noise or hiding a slow, steady decline behind
a currently-survivable absolute lag number.


Example:


class BackpressureController:
    def __init__(self, high_watermark, low_watermark):
        self.high = high_watermark
        self.low = low_watermark
        self.paused = False

    def on_queue_depth_change(self, depth):
        if not self.paused and depth >= self.high:
            self.paused = True
            return "pause"
        if self.paused and depth <= self.low:
            self.paused = False
            return "resume"
        return None

def burn_rate(lag_samples, interval_seconds):
    return [(lag_samples[i] - lag_samples[i - 1]) / interval_seconds
            for i in range(1, len(lag_samples))]

controller = BackpressureController(high_watermark=500, low_watermark=100)
depths = [50, 300, 520, 480, 300, 90, 40, 200, 600, 550, 80]
for depth in depths:
    action = controller.on_queue_depth_change(depth)
    if action:
        print(f"depth={depth:>4}  action={action}")

sample_interval_s = 30
recovering_samples = [4200, 3600, 3000, 2500, 2100]
degrading_samples = [800, 1400, 2000, 2700, 3400]
for label, samples in (("recovering", recovering_samples), ("degrading", degrading_samples)):
    rates = burn_rate(samples, sample_interval_s)
    print(f"{label}: current lag={samples[-1]}  latest burn rate={rates[-1]:+.1f} rec/s")

Concept 1 — k-NN Distance to an Account's Own Peer History


Reusing Week 04 Day 2 Concept 2's brute_force_topk unchanged — retargeted here from
"nearest corpus vectors for a benchmark" to "nearest historical transactions for THIS
account". The anomaly signal is distance to the account's own past, never to some global
population — a transaction pattern that is completely ordinary for one account can be exactly
what makes it anomalous for another.


Example:


import numpy as np

def brute_force_topk(points, query, k=10):
    return np.argsort(np.linalg.norm(points - query, axis=1))[:k]

def peer_distance_score(new_vec, history_vecs, k=3):
    """Mean distance to the k nearest historical transactions for this same
    account -- large mean k-NN distance means 'looks like nothing in this
    account's own past', not 'looks unusual in general'."""
    if len(history_vecs) == 0:
        return None
    k = min(k, len(history_vecs))
    idx = brute_force_topk(history_vecs, new_vec, k=k)
    dists = np.linalg.norm(history_vecs[idx] - new_vec, axis=1)
    return float(dists.mean())

# Account ACC0000001's ordinary pattern: small recurring grocery/gas/pharmacy POS purchases.
history_txns = [
    dict(memo="POS purchase groceries", counterparty="FRESHMART 04821", channel="POS"),
    dict(memo="POS purchase groceries", counterparty="FRESHMART 04821", channel="POS"),
    dict(memo="POS purchase gas station", counterparty="SHELL 00931", channel="POS"),
    dict(memo="POS purchase pharmacy", counterparty="CVS 01822", channel="POS"),
    dict(memo="POS purchase groceries", counterparty="FRESHMART 04821", channel="POS"),
]
history_vecs = np.array([embed(compose_txn_text(t)) for t in history_txns])

Concept 2 — Rule-Based Signals: Structuring, Velocity, Sanctions


Three independent rule signals, each answering a different question a distance score cannot:
structuring (multiple transactions each sitting just under the $10,000 CTR reporting
threshold, whose sum crosses it), velocity (more transactions in a short window than is
plausible), and sanctions (a counterparty name matching a watchlist). structuring_signal
flags the transaction that completes a structuring cluster looking backward — a design
choice worth stating plainly, not the whole cluster including transactions before it.


Example:


import dataclasses
import datetime as dt

SANCTIONS_LIST = {"OFFSHORE HOLD CO LTD", "NORTHSTAR SHELL TRADING", "VELOCITY CASH EXCHANGE"}
CTR_THRESHOLD = 10_000.00
STRUCTURING_MARGIN = 0.10

@dataclasses.dataclass
class Txn:
    txn_id: str
    account_id: str
    amount: float
    counterparty: str
    ts: dt.datetime

def structuring_signal(account_txns, window_hours=24):
    """Flags the SPECIFIC near-threshold transactions whose look-back window
    (also near-threshold) sums past CTR_THRESHOLD -- looking backward only, so
    the transaction that completes a cluster is flagged, not every transaction
    whose own window happens to contain one."""
    txns = sorted(account_txns, key=lambda t: t.ts)
    near_threshold_all = [t for t in txns
                           if CTR_THRESHOLD * (1 - STRUCTURING_MARGIN) <= t.amount < CTR_THRESHOLD]
    hits = []
    for t in near_threshold_all:
        window = [u for u in near_threshold_all
                  if 0 <= (t.ts - u.ts).total_seconds() <= window_hours * 3600]
        if len(window) >= 2 and sum(u.amount for u in window) >= CTR_THRESHOLD:
            hits.append(t.txn_id)
    return sorted(set(hits))

def velocity_signal(account_txns, window_minutes=60, max_count=3):
    txns = sorted(account_txns, key=lambda t: t.ts)
    hits = []
    for t in txns:
        window = [u for u in txns if 0 <= (t.ts - u.ts).total_seconds() <= window_minutes * 60]
        if len(window) > max_count:
            hits.append(t.txn_id)
    return sorted(set(hits))

def sanctions_signal(txns):
    return sorted(t.txn_id for t in txns if t.counterparty.upper() in SANCTIONS_LIST)

Concept 3 — Normalizing and Combining Distance and Rule Signals


peer_distance has no natural 0-1 ceiling (Concept 1's cosine-normalized-vector distances
can exceed 1.4); the three rule signals are already booleans. Clipping distance against an
empirically observed maximum before combining is what makes the two comparable at all —
combining a raw distance number with a 0/1 flag with no normalization would let the units
themselves, not the actual risk, decide which signal dominates.


Example:


def normalize_distance(d, max_expected=1.5):
    return min(d / max_expected, 1.0)

DISTANCE_WEIGHT = 0.30

def combined_risk_score(c):
    distance_component = normalize_distance(c["peer_distance"]) * DISTANCE_WEIGHT
    rule_component = (int(c["structuring_hit"]) + int(c["velocity_hit"]) + int(c["sanctions_hit"])) / 3 * (1 - DISTANCE_WEIGHT)
    return round(distance_component + rule_component, 4)

candidates = [
    dict(txn_id="TXN4001", peer_distance=0.02, structuring_hit=False, velocity_hit=False, sanctions_hit=False),
    dict(txn_id="TXN4002", peer_distance=1.04, structuring_hit=False, velocity_hit=False, sanctions_hit=False),
    dict(txn_id="TXN4003", peer_distance=0.15, structuring_hit=True, velocity_hit=False, sanctions_hit=False),
    dict(txn_id="TXN4004", peer_distance=0.08, structuring_hit=False, velocity_hit=True, sanctions_hit=False),
    dict(txn_id="TXN4005", peer_distance=1.30, structuring_hit=False, velocity_hit=False, sanctions_hit=True),
]
for c in candidates:
    score = combined_risk_score(c)
    c["risk_score"] = score
    print(f"{c['txn_id']}  peer_distance={c['peer_distance']:.2f}  rules="
          f"[S={int(c['structuring_hit'])} V={int(c['velocity_hit'])} X={int(c['sanctions_hit'])}]  "
          f"risk_score={score:.4f}")

Concept 4 — Tuning for Alert Precision at a Fixed Daily Review Volume


An analyst team can review a fixed number of alerts per day, no matter how many candidates
score above zero. Ranking candidates by combined_risk_score and taking the top-N (N = daily
review capacity) trades precision against recall exactly the way Week 26/27's evaluation
harnesses traded metric floors against coverage — a real, measured tradeoff to report, not a
single "best" number.


Example:


import random
random.seed(31)

    peer_distance = random.gauss(0.9, 0.35) if is_fraud else random.gauss(0.25, 0.25)
    peer_distance = max(0.0, peer_distance)
    p_rule = 0.55 if is_fraud else 0.08
    structuring_hit = random.random() < p_rule
    velocity_hit = random.random() < p_rule * 0.6
    sanctions_hit = random.random() < (0.15 if is_fraud else 0.01)
    return dict(txn_id=txn_id, peer_distance=peer_distance, structuring_hit=structuring_hit,
                velocity_hit=velocity_hit, sanctions_hit=sanctions_hit, is_fraud=is_fraud)

FRAUD_RATE = 0.06

pop_candidates = [make_candidate(f"TXN{5000+i}", labels[i]) for i in range(N_CANDIDATES)]
for c in pop_candidates:

ranked = sorted(pop_candidates, key=lambda c: c["risk_score"], reverse=True)

    print(f"review_capacity={review_capacity:>4}  precision={precision:.3f}  recall={recall:.3f}  "

Concept 1 — Alert Queue With an Evidence Bundle


An alert opened with only a risk score forces an analyst to re-derive why it fired from
scratch. EvidenceBundle carries the specific triggered rules and the nearest historical
transactions Day 3 Concept 1 already found — the exact evidence an analyst needs to make a
disposition, generated once at alert-open time rather than re-queried during review.


Example:


import dataclasses
import datetime as dt

@dataclasses.dataclass
class EvidenceBundle:
    triggered_rules: list
    nearest_history: list
    peer_distance: float
    risk_score: float

@dataclasses.dataclass
class Alert:
    alert_id: str
    txn_id: str
    account_id: str
    opened_at: dt.datetime
    evidence: EvidenceBundle
    disposition: object = None

def build_evidence_bundle(candidate, nearest_history):
    rules = [name for name, hit in (("structuring", candidate["structuring_hit"]),
                                     ("velocity", candidate["velocity_hit"]),
                                     ("sanctions", candidate["sanctions_hit"])) if hit]
    return EvidenceBundle(triggered_rules=rules, nearest_history=nearest_history,
                          peer_distance=candidate["peer_distance"], risk_score=candidate["risk_score"])

def open_alert(alert_id, candidate, account_id, opened_at, nearest_history):
    bundle = build_evidence_bundle(candidate, nearest_history)
    return Alert(alert_id, candidate["txn_id"], account_id, opened_at, bundle)

Concept 3 — SLA Timers and Escalation for Aging Alerts


An alert's tier (derived from its own risk score) sets how long it may sit undispositioned
before escalating — a high-risk alert gets 2 hours, medium gets 8, low gets 24. sla_status
checks age against the tier's SLA only for alerts still open; a dispositioned alert is simply
"closed", regardless of how long it took.


Example:


SLA_HOURS_BY_RISK = {"high": 2, "medium": 8, "low": 24}

def risk_tier(risk_score):
    if risk_score >= 0.4:
        return "high"
    if risk_score >= 0.2:
        return "medium"
    return "low"

def sla_status(alert, now):
    if alert.disposition is not None:
        return "closed"

    return f"within SLA (tier={tier}, sla={sla_hours}h, age={age_hours:.1f}h)"

Concept 4 — Closing the Loop: Re-Tuning Thresholds From Dispositions


Once a batch of alerts carries real analyst dispositions, precision_by_signal measures each
rule's actual confirmed-fraud rate directly from those labels — the number that should drive
whether a signal's weight goes up or down next cycle, replacing Day 3's synthetic ground
truth with genuine review outcomes. recommend_threshold sweeps the batch's own risk scores
and returns the lowest threshold that still meets a target precision, closing the loop Day 3
Concept 4 opened.


Example:


import random
random.seed(72)

@dataclasses.dataclass
class DispositionedAlert:
    alert_id: str
    triggered_rules: list
    risk_score: float
    verdict: Verdict

def make_review_batch(n):
    batch = []
    for i in range(n):
        is_fraud = random.random() < 0.35
        rules = []
        if random.random() < (0.7 if is_fraud else 0.25):
            rules.append("structuring")
        if random.random() < (0.5 if is_fraud else 0.10):
            rules.append("velocity")
        if random.random() < (0.2 if is_fraud else 0.02):
            rules.append("sanctions")
        risk_score = round(random.uniform(0.55, 0.95) if is_fraud else random.uniform(0.15, 0.6), 3)
        verdict = Verdict.CONFIRMED_FRAUD if is_fraud else Verdict.FALSE_POSITIVE
        batch.append(DispositionedAlert(f"ALT-{2000+i}", rules, risk_score, verdict))
    return batch

def precision_by_signal(dispositioned):
    result = {}
    for signal in ("structuring", "velocity", "sanctions"):
        fired = [a for a in dispositioned if signal in a.triggered_rules]
        if not fired:
            result[signal] = None
            continue
        hits = sum(1 for a in fired if a.verdict == Verdict.CONFIRMED_FRAUD)
        result[signal] = hits / len(fired)
    return result

def recommend_threshold(dispositioned, target_precision):
    thresholds = sorted({a.risk_score for a in dispositioned})
    best = None
    for t in thresholds:
        above = [a for a in dispositioned if a.risk_score >= t]
        if not above:
            continue
        hits = sum(1 for a in above if a.verdict == Verdict.CONFIRMED_FRAUD)
        precision = hits / len(above)
        if precision >= target_precision:
            if best is None or t < best:
                best = t
    return best

batch = make_review_batch(200)
sigs = precision_by_signal(batch)
for signal, prec in sigs.items():
    print(f"signal={signal:<12} precision-when-fired={prec:.3f}" if prec is not None
          else f"signal={signal:<12} never fired in this batch")
for target in (0.5, 0.6, 0.7):
    t = recommend_threshold(batch, target)
    print(f"target_precision={target}  recommended_threshold={t}")

Concept 2 — SLO, Error Budget, and Multi-Window Burn-Rate Alerting


Reusing Curriculum/Week_17_Capstone_Scale/W17_D3_Pipeline_Monitoring.ipynb CONCEPT 4's
SLO dataclass unchanged (error budget as 1 - target, burn rate as the error rate divided
by that budget fraction, and a two-window PAGE/TICKET/None alert rule) — the SLI here is
"fraction of streaming-sourced alerts delivered within their p95 latency budget", not
pipeline-run success, but the dataclass itself needs no change at all to carry a different
SLI.


Example:


from typing import Optional

@dataclasses.dataclass
class SLO:
    name: str
    sli_description: str
    target: float
    window_days: int = 30

    @property
    def error_budget_fraction(self) -> float:
        return 1.0 - self.target

    def error_budget_minutes(self) -> float:
        return self.window_days * 24 * 60 * self.error_budget_fraction

    def burn_rate(self, current_error_rate: float) -> float:
        if self.error_budget_fraction == 0:
            return float("inf")
        return current_error_rate / self.error_budget_fraction

    def budget_remaining(self, errors_so_far: int, total_events: int) -> float:
        if total_events == 0:
            return 1.0
        actual_error_rate = errors_so_far / total_events
        consumed = actual_error_rate / self.error_budget_fraction
        return max(0.0, 1.0 - consumed)

    def alert(self, burn_rate_1h: float, burn_rate_6h: float) -> Optional[str]:
        if burn_rate_1h > 14 and burn_rate_6h > 14:
            return "PAGE -- fast burn: budget exhausted in ~2 days"
        if burn_rate_1h > 5 and burn_rate_6h > 5:
            return "TICKET -- slow burn: budget exhausted in ~6 days"
        return None

streaming_slo = SLO(name="fraud-alert-streaming-latency",
                     sli_description="fraction of streaming-sourced alerts delivered within the 200ms p95 budget",
                     target=0.98, window_days=30)
print(f"SLO target: {streaming_slo.target*100:.1f}%  error budget: {streaming_slo.error_budget_fraction*100:.2f}%  "
      f"= {streaming_slo.error_budget_minutes():.0f} min over {streaming_slo.window_days} days")
late_events, total_events = 340, 10_000
br = streaming_slo.burn_rate(late_events / total_events)
remaining = streaming_slo.budget_remaining(late_events, total_events)
print(f"current state: {late_events}/{total_events} alerts missed the budget")
print(f"burn rate: {br:.2f}x   budget remaining: {remaining*100:.1f}%")
print(f"alert: {streaming_slo.alert(burn_rate_1h=br, burn_rate_6h=br*0.7)}")

Architecture Decision — Week 31


Choosing between: near-real-time streaming fraud/AML detection (this week's pipeline:
replay, embed, score, alert, all within a couple hundred milliseconds of a record reaching
Kafka) and true real-time detection (scoring a transaction before it settles, in the
authorization path itself) — decided against what Day 1 established as this system's actual
source of truth: a nightly mainframe batch cycle.


Rule of thumb: Build near-real-time streaming detection, exactly this week's pipeline, when
the source itself is periodic — a nightly extract, an end-of-day settlement file, any batch
cycle this pipeline does not control — because true real-time detection promises a guarantee
the source cannot back up. Day 5 Concept 1's own numbers make the case directly: the streaming
path adds under 200ms end to end, but the earliest any of that streaming engineering can
possibly start is gated by Day 1's batch drop time, itself many hours behind the transactions
it describes. Promising "real-time fraud detection" against data that is, by construction,
already hours old at the moment it first becomes visible is exactly the failure mode Week 07's
own closing Architecture Decision named for CDC sources — a written promise the source was
never going to keep — now demonstrated end to end against a working pipeline instead of argued
in the abstract.


True real-time detection is the right target only when the transaction itself streams live —
a card-authorization system with a synchronous, sub-100ms decision in the actual payment path,
where the source of truth is the authorization request itself, not a downstream extract of it.
That is a genuinely different system, with a genuinely different latency budget (the p95
figures in this week's own Day 5 Concept 1 would be an order of magnitude too generous for an
authorization decision), a different failure mode (a slow score blocks a real transaction
instead of merely delaying an alert), and a different acceptable false-positive cost (declining
a legitimate purchase in real time costs a customer relationship in a way a same-day analyst
review does not). Migrating this week's pipeline toward that target is not a matter of tuning
Day 2's micro-batcher down to batch size 1 — it requires a genuinely different source
integration, one this week's mainframe-sourced system does not have and, per Week 07's own
capability matrix, cannot be made to have without a different source system entirely.


The professional deliverable this capstone — and this entire 31-week track — has been
building toward is not "the fastest possible pipeline." It is a pipeline that is honest, in
writing, about exactly how fresh its answers are: Week 07's per-record provenance and
staleness budget, now closed by this week's own working demonstration that near-real-time
streaming detection against a nightly-batch source of truth is not a compromise to apologize
for. It is the correct engineering answer to the source's own real constraints, stated
plainly rather than disguised as something faster than it is — the same discipline every
capstone in Phase 6, and every Royal Road Standard since Week 01, has asked for: know exactly
what your system actually guarantees, and never claim more than that in front of a regulator,
an analyst, or a customer whose transaction it just flagged.
