Concept 1 — Normalize Before You Hash

A raw byte-for-byte hash of a document's text is the wrong comparison. Two exports of the exact same claim note commonly differ in whitespace, casing, or a trailing boilerplate footer stamped on by whatever system last touched the file — none of which is a real content change, and none of which should burn an embedding call. Hash the normalized text: whitespace collapsed, lowercased, and any known boilerplate stripped.

The normalization function is itself a piece of pipeline logic that has to be versioned and reused consistently — if the ingest job and the drift-detection job normalize differently, they will disagree about what "changed" means.

Example:

import hashlib
import re

def normalize_for_hash(text):
    """Lowercase, collapse whitespace, strip a trailing boilerplate footer.
    Two documents that differ only in these ways are the same content for
    re-embedding purposes -- hashing the raw bytes would treat them as changed
    and burn an embedding call for no real difference."""
    text = re.sub(r"\s+", " ", text.strip().lower())
    text = re.sub(r"this document is confidential.*$", "", text).strip()
    return text

def content_hash(text):
    return hashlib.sha256(normalize_for_hash(text).encode("utf-8")).hexdigest()

doc_a = "Policy POL-88213 covers water damage up to $50,000.\n\nThis document is confidential and intended for internal use only."
doc_b = "policy pol-88213   covers water damage up to $50,000.  \nThis document is confidential and intended for internal use only. v2 stamp"
doc_c = "Policy POL-88213 covers water damage up to $75,000.\n\nThis document is confidential and intended for internal use only."

print("hash(a):", content_hash(doc_a)[:16])
print("hash(b):", content_hash(doc_b)[:16])
print("hash(c):", content_hash(doc_c)[:16])
print("a == b (whitespace/case/footer differ only):", content_hash(doc_a) == content_hash(doc_b))
print("a == c (real content differs):", content_hash(doc_a) == content_hash(doc_c))

Concept 2 — Chunk-Level Hashes Find the Change, Document-Level Hashes Only Find That Something Changed


A document-level hash tells you a policy changed somewhere. It does not tell you which
of its 40 chunks actually changed, so acting on it alone means re-embedding the whole
document — exactly the full-reindex cost this week exists to avoid. Hash each chunk
independently and you localize the change: only the chunks whose hash moved need a new
embedding call, and every other chunk's existing vector is still correct and reusable.


The cost of chunk-level hashing is bookkeeping — you now store one hash per chunk
instead of one per document — and that cost is worth it the moment a document has more
than a handful of chunks.


Example:


def split_into_chunks(text, size=60):
    words = text.split()
    chunks = []
    cur = []
    cur_len = 0
    for w in words:
        cur.append(w)
        cur_len += len(w) + 1
        if cur_len >= size:
            chunks.append(" ".join(cur))
            cur, cur_len = [], 0
    if cur:
        chunks.append(" ".join(cur))
    return chunks

    "premises up to the stated limit. Section 2. Exclusions. Flood damage "
    "arising from a named storm is excluded unless a flood endorsement is "
    "attached. Section 3. Deductible. The deductible is five hundred dollars "
    "per occurrence, applied before any payout is calculated."
)

    "arising from a named storm is excluded unless a flood endorsement is "

Concept 3 — Storing source_hash Beside the Vector


The hash only pays off once it is stored next to the embedding it corresponds to, so a
sync job can compare "what's the hash of this chunk right now" against "what hash did
we embed last time" before deciding whether to call the embedding API at all. This is
the same idea Week 06 used for the point-id hash, applied one step earlier in the
pipeline: there, the hash made a duplicate delivery a harmless no-op at write time; here,
it makes an unchanged document a skipped embedding call before any write is attempted.


Example:


import numpy as np

class VectorIndexRow:
    def __init__(self, chunk_id, source_hash, embedding, model_id):
        self.chunk_id = chunk_id
        self.source_hash = source_hash
        self.embedding = embedding
        self.model_id = model_id

def fake_embed(text, dim=8, seed=None):
    rng = np.random.default_rng(seed if seed is not None else abs(hash(text)) % (2**32))
    return rng.normal(size=dim).round(4)

index = {}
embed_calls = 0

def sync_document(doc_id, chunks, model_id="embed-v1"):
    global embed_calls
    n_reused, n_embedded = 0, 0
    for i, chunk_text in enumerate(chunks):
        chunk_id = f"{doc_id}::chunk{i}"
        h = content_hash(chunk_text)
        existing = index.get(chunk_id)
        if existing is not None and existing.source_hash == h and existing.model_id == model_id:
            n_reused += 1
            continue
        embed_calls += 1
        n_embedded += 1
        index[chunk_id] = VectorIndexRow(chunk_id, h, fake_embed(chunk_text), model_id)
    return n_reused, n_embedded

r1 = sync_document("POL-88213", chunks_v1)
print(f"first sync : reused={r1[0]}  embedded={r1[1]}  total embed calls so far={embed_calls}")
r2 = sync_document("POL-88213", chunks_v1)
print(f"re-sync, no change : reused={r2[0]}  embedded={r2[1]}  total embed calls so far={embed_calls}")
r3 = sync_document("POL-88213", chunks_v2)
print(f"re-sync after edit : reused={r3[0]}  embedded={r3[1]}  total embed calls so far={embed_calls}")

BFSI Reality Check — Day 1


Legacy angle: A nightly extract off an on-prem policy admin system frequently
re-writes every row's last_modified timestamp on every extract run, whether or not the
row's actual content changed — a batch-job artifact, not a real edit. A pipeline that
trusts last_modified for change detection re-embeds the entire corpus every night;
content hashing is what actually detects a real change under that constraint.


Compliance angle: A source_hash column recorded beside every embedding is exactly
the evidence a "why was this record re-processed" audit question needs — it lets you
show precisely which chunks changed and when, rather than asserting a re-embed happened
for a good reason with nothing to back it.


What breaks in production: Two teams normalize differently before hashing — one
strips a footer, the other doesn't — and their change-detection jobs quietly disagree
about which documents changed. normalize_for_hash has to live in one shared library,
not be reimplemented per job.

Concept 1 — model_id and dim as First-Class Columns


Vectors from two different embedding models are not comparable, even at the same
dimension — they were produced by different projections of meaning into vector space,
and a cosine score between them means nothing. The only safe practice is to record which
model produced a vector, and its dimension, as real columns on the stored record, and to
refuse any operation that would mix vectors carrying different model_id values inside
one comparison.


Example:


from dataclasses import dataclass

@dataclass
class EmbeddingRecord:
    chunk_id: str
    model_id: str
    dim: int
    vector: tuple

def make_record(chunk_id, model_id, dim, vector):
    if len(vector) != dim:
        raise ValueError(f"{chunk_id}: vector has {len(vector)} components, dim says {dim}")
    return EmbeddingRecord(chunk_id, model_id, dim, tuple(vector))

rec_v1 = make_record("POL-88213::chunk0", "embed-v1", 4, [0.1, 0.2, 0.3, 0.4])
rec_v2 = make_record("POL-88213::chunk0", "embed-v2-1536d", 6, [0.11, 0.22, 0.31, 0.4, 0.5, 0.6])
print(rec_v1)
print(rec_v2)
print("comparable across model_id/dim:", rec_v1.model_id == rec_v2.model_id and rec_v1.dim == rec_v2.dim)

try:
    make_record("bad", "embed-v2", 8, [0.1, 0.2])
except ValueError as e:
    print("rejected mismatched vector:", e)

Concept 2 — Dual-Write During a Model Change


The moment you decide to move to a new embedding model, you have two options for the
transition: cut over instantly (and lose the ability to compare or roll back), or write
every new/changed chunk to both the old and the new model's collection while the
migration is in flight. Dual-write is more expensive — every embedding call happens
twice, against two different models — but it is the only way to have a fully populated
new collection to evaluate before committing to it, without a service outage in between.


Example:


import hashlib
import numpy as np

def fake_embed(text, dim, model_tag):
    """Deterministic stand-in for a real embedding call, built as a hashed
    bag-of-words vector so it actually carries word-overlap signal (unlike pure
    random noise) -- close enough to a real embedding's behaviour that two
    different model_tags still largely agree on *which* documents are similar,
    while producing vectors of different width that are not directly comparable
    across model_tag (a different hash salt per model, exactly like two real
    embedding models are two different, non-interchangeable projections)."""
    vec = np.zeros(dim)
    for word in text.lower().split():
        h = int(hashlib.sha256(f"{model_tag}|{word}".encode()).hexdigest(), 16)
        idx = h % dim
        sign = 1.0 if (h // dim) % 2 == 0 else -1.0
        vec[idx] += sign
    norm = np.linalg.norm(vec)
    return (vec / norm if norm > 0 else vec).round(4).tolist()

collection_v1 = {}
collection_v2 = {}

def dual_write(chunk_id, text):
    collection_v1[chunk_id] = make_record(chunk_id, "embed-v1", 16, fake_embed(text, 16, "embed-v1"))
    collection_v2[chunk_id] = make_record(chunk_id, "embed-v2", 24, fake_embed(text, 24, "embed-v2"))

texts = {
    "POL-1::chunk0": "Water damage covered up to policy limit.",
    "POL-2::chunk0": "Flood damage excluded without endorsement.",
    "POL-3::chunk0": "Deductible five hundred dollars per occurrence.",
    "POL-4::chunk0": "Total loss settlement paid within thirty days.",
    "POL-5::chunk0": "Named-storm exclusion applies to this endorsement.",
    "POL-6::chunk0": "Renewal premium increased by four percent.",
    "POL-7::chunk0": "Subrogation rights reserved against third party.",
    "POL-8::chunk0": "Umbrella policy extends liability coverage.",
}
for cid, t in texts.items():
    dual_write(cid, t)

print(f"collection_v1 size={len(collection_v1)} (model_id={next(iter(collection_v1.values())).model_id})")
print(f"collection_v2 size={len(collection_v2)} (model_id={next(iter(collection_v2.values())).model_id})")
print("both collections stay fully populated and searchable during the migration window.")

Concept 3 — A Shadow Index Gets Scored Before It Gets Trusted


Having a fully populated new-model collection is not the same as having a good new
collection. Before any cutover, run the same fixed query set from Week 01 Day 5 against
both collections and measure how much the new model's top-k results agree with the old
model's — the "shadow index" is evaluated exactly like an ANN configuration change,
against a real metric, with a real gate. A migration that skips this step finds out
whether the new model was any good only after users are already searching it.


Example:


def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float((a @ b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def search(store, query_vec, k=2):
    scored = [(cid, cosine(rec.vector, query_vec)) for cid, rec in store.items()]
    scored.sort(key=lambda x: -x[1])
    return [cid for cid, _ in scored[:k]]

query_texts = [
    "water damage claim",
    "flood exclusion question",
    "premium renewal notice",
    "liability coverage extension",
]

def recall_at_k(results_a, results_b, k):
    return len(set(results_a[:k]) & set(results_b[:k])) / k

K = 3
overlaps = []
for q in query_texts:
    qv1 = fake_embed(q, 16, "embed-v1")
    qv2 = fake_embed(q, 24, "embed-v2")
    top_v1 = search(collection_v1, qv1, k=K)
    top_v2 = search(collection_v2, qv2, k=K)
    overlaps.append(recall_at_k(top_v1, top_v2, K))
    print(f"query={q!r:32}  top_v1={top_v1}  top_v2={top_v2}  overlap@{K}={overlaps[-1]:.2f}")
mean_overlap = sum(overlaps) / len(overlaps)
print(f"mean overlap@{K} across query set: {mean_overlap:.2f}")

CUTOVER_THRESHOLD = 0.8
decision = "CUTOVER APPROVED" if mean_overlap >= CUTOVER_THRESHOLD else "HOLD -- shadow index not ready"
print(f"decision at threshold {CUTOVER_THRESHOLD}: {decision}")

Concept 1 — An Alias Is the Only Thing a Reader Should Ever Know About


Readers should query a name, never a specific collection. Building the point of
indirection in up front — an alias that maps a stable name to whichever concrete
collection is currently live — turns "cut over to the rebuilt index" into a single
pointer update instead of a coordinated change across every caller.


Example:


collections = {
    "claims_v1": {"chunk_a": "vec-a-v1", "chunk_b": "vec-b-v1"},
    "claims_v2": {"chunk_a": "vec-a-v2", "chunk_b": "vec-b-v2", "chunk_c": "vec-c-v2"},
}
alias = {"claims_search": "claims_v1"}

def resolve(alias_name):
    return collections[alias[alias_name]]

def swap_alias(alias_name, new_target):
    if new_target not in collections:
        raise KeyError(f"cannot point alias at unknown collection {new_target!r}")
    old = alias[alias_name]
    alias[alias_name] = new_target
    return old, new_target

print("reads before swap:", resolve("claims_search"))
old, new = swap_alias("claims_search", "claims_v2")
print(f"alias swapped: {old} -> {new}")
print("reads after swap :", resolve("claims_search"))
print("no reader changed a single line of query code -- only the alias target moved.")

Concept 2 — A Throttled Backfill Worker Fed by a Queue


Rebuilding a collection from scratch means re-embedding every chunk, and doing that as
fast as possible is exactly how you exhaust an embedding API's rate limit or starve every
other consumer of it. A backfill worker instead pulls fixed-size batches off a queue at a
throttled rate, and its progress is itself a piece of state — how many batches are done,
how many remain — that a reader can check without touching the collection being built.


Example:


def build_backfill_queue(source_ids, batch_size):
    return [source_ids[i:i + batch_size] for i in range(0, len(source_ids), batch_size)]

def run_backfill(queue, embed_cost_ms_per_item, rate_limit_batches_per_tick):
    ticks = 0
    processed = 0
    log = []
    i = 0
    while i < len(queue):
        this_tick_batches = queue[i:i + rate_limit_batches_per_tick]
        for batch in this_tick_batches:
            processed += len(batch)
        log.append((ticks, processed))
        i += rate_limit_batches_per_tick
        ticks += 1
    total_ms = processed * embed_cost_ms_per_item
    return ticks, processed, total_ms, log

source_ids = [f"claim-{i:04d}" for i in range(1, 251)]
queue = build_backfill_queue(source_ids, batch_size=25)
print(f"queue has {len(queue)} batches of up to 25 items each ({len(source_ids)} total ids)")

ticks, processed, total_ms, log = run_backfill(queue, embed_cost_ms_per_item=40, rate_limit_batches_per_tick=2)
print(f"backfill finished in {ticks} ticks, processed {processed} items, "
      f"estimated embed time {total_ms/1000:.1f}s")
print("progress checkpoints (tick, cumulative processed):", log)

Concept 3 — Reads Stay Served Throughout the Rebuild


Put Concepts 1 and 2 together and the shape of a real zero-downtime reindex falls out:
the alias keeps serving the old collection while the backfill worker populates the
new one in the background, and only once the backfill reports complete does the alias
move. At every point before that, a reader gets a complete, correct (if slightly stale)
answer from the old collection — never a partial answer from a collection still being
built.


Example:


from dataclasses import dataclass

@dataclass
class ReindexRun:
    target_collection: str
    total_batches: int
    completed_batches: int = 0
    status: str = "running"

    def checkpoint(self, n_batches_done):
        self.completed_batches += n_batches_done
        if self.completed_batches >= self.total_batches:
            self.status = "ready_for_cutover"
        return self.progress_pct()

    def progress_pct(self):
        return round(100 * self.completed_batches / self.total_batches, 1)

run = ReindexRun(target_collection="claims_v3", total_batches=10)
serving_from = "claims_v2"
for step in (3, 3, 4):
    pct = run.checkpoint(step)
    print(f"backfill progress: {pct}%  status={run.status}  reads still served from={serving_from}")

if run.status == "ready_for_cutover":
    print(f"cutover: reads now served from {run.target_collection}; old collection {serving_from} kept until confirmed stable")

What breaks in production: A cutover triggered by a backfill job that reports
"complete" based on batch count alone, without verifying every batch actually succeeded.
A batch that silently failed mid-run still counts toward "done", and the new collection
goes live missing exactly the chunks that failed — which Day 4's reconciliation count is
built to catch.

Concept 1 — A Freshness Metric Emitted Per Source System


Staleness is a simple, honest measurement: how long has the index been behind the
source's last known change, measured right now. If the index was written after the
source's last change, staleness is zero — the index is caught up. If not, staleness
grows every second the gap goes unaddressed, and it has to be computed per source
system, because different sources land on wildly different schedules.


Example:


import datetime as dt

def staleness_seconds(source_changed_at, indexed_at, now):
    if indexed_at >= source_changed_at:
        return 0.0
    return (now - source_changed_at).total_seconds()

NOW = dt.datetime(2026, 9, 5, 9, 0, 0, tzinfo=dt.timezone.utc)

    ("claims_core_mssql", dt.datetime(2026, 9, 5, 8, 40, tzinfo=dt.timezone.utc), dt.datetime(2026, 9, 5, 8, 58, tzinfo=dt.timezone.utc)),
    ("policy_admin_oracle", dt.datetime(2026, 9, 5, 4, 10, tzinfo=dt.timezone.utc), dt.datetime(2026, 9, 4, 23, 0, tzinfo=dt.timezone.utc)),
    ("agent_notes_api", dt.datetime(2026, 9, 5, 8, 59, tzinfo=dt.timezone.utc), dt.datetime(2026, 9, 5, 9, 0, tzinfo=dt.timezone.utc)),
]
for name, changed_at, indexed_at in sources:
    s = staleness_seconds(changed_at, indexed_at, NOW)
    print(f"{name:22} staleness={s:8.0f}s  ({s/60:6.1f} min)")

Concept 2 — Alert Thresholds Tied to a Written Staleness Budget


The same staleness number means something completely different to two different
downstream use cases. Week 07 Day 4 introduced UseCase and freshness_gate to filter
individual records by a per-use-case staleness budget at read time; reused here, the same
UseCase.max_staleness_seconds becomes the threshold an alert fires against at the
source-system level, closing the loop between "here is the budget we promised" and "here
is whether we are inside it right now."


Example:

# *budget* an alert fires against, rather than a per-record read-time filter.
from dataclasses import dataclass

Concept 3 — Orphaned Vectors Left Behind by Source Deletes


Staleness so far assumes the source record still exists somewhere, just not yet
reflected in the index. The opposite failure is just as real: a source record gets
deleted, and nothing ever tells the vector index to remove the chunks that used to belong
to it. Those chunks are now orphans — searchable, retrievable, and referring to a claim
or policy that no longer exists in the system of record. Finding them means comparing the
live set of source ids against the set of document ids the index actually holds.


Example:


source_ids_now = {"CLM-1001", "CLM-1002", "CLM-1004", "CLM-1005"}
indexed_chunk_ids = {
    "CLM-1001::chunk0", "CLM-1001::chunk1",
    "CLM-1002::chunk0",
    "CLM-1003::chunk0",   # CLM-1003 was deleted at source, never removed from the index
    "CLM-1004::chunk0",
}

def find_orphans(indexed_chunk_ids, source_ids_now):
    return sorted({cid for cid in indexed_chunk_ids if cid.split("::")[0] not in source_ids_now})

orphans = find_orphans(indexed_chunk_ids, source_ids_now)
print("orphaned chunk ids (source record no longer exists):", orphans)
print(f"orphan rate: {len(orphans)}/{len(indexed_chunk_ids)} indexed chunks")

BFSI Reality Check — Day 4


Legacy angle: A source-system delete on an on-prem mainframe is frequently a soft
delete — a status flag flips rather than the row disappearing — and a naive "row missing
from a nightly extract" orphan check misses it entirely, because the row is still there,
just flagged inactive. The reconciliation logic has to know each source system's actual
delete semantics, not assume a uniform one.


Compliance angle: An orphaned vector for a deleted claim is a live data-retention
problem, not just a housekeeping one — if the source system deleted the record to honor a
retention or right-to-erasure obligation, a surviving searchable vector defeats that
deletion. Orphan reconciliation is part of making a deletion actually complete.


What breaks in production: Staleness alerts are wired up, watched closely for the
first month, and then the alert channel gets muted during an unrelated incident and never
unmuted. A staleness monitor nobody is actually reading is functionally the same as having
none, and it is worse than having none if its presence is what let the "we monitor this"
box get checked.

Concept 1 — Diff Source Against Stored Hashes, Re-Embed Only What Changed


Everything from Days 1–4 comes together in one job: for every document in the source,
compute its current content hash, compare it against the hash stored from the last run,
and only call the embedding API for documents whose hash actually moved (or that are
brand new). Everything else is skipped, cheaply, by a dictionary lookup.


Example:


import hashlib
import re
import random

def normalize_for_hash(text):
    return re.sub(r"\s+", " ", text.strip().lower())

def content_hash(text):
    return hashlib.sha256(normalize_for_hash(text).encode("utf-8")).hexdigest()

random.seed(42)
TOPICS = [
    "water damage kitchen ceiling upstairs pipe burst",
    "rear-end collision intersection bumper damage",
    "theft laptop jewelry vehicle parking lot",
    "flood exclusion named storm endorsement required",
    "total loss settlement thirty day payout window",
    "subrogation rights reserved third party claim",
    "deductible five hundred dollars per occurrence",
    "renewal premium increase four percent notice",
    "umbrella policy extends liability coverage limit",
    "fire damage detached garage smoke contamination",
]
CORPUS_SIZE = 400
corpus = {f"CLM-{i:05d}": f"{TOPICS[i % len(TOPICS)]} case reference {i}" for i in range(CORPUS_SIZE)}

# Simulated prior run's stored hashes -- the state the incremental job diffs against.
stored_hashes = {doc_id: content_hash(text) for doc_id, text in corpus.items()}

# One day's real-world change volume: a small number of documents actually changed.
changed_ids = random.sample(list(corpus.keys()), k=12)
today_corpus = dict(corpus)
for cid in changed_ids:
    today_corpus[cid] = today_corpus[cid] + " amended endorsement attached"

def diff_against_stored_hashes(today_corpus, stored_hashes):
    changed, unchanged, new = [], [], []
    for doc_id, text in today_corpus.items():
        h = content_hash(text)
        if doc_id not in stored_hashes:
            new.append(doc_id)
        elif stored_hashes[doc_id] != h:
            changed.append(doc_id)
        else:
            unchanged.append(doc_id)
    return changed, unchanged, new

changed, unchanged, new = diff_against_stored_hashes(today_corpus, stored_hashes)
print(f"corpus size: {len(today_corpus)}")
print(f"changed: {len(changed)}   unchanged: {len(unchanged)}   new: {len(new)}")
print("changed ids match the injected edits:", sorted(changed) == sorted(changed_ids))

Concept 2 — Delete-Then-Upsert vs In-Place Update, Per Store


Not every vector store updates an existing point the same way. Some (older collection
APIs without a native upsert) require deleting the old point before the new one can be
written; others (pgvector via ON CONFLICT, Qdrant's native upsert, modern Milvus) update
in place by primary key with no separate delete step. The two converge on the same final
state, but delete-then-upsert opens a brief window where a concurrent read for that exact
id can miss — a window in-place update never has.


Example:


index_delete_then_upsert = {doc_id: {"hash": h, "vector": f"vec::{doc_id}::v1"} for doc_id, h in stored_hashes.items()}
index_in_place = dict(index_delete_then_upsert)

def fake_embed_id(doc_id, text):
    return f"vec::{doc_id}::{content_hash(text)[:6]}"

def apply_delete_then_upsert(index, doc_id, text):
    if doc_id in index:
        del index[doc_id]
    index[doc_id] = {"hash": content_hash(text), "vector": fake_embed_id(doc_id, text)}

def apply_in_place_update(index, doc_id, text):
    index[doc_id] = {"hash": content_hash(text), "vector": fake_embed_id(doc_id, text)}

for cid in changed_ids:
    apply_delete_then_upsert(index_delete_then_upsert, cid, today_corpus[cid])
    apply_in_place_update(index_in_place, cid, today_corpus[cid])

print(f"index size after delete-then-upsert path: {len(index_delete_then_upsert)} (should equal {CORPUS_SIZE})")
print(f"index size after in-place update path   : {len(index_in_place)} (should equal {CORPUS_SIZE})")
both_agree = all(index_delete_then_upsert[cid]["hash"] == index_in_place[cid]["hash"] for cid in changed_ids)
print("both paths converge to the same stored hash per changed id:", both_agree)

Concept 3 — Verifying Counts and Measuring the Spend Saved


The job is only trustworthy once you can show the source and the index agree on
membership after it runs, and once you can put a number on what skipping unchanged
documents actually saved. Both come nearly free once Concepts 1 and 2 exist: the count
check is a set-equality comparison, and the cost saved is the ratio of what you actually
embedded against what a full reindex would have embedded.


Example:


COST_PER_EMBED_CALL_USD = 0.0001  # illustrative flat per-chunk embedding cost

def run_incremental_job(today_corpus, stored_hashes, cost_per_call):
    changed, unchanged, new = diff_against_stored_hashes(today_corpus, stored_hashes)
    to_embed = changed + new
    new_hashes = dict(stored_hashes)
    for doc_id in to_embed:
        new_hashes[doc_id] = content_hash(today_corpus[doc_id])
    return {
        "embedded": len(to_embed),
        "skipped": len(unchanged),
        "total": len(today_corpus),
        "cost_usd": round(len(to_embed) * cost_per_call, 6),
        "new_hashes": new_hashes,
    }

full_reindex_cost = round(len(today_corpus) * COST_PER_EMBED_CALL_USD, 6)
result = run_incremental_job(today_corpus, stored_hashes, COST_PER_EMBED_CALL_USD)
savings_pct = round(100 * (1 - result["cost_usd"] / full_reindex_cost), 1)

print(f"full reindex would embed all {len(today_corpus)} chunks, cost=${full_reindex_cost}")
print(f"incremental job embedded {result['embedded']}, skipped {result['skipped']}, cost=${result['cost_usd']}")
print(f"embedding spend saved vs full reindex: {savings_pct}%")

def verify_counts(today_corpus, new_hashes):
    return set(today_corpus) == set(new_hashes)

print("source vs index count reconciliation after the run:", verify_counts(today_corpus, result["new_hashes"]))

BFSI Reality Check — Day 5


Legacy angle: "The source" is rarely one clean feed — a real claims corpus is
assembled from a nightly MSSQL extract, an intraday adjuster-notes API, and an
occasional manual CSV correction, each on its own schedule. The incremental job's
stored_hashes dict has to be keyed consistently across all three, or a document that
changed in one feed but not another gets silently missed.


Compliance angle: The savings-percentage figure this job produces is not just a cost
metric — it is evidence, alongside the reconciliation check, that the pipeline processed
exactly the records that changed and nothing else, which is precisely the kind of
declared, reproducible processing record a documentation-obligation audit asks for.


What breaks in production: The incremental job runs fine for months, quietly assuming
stored_hashes never gets corrupted or reset. The day someone truncates that table by
accident, every document in the corpus reads as "new," and the next run silently becomes
a full reindex — at full cost, with no warning, on whatever schedule the job normally
runs on unattended.




Architecture Decision — Week 11


Choosing between: full periodic reindex vs. incremental (diff-and-patch) updates vs.
dual-write during a migration.


Rule of thumb: run incremental updates as the default steady-state job — Day 5's
measurement showed a 97% embedding-spend reduction against a full reindex on a corpus
where only 3% of documents actually changed, and that ratio only improves as the corpus
grows while daily change volume stays roughly flat. Fall back to a full periodic reindex
only when the incremental job's own precondition breaks — the stored-hash table is lost
or suspected corrupted, the chunking strategy itself changes (Week 09's boundaries move,
so every existing chunk id is stale by definition), or a scheduled reconciliation
(Day 4) finds drift too large to trust incremental patching to close safely. Reach for
dual-write only for the one case it actually solves — a change of embedding model,
where old and new vectors are never comparable in the same index regardless of how
current either one is — and treat it as a bounded-duration migration state, not a
steady-state pattern: it doubles embedding cost for as long as it runs, and it exists
solely to populate a shadow index that a real evaluation, not a deadline, should be what
authorizes cutting over.
