Concept 1 — Typed State With TypedDict and Annotated Reducers

A StateGraph's state is a plain TypedDict (or a Pydantic model), but a field with no Annotated reducer is simply overwritten by whatever a node returns for it — a node that only wants to append a note, not replace every note a previous node wrote, needs a real reducer function attached via Annotated[type, reducer]. operator.add is the simplest one: for a list-typed field it concatenates, so each node's partial return merges into the accumulated state instead of clobbering it.

Example:

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class ClaimState(TypedDict):
    claim_id: str
    notes: Annotated[list[str], operator.add]
    risk_score: float

def intake_node(state):
    return {"notes": ["intake: claim received"], "risk_score": 0.0}

def score_node(state):
    return {"notes": ["scoring: applied fraud model"], "risk_score": 0.62}

g = StateGraph(ClaimState)
g.add_node("intake", intake_node)
g.add_node("score", score_node)
g.add_edge(START, "intake")
g.add_edge("intake", "score")
g.add_edge("score", END)
graph = g.compile()

result = graph.invoke({"claim_id": "CLM-1001", "notes": [], "risk_score": 0.0})
print(f"notes: {result['notes']}")
print(f"risk_score: {result['risk_score']}")

Concept 2 — add_messages Versus operator.add, and Writing a Custom Reducer


add_messages (the reducer behind every message-carrying LangGraph state) is not just
"concatenate like operator.add" — it merges by each message's id, so a node that
returns a message sharing an existing message's id REPLACES it in place rather than
appending a duplicate. That matters for a status message a pipeline updates in place as a
claim moves through stages, not a full transcript where every turn should be kept. A
reducer is nothing more than a two-argument (existing, new) -> merged function — nothing
stops writing one for a type add_messages/operator.add were never designed for, like
keeping the worst-case duration recorded for a stage across a retry instead of letting the
retry's number silently overwrite the first attempt's.


Example:


from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list, add_messages]

def status_v1(state):
    return {"messages": [{"role": "assistant", "content": "processing your claim", "id": "status-msg"}]}

def status_v2(state):
    return {"messages": [{"role": "assistant", "content": "claim approved", "id": "status-msg"}]}

g = StateGraph(ChatState)
g.add_node("v1", status_v1)
g.add_node("v2", status_v2)
g.add_edge(START, "v1")
g.add_edge("v1", "v2")
g.add_edge("v2", END)
graph = g.compile()
result = graph.invoke({"messages": []})
print(f"add_messages result: {len(result['messages'])} message(s), final content = {result['messages'][0].content!r}")

def merge_max_duration(existing: dict, new: dict) -> dict:
    merged = dict(existing)
    for stage, seconds in new.items():
        merged[stage] = max(merged.get(stage, 0.0), seconds)
    return merged

class PipelineState(TypedDict):
    stage_durations: Annotated[dict, merge_max_duration]

def parse_node(state):
    return {"stage_durations": {"parse": 1.2}}

def parse_retry_node(state):
    return {"stage_durations": {"parse": 3.4}}

g2 = StateGraph(PipelineState)
g2.add_node("parse", parse_node)
g2.add_node("parse_retry", parse_retry_node)
g2.add_edge(START, "parse")
g2.add_edge("parse", "parse_retry")
g2.add_edge("parse_retry", END)
graph2 = g2.compile()
result2 = graph2.invoke({"stage_durations": {}})
print(f"custom reducer kept the slower retry duration: {result2['stage_durations']['parse'] == 3.4}")

Concept 3 — Keeping Large Documents Out of State


Every LangGraph state value gets copied into a checkpoint on every superstep once a
checkpointer is attached (Day 2), and streamed back out of .invoke()/.stream() on
every call regardless. A state field holding a full parsed policy document's text pays
that cost on every single step of the graph, for a value most nodes never read — the same
"pass object keys through XCom, never payloads" principle Week 12 established for Airflow
applies here just as directly: state should carry a reference (an S3 key, a document ID) a
node can dereference when it actually needs the content, not the content itself.


Example:


import sys

policy_text = ("This policy covers named perils including fire, theft, and water damage. " * 400)

doc_ref_state = {"doc_ref": "s3://claims-bucket/policies/POL-88213.pdf"}
doc_blob_state = {"doc_blob": policy_text}

ref_bytes = sys.getsizeof(doc_ref_state["doc_ref"])
blob_bytes = sys.getsizeof(doc_blob_state["doc_blob"])
print(f"reference bytes: {ref_bytes}")
print(f"full-text blob bytes: {blob_bytes}")
print(f"reference is smaller by a factor of: {round(blob_bytes / ref_bytes, 1)}")

The exact factor depends on document length and is not the point to memorize — the point

Concept 4 — Assembling a StateGraph With add_conditional_edges


START and END are LangGraph's fixed entry and exit sentinels — every graph's edges
must eventually route from START to END. add_conditional_edges(source, router_fn, path_map) is how a graph branches: router_fn receives the current state and returns a
key from path_map, and only that one branch's node runs next — this is genuine
conditional routing, not every branch executing and being filtered afterward.


Example:


from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class UnderwritingState(TypedDict):
    risk_score: float
    notes: Annotated[list[str], operator.add]

def score_node(state):
    return {"notes": ["scored"]}

def auto_approve_node(state):
    return {"notes": ["auto-approved: below manual-review threshold"]}

def manual_review_node(state):
    return {"notes": ["routed to manual review: above threshold"]}

def route_by_risk(state):
    return "manual_review" if state["risk_score"] >= 0.5 else "auto_approve"

g = StateGraph(UnderwritingState)
g.add_node("score", score_node)
g.add_node("auto_approve", auto_approve_node)
g.add_node("manual_review", manual_review_node)
g.add_edge(START, "score")
g.add_conditional_edges("score", route_by_risk, {"auto_approve": "auto_approve", "manual_review": "manual_review"})
g.add_edge("auto_approve", END)
g.add_edge("manual_review", END)
graph = g.compile()

low = graph.invoke({"risk_score": 0.2, "notes": []})
high = graph.invoke({"risk_score": 0.8, "notes": []})
print(f"low risk notes: {low['notes']}")
print(f"high risk notes: {high['notes']}")

BFSI Reality Check — Day 1


Legacy angle: A graph's state schema is, in effect, a contract between every node
that touches it — the same kind of contract Week 01's dataclasses and Week 02's
Pydantic models formalized for plain function I/O. A BFSI team migrating a hand-rolled
if/elif claims-routing script onto StateGraph gets this contract for free, which is
often the actual value of the migration, independent of anything LangGraph does at
runtime.


Compliance angle: notes accumulating via operator.add rather than being
overwritten is itself an audit property — the state at END carries the full sequence of
what every node decided, not just the last node's opinion, which is exactly the kind of
trail Week 17's Article 12 record-keeping requirement expects a system to keep.


What breaks in production: A field that should accumulate (like notes) but ships
with no Annotated reducer silently and quietly loses every earlier node's contribution
the moment two nodes both write to it — LangGraph raises no error for this, since a
missing reducer just means "overwrite," a perfectly valid default for plenty of other
fields. Reviewing every state field's reducer choice explicitly, rather than accepting
the default for fields that clearly need one, is a real code-review item this week's
Concept 1 exists to justify.

Concept 1 — PostgresSaver for Production Versus InMemorySaver for Tests


A checkpointer is what turns a StateGraph from a stateless function call into a durably
resumable run: graph.compile(checkpointer=...) writes the state after every superstep,
keyed by the thread_id passed in config["configurable"]. InMemorySaver keeps every
checkpoint in a plain Python dict living on the checkpointer object itself — genuinely
useful for tests, since no setup is needed, but its durability is exactly as long as that
object stays alive; nothing survives the process ending. PostgresSaver.from_conn_string
and its required one-time .setup() call (which creates the checkpoint tables) are this
sandbox's REAL MODE exception this week, needing a live PostgreSQL server — the correct,
checked call shape is with PostgresSaver.from_conn_string(DB_URI) as checkpointer: checkpointer.setup().


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from typing import TypedDict

class State(TypedDict):
    step_log: list

def step1(state):
    return {"step_log": state["step_log"] + ["step1"]}

def step2(state):
    return {"step_log": state["step_log"] + ["step2"]}

g = StateGraph(State)
g.add_node("step1", step1)
g.add_node("step2", step2)
g.add_edge(START, "step1")
g.add_edge("step1", "step2")
g.add_edge("step2", END)

checkpointer_a = InMemorySaver()
graph_a = g.compile(checkpointer=checkpointer_a)
config = {"configurable": {"thread_id": "claim-mem-1"}}
graph_a.invoke({"step_log": []}, config=config)
print(f"state while checkpointer_a is still alive: {graph_a.get_state(config).values}")

# A fresh InMemorySaver stands in for the process actually restarting -- it has never
# heard of this thread_id, because nothing about it was ever written to disk.
checkpointer_b = InMemorySaver()
graph_b = g.compile(checkpointer=checkpointer_b)
state_b = graph_b.get_state(config)
print(f"same thread_id against a brand-new InMemorySaver: {state_b.values}")
print(f"history is completely empty after the simulated restart: {len(list(graph_b.get_state_history(config))) == 0}")

# REAL MODE -- not executed (needs a live PostgreSQL server this sandbox does not have):
#   from langgraph.checkpoint.postgres import PostgresSaver

Concept 2 — thread_id and checkpoint_id in the configurable Config


config["configurable"]["thread_id"] is the only field required to checkpoint a run; the
same dict can also carry checkpoint_id to address one SPECIFIC past checkpoint rather
than "whatever the thread's latest one is." langgraph-checkpoint-sqlite's SqliteSaver
installs and runs genuinely in this sandbox — an on-disk file, not an in-memory dict — and
is used for the rest of this day as a real, durable stand-in for the same BaseCheckpointSaver
interface PostgresSaver implements, so every claim this day makes about durability is
demonstrated against a real file surviving a real Python-process restart, not asserted.
checkpoint_id values themselves are real UUIDs generated fresh on every run (LangGraph
uses a time-ordered UUID7, so successive ids from one run even share a common leading
prefix) — the Example below never presents one as a fixed value, only compares them for
uniqueness and count, which are genuinely stable across runs.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.sqlite import SqliteSaver
from typing import TypedDict
import sqlite3
import os

class State(TypedDict):
    step_log: list

def step1(state):
    return {"step_log": state["step_log"] + ["step1"]}

def step2(state):
    return {"step_log": state["step_log"] + ["step2"]}

def step3(state):
    return {"step_log": state["step_log"] + ["step3"]}

g = StateGraph(State)
g.add_node("step1", step1)
g.add_node("step2", step2)
g.add_node("step3", step3)
g.add_edge(START, "step1")
g.add_edge("step1", "step2")
g.add_edge("step2", "step3")
g.add_edge("step3", END)

if os.path.exists("checkpoints.db"):
    os.remove("checkpoints.db")
conn = sqlite3.connect("checkpoints.db", check_same_thread=False)
checkpointer = SqliteSaver(conn)
checkpointer.setup()
graph = g.compile(checkpointer=checkpointer)
config = {"configurable": {"thread_id": "claim-history-1"}}
graph.invoke({"step_log": []}, config=config)

history = list(graph.get_state_history(config))
ids = [h.config["configurable"]["checkpoint_id"] for h in history]
print(f"checkpoints recorded: {len(history)}")
print(f"every checkpoint_id is unique: {len(set(ids)) == len(ids)}")
print(f"step_log at each checkpoint, newest first: {[h.values.get('step_log') for h in history]}")

Concept 3 — get_state()/get_state_history() for Replay and Time Travel


Passing a specific checkpoint's config (the one returned alongside it in
get_state_history(), carrying that checkpoint's own checkpoint_id) back into
graph.invoke(None, config=that_checkpoint_config) does not merely READ that old state —
it resumes EXECUTION from it, re-running every node still pending at that point forward.
This is real time travel: replaying a run "as if" it had continued from an earlier point,
without touching the two steps that already ran before it.


Example:


history = list(graph.get_state_history(config))
after_step2 = history[1]  # newest-first: [after step3, after step2, after step1, empty, pre-start]
print(f"checkpoint chosen for the fork has step_log: {after_step2.values}")

result = graph.invoke(None, config=after_step2.config)
print(f"result replaying forward from after step2: {result}")
print(f"step3 ran again with no duplicate step1/step2: {result['step_log'] == ['step1', 'step2', 'step3']}")

Concept 4 — What a Mid-Run Crash Actually Costs, By Durability Setting


Combining a checkpointer that raises inside a node with two different backing stores
proves, rather than argues, what each setting actually costs when a crash happens
mid-run: with InMemorySaver, a real process restart (a brand-new checkpointer object)
loses every checkpoint written to the dead one, including the one step that DID complete
before the crash; with a genuinely on-disk store like SqliteSaver, reopening the same
file after the same kind of restart recovers exactly the progress made before the crash,
and resuming completes the run without re-running the step that already succeeded.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.sqlite import SqliteSaver
from typing import TypedDict
import sqlite3
import os

class State(TypedDict):
    step_log: list

call_count = {"mem": 0, "sqlite": 0}

def step1(state):
    return {"step_log": state["step_log"] + ["step1"]}

def make_flaky_step2(counter_key):
    def flaky(state):
        call_count[counter_key] += 1
        if call_count[counter_key] == 1:
            raise RuntimeError("simulated crash")
        return {"step_log": state["step_log"] + ["step2"]}
    return flaky

config = {"configurable": {"thread_id": "claim-x"}}

# InMemorySaver side
g_mem = StateGraph(State)
g_mem.add_node("step1", step1)
g_mem.add_node("step2", make_flaky_step2("mem"))
g_mem.add_edge(START, "step1")
g_mem.add_edge("step1", "step2")
g_mem.add_edge("step2", END)
mem_graph = g_mem.compile(checkpointer=InMemorySaver())
try:
    mem_graph.invoke({"step_log": []}, config=config)
except RuntimeError:
    pass

# a real process restart: a brand-new InMemorySaver object
mem_graph_after_restart = g_mem.compile(checkpointer=InMemorySaver())
print(f"InMemorySaver after a real process restart: {mem_graph_after_restart.get_state(config).values}")

# SqliteSaver side
if os.path.exists("crash_test.db"):
    os.remove("crash_test.db")
conn = sqlite3.connect("crash_test.db", check_same_thread=False)
sqlite_checkpointer = SqliteSaver(conn)
sqlite_checkpointer.setup()
g_sqlite = StateGraph(State)
g_sqlite.add_node("step1", step1)
g_sqlite.add_node("step2", make_flaky_step2("sqlite"))
g_sqlite.add_edge(START, "step1")
g_sqlite.add_edge("step1", "step2")
g_sqlite.add_edge("step2", END)
sqlite_graph = g_sqlite.compile(checkpointer=sqlite_checkpointer)
try:
    sqlite_graph.invoke({"step_log": []}, config=config)
except RuntimeError:
    pass
conn.close()

# reopen from the same file -- simulating the real process restart
conn2 = sqlite3.connect("crash_test.db", check_same_thread=False)
sqlite_graph_after_restart = g_sqlite.compile(checkpointer=SqliteSaver(conn2))
print(f"SqliteSaver after a real process restart (reopened from file): {sqlite_graph_after_restart.get_state(config).values}")
result = sqlite_graph_after_restart.invoke(None, config=config)
print(f"SqliteSaver resumes and completes without re-running step1: {result}")

BFSI Reality Check — Day 2


Legacy angle: A BFSI shop already running PostgreSQL for its transactional core has an
obvious, low-friction home for PostgresSaver — no new database technology to get
approved, just new tables in an existing one. That is a real adoption argument distinct
from LangGraph's own feature set.


Compliance angle: get_state_history()'s full checkpoint trail is, again, a Week 17
Article 12 record-keeping asset for free: every intermediate state a claim's processing
run passed through is independently queryable, not just the final outcome.


What breaks in production: A team ships with InMemorySaver past its test/demo stage
because "it worked in every test we ran" — and every one of those tests ran inside a
single, uninterrupted process, the one condition under which InMemorySaver genuinely
looks indistinguishable from a durable store. The very first real deploy restart (a
routine one, not even a crash) silently drops every in-flight run's progress, and nothing
in InMemorySaver's own behavior warns that this is coming — Concept 4's side-by-side
comparison is the check that catches it before a production incident does.

Concept 1 — Bounded Retries and Backoff With RetryPolicy


Attaching retry_policy=RetryPolicy(...) to add_node() makes LangGraph itself catch an
exception a node raises, wait according to initial_interval/backoff_factor/
max_interval, and re-invoke the SAME node — up to max_attempts times — before giving
up. retry_on restricts which exception types actually trigger a retry at all; anything
else propagates immediately, which Concept 3 below relies on directly.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import RetryPolicy
from typing import TypedDict

class State(TypedDict):
    attempts: int

class TransientError(Exception):
    pass

attempt_counter = {"n": 0}

def flaky_node(state):
    attempt_counter["n"] += 1
    if attempt_counter["n"] < 3:
        raise TransientError("upstream service timeout")
    return {"attempts": attempt_counter["n"]}

g = StateGraph(State)
g.add_node("flaky", flaky_node, retry_policy=RetryPolicy(
    max_attempts=5,
    initial_interval=0.01,
    backoff_factor=2.0,
    retry_on=(TransientError,),
))
g.add_edge(START, "flaky")
g.add_edge("flaky", END)
graph = g.compile()

result = graph.invoke({"attempts": 0})
print(f"result: {result}")
print(f"succeeded within max_attempts: {result['attempts'] == 3}")

Concept 2 — Idempotent Tool Nodes: a Retry Must Never Double-Post


RetryPolicy re-invoking a node after a transient failure is only safe if the node itself
is idempotent — the real risk Concept 1 glosses over is that the FIRST attempt might have
actually succeeded on the far side (a payment gateway that processed the charge before
timing out on the response), and a naive retry then posts it a second time. An
idempotency key checked and recorded BEFORE any side-effecting action genuinely executes
is what makes a retry safe: the second call for the same key returns the already-known
result instead of repeating the side effect.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import RetryPolicy
from typing import TypedDict

class State(TypedDict):
    idempotency_key: str
    payment_posted: bool

processed_keys = set()
post_call_count = {"n": 0}

class TransientError(Exception):
    pass

def post_payment_idempotent(state):
    key = state["idempotency_key"]
    if key in processed_keys:
        return {"payment_posted": True}
    post_call_count["n"] += 1
    if post_call_count["n"] == 1:
        raise TransientError("gateway timeout -- payment may or may not have posted")
    processed_keys.add(key)
    return {"payment_posted": True}

g = StateGraph(State)
g.add_node("pay", post_payment_idempotent, retry_policy=RetryPolicy(max_attempts=3, initial_interval=0.01, retry_on=(TransientError,)))
g.add_edge(START, "pay")
g.add_edge("pay", END)
graph = g.compile()

result = graph.invoke({"idempotency_key": "CLM-1001-refund", "payment_posted": False})
print(f"result: {result}")
print(f"post_payment was called exactly twice (one failure, one real success): {post_call_count['n'] == 2}")

# A second, independent invoke with the SAME key -- simulating LangGraph re-entering this
# node after some later, unrelated crash downstream -- must not post the payment again.
result2 = graph.invoke({"idempotency_key": "CLM-1001-refund", "payment_posted": False})
print(f"second invoke with the same key did not call the real posting logic again: {post_call_count['n'] == 2}")

Concept 3 — Retryable Transport Errors Versus Terminal Validation Errors


retry_on is not just a performance knob — it is the mechanism that keeps a permanently
broken input from being retried five times for no reason. A malformed claim ID or a
negative claim amount will fail identically on attempt 1 and attempt 5; retrying it wastes
the retry budget and delays the terminal failure a caller needed to see immediately. The
fix is naming the actually-transient exception types (a timeout, a 503, a connection
reset) in retry_on and letting everything else — a validation error the caller needs to
fix, not wait out — propagate on the very first attempt.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import RetryPolicy
from typing import TypedDict

class State(TypedDict):
    attempts: int

class TransientError(Exception):
    pass

class ValidationError(Exception):
    pass

attempt_counter = {"n": 0}

def validation_node(state):
    attempt_counter["n"] += 1
    raise ValidationError("claim_amount must be positive")

g = StateGraph(State)
g.add_node("validate", validation_node, retry_policy=RetryPolicy(max_attempts=5, retry_on=(TransientError,)))
g.add_edge(START, "validate")
g.add_edge("validate", END)
graph = g.compile()

try:
    graph.invoke({"attempts": 0})
except ValidationError as e:
    print(f"ValidationError raised immediately (not retried): {e}")
print(f"validate node was called exactly once, not retried: {attempt_counter['n'] == 1}")

Concept 4 — Compensation Branches and Dead-Letter Routing


A crucial gotcha RetryPolicy does not solve: once max_attempts is exhausted, the
exception propagates all the way out of graph.invoke() and ends the ENTIRE run, not just
that one node's branch — there is no built-in "on retry exhaustion, route to node X" hook.
Routing a permanently-failed operation to a compensation or dead-letter path instead of
crashing the whole run means the node itself must catch its own terminal failure and
record it in state as data, then add_conditional_edges branches on that recorded status
— the same pattern Day 1 Concept 4 used for risk-tier routing, applied to failure
handling instead of a business decision.


Example:


from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
import operator

class State(TypedDict):
    claim_id: str
    payment_status: str
    notes: Annotated[list[str], operator.add]

class PermanentError(Exception):
    pass

def post_payment(state):
    try:
        raise PermanentError("claim CLM-9001 was already refunded -- duplicate payment request")
    except PermanentError as e:
        return {"payment_status": "failed", "notes": [f"payment failed permanently: {e}"]}

def confirm_node(state):
    return {"notes": ["payment confirmed"]}

def compensate_node(state):
    return {"notes": ["compensation: reversed any partial hold, notified claims adjuster"]}

def dead_letter_node(state):
    return {"notes": ["routed to dead-letter queue for manual reconciliation"]}

def route_on_payment(state):
    return "confirm" if state["payment_status"] == "succeeded" else "compensate"

g = StateGraph(State)
g.add_node("post_payment", post_payment)
g.add_node("confirm", confirm_node)
g.add_node("compensate", compensate_node)
g.add_node("dead_letter", dead_letter_node)
g.add_edge(START, "post_payment")
g.add_conditional_edges("post_payment", route_on_payment, {"confirm": "confirm", "compensate": "compensate"})
g.add_edge("confirm", END)
g.add_edge("compensate", "dead_letter")
g.add_edge("dead_letter", END)
graph = g.compile()

result = graph.invoke({"claim_id": "CLM-9001", "payment_status": "pending", "notes": []})
print(f"notes: {result['notes']}")

Legacy angle: A payment or claims-posting call into a core system that itself has no

Concept 1 — Pausing Mid-Graph With interrupt() and Command(resume=...)


interrupt(payload) called inside a node genuinely PAUSES the run at that exact point —
graph.invoke() returns immediately with an __interrupt__ key carrying payload, and
graph.get_state(config).next shows the paused node still pending. Nothing resumes it
until a separate graph.invoke(Command(resume=decision), config=config) call supplies
decision, which becomes interrupt()'s own return value back inside the node — the node
picks up exactly where it left off, not from the top of the graph.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver
from typing import TypedDict

class State(TypedDict):
    claim_amount: float
    approved: bool

def intake_node(state):
    return {}

def approval_node(state):
    decision = interrupt({"question": "approve this high-value claim?", "claim_amount": state["claim_amount"]})
    return {"approved": decision}

def pay_node(state):
    return {}

g = StateGraph(State)
g.add_node("intake", intake_node)
g.add_node("approval", approval_node)
g.add_node("pay", pay_node)
g.add_edge(START, "intake")
g.add_edge("intake", "approval")
g.add_edge("approval", "pay")
g.add_edge("pay", END)
graph = g.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "claim-approval-1"}}

result = graph.invoke({"claim_amount": 75000.0, "approved": False}, config=config)
print(f"graph paused, interrupt payload: {result['__interrupt__'][0].value}")
print(f"next node still pending: {graph.get_state(config).next}")

resumed = graph.invoke(Command(resume=True), config=config)
print(f"after human approval: {resumed}")

Concept 2 — An Approval Queue Backed by the Checkpointer, Not In-Process State


A team's first instinct is often a separate in-process list of "claims waiting for
approval" — but that list is exactly as durable as InMemorySaver was in Day 2: it
vanishes on restart. The checkpointer ALREADY IS the approval queue: any thread whose
get_state(config).next is non-empty is, by definition, paused waiting on something, and
scanning a known set of thread_ids for that condition needs no separate queue data
structure at all. Built on SqliteSaver (Day 2's genuinely-executable durable stand-in),
this queue survives exactly the kind of process restart an in-process list would not.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.sqlite import SqliteSaver
from typing import TypedDict
import sqlite3
import os

class State(TypedDict):
    claim_id: str
    claim_amount: float
    approved: bool

def approval_node(state):
    decision = interrupt({"claim_id": state["claim_id"], "claim_amount": state["claim_amount"]})
    return {"approved": decision}

g = StateGraph(State)
g.add_node("approval", approval_node)
g.add_edge(START, "approval")
g.add_edge("approval", END)

if os.path.exists("approval_queue.db"):
    os.remove("approval_queue.db")
conn = sqlite3.connect("approval_queue.db", check_same_thread=False)
checkpointer = SqliteSaver(conn)
checkpointer.setup()
graph = g.compile(checkpointer=checkpointer)

claims = [("CLM-1001", 30000.0), ("CLM-1002", 90000.0), ("CLM-1003", 15000.0)]
for claim_id, amount in claims:
    config = {"configurable": {"thread_id": claim_id}}
    graph.invoke({"claim_id": claim_id, "claim_amount": amount, "approved": False}, config=config)

# approve one of the three, leaving the other two pending
graph.invoke(Command(resume=True), config={"configurable": {"thread_id": "CLM-1002"}})

def list_pending_approvals(graph, thread_ids):
    return [tid for tid in thread_ids if graph.get_state({"configurable": {"thread_id": tid}}).next]

pending = list_pending_approvals(graph, [c[0] for c in claims])
print(f"pending approvals: {sorted(pending)}")

Concept 3 — Wiring the Pause to Week 17's Article 14 Oversight Requirement


interrupt() pausing a graph is a mechanism; Week 17 Day 5's execute_high_stakes_action/
ApprovalRequiredError hard gate (genuinely reused here unchanged) is the actual Article
14(4) enforcement — the intervene-or-stop measure that must reject a high-stakes action
outright when no real approval was given, not merely display an approval button a bug
could leave disconnected. Combining them means the interrupt payload asks for a real
approval TOKEN (who approved, not just yes/no), and the same hard gate from Week 17 still
runs after resume, enforcing the requirement even at this layer.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver
from typing import TypedDict

class ApprovalRequiredError(Exception):
    pass

def execute_high_stakes_action(action_name, approval_token):
    if not approval_token:
        raise ApprovalRequiredError(f"'{action_name}' requires an explicit human approval token before executing")
    return f"executed: {action_name} (approved by {approval_token})"

class State(TypedDict):
    claim_id: str
    action_result: str

def deny_claim_node(state):
    approval_token = interrupt({
        "action_name": "deny_life_insurance_claim",
        "claim_id": state["claim_id"],

    })
    result = execute_high_stakes_action("deny_life_insurance_claim", approval_token)
    return {"action_result": result}

g = StateGraph(State)
g.add_node("deny_claim", deny_claim_node)
g.add_edge(START, "deny_claim")
g.add_edge("deny_claim", END)
graph = g.compile(checkpointer=InMemorySaver())

config_a = {"configurable": {"thread_id": "claim-deny-1"}}
graph.invoke({"claim_id": "CLM-7001", "action_result": ""}, config=config_a)
resumed = graph.invoke(Command(resume="claims_manager_avaz"), config=config_a)

Concept 4 — Expiry and Escalation When Nobody Approves Inside the SLA


A pause with no automatic timeout is a pause that can wait forever — a real approval
workflow needs an SLA and an escalation path for when a human simply never responds. The
SLA check itself is a pure, independently-testable function; wiring it in means the node
that resumes execution treats a LATE response as an automatic escalation rather than
honoring a stale decision, regardless of what that decision actually was.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver
from typing import TypedDict
import datetime

def sla_status(submitted_at, as_of, sla_hours=4):
    elapsed_hours = (as_of - submitted_at).total_seconds() / 3600
    return "expired" if elapsed_hours > sla_hours else "within_sla"

class State(TypedDict):
    claim_id: str
    submitted_at: object
    outcome: str

def approval_node(state):
    response = interrupt({"claim_id": state["claim_id"], "submitted_at": state["submitted_at"].isoformat()})
    status = sla_status(state["submitted_at"], response["responded_at"])
    if status == "expired":
        return {"outcome": "escalated_to_senior_underwriter"}
    return {"outcome": response["decision"]}

g = StateGraph(State)
g.add_node("approval", approval_node)
g.add_edge(START, "approval")
g.add_edge("approval", END)
graph = g.compile(checkpointer=InMemorySaver())

submitted = datetime.datetime(2026, 9, 17, 9, 0)

config_a = {"configurable": {"thread_id": "claim-sla-1"}}
graph.invoke({"claim_id": "CLM-8001", "submitted_at": submitted, "outcome": ""}, config=config_a)
result_a = graph.invoke(Command(resume={"decision": "approved", "responded_at": datetime.datetime(2026, 9, 17, 11, 0)}), config=config_a)
print(f"responded within SLA: {result_a['outcome']}")

config_b = {"configurable": {"thread_id": "claim-sla-2"}}
graph.invoke({"claim_id": "CLM-8002", "submitted_at": submitted, "outcome": ""}, config=config_b)
result_b = graph.invoke(Command(resume={"decision": "approved", "responded_at": datetime.datetime(2026, 9, 17, 14, 0)}), config=config_b)
print(f"responded after SLA lapsed (decision overridden): {result_b['outcome']}")

Concept 1 — Send for Map-Reduce Fan-Out Across Many Documents


add_conditional_edges(START, router_fn, [target_node]) where router_fn returns a LIST
of Send(node_name, payload) objects, rather than a single routing key, fans a single
run out into one independent invocation of node_name per Send — this is genuine
map-reduce: each fan-out branch gets its own state slice (payload), runs independently,
and their Annotated reducer-merged fields (Day 1 Concept 1) combine the results back
into one parent state once every branch completes.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.types import Send
from typing import TypedDict, Annotated
import operator

class ParentState(TypedDict):
    doc_ids: list
    extracted_fields: Annotated[list, operator.add]

def fan_out(state):
    return [Send("extract_doc", {"doc_id": d, "extracted_fields": []}) for d in state["doc_ids"]]

def extract_doc(state):
    return {"extracted_fields": [f"{state['doc_id']}: policy_number=POL-{state['doc_id'][-4:]}"]}

g = StateGraph(ParentState)
g.add_node("extract_doc", extract_doc)

Concept 2 — Subgraphs With Their Own State and Checkpoint Namespaces


A compiled StateGraph can be added as a node directly inside another StateGraph —
LangGraph treats it as a subgraph, running it to completion as one step of the parent.
Its checkpoints are NOT mixed into the parent's own checkpoint stream: they live under a
distinct checkpoint_ns (namespace) string prefixed with the subgraph node's name, so a
parent thread's history and a subgraph's internal step-by-step history stay independently
queryable rather than interleaved into one undifferentiated log.


Example:


from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from typing import TypedDict

class SubState(TypedDict):
    doc_id: str
    parsed: bool
    chunked: bool

def parse_node(state):
    return {"parsed": True}

def chunk_node(state):
    return {"chunked": True}

sub = StateGraph(SubState)
sub.add_node("parse", parse_node)
sub.add_node("chunk", chunk_node)
sub.add_edge(START, "parse")
sub.add_edge("parse", "chunk")
sub.add_edge("chunk", END)
subgraph = sub.compile()

class ParentState(TypedDict):
    doc_id: str
    parsed: bool
    chunked: bool
    embedded: bool

def embed_node(state):
    return {"embedded": True}

parent = StateGraph(ParentState)
parent.add_node("dataprep", subgraph)
parent.add_node("embed", embed_node)
parent.add_edge(START, "dataprep")
parent.add_edge("dataprep", "embed")
parent.add_edge("embed", END)
checkpointer = InMemorySaver()
graph = parent.compile(checkpointer=checkpointer)
config = {"configurable": {"thread_id": "claim-subgraph-1"}}

result = graph.invoke({"doc_id": "CLM-1001", "parsed": False, "chunked": False, "embedded": False}, config=config)
print(f"result: {result}")

checkpoints = list(checkpointer.list(config))
namespaces = set(c.config["configurable"].get("checkpoint_ns", "") for c in checkpoints)
print(f"root namespace present: {'' in namespaces}")
print(f"a distinct subgraph namespace under dataprep exists: {any(ns.startswith('dataprep:') for ns in namespaces)}")

Expected output (actually run):

Concept 3 — Streaming Modes values, updates, and messages


graph.stream(input, stream_mode=...) reports progress differently depending on the
mode: "values" yields the FULL accumulated state after every superstep (useful for a UI
showing current status); "updates" yields only the PARTIAL dict each node itself
returned, keyed by node name (useful for an audit log of who changed what); "messages"
streams individual LLM tokens as they're generated inside a node — and, checked directly,
yields NOTHING for a graph with no actual chat-model call inside any node, since it is
purely a callback hook into token generation, not a general node-progress channel.


Example:


from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
import operator

class State(TypedDict):
    notes: Annotated[list[str], operator.add]

def parse_node(state):
    return {"notes": ["parsed"]}

def chunk_node(state):
    return {"notes": ["chunked"]}

def embed_node(state):
    return {"notes": ["embedded"]}

g = StateGraph(State)
g.add_node("parse", parse_node)
g.add_node("chunk", chunk_node)
g.add_node("embed", embed_node)
g.add_edge(START, "parse")
g.add_edge("parse", "chunk")
g.add_edge("chunk", "embed")
g.add_edge("embed", END)
graph = g.compile()

values_chunks = list(graph.stream({"notes": []}, stream_mode="values"))
print(f"values mode yields the full state after each step: {[c['notes'] for c in values_chunks]}")

updates_chunks = list(graph.stream({"notes": []}, stream_mode="updates"))
print(f"updates mode yields only each node's own partial return: {updates_chunks}")

messages_chunks = list(graph.stream({"notes": []}, stream_mode="messages"))
print(f"messages mode with no LLM calls in any node yields nothing: {messages_chunks == []}")

Concept 4 — Per-Node Latency Spans and langgraph.json Deployment Configuration


stream_mode="debug" emits a "task" event when a node starts and a matching
"task_result" event when it finishes, each carrying a real ISO timestamp — diffing the
two for a given node's task id genuinely measures that node's wall-clock latency, no
external tracing library required. Per-call TOKEN spans need an actual LLM call inside a
node (REAL MODE here, since no live model is called this week), but the latency mechanism
itself needs nothing beyond stream_mode="debug". langgraph.json ({"dependencies": [...], "graphs": {"agent": "./agent.py:graph"}, "env": ".env"}) is the deployment manifest
LangGraph Platform/langgraph dev reads to find and serve a compiled graph — a
configuration file, not a runtime call, so it is shown here as reference shape rather than
executed.


Example:


from langgraph.graph import StateGraph, START, END
from typing import TypedDict
import time
import datetime

class State(TypedDict):
    notes: list

def slow_node(state):
    time.sleep(0.05)
    return {"notes": ["slow done"]}

def fast_node(state):
    return {"notes": ["fast done"]}

g = StateGraph(State)
g.add_node("slow", slow_node)
g.add_node("fast", fast_node)
g.add_edge(START, "slow")
g.add_edge("slow", "fast")
g.add_edge("fast", END)
graph = g.compile()

starts = {}
durations = {}
for chunk in graph.stream({"notes": []}, stream_mode="debug"):
    name = chunk["payload"]["name"]
    if chunk["type"] == "task":
        starts[chunk["payload"]["id"]] = chunk["timestamp"]
    elif chunk["type"] == "task_result":
        t0 = datetime.datetime.fromisoformat(starts[chunk["payload"]["id"]])
        t1 = datetime.datetime.fromisoformat(chunk["timestamp"])
        durations[name] = (t1 - t0).total_seconds()

print(f"slow node measured slower than fast node: {durations['slow'] > durations['fast']}")
print(f"slow node took at least 0.04s (slept 0.05s): {durations['slow'] >= 0.04}")

# langgraph.json -- reference shape only, read by `langgraph dev`/LangGraph Platform, not executed here:
#   {
#     "dependencies": ["."],
#     "graphs": {"claims_pipeline": "./claims_graph.py:graph"},
#     "env": ".env"
#   }

Expected output (actually run):

Concept 5 — Supervisor Routing Across Specialist Subgraphs


Adapted from Curriculum/Week_11_Advanced_AI/W11_D1d_MultiAgent_Orchestration.ipynb's
"Real LangGraph Subgraphs" and "Agent Handoff via Conditional Edges" concepts, re-grounded
in claims data rather than that notebook's SQL/report-agent example: a compiled subgraph
(Concept 2) can be added as a node under add_conditional_edges(START, router_fn, [node_names]) exactly like a plain function node, so a supervisor's routing decision and
Concept 2's namespace-isolated subgraphs compose directly — each route target is itself a
fully independent, standalone-testable pipeline, not just a branch of logic living inside
one big function.


Example:


from langgraph.graph import StateGraph, START, END
from typing import TypedDict

class FraudReviewState(TypedDict):
    claim_id: str
    amount: float
    result: str

def flag_for_investigator(state: FraudReviewState) -> FraudReviewState:
    return {"result": f"claim {state['claim_id']} routed to SIU investigator (amount {state['amount']})"}

fraud_builder = StateGraph(FraudReviewState)
fraud_builder.add_node("flag", flag_for_investigator)
fraud_builder.add_edge(START, "flag")
fraud_builder.add_edge("flag", END)
fraud_subgraph = fraud_builder.compile()   # standalone-testable, same as Concept 2

print("fraud subgraph tested standalone:", fraud_subgraph.invoke({"claim_id": "CLM-9001", "amount": 48000.0, "result": ""}))

class StandardState(TypedDict):
    claim_id: str
    amount: float
    result: str

def auto_settle(state: StandardState) -> StandardState:
    return {"result": f"claim {state['claim_id']} auto-settled for {state['amount']}"}

standard_builder = StateGraph(StandardState)
standard_builder.add_node("settle", auto_settle)
standard_builder.add_edge(START, "settle")
standard_builder.add_edge("settle", END)
standard_subgraph = standard_builder.compile()

class SupervisorState(TypedDict):
    claim_id: str
    amount: float
    flagged: bool
    result: str

def route_claim(state: SupervisorState) -> str:
    if state["flagged"] or state["amount"] > 25000:
        return "fraud_review"
    return "standard_processing"

parent = StateGraph(SupervisorState)
parent.add_node("fraud_review", fraud_subgraph)
parent.add_node("standard_processing", standard_subgraph)
parent.add_conditional_edges(START, route_claim, ["fraud_review", "standard_processing"])
parent.add_edge("fraud_review", END)
parent.add_edge("standard_processing", END)
graph = parent.compile()

claims = [
    {"claim_id": "CLM-9001", "amount": 48000.0, "flagged": False, "result": ""},
    {"claim_id": "CLM-9002", "amount": 1200.0, "flagged": False, "result": ""},
    {"claim_id": "CLM-9003", "amount": 500.0, "flagged": True, "result": ""},
]
for c in claims:
    out = graph.invoke(c)
    print(out["result"])

routed_to_fraud = sum(1 for c in claims if c["flagged"] or c["amount"] > 25000)
print(f"claims routed to fraud review: {routed_to_fraud}")

BFSI Reality Check — Day 5


Legacy angle: Send's per-document fan-out maps directly onto Week 12's DataPrep DAG
task-per-document granularity — the same reasoning about retryability and observability
per unit of work applies whether the orchestrator is Airflow or a LangGraph StateGraph.


Compliance angle: Subgraph checkpoint namespaces (Concept 2) mean a dataprep
subprocess's own step-by-step history is independently auditable from the parent claims
pipeline's history — a regulator asking "what exactly happened during parsing" gets a
scoped answer, not the entire pipeline's undifferentiated checkpoint log to search
through.


What breaks in production: A team wires a progress UI to stream_mode="messages"
expecting per-node status updates, copying a pattern that works for a chat interface —
and gets nothing, because "messages" only fires for actual LLM token generation, not
general node progress. Concept 3's own direct check (messages_chunks == [] for a graph
with no LLM calls) is exactly the verification that would have caught this before it
shipped as a broken progress bar.




Architecture Decision — Week 19


Choosing between: a stateless straight-line script (what Phase 3's pipelines all
were) vs a StateGraph with checkpointing, retries, and human-approval interrupts vs a
fully custom orchestration layer built in-house.


Rule of thumb: adopt StateGraph with a durable checkpointer (PostgresSaver in
production, proven this week against SqliteSaver's genuinely-executable behavior) the
moment a pipeline has ANY of: a step that can legitimately fail and need a bounded retry
without re-running everything before it (Day 3); a decision point that must pause for a
human, with an SLA and an audit trail, rather than block a thread indefinitely (Day 4); or
enough independent units of work (many documents, many claims) that per-unit failure
isolation and fan-out parallelism (Day 5) matter more than one script's simplicity. A
pipeline with none of these — a short, linear, idempotent batch job with nothing to pause
for and nothing worth retrying independently — does not need this machinery, and adding it
anyway is pure overhead: InMemorySaver-style state and a plain function call are still
the right choice for that shape of work, exactly as Day 2 disclosed InMemorySaver's real
place is tests and short-lived scripts, not anything meant to survive a restart. A custom
in-house orchestration layer is worth building only once a team can point to a concrete
gap StateGraph's reducers, checkpointing, retry policies, and interrupt() genuinely do
not cover — not as a default starting position, since every one of those primitives this
week built from scratch already exists, tested, in the library itself.
