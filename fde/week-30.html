Concept 1 — A JSON Schema Contract for the Customer-Query Topic

An inbound customer query is free text typed by a person, but the envelope carrying it into the pipeline should not be. Every producer allowed to publish to customer-query-intake — the web chat widget, the mobile app, a phone-transcript batch job, an email parser — agrees to the same explicit contract before anything downstream (Day 2's retrieval, Day 3's guardrails) ever sees a record. jsonschema is the same library this track's earlier weeks used for contract validation; here the contract is the topic's own shape, not a model's output shape.

Example:

import jsonschema

CUSTOMER_QUERY_SCHEMA = {
    "type": "object",
    "required": ["query_id", "customer_id", "channel", "text", "submitted_at"],
    "properties": {
        "query_id": {"type": "string", "pattern": "^Q-[0-9A-F]{8}$"},
        "customer_id": {"type": "string", "pattern": "^CUST-[0-9]{6}$"},
        "channel": {"type": "string", "enum": ["web_chat", "mobile_app", "phone_transcript", "email"]},
        "text": {"type": "string", "minLength": 1, "maxLength": 2000},
        "submitted_at": {"type": "string", "format": "date-time"},
    },
    "additionalProperties": False,
}

def validate_query(record):
    try:
        jsonschema.validate(record, CUSTOMER_QUERY_SCHEMA,
                             format_checker=jsonschema.FormatChecker())
        return True, None
    except jsonschema.ValidationError as exc:
        return False, exc.message

good_record = {
    "query_id": "Q-1A2B3C4D", "customer_id": "CUST-004821", "channel": "web_chat",
    "text": "Why was my premium payment declined this month?",
    "submitted_at": "2026-09-19T14:02:11+00:00",
}
bad_record = {
    "query_id": "Q-1A2B3C4D", "customer_id": "4821", "channel": "carrier_pigeon",
    "text": "Why was my premium payment declined this month?",
    "submitted_at": "2026-09-19T14:02:11+00:00",
}

for label, record in (("good_record", good_record), ("bad_record", bad_record)):
    ok, error = validate_query(record)
    print(f"{label}: valid={ok}  error={error}")

Concept 2 — Commit After the Acknowledgement, Not Before


Reusing Week 06 Day 3 Concept 1's simulate(mode) structure verbatim, retargeted from a
claim-index upsert to a customer-query intake acknowledgement — the same "what does a
commit actually promise, and is it true yet" question, just a different unit of completed
work. enable.auto.commit=True commits on a timer based on what has been fetched, with
no knowledge of whether Day 1's own schema validation (and any downstream routing it
triggers) has actually finished for those records. A manual commit() called only after a
batch has genuinely been acknowledged can never commit past incomplete work.


Example:


FETCH_AHEAD = 8
ACK_EVERY_N_TICKS = 3
AUTO_COMMIT_EVERY = 10
MANUAL_COMMIT_BATCH = 5
TOTAL_RECORDS = 200
CRASH_AT_TICK = 31

def simulate(mode):
    fetch_cursor = -1
    ack_cursor = -1
    committed_offset = -1
    since_last_manual_commit = 0
    for tick in range(CRASH_AT_TICK):
        if fetch_cursor - ack_cursor < FETCH_AHEAD and fetch_cursor + 1 < TOTAL_RECORDS:
            fetch_cursor += 1
        if tick % ACK_EVERY_N_TICKS == 0 and ack_cursor < fetch_cursor:
            ack_cursor += 1
            since_last_manual_commit += 1
        if mode == "auto":
            if tick % AUTO_COMMIT_EVERY == 0:
                committed_offset = fetch_cursor
        elif mode == "manual":
            if since_last_manual_commit >= MANUAL_COMMIT_BATCH:
                committed_offset = ack_cursor
                since_last_manual_commit = 0
    return committed_offset, ack_cursor

for mode in ("auto", "manual"):
    committed_offset, ack_cursor = simulate(mode)
    resume_from = committed_offset + 1
    lost = max(0, committed_offset - ack_cursor)
    duplicates = max(0, ack_cursor - committed_offset)
    print(f"mode={mode:>6}  committed_offset={committed_offset:>3}  "
          f"actually_acked_through={ack_cursor:>3}  resume_from={resume_from:>3}  "
          f"lost_queries={lost:>2}  duplicate_replays_on_restart={duplicates:>2}")

Concept 3 — Dead-Letter Topic for Schema Violations, Not a Poison-Pill Stall


Reusing Week 06 Day 5 Concept 2's build_dlq_envelope shape verbatim, retargeted from an
embedding-API failure to a Concept 1 schema-contract violation caught at intake. A record
that fails validate_query is not something the consumer should retry in place — retrying
a malformed record against the same schema produces the same failure every time (Week 06
Day 5 Concept 3's terminal-error classification applies directly: a schema violation is
never transient). It is published to customer-query-dlq instead, with an envelope
carrying enough to find, fix, and later replay it.


Example:


import json, datetime, jsonschema

CUSTOMER_QUERY_SCHEMA = {
    "type": "object",
    "required": ["query_id", "customer_id", "channel", "text", "submitted_at"],
    "properties": {
        "query_id": {"type": "string", "pattern": "^Q-[0-9A-F]{8}$"},
        "customer_id": {"type": "string", "pattern": "^CUST-[0-9]{6}$"},
        "channel": {"type": "string", "enum": ["web_chat", "mobile_app", "phone_transcript", "email"]},
        "text": {"type": "string", "minLength": 1, "maxLength": 2000},
        "submitted_at": {"type": "string", "format": "date-time"},
    },
    "additionalProperties": False,
}

def build_dlq_envelope(original_message, error_message, first_seen_at):
    return {
        "original_topic": original_message["topic"],
        "original_partition": original_message["partition"],
        "original_offset": original_message["offset"],
        "original_key": original_message["key"],
        "original_timestamp": original_message["timestamp"],
        "propagated_headers": original_message["headers"],
        "error_type": "SchemaValidationError",
        "error_message": error_message,
        "attempt_count": 1,
        "first_seen_at": first_seen_at,
        "failed_at": datetime.datetime.now(datetime.timezone.utc).isoformat(),
    }

def route_customer_query(raw_value, original_message):
    try:
        jsonschema.validate(raw_value, CUSTOMER_QUERY_SCHEMA,
                             format_checker=jsonschema.FormatChecker())
        return "main_topic", raw_value, None
    except jsonschema.ValidationError as exc:
        envelope = build_dlq_envelope(
            original_message, exc.message,
            first_seen_at=original_message["timestamp"],
        )
        return "dead_letter_topic", None, envelope

Concept 4 — Offset Replay to Reconstruct an Incident Window


Reusing Week 06 Day 5 Concept 4's build_replay_plan verbatim, retargeted from a
re-embedding bug window to a customer-query incident window — Day 3's guardrail config
shipping a bad self-check prompt for two hours is exactly the kind of incident where every
query answered in that window needs to be identified and, once fixed, safely re-run.


Example:


def build_replay_plan(partition_offset_ranges, idempotent_downstream):
    plan = []
    total = 0
    for partition, (start, end) in partition_offset_ranges.items():
        count = end - start + 1
        total += count
        plan.append({"partition": partition, "seek_to_offset": start,
                     "replay_through_offset": end, "expected_record_count": count})
    precondition = (
        "safe: answers are keyed by query_id, so re-processing an already-answered "
        "query is a no-op" if idempotent_downstream else
        "UNSAFE: downstream answer storage is not idempotent -- replaying will duplicate transcripts"
    )
    return {"plan": plan, "total_expected_records": total,
            "safe_to_replay": idempotent_downstream, "precondition": precondition}

incident_window = {0: (550_100, 550_412), 1: (549_980, 550_301), 2: (550_050, 550_390)}
result = build_replay_plan(incident_window, idempotent_downstream=True)
for entry in result["plan"]:
    print(f"partition {entry['partition']}: seek to {entry['seek_to_offset']}, "
          f"replay through {entry['replay_through_offset']} "
          f"({entry['expected_record_count']} records)")
print(f"total expected records: {result['total_expected_records']}")
print(f"precondition: {result['precondition']}")

Concept 1 — Fixing Mojibake and Rejoining Hard Line Wraps


An on-prem Oracle CLOB export pulled with the wrong client NLS_LANG setting turns real
UTF-8 bytes (a right single quote, an en dash) into mojibake when re-decoded as
Windows-1252 — the single most common encoding defect this kind of extract carries, and a
fixed, checkable lookup table, not guesswork: each entry is the exact byte sequence a
genuine UTF-8-misread-as-cp1252 round trip produces for one specific character. Separately,
the same extract job wraps every line at a fixed column width with no sentence awareness —
a real paragraph break (blank line) has to survive, but a mid-sentence wrap has to be
rejoined with a single space, not a newline that silently splits one sentence into what a
downstream chunker would treat as two.


Example:


MOJIBAKE_FIXES = {
    "â\u0080\u0099": "’",   # right single quotation mark
    "â\u0080\u009c": "“",   # left double quotation mark
    "â\u0080\u009d": "”",   # right double quotation mark
    "â\u0080\u0093": "–",   # en dash
    "Ã©": "é",         # e-acute
}

def fix_mojibake(text):
    for bad, good in MOJIBAKE_FIXES.items():
        text = text.replace(bad, good)
    return text

def rejoin_hard_wraps(raw_text):
    paragraphs = raw_text.split("\n\n")
    joined = []
    for para in paragraphs:
        lines = [ln.strip() for ln in para.split("\n") if ln.strip()]
        joined.append(" ".join(lines))
    return "\n\n".join(joined)

def clean_clob_export(raw_text):
    return rejoin_hard_wraps(fix_mojibake(raw_text))

Concept 2 — Near-Duplicate Revisions Collapsed by Trigram-Shingle Similarity


Reusing Week 05 Day 2's trigrams() character-shingling tokenizer verbatim, here as
Jaccard similarity over trigram sets rather than Week 05's hashed-embedding cosine
stand-in for semantic search. The two jobs are genuinely different: semantic search has to
rank a paraphrase as relevant even with low character overlap (Week 05's whole point),
while near-dup collapse specifically wants to catch a revision that is almost
byte-for-byte the same text re-exported again — exactly what character-shingle overlap
measures directly. Real Oracle CLOB exports of a content-management table routinely carry
several rows per logical document, one per re-export or minor formatting touch-up, not one
row per genuine wording change.


Example:


def trigrams(text):
    t = "  " + text.lower() + "  "
    return [t[i:i + 3] for i in range(len(t) - 2)]

def jaccard(a, b):
    sa, sb = set(a), set(b)
    return len(sa & sb) / len(sa | sb) if (sa or sb) else 1.0

revisions = [
    {"doc_id": "FAQ-CLAIM-0091-r1", "effective_date": "2024-01-01",
     "text": "You can report a water damage claim within 30 days of the date of loss."},
    {"doc_id": "FAQ-CLAIM-0091-r2", "effective_date": "2024-06-15",
     "text": "You can report a water damage claim within 30 days of the date of loss!"},
    {"doc_id": "FAQ-CLAIM-0091-r3", "effective_date": "2026-03-01",
     "text": "Water damage claims must be reported within 14 days of the loss date, or coverage may be denied."},
]

def collapse_near_duplicates(revisions, threshold=0.90):
    grams = [trigrams(r["text"]) for r in revisions]
    kept = []
    collapsed_into = {}
    for i, r in enumerate(revisions):
        merged = False
        for j in kept:
            sim = jaccard(grams[i], grams[j])
            if sim >= threshold:
                collapsed_into[r["doc_id"]] = (revisions[j]["doc_id"], round(sim, 4))
                merged = True
                break
        if not merged:
            kept.append(i)
    return [revisions[i] for i in kept], collapsed_into

kept, collapsed_into = collapse_near_duplicates(revisions)
print(f"kept: {[r['doc_id'] for r in kept]}")
for doc_id, (into, sim) in collapsed_into.items():
    print(f"collapsed: {doc_id} -> {into}  (jaccard={sim})")

Once Concept 2 leaves one entry per genuine wording change, each still carries the
effective_date it was exported with. Retrieval must only ever surface the wording
actually in force as of a given as_of date — never a version superseded by a later
change, and never a future version that has not taken effect yet, however confidently it
reads.

Concept 4 — Parallel BM25 and Vector Indexes From the Same Cleaned Corpus


Reusing Week 05 Day 1's tokenize/idf/bm25_score and Day 2's trigrams/embed
verbatim, both built once from the same cleaned, deduped, in-force corpus Concepts 1-3
just produced. The two indexes disagree on tail ordering for the same query exactly the
way Week 05 Day 2 first measured for identifier-bearing text — the reason this pipeline
carries both indexes rather than picking one, with fusion left to Day 3's agent loop.


Example:


import re
import zlib
import numpy as np

def tokenize(text):
    return re.findall(r"[a-z0-9]+(?:-[a-z0-9]+)*", text.lower())

DIM = 32

def trigrams(text):
    t = "  " + text.lower() + "  "
    return [t[i:i + 3] for i in range(len(t) - 2)]

def embed(text, dim=DIM):
    vec = np.zeros(dim)
    for gram in trigrams(text):
        seed = zlib.crc32(gram.encode("utf-8"))
        rng = np.random.default_rng(seed)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

IN_FORCE_CORPUS = [
    {"doc_id": "FAQ-CLAIM-0091-r3", "text": "Report a water damage claim within 14 days of loss, or coverage may be denied."},
    {"doc_id": "FAQ-BILLING-0044-r1", "text": "Autopay can be cancelled any time before the next draft date."},
    {"doc_id": "FAQ-CLAIM-0102-r1", "text": "A theft claim needs a police report filed within 48 hours of discovery."},
    {"doc_id": "FAQ-POLICY-0077-r1", "text": "Policy POL-8842-C renews automatically unless cancelled 30 days before expiry."},
]

def build_bm25_index(corpus):
    tokens = [tokenize(d["text"]) for d in corpus]
    N = len(corpus)
    doc_lens = np.array([len(t) for t in tokens])
    avgdl = doc_lens.mean()
    df = {}
    for t in tokens:
        for w in set(t):
            df[w] = df.get(w, 0) + 1

    def idf(term):
        n = df.get(term, 0)
        return np.log(1 + (N - n + 0.5) / (n + 0.5))

    def bm25_score(query_terms, doc_tokens, doc_len, k1=1.5, b=0.75):
        counts = {}
        for w in doc_tokens:
            counts[w] = counts.get(w, 0) + 1
        score = 0.0
        for term in query_terms:
            if term not in counts:
                continue
            f = counts[term]
            num = f * (k1 + 1)
            denom = f + k1 * (1 - b + b * doc_len / avgdl)
            score += idf(term) * (num / denom)
        return score

    def rank(query_text):
        q = tokenize(query_text)
        scores = [float(bm25_score(q, tokens[i], doc_lens[i])) for i in range(N)]
        order = sorted(range(N), key=lambda i: -scores[i])
        return [(corpus[i]["doc_id"], round(scores[i], 4)) for i in order]

    return rank

def build_vector_index(corpus):
    vecs = np.array([embed(d["text"]) for d in corpus])

    def rank(query_text):
        q = embed(query_text)
        scores = vecs @ q
        order = sorted(range(len(corpus)), key=lambda i: -scores[i])
        return [(corpus[i]["doc_id"], round(float(scores[i]), 4)) for i in order]

    return rank

bm25_rank = build_bm25_index(IN_FORCE_CORPUS)
vector_rank = build_vector_index(IN_FORCE_CORPUS)

for query in ("POL-8842-C renewal", "how many days do I have to report water damage"):
    print(f"query: {query!r}")
    print(f"  bm25:   {bm25_rank(query)}")
    print(f"  vector: {vector_rank(query)}")

Concept 3 — Account-Lookup Tool Scoped to Least Privilege, Read-Only


Answering "why was my payment declined" needs a real account lookup, but the tool making
that call must never be able to do more than exactly that lookup — not because a runbook
says so, but because the credential it holds is enforced in code. A read-only service
credential is scoped to a fixed field allow-list; the backing account record legitimately
contains far more (an SSN, a full card number) that this tool must never be able to
surface even though the row itself is reachable, the same separation a real accounts
table enforces with column-level grants.


Example:


import dataclasses

READ_ONLY_ALLOWED_FIELDS = frozenset({
    "customer_id", "policy_number", "premium_status", "last_payment_date",
    "next_draft_date", "autopay_enabled",
})

@dataclasses.dataclass(frozen=True)
class ServiceCredential:
    role: str
    allowed_fields: frozenset
    can_write: bool

READ_ONLY_SERVICE_CREDENTIAL = ServiceCredential(
    role="customer_service_agent_readonly",
    allowed_fields=READ_ONLY_ALLOWED_FIELDS,
    can_write=False,
)

ACCOUNT_RECORD = {
    "customer_id": "CUST-004821", "policy_number": "POL-8842-C",
    "premium_status": "declined", "last_payment_date": "2026-08-01",
    "next_draft_date": "2026-09-01", "autopay_enabled": True,
    "ssn": "512-34-9821", "full_card_number": "4111111111111234",
}

class AccountLookupTool:
    def __init__(self, credential, backing_store):
        self.credential = credential
        self.backing_store = backing_store

    def lookup(self, customer_id, requested_fields):
        if not self.credential.allowed_fields.issuperset(requested_fields):
            denied = sorted(set(requested_fields) - self.credential.allowed_fields)
            raise PermissionError(f"credential '{self.credential.role}' cannot read: {denied}")
        record = self.backing_store.get(customer_id)
        if record is None:
            raise KeyError(f"no account found for {customer_id}")
        return {field: record[field] for field in requested_fields}

    def update(self, customer_id, updates):
        if not self.credential.can_write:
            raise PermissionError(f"credential '{self.credential.role}' is read-only, cannot write")
        raise NotImplementedError  # unreachable for a read-only credential

Concept 1 — OpenLineage Events Across Intake, Retrieve, Guardrail and Answer


Reusing Week 16 Day 3 Concept 2's OpenLineageClient/ConsoleTransport/emit_stage_run
context-manager pattern verbatim — the same pattern Week 29 Day 5 Concept 2 already
retargeted once, from a five-stage underwriting pipeline to this week's own four
servicing stages (intake, retrieve, guardrail, answer). Every stage gets its own
START/COMPLETE (or FAIL) run event with a fresh run_id, giving a lineage tool a

Example:


# Reusing OpenLineageClient/ConsoleTransport/RunEvent/emit_stage_run pattern
# from Week 16 Day 3 Concept 2 (and Week 29 Day 5 Concept 2's retargeting of
# it) verbatim, now around this week's intake/retrieve/guardrail/answer
# stages. ConsoleTransport logs through Python's logging module to stderr,
# never captured/diffed as part of this block's stdout.
import contextlib
import datetime
import logging

from openlineage.client import OpenLineageClient
from openlineage.client.transport.console import ConsoleConfig, ConsoleTransport
from openlineage.client.run import Dataset, Job, Run, RunEvent, RunState
from openlineage.client.uuid import generate_new_uuid

logging.basicConfig(level=logging.INFO, format="%(message)s")
client = OpenLineageClient(transport=ConsoleTransport(ConsoleConfig()))


@contextlib.contextmanager
def emit_stage_run(job_namespace, job_name, producer="fde-service-agent-pipeline"):
    run_id = str(generate_new_uuid())
    run, job = Run(runId=run_id), Job(namespace=job_namespace, name=job_name)
    client.emit(RunEvent(
        eventType=RunState.START,
        eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
        run=run, job=job, producer=producer,
    ))
    try:
        yield run_id
    except Exception:
        client.emit(RunEvent(
            eventType=RunState.FAIL,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))
        raise
    else:
        client.emit(RunEvent(
            eventType=RunState.COMPLETE,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))

Concept 2 — Correlation ID Carried From Kafka Offset Through to the Final Answer


A regulator reconstructing "why did the bot say this" needs one id that identifies a
single answer end to end — derived from the exact Kafka coordinates Day 1's intake
consumed, not a fresh UUID minted somewhere in the middle that loses the link back to the
original message. Deriving it deterministically from (topic, partition, offset) means a
regulator handed only those three values from Day 1's replay plan can recompute the same
id and pull the matching trace back up, with no separate id-lookup table required.


Example:


import hashlib
import dataclasses

def build_correlation_id(topic, partition, offset):
    raw = f"{topic}:{partition}:{offset}"
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()[:16]

@dataclasses.dataclass
class TraceStep:
    stage: str
    correlation_id: str
    detail: str

def run_traced_pipeline(topic, partition, offset, query_text):
    correlation_id = build_correlation_id(topic, partition, offset)
    trace = []
    trace.append(TraceStep("intake", correlation_id, f"received: {query_text!r}"))
    retrieved_doc = "FAQ-CLAIM-0091-r3"

    trace.append(TraceStep("guardrail", correlation_id, "passed: no violation"))
    answer = f"Your payment was declined -- see {retrieved_doc}."
    trace.append(TraceStep("answer", correlation_id, answer))
    return correlation_id, trace

Concept 3 — Retrieved-Chunk Provenance Persisted for Replay


A regulator asking "why did the bot say 14 days, not 30" needs to see exactly which chunk
(and which effective-date version of it) the answer was actually grounded in — not just
the final answer text. Persisting a provenance record per answer, keyed by
correlation_id, makes an answer replayable months later even after Day 2's corpus has
moved on to a newer revision, because the record freezes the exact wording that was in
force at the moment this specific answer was given.


Example:


import dataclasses

@dataclasses.dataclass
class AnswerProvenance:
    correlation_id: str
    retrieved_doc_id: str
    retrieved_effective_date: str
    retrieval_method: str
    answer_text: str

PROVENANCE_STORE = {}

def record_provenance(correlation_id, retrieved_doc_id, retrieved_effective_date,
                       retrieval_method, answer_text):
    record = AnswerProvenance(correlation_id, retrieved_doc_id, retrieved_effective_date,
                               retrieval_method, answer_text)
    PROVENANCE_STORE[correlation_id] = record
    return record

def replay_answer(correlation_id):
    record = PROVENANCE_STORE.get(correlation_id)
    if record is None:

    return (f"answer {record.answer_text!r} was grounded in {record.retrieved_doc_id} "
            f"(effective {record.retrieved_effective_date}), found via {record.retrieval_method}")

Concept 4 — Retention and Masking Policy for Stored Transcripts


Adapting the reversible-tokenization masking discipline Week 29 Day 2 Concept 2
established for underwriting notes to this week's stored transcripts — here a fixed-
pattern regex mask rather than Presidio's NER-driven recognizers, since a transcript's PII
(a policy number a customer types back to the bot, an SSN offered for verification) is
structured enough not to need NER. Every stored transcript also carries a
retention_days window; a regulator's retention rule is only real if there is code that
can actually answer "which transcripts are past their retention window today."


Example:


import re
import datetime
import dataclasses

POLICY_NUMBER_RE = re.compile(r"\bPOL-\d{4}-[A-Z]\b")
SSN_RE = re.compile(r"\b\d{3}-\d{2}-\d{4}\b")

def mask_transcript_text(text):
    text = SSN_RE.sub("[SSN-REDACTED]", text)
    text = POLICY_NUMBER_RE.sub("[POLICY-REDACTED]", text)
    return text

@dataclasses.dataclass
class StoredTranscript:
    correlation_id: str
    stored_at: str
    masked_text: str
    retention_days: int = 365

def build_stored_transcript(correlation_id, raw_text, stored_at, retention_days=365):
    return StoredTranscript(
        correlation_id=correlation_id,
        stored_at=stored_at,
        masked_text=mask_transcript_text(raw_text),
        retention_days=retention_days,
    )

def is_past_retention(transcript, as_of):
    stored = datetime.date.fromisoformat(transcript.stored_at)
    as_of_date = datetime.date.fromisoformat(as_of)
    return (as_of_date - stored).days > transcript.retention_days

Architecture Decision — Week 30


Choosing between: persisting full regulator-replayable provenance for every answer
(Day 4 Concept 3's PROVENANCE_STORE, keyed by chunk id and effective-date) versus
logging only pipeline-health telemetry (Day 4 Concept 1's OpenLineage run events, which
prove a stage ran and how long it took, but not what wording it actually relied on).


The tradeoff: full per-answer provenance is the only artifact that actually answers a
regulator's real question — "why did the bot tell this specific customer 14 days, not
30" — months after the corpus has moved on to a newer revision; operational lineage alone
proves the pipeline executed but cannot reconstruct the substance of any one answer.
Provenance is also the more expensive commitment: it means storing, masking (Day 4
Concept 4), and retention-managing a per-query record forever the retention window
requires, not just an ephemeral trace a monitoring dashboard discards after a rolling
window.


Rule of thumb: persist full chunk-level provenance for any answer a regulator could
plausibly be asked to justify after the fact — which, for a BFSI customer-service agent
covered by Article 50 transparency and (per Day 5 Concept 1) potentially Annex III once it
touches autopay, is every answer, not a sample. Keep operational-only lineage (Day 4
Concept 1's run events, without Concept 3's provenance layer) for purely internal
pipelines with no customer-facing output and no regulator ever asking "why did you say
that" about a specific interaction — a batch data-quality job, for instance, where knowing
a stage ran and its duration is the whole of what anyone will ever need to know about that
run.
