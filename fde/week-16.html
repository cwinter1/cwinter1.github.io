Concept 1 — RunEvent Lifecycle: START, RUNNING, COMPLETE, FAIL, ABORT

OpenLineage models one execution of one pipeline stage as a run — a UUID that stays fixed across every event describing that execution — and reports its progress as a sequence of RunEvents, each carrying an eventType from a fixed RunState enum: START, RUNNING (an optional heartbeat for a long-running stage), COMPLETE, FAIL, or ABORT. A consumer like Marquez rebuilds "did this run succeed" purely from which terminal state (COMPLETE, FAIL, or ABORT) the last event for a given run.runId carried — there is no separate "status" field anywhere else. A Job is namespaced separately from the run: job.namespace + job.name identifies what runs (a stable pipeline-stage identity, reused across every execution), while run.runId identifies this one execution of it. run_id/fail_run_id below are real UUIDv7 values that differ on every run -- only their relationship, not their literal digits, is deterministic, so the Example checks their shape and relationship rather than printing the raw values.

Example:

import datetime
from openlineage.client.run import RunEvent, RunState, Run, Job
from openlineage.client.uuid import generate_new_uuid

def make_event(state, run_id, job_namespace, job_name, producer="fde-finserv-dataprep"):
    return RunEvent(
        eventType=state,
        eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
        run=Run(runId=run_id),
        job=Job(namespace=job_namespace, name=job_name),
        producer=producer,
    )

run_id = str(generate_new_uuid())
print(f"run_id is a real UUID: {len(run_id) == 36}")

states_seen = []
for state in (RunState.START, RunState.RUNNING, RunState.COMPLETE):
    ev = make_event(state, run_id, "fde.finserv.dataprep", "parse_policy_pdf")
    states_seen.append(ev.eventType.value)
print(f"lifecycle emitted for one run: {states_seen}")

fail_run_id = str(generate_new_uuid())
fail_ev = make_event(RunState.FAIL, fail_run_id, "fde.finserv.dataprep", "parse_policy_pdf")
print(f"a FAILED execution gets its OWN run_id: {fail_run_id != run_id}")
print(f"its eventType: {fail_ev.eventType.value}")

Concept 2 — Dataset Naming: postgres://, s3://, and Vector-Store Namespaces


A Dataset is namespaced the same two-part way a Job is: namespace identifies where
the data lives (a connection string convention, not the actual credential), name
identifies which dataset within it. OpenLineage's own convention for namespace is a
URI scheme plus host — postgres://host:port, s3://bucket, hdfs://namenode:port — so
two pipelines emitting lineage for the same physical Postgres table always agree on its
namespace without coordinating in advance. Nothing in the spec defines a reserved scheme
for a vector store, because none existed when the spec's early conventions were set — this
week adopts the same scheme://host:port shape for Qdrant/Milvus/pgvector namespaces
(qdrant://host:6333, milvus://host:19530) so a chunk-index dataset composes with the
same tooling a postgres:// dataset does, rather than inventing an incompatible shape.


Example:


from openlineage.client.run import Dataset, Job

pg_ds = Dataset(namespace="postgres://finserv-db.internal:5432", name="claims.policy_documents")
s3_ds = Dataset(namespace="s3://finserv-raw-policies", name="2026/09/policy_batch_0417.pdf")
vec_ds = Dataset(namespace="qdrant://finserv-vectors:6333", name="policy_chunks_v3")

for ds in (pg_ds, s3_ds, vec_ds):
    print(f"{ds.namespace!r} / {ds.name!r}")

job_names = [
    Job(namespace="fde.finserv.dataprep", name="parse_policy_pdf"),
    Job(namespace="fde.finserv.dataprep", name="chunk_policy_text"),
    Job(namespace="fde.finserv.dataprep", name="embed_policy_chunks"),
    Job(namespace="fde.finserv.retrieval", name="retrieve_policy_chunks"),
]
for j in job_names:
    print(f"{j.namespace}.{j.name}")

Concept 3 — Why Parse/Chunk/Embed Has No Off-the-Shelf Integration


Airflow's own OpenLineage provider emits lineage automatically for a PythonOperator or a
SQL operator, because Airflow already knows a task's inputs/outputs at the operator level.
dbt's OpenLineage integration works the same way, reading dbt's own manifest. Neither
mechanism has anything to attach to for a hand-written parse_policy_pdf() function
called directly inside a script — there is no operator, no manifest, no SQL statement for
an off-the-shelf integration to introspect. The only way lineage exists for this shape of
pipeline is a human wrapping each stage explicitly, which is exactly what the rest of this
week builds. This concept proves the gap is real (not just asserted) by wrapping one stage
by hand and showing the emitted events with OpenLineage's own ConsoleTransport — the
same client code path HttpTransport uses, minus an actual network call to Marquez.
ConsoleTransport logs its JSON through Python's logging module (to stderr by default,
verifiable by running this block directly in a terminal), so only the print() lines
below are real, captured stdout.


Example:


import contextlib
import datetime
import logging

from openlineage.client import OpenLineageClient
from openlineage.client.transport.console import ConsoleConfig, ConsoleTransport
from openlineage.client.run import Job, Run, RunEvent, RunState
from openlineage.client.uuid import generate_new_uuid

logging.basicConfig(level=logging.INFO, format="%(message)s")
client = OpenLineageClient(transport=ConsoleTransport(ConsoleConfig()))

@contextlib.contextmanager
def emit_stage_run(job_namespace, job_name, producer="fde-finserv-dataprep"):
    run_id = str(generate_new_uuid())
    run, job = Run(runId=run_id), Job(namespace=job_namespace, name=job_name)
    client.emit(RunEvent(
        eventType=RunState.START,
        eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
        run=run, job=job, producer=producer,
    ))
    try:
        yield run_id
    except Exception:
        client.emit(RunEvent(
            eventType=RunState.FAIL,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))
        raise
    else:
        client.emit(RunEvent(
            eventType=RunState.COMPLETE,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))

def parse_policy_pdf(path):
    if path.endswith(".corrupt"):
        raise ValueError("cannot parse corrupt PDF")
    return f"parsed text from {path}"

with emit_stage_run("fde.finserv.dataprep", "parse_policy_pdf"):
    result = parse_policy_pdf("policy_batch_0417.pdf")
print(f"stage succeeded, result: {result!r}")

try:
    with emit_stage_run("fde.finserv.dataprep", "parse_policy_pdf"):
        parse_policy_pdf("policy_batch_0418.corrupt")
except ValueError as e:
    print(f"stage raised and FAIL was emitted before re-raise: {e}")

BFSI Reality Check — Day 1


Legacy angle: A mainframe-sourced extract (Week 13) already has no off-the-shelf
lineage tool either — this week's hand-wrapped-stage pattern is the same shape needed
there, not a new problem specific to unstructured documents.


Compliance angle: A regulator's single question — "where did this answer's source data
come from" — is exactly what a run.runId chain from retrieve back to parse is built to
answer. Without it, the honest answer to that question is "we don't know," which is a
finding, not a technicality.


What breaks in production: A team wraps parse and embed with emit_stage_run but
forgets chunk because it "felt like an internal implementation detail." Every lineage
query from then on has a gap in the middle of the chain — retrieve can be traced back to an
embed run, and an embed run's inputs point at a document, but which chunk of it, and by
what rule it was split, is unrecoverable after the fact.

Concept 1 — OpenLineageClient via HttpTransport and openlineage.yml


Day 1's ConsoleTransport was passed to OpenLineageClient explicitly in code. In a real
deployment the transport is configured externally, through an openlineage.yml file (or
the equivalent environment variables) that names transport.type: http plus the target
Marquez URL — so the same pipeline code emits to a laptop's local Marquez in dev and a
shared production Marquez without a single code change. OpenLineageClient() with no
arguments reads that config automatically (via the OPENLINEAGE_CONFIG environment
variable, or ~/.openlineage/client.yaml as a fallback) and builds the transport it
describes. Building and inspecting an HttpTransport this way is genuinely real — the
same object client.emit() would use to POST to an actual Marquez — it is only the
network call itself this sandbox cannot make, so this concept stops one step short of that
call, at "the client is correctly configured and ready to send." OpenLineageClient also
logs its transport choice through Python's logging module (to stderr by default), so
only the print() lines below are real, captured stdout.


Example:


import os
import tempfile

from openlineage.client.client import OpenLineageClient

cfg_yaml = """
transport:
  type: http
  url: http://marquez.internal:5000
  endpoint: api/v1/lineage
  timeout: 5
"""
with tempfile.TemporaryDirectory() as d:
    cfg_path = os.path.join(d, "openlineage.yml")
    with open(cfg_path, "w") as f:
        f.write(cfg_yaml)
    os.environ["OPENLINEAGE_CONFIG"] = cfg_path
    configured_client = OpenLineageClient()
    print(f"transport kind: {configured_client.transport.kind}")
    print(f"transport url: {configured_client.transport.config.url}")
    print(f"transport endpoint: {configured_client.transport.config.endpoint}")
    print(f"transport timeout: {configured_client.transport.config.timeout}")
del os.environ["OPENLINEAGE_CONFIG"]

Concept 2 — Paired START/COMPLETE Emission Around Each Pipeline Stage


Day 1 Concept 3 built emit_stage_run as a proof that the wrapping has to be hand-written.
This concept makes it the week's reusable baseline: a context manager that always emits a
matched START immediately before the wrapped code runs and exactly one terminal event
(COMPLETE on normal exit, FAIL on an exception, propagated in both cases) immediately
after — never zero terminal events, never two. It also accepts an optional run_facets
dict so later concepts can attach structure (a parent-run link, a schema facet) to the
Run object itself without changing the emission logic. ConsoleTransport logs its real
JSON through Python's logging module (to stderr, not captured below), and run_id is a
fresh, genuinely different value on every run, so the Example checks its shape rather
than printing the raw value.


Example:


import contextlib
import datetime
import logging

from openlineage.client import OpenLineageClient
from openlineage.client.transport.console import ConsoleConfig, ConsoleTransport
from openlineage.client.run import Job, Run, RunEvent, RunState
from openlineage.client.uuid import generate_new_uuid

logging.basicConfig(level=logging.INFO, format="%(message)s")
console_client = OpenLineageClient(transport=ConsoleTransport(ConsoleConfig()))

@contextlib.contextmanager
def emit_stage_run(client, job_namespace, job_name, producer="fde-finserv-dataprep", run_facets=None):
    run_id = str(generate_new_uuid())
    run = Run(runId=run_id, facets=run_facets or {})
    job = Job(namespace=job_namespace, name=job_name)
    client.emit(RunEvent(
        eventType=RunState.START,
        eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
        run=run, job=job, producer=producer,
    ))
    try:
        yield run_id
    except Exception:
        client.emit(RunEvent(
            eventType=RunState.FAIL,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))
        raise
    else:
        client.emit(RunEvent(
            eventType=RunState.COMPLETE,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))

with emit_stage_run(console_client, "fde.finserv.dataprep", "parse_policy_pdf") as run_id:
    print(f"parse stage ran under a real UUID run_id: {len(run_id) == 36}")

Concept 3 — parentRunFacet: Linking Stage Runs to One Orchestrating DAG Run


Each stage run built so far stands alone — nothing connects parse_policy_pdf's run to
chunk_policy_text's run as part of the same pipeline execution. parentRunFacet
(the real facet is ParentRunFacet, attached under run.facets["parent"]) closes that
gap: it records the orchestrating run's own runId plus its job's namespace and name
inside each child stage's Run object. A Marquez UI or lineage-graph API query can then
group every stage run under the one DAG run that orchestrated them, and separately, two
different DAG runs (an ingest pipeline and a retrieval pipeline) never get their stage runs
confused with each other because each set of children carries its own distinct parent
runId. ConsoleTransport logs the real JSON for every one of these events through
Python's logging module (to stderr, not captured below); dag_run_id and each stage's
run_id are fresh, genuinely different values every run, so the Example checks their
shape rather than printing the raw values.


Example:


from openlineage.client.facet_v2 import parent_run

@contextlib.contextmanager
def emit_child_stage_run(client, job_namespace, job_name, dag_run_id, dag_job, producer="fde-finserv-dataprep"):
    parent_facet = parent_run.ParentRunFacet(
        run=parent_run.Run(runId=dag_run_id),
        job=parent_run.Job(namespace=dag_job.namespace, name=dag_job.name),
    )
    with emit_stage_run(client, job_namespace, job_name, producer, run_facets={"parent": parent_facet}) as run_id:
        yield run_id

dag_run_id = str(generate_new_uuid())
dag_job = Job(namespace="fde.finserv.dataprep", name="policy_ingest_dag")
console_client.emit(RunEvent(
    eventType=RunState.START,
    eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
    run=Run(runId=dag_run_id), job=dag_job, producer="fde-finserv-dataprep",
))

child_run_ids = []
for stage_name in ("parse_policy_pdf", "chunk_policy_text", "embed_policy_chunks"):
    with emit_child_stage_run(console_client, "fde.finserv.dataprep", stage_name, dag_run_id, dag_job) as run_id:
        child_run_ids.append(run_id)

console_client.emit(RunEvent(
    eventType=RunState.COMPLETE,
    eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
    run=Run(runId=dag_run_id), job=dag_job, producer="fde-finserv-dataprep",
))

print(f"dag_run_id is a real UUID: {len(dag_run_id) == 36}")
print(f"three stage runs, all distinct: {len(set(child_run_ids)) == 3}")

BFSI Reality Check — Day 2


Legacy angle: The openlineage.yml-vs-code-config split (Concept 1) matters more for
a legacy-adjacent pipeline than a greenfield one: the same ingest code that ran against a
COBOL extract in a dev sandbox can point at production Marquez purely by shipping a
different config file with the deploy, with no risk of a hardcoded dev URL leaking into a
production build.


Compliance angle: parentRunFacet is what turns "we have lineage for individual
stages" into "we have lineage for this specific customer-facing pipeline execution that
produced this specific answer" — a regulator's audit question is almost always about one
execution, not the general capability.


What breaks in production: Two independent pipelines (an ingest DAG and a retrieval
DAG) are wired to write to the same Marquez, and a developer copy-pastes the ingest DAG's
dag_job object into the retrieval pipeline's stage-wrapping code without giving it a
different name. Marquez now shows retrieval stage runs nested under what looks like an
ingest job, and any lineage query scoped to "the ingest pipeline" silently includes runs
that were never part of it.

Concept 1 — Stable Dataset Identifiers for a Chunk Set and an Index Collection


Everything emitted so far described runs (executions of a stage). This concept turns
to the other half of the spec: datasets as first-class, addressable things a run
reads from or writes to. A document's chunk set needs a name that is stable across every
re-run of the chunking stage for the same source document — {doc_id}::chunk_set, not a
name derived from a random ID generated fresh each run — so a lineage query can find "the
chunks for policy_doc_101" regardless of which run produced them most recently. The vector
index collection they land in is a second, separate dataset (policy_chunks_v3 in the
qdrant:// namespace already introduced Day 1), because the chunk set and the index
collection have different lifecycles: re-chunking a document replaces its chunk-set
dataset's content, but the index collection persists across many documents' worth of
upserts.


Example:


from openlineage.client.run import Dataset

def chunk_set_dataset(doc_id):
    return Dataset(namespace="fde.finserv.dataprep", name=f"{doc_id}::chunk_set")

def index_collection_dataset():
    return Dataset(namespace="qdrant://finserv-vectors:6333", name="policy_chunks_v3")

doc_101_chunks_run1 = chunk_set_dataset("policy_doc_101")
doc_101_chunks_run2 = chunk_set_dataset("policy_doc_101")
doc_102_chunks = chunk_set_dataset("policy_doc_102")
index_ds = index_collection_dataset()

print(f"same doc, two runs, SAME dataset identity: {doc_101_chunks_run1.name == doc_101_chunks_run2.name}")
print(f"two different docs, DIFFERENT identity: {doc_101_chunks_run1.name != doc_102_chunks.name}")
print(f"chunk-set namespace vs index namespace: {doc_101_chunks_run1.namespace!r} vs {index_ds.namespace!r}")

Concept 2 — schemaDatasetFacet: Chunk Fields and Embedding Dimension


A chunk-set dataset is more useful once its shape is attached, not just its name.
SchemaDatasetFacet carries a list of SchemaDatasetFacetFields — each with a name,
type, and optional description — describing exactly the fields a downstream consumer

description rather than being silently implied).

Concept 3 — Custom Facets, and Keeping Fan-Out From Exploding the Graph


The spec's built-in facets don't have a field for "which chunker version produced this"
or "which embedding model name" — those are pipeline-specific, so OpenLineage lets any
producer define a custom facet: a plain attrs-decorated class carrying whatever
fields it needs, inheriting from DatasetFacet (or RunFacet/JobFacet) so it still
carries the required _producer/_schemaURL metadata every facet needs. Separately, and
more consequentially for a busy pipeline: one document with 20 chunks does not mean 20
new graph nodes. Modeling the chunk set as one dataset (Concept 1) rather than one
dataset per chunk is what keeps a lineage graph proportional to document count instead of
chunk count — this concept measures that difference rather than just asserting it.


Example:

print(f"chunker: {chunker_facet.chunker_name} v{chunker_facet.chunker_version}")

Concept 3 — dataQualityAssertionsDatasetFacet: Asserting Dimension and Null Rate


DataQualityAssertionsDatasetFacet carries a list of Assertions — each a named check
with a boolean success, and optionally the column it applies to plus expected/
actual values recorded as strings for display. This turns Concept 2's raw measurements
into pass/fail gates: "embedding dimension must equal the declared schema dimension" and
"null rate must stay under a threshold" are both real assertions a pipeline can act on
(quarantine the batch, page someone) rather than numbers nobody is watching.


Example:


from openlineage.client.facet_v2 import data_quality_assertions_dataset as dqa

EXPECTED_EMBEDDING_DIM = 384

def assert_embedding_dimension(vectors, expected_dim):
    bad = [i for i, v in enumerate(vectors) if len(v) != expected_dim]
    return dqa.Assertion(
        assertion="embedding dimension equals declared schema dimension",
        success=(len(bad) == 0),
        column="embedding_vector",
        expected=str(expected_dim),
        actual=str(sorted(set(len(v) for v in vectors))),
    )

def assert_null_rate(null_rate, threshold):
    return dqa.Assertion(
        assertion=f"null rate below {threshold:.0%}",
        success=(null_rate <= threshold),
        column="chunk_text",
        expected=f"<= {threshold}",
        actual=f"{null_rate:.3f}",
    )

vectors_ok = [[0.0] * 384 for _ in range(5)]
vectors_bad = [[0.0] * 384 for _ in range(4)] + [[0.0] * 300]

assertion_ok = assert_embedding_dimension(vectors_ok, EXPECTED_EMBEDDING_DIM)
assertion_bad = assert_embedding_dimension(vectors_bad, EXPECTED_EMBEDDING_DIM)
assertion_nulls = assert_null_rate(0.042, 0.05)

assertions_facet = dqa.DataQualityAssertionsDatasetFacet(
    assertions=[assertion_ok, assertion_bad, assertion_nulls]
)
for a in assertions_facet.assertions:
    print(f"{a.assertion}: success={a.success} expected={a.expected} actual={a.actual}")

Concept 4 — errorMessageRunFacet: Attaching a Real Error to a FAIL Event

captured below).

Concept 1 — Walking a Citation Back Through Retrieve, Embed, Chunk, Parse


Every prior day built the pieces — runs, datasets, facets — that a lineage graph is made
of. This concept assembles them into the thing the week exists to answer: given one cited
chunk, walk backward stage by stage to the original source document. The walk itself needs
no live Marquez — it is pure graph traversal over the same {job, inputs, outputs} shape
every event emitted this week already carries, so it is built and run genuinely here, over
an in-memory list of exactly the kind of records emit_stage_run (Day 2) would have
produced across one full pipeline execution.


Example:


lineage_events = [
    {"job": "parse_policy_pdf", "run_id": "run-parse-01",
     "inputs": ["s3://finserv-raw-policies/policy_batch_0417.pdf"],
     "outputs": ["fde.finserv.dataprep/policy_doc_101::parsed_text"]},
    {"job": "chunk_policy_text", "run_id": "run-chunk-01",
     "inputs": ["fde.finserv.dataprep/policy_doc_101::parsed_text"],
     "outputs": ["fde.finserv.dataprep/policy_doc_101::chunk_set"]},
    {"job": "embed_policy_chunks", "run_id": "run-embed-01",
     "inputs": ["fde.finserv.dataprep/policy_doc_101::chunk_set"],
     "outputs": ["qdrant://finserv-vectors:6333/policy_chunks_v3"]},
    {"job": "retrieve_policy_chunks", "run_id": "run-retrieve-01",
     "inputs": ["qdrant://finserv-vectors:6333/policy_chunks_v3"],
     "outputs": ["fde.finserv.retrieval/answer_042::retrieved_chunks"]},
]

def trace_citation(dataset_name, events):
    chain = []
    current = dataset_name
    while True:
        producing = [e for e in events if current in e["outputs"]]
        if not producing:
            break
        stage = producing[0]
        chain.append(stage["job"])
        current = stage["inputs"][0]
    chain.append(f"SOURCE: {current}")
    return chain

chain = trace_citation("fde.finserv.retrieval/answer_042::retrieved_chunks", lineage_events)
print(" <- ".join(chain))

Concept 2 — Marquez Lineage API Traversal for a Regulator's Single Question


A real Marquez server exposes GET /api/v1/lineage?nodeId=dataset:{namespace}:{name}&depth=N,
returning the upstream (and downstream) graph within depth hops of one node — the actual
HTTP call needs a live Marquez this sandbox doesn't have, so that specific request stays
REAL MODE — not executed: the correct endpoint shape, not a guess. What genuinely
executes here is the traversal logic the endpoint implements: a breadth-first walk
bounded by depth, over the same event list Concept 1 built — the identical shape a
regulator's "where did this come from" question needs answered, satisfied without a
network call. This uses lineage_events exactly as Concept 1's Example built it — Concept
1's Exercise (which adds a rerank_policy_chunks stage) is a reader exercise, not code
shipped in this file, so this concept's own lineage_events does not include it.


Example:


def marquez_style_lineage_query(node_id, events, depth=5):
    """Mimics GET /api/v1/lineage?nodeId=dataset:{namespace}:{name}&depth=N:
    REAL MODE for the actual HTTP call against a live Marquez; this traversal
    logic itself is genuinely executed over the same event shape Marquez stores."""
    visited = []
    frontier = [node_id]
    for _ in range(depth):
        next_frontier = []
        for node in frontier:
            producing = [e for e in events if node in e["outputs"]]
            for e in producing:
                if e not in visited:
                    visited.append(e)
                next_frontier.extend(e["inputs"])
        if not next_frontier:
            break
        frontier = next_frontier
    return visited

result = marquez_style_lineage_query("fde.finserv.retrieval/answer_042::retrieved_chunks", lineage_events, depth=5)
print(f"nodes visited answering the regulator's single question: {[n['job'] for n in result]}")

shallow = marquez_style_lineage_query("fde.finserv.retrieval/answer_042::retrieved_chunks", lineage_events, depth=1)
print(f"depth-1 query visits fewer nodes than depth-5: {len(shallow) < len(result)}")

What breaks in production: A document is re-embedded and the pipeline reuses the SAME
dataset version string (or omits datasetVersion entirely) instead of minting a new one.
Every citation traced against an answer given before the re-embed now resolves to the
NEW chunk content, which may say something different from what the answer actually quoted
— an audit trail that silently rewrites history is worse than no audit trail, because it
looks trustworthy while being wrong.




Architecture Decision — Week 16


Choosing between: emitting a full START/COMPLETE (or FAIL) lineage event, with
every applicable facet, for every single pipeline stage execution — vs. sampling or
batching lineage emission for high-volume stages to keep emission overhead low.


Rule of thumb: Any stage on the path that produces content a customer-facing answer
can actually cite — parse, chunk, embed, retrieve, and anything downstream of retrieve —
emits full, unsampled lineage for every execution, with no exception, the same way Week
15's Architecture Decision kept irreversible-harm guardrails inline regardless of cost:
losing a lineage record for one chunk that ends up cited in one answer is exactly the gap
Day 5's "an audit trail that silently omits data is worse than no audit trail" finding
warns about, and there is no way to know in advance which chunk that will be. A
stage that exists purely for internal instrumentation — a periodic health-check ping, a
cache-warming job that touches no dataset an answer could ever cite — can be sampled or
batched, because losing one of its records has no audit consequence. The dividing line is
never "is this stage expensive to instrument," it is "could this stage's output ever be
the answer to a regulator's single question" — Day 5 exists because the answer to that
question, for this week's whole parse→chunk→embed→retrieve chain, is always yes.
