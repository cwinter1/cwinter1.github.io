Concept 1 — Prohibited Practices Under Article 5

Article 5 bans a short, fixed list of AI practices outright — no risk-tiering, no documentation exception, no permitted use case. For BFSI, the two that matter most in practice are subliminal/manipulative techniques causing significant harm (Article 5(1)(a)), exploiting a vulnerable group's age, disability, or socioeconomic situation (Article 5(1)(b)), social scoring by a public authority leading to unjustified or disproportionate detrimental treatment (Article 5(1)(c)), and biometric categorization inferring race, political opinion, religion, or sexual orientation (Article 5(1)(g)). A system landing in any of these is not "high-risk with extra paperwork" — it cannot be placed on the market at all.

Example:

import dataclasses

PROHIBITED_PRACTICES = {
    "subliminal_manipulation": "Article 5(1)(a): subliminal techniques materially distorting behavior, causing significant harm",
    "exploitation_of_vulnerability": "Article 5(1)(b): exploiting age/disability/socioeconomic vulnerability, causing significant harm",
    "social_scoring": "Article 5(1)(c): social scoring by public authorities leading to unjustified or disproportionate detrimental treatment",
    "biometric_categorization_protected": "Article 5(1)(g): biometric categorization inferring race, political opinions, religion, or sexual orientation",
}

@dataclasses.dataclass
class SystemDescription:
    name: str
    uses_subliminal_technique: bool = False
    exploits_vulnerable_group: bool = False
    performs_social_scoring_by_public_authority: bool = False
    infers_protected_biometric_categories: bool = False

def check_article5_prohibited(system):
    violations = []
    if system.uses_subliminal_technique:
        violations.append("subliminal_manipulation")
    if system.exploits_vulnerable_group:
        violations.append("exploitation_of_vulnerability")
    if system.performs_social_scoring_by_public_authority:
        violations.append("social_scoring")
    if system.infers_protected_biometric_categories:
        violations.append("biometric_categorization_protected")
    return violations

fraud_score_model = SystemDescription(name="fraud_scoring_v3")
social_credit_pilot = SystemDescription(
    name="citizen_trust_pilot",
    performs_social_scoring_by_public_authority=True,
)

print(f"{fraud_score_model.name}: {check_article5_prohibited(fraud_score_model)}")
print(f"{social_credit_pilot.name}: {check_article5_prohibited(social_credit_pilot)}")

Concept 2 — High-Risk Classification Under Annex III Point 5(b) and 5(c)


Annex III lists the use-case categories that make a system high-risk under Article 6.
Point 5 covers essential private/public services; point 5(b) is "evaluation of the
creditworthiness of natural persons or establishing their credit score" — WITH an explicit
carve-out for systems used purely for detecting financial fraud — and point 5(c) is "risk
assessment and pricing in relation to natural persons in the case of life and health
insurance." Both are named explicitly because they are exactly what a BFSI underwriting or
scoring pipeline does; a generic support chatbot classifying nothing under Annex III at
all is the contrasting case that shows the boundary isn't "any AI system in finance."


Example:


@dataclasses.dataclass
class AnnexIIISystem:
    name: str
    domain: str
    purpose: str
    is_fraud_detection: bool = False

def classify_annex_iii_point_5(system):
    if system.domain == "credit":
        if system.is_fraud_detection:
            return None
        return "5(b)"
    if system.domain == "insurance" and system.purpose in ("risk_assessment", "pricing"):
        return "5(c)"
    return None

underwriting_model = AnnexIIISystem(name="sme_credit_scorer", domain="credit", purpose="scoring")
fraud_model = AnnexIIISystem(name="txn_fraud_detector", domain="credit", purpose="fraud_detection", is_fraud_detection=True)
life_pricing_model = AnnexIIISystem(name="life_policy_pricer", domain="insurance", purpose="pricing")
chatbot = AnnexIIISystem(name="faq_chatbot", domain="support", purpose="answering")

for sys_ in (underwriting_model, fraud_model, life_pricing_model, chatbot):
    print(f"{sys_.name}: {classify_annex_iii_point_5(sys_)}")

Concept 3 — The Article 6(3) Narrow-Task Derogation and the Article 6(4) Duty to Document


Landing in an Annex III category is not automatically final. Article 6(3) says a system is
NOT high-risk if it does not pose a significant risk of harm and meets at least one of
four narrow-task conditions: (a) a narrow procedural task, (b) improving the result of a
previously completed human activity, (c) detecting deviation from a prior human
decision-making pattern without replacing or influencing that human assessment, or (d) a
preparatory task to an Annex III assessment. But there is a hard override: Article 6(3)'s
final subparagraph says a system that profiles natural persons is ALWAYS high-risk,
regardless of meeting any of those four conditions. And separately, Article 6(4) requires
the provider to document that derogation assessment BEFORE the system is placed on the
market — the documentation duty applies whichever way the classification comes out.


Example:


NARROW_TASK_CONDITIONS = {
    "procedural_task": "Article 6(3)(a): narrow procedural task",
    "improves_human_output": "Article 6(3)(b): improves the result of a previously completed human activity",
    "detects_deviation_no_replace": "Article 6(3)(c): detects deviation from a prior human decision-making pattern, without replacing or influencing that human assessment",
    "preparatory_task": "Article 6(3)(d): preparatory task to an Annex III assessment",
}

@dataclasses.dataclass
class DerogationAssessment:
    system_name: str
    annex_iii_point: str
    meets_condition: str = None
    performs_profiling: bool = False
    documented_before_market: bool = False

def is_high_risk_after_derogation(assessment):
    if assessment.performs_profiling:
        return True
    if assessment.meets_condition in NARROW_TASK_CONDITIONS:
        return False
    return True

def article_6_4_compliant(assessment):
    return assessment.documented_before_market

derogated_case = DerogationAssessment(
    system_name="credit_score_qa_flagger",
    annex_iii_point="5(b)",
    meets_condition="detects_deviation_no_replace",
    documented_before_market=True,
)
print(f"{derogated_case.system_name}: high_risk={is_high_risk_after_derogation(derogated_case)}, article_6_4_compliant={article_6_4_compliant(derogated_case)}")

no_derogation_case = DerogationAssessment(
    system_name="sme_credit_scorer",
    annex_iii_point="5(b)",
    meets_condition=None,
    documented_before_market=True,
)
print(f"{no_derogation_case.system_name}: high_risk={is_high_risk_after_derogation(no_derogation_case)}")

undocumented_case = DerogationAssessment(
    system_name="life_policy_pricer",
    annex_iii_point="5(c)",
    meets_condition=None,
    documented_before_market=False,
)
print(f"{undocumented_case.system_name}: article_6_4_compliant={article_6_4_compliant(undocumented_case)}")

Concept 4 — Article 50 Transparency Obligations for Lower-Risk Systems


A system that is not high-risk at all is not necessarily obligation-free. Article 50
requires disclosure to natural persons interacting with an AI system, unless it is obvious
from context that they are interacting with one (Article 50(1)) — a plain FAQ chatbot
needs disclosure, an IVR menu explicitly labelled as automated does not. Separately,
Article 50(2) requires AI-generated or manipulated content (synthetic audio, image, video,
or text presented as authentic) to be marked as artificially generated. These are the
right-sized obligation for a system that never touched Annex III at all.


Example:


@dataclasses.dataclass
class TransparencySystem:
    name: str
    interacts_with_natural_persons: bool = False
    obviously_ai: bool = False
    generates_synthetic_content: bool = False

def article_50_disclosure_required(system):
    reasons = []
    if system.interacts_with_natural_persons and not system.obviously_ai:
        reasons.append("Article 50(1): must inform the natural person they are interacting with an AI system")
    if system.generates_synthetic_content:
        reasons.append("Article 50(2): AI-generated or manipulated content must be marked as artificially generated")
    return reasons

support_chatbot = TransparencySystem(name="claims_faq_chatbot", interacts_with_natural_persons=True)
disclosed_ivr = TransparencySystem(name="ivr_menu_bot", interacts_with_natural_persons=True, obviously_ai=True)
deepfake_marketing = TransparencySystem(name="synthetic_testimonial_generator", generates_synthetic_content=True)

for sys_ in (support_chatbot, disclosed_ivr, deepfake_marketing):
    print(f"{sys_.name}: {article_50_disclosure_required(sys_)}")

BFSI Reality Check — Day 1


Legacy angle: A twenty-year-old underwriting rules engine being "AI-washed" into a
scoring model doesn't change what Annex III cares about — 5(b)/5(c) classification turns
on the purpose (creditworthiness evaluation, insurance risk/pricing), not on whether the
implementation is a modern gradient-boosted model or a legacy decision table.


Compliance angle: The Article 6(3) narrow-task derogation is the single most
consequential judgment call this week covers — claiming it wrongly for a system that
actually does replace a human's credit decision is not a paperwork error, it is
misclassifying a high-risk system as exempt, which is worse than never having assessed it.


What breaks in production: A team documents the Article 6(4) derogation assessment
once, at initial launch, and never revisits it. Six months later a "minor" model update
adds an automated decline path that previously always routed to a human reviewer — the
system no longer meets condition (b) ("improves the result of a previously completed
human activity"), but nobody re-ran the assessment, so the system is now high-risk in
practice while still being treated as exempt on paper.

Concept 1 — Article 3's Provider, Deployer, and Putting-Into-Service Definitions


Article 3 defines a provider as whoever develops an AI system (or has one developed)
and places it on the market or puts it into service under its own name or trademark — the
entity whose brand the system carries. A deployer is whoever uses a system under its
own authority, EXCEPT for personal, non-professional use, which Article 3(4) carves out of
the deployer definition entirely. Putting into service means supplying the system for
first use directly to a deployer, or for the provider's own use, for its intended purpose.
These roles are not mutually exclusive titles a company picks — a bank that builds and
brands its own scoring model is a provider of that system; the same bank licensing and
using a third-party vendor's model in its own lending decisions is a deployer of that one.


Example:


import dataclasses

@dataclasses.dataclass
class Actor:
    name: str
    developed_system: bool = False
    placed_on_market_under_own_name: bool = False
    uses_system_under_own_authority: bool = False
    personal_non_professional_use: bool = False

def classify_role(actor):
    if actor.personal_non_professional_use:
        return None
    if actor.developed_system and actor.placed_on_market_under_own_name:
        return "provider"
    if actor.uses_system_under_own_authority:
        return "deployer"
    return "neither"

fintech_builder = Actor(name="fintech_scorer_co", developed_system=True, placed_on_market_under_own_name=True)
bank_licensee = Actor(name="regional_bank", uses_system_under_own_authority=True)
personal_user = Actor(name="individual_budgeter", uses_system_under_own_authority=True, personal_non_professional_use=True)

for actor in (fintech_builder, bank_licensee, personal_user):
    print(f"{actor.name}: {classify_role(actor)}")

Concept 2 — Article 25: When a Deployer Becomes a Provider


Article 25(1) lists three circumstances under which a distributor, importer, deployer, or
other third party is treated as a provider and inherits full provider obligations: (a)
putting its own name or trademark on a high-risk system already on the market — UNLESS a
contractual arrangement explicitly keeps the original provider's obligations in place;
(b) substantially modifying a high-risk system already placed on the market such that it
remains high-risk; or (c) modifying the intended purpose of a system — including a
general-purpose system not originally classified high-risk — in a way that makes it
high-risk. Reselling an unmodified system under someone else's contractual arrangement
does none of these.


Example:


@dataclasses.dataclass
class ThirdPartyModification:
    actor_name: str
    rebrands_under_own_name: bool = False
    substantially_modifies_high_risk_system: bool = False
    changes_intended_purpose_to_high_risk: bool = False
    contractual_arrangement_keeps_original_provider: bool = False

def becomes_provider_under_article_25(mod):
    if mod.contractual_arrangement_keeps_original_provider and mod.rebrands_under_own_name:
        return False
    return (
        mod.rebrands_under_own_name
        or mod.substantially_modifies_high_risk_system
        or mod.changes_intended_purpose_to_high_risk
    )

white_label_reseller = ThirdPartyModification(actor_name="white_label_reseller", rebrands_under_own_name=True)
contracted_reseller = ThirdPartyModification(
    actor_name="contracted_reseller",
    rebrands_under_own_name=True,
    contractual_arrangement_keeps_original_provider=True,
)
finetuning_bank = ThirdPartyModification(actor_name="finetuning_bank", substantially_modifies_high_risk_system=True)
repurposing_bank = ThirdPartyModification(actor_name="repurposing_bank", changes_intended_purpose_to_high_risk=True)

for mod in (white_label_reseller, contracted_reseller, finetuning_bank, repurposing_bank):
    print(f"{mod.actor_name}: becomes_provider={becomes_provider_under_article_25(mod)}")

Concept 3 — Article 26 Deployer Duties and the Article 27 FRIA for 5(b)/5(c) Deployers


Article 26 sets the deployer's own duties: use the system per the provider's instructions;
assign human oversight to competent, trained personnel; ensure input data is relevant and
sufficiently representative for the intended purpose; monitor operation and report risks
to the provider or market surveillance authority; and keep the automatically generated
logs for at least six months (Article 26(6) — the deployer side of Day 4's retention
requirement). Article 27 adds a Fundamental Rights Impact Assessment (FRIA) requirement
that names BFSI explicitly: it is required for deployers that are bodies governed by
public law (or private operators providing public services), AND SEPARATELY for any
deployer of the Annex III point 5(b) or 5(c) systems this week's Day 1 covered — meaning a
bank or insurer deploying a credit-scoring or insurance-pricing system needs a FRIA
regardless of whether it is a public body at all.


Example:


ARTICLE_26_DEPLOYER_DUTIES = [
    "use the system per the provider's instructions",
    "assign human oversight to competent, trained personnel",
    "ensure input data is relevant and sufficiently representative for the intended purpose",
    "monitor operation and inform the provider/market surveillance authority of risks",
    "keep automatically generated logs for at least six months (Article 26(6))",
]

def requires_fria(annex_iii_point, is_public_body=False):
    if is_public_body:
        return True
    return annex_iii_point in ("5(b)", "5(c)")

bank_deployer_fria = requires_fria("5(b)")
insurer_deployer_fria = requires_fria("5(c)")
public_benefits_body_fria = requires_fria("5(a)", is_public_body=True)
private_non_5bc_fria = requires_fria("5(a)", is_public_body=False)

print(f"bank deploying 5(b) credit scoring: FRIA required = {bank_deployer_fria}")
print(f"insurer deploying 5(c) risk pricing: FRIA required = {insurer_deployer_fria}")
print(f"public body deploying 5(a) benefits eligibility: FRIA required = {public_benefits_body_fria}")
print(f"private non-public-body deploying 5(a): FRIA required = {private_non_5bc_fria}")
print(f"deployer duty count under Article 26: {len(ARTICLE_26_DEPLOYER_DUTIES)}")

Concept 4 — Article 53 GPAI Provider Duties, and Why Calling an API Doesn't Inherit Them


Article 53 obligates a general-purpose AI model provider — the company that built the
foundation model itself — to maintain technical documentation of the model, provide
integration documentation to downstream providers, maintain an EU-copyright-law compliance
policy, and publish a sufficiently detailed summary of the training content. A BFSI team
that calls a foundation model's API to build a RAG or agent application is a downstream
user of that model, not its provider, and Article 53's duties stay with the foundation-
model company. What DOES pull the downstream team into provider obligations is Concept 2's
Article 25 substantial-modification threshold — genuinely modifying the underlying model
itself (fine-tuning that changes its risk profile), not merely prompting it through an
API.


Example:


ARTICLE_53_GPAI_PROVIDER_DUTIES = [
    "maintain technical documentation of the general-purpose AI model",
    "provide information/documentation to downstream providers integrating the model",
    "put in place a policy to comply with EU copyright law",
    "publish a sufficiently detailed summary of the training content",
]

@dataclasses.dataclass
class DownstreamTeam:
    name: str
    calls_foundation_model_via_api: bool = False
    substantially_modifies_the_model_itself: bool = False

def inherits_gpai_provider_duties(team):
    return team.substantially_modifies_the_model_itself

typical_rag_team = DownstreamTeam(name="claims_rag_team", calls_foundation_model_via_api=True)
model_finetuning_team = DownstreamTeam(name="proprietary_finetune_team", calls_foundation_model_via_api=True, substantially_modifies_the_model_itself=True)

for team in (typical_rag_team, model_finetuning_team):
    print(f"{team.name}: inherits_Article_53_duties={inherits_gpai_provider_duties(team)}")

BFSI Reality Check — Day 2


Legacy angle: A bank that "just" wraps a decades-old mainframe underwriting engine in
a new AI-branded UI, without changing the underlying decision logic at all, is not
automatically a provider under Article 25 — the underlying engine was never an AI system
to begin with, and wrapping it in a UI is not the kind of substantial modification the
Article targets. The classification question is about the AI system's own risk profile,
not about how modern its packaging looks.


Compliance angle: Article 27's explicit naming of 5(b)/5(c) deployers means a mid-size
regional bank or insurer cannot assume FRIA is "a big-tech-and-government thing" — it is
required specifically because the deployer is a bank or insurer running a credit-scoring
or insurance-pricing system, independent of size or public/private status.


What breaks in production: A bank fine-tunes a vendor's fraud-detection model on its
own transaction data to improve recall, genuinely changing its false-positive/false-
negative tradeoff — a real, substantial modification under Article 25(1)(b) — but treats
itself as still just a "deployer" because it never rebranded the system. The bank has
silently become the system's provider for regulatory purposes and has taken on Article 16
provider obligations it isn't tracking, discovered only when an audit asks who the
provider of record is.

Concept 1 — Article 11 and the Annex IV Content List as a Repository-Resident Document


Article 11 requires a high-risk system's technical documentation to be drawn up before the
system is placed on the market, covering the content list Annex IV specifies: a general
description and intended purpose, design specifications, a description of training/
validation/testing data, the human oversight measures put in place, accuracy/robustness/
cybersecurity metrics, the risk management system, and a log of changes and versions. The
natural home for this is not a slide deck or a Word document living outside the codebase —
it is a structured document versioned in the same repository as the pipeline it describes,
checked programmatically for completeness the same way this track checks every other
lesson's structure.

Concept 2 — Article 10 Data Governance: Bias Examination and Dataset Provenance


Article 10 requires training, validation, and testing datasets to be subject to data
governance practices appropriate to the intended purpose, including examination for
possible biases likely to affect health, safety, or fundamental rights, and to be
relevant, sufficiently representative, and to the best extent possible free of errors.
Recording dataset provenance (source, collection date, and a demographic breakdown to
examine) is the concrete artifact that makes Article 10's "examination for bias" a real,
repeatable check rather than a one-time assertion — the same underrepresentation
computed here today should re-run cleanly against next quarter's retraining data.


Example:


@dataclasses.dataclass
class DatasetProvenance:
    dataset_name: str
    source: str
    collection_date: str
    demographic_breakdown: dict

def bias_examination(provenance, protected_group_key, minimum_share=0.05):
    total = sum(provenance.demographic_breakdown.values())
    flagged = []
    for group, count in provenance.demographic_breakdown.items():
        share = count / total
        if share < minimum_share:
            flagged.append((group, round(share, 4)))
    return flagged

training_set = DatasetProvenance(
    dataset_name="sme_credit_training_v4",
    source="internal_loan_book_2021_2025",
    collection_date="2026-01-15",
    demographic_breakdown={"group_a": 4200, "group_b": 3900, "group_c": 150},
)

flagged_groups = bias_examination(training_set, protected_group_key="region")
print(f"{training_set.dataset_name}: underrepresented groups = {flagged_groups}")

Concept 3 — Model and Dataset Cards Versioned in Git Next to the Pipeline Code


"Versioned in git next to the pipeline code" is not a metaphor — it means the technical
documentation's own change history is exactly the repository's real commit history for
that file, queryable the same way any code file's history is. This concept proves it
genuinely, not by assertion: it runs a real git log against this actual repository,
using the :/<path> pathspec so the lookup works regardless of which directory the
command runs from. The exact commit SHA and timestamp this returns vary as this
repository's history grows — only the FOUND/40-char-SHA shape below is stable.


Example:


import subprocess

def last_commit_for_path(repo_relative_path):
    result = subprocess.run(
        ["git", "log", "-1", "--format=%H %ci", "--", f":/{repo_relative_path}"],
        capture_output=True, text=True,
    )
    return result.stdout.strip()

model_card_path = "FDE_Fintech_Insurance/Week_14_PII_Masking_Presidio/W14_PII_Masking_Presidio.md"
last_commit = last_commit_for_path(model_card_path)
print(f"last commit touching {model_card_path.split('/')[-1]}: {'FOUND' if last_commit else 'NONE'}")
print(f"commit line has a real 40-char SHA: {len(last_commit.split()[0]) == 40 if last_commit else False}")

Concept 4 — Regenerating Documentation From Pipeline Metadata


A model card maintained by hand drifts from the pipeline it describes the moment someone
updates the model without remembering to update the card. Regenerating the card from the
pipeline's own structured metadata — the version string, training dataset name, and
measured accuracy already tracked elsewhere in the pipeline — makes staleness impossible
by construction: the card can never say something the metadata doesn't say, because it is
rendered from that metadata every time.


Example:


def render_model_card(metadata):
    lines = [f"# Model Card: {metadata['name']}", ""]
    lines.append(f"**Version:** {metadata['version']}")
    lines.append(f"**Intended purpose:** {metadata['intended_purpose']}")
    lines.append(f"**Training data:** {metadata['training_data']}")
    lines.append(f"**Accuracy (holdout):** {metadata['accuracy']}")
    return "\n".join(lines)

pipeline_metadata = {
    "name": "sme_credit_scorer",
    "version": "4.2.0",
    "intended_purpose": "Annex III 5(b) creditworthiness evaluation",
    "training_data": "sme_credit_training_v4",
    "accuracy": 0.891,
}

card_1 = render_model_card(pipeline_metadata)
card_2 = render_model_card(pipeline_metadata)
print(card_1)
print(f"regenerating from the same metadata is deterministic: {card_1 == card_2}")

Concept 1 — Article 12: Automatic Event Recording Across the System Lifetime


Article 12 requires a high-risk system to automatically record events ("logs") throughout
its lifetime, at a level that ensures the system's operation is traceable for its intended
purpose. "Throughout its lifetime" means every stage of a run, not a subset picked for
convenience — a log covering parse/chunk/embed/retrieve/generate but silently dropping the
guardrail check that actually decided whether to answer is not traceable in the sense
Article 12 means, even though most of the pipeline is covered.


Example:


import dataclasses

LIFECYCLE_STAGES = ["parse", "chunk", "embed", "retrieve", "generate", "guardrail_check", "deliver"]

@dataclasses.dataclass
class RunLifecycleLog:
    run_id: str
    stages_logged: list

def missing_lifecycle_stages(log):
    return [s for s in LIFECYCLE_STAGES if s not in log.stages_logged]

complete_run = RunLifecycleLog(run_id="run-042", stages_logged=list(LIFECYCLE_STAGES))
incomplete_run = RunLifecycleLog(run_id="run-043", stages_logged=["parse", "chunk", "embed", "retrieve", "generate"])

print(f"{complete_run.run_id}: missing = {missing_lifecycle_stages(complete_run)}")
print(f"{incomplete_run.run_id}: missing = {missing_lifecycle_stages(incomplete_run)}")

Concept 2 — Retention: Article 19 for Providers, Article 26(6) for Deployers


Both Article 19 (the provider's own logs) and Article 26(6) (logs a deployer keeps when
using a high-risk system under its own authority) set the same floor: at least six months,
unless other applicable Union or national law requires a longer period. Six months is a
minimum, not a target — a retention window one day short of that floor is non-compliant
regardless of how close it is.


Example:


import datetime

MINIMUM_RETENTION_DAYS = 6 * 30  # Article 19 / Article 26(6): "at least six months"

def retention_compliant(role, retention_period_days):
    return retention_period_days >= MINIMUM_RETENTION_DAYS

def log_deletion_eligible(log_timestamp, current_time, retention_period_days):
    age_days = (current_time - log_timestamp).days
    return age_days > retention_period_days

provider_retention = retention_compliant("provider", 210)
deployer_retention = retention_compliant("deployer", 150)

print(f"provider retaining 210 days: compliant = {provider_retention}")
print(f"deployer retaining 150 days: compliant = {deployer_retention}")

old_log_ts = datetime.datetime(2025, 1, 1)
now = datetime.datetime(2026, 9, 16)
eligible = log_deletion_eligible(old_log_ts, now, retention_period_days=180)
print(f"a log from {old_log_ts.date()} evaluated on {now.date()} against a 180-day retention: deletion_eligible = {eligible}")

Concept 3 — The Event Schema: Input, Retrieved Context, Model Version, Verdict, Outcome


A log event that satisfies Article 12's "ensures traceability" test in a RAG-agent context
needs a specific, non-negotiable set of fields: the input that triggered the run, the
retrieved context it was grounded in, the exact model version that generated the response,
the guardrail verdict that gated it, and the final outcome. Missing any one of these
breaks a specific kind of audit question — no retrieved-context IDs means "what did it
actually cite" is unanswerable after the fact, regardless of how complete every other
field is.


Example:


@dataclasses.dataclass

    input_summary: str
    retrieved_context_ids: list
    model_version: str
    guardrail_verdict: str
    outcome: str

REQUIRED_EVENT_FIELDS = ["run_id", "input_summary", "retrieved_context_ids", "model_version", "guardrail_verdict", "outcome"]

def validate_log_event_schema(raw_event: dict):

Concept 4 — Reusing Week 16's Lineage Emission as the Logging Substrate


Building a second, parallel logging system for Article 12 compliance next to Week 16's
OpenLineage lineage emission would mean every future pipeline change has to be kept in
sync in two places. Instead, this concept genuinely reuses Week 16 Day 2 Concept 2's
emit_stage_run context manager — copied in here, unchanged in its START/COMPLETE-or-FAIL
mechanics — and attaches this week's compliance fields as a custom RunFacet subclass
carried on the SAME Run object Week 16 already emits. One emission call now serves both
Week 16's "where did this answer's source data come from" question and this week's
Article 12 "what happened during this run" question. ConsoleTransport logs its JSON
through Python's logging module (to stderr, not captured below); the code prints a
UUID-shape check on the real run_id rather than the raw value, since that value is
genuinely different on every run and printing it directly would make this block's
documented output non-reproducible.


Example:


import contextlib
import logging

import attr
from openlineage.client import OpenLineageClient
from openlineage.client.transport.console import ConsoleConfig, ConsoleTransport
from openlineage.client.run import Job, Run, RunEvent, RunState
from openlineage.client.uuid import generate_new_uuid
from openlineage.client.facet_v2 import RunFacet

logging.basicConfig(level=logging.INFO, format="%(message)s")
compliance_client = OpenLineageClient(transport=ConsoleTransport(ConsoleConfig()))

@attr.define
class AIActEventFacet(RunFacet):
    input_summary: str = ""
    retrieved_context_ids: list = attr.field(factory=list)
    model_version: str = ""
    guardrail_verdict: str = ""
    outcome: str = ""

@contextlib.contextmanager
def emit_stage_run(client, job_namespace, job_name, producer="fde-finserv-dataprep", run_facets=None):
    # Reusing Week 16 Day 2 Concept 2's emit_stage_run pattern, adapted here to
    # carry Article 12 record-keeping fields rather than just lineage facets.
    run_id = str(generate_new_uuid())
    run = Run(runId=run_id, facets=run_facets or {})
    job = Job(namespace=job_namespace, name=job_name)
    client.emit(RunEvent(
        eventType=RunState.START,
        eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
        run=run, job=job, producer=producer,
    ))
    try:
        yield run_id
    except Exception:
        client.emit(RunEvent(
            eventType=RunState.FAIL,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))
        raise
    else:
        client.emit(RunEvent(
            eventType=RunState.COMPLETE,
            eventTime=datetime.datetime.now(datetime.timezone.utc).isoformat(),
            run=run, job=job, producer=producer,
        ))

ai_act_facet = AIActEventFacet(
    input_summary="customer asked about claim CLM-88213 status",
    retrieved_context_ids=["chunk-101", "chunk-104"],
    model_version="claims-agent-v3.2",
    guardrail_verdict="safe",
    outcome="answered",
)

with emit_stage_run(compliance_client, "fde.finserv.compliance", "claims_agent_turn", run_facets={"aiActRecord": ai_act_facet}) as run_id:
    print(f"compliance turn logged: run_id is a real UUID = {len(run_id) == 36}")

print("the SAME emit_stage_run mechanism serves both lineage (Week 16) and Article 12 logging (this week): True")

Concept 1 — Article 14: Interpretability, Automation-Bias Awareness, and Intervene-or-Stop


Article 14(4) lists five specific oversight measures a provider must enable a deployer to
implement: understanding the system's capacities and limitations while monitoring for
anomalous behavior; remaining aware of the tendency to automatically over-rely on system
output ("automation bias") — the Act names this risk explicitly, it is not a vague
platitude; correctly interpreting output given available interpretation tools and their
limits; being able to decide not to use, or to disregard, reverse, or override the output
in a specific case; and being able to intervene in or stop the system's operation through
a stop button or equivalent procedure. A system with a polished UI that never actually
lets a human override or stop it satisfies none of the measures that matter most.


Example:

Concept 2 — Article 15: Declared Accuracy, Robustness, and Cybersecurity


Article 15 requires a high-risk system to achieve, and be designed to consistently
perform at, an appropriate level of accuracy, robustness, and cybersecurity throughout
its lifecycle, with the levels declared in the accompanying instructions of use. "Declared
and consistently performs at" is a testable claim, not a marketing statement — a system
whose measured accuracy has drifted meaningfully below what was declared is failing
Article 15 even if nothing else about it changed.


Example:


@dataclasses.dataclass
class RobustnessDeclaration:
    system_name: str
    declared_accuracy: float
    measured_accuracy: float
    robustness_test_passed: bool
    cybersecurity_controls: list

def performs_consistently_with_declaration(decl, tolerance=0.02):
    return abs(decl.measured_accuracy - decl.declared_accuracy) <= tolerance

sme_scorer_decl = RobustnessDeclaration(
    system_name="sme_credit_scorer",
    declared_accuracy=0.89,
    measured_accuracy=0.891,
    robustness_test_passed=True,
    cybersecurity_controls=["input_validation", "adversarial_perturbation_testing", "model_access_logging"],
)
drifted_decl = RobustnessDeclaration(
    system_name="fraud_scoring_v3",
    declared_accuracy=0.95,
    measured_accuracy=0.87,
    robustness_test_passed=True,
    cybersecurity_controls=["input_validation"],

Concept 3 — Oversight as an Explicit Pipeline Approval Step, Not a UI Afterthought


The right place to implement Article 14(4)(d)/(e)'s override-and-stop capability is a
hard gate the pipeline code itself enforces before a high-stakes action executes — not a
UI button that a backend function ignores if nobody happens to click it. This concept
builds that gate as a function that raises unless it receives an explicit, non-None
approval token, so "was this approved" is a precondition the code refuses to skip, not a
step a caller can silently bypass by not wiring up the UI.


Example:


class ApprovalRequiredError(Exception):
    pass

def execute_high_stakes_action(action_name, approval_token):
    if approval_token is None:
        raise ApprovalRequiredError(f"'{action_name}' requires an explicit human approval token before executing")
    return f"executed: {action_name} (approved by {approval_token})"

try:
    execute_high_stakes_action("decline_sme_loan_application", approval_token=None)
except ApprovalRequiredError as e:
    print(f"blocked without approval: {e}")

result = execute_high_stakes_action("decline_sme_loan_application", approval_token="underwriter_jsmith")
print(result)

Concept 4 — Cross-Referenced Local Analogs: SR 11-7, the NAIC Model Bulletin, Israeli PPL Amendment 13


None of Article 14's measures exist in a vacuum for a BFSI team already operating under
other regimes: US SR 11-7 already requires effective challenge and avoiding undue
deference to model output (echoing automation-bias awareness); the NAIC Model Bulletin on
the use of AI by insurers requires monitoring and human override capability; and Israeli
Privacy Protection Law Amendment 13 grants a right to human review of an automated
decision. These are real, named cross-references, not a comprehensive one-to-one mapping
— some Article 14 measures have a local analog in all three regimes, some in only one,
and at least one (correct_interpretation) has none of these three as a direct analog at
all, which this concept's own lookup function surfaces honestly rather than papering over.


Example:


CROSS_REFERENCED_ANALOGS = {
    "monitor_capabilities_limitations": {
        "sr_11_7": "SR 11-7 Section III: ongoing monitoring of model performance against expectations",
        "naic_model_bulletin": "NAIC Model Bulletin Section 4(A): insurer AI system governance and monitoring",
        "israeli_ppl_amendment_13": "Amendment 13 Section 8: monitoring obligations for automated decision systems",
    },
    "automation_bias_awareness": {
        "sr_11_7": "SR 11-7 Section IV: effective challenge, avoiding undue deference to model output",
        "naic_model_bulletin": "NAIC Model Bulletin Section 4(B): avoiding overreliance on AI-generated recommendations",
        "israeli_ppl_amendment_13": None,
    },
    "intervene_or_stop": {
        "sr_11_7": None,
        "naic_model_bulletin": "NAIC Model Bulletin Section 4(C): human override capability for adverse AI-driven decisions",
        "israeli_ppl_amendment_13": "Amendment 13 Section 9: right to human review of an automated decision",

}

def local_analogs_for(measure_key):
    return {k: v for k, v in CROSS_REFERENCED_ANALOGS.get(measure_key, {}).items() if v is not None}

for measure in ("monitor_capabilities_limitations", "automation_bias_awareness", "intervene_or_stop"):
    analogs = local_analogs_for(measure)
    print(f"{measure}: {len(analogs)} local analog(s) -> {sorted(analogs.keys())}")

BFSI Reality Check — Day 5


Legacy angle: A twenty-year-old mainframe underwriting system already has an
operator-facing override screen that predates the AI Act by decades — Article 14(4)(d)/(e)
does not require reinventing that control, it requires confirming the AI-driven layer
sitting in front of it doesn't quietly bypass the same override path the legacy system
already had.


Compliance angle: SR 11-7's "effective challenge" concept and Article 14(4)(b)'s
automation-bias awareness are close enough in intent that a US-regulated bank's existing
model-risk-management program is real, reusable groundwork for AI Act compliance — not a
parallel program to build from scratch.


What breaks in production: A claims-triage system's UI has a prominent "Override"
button, satisfying Article 14 on a demo. In production, the button calls a function that
silently no-ops because nobody wired it to the actual decision pipeline after a refactor
six sprints ago — Concept 3's hard-gate pattern (raise unless a real approval token is
present) exists precisely because a UI affordance that isn't backed by an enforced
precondition can drift into looking compliant while doing nothing.




Architecture Decision — Week 17


Choosing between: treating EU AI Act compliance as a static legal-review document
maintained outside the codebase, versus building each obligation this week covered
(classification, provider/deployer role, documentation, logging, oversight) as executable
checks wired directly into the pipeline the way every other control in this track has
been built.


Rule of thumb: any obligation with objective, checkable criteria — Annex III
membership, the Article 19/26(6) retention floor, the Article 12 event schema, the
Article 14(4) measure checklist — belongs in code, exactly like this week's classify_ annex_iii_point_5, retention_compliant, validate_log_event_schema, and missing_ oversight_measures functions, because a static document describing these checks drifts
from reality the moment the pipeline changes and nobody remembers to re-read the document.
But the genuinely judgment-dependent calls — does this system really meet an Article 6(3)
narrow-task condition, does this change really cross Article 25's substantial-
modification threshold — must never be auto-resolved by code pretending to have legal
judgment it doesn't have. The right shape is code that SURFACES the question and requires
a recorded human decision (the same DerogationAssessment.documented_before_market field
Day 1 built, the same approval_token precondition Day 5 Concept 3 enforces) rather than
code that silently decides the answer either way. Move a check from "human judgment call"
to "automated code check" only when the underlying legal criterion is itself objective
enough that two different reviewers would reliably reach the same answer — the moment that
stops being true, the check belongs back with a person, recorded, not guessed by a
function.
