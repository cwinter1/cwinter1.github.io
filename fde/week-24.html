Concept 1 — Rewriting Underspecified Servicing Questions

A real servicing question rarely arrives retrieval-ready. A policyholder types "can I still get money back" — three words of actual signal (money, back, still) with almost no overlap against the policy clause that answers it ("free look period... full premium refund... within 10 days of issue"). An LLM query-rewrite step takes the underspecified question plus a short instruction ("rewrite this insurance servicing question to be specific and retrieval-ready") and produces a version that shares real vocabulary with the target clause — that rewrite call itself needs a live LLM this sandbox does not have, so the three rewritten queries below are hand-written stand-ins for what that call would produce, disclosed honestly rather than presented as a live generation. What IS built and run for real is the retrieval mechanics on both sides: a small BFSI corpus, a bag-of-words cosine retriever over a fixed insurance vocabulary (the same toy-embedding stand-in pattern Week 23 used, standing in for a real embedding API), and recall@k computed before and after rewriting on a fixed 3-question set.

Example:

import math

def tokenize(text):
    return text.lower().replace(",", " ").replace(".", " ").split()

VOCAB = {
    "free", "look", "period", "cancel", "cancellation", "refund", "premium", "return",
    "days", "reinstate", "reinstatement", "lapse", "lapsed", "grace", "deductible",
    "waive", "waiver", "beneficiary", "change", "claim", "rider", "endorsement",
    "underwriting", "medical", "exam", "glass", "windshield", "crack", "chip", "repair",
    "comprehensive", "coverage", "towing", "rock", "roadside", "rental", "reimbursement",
}

def bow(text):
    toks = tokenize(text)
    return {t: toks.count(t) for t in toks if t in VOCAB}

def cosine(v1, v2):
    common = set(v1) & set(v2)
    dot = sum(v1[t] * v2[t] for t in common)
    n1 = math.sqrt(sum(x * x for x in v1.values())) or 1.0
    n2 = math.sqrt(sum(x * x for x in v2.values())) or 1.0
    return dot / (n1 * n2)

# One corpus, reused for every concept in this day. This BOW-cosine retriever stands in
# for a real embedding-model + vector-index pair -- the retrieval MECHANICS below
# (ranking, recall@k) are the same regardless of what produces the vectors.
CORPUS = [
    ("DOC-B", "Roadside assistance: towing, flat tire changes, and lockout service are included at no extra premium under the standard auto rider."),
    ("DOC-C", "Rental reimbursement: a daily rental car allowance applies while a covered vehicle is in the shop after an approved claim."),
    ("DOC-5", "Grace period for premium payment: coverage stays active for 31 days past the due date before the policy lapses for nonpayment."),
    ("DOC-4", "Deductible waiver rider: this rider waives the standard deductible for the first claim filed after the rider's effective date."),
    ("DOC-A", "Auto glass coverage: chip and crack repair to the windshield or any vehicle glass is covered in full with no deductible under the standard comprehensive endorsement, regardless of how the damage occurred."),
    ("DOC-1", "Free look period: a new auto policy may be canceled within 10 days of issue for a full premium refund, no questions asked."),
    ("DOC-2", "Reinstatement after lapse: a lapsed policy can be reinstated within 90 days of lapse if all past-due premium is paid, without new underwriting."),
    ("DOC-3", "Beneficiary changes: the policyholder may change the named beneficiary at any time before a claim is filed, using the standard change-of-beneficiary form."),
]

def retrieve(query_text, k=3):
    qv = bow(query_text)
    scored = [(doc_id, cosine(qv, bow(text))) for doc_id, text in CORPUS]
    scored.sort(key=lambda x: -x[1])
    return scored[:k]

def recall_at_k(ranked_ids, relevant_id, k):
    return 1.0 if relevant_id in ranked_ids[:k] else 0.0

# REAL MODE: in production these three "rewritten" strings come from a live LLM call
# (e.g. `llm.invoke(REWRITE_PROMPT.format(question=underspecified))`). Hand-written here
# as honest stand-ins for that call's output, not measured from a live generation.
fixed_query_set = [
    ("can I still get money back",
     "what is the refund available for canceling a new auto policy within the free look period",
     "DOC-1"),
    ("my policy stopped, can I fix it",
     "how do I reinstate a policy that lapsed due to nonpayment",
     "DOC-2"),
    ("can I switch who gets paid",
     "how do I change the named beneficiary on my policy",
     "DOC-3"),
]

under_scores, rewritten_scores = [], []
for under, rewritten, rel in fixed_query_set:
    u_ids = [d for d, _ in retrieve(under, 3)]
    r_ids = [d for d, _ in retrieve(rewritten, 3)]
    u = recall_at_k(u_ids, rel, 3)
    r = recall_at_k(r_ids, rel, 3)
    under_scores.append(u)
    rewritten_scores.append(r)
    print(f"relevant={rel}  underspecified_recall@3={u:.2f}  rewritten_recall@3={r:.2f}")

print(f"mean recall@3: underspecified={sum(under_scores)/3:.3f}  rewritten={sum(rewritten_scores)/3:.3f}")

Concept 2 — HyDE: Hypothetical Document Embeddings


Query rewriting still embeds a QUESTION. HyDE (Hypothetical Document Embeddings) instead
asks an LLM to write a plausible ANSWER to the question — a fake but topically fluent
document — and embeds THAT instead of the question. The intuition: a real policy clause
is written in answer-shaped prose ("Yes, this is covered... under the endorsement..."),
not question-shaped prose ("is this covered?"), so a hypothetical answer document often
sits closer in embedding space to the real clause than the literal question ever would —
even though the hypothetical document is entirely fabricated and never actually
retrieved or shown to the user. Generating that hypothetical document is the one step
here that genuinely needs a live LLM; disclosed as REAL MODE below. What's real and run
is the retrieval comparison: the same underspecified question embedded directly vs. the
hand-written hypothetical document embedded in its place, against the same corpus and
retriever from Concept 1.


Example:


# Reusing retrieve, recall_at_k, CORPUS from Concept 1

narrow_query = "is a little ding on my window something my plan pays for"

# REAL MODE: in production this comes from `llm.invoke(HYDE_PROMPT.format(question=narrow_query))`.
# Hand-written here as an honest stand-in for that generation, not a live LLM call.
hypothetical_doc = (
    "Yes, this type of damage is covered. Windshield chip and crack repair from road "
    "debris is included under the auto glass coverage endorsement, with no deductible "
    "applied regardless of how the chip occurred, whether from a rock, gravel, or debris."
)

direct_top = [d for d, _ in retrieve(narrow_query, 3)]
hyde_top = [d for d, _ in retrieve(hypothetical_doc, 3)]

print("direct query top-3:", direct_top, " recall@3:", recall_at_k(direct_top, "DOC-A", 3))
print("HyDE top-3:        ", hyde_top, " recall@3:", recall_at_k(hyde_top, "DOC-A", 3))

Concept 3 — Step-Back Prompting for Policy-Clause Questions


Step-back prompting takes the opposite move from rewriting: instead of making a question
MORE specific, it asks the LLM to generalize a narrow, clause-level question into the
broader topic it belongs to, retrieves against the broad topic, then answers the narrow
question using whatever context comes back. This helps when the narrow question's exact
phrasing ("a cracked windshield caused by debris during towing") pulls in the WRONG
narrowly-related document (here, the roadside-towing clause, because "towing" is a strong
literal match) instead of the actually-relevant general clause (the glass-coverage rider,
which covers the damage regardless of how it happened). The step-back rewrite is the
LLM-generation step here — REAL MODE, hand-written below — while the retrieval
comparison at k=1 (a tighter cutoff than Concepts 1-2, chosen because this failure mode
is specifically about what wins at rank 1) is real, executed code.


Example:


# Reusing retrieve, recall_at_k, CORPUS from Concept 1

narrow_clause_query = "does the rider cover a cracked windshield caused by debris during towing"
# REAL MODE: in production this comes from `llm.invoke(STEP_BACK_PROMPT.format(question=narrow_clause_query))`.
step_back_query = "what does the auto glass coverage rider cover in general"

stepback_top1 = [d for d, _ in retrieve(step_back_query, 1)]

print("direct clause query top-1:", direct_top1, " recall@1:", recall_at_k(direct_top1, "DOC-A", 1))
print("step-back query top-1:    ", stepback_top1, " recall@1:", recall_at_k(stepback_top1, "DOC-A", 1))

BFSI Reality Check — Day 1


Legacy angle: an underspecified question is not a training-data gap to fix once — it
is the permanent shape of how policyholders actually type into a chat box, so rewriting
has to run on every single query at inference time, adding one more LLM call (and its
latency and cost, see Week 23) to a path that used to be a single embedding call.


Compliance angle: a rewrite or HyDE-generated hypothetical document is never shown to
the end user, but it IS the thing that actually determined what context the model saw —
an audit trail for a disputed claims answer that logs only the original question and the
final answer, with no record of the rewritten query or hypothetical document in between,
cannot actually explain why the wrong (or right) clause was retrieved.


What breaks in production: a rewrite prompt tuned against the vocabulary of ONE
policy line (auto) silently degrades on another (life, or commercial property) whose
clause vocabulary the prompt's few-shot examples never covered — rewrite quality is a
per-product-line variable, not a track-wide constant, and Day 5's bake-off methodology
(measuring lift on a labeled set, not assuming it) is exactly how that degradation gets
caught before it reaches production.

Concept 1 — LangChain MultiQueryRetriever: n Query Variants, One Union


MultiQueryRetriever asks an LLM to write several differently-phrased variants of one
question, retrieves each variant separately, then merges the result lists. langchain
1.4.1's own 1.0 restructure moved this class (and ParentDocumentRetriever,
SelfQueryRetriever, InMemoryStore) out of the core langchain package into a separate
langchain-classic package, confirmed directly in this sandbox — from langchain.retrievers import MultiQueryRetriever raises ModuleNotFoundError on this version; the working
import is from langchain_classic.retrievers.multi_query import MultiQueryRetriever. The
LLM call that actually WRITES the n variants is MultiQueryRetriever.generate_queries() —
REAL MODE, since it needs a live LLM — but everything downstream of that call is real,
installed, executable langchain_classic code: a real InMemoryVectorStore retriever
built on the deterministic KeywordBucketEmbeddings stand-in (in place of a live embedding
API), and the retriever's own retrieve_documents()/unique_union() methods called
directly against 3 hand-written variants standing in for a live generation.


Example:


import math, hashlib
from langchain_core.embeddings import Embeddings
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_core.documents import Document
from langchain_core.callbacks import CallbackManagerForRetrieverRun
from langchain_core.runnables import RunnableLambda
from langchain_classic.retrievers.multi_query import MultiQueryRetriever

KEYWORDS = ["deductible", "premium", "claim", "policy", "underwriting", "exclusion",
            "coverage", "lapse", "renewal", "rider", "beneficiary", "grace"]

class KeywordBucketEmbeddings(Embeddings):
    def _vec(self, text):
        t = text.lower()
        v = [float(t.count(k)) for k in KEYWORDS]
        h = int(hashlib.sha256(t.encode()).hexdigest(), 16)
        for i in range(8):
            v.append(((h >> (i * 4)) % 7) / 7.0)
        norm = math.sqrt(sum(x * x for x in v)) or 1.0
        return [x / norm for x in v]
    def embed_documents(self, texts):
        return [self._vec(t) for t in texts]
    def embed_query(self, text):
        return self._vec(text)

docs = [
    Document(page_content="Grace period: premium not paid within 31 days causes lapse.", metadata={"chunk_id": "c1"}),
    Document(page_content="Reinstatement after lapse requires payment of past-due premium within 90 days.", metadata={"chunk_id": "c2"}),
    Document(page_content="Beneficiary designation can be changed any time before a claim is filed.", metadata={"chunk_id": "c3"}),
    Document(page_content="Deductible resets each policy year on the renewal date.", metadata={"chunk_id": "c4"}),
]

vs = InMemoryVectorStore(KeywordBucketEmbeddings())
vs.add_documents(docs)
base_retriever = vs.as_retriever(search_kwargs={"k": 4})

# llm_chain would normally be `prompt | llm | LineListOutputParser()` (see
# MultiQueryRetriever.from_llm()) -- stubbed with a no-op Runnable here since we supply
# pre-generated variants directly below instead of making a live LLM call.
stub_llm_chain = RunnableLambda(lambda x: [])
mqr = MultiQueryRetriever(retriever=base_retriever, llm_chain=stub_llm_chain, include_original=False)

# calling a live LLM. Hand-written here as honest stand-ins for that generation.

Concept 2 — Reciprocal Rank Fusion, k=60


Reciprocal Rank Fusion (RRF) is the standard way to turn several ranked lists into one:
for each list a document appears in, add 1 / (k + rank) to its running score, where
rank is its 1-indexed position in that list and k=60 is the conventional damping
constant — large enough that rank 1 vs. rank 2 in one list is not overwhelmingly more
valuable than appearing consistently across several lists. A document ranked #1 in
exactly one variant's results can still lose to one ranked #2-#3 in every variant,
because consistency across rephrasings is itself a relevance signal unique_union throws
away.

# Reusing query_variants, base_retriever from Concept 1

# Adapted from Curriculum/Week_10_AI_Engineering/W10_D5b_RAG_Advanced.ipynb CONCEPT 4
# (this week's ROADMAP.md-mandated copy-in), unchanged except the docstring.
def reciprocal_rank_fusion(ranked_lists, k=60):
    """RRF: doc score = sum of 1/(k + rank) across every list it appears in."""
    scores = {}
    for ranked_list in ranked_lists:
        for rank, doc_id in enumerate(ranked_list, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

# unique_union above threw away per-variant RANK -- RRF needs the ranked lists themselves,
# so retrieve each variant's ranking separately (chunk_id, not the Document object, is
# what RRF scores -- the same field Concept 4 dedupes on).
per_variant_rankings = []
for variant in query_variants:
    ranked = base_retriever.invoke(variant)
    per_variant_rankings.append([d.metadata["chunk_id"] for d in ranked])

for variant, ranking in zip(query_variants, per_variant_rankings):
    print(f"  {variant[:45]:<45} -> {ranking}")

fused = reciprocal_rank_fusion(per_variant_rankings, k=60)
print("\nfused ranking (RRF, k=60):")
for chunk_id, score in fused:
    print(f"  {chunk_id}: fused_score={score:.4f}")

Concept 3 — Fusing BM25 and Dense Result Lists


RRF does not care WHAT produced a ranked list — it only needs a list of doc IDs in rank
order. That means it fuses fundamentally different retrieval methods just as easily as it
fused three paraphrases of one dense query: a lexical BM25 ranking (exact term overlap —
strong on an exact policy-form name or claim number, blind to paraphrases) and a dense
semantic ranking (the opposite trade-off) fuse into one list with no method-specific
weighting logic required, unlike the weighted-sum hybrid score Concept 1 of the copied-in
notebook used.

that file's function unchanged.

def bm25_score(query_terms, doc_terms, corpus_doc_terms, k1=1.5, b=0.75):
    """BM25: the standard lexical relevance score behind classic keyword search."""
    N = len(corpus_doc_terms)
    avgdl = sum(len(d) for d in corpus_doc_terms) / N
    doc_len = len(doc_terms)
    score = 0.0
    for term in set(query_terms):
        n_docs_with_term = sum(1 for d in corpus_doc_terms if term in d)
        if n_docs_with_term == 0:
            continue
        idf = math.log((N - n_docs_with_term + 0.5) / (n_docs_with_term + 0.5) + 1)
        tf = doc_terms.count(term)
        denom = tf + k1 * (1 - b + b * doc_len / avgdl)
        score += idf * (tf * (k1 + 1)) / denom
    return score

def tokenize(text):
    return text.lower().replace(",", " ").replace(".", " ").split()

Concept 4 — Dedupe by chunk_id Before Scoring


RRF's formula assumes each ranked list contains a document AT MOST ONCE. A retriever bug
(overlapping chunk boundaries producing two chunks that share one chunk_id, a variant
that legitimately retrieves the same chunk twice because a smaller top-k window wrapped
around) breaks that assumption silently — RRF adds 1/(k+rank) once per OCCURRENCE, so a
chunk that appears twice in one list gets double-counted and can out-rank a chunk that
genuinely deserves to win. Deduping each per-list ranking by chunk_id, keeping only the
first (best-ranked) occurrence, before fusion is the fix.


Example:


# Reusing reciprocal_rank_fusion from Concept 2

def dedupe_ranked_list(ranked_list):
    seen = set()
    deduped = []
    for chunk_id in ranked_list:
        if chunk_id not in seen:
            seen.add(chunk_id)
            deduped.append(chunk_id)
    return deduped

# A retriever that returns the SAME chunk at two different ranks across two variants
# (e.g. a document-splitting bug that produced overlapping chunks with the same id) would
# otherwise let RRF double-count it purely because it appears twice in one list.
noisy_list_a = ["c1", "c1", "c2", "c4"]
noisy_list_b = ["c2", "c3", "c1"]

print("before dedupe, RRF over noisy lists:")
for chunk_id, score in reciprocal_rank_fusion([noisy_list_a, noisy_list_b], k=60):
    print(f"  {chunk_id}: fused_score={score:.4f}")

deduped_a = dedupe_ranked_list(noisy_list_a)
deduped_b = dedupe_ranked_list(noisy_list_b)
print("\nafter dedupe, RRF over cleaned lists:")
for chunk_id, score in reciprocal_rank_fusion([deduped_a, deduped_b], k=60):
    print(f"  {chunk_id}: fused_score={score:.4f}")

Concept 1 — LangChain ParentDocumentRetriever: Small-to-Big


A chunk small enough to embed precisely is often too small to ANSWER a question in full —
a 120-character child chunk might match a query's vocabulary exactly while cutting off the
sentence that actually states the number the user needs. "Small-to-big" splits every
document twice: once into small CHILD chunks that go into the vector index (what gets
SEARCHED), and once into larger PARENT chunks kept in a separate docstore keyed by
parent_id (what gets RETURNED for generation). ParentDocumentRetriever wires this up
directly: it searches the child index, then swaps each hit for its full parent before
returning results — real, installed langchain_classic code, no live LLM required for any
of it.


Example:


import hashlib, math

from langchain_text_splitters import RecursiveCharacterTextSplitter

KEYWORDS = ["deductible", "premium", "claim", "policy", "underwriting", "exclusion",
            "coverage", "endorsement", "lapse", "renewal", "rider", "beneficiary",
            "waiver", "waive"]

class KeywordBucketEmbeddings(Embeddings):
    def _vec(self, text):
        t = text.lower()
        v = [float(t.count(k)) for k in KEYWORDS]
        h = int(hashlib.sha256(t.encode()).hexdigest(), 16)
        for i in range(8):
            v.append(((h >> (i * 4)) % 7) / 7.0)
        norm = math.sqrt(sum(x * x for x in v)) or 1.0
        return [x / norm for x in v]
    def embed_documents(self, texts):
        return [self._vec(t) for t in texts]
    def embed_query(self, text):
        return self._vec(text)

SINGLE sentence (maximally precise for matching), but every node's metadata carries a

small-search/large-generate trade Concept 1 made at the chunk level, applied at the

Concept 3 — LlamaIndex AutoMergingRetriever


HierarchicalNodeParser splits a document into MULTIPLE chunk-size tiers at once (e.g.
400-char sections, each further split into ~100-char leaves), with every node tracking its
parent. AutoMergingRetriever wraps a normal leaf-level retriever: if enough of one
parent's children come back in a single query's results, it MERGES them back into that
parent and returns the merged node instead of several disconnected fragments — small-to-
big, but decided dynamically per query based on how much of one section actually matched,
rather than always returning the whole parent the way Concept 1's retriever does.


Example:

        return self._vec(query)
    async def _aget_query_embedding(self, query):
        return self._vec(query)
    def _get_text_embedding(self, text):
        return self._vec(text)
    def _vec(self, text):
        kws = ["deductible", "premium", "claim", "policy", "underwriting", "lapse"]
        t = text.lower()
        v = [float(t.count(k)) for k in kws]
        h = int(hashlib.sha256(t.encode()).hexdigest(), 16)
        for i in range(6):
            v.append(((h >> (i * 4)) % 7) / 7.0)
        n = math.sqrt(sum(x * x for x in v)) or 1.0
        return [x / n for x in v]

Concept 4 — Parent Pointers as pgvector Metadata Columns


ParentDocumentRetriever and AutoMergingRetriever both keep the parent/child link in an
in-process docstore. A production pgvector deployment keeps the SAME link as an ordinary
metadata column instead: every CHILD chunk's row carries its own embedding plus a
parent_id column, and "return the parent" becomes a second SQL lookup (SELECT ... WHERE doc_id = ANY(:parent_ids)) rather than an in-memory dict access. Building the row schema
and the child→parent lookup is genuine, executable Python; the actual INSERT/SELECT
against a live Postgres instance needs a database this sandbox does not have, shown
further below as reference syntax only, once this Example's real Python has run.


Example:


KEYWORDS_4 = ["deductible", "premium", "claim", "policy", "underwriting", "lapse", "rider"]

def embed_4(text):
    t = text.lower()
    v = [float(t.count(k)) for k in KEYWORDS_4]
    h = int(hashlib.sha256(t.encode()).hexdigest(), 16)
    for i in range(4):
        v.append(((h >> (i * 4)) % 7) / 7.0)
    norm = math.sqrt(sum(x * x for x in v)) or 1.0
    return [x / norm for x in v]

def build_pgvector_rows(parent_id, child_chunks):
    return [
        {"child_id": f"{parent_id}-child-{i}", "parent_id": parent_id,
         "embedding": embed_4(chunk_text), "content": chunk_text}
        for i, chunk_text in enumerate(child_chunks)
    ]

def cosine_4(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a)) or 1.0
    nb = math.sqrt(sum(x * x for x in b)) or 1.0
    return dot / (na * nb)

def query_top_parents(rows, query_text, k=2):
    qv = embed_4(query_text)
    scored = sorted(rows, key=lambda r: -cosine_4(qv, r["embedding"]))[:k]
    seen = []
    for r in scored:
        if r["parent_id"] not in seen:
            seen.append(r["parent_id"])
    return seen

pol_1001_children = [
    "SECTION 4: DEDUCTIBLES. Applies once per claim year.",
    "A deductible of 500 USD applies to collision claims.",
    "A deductible of 250 USD applies to comprehensive claims.",
]
pol_1002_children = [
    "SECTION 7: LAPSE. Coverage lapses after 31 days unpaid.",
    "Reinstatement within 90 days needs no new underwriting.",

rows = build_pgvector_rows("POL-1001", pol_1001_children) + build_pgvector_rows("POL-1002", pol_1002_children)
print("total rows:", len(rows), " columns:", sorted(rows[0].keys()))
print("top distinct parent_ids for the query:",
      query_top_parents(rows, "how much do I pay out of pocket for a collision claim"))

BFSI Reality Check — Day 3


Legacy angle: a parent-child index effectively doubles what a pipeline stores — the
child chunks for search AND the parent chunks (or, for pgvector, the parent document
table) for generation — which is a real storage and sync cost a single-chunk-size index
never had to budget for, and one more place a re-ingestion job can leave the two sides out
of step with each other.


Compliance angle: when an answer traces back to a MERGED parent section rather than
the specific child chunk that actually matched, an audit trail needs to record which
child(ren) triggered the merge, not just the final parent text handed to the model —
otherwise a reviewer asking "why was this section retrieved" has no way to see which
sentence inside it actually caused the match.


What breaks in production: Day 5's bake-off (see Concept 1's own finding there) shows
parent-child chunking gives NO measurable lift on short, single-topic documents — its
value is specifically on long, multi-clause sections where a full-document embedding would
otherwise dilute a specific clause's signal; deploying it as a blanket default across every
document type in a corpus, regardless of document length, spends the extra storage and
sync cost in places it buys nothing.

Concept 1 — Declaring a Metadata Schema and Translating a Structured Predicate


SelfQueryRetriever needs to know, in advance, WHICH metadata fields it is allowed to
filter on and what each one means — that declaration is a real, installed
langchain_classic object (AttributeInfo), not something the LLM invents on the fly.
Given that schema, the retriever's LLM step translates a natural-language question like
"claims after 2023 above 50k in New York" into a StructuredQuery whose filter is a real
langchain_core.structured_query.Operation/Comparison tree — the exact objects
Operation/Comparison prototyped in Day 1's design work, used here for real. Turning
that tree into something a vector store can actually apply is the job of a Visitor
subclass — every real per-store translator (PGVectorTranslator, ChromaTranslator, etc.
in langchain_community) is one; a minimal one is built and run below, genuinely
subclassing langchain_core.structured_query.Visitor, needing no live vector store at all.
The one step that genuinely needs a live LLM is the NL→StructuredQuery translation
itself — that step needs a live LLM this sandbox doesn't have, so it is hand-built as an
honest stand-in inside the example below (flagged with an inline comment at that exact
line, not up here).

class SimpleFilterTranslator(Visitor):
    """A minimal real Visitor implementation (the same pattern langchain_community's
    per-vectorstore translators, e.g. PGVectorTranslator, implement) that walks a
    StructuredQuery's filter tree into a plain Python predicate function."""
    allowed_comparators = [Comparator.EQ, Comparator.GTE, Comparator.LT]
    allowed_operators = [Operator.AND, Operator.OR]

    def visit_comparison(self, comparison):
        attr, comp, val = comparison.attribute, comparison.comparator, comparison.value
        if comp == Comparator.EQ:
            return lambda md: md.get(attr) == val
        if comp == Comparator.GTE:
            return lambda md: md.get(attr) is not None and md.get(attr) >= val
        if comp == Comparator.LT:
            return lambda md: md.get(attr) is not None and md.get(attr) < val
        raise NotImplementedError(comp)

    def visit_operation(self, operation):
        fns = [self.visit(arg) for arg in operation.arguments]
        if operation.operator == Operator.AND:
            return lambda md: all(f(md) for f in fns)
        if operation.operator == Operator.OR:
            return lambda md: any(f(md) for f in fns)
        raise NotImplementedError(operation.operator)

    def visit_structured_query(self, structured_query):
        return None if structured_query.filter is None else self.visit(structured_query.filter)

    def visit(self, node):
        if isinstance(node, Comparison):
            self._validate_func(node.comparator)
            return self.visit_comparison(node)
        if isinstance(node, Operation):
            self._validate_func(node.operator)
            return self.visit_operation(node)
        raise NotImplementedError(node)

Concept 2 — Pre-Filter vs. Post-Filter Recall Loss


Given a predicate, WHEN it's applied matters as much as whether it's applied at all.
Pre-filtering narrows the candidate set to only rows that pass the predicate, THEN ranks
by similarity within that narrowed set. Post-filtering ranks the full unfiltered corpus
first, takes the top-k, and only THEN discards whatever fails the predicate — which can
silently return fewer than k results, or zero, if the top-k unfiltered ranking happens to
be dominated by documents the predicate would have excluded.
langchain_core.vectorstores.InMemoryVectorStore genuinely implements pre-filtering: its
filter argument is applied to candidates BEFORE the top-k truncation (confirmed by
reading its source), so the comparison below is two real, different code paths through the
same real vector store, not a hypothetical.

import hashlib, math

KEYWORDS = ["claim", "liability", "collision", "underwriting", "policy", "coverage",
            "loss", "injury", "property", "auto", "large"]

class KeywordBucketEmbeddings(Embeddings):
    def _vec(self, text):
        t = text.lower()
        v = [float(t.count(k)) for k in KEYWORDS]
        h = int(hashlib.sha256(t.encode()).hexdigest(), 16)
        for i in range(8):
            v.append(((h >> (i * 4)) % 7) / 7.0)
        norm = math.sqrt(sum(x * x for x in v)) or 1.0
        return [x / norm for x in v]
    def embed_documents(self, texts):
        return [self._vec(t) for t in texts]
    def embed_query(self, text):
        return self._vec(text)

Concept 3 — pgvector Iterative Index Scans for Selective Filters


An ANN index (HNSW, IVFFlat) is built to find the k nearest neighbors FAST — it is not
built to guarantee k neighbors that also pass an arbitrary metadata filter. When the
filter is highly selective (few rows qualify), a single index scan pass can come back with
fewer than k passing rows even though enough exist somewhere in the corpus — exactly
Concept 2's post-filter failure mode, but happening INSIDE the index rather than in
application code. pgvector's hnsw.iterative_scan setting addresses this by re-scanning
with a widening search window until k qualifying rows are found or a tuple cap is hit,
instead of giving up after one pass. The scan-widening LOGIC below is genuine, deterministic
Python that actually runs; the actual HNSW index internals are not built here, since they
need a live Postgres+pgvector instance this sandbox doesn't have.


Example:


import random

def make_ranked_candidates(n, seed=7):
    rnd = random.Random(seed)
    return [
        {"doc_id": f"CLM-{90000 + i}",
         "state": rnd.choice(["NY", "CA", "TX", "FL", "NJ", "OH", "IL", "PA", "WA", "MA"])}
        for i in range(n)
    ]

def iterative_index_scan(candidates, predicate, k, initial_batch=20, max_tuples=200):
    """Simulates pgvector's hnsw.iterative_scan: expand the scanned batch until k rows
    pass the predicate or max_tuples is hit, without re-scanning already-examined tuples."""
    batch_size, examined, matches = initial_batch, 0, []
    while examined < len(candidates) and examined < max_tuples:
        next_examined = min(examined + batch_size, len(candidates), max_tuples)
        matches.extend(c for c in candidates[examined:next_examined] if predicate(c))
        examined = next_examined
        if len(matches) >= k:
            break
        batch_size *= 2
    return matches[:k], examined

candidates = make_ranked_candidates(300)
single_pass_ny = sum(1 for c in candidates[:20] if c["state"] == "NY")
print(f"single-pass scan (first 20 nearest neighbors): {single_pass_ny} NY matches (need 5)")

ny_matches, ny_examined = iterative_index_scan(candidates, lambda c: c["state"] == "NY", k=5)
print(f"iterative scan for NY (selective, ~9% of corpus): found {len(ny_matches)} after examining {ny_examined} tuples")

group_matches, group_examined = iterative_index_scan(
    candidates, lambda c: c["state"] in {"NY", "CA", "TX", "FL"}, k=5)
print(f"iterative scan for 4-state group (less selective, ~40%): found {len(group_matches)} after examining {group_examined} tuples")

Concept 4 — End-to-End: Schema-Validated Predicate From a Fresh Question


Putting Concepts 1-3 together: a real self-query pipeline must reject a filter on a field
it never declared in its metadata_field_info schema, not silently build a broken
predicate for it — an LLM occasionally hallucinates a plausible-sounding field name
(claim_amount_usd instead of the declared schema's fields) that was never part of the
contract, and that must fail loudly, not filter on a field that doesn't exist and silently
match everything or nothing.


Example:

    for attr, _, _ in comparisons:

BFSI Reality Check — Day 4


Legacy angle: a metadata_field_info schema is itself a contract between the retrieval
layer and whatever wrote the original documents' metadata — a legacy ingestion job that
starts writing state as a full name ("New York") instead of the two-letter code the
schema and every existing filter predicate assume breaks every downstream self-query
silently (a predicate that never matches, not an error).


Compliance angle: Concept 4's rejection of an undeclared field is a real guardrail
worth logging, not just raising — an LLM repeatedly attempting to filter on a field like
ssn or date_of_birth that was deliberately left out of metadata_field_info is a
signal worth a compliance review on its own, independent of whether the query that
triggered it was otherwise benign.


What breaks in production: Concept 2's near-zero post-filter recall is not a corner
case reserved for adversarial decoy documents — it is what happens ANY time a corpus
contains boilerplate or template language (a standard disclosure paragraph repeated across
many documents) that scores artificially high for a common query regardless of which
document it belongs to; pre-filtering is the only one of the two approaches that is safe to
default to whenever a predicate is available at all.

Concept 2 — Four Strategies, One Ranking Interface


Every strategy below returns the same shape — a ranked list of doc_ids at a fixed
k=3 — so they can be scored identically in Concept 3. baseline and rewrite are
direct calls into Day 1's retrieve; rrf_fusion reuses Day 2's real
reciprocal_rank_fusion to fuse three independently-retrieved rankings (the
underspecified query, the rewrite, and the HyDE hypothetical document) instead of
picking just one of them; parent_child reuses the small-to-big idea from Day 3, built
here as a lightweight child-chunk index over just the 3 long POL-* sections (the 8
short docs are their own single child, exactly as Day 3's closing note said a
single-clause document has no parent/child split worth making).


Example:


# Reusing retrieve, recall_at_k, CORPUS, bow, cosine from Day 1;
# reciprocal_rank_fusion from Day 2 Concept 2

def split_sentences(text):
    return [p.strip() for p in text.replace("\n", " ").split(". ") if p.strip()]

def make_children():
    """Every short CORPUS doc is its own single child (parent == child); each long
    POL-* section is split into 2-sentence children pointing back at its parent_id --
    the same small-search/large-generate split Day 3 built, applied to this corpus."""
    children = []
    for doc_id, text in CORPUS:
        if doc_id.startswith("POL-"):
            sents = split_sentences(text)
            for i in range(0, len(sents), 2):
                chunk = ". ".join(sents[i:i + 2])
                children.append((f"{doc_id}-c{i // 2}", doc_id, chunk))
        else:
            children.append((f"{doc_id}-c0", doc_id, text))
    return children

CHILDREN = make_children()

def retrieve_parent_child(query_text, k=3):
    qv = bow(query_text)
    scored = [(cid, pid, cosine(qv, bow(text))) for cid, pid, text in CHILDREN]
    scored.sort(key=lambda x: -x[2])
    seen = []
    for cid, pid, s in scored:
        if pid not in seen:
            seen.append(pid)
        if len(seen) >= k:
            break
    return seen

def baseline_ranker(under, rewritten, hyde, k=3):
    return [d for d, _ in retrieve(under, k)]

def rewrite_ranker(under, rewritten, hyde, k=3):
    return [d for d, _ in retrieve(rewritten, k)]

def rrf_ranker(under, rewritten, hyde, k=3):
    base_r = [d for d, _ in retrieve(under, k + 2)]
    rewrite_r = [d for d, _ in retrieve(rewritten, k + 2)]
    hyde_r = [d for d, _ in retrieve(hyde, k + 2)]
    fused = reciprocal_rank_fusion([base_r, rewrite_r, hyde_r], k=60)
    return [d for d, _ in fused][:k]

def parentchild_ranker(under, rewritten, hyde, k=3):
    return retrieve_parent_child(rewritten, k)

Concept 3 — Recall@k, MRR, and p95 Latency Across the Full Set


Scoring one query at a time (Concept 2) does not tell you which strategy actually wins.
This concept runs every strategy against every one of the 12 labeled queries and
aggregates three real, measured numbers per strategy: mean recall@3 (did the right
document land in the top 3 at all), MRR (mean reciprocal rank — rewards ranking the
right document FIRST, not just somewhere in the top 3, the gap Concept 2's exercise just
surfaced), and p95 latency. The latency here is real, measured wall-clock time for the
retrieval mechanics only (bow/cosine scoring and RRF fusion over an 11-document,
15-child in-process corpus) — it excludes the live LLM rewrite/HyDE-generation calls
Concept 1 disclosed as stand-ins, and its absolute milliseconds are two orders of
magnitude below anything a real embedding-API round trip would cost, so it is reported
here as a deterministic bucket check rather than a raw number a rerun could drift on.


Example:


import time

def reciprocal_rank(ranked_ids, relevant_id):
    if relevant_id in ranked_ids:
        return 1.0 / (ranked_ids.index(relevant_id) + 1)
    return 0.0

K = 3
STRATEGIES = {
    "baseline": baseline_ranker,
    "rewrite": rewrite_ranker,
    "rrf_fusion": rrf_ranker,
    "parent_child": parentchild_ranker,
}

bakeoff_results = {}
for name, ranker in STRATEGIES.items():
    recalls, rrs, latencies_ms, by_type = [], [], [], {}
    for qtype, under, rewritten, hyde, rel in QUERY_SET:
        t0 = time.perf_counter()
        ranked = ranker(under, rewritten, hyde, K)
        t1 = time.perf_counter()
        r = recall_at_k(ranked, rel, K)
        recalls.append(r)
        rrs.append(reciprocal_rank(ranked, rel))
        latencies_ms.append((t1 - t0) * 1000.0)
        by_type.setdefault(qtype, []).append(r)
    latencies_ms.sort()
    p95_idx = min(len(latencies_ms) - 1, int(round(0.95 * (len(latencies_ms) - 1))))
    bakeoff_results[name] = {
        "mean_recall": sum(recalls) / len(recalls),
        "mrr": sum(rrs) / len(rrs),
        "p95_ms": latencies_ms[p95_idx],
        "by_type": by_type,
    }

for name, m in bakeoff_results.items():
    print(f"{name:14} recall@{K}={m['mean_recall']:.3f}  MRR={m['mrr']:.3f}  "
          f"p95_latency_under_5ms={m['p95_ms'] < 5.0}")

BFSI Reality Check — Day 5


Legacy angle: a 12-question labeled set (or even a real 30-question one) is a
snapshot of the query vocabulary and document set that existed the day it was built — a
legacy underwriting system's clause wording changing during a policy-admin migration
silently invalidates every doc_id label the set was built against, the same staleness
risk a unit test suite has against a codebase that moved out from under it, except
nothing here fails loudly the way a broken import does.


Compliance angle: the per-query-type table (Concept 4), not just the aggregate
recall@3/MRR numbers (Concept 3), is what a model-risk review actually needs — an
aggregate number can mask a strategy that is excellent on 4 of 5 query types and
silently broken on the fifth, and BFSI retrieval failures are rarely evenly distributed
across query types; they cluster on whichever product line or clause pattern the
labeled set's authors happened not to think to include.


What breaks in production: every non-baseline strategy tying at recall@3=1.000 on
this 12-query set (Concept 4) is the single clearest argument in this whole week for why
production evaluation sets run to 30+ queries and beyond, not 12 — a set this small
cannot statistically distinguish "genuinely equivalent" from "not enough queries to tell
them apart yet," and shipping a default strategy chosen from ties this narrow, without
ever widening the set, is exactly how a real regression on an underrepresented query
type goes undetected until a claims adjuster hits it in production.




Architecture Decision — Week 24


Choosing between: plain LLM query rewriting as the retrieval default (Day 1's
rewrite step alone, one extra LLM call per query, no fusion) vs. RRF fusion of
baseline + rewrite + HyDE (Day 2's fusion, three retrieval passes plus the fusion
math, no extra LLM calls beyond what rewrite and HyDE already need) vs. parent-child
indexing as an always-on default (Day 3's small-to-big split applied to every document
regardless of length).


Rule of thumb: default to plain rewrite for the general case. Day 5's bake-off
measured all three non-baseline strategies tying at recall@3=1.000 on this labeled
set, so recall@3 gives no reason to prefer one over another — but MRR does, and
plain rewrite's MRR=1.000 beat RRF fusion's 0.806 on the very same set, because
fusion kept baseline's weak, unrewritten ranking in the vote alongside two strong
signals (rewrite and HyDE) and let it occasionally drag the true answer off rank 1. That
is the concrete failure case fusion has to earn its way past: only add RRF fusion when
a second signal is independently strong enough to be worth fusing — for example,
fusing rewrite with a real BM25 lexical ranking (Day 2 Concept 3), which brings a
genuinely different failure mode (exact-term recall) rather than fusing in a signal
(baseline, unrewritten) already known to be the weakest of the three. Never fuse in a
signal you would not trust alone.


Move to parent-child indexing only for document types independently known to be
long and multi-clause enough that a single embedding would dilute a specific clause's
signal — Day 5 Concept 3's own combined-type check showed parent-child buys nothing over
plain rewrite on the baseline_friendly and parent_child query types in THIS labeled
set, because none of its 3 long POL-* sections happened to be long enough, or its
clauses similar enough to each other, to create real dilution. Turning parent-child
indexing on for every document in a corpus, regardless of length, is exactly the
default Day 3's own closing BFSI Reality Check warned against: it spends real storage
and parent/child sync cost in places the bake-off shows it buys nothing. The actual
failure case for the chosen default (plain rewrite) is the one this whole week keeps
returning to: a rewrite prompt whose few-shot examples cover one product line's
vocabulary (auto) degrades silently on another (life, commercial property) the labeled
set never tested — which is precisely why Day 5's methodology (a fixed labeled set,
re-run whenever the corpus or product-line mix changes, not a one-time bake-off result
trusted forever) is the actual deliverable of this week, not any one strategy's win.
