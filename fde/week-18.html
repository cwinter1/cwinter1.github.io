Concept 1 — MSSQL's Own Catalog: sys.objects, sys.sql_modules, sys.foreign_keys

When no separate data catalog exists, sys.objects (every table, procedure, view, and function in the database, with real columns object_id, name, type, and type_desc — 'USER_TABLE' and 'SQL_STORED_PROCEDURE' are real type_desc values, not placeholders), sys.sql_modules (the actual T-SQL definition text for any object that has one, keyed by object_id), and sys.foreign_keys (parent_object_id → referenced_object_id, the only place a legacy database's real relationships are recorded if no ER diagram survived) ARE the catalog. Running the real query against a live server is REAL MODE here — no such server exists in this sandbox — but the parsing logic that turns those three result sets into one usable catalog needs no live connection at all.

Example:

import dataclasses

# Simulated result sets shaped exactly like sys.objects/sys.sql_modules/sys.foreign_keys
# would return them (REAL MODE only for the live query itself).
SIMULATED_SYS_OBJECTS = [
    {"object_id": 101, "name": "CLAIMS", "type": "U", "type_desc": "USER_TABLE"},
    {"object_id": 102, "name": "POLICIES", "type": "U", "type_desc": "USER_TABLE"},
    {"object_id": 201, "name": "usp_ProcessClaim", "type": "P", "type_desc": "SQL_STORED_PROCEDURE"},
    {"object_id": 202, "name": "usp_RenewPolicy", "type": "P", "type_desc": "SQL_STORED_PROCEDURE"},
]

SIMULATED_SYS_SQL_MODULES = {
    201: "CREATE PROCEDURE usp_ProcessClaim AS INSERT INTO CLAIMS SELECT * FROM STAGING_CLAIMS",
    202: "CREATE PROCEDURE usp_RenewPolicy AS UPDATE POLICIES SET STATUS = 'ACTIVE'",
}

SIMULATED_SYS_FOREIGN_KEYS = [
    {"name": "FK_CLAIMS_POLICIES", "parent_object_id": 101, "referenced_object_id": 102},
]

@dataclasses.dataclass
class CatalogEntry:
    object_id: int
    name: str
    type_desc: str
    definition: str = None

def build_catalog(sys_objects, sys_sql_modules):
    return [
        CatalogEntry(
            object_id=obj["object_id"],
            name=obj["name"],
            type_desc=obj["type_desc"],
            definition=sys_sql_modules.get(obj["object_id"]),
        )
        for obj in sys_objects
    ]

catalog = build_catalog(SIMULATED_SYS_OBJECTS, SIMULATED_SYS_SQL_MODULES)
for entry in catalog:
    has_definition = entry.definition is not None
    print(f"{entry.name} ({entry.type_desc}): has_definition={has_definition}")

fk_summary = [(fk["name"], fk["parent_object_id"], fk["referenced_object_id"]) for fk in SIMULATED_SYS_FOREIGN_KEYS]
print(f"foreign keys discovered: {fk_summary}")

Concept 2 — sys.dm_db_index_usage_stats: Separating Live Tables From Dead Ones

A twenty-year-old database accumulates tables nobody reads from anymore but something still occasionally writes to, tables nobody touches at all, and tables that are still genuinely load-bearing — and sys.objects alone cannot tell these apart, since it has no concept of "used." sys.dm_db_index_usage_stats's real columns (user_seeks, user_scans, user_lookups, user_updates, last_user_seek, last_user_scan) are what actually distinguishes them: zero reads and zero writes is dead; zero reads but ongoing writes is write-only (an audit/log table, not a candidate for archival); reads that happened once but not within a chosen staleness window is stale; anything else is live.

Example:

import datetime

@dataclasses.dataclass
class IndexUsageStat:
    object_id: int
    table_name: str
    user_seeks: int
    user_scans: int
    user_lookups: int
    user_updates: int
    last_user_seek: datetime.date = None
    last_user_scan: datetime.date = None

def classify_table(stat, as_of, dead_threshold_days=365):
    read_activity = stat.user_seeks + stat.user_scans + stat.user_lookups
    if read_activity == 0 and stat.user_updates == 0:
        return "dead"
    if read_activity == 0 and stat.user_updates > 0:
        return "write_only"
    last_read = max(d for d in (stat.last_user_seek, stat.last_user_scan) if d is not None) if read_activity else None
    if last_read and (as_of - last_read).days > dead_threshold_days:
        return "stale"
    return "live"

as_of_date = datetime.date(2026, 9, 16)
claims_usage = IndexUsageStat(object_id=101, table_name="CLAIMS", user_seeks=15000, user_scans=200, user_lookups=800, user_updates=500, last_user_seek=datetime.date(2026, 9, 15))
legacy_archive_usage = IndexUsageStat(object_id=999, table_name="LEGACY_ARCHIVE_1998", user_seeks=0, user_scans=0, user_lookups=0, user_updates=0)
write_only_usage = IndexUsageStat(object_id=888, table_name="AUDIT_TRAIL", user_seeks=0, user_scans=0, user_lookups=0, user_updates=1200)

for usage in (claims_usage, legacy_archive_usage, write_only_usage):
    print(f"{usage.table_name}: {classify_table(usage, as_of_date)}")

Concept 3 — COBOL Copybooks as the Schema of Record When No Catalog Exists at All


Week 13 built CopybookField to parse a mainframe record's byte layout. This week reuses
that same dataclass — copied in unchanged — but re-grounds its role: for a mainframe
extract, the copybook is not "one more source to catalog," it is the ENTIRE catalog
entry, because no sys.objects/ALL_TAB_COLUMNS equivalent exists for a COBOL file
section at all. A mainframe catalog entry therefore has no object_id — there is no
system that assigns one.


Example:


@dataclasses.dataclass
class CopybookField:
    level: int
    name: str
    pic: str
    usage: str = "DISPLAY"

POLICY_RECORD_COPYBOOK = [
    CopybookField(1, "POLICY-RECORD", None),
    CopybookField(5, "POLICY-ID", "X(10)"),
    CopybookField(5, "POLICY-HOLDER-NAME", "X(30)"),
    CopybookField(5, "PREMIUM-AMOUNT", "S9(7)V99", usage="COMP-3"),
    CopybookField(5, "POLICY-STATUS", "X(1)"),
]

def copybook_as_catalog_entry(fields, source_system):
    record_name = next(f.name for f in fields if f.level == 1)
    columns = [f.name for f in fields if f.level != 1]
    return CatalogEntry(object_id=None, name=record_name, type_desc=f"COBOL_COPYBOOK ({source_system})", definition=f"{len(columns)} fields")

mainframe_entry = copybook_as_catalog_entry(POLICY_RECORD_COPYBOOK, source_system="policy_extract_nightly")
print(f"{mainframe_entry.name}: type_desc={mainframe_entry.type_desc}, definition={mainframe_entry.definition}")

Concept 4 — Oracle's Equivalents: ALL_TAB_COLUMNS, ALL_SOURCE, DBA_DEPENDENCIES


An Oracle-sourced legacy estate has its own real system views doing the same job:
ALL_TAB_COLUMNS for column-level metadata (the sys.columns equivalent), ALL_SOURCE
for the actual PL/SQL source text of a procedure or package (the sys.sql_modules
equivalent), and DBA_DEPENDENCIES for object-level dependency relationships (the closest
analog to sys.foreign_keys, though it tracks a broader dependency graph, not only FK
constraints). A catalog-building function honest about which of these mappings is exact
and which is only "closest analog" is more useful than one that pretends a clean
one-to-one mapping exists everywhere.


Example:


MSSQL_TO_ORACLE_CATALOG_EQUIVALENTS = {
    "sys.objects": "ALL_OBJECTS",
    "sys.columns": "ALL_TAB_COLUMNS",
    "sys.sql_modules": "ALL_SOURCE",
    "sys.foreign_keys": "DBA_DEPENDENCIES (constraint dependencies) / ALL_CONSTRAINTS",
}

def oracle_equivalent_for(mssql_view):
    return MSSQL_TO_ORACLE_CATALOG_EQUIVALENTS.get(mssql_view, "no direct equivalent")

for mssql_view in ("sys.objects", "sys.columns", "sys.sql_modules", "sys.foreign_keys"):
    print(f"{mssql_view} -> {oracle_equivalent_for(mssql_view)}")

BFSI Reality Check — Day 1


Legacy angle: The catalog built this concept-by-concept is derived, not authoritative
— nobody at the organization signs off on it, and it can drift the moment the underlying
schema changes without anyone updating the derivation script. That is a real limitation
to disclose, not a reason to skip building it.


Compliance angle: A regulator asking "what personal data does this system hold" gets
a real, if imperfect, answer from this derived catalog — the alternative, for a genuinely
undocumented legacy estate, is often no answer at all.


What breaks in production: A table that sys.dm_db_index_usage_stats classifies
dead gets archived and its extract job disabled — but the usage stats reset on every
SQL Server service restart, so a table that was actually read once a quarter by a
batch job that hadn't run since the last restart looks dead when it isn't. Usage stats
are a strong signal, not proof, and Concept 2's classification function should be
re-checked against a longer observation window before anything gets archived on its say
alone.

Concept 1 — Column-Name Heuristics, Then Presidio Sampling to Confirm or Reject


Day 1's derived catalog has column names but no sensitivity labels — nobody left behind
a data dictionary saying which columns hold PII. A column-name heuristic (CUST_SSN
plausibly holds an SSN, POLICY_ID plausibly doesn't) is a fast first pass, but it is
only a candidate list — the heuristic has no idea what the actual VALUES look like.
Sampling real values through Presidio's AnalyzerEngine (genuinely reused from Week 14)
is what confirms or rejects each candidate against real content, not just a plausible
name. One of this concept's own sample SSNs is deliberately the textbook "123-45-6789" —
verified against UsSsnRecognizer.invalidate_result's real source, Presidio hardcodes an
exclusion for exactly this value (along with 987654320 and 078051120, the actual
number printed on a famous 1938 Woolworth wallet-novelty ad and reused as a real SSN by
thousands of people for decades afterward) as a known published placeholder, so its own
rejection below is real recognizer behavior, not a bug in this sampling code.


Example:


import re

from presidio_analyzer import AnalyzerEngine
from presidio_analyzer.nlp_engine import NlpEngineProvider

nlp_config = {"nlp_engine_name": "spacy", "models": [{"lang_code": "en", "model_name": "en_core_web_sm"}]}
nlp_engine = NlpEngineProvider(nlp_configuration=nlp_config).create_engine()
analyzer = AnalyzerEngine(nlp_engine=nlp_engine, supported_languages=["en"])

COLUMN_NAME_HEURISTICS = {
    r"NAME": "PERSON",
    r"SSN|TAX.?ID|NATIONAL.?ID": "US_SSN",
    r"DOB|BIRTH.?DATE": "DATE_TIME",
    r"PHONE|MOBILE|TEL": "PHONE_NUMBER",
    r"ADDR": "LOCATION",
    r"NOTES|REMARKS|COMMENTS": "FREE_TEXT",
}

def heuristic_candidates(column_names):
    candidates = {}
    for col in column_names:
        for pattern, entity in COLUMN_NAME_HEURISTICS.items():
            if re.search(pattern, col, re.IGNORECASE):
                candidates[col] = entity
                break
    return candidates

def confirm_with_presidio(sample_values, expected_entity, score_threshold=0.0):
    hits = 0
    for value in sample_values:
        results = analyzer.analyze(text=str(value), language="en", entities=[expected_entity], score_threshold=score_threshold)
        if results:
            hits += 1
    return hits, len(sample_values)

legacy_columns = ["CUST_NAME", "CUST_SSN", "CUST_DOB", "CUST_PHONE", "POLICY_ID", "STATUS_FLAG"]
candidates = heuristic_candidates(legacy_columns)
print(f"heuristic candidates: {candidates}")

name_samples = ["John Smith", "Maria Garcia", "David Cohen"]
hits, total = confirm_with_presidio(name_samples, "PERSON")
print(f"CUST_NAME sample confirmed as PERSON: {hits}/{total}")

ssn_samples = ["219-09-9999", "045-33-2214", "123-45-6789"]
ssn_hits, ssn_total = confirm_with_presidio(ssn_samples, "US_SSN")
print(f"CUST_SSN sample confirmed as US_SSN: {ssn_hits}/{ssn_total}")
print("the one rejected value, '123-45-6789', is Presidio's own denylisted canonical placeholder SSN -- a real recognizer behavior, not a bug in this sampling code")

Concept 2 — Confidence Tiers and a Human Review Queue for Ambiguous Columns


A column that Presidio confirms on every sample (CUST_NAME, 3/3) is a different case
from one that confirms on some but not all samples (CUST_SSN, 2/3 — not because the
detector is unreliable, but because real sample data mixes genuine values with an
occasional placeholder). Neither case should auto-resolve into "definitely PII" or
"definitely not" without a human looking at the ambiguous middle tier — a fixed
confirmation-rate threshold turns Concept 1's raw hit counts into three actionable
buckets: confirmed_high, review_queue, and rejected.


Example:


import dataclasses

@dataclasses.dataclass
class ColumnFinding:
    column_name: str
    heuristic_entity: str
    presidio_hits: int
    presidio_total: int

def classify_confidence(finding):
    if finding.presidio_total == 0:
        return "review_queue"
    rate = finding.presidio_hits / finding.presidio_total
    if rate >= 0.8:
        return "confirmed_high"
    if rate >= 0.3:
        return "review_queue"
    return "rejected"

name_finding = ColumnFinding("CUST_NAME", "PERSON", hits, total)
ssn_finding = ColumnFinding("CUST_SSN", "US_SSN", ssn_hits, ssn_total)
ambiguous_finding = ColumnFinding("REF_CODE", "PERSON", presidio_hits=1, presidio_total=3)

for finding in (name_finding, ssn_finding, ambiguous_finding):
    print(f"{finding.column_name}: {classify_confidence(finding)}")

Concept 3 — Free-Text NOTES and REMARKS: the Highest-Risk Unmanaged PII


A structured PHONE column at least has a predictable shape a scanner can reason about.
A free-text NOTES or REMARKS column — where a legacy system's users have been typing
whatever they wanted for twenty years — can carry any entity type in any combination, row
by row, with no schema constraint stopping it. This concept scans both kinds of column
with the same function and shows the real, qualitative difference: a structured column's
rows tend to (or fail to) confirm uniformly, while a free-text column's rows carry a
genuinely varying, unmanaged mix of entity types. The structured column's 555-0101
-style values below are a real, verified finding, not bad sample data — they are 7-digit
local numbers with no area code, exactly the shape a genuinely old legacy phone column
often stores, and Presidio's phonenumbers-backed recognizer needs a full
area-code-plus-number shape to even attempt a match, so it flags none of them.


Example:


structured_phone_column = ["555-0101", "555-0102", "555-0103"]
notes_column = [
    "Called customer, spoke with John Smith at 555-0199, will follow up Monday",
    "Policyholder Maria Garcia requested address change, new address 42 Elm St",
    "No PII in this one, routine renewal confirmed",
]

def scan_free_text_for_pii(values):
    findings = []
    for value in values:
        results = analyzer.analyze(text=value, language="en")
        entity_types = sorted({r.entity_type for r in results if r.score >= 0.5})
        findings.append((value[:40] + "...", entity_types))
    return findings

structured_findings = scan_free_text_for_pii(structured_phone_column)
notes_findings = scan_free_text_for_pii(notes_column)

print("structured PHONE column (one entity type expected per row):")
for preview, entities in structured_findings:
    print(f"  {preview} -> {entities}")

print("free-text NOTES column (multiple, unmanaged entity types per row):")
for preview, entities in notes_findings:
    print(f"  {preview} -> {entities}")

rows_with_multiple_entity_types = sum(1 for _, entities in notes_findings if len(entities) > 1)
print(f"NOTES rows carrying more than one entity type in a single free-text field: {rows_with_multiple_entity_types}")

Concept 4 — Writing Findings Back as sys.extended_properties or Oracle Column Comments


A classification that lives only in this week's script is gone the moment the script
isn't re-run — the next person to touch this database has no way to know a prior scan
ever happened. sys.sp_addextendedproperty (MSSQL) and COMMENT ON COLUMN (Oracle) both
let a classification attach to the schema object itself, so it outlives the script and
is visible to anyone who queries the catalog directly, including a future run of this
same classification pipeline. Generating the SQL statement text below is genuinely
executed; actually connecting to a live server to run it needs a database this sandbox
does not have.


Example:


def mssql_extended_property_statement(table, column, classification):
    return (
        f"EXEC sys.sp_addextendedproperty "
        f"@name = N'pii_classification', @value = N'{classification}', "
        f"@level0type = N'SCHEMA', @level0name = N'dbo', "
        f"@level1type = N'TABLE', @level1name = N'{table}', "
        f"@level2type = N'COLUMN', @level2name = N'{column}';"
    )

def oracle_column_comment_statement(table, column, classification):
    return f"COMMENT ON COLUMN {table}.{column} IS 'pii_classification={classification}';"

mssql_stmt = mssql_extended_property_statement("CUSTOMERS", "CUST_NAME", "confirmed_high:PERSON")
oracle_stmt = oracle_column_comment_statement("CUSTOMERS", "CUST_NAME", "confirmed_high:PERSON")
print(mssql_stmt)
print(oracle_stmt)

Concept 1 — Parsing T-SQL and PL/SQL Procedure Bodies With sqlglot


A legacy estate's real lineage lives inside stored-procedure bodies nobody has diagrammed
in years — usp_ProcessClaim might insert into three tables and update two more, and the
only record of that is the T-SQL or PL/SQL text itself. sqlglot genuinely parses both
dialects (read="tsql", read="oracle") into a real AST, and walking that AST for
INSERT/UPDATE nodes gives a genuine source-to-target extraction — no live database
connection needed, since this is pure text parsing. One real thing the Example's own
target_table_name below has to handle, found by actually running an early version
against the PL/SQL case: when an INSERT names an explicit column list (INSERT INTO policy_history (policy_id, renewed_date)), sqlglot wraps the target Table inside a
Schema node instead of exposing it directly — a bare .this.name silently returns an
empty string in that case, which the function's isinstance check exists to catch.


Example:


import sqlglot
from sqlglot import exp

def target_table_name(insert_or_update_node):
    node = insert_or_update_node.this
    if not isinstance(node, exp.Table):
        table = node.find(exp.Table)
        return table.name if table else None
    return node.name

def extract_lineage(sql_text, dialect):
    tree = sqlglot.parse_one(sql_text, read=dialect)
    lineage = []
    for ins in tree.find_all(exp.Insert):
        target = target_table_name(ins)
        sources = sorted(set(t.name for t in ins.find_all(exp.Table)) - {target})
        lineage.append({"statement": "INSERT", "target": target, "sources": sources})
    for upd in tree.find_all(exp.Update):
        target = target_table_name(upd)
        sources = sorted(set(t.name for t in upd.find_all(exp.Table)) - {target})
        lineage.append({"statement": "UPDATE", "target": target, "sources": sources})
    return lineage

tsql_proc = """
CREATE PROCEDURE usp_ProcessClaim AS
BEGIN
    INSERT INTO CLAIMS_SUMMARY
    SELECT customer_id, SUM(claim_amount) AS total_claims
    FROM CLAIMS
    JOIN POLICIES ON CLAIMS.policy_id = POLICIES.policy_id
    GROUP BY customer_id;

    UPDATE POLICIES SET last_claim_date = GETDATE() FROM CLAIMS WHERE CLAIMS.policy_id = POLICIES.policy_id;
END
"""
tsql_lineage = extract_lineage(tsql_proc, dialect="tsql")
for entry in tsql_lineage:
    print(f"{entry['statement']} {entry['target']} <- {entry['sources']}")

plsql_proc = """
CREATE OR REPLACE PROCEDURE renew_policy AS
BEGIN
    INSERT INTO policy_history (policy_id, renewed_date)
    SELECT policy_id, SYSDATE FROM policies WHERE status = 'ACTIVE';
END;
"""
plsql_lineage = extract_lineage(plsql_proc, dialect="oracle")
for entry in plsql_lineage:
    print(f"{entry['statement']} {entry['target']} <- {entry['sources']}")
print("target extraction handles BOTH a bare Table node (T-SQL, no column list) and a Table wrapped in a Schema node (Oracle, explicit column list): True")

Concept 2 — Reading SSIS .dtsx Package XML for Data-Flow Wiring


An SSIS package's real Data Flow wiring lives in its .dtsx file's DTS:ObjectData
section as a <pipeline> of <component> elements connected by <path> elements whose
startId/endId attributes name a specific component's output or input port. No SSIS
designer exists in this sandbox to export an actual package, so the XML below is a
hand-authored snippet shaped like a real export's structure and real namespace
(www.microsoft.com/SqlServer/Dts) rather than a captured file — but parsing it with
Python's own xml.etree.ElementTree is genuinely executed, no live SSIS runtime needed.


Example:


import xml.etree.ElementTree as ET

DTSX_SNIPPET = """<?xml version="1.0"?>
<DTS:Executable xmlns:DTS="www.microsoft.com/SqlServer/Dts">

    components = [c.get("name") for c in root.findall(".//component")]

        start_component = path.get("startId").split(".")[0]
        end_component = path.get("endId").split(".")[0]
        edges.append((start_component, end_component))
    return components, edges

Concept 3 — JCL Job Steps and COBOL File Sections as the Mainframe Lineage Source


A mainframe batch job's real lineage is encoded in its JCL: each //STEPNAME EXEC PGM=... names a program, and each //DDNAME DD DSN=dataset.name,DISP=... binds a
dataset to that step under a specific DD name. Step-to-step lineage is derivable purely
from text: if one step's OUTFILE DD names the same dataset (DSN=) a later step's
INFILE DD names, the second step consumes the first step's output — the same
control-flow-from-text-alone technique Week 13 used for copybook byte offsets, applied
here to job-step data flow instead of record layout.


Example:


import re

JCL_JOB = """\
//CLMEXTR  JOB (ACCT01),'NIGHTLY CLAIMS EXTRACT',CLASS=A
//STEP010  EXEC PGM=CLMEXTR
//INFILE   DD  DSN=PROD.CLAIMS.MASTER,DISP=SHR
//OUTFILE  DD  DSN=PROD.CLAIMS.EXTRACT,DISP=(NEW,CATLG,DELETE)
//STEP020  EXEC PGM=CLMLOAD
//INFILE   DD  DSN=PROD.CLAIMS.EXTRACT,DISP=SHR
//OUTFILE  DD  DSN=PROD.CLAIMS.STAGING,DISP=(NEW,CATLG,DELETE)
"""

STEP_RE = re.compile(r"^//(\S+)\s+EXEC\s+PGM=(\S+)", re.MULTILINE)
DD_RE = re.compile(r"^//(\S+)\s+DD\s+DSN=([^,]+),DISP=(\S+)", re.MULTILINE)

def parse_jcl_steps(jcl_text):
    steps = []
    current_step = None
    for line in jcl_text.splitlines():
        step_match = STEP_RE.match(line)
        if step_match:
            current_step = {"step_name": step_match.group(1), "pgm": step_match.group(2), "dd_statements": []}
            steps.append(current_step)
            continue
        dd_match = DD_RE.match(line)
        if dd_match and current_step is not None:
            current_step["dd_statements"].append({
                "dd_name": dd_match.group(1),
                "dsn": dd_match.group(2),
                "disp": dd_match.group(3),
            })
    return steps

steps = parse_jcl_steps(JCL_JOB)
for step in steps:
    print(f"{step['step_name']} (PGM={step['pgm']}):")
    for dd in step["dd_statements"]:
        print(f"  {dd['dd_name']}: {dd['dsn']} DISP={dd['disp']}")

def derive_step_lineage(steps):
    lineage = []
    for i, step in enumerate(steps):
        out_dsns = {dd["dsn"] for dd in step["dd_statements"] if dd["dd_name"] == "OUTFILE"}
        for later_step in steps[i + 1:]:
            in_dsns = {dd["dsn"] for dd in later_step["dd_statements"] if dd["dd_name"] == "INFILE"}
            shared = out_dsns & in_dsns
            if shared:
                lineage.append((step["step_name"], later_step["step_name"], sorted(shared)))
    return lineage

step_lineage = derive_step_lineage(steps)
print(f"derived step-to-step lineage: {step_lineage}")

Concept 1 — Masking on the Way Out, Because the Core Cannot Be Altered


The core cannot be altered, re-tested, or redeployed — that constraint is the whole
reason this week exists. So masking cannot happen inside the core at all; it has to
happen in the EXTRACT pipeline, on the data's way OUT, genuinely reusing Week 14's real
AnonymizerEngine/hash operator pattern. The core rows themselves are read and left
completely untouched — only the copy leaving the extract boundary is transformed.


Example:


from presidio_analyzer import RecognizerResult
from presidio_anonymizer import AnonymizerEngine
from presidio_anonymizer.entities import OperatorConfig

anonymizer = AnonymizerEngine()

CORE_CUSTOMER_ROWS = [
    {"customer_id": "C1001", "name": "John Smith", "ssn": "219-09-9999"},
    {"customer_id": "C1002", "name": "Maria Garcia", "ssn": "045-33-2214"},
]

def extract_and_mask(core_rows, fields_to_mask, salt="fde-week18-fixed-salt"):
    extracted = []
    for row in core_rows:
        masked_row = dict(row)
        for field in fields_to_mask:
            text = str(row[field])
            result = RecognizerResult(entity_type="GENERIC", start=0, end=len(text), score=1.0)
            operators = {"GENERIC": OperatorConfig("hash", {"hash_type": "sha256", "salt": salt})}
            anonymized = anonymizer.anonymize(text=text, analyzer_results=[result], operators=operators)
            masked_row[field] = anonymized.text
        extracted.append(masked_row)
    return extracted

extracted_customers = extract_and_mask(CORE_CUSTOMER_ROWS, fields_to_mask=["ssn"])
for row in extracted_customers:
    print(f"{row['customer_id']}: name={row['name']}, ssn={row['ssn'][:16]}...")

print(f"core rows themselves were never modified: {CORE_CUSTOMER_ROWS[0]['ssn'] == '219-09-9999'}")

Two tables extracted separately (CUSTOMERS, CLAIMS) both carry the same real
customer_id values, joined on that key today. If each extraction masks customer_id
independently with the SAME fixed salt — Week 14 Day 3's real finding, that Presidio's
hash operator only produces identical digests for identical input when given an

though neither extraction knows about the other's run.

Concept 3 — Referential Integrity Verification and Hold-Back Mapping-Table Custody


Deterministic tokenization is a design choice; verifying it actually preserved
referential integrity is a separate, necessary check — count how many rows joined
successfully BEFORE masking and confirm the same count joins successfully AFTER. Separate
again from both: the mapping from a masked token back to its real value must be held
under STRICTER custody than the masked data itself — a different access-control boundary,
never derivable from the masked output alone — so re-identification is possible only
through that explicit, audited path.


Example:


def verify_referential_integrity(original_rows, masked_rows, original_key, masked_key, other_table_original, other_table_masked):
    original_join_count = sum(1 for r in original_rows if any(o["customer_id"] == r["customer_id"] for o in other_table_original))
    masked_join_count = sum(1 for r in masked_rows if any(o["customer_id"] == r["customer_id"] for o in other_table_masked))
    return original_join_count, masked_join_count

orig_count, masked_count = verify_referential_integrity(
    CORE_CLAIMS_ROWS, masked_claims, "customer_id", "customer_id", CORE_CUSTOMER_ROWS, masked_customers
)
print(f"joinable rows before masking: {orig_count}, after masking: {masked_count}")
print(f"referential integrity preserved (counts match): {orig_count == masked_count}")

mapping_table = {row["customer_id"]: masked["customer_id"] for row, masked in zip(CORE_CUSTOMER_ROWS, masked_customers)}
reverse_mapping = {v: k for k, v in mapping_table.items()}

def reidentify(masked_value, reverse_mapping):
    return reverse_mapping.get(masked_value, "NOT FOUND -- requires mapping table custodian")

sample_masked_id = masked_customers[0]["customer_id"]
print(f"re-identifying a masked customer_id via the custody-held mapping table: {reidentify(sample_masked_id, reverse_mapping)}")

BFSI Reality Check — Day 4


Legacy angle: The two-hour window is not a soft target — it is usually the literal
gap between one business day's batch cycle ending and the next day's online processing
needing the core back, inherited from decades-old operational scheduling that nobody
still working there has the authority to change.


Compliance angle: Hold-back custody of the mapping table is what makes deterministic
tokenization defensible under audit at all — without a documented, access-controlled

Concept 1 — Composing Catalog, Lineage, Masking Gate, and Guardrails Into One Landing Zone


Every prior day built one piece: Day 1's derived catalog, Day 3's derived lineage, Day 4's
masking gate. None of them alone is "governance" — a governed landing zone is the
composition of all of them PLUS a guardrail (genuinely reusing Week 11/15's GuardRail
middleware shape, re-grounded here as the last-line-of-defense check that nothing
unmasked leaves the zone) refusing to extract a table with no catalog entry at all, and
refusing to hand back any row that still contains an unmasked SSN pattern after the
masking pass supposedly ran.


Example:


import re

class GuardRail:
    def __init__(self):
        self._output_checks = []

    def add_output_check(self, check_fn):
        self._output_checks.append(check_fn)
        return self

    def run(self, produce_fn, *args, **kwargs):
        output = produce_fn(*args, **kwargs)
        for check in self._output_checks:
            check(output)
        return output

SSN_PATTERN = re.compile(r"\b\d{3}-\d{2}-\d{4}\b")

def check_no_unmasked_ssn(rows):
    for row in rows:
        for value in row.values():
            if isinstance(value, str) and SSN_PATTERN.search(value):
                raise ValueError(f"guardrail blocked: unmasked SSN pattern found in extracted row: {row}")

class GovernanceGapError(Exception):
    pass

DERIVED_CATALOG = {
    "CUSTOMERS": CatalogEntry(object_id=101, name="CUSTOMERS", type_desc="USER_TABLE"),
    "CLAIMS": CatalogEntry(object_id=102, name="CLAIMS", type_desc="USER_TABLE"),
}
DERIVED_LINEAGE = {
    "CLAIMS_SUMMARY": {"target": "CLAIMS_SUMMARY", "sources": ["CLAIMS", "CUSTOMERS"]},
}

def governed_extract(table_name, core_rows, sensitive_fields, catalog=DERIVED_CATALOG, lineage=DERIVED_LINEAGE, guardrail=None):
    if table_name not in catalog:
        raise GovernanceGapError(f"'{table_name}' has no derived catalog entry -- cannot govern an unknown table")
    guardrail = guardrail or GuardRail().add_output_check(check_no_unmasked_ssn)
    return guardrail.run(extract_and_mask, core_rows, sensitive_fields)

core_customers = [{"customer_id": "C1001", "name": "John Smith", "ssn": "219-09-9999"}]
governed_result = governed_extract("CUSTOMERS", core_customers, sensitive_fields=["ssn"])
print(f"governed extract result: {[(r['customer_id'], r['ssn'][:12]) for r in governed_result]}")

Concept 2 — Naming a Data Owner Where None Exists, and Recording the Gap Explicitly


A governance layer needs an accountable owner per table — but a twenty-year-old legacy
estate genuinely has tables with no living owner, the original team long since
reorganized away. The honest move is a real, explicit UNOWNED sentinel value recorded
in the ownership registry, not a silent lookup miss that looks identical to "nobody
checked yet."


Example:


UNOWNED = "UNOWNED -- gap recorded, needs assignment"

DATA_OWNERSHIP_REGISTRY = {
    "CUSTOMERS": "retail_banking_data_steward",
    "CLAIMS": "claims_operations_lead",

def owner_for(table_name):
    return DATA_OWNERSHIP_REGISTRY.get(table_name, UNOWNED)

for table in ("CUSTOMERS", "CLAIMS", "LEGACY_ARCHIVE_1998"):
    print(f"{table}: owner = {owner_for(table)}")

Concept 3 — An Evidence Pack an Auditor Accepts Without Granting Access to the Core


Every previous concept this week produces one fact an auditor would ask for. This concept
assembles them into a single artifact — catalog type, lineage, owner, and a masking
confirmation flag — that an auditor reviews on its own terms, with core_access_granted_ to_auditor hardcoded False because the entire point of this week's governance layer is
answering an auditor's questions WITHOUT ever handing over core access.


Example:


def build_evidence_pack(table_name):
    catalog_entry = DERIVED_CATALOG.get(table_name)
    lineage_entries = [v for v in DERIVED_LINEAGE.values() if table_name in v["sources"] or table_name == v["target"]]
    owner = owner_for(table_name)
    return {
        "table": table_name,
        "catalog_type": catalog_entry.type_desc if catalog_entry else "NO CATALOG ENTRY",
        "lineage": lineage_entries,
        "owner": owner,
        "masking_applied": True,
        "core_access_granted_to_auditor": False,
    }

evidence = build_evidence_pack("CUSTOMERS")
for key, value in evidence.items():
    print(f"{key}: {value}")

BFSI Reality Check — Day 5


Legacy angle: The governed landing zone this week assembled sits entirely OUTSIDE the
core — every piece (catalog, lineage, masking, guardrail) operates on an extracted copy,
because that is the only kind of change this core ever tolerates.


Compliance angle: An UNOWNED gap recorded explicitly in a registry is a real,
auditable finding an organization can act on; an UNOWNED gap that only exists as "the
table isn't in anyone's spreadsheet" is invisible until something goes wrong and someone
asks who was responsible.


What breaks in production: A governed landing zone is built and works well for the
five tables it was piloted against — but the pilot's GovernanceGapError (Concept 1) is
treated as a rare edge case instead of the expected steady state for a twenty-year-old
estate, so when the rollout hits table #6 with no catalog entry, the team's first
instinct is to bypass the guardrail "just this once" rather than treat the gap itself as
the finding the governance layer exists to surface.




Architecture Decision — Week 18


Choosing between: governing the legacy core IN PLACE — building the catalog,
lineage, masking, and guardrail layer this week assembled as a permanent wrapper around a
system that stays exactly where it is — versus a governed COPY under a strangler-fig
migration, where new traffic is gradually redirected to a modern, natively-governed
replacement system while the legacy core is slowly starved of use until it can be
retired.


Rule of thumb: Govern in place when the legacy core's remaining lifespan is short
relative to the cost of a strangler-fig migration, or when the core's business logic is
too poorly understood to safely reimplement — this week's whole governance layer is
explicitly designed for exactly that situation, and it works well there precisely because
it asks nothing of the core itself. Move to a strangler-fig migration once the governance
layer itself becomes the bottleneck — once Day 1's GovernanceGapError and Day 5's
UNOWNED sentinel start firing on a majority of tables rather than a minority, that is a
signal the estate has outgrown "wrap it and extract carefully" and needs the underlying
system replaced, not just governed harder. The two are not mutually exclusive stages: a
strangler-fig migration's whole strategy is routing new traffic to the modern system while
the OLD system, still running underneath, still needs exactly this week's governance
layer for as long as it keeps serving any traffic at all — in-place governance is not
undone by starting a migration, it is what makes the migration period itself safe to run.
