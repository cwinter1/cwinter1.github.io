Concept 1 — A Pydantic-Typed Tool Around dbo.usp_GetPolicyBalance @PolicyNo

The real procedure signature is dbo.usp_GetPolicyBalance @PolicyNo VARCHAR(10) — a bare string parameter with no format check inside the procedure itself, because the original application code was trusted to only ever send a well-formed policy number. An agent cannot be trusted the same way: it can be prompted (or manipulated) into passing anything a string will hold. Wrapping the call in a Pydantic input model with a real pattern constraint enforces the policy-number shape BEFORE the call ever reaches the core, and a typed output model turns whatever the procedure returns into a stable contract the rest of the agent's code can rely on regardless of how the underlying T-SQL changes later.

Example:

from pydantic import BaseModel, Field
from typing import Literal

class GetPolicyBalanceInput(BaseModel):
    policy_no: str = Field(
        ...,
        pattern=r"^POL-\d{6}$",
        description="Maps to @PolicyNo -- the legacy proc has no format check of its own, so the tool enforces one before the call ever reaches the core",
    )

class GetPolicyBalanceOutput(BaseModel):
    policy_no: str
    balance: float
    currency: Literal["USD", "EUR", "GBP"]
    as_of_date: str
    status_code: int = Field(description="raw @ReturnCode OUTPUT parameter from the proc -- 0 = ok, negative = a legacy error the tool surfaces rather than hides")

SIMULATED_CORE_RESPONSES = {
    "POL-100234": {"balance": 18420.55, "currency": "USD", "as_of_date": "2026-09-17", "status_code": 0},
    "POL-999999": {"balance": 0.0, "currency": "USD", "as_of_date": "2026-09-17", "status_code": -2},
}

def call_usp_get_policy_balance(payload: GetPolicyBalanceInput) -> GetPolicyBalanceOutput:
    raw = SIMULATED_CORE_RESPONSES.get(payload.policy_no)
    if raw is None:
        raise LookupError(f"no simulated core response registered for {payload.policy_no}")
    return GetPolicyBalanceOutput(policy_no=payload.policy_no, **raw)

good = call_usp_get_policy_balance(GetPolicyBalanceInput(policy_no="POL-100234"))
print(good.model_dump())

bad_status = call_usp_get_policy_balance(GetPolicyBalanceInput(policy_no="POL-999999"))
print(bad_status.model_dump())

except Exception as e:

Concept 2 — An Explicit Procedure Allowlist Instead of Free-Text SQL


The single most important safety property of a tool layer over a legacy core is that an
agent can never assemble its own SQL — it can only name one of a small, explicitly
allowed set of procedures, each with its own tier and rate limit. A requested name that
isn't on the allowlist is rejected outright, and so is a parameter value that itself
looks like SQL, since a clever prompt could otherwise smuggle a second statement in
through what looks like an ordinary string argument.


Example:


import re

PROCEDURE_ALLOWLIST = {
    "dbo.usp_GetPolicyBalance": {"tier": "read", "max_calls_per_minute": 120},
    "dbo.usp_GetClaimStatus": {"tier": "read", "max_calls_per_minute": 120},
    "dbo.usp_RenewPolicy": {"tier": "write", "max_calls_per_minute": 10},
}

FREE_TEXT_SQL_PATTERN = re.compile(r"\b(SELECT|INSERT|UPDATE|DELETE|DROP|EXEC|EXECUTE)\b", re.IGNORECASE)

class ProcedureNotAllowedError(Exception):
    pass

def resolve_tool_call(requested_name: str) -> dict:
    if requested_name not in PROCEDURE_ALLOWLIST:
        raise ProcedureNotAllowedError(
            f"'{requested_name}' is not on the procedure allowlist -- an agent tool can only "
            f"name a procedure, never assemble SQL text"
        )
    return {"procedure": requested_name, **PROCEDURE_ALLOWLIST[requested_name]}

def reject_if_looks_like_free_text_sql(agent_argument: str) -> None:
    if FREE_TEXT_SQL_PATTERN.search(agent_argument):
        raise ProcedureNotAllowedError(
            f"argument '{agent_argument}' contains a raw SQL keyword -- tools accept typed "
            f"parameters only, never a string an agent assembled itself"
        )

resolved = resolve_tool_call("dbo.usp_GetPolicyBalance")
print(f"resolved allowlisted call: {resolved}")

try:
    resolve_tool_call("dbo.usp_DropAllTables")
except ProcedureNotAllowedError as e:
    print(f"blocked non-allowlisted procedure: {e}")

try:
    reject_if_looks_like_free_text_sql("POL-100234; DROP TABLE POLICIES")
except ProcedureNotAllowedError as e:
    print(f"blocked free-text SQL disguised as a parameter: {type(e).__name__}")

reject_if_looks_like_free_text_sql("POL-100234")
print("a genuinely plain parameter value passes the free-text SQL check")

Concept 3 — Mapping OUTPUT Parameters and Multiple Result Sets Into One Response Schema


A legacy procedure accumulated over twenty years rarely returns just one clean row set.
dbo.usp_GetClaimStatus genuinely does three separate things: it sets an
@TotalPaidToDate OUTPUT parameter, returns a first result set (the claim header), and
returns a second result set (the payment history) that pyodbc's real
cursor.nextset() call is needed to reach. A tool's job is to flatten all three of those
into ONE stable Pydantic response — the caller never needs to know how many result sets
or OUTPUT parameters the underlying T-SQL actually used.


Example:


from typing import List

class FakeLegacyCursor:
    """Shaped exactly like pyodbc's cursor -- fetchall() + nextset() -- standing in
    for a live connection this sandbox does not have."""
    def __init__(self, result_sets, output_params):
        self._result_sets = list(result_sets)
        self._index = 0
        self.output_params = output_params

    def fetchall(self):
        return self._result_sets[self._index]

    def nextset(self):
        self._index += 1
        return self._index < len(self._result_sets)


class PaymentRow(BaseModel):
    payment_date: str
    amount: float


class ClaimStatusResponse(BaseModel):
    claim_id: str
    status: str
    adjuster: str
    payments: List[PaymentRow]
    total_paid_to_date: float  # sourced from the @TotalPaidToDate OUTPUT parameter, not a result set


def map_claim_status_cursor(cursor: FakeLegacyCursor) -> ClaimStatusResponse:
    header_rows = cursor.fetchall()
    claim_id, status, adjuster = header_rows[0]

    has_more = cursor.nextset()
    payments = []
    if has_more:
        for payment_date, amount in cursor.fetchall():
            payments.append(PaymentRow(payment_date=payment_date, amount=amount))

    return ClaimStatusResponse(
        claim_id=claim_id,
        status=status,
        adjuster=adjuster,
        payments=payments,
        total_paid_to_date=cursor.output_params["TotalPaidToDate"],
    )


fake_cursor = FakeLegacyCursor(
    result_sets=[
        [("CLM-4471", "IN_REVIEW", "J.Reyes")],
        [("2026-08-01", 1200.00), ("2026-08-15", 950.50)],
    ],
    output_params={"TotalPaidToDate": 2150.50},
)

response = map_claim_status_cursor(fake_cursor)
print(response.model_dump())
print(f"payments result set merged with the header row and the OUTPUT parameter into one schema: {len(response.payments)} payments, total_paid_to_date={response.total_paid_to_date}")

no_payments_cursor = FakeLegacyCursor(
    result_sets=[[("CLM-9002", "OPENED", "M.Chen")]],
    output_params={"TotalPaidToDate": 0.0},
)
no_payments_response = map_claim_status_cursor(no_payments_cursor)
print(no_payments_response.model_dump())

Concept 4 — Documenting Undocumented Parameter Semantics in the Tool Contract Itself


dbo.usp_RenewPolicy's real @StatusFlag parameter is a single legacy character with no
comment anywhere in the procedure body and no lookup table anywhere in the schema — its
meaning only survives in institutional memory (here: a retired underwriter's paper
notes). A Pydantic Field(description=...) is not decoration; model_json_schema()
turns it into the exact JSON Schema an LLM tool-calling framework reads to decide how to
call the tool, so writing the undocumented meaning into the field description ships that
institutional knowledge with the tool itself, rather than leaving it in someone's head.


Example:


import json

class RenewPolicyInput(BaseModel):
    policy_no: str = Field(..., description="maps to @PolicyNo")
    status_flag: Literal["P", "A", "X", "H"] = Field(
        ...,
        description=(
            "maps to @StatusFlag, a single legacy character undocumented anywhere in the "
            "database itself: 'P' = pending underwriting, 'A' = active/renewed, "
            "'X' = cancelled, 'H' = held for manual review. Discovered from a retired "
            "underwriter's paper notes, not from any schema comment."
        ),
    )
    effective_date: str = Field(..., description="maps to @EffectiveDate, format YYYY-MM-DD")


schema = RenewPolicyInput.model_json_schema()
status_flag_doc = schema["properties"]["status_flag"]["description"]
print(f"status_flag description length: {len(status_flag_doc)} chars")
print(f"status_flag description mentions all four legacy codes: {all(code in status_flag_doc for code in ('pending', 'active', 'cancelled', 'held'))}")

BFSI Reality Check — Day 1


Legacy angle: usp_RenewPolicy's @StatusFlag meaning genuinely came from a retired
employee's notes, not from the database — the tool contract this concept builds is often
the FIRST time that meaning has ever been written down anywhere a machine can read it.


Compliance angle: A typed, allowlisted tool boundary is itself an audit artifact — a
regulator asking "what could this agent possibly have done to the core" gets answered by
reading PROCEDURE_ALLOWLIST, not by reverse-engineering a transcript of every SQL
statement the agent could theoretically have generated.


What breaks in production: GetPolicyBalanceInput's pattern=r"^POL-\d{6}$" assumes
every policy number in the core follows that shape — but a core running for twenty years
often has a handful of legacy records from BEFORE the current numbering convention was
adopted, whose real @PolicyNo values don't match the pattern at all. A tool this strict
correctly blocks SQL injection but will also silently refuse to ever look up those old
records, and that gap needs a deliberate decision (a second allowed pattern, or an
explicit legacy-record exception list), not a regex tightened in isolation without
checking what's actually in the core.

Concept 1 — GRANT EXECUTE on Individual Procedures, No Underlying Table Rights


The real, minimal grant for a service account that only ever calls procedures is GRANT EXECUTE ON dbo.usp_GetPolicyBalance TO svc_agent_reader — with no accompanying GRANT SELECT ON POLICIES at all. That account can run the two procedures it was explicitly
granted EXECUTE on and genuinely cannot query any table directly, even the tables those
same procedures read from internally. This is the real least-privilege boundary a legacy
core's own permission system already provides, before any application-level allowlist
gets involved.


Example:


import dataclasses

class GrantSet:
    def __init__(self, principal, procedure_execute_grants, table_direct_grants):
        self.principal = principal
        self.procedure_execute_grants = procedure_execute_grants
        self.table_direct_grants = table_direct_grants

SVC_AGENT_READER_GRANTS = GrantSet(
    principal="svc_agent_reader",
    procedure_execute_grants={"dbo.usp_GetPolicyBalance", "dbo.usp_GetClaimStatus"},
    table_direct_grants={},  # genuinely empty -- no direct table access at all
)

def can_execute_procedure(grants: GrantSet, procedure: str) -> bool:
    return procedure in grants.procedure_execute_grants

def can_query_table_directly(grants: GrantSet, table: str, permission: str) -> bool:
    return permission in grants.table_direct_grants.get(table, set())

print(f"svc_agent_reader can EXECUTE usp_GetPolicyBalance: {can_execute_procedure(SVC_AGENT_READER_GRANTS, 'dbo.usp_GetPolicyBalance')}")
print(f"svc_agent_reader can SELECT directly against POLICIES: {can_query_table_directly(SVC_AGENT_READER_GRANTS, 'POLICIES', 'SELECT')}")
print(f"svc_agent_reader can EXECUTE an unlisted procedure: {can_execute_procedure(SVC_AGENT_READER_GRANTS, 'dbo.usp_DeleteAllPolicies')}")

blast_radius = f"limited to exactly what {len(SVC_AGENT_READER_GRANTS.procedure_execute_grants)} allowlisted procedures do internally, zero direct table rights"
print(f"blast radius: {blast_radius}")

Concept 2 — EXECUTE AS and Definer's-Rights Packages as the Real Privilege Boundary


CREATE PROCEDURE dbo.usp_RenewPolicy WITH EXECUTE AS OWNER AS ... is real T-SQL syntax:
every statement inside that procedure body runs under the PROCEDURE OWNER's own
permissions, not the caller's — Oracle's PL/SQL package works the same way by default
(definer's rights, unless the package is explicitly declared AUTHID CURRENT_USER). This
means Concept 1's caller-side grants are not the real privilege boundary at all once
EXECUTE AS OWNER is in play — the real boundary is whatever tables and operations the
PROCEDURE BODY itself touches, which a caller with zero direct table rights can still
trigger.


Example:


class ProcedureDefinition:
    def __init__(self, name, execute_as, tables_touched):
        self.name = name
        self.execute_as = execute_as  # "OWNER" (definer's rights) or "CALLER" (invoker's rights)
        self.tables_touched = tables_touched  # table -> set of operations the BODY performs

USP_RENEW_POLICY = ProcedureDefinition(
    name="dbo.usp_RenewPolicy",
    execute_as="OWNER",
    tables_touched={"POLICIES": {"SELECT", "UPDATE"}, "POLICY_HISTORY": {"INSERT"}},
)

def real_blast_radius(proc: ProcedureDefinition) -> dict:
    if proc.execute_as == "OWNER":
        # the caller's own grants are irrelevant -- the body's own table touches ARE the boundary
        return {table: sorted(ops) for table, ops in proc.tables_touched.items()}
    raise NotImplementedError("invoker's-rights boundary needs the caller's own grants")

radius = real_blast_radius(USP_RENEW_POLICY)
print(f"usp_RenewPolicy real blast radius (EXECUTE AS OWNER, caller grants irrelevant): {radius}")

caller_grants = {"POLICIES": set(), "POLICY_HISTORY": set()}  # svc_agent_writer: EXECUTE only, zero direct table rights
print(f"caller's own direct table grants (irrelevant under EXECUTE AS OWNER): {caller_grants}")
print(f"the procedure can UPDATE POLICIES even though the caller has zero direct rights on it: {'UPDATE' in radius['POLICIES']}")

Concept 3 — Read, Dry-Run, and Write Tools in Distinct Permission Tiers


Not every tool in an agent's registry should be reachable by every calling role. Tagging
each ToolDefinition with an explicit tier — READ (changes nothing), DRY_RUN (asks
the procedure to validate/plan without committing, a real capability a write procedure
needs to be deliberately built with), or WRITE (actually commits) — and checking a
calling role's allowed tier SET at authorization time keeps an analyst-level agent role
from ever reaching a write-tier tool at all, regardless of what the underlying model
decides to attempt.


Example:


from pydantic import BaseModel
from typing import Literal

class ToolDefinition(BaseModel):
    name: str
    procedure: str
    tier: Literal["READ", "DRY_RUN", "WRITE"]

TOOL_REGISTRY = [
    ToolDefinition(name="get_policy_balance", procedure="dbo.usp_GetPolicyBalance", tier="READ"),
    ToolDefinition(name="preview_policy_renewal", procedure="dbo.usp_RenewPolicy_DryRun", tier="DRY_RUN"),
    ToolDefinition(name="renew_policy", procedure="dbo.usp_RenewPolicy", tier="WRITE"),
]

ROLE_ALLOWED_TIERS = {
    "agent_analyst": {"READ", "DRY_RUN"},
    "agent_operator": {"READ", "DRY_RUN", "WRITE"},
}

class ToolAccessDeniedError(Exception):
    pass

def authorize_tool_call(role: str, tool_name: str) -> ToolDefinition:
    tool = next((t for t in TOOL_REGISTRY if t.name == tool_name), None)
    if tool is None:
        raise ToolAccessDeniedError(f"'{tool_name}' is not a registered tool")
    allowed = ROLE_ALLOWED_TIERS.get(role, set())
    if tool.tier not in allowed:
        raise ToolAccessDeniedError(f"role '{role}' is not permitted to call a {tool.tier}-tier tool ('{tool_name}')")
    return tool

analyst_read = authorize_tool_call("agent_analyst", "get_policy_balance")
print(f"agent_analyst -> get_policy_balance: authorized, tier={analyst_read.tier}")

try:
    authorize_tool_call("agent_analyst", "renew_policy")
except ToolAccessDeniedError as e:
    print(f"agent_analyst -> renew_policy: {e}")

operator_write = authorize_tool_call("agent_operator", "renew_policy")
print(f"agent_operator -> renew_policy: authorized, tier={operator_write.tier}")

Concept 1 — CLOSED/OPEN/HALF-OPEN Retuned for a Core That Blocks for Minutes


CircuitBreaker below is copied in unchanged from
Curriculum/Week_8_Production/W8_D5_Final_Project.ipynb's real "Circuit Breaker & Model
Fallback Chain" concept, per this week's [legacy thread] copy-in — the same three-state
CLOSED/OPEN/HALF-OPEN machine originally tuned for a flaky LLM API that fails FAST, in
milliseconds. That tuning is exactly wrong here: a legacy core call that eventually
SUCCEEDS but takes minutes to do it is not a "failure" under the original .call()
alone, so this concept adds a latency-budget wrapper that turns a too-slow-but-successful
call into a real circuit-breaker failure, and retunes the breaker itself with a lower
failure_threshold and a much longer cooldown_seconds — giving up fast and staying
quiet, rather than hammering an already-struggling core every few seconds.


Example:


import time
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class CircuitBreaker:
    """Simple circuit breaker with three states."""
    failure_threshold: int   = 3
    cooldown_seconds:  float = 10.0
    _failures:  int   = field(default=0, repr=False)
    _state:     str   = field(default='CLOSED', repr=False)
    _opened_at: float = field(default=0.0, repr=False)

    def call(self, fn: Callable, *args, **kwargs):
        if self._state == 'OPEN':
            if time.monotonic() - self._opened_at < self.cooldown_seconds:
                raise RuntimeError(f'Circuit OPEN — blocked ({self._failures} failures)')
            self._state = 'HALF-OPEN'
        try:
            result = fn(*args, **kwargs)
            self._failures = 0
            self._state    = 'CLOSED'
            return result
        except Exception as e:
            self._failures += 1
            if self._failures >= self.failure_threshold:
                self._state    = 'OPEN'
                self._opened_at = time.monotonic()
            raise


class SlowCallExceedsBudget(Exception):
    pass


def call_with_latency_budget(breaker: CircuitBreaker, fn, latency_budget_seconds: float, *args, **kwargs):
    """Even a call that eventually SUCCEEDS still counts as a circuit-breaker failure if
    it blows past the latency budget -- a legacy core holding a connection open for
    minutes is exactly the failure mode Week 8's original fast-fail LLM tuning never had
    to handle."""
    def timed_call():
        start = time.monotonic()
        result = fn(*args, **kwargs)
        elapsed = time.monotonic() - start
        if elapsed > latency_budget_seconds:
            raise SlowCallExceedsBudget(f"call exceeded its {latency_budget_seconds}s latency budget")
        return result
    return breaker.call(timed_call)


# Week 8's original tuning: failure_threshold=3, cooldown_seconds=10 (fits a flaky API
# retried within seconds). Week 22's core-tuned breaker: a lower failure_threshold=2
# (the nightly batch window means the agent should give up FAST, not hammer a busy core)
# and a much longer cooldown_seconds=300 (5 minutes -- retrying a blocked core every 10
# seconds just adds more load to something already struggling).
core_breaker = CircuitBreaker(failure_threshold=2, cooldown_seconds=300.0)

def instant_call():
    return "ok"

def slow_call():
    time.sleep(0.05)
    return "ok, but slow"

result1 = call_with_latency_budget(core_breaker, instant_call, latency_budget_seconds=1.0)
print(f"fast call within budget: {result1}, breaker state after: {core_breaker._state}")

for attempt in range(2):
    try:
        call_with_latency_budget(core_breaker, slow_call, latency_budget_seconds=0.01)
    except SlowCallExceedsBudget as e:
        print(f"attempt {attempt + 1}: {e}, breaker state: {core_breaker._state}, failures: {core_breaker._failures}")

try:
    call_with_latency_budget(core_breaker, instant_call, latency_budget_seconds=1.0)
except RuntimeError as e:
    print(f"third attempt while OPEN: {e}")

Concept 2 — Statement Timeouts and LOCK_TIMEOUT So an Agent Cannot Hold Locks


SET LOCK_TIMEOUT <ms> (SQL Server) and Oracle's session-level statement/DDL timeout
settings are the real server-side defense against an agent's call holding a lock the
nightly batch needs — no live core exists in this sandbox to prove the server-side abort,
but the CLIENT-side backstop an agent tool adds on top of it (a hard wall-clock deadline
that gives up on a call regardless of what the server eventually does) is genuinely
executable: a background thread runs the call, and the calling code refuses to wait past
its own deadline, treating a still-running call as blocked rather than retrying it
against a core that may be mid-batch.


Example:


import threading

class StatementTimeoutError(Exception):
    pass

def call_with_statement_timeout(fn, timeout_seconds, *args, **kwargs):
    result_box = {}
    def target():
        try:
            result_box["value"] = fn(*args, **kwargs)
        except Exception as e:
            result_box["error"] = e

    thread = threading.Thread(target=target, daemon=True)
    thread.start()
    thread.join(timeout=timeout_seconds)
    if thread.is_alive():
        raise StatementTimeoutError(
            f"call did not return within the {timeout_seconds}s LOCK_TIMEOUT -- treated as "
            f"blocked, NOT retried against a core that may be mid-batch"
        )
    if "error" in result_box:
        raise result_box["error"]
    return result_box["value"]

    return {"policy_no": "POL-100234", "balance": 18420.55}

def blocked_by_nightly_batch():
    time.sleep(1.0)  # simulates a real lock held by the nightly batch job
    return "should never get here within the timeout"

    print(f"blocked call correctly timed out: {e}")

Concept 3 — Connection-Pool Starvation and Bulkhead Isolation Per Tool


A single shared connection pool means one slow tool (a report procedure that genuinely
takes minutes) can hold every connection in the pool, starving a completely unrelated
fast tool that has nothing to do with the slow one. A BULKHEAD — borrowed from ship
design, where separate watertight compartments keep one hull breach from sinking the
whole vessel — gives each tool its own small, dedicated pool instead. A real
threading.Semaphore-backed pool genuinely blocks or raises when a tool's own bulkhead
is exhausted, with zero effect on any other tool's pool.


Example:


import threading

class PoolExhaustedError(Exception):
    pass

class BulkheadPool:
    def __init__(self, tool_name, size):
        self.tool_name = tool_name
        self._semaphore = threading.Semaphore(size)
        self.size = size

    def acquire(self, blocking=False):
        acquired = self._semaphore.acquire(blocking=blocking)
        if not acquired:
            raise PoolExhaustedError(f"'{self.tool_name}' bulkhead exhausted (size={self.size}) -- other tools' pools are unaffected")
        return acquired

    def release(self):
        self._semaphore.release()


REPORT_POOL = BulkheadPool("run_slow_report", size=1)
BALANCE_POOL = BulkheadPool("get_policy_balance", size=3)

REPORT_POOL.acquire()  # simulates one long-running report call holding its only connection
print("run_slow_report holds its single bulkhead connection")

try:
    REPORT_POOL.acquire()
except PoolExhaustedError as e:
    print(f"a second concurrent run_slow_report call: {e}")

balance_conn = BALANCE_POOL.acquire()
print(f"get_policy_balance still acquires its own connection fine, unaffected by run_slow_report's exhausted pool: {balance_conn}")

REPORT_POOL.release()
print("run_slow_report released its connection")
REPORT_POOL.acquire()
print("a fresh run_slow_report call can now acquire the bulkhead again")

Concept 4 — Degraded Fallback Answers While the Core Is Inside Its Batch Window


The nightly batch window is a KNOWN, scheduled maintenance period, not a surprise
failure — an agent tool can check the current time against that window BEFORE even
attempting a call, and serve a degraded, clearly-labelled-as-stale last-known-good answer
instead of hammering a core that predictably cannot answer right now. The window itself
often wraps past midnight (23:00-02:00), which the membership check has to handle
explicitly rather than assuming a simple start <= now <= end always works.


Example:


import datetime

BATCH_WINDOW_START = datetime.time(23, 0)
BATCH_WINDOW_END = datetime.time(2, 0)  # wraps past midnight

def is_inside_batch_window(now: datetime.time) -> bool:
    if BATCH_WINDOW_START <= BATCH_WINDOW_END:
        return BATCH_WINDOW_START <= now <= BATCH_WINDOW_END
    # window wraps midnight: inside if AFTER start OR BEFORE end
    return now >= BATCH_WINDOW_START or now <= BATCH_WINDOW_END


LAST_KNOWN_GOOD_CACHE = {
    "POL-100234": {"balance": 18102.10, "as_of_date": "2026-09-16", "stale": True},
}

        if cached is None:
            raise RuntimeError(f"core is inside its batch window and no cached value exists for {policy_no}")
        return {**cached, "degraded": True, "reason": "core inside nightly batch window, serving last-known-good"}
    return {**live_call(policy_no), "degraded": False}

Concept 1 — A Submit, Poll, Fetch Tool Triple for Work That Is Not Request-Response


A mainframe batch job (a JCL-submitted nightly claims run, a policy renewal batch) has no
single call that both starts it and returns its result — the real shape is three
separate tools: SUBMIT (returns a job ticket immediately; the job runs asynchronously),
POLL (checks status by ticket, cheap, safe to call repeatedly), and FETCH (retrieves the
actual result, only valid once POLL reports completion). Modeling this as three tools,
not one blocking call, is what lets an agent do other work while a job that may take
twenty minutes runs in the background — and what stops it from ever fetching a result
that doesn't exist yet.


Example:


from pydantic import BaseModel
from typing import Literal, Optional

class SubmitJobInput(BaseModel):
    job_type: Literal["CLAIMS_EXTRACT", "POLICY_RENEWAL_BATCH"]
    params: dict

class JobTicket(BaseModel):
    job_id: str
    status: Literal["QUEUED", "RUNNING", "COMPLETE", "FAILED"]

class JobResult(BaseModel):
    job_id: str
    output_dataset: Optional[str] = None
    row_count: Optional[int] = None


class InMemoryJobStore:
    """Stands in for the real mainframe job scheduler -- no live JES/JCL submission
    exists in this sandbox, but the submit/poll/fetch state machine an agent tool wraps
    around it is genuinely exercised."""
    def __init__(self):
        self._jobs = {}

    def submit(self, payload: SubmitJobInput) -> JobTicket:
        job_id = f"JOB{len(self._jobs) + 1:06d}"
        self._jobs[job_id] = {"status": "QUEUED", "payload": payload, "result": None}
        return JobTicket(job_id=job_id, status="QUEUED")

    def advance(self, job_id: str, new_status: str, result: dict = None) -> None:
        """Test-only hook standing in for the real scheduler's own state transitions
        over wall-clock time."""
        self._jobs[job_id]["status"] = new_status
        if result is not None:
            self._jobs[job_id]["result"] = result

    def poll(self, job_id: str) -> JobTicket:
        job = self._jobs[job_id]
        return JobTicket(job_id=job_id, status=job["status"])

    def fetch(self, job_id: str) -> JobResult:
        job = self._jobs[job_id]
        if job["status"] != "COMPLETE":
            raise RuntimeError(f"job {job_id} is not COMPLETE yet (status={job['status']}) -- poll before fetching")
        return JobResult(job_id=job_id, **job["result"])

Concept 2 — Job Ticket Identifiers and Idempotency Keys Against Double Submission


A network timeout between an agent submitting a job and receiving the acknowledgment does
NOT mean the submission failed — the mainframe may have genuinely queued it anyway. A
naive retry that resubmits blindly can double-run a real batch job: double-paying claims,
double-renewing policies. Keying the store by a CALLER-supplied idempotency_key (never
generated server-side — the retry has to send the SAME key deliberately) means a retry
with the same key returns the EXISTING job ticket instead of creating a second one.


Example:


class SubmitJobInputWithKey(BaseModel):
    job_type: Literal["CLAIMS_EXTRACT", "POLICY_RENEWAL_BATCH"]
    params: dict
    idempotency_key: str


class IdempotentJobStore:
    def __init__(self):
        self._jobs = {}
        self._by_idempotency_key = {}

    def submit(self, payload: SubmitJobInputWithKey) -> JobTicket:
        existing_job_id = self._by_idempotency_key.get(payload.idempotency_key)
        if existing_job_id is not None:
            job = self._jobs[existing_job_id]
            return JobTicket(job_id=existing_job_id, status=job["status"])
        job_id = f"JOB{len(self._jobs) + 1:06d}"
        self._jobs[job_id] = {"status": "QUEUED", "payload": payload}
        self._by_idempotency_key[payload.idempotency_key] = job_id
        return JobTicket(job_id=job_id, status="QUEUED")

Concept 4 — Batch-Window and Cutoff Constraints Encoded in the Tool


A same-day CLAIMS_EXTRACT job submitted after the real 20:00 cutoff misses that night's
batch window entirely and genuinely runs the FOLLOWING business day — a hard constraint
of the mainframe's own job scheduling calendar, not something a prompt should be trusted
to remember. Encoding it in the tool means the agent's response to "submit today's
claims extract" at 21:00 correctly says "queued for tomorrow," not a false promise of
same-day completion.


Example:


import datetime

SAME_DAY_CUTOFF = datetime.time(20, 0)

class ScheduledSubmission(BaseModel):
    requested_at: str
    scheduled_run_date: str
    same_day: bool


def schedule_batch_submission(requested_at: datetime.datetime) -> ScheduledSubmission:
    if requested_at.time() < SAME_DAY_CUTOFF:
        run_date = requested_at.date()
        same_day = True
    else:
        run_date = requested_at.date() + datetime.timedelta(days=1)
        same_day = False
    return ScheduledSubmission(
        requested_at=requested_at.isoformat(),
        scheduled_run_date=run_date.isoformat(),
        same_day=same_day,
    )


before_cutoff = schedule_batch_submission(datetime.datetime(2026, 9, 17, 14, 30))
print(f"submitted before the 20:00 cutoff: {before_cutoff.model_dump()}")

after_cutoff = schedule_batch_submission(datetime.datetime(2026, 9, 17, 21, 15))

Concept 1 — Logging Every Tool Call With Arguments, Principal, and Legacy Return Code


Every tool this week built needs one audit log entry recording: which tool, what
arguments, WHICH calling principal (never a shared service account, per Day 2), and the
legacy return code the core actually gave back — enough to replay exactly what happened
later, for an incident review or a regulator's request, without having to reconstruct it
from scattered application logs.


Example:


from pydantic import BaseModel

class ToolCallAuditEntry(BaseModel):
    sequence: int
    tool_name: str
    arguments: dict
    calling_principal: str
    legacy_return_code: int
    result_summary: str


class AuditLog:
    def __init__(self):
        self._entries = []

    def record(self, tool_name: str, arguments: dict, calling_principal: str, legacy_return_code: int, result_summary: str) -> ToolCallAuditEntry:
        entry = ToolCallAuditEntry(
            sequence=len(self._entries) + 1,
            tool_name=tool_name,
            arguments=arguments,
            calling_principal=calling_principal,
            legacy_return_code=legacy_return_code,
            result_summary=result_summary,
        )
        self._entries.append(entry)
        return entry

    def all_entries(self):
        return list(self._entries)

    def entries_for_principal(self, calling_principal: str):
        return [e for e in self._entries if e.calling_principal == calling_principal]

Concept 2 — Shadow Mode: the Agent Drafts, a Human Commits Before Any Write Lands


Shadow mode: the agent DRAFTS a write action — which procedure, which arguments — but
never actually executes it. A human reviews the draft and explicitly commits it before
the real call reaches the core. This is a separate safety layer from Day 2's permission
tiers: even a human with WRITE-tier access can require an explicit second approval step
before an agent-originated write goes live, and a draft that is never approved (or is
explicitly rejected) can never reach commit no matter what the agent proposed.


Example:


from typing import Literal, Optional

class WriteDraft(BaseModel):
    draft_id: str
    tool_name: str
    arguments: dict
    proposed_by: str  # the agent's own identity, never a human's
    status: Literal["DRAFT", "APPROVED", "REJECTED", "COMMITTED"] = "DRAFT"
    approved_by: Optional[str] = None


class ShadowModeError(Exception):
    pass


class ShadowModeGateway:
    def __init__(self):
        self._drafts = {}

    def draft(self, tool_name: str, arguments: dict, proposed_by: str) -> WriteDraft:
        draft_id = f"DRAFT{len(self._drafts) + 1:04d}"
        write_draft = WriteDraft(draft_id=draft_id, tool_name=tool_name, arguments=arguments, proposed_by=proposed_by)
        self._drafts[draft_id] = write_draft
        return write_draft

    def approve(self, draft_id: str, approved_by: str) -> WriteDraft:
        draft = self._drafts[draft_id]
        draft.status = "APPROVED"
        draft.approved_by = approved_by
        return draft

    def reject(self, draft_id: str, rejected_by: str) -> WriteDraft:
        draft = self._drafts[draft_id]
        draft.status = "REJECTED"
        draft.approved_by = rejected_by
        return draft

    def commit(self, draft_id: str, execute_fn) -> dict:
        draft = self._drafts[draft_id]
        if draft.status != "APPROVED":
            raise ShadowModeError(f"draft {draft_id} is {draft.status}, not APPROVED -- a human must approve before any write reaches the core")
        result = execute_fn(draft.arguments)
        draft.status = "COMMITTED"
        return result

    tool_name="renew_policy",
    arguments={"policy_no": "POL-100234", "status_flag": "A"},
    proposed_by="agent_operator",
)

    return {"status": "renewed", "policy_no": args["policy_no"]}

Concept 3 — Deterministic Replay Against the Week 19 Checkpointer


Week 19's real SqliteSaver checkpointer (genuinely reused, not reimplemented) durably
records every state transition a LangGraph run makes, keyed by thread_id. Feeding this
week's own audit-log entries through a graph node — one graph step per recorded tool
call — turns the checkpointer's own history into a DETERMINISTIC replay of exactly what
the agent did, in exactly the order it did it: any past checkpoint is individually
addressable by its own checkpoint_id, independent of the in-memory AuditLog object
that originally recorded it.


Example:


import sqlite3
from typing import TypedDict
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.sqlite import SqliteSaver

class ReplayState(TypedDict):
    applied_calls: list  # plain overwrite -- each invoke passes the FULL snapshot
                          # explicitly, so there is no ambiguity about how updates merge

def apply_one_call(state: ReplayState) -> ReplayState:
    return state

builder = StateGraph(ReplayState)
builder.add_node("apply_call", apply_one_call)
builder.set_entry_point("apply_call")
builder.add_edge("apply_call", END)

conn = sqlite3.connect(":memory:", check_same_thread=False)
checkpointer = SqliteSaver(conn)
graph = builder.compile(checkpointer=checkpointer)

REPLAYED_AUDIT_ENTRIES = [
    {"sequence": 1, "tool_name": "get_policy_balance", "calling_principal": "jreyes"},
    {"sequence": 2, "tool_name": "renew_policy", "calling_principal": "jreyes"},
    {"sequence": 3, "tool_name": "get_policy_balance", "calling_principal": "mchen"},
]

config = {"configurable": {"thread_id": "run-2026-09-17-001"}}
applied_so_far = []
for entry in REPLAYED_AUDIT_ENTRIES:
    applied_so_far = applied_so_far + [f"#{entry['sequence']} {entry['calling_principal']} -> {entry['tool_name']}"]
    graph.invoke({"applied_calls": applied_so_far}, config=config)

final_state = graph.get_state(config)
print(f"final checkpointed state after replaying {len(REPLAYED_AUDIT_ENTRIES)} audit entries: {final_state.values['applied_calls']}")

# walk the checkpoint history (newest first, as get_state_history returns it) and find the
# most recent checkpoint whose applied_calls has exactly 2 entries -- proving an earlier
# point in the run is individually addressable, not just the final state
history = list(graph.get_state_history(config))

replayed_at_checkpoint = graph.get_state({"configurable": {"thread_id": "run-2026-09-17-001", "checkpoint_id": two_call_checkpoint.config["configurable"]["checkpoint_id"]}})

same_thread_new_checkpointer_state = fresh_graph.get_state(config)

Legacy angle: legacy_return_code in ToolCallAuditEntry is not decorative — it is
often the ONLY signal a legacy core ever gives back about why a call failed, and it needs
to survive into the audit trail verbatim, not translated into a friendlier message that
loses the original code a mainframe operator would recognize.


Compliance angle: Shadow mode's proposed_by/approved_by split on WriteDraft is
the literal artifact a SOX or model-risk review asks for: proof that a specific human,
identified by name, made the actual commit decision, with the agent's own proposal
preserved unmodified alongside it.


What breaks in production: ShadowModeGateway's _drafts dict is in-memory only —
in a real deployment, a draft awaiting approval has to survive a process restart between
when the agent proposes it and when a human gets around to reviewing it hours later, or
every unapproved draft silently vanishes the moment the service redeploys. The Week 19
checkpointer this concept genuinely reused for run replay is exactly the kind of durable
store a production shadow-mode queue would need too — the same mechanism, applied to a
different problem.




Architecture Decision — Week 22


Choosing between: agent writes directly (a WRITE-tier tool call reaches the legacy
core the moment the agent decides to call it, with permission tiers and circuit breakers
as the only gates) vs. agent drafts, human commits (every write becomes a
ShadowModeGateway draft — Day 5's Concept 2 — that sits in DRAFT status until a named
human explicitly approves it, and only THEN can commit reach the core).


Rule of thumb: use agent writes directly when the tool's own blast radius is small
and well-understood (a single, well-scoped procedure like dbo.usp_RenewPolicy, called
under a WRITE-tier permission already bound to a specific requesting user per Day 2,
with a circuit breaker and bulkhead already limiting how much damage a malfunction can do
per Day 3) AND the action is easily and cheaply reversible if wrong. Move to agent
drafts, human commits the moment any one of those conditions breaks: the procedure's
EXECUTE AS OWNER body touches more tables than the caller's own grants would suggest
(Day 2, Concept 2), the action is expensive or slow to reverse (a mainframe batch job
already submitted and running, per Day 4 — there is no UNDO tool for a JCL job halfway
through), or the organization's own risk appetite for THIS specific procedure (a claims
payment, a policy cancellation) is lower than for a read-only balance lookup, regardless
of how well-scoped the write tool otherwise is.


In practice this is not a single track-wide choice — it is a PER-TOOL decision, made
explicit in the same ToolDefinition/tier metadata Day 2 Concept 3 already attaches to
every tool, not left to be inferred from the tool's name. A newly-added write tool
defaults to agent drafts, human commits until its own blast radius, reversibility, and
audit-trail track record earn it a deliberate, documented promotion to direct-write —
never the other way around, and never assumed from a tool that merely LOOKS safe.
