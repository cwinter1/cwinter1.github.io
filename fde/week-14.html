Concept 1 — AnalyzerEngine.analyze() and the RecognizerResult span

Claims

  • AnalyzerEngine is the detection half of Presidio. It runs a set of recognizers over text and returns a list of RecognizerResult objects — it does not modify the text. Changing the text is AnonymizerEngine's job (Day 3).
  • Each RecognizerResult carries four things that matter: entity_type, start, end, and score. The span is a character offset pair into the original string, which is what makes downstream masking possible without re-finding anything.
  • Recognizers are independent and overlapping by design. The same character range can come back under several entity types at several scores, and nothing in Presidio resolves that for you by default — the caller decides.
  • The engine needs an NLP backend for the model-driven recognizers (PERSON, LOCATION, ORGANIZATION, DATE_TIME). Pattern-driven ones (CREDIT_CARD, IBAN_CODE) are regex plus validation and do not depend on it.

Example:

# EXECUTED
from presidio_analyzer import AnalyzerEngine
from presidio_analyzer.nlp_engine import NlpEngineProvider

# Presidio's documented default is en_core_web_lg; this sandbox has en_core_web_sm,
# so the model is named explicitly rather than left to the default.
provider = NlpEngineProvider(nlp_configuration={
    "nlp_engine_name": "spacy",
    "models": [{"lang_code": "en", "model_name": "en_core_web_sm"}],
})
analyzer = AnalyzerEngine(nlp_engine=provider.create_engine())

claim_note = (
    "Adjuster note: spoke with Dana Cohen about claim CLM-2291. "
    "Teudat Zehut 123456782 on file. Refund issued to card 4111111111111111, "
    "settlement wired to IBAN IL620108000000099999999."
)

results = analyzer.analyze(text=claim_note, language="en")
print("total RecognizerResult objects:", len(results))
print()
# entity_type breaks score ties so this listing is reproducible run to run
for r in sorted(results, key=lambda r: (r.start, -r.score, r.entity_type)):
    print(f"{r.entity_type:<18}{r.start:>4}-{r.end:<4}score={r.score:.2f}  "
          f"{claim_note[r.start:r.end]!r}")

Concept 2 — score_threshold and an explicit entities list


Claims


    

  • analyze() takes an entities list. Passing it restricts detection to those types and
is the single most effective way to cut false positives, because most noise comes from
recognizers you never wanted.
    • 

  • score_threshold drops results below a confidence floor. It is coarser than it looks:
Presidio scores are mostly recognizer-defined constants, not a smooth distribution, so
the threshold behaves like a step function.
    • 

  • Restricting entities is a compliance decision, not a tuning one. The list is the written
answer to "which categories of personal data does this pipeline claim to handle", and it
belongs in the same document as your DPIA.
    • 



Example:


# EXECUTED -- continues from Concept 1's analyzer and claim_note
WANTED = ["PERSON", "CREDIT_CARD", "IBAN_CODE", "US_BANK_NUMBER"]

filtered = analyzer.analyze(
    text=claim_note,
    language="en",
    entities=WANTED,
    score_threshold=0.5,
)

The threshold sweep is the more instructive half, because it does not behave like a dial.
Every value from 0.3 through 0.85 gives the same seven results. That is not a bug — it is
what happens when scores cluster on a handful of recognizer-defined constants (0.01, 0.05,

feels like tightening and changes nothing; turning it from 0.85 to 1.0 feels like a small
step and silently discards the PERSON match, because NER results land at 0.85 and only
checksum-validated pattern matches reach 1.00.


So a threshold of 1.0 on a claims pipeline means "mask card numbers and IBANs, and let
every customer name through." Anyone tuning this by feel, without printing the score
distribution first, will ship that.

Concept 3 — Why regex alone is not a masking strategy, and where the Israeli gap is


Claims


    

  • A regex catches things with shape: card numbers, IBANs, fixed-length IDs. It cannot
catch a person's name, because names have no shape — they are identified by context and
statistics, which is exactly what the NER model is for.
    • 

  • Presidio ships no Israeli entity. There is no IL_ID, no IL_TEUDAT_ZEHUT, nothing in
the IL_* namespace. A nine-digit Teudat Zehut therefore falls through to whichever
US-centric or model-driven recognizer happens to fire on nine digits.
    • 

  • Worse, Presidio's response to a Teudat Zehut is identical whether or not its check
digit is valid, because none of the recognizers firing on it know the checksum rule. A
valid ID and a random nine-digit string are indistinguishable to the default engine.
    • 

  • That is the argument for Day 2's custom recognizer, and it is a validation argument
rather than a pattern one: \d{9} is trivial, the checksum is what separates an ID from
an account number.
    • 



Example:


# EXECUTED -- continues from Concept 1's analyzer, claim_note and results
import re

CARD_RE = re.compile(r"\b\d{4}[ -]?\d{4}[ -]?\d{4}[ -]?\d{4}\b")
IBAN_RE = re.compile(r"\b[A-Z]{2}\d{2}[A-Z0-9]{11,30}\b")
ID9_RE = re.compile(r"\b\d{9}\b")


def regex_only_spans(text):
    spans = []
    for label, rx in (("CARD", CARD_RE), ("IBAN", IBAN_RE), ("ID9", ID9_RE)):
        for m in rx.finditer(text):
            spans.append((label, m.start(), m.end()))
    return sorted(spans, key=lambda s: s[1])


regex_spans = regex_only_spans(claim_note)
print("regex-only found:")
for label, s, e in regex_spans:
    print(f"  {label:<6}{claim_note[s:e]!r}")

analyzer_person = [r for r in results if r.entity_type == "PERSON"]
print()
print("what regex structurally cannot find:")
for r in analyzer_person:
    covered = any(s <= r.start and r.end <= e for _, s, e in regex_spans)
    print(f"  PERSON {claim_note[r.start:r.end]!r} covered by any regex span: {covered}")


def teudat_zehut_valid(digits):
    """Israeli ID check digit: alternate weights 1,2 across 9 digits, sum the
    digits of each product, total must be divisible by 10."""
    if len(digits) != 9 or not digits.isdigit():
        return False
    total = 0
    for i, ch in enumerate(digits):
        p = int(ch) * (1 if i % 2 == 0 else 2)
        total += p if p < 10 else p - 9
    return total % 10 == 0


print()
for candidate in ("123456782", "123456789", "000000018"):
    labels = sorted({r.entity_type for r in
                     analyzer.analyze(text=f"ID {candidate} on file.", language="en")})
    print(f"  {candidate}  checksum_valid={teudat_zehut_valid(candidate)!s:<5} "
          f"presidio_says={labels}")

And the Teudat Zehut lines are the one to sit with. All three nine-digit strings come back
with essentially the same US-centric label set. The valid ID 123456782 and the invalid
123456789 are treated the same, because nothing in that label set validates an Israeli
check digit — US_SSN fires on one and not the other purely as an artifact of its own
unrelated pattern rules, not because it knows anything about Teudat Zehut. If your
compliance register says "Israeli national ID numbers are detected and masked", the
default engine does not support that claim.

BFSI Reality Check — Day 1


Legacy angle. The claim notes this week masks do not arrive as tidy UTF-8 paragraphs.
In an insurer running the stack Phase 2 dealt with, adjuster free text lives in a
VARCHAR(4000) column on an on-prem MSSQL box, often mixed-encoding, frequently
containing the customer's ID because a 2009 data-entry screen had one free-text field and
no validation. Presidio operates on strings, so everything upstream — the EBCDIC
conversion from Week 13, the encoding normalisation — has to be right before detection
even starts. A mojibake'd name is a name the NER model will not recognise, and a detection
layer cannot mask what the decoder already mangled.


Compliance angle. Under Israeli PPPA, and under GDPR where an insurer has EU
exposure, the relevant question at audit is not "do you mask PII" but "what is your
evidence for the categories you claim to handle." The entities list from Concept 2 is
that evidence, which is why it belongs in version control next to the DPIA rather than
inline in a script. The Teudat Zehut gap in Concept 3 is a live finding in exactly that
frame: a register claiming Israeli national IDs are masked, backed by an engine with no
Israeli recognizer, is a documented control that does not exist.


What breaks in production. The failure is quiet, and it is almost always recall rather
than precision. Over-masking is loud — someone complains the retrieval results are useless
— and gets fixed within a day. Under-masking produces a pipeline that runs clean, passes
its tests, and writes unmasked names into a vector store for months, discovered only when
somebody greps an index for a customer who exercised a deletion request. Assume every
PERSON miss in Concept 1's exercise is a row in a vector store that you cannot
selectively delete, and the priority ordering for the rest of this week follows.

Concept 1 — PatternRecognizer from Pattern, and deny_list vs allow_list


Claims


    

  • A PatternRecognizer is built from one or more Pattern(name, regex, score) objects
plus supported_entity, the entity type it reports. Register it with
analyzer.registry.add_recognizer(...) and it runs on every later analyze() call
exactly like a built-in recognizer — Presidio does not distinguish custom from built-in
once registered.
    • 

  • deny_list is not an exclusion list, despite the name reading that way. It is a list of
exact terms to flag, compiled internally into a regex and matched at deny_list_score
(default 1.0). Use it for identifiers with no shape a regex can express — an internal
project codename, a product nickname — where Pattern has nothing to match against.
    • 

  • The actual exclusion mechanism is allow_list, and it lives on AnalyzerEngine.analyze()
itself, not on the recognizer. It exempts specific exact values from every recognizer's
output at once, for the one case a shaped pattern legitimately over-matches: a code that
is public knowledge, not a secret, even though it fits the regex.
    • 

  • Patterns can be appended to an already-registered PatternRecognizer instance after the
fact (recognizer.patterns.append(...)) — the registry holds a reference to the object,
not a snapshot, so later analyze() calls pick up the change without re-registering.
    • 



Example:


# EXECUTED
from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
from presidio_analyzer.nlp_engine import NlpEngineProvider

provider = NlpEngineProvider(nlp_configuration={
    "nlp_engine_name": "spacy",
    "models": [{"lang_code": "en", "model_name": "en_core_web_sm"}],
})
analyzer = AnalyzerEngine(nlp_engine=provider.create_engine())

product_pattern = Pattern(name="claim_product_code", regex=r"\bCLM-\d{4}\b", score=0.9)
branch_pattern = Pattern(name="branch_code", regex=r"\bBR-\d{3}\b", score=0.9)

# "Project Nightingale" has no shape a regex can express -- deny_list flags it
# by exact term instead. deny_list is a list of terms TO FLAG, not to exclude.
internal_code_recognizer = PatternRecognizer(
    supported_entity="FINSERV_INTERNAL_CODE",
    name="internal_code_recognizer",
    patterns=[product_pattern, branch_pattern],
    deny_list=["Project Nightingale", "Project Falcon"],
)
analyzer.registry.add_recognizer(internal_code_recognizer)

note = (
    "Adjuster note: spoke with Dana Cohen about claim CLM-2291 at branch BR-014, "
    "part of Project Nightingale's fast-track pilot. Head office branch BR-000 "
    "handled the escalation. Refund issued to card 4111111111111111."
)

print("without allow_list:")
results = analyzer.analyze(text=note, language="en",
                            entities=["FINSERV_INTERNAL_CODE", "PERSON", "CREDIT_CARD"])
for r in sorted(results, key=lambda r: r.start):
    print(f"  {r.entity_type:<24}score={r.score:.2f}  {note[r.start:r.end]!r}")

print()
print("with allow_list=['BR-000'] (head office code is public, not a secret):")
results2 = analyzer.analyze(text=note, language="en",
                             entities=["FINSERV_INTERNAL_CODE", "PERSON", "CREDIT_CARD"],
                             allow_list=["BR-000"])
for r in sorted(results2, key=lambda r: r.start):
    print(f"  {r.entity_type:<24}score={r.score:.2f}  {note[r.start:r.end]!r}")

print()
print(f"result count: no_allow_list={len(results)}  with_allow_list={len(results2)}")

Concept 2 — context words and the LemmaContextAwareEnhancer score uplift


Claims


    

  • A PatternRecognizer can take a context list: words that, when found near a match,
raise its score. This is how Presidio turns a deliberately weak, over-matching pattern
into something usable — start the pattern's own score low and let context do the
discrimination.
    • 

  • AnalyzerEngine wires a LemmaContextAwareEnhancer by default. Its
context_similarity_factor (default 0.35) is added to the base score when a context
word is found nearby, so the arithmetic is not mysterious: a score=0.3 pattern near its
context word becomes 0.3 + 0.35 = 0.65.
    • 

  • "Nearby" is asymmetric and configurable, not just "somewhere in the sentence":
context_prefix_count defaults to 5 words before the match, context_suffix_count
defaults to 0 words after it. A context word placed after the match does nothing by
default.
    • 

  • Matching is lemma-based, not exact-string. context=["account"] also boosts on
"accounts" and other inflections, because the enhancer compares lemmas of the surrounding
tokens to the lemmas of the context words, not the raw text.
    • 



Example:


# EXECUTED
from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
from presidio_analyzer.nlp_engine import NlpEngineProvider

provider = NlpEngineProvider(nlp_configuration={
    "nlp_engine_name": "spacy",
    "models": [{"lang_code": "en", "model_name": "en_core_web_sm"}],
})

# Deliberately weak: an 8-10 digit run is common enough (amounts, phone
# fragments, references) that it should not mask everywhere -- only near a
# word that says "this is an account".
weak_account_pattern = Pattern(name="weak_account_number", regex=r"\b\d{8,10}\b", score=0.3)

no_context_recognizer = PatternRecognizer(
    supported_entity="FINSERV_ACCOUNT_NUMBER",
    name="account_number_recognizer_no_context",
    patterns=[weak_account_pattern],
)
with_context_recognizer = PatternRecognizer(
    supported_entity="FINSERV_ACCOUNT_NUMBER",
    name="account_number_recognizer_with_context",
    patterns=[weak_account_pattern],
    context=["account", "acct", "account number"],
)

analyzer_bare = AnalyzerEngine(nlp_engine=provider.create_engine())
analyzer_bare.registry.add_recognizer(no_context_recognizer)

analyzer_with_ctx = AnalyzerEngine(nlp_engine=provider.create_engine())
analyzer_with_ctx.registry.add_recognizer(with_context_recognizer)

near_context = "Please debit account number 88213410 for this month's premium."
far_context = "Policy renewal reference 88213410 was generated overnight."
after_context = "Reference 88213410 was applied to the account balance."

for label, text in (
    ("context word before match", near_context),
    ("no context word nearby", far_context),
    ("context word after match (suffix_count=0)", after_context),
):
    bare = analyzer_bare.analyze(text=text, language="en", entities=["FINSERV_ACCOUNT_NUMBER"])
    ctx = analyzer_with_ctx.analyze(text=text, language="en", entities=["FINSERV_ACCOUNT_NUMBER"])
    b = round(bare[0].score, 2) if bare else None
    c = round(ctx[0].score, 2) if ctx else None
    print(f"{label:<42} no_context_recognizer={b}  with_context_recognizer={c}")

Concept 3 — Checksum validation inside a custom EntityRecognizer


Claims


    

  • PatternRecognizer is a convenience subclass of the more general EntityRecognizer.
Writing an EntityRecognizer directly means implementing load() and
analyze(text, entities, nlp_artifacts) yourself and returning a list of
RecognizerResult — full control, in exchange for doing the finding yourself instead of
handing a regex to the base class.
    • 

  • That control is exactly what a checksum needs. \b\d{9}\b finds every nine-digit run;
it cannot express "and the check digit must be valid," because that is arithmetic over
the matched digits, not a shape. A custom EntityRecognizer.analyze() can run the regex
and then filter by the checksum before ever constructing a RecognizerResult — so
only valid IDs are reported at all, not valid ones at a higher score than invalid ones.
    • 

  • This directly resolves Day 1 Concept 3's failing test: a real IL_TEUDAT_ZEHUT entity
type now exists, and only fires on candidates whose check digit passes.
    •

# EXECUTED -- reuses ID9_RE and teudat_zehut_valid() from Day 1 Concept 3
import re
from presidio_analyzer import AnalyzerEngine, EntityRecognizer, RecognizerResult
from presidio_analyzer.nlp_engine import NlpEngineProvider

ID9_RE = re.compile(r"\b\d{9}\b")


def teudat_zehut_valid(digits):
    if len(digits) != 9 or not digits.isdigit():
        return False
    total = 0
    for i, ch in enumerate(digits):
        p = int(ch) * (1 if i % 2 == 0 else 2)
        total += p if p < 10 else p - 9
    return total % 10 == 0


class TeudatZehutRecognizer(EntityRecognizer):
    """Checksum-validated Israeli national ID recognizer.

    Day 1's regex_only_spans fired on every nine-digit run, valid or not.
    This one only reports a span when the check digit actually passes.
    """

    ENTITY = "IL_TEUDAT_ZEHUT"

    def __init__(self):
        super().__init__(supported_entities=[self.ENTITY], name="teudat_zehut_recognizer")

    def load(self):
        pass

    def analyze(self, text, entities, nlp_artifacts):
        if self.ENTITY not in entities:
            return []
        results = []
        for m in ID9_RE.finditer(text):
            if teudat_zehut_valid(m.group()):
                results.append(RecognizerResult(
                    entity_type=self.ENTITY, start=m.start(), end=m.end(), score=0.9,
                ))
        return results

BFSI Reality Check — Day 2


Legacy angle. Mainframe COBOL fields store a Teudat Zehut as a fixed-width PIC 9(9)
zero-padded numeric, e.g. 005328155 — but once that value crosses into a spreadsheet or
a free-text export (a very Israeli-insurance-specific failure mode: an adjuster pastes a
claimant list from Excel into a note), Excel silently drops the leading zeros and the field
becomes 5328155, seven digits. ID9_RE will not even find it — \b\d{9}\b requires
nine digits, and the checksum math in teudat_zehut_valid assumes nine positions with
specific alternating weights, so a naive re-pad is not safe either: 005328155 and
5328155 zero-padded the wrong way are different candidate strings. Handling this
correctly means re-padding on the left specifically, which is exactly the kind of
legacy-format assumption that has to be verified against the source system rather than
guessed from the free-text side alone.


Compliance angle. TeudatZehutRecognizer is a control an auditor can ask to see
evidence for, same as Day 1's entities list — but a hand-written checksum recognizer is
also a piece of code with a bug surface a built-in recognizer doesn't have. The exercise's
labelled test set is not busywork: it is the artifact that lets you answer "how do you
know this recognizer works" with a number instead of a claim. The same applies to
deny_list from Concept 1 — a list of internal codenames is only as good as its last
update, and a compliance register that says "internal project names are masked" needs
that list treated as a maintained, version-controlled artifact, not a one-time hardcode.


What breaks in production. A Teudat Zehut printed on a scanned form or typed by a
customer often carries a separator before the check digit — 12345678-2 — because that is
how the number is visually grouped on the physical ID card. ID9_RE finds nothing in that
string at all: the hyphen splits it into an eight-digit run and a one-digit run, neither
of which is nine contiguous digits, so this is a silent recall failure, not a rejected
match. Stripping non-digit characters before matching (re.sub(r"[^0-9]", "", s)) recovers
123456782 correctly here, but doing that on the whole free-text note before detection
would also silently collapse CLM-2291 and the IBAN into different, wrong strings. The
fix belongs inside the recognizer, applied only to what already looks like a candidate
span, not upstream on the raw text — another reason EntityRecognizer control matters
more than it looks like it should for what seems like a two-line regex problem.

Concept 1 — OperatorConfig per entity type, and why hash is not a free pseudonym


Claims


    

  • AnonymizerEngine.anonymize() takes the original text plus the RecognizerResult list
from analyze(). With no operators argument it wraps every match in
<ENTITY_TYPE>, which is a reasonable default and also the reason Day 1/2's examples
never had to think about anonymization at all — detection and replacement are
genuinely separate engines.
    • 

  • The real control surface is an operators dict keyed by entity type, each value an
OperatorConfig(operator_name, params). replace takes new_value; mask takes
masking_char, chars_to_mask, from_end; hash takes hash_type (sha256 or
sha512). Each EngineResult.items entry records which operator actually ran, which
matters once several entity types are masked differently in one call.
    • 

  • hash is not a stable fingerprint by default. It salts every value with 32 random
bytes from os.urandom() before hashing, generated fresh per match — so the same
string, masked twice in the same call, gets two different digests, and masking the
same document again a minute later gets a third. This is a deliberate anti-dictionary-
attack design, not a bug, but it means hash cannot be used as a join key or a
coreference-preserving pseudonym unless you override it.
    • 

  • Passing an explicit salt (bytes or a string of at least 16 bytes) makes hash
fully deterministic: the same plaintext and salt always produce the same digest,
in the same call and across separate runs. That determinism is exactly what a
deterministic-tokenization requirement (Week 18's masked join keys) needs — and
exactly what it gives up on unlinkability, since anyone who guesses the salt and a
candidate plaintext can confirm a match by re-hashing.
    •

Concept 2 — DeanonymizeEngine, encrypt/decrypt, and key custody


Claims


    

  • encrypt is the only anonymization operator built for two-way use. It runs AES under
the hood and takes a key of exactly 128, 192, or 256 bits — as a str (UTF-8
encoded) or bytes — raising InvalidParamError immediately if the length doesn't
match one of those three sizes, before any encryption happens.
    • 

  • DeanonymizeEngine.deanonymize() reverses it: it takes the anonymized text, the
EngineResult.items list anonymize() returned, and an operators dict mapping
entity type (or the literal string "DEFAULT", which applies whenever no
entity-specific key is given) to a decrypt OperatorConfig carrying the same key.
There is no separate "encrypted blob" object to pass around — the ciphertext already
lives inline in the anonymized string, and items is only the coordinate list telling
deanonymize() where to find it.
    • 

  • item.start/item.end on an EngineResult item are offsets into the anonymized
text, not the original. That has to be true for deanonymize() to work at all, since
ciphertext is a different length than the plaintext it replaced, and it means you
cannot reuse analyze()'s original RecognizerResult spans to locate anything after
anonymization — only the items anonymize() itself returns are valid for that.
    • 

  • The wrong key does not silently return garbage text — AES's padding check fails first
and deanonymize() raises ValueError. That fail-loud behavior is worth relying on:
a key-rotation bug shows up as a crash on the next decrypt, not as a customer service
rep reading corrupted mojibake off a screen.
    • 

  • Key custody is the entire security model here, and it is deliberately outside
Presidio's scope: nothing in either engine persists, rotates, or protects the key. It
is exactly as sensitive as the plaintext it can unlock and belongs in a secrets
manager, never in the same table, log line, or git repository as the ciphertext it
decrypts.
    •

Concept 3 — Consistent pseudonyms with a custom operator, and choosing reversible vs irreversible


Claims


    

  • OperatorConfig("custom", {"lambda": fn}) runs fn(matched_text) per match and
substitutes whatever string it returns. Nothing else in the built-in operator set can
see the matched text and decide the replacement itself — replace is a fixed literal,
hash/encrypt are one-way transforms of the text, but custom is a genuine hook.
    • 

  • A closure over a plain dict is enough to build a consistent per-entity pseudonym:
look the matched text up, assign a new label only the first time it's seen, and return
the same label on every later match. Because analyze()'s spans and anonymize()'s
substitution both work off exact string equality within one call, this preserves
coreference — every mention of the same customer collapses to the same pseudonym —
without needing a database or a second pass over the document.
    • 

  • A per-match counter with no memory (itertools.count(), or len(seen) + 1 recomputed
fresh each call) looks similar but is not the same thing: it assigns a new value to
every match regardless of whether the underlying text repeats, destroying the exact
coreference signal a pseudonym is supposed to carry.
    • 

  • This is the reversible half of the reversible-vs-irreversible decision from Concept 2,
generalized: replace/mask/redact throw the original value away and are the right
default for anything headed to a vector store or a third-party analytics sink that
never legitimately needs it back. encrypt and a custody-tracked custom pseudonym map
are for the minority of downstream consumers — a fraud investigation, a regulator
audit response, a customer's own subject-access request — who have a specific,
documented reason to re-identify a record later. The map (or the key) is exactly as
sensitive as the data it protects and needs the same access control, which is the
argument for choosing irreversible redaction by default and only reaching for the
reversible path when a named consumer actually requires it.
    •

BFSI Reality Check — Day 3


Legacy angle. A masking gate that runs once per document, as every example above
does, is the easy case. A real claims system re-processes the same claim note every time
it is amended, and a mainframe-sourced export (Week 13) frequently re-sends the entire
customer history on every nightly batch rather than just the delta. If the pseudonym map
from Concept 3 lives only in the process's memory, the same "Dana Cohen" gets a new
CUSTOMER_N on every batch run, and any downstream system joining on that pseudonym
silently loses the link. The map has to be a persisted, keyed store — typically the
claims system's own customer ID, not the free-text name, as the real join key, with the
name-to-pseudonym mapping as a derived, rebuildable cache rather than the source of
truth.


Compliance angle. Reversible pseudonymization and encryption are not "more
compliant" than irreversible redaction by default — they are a different control with
a different obligation attached. Choosing encrypt over replace for a field means the
organization now has to document who holds the key, under what access control, with
what rotation and audit-logging policy, because that key is a single point of
re-identification for every record it touches. Under GDPR Recital 26 and equivalent
Israeli PPPA guidance, pseudonymized data is still personal data precisely because it is
reversible — only irreversibly anonymized data exits the regulation's scope entirely.
A DPIA that lists "customer names are anonymized" without saying which mechanism was
used, and who can turn it back, has not actually answered the auditor's question.


What breaks in production. The failure mode unique to this day is losing the key,
not leaking it. An encryption key stored only in a deploy-time environment variable, on
a service that gets redeployed without its previous env preserved, makes every
previously-encrypted record permanently unrecoverable — not a breach, but a silent,
irreversible data-loss event against the organization's own retained records, discovered
only when a regulator's subject-access request or a fraud investigation asks for a
record the team can no longer open. The fix is the same one every other credential in
this stack needs — a secrets manager with versioned keys, never a bare env var — but
the failure here is easy to miss in testing, because encryption and decryption both work
fine right up until the key that made them work is the one thing nobody backed up.

Concept 1 — BatchAnalyzerEngine/BatchAnonymizerEngine over dict and iterator inputs


Claims


    

  • Days 1-3 called analyzer.analyze()/anonymizer.anonymize() once per string. A claims
extract is thousands of rows across several free-text columns, not one string —
BatchAnalyzerEngine.analyze_dict() and BatchAnonymizerEngine.anonymize_dict() are the
same two engines wrapped to walk a dict of column_name -> list_of_values (or a nested
dict of dicts) without a manual loop.
    • 

  • analyze_dict() returns an iterator of DictAnalyzerResult — one per input key, each
carrying .key, .value (the original list) and .recognizer_results (a list of
RecognizerResult lists, same order as the input rows). Passing that iterator straight
into anonymize_dict() is enough; it does not need re-flattening by hand.
    • 

  • keys_to_skip excludes named columns from analysis entirely — the right tool for a
column that is a coded reference number, not free text, and would otherwise cost a model
call for nothing.
    • 

  • Skipping a column is not the same as the model correctly ignoring it. A coded reference
number's shape (letters, digits, a dash) still resembles something spaCy's NER model was
trained to recognize, and left unskipped it produces confident-looking, wrong labels.
    •

Concept 2 — Column-level presidio-structured analysis, and tokenization that survives a join


Claims


    

  • PandasAnalysisBuilder(analyzer).generate_analysis(df) infers one entity type per
column — a StructuredAnalysis with an entity_mapping dict — by sampling values and
taking the most common AnalyzerEngine result across the column, rather than analyzing
every cell independently the way BatchAnalyzerEngine does. This is the right level for
a DataFrame with a name column and a national-ID column: the schema, not the cell text,
usually already tells you what a column is.
    • 

  • Column-level inference inherits row-level false positives: a column of coded IDs
(customer_id, claim_id) or short numeric strings (national_id) gets misclassified
by the same model quirks Concept 1 showed, just voted over the whole column instead of
reported per cell. generate_analysis()'s output is a starting point to review and
correct, never a mapping to trust blindly and hand straight to anonymize().
    • 

  • StructuredEngine().anonymize(df, structured_analysis, operators) applies one operator
per mapped column to every value in that column — it is AnonymizerEngine, retargeted
from "spans inside one string" to "cells inside one column."
    • 

  • OperatorConfig("hash", {"salt": <fixed string>}), applied to the same column name
(here customer_id) in two DataFrames that share that column, produces the same
ciphertext for the same plaintext in both outputs — because a fixed salt makes hash
deterministic (Day 3, Concept 1). That determinism, not anything specific to
presidio-structured, is what lets two independently-extracted, independently-masked
tables still be joined on the masked key afterward.
    •

Concept 3 — Throughput and false-positive cost, measured, not assumed


Claims


    

  • The Metadata table at the top of this file already names the en_core_web_sm vs
en_core_web_lg substitution this sandbox requires. The claim worth checking, not just
restating, is what that substitution actually costs: raw analysis throughput, and the
false-positive rate a downstream masking gate inherits from whichever model runs it.
    • 

  • BatchAnalyzerEngine.analyze_iterator() timed over an identical batch, once per model,
isolates the throughput question from everything else (same text, same entity set, same
machine, back to back).
    • 

  • Model file size (en_core_web_sm ≈ 12 MB, en_core_web_lg ≈ 400 MB, per spaCy's own
published package listing) is a real, separate cost from per-record throughput: it is
what determines cold-start time and memory footprint for every worker process in a
horizontally-scaled batch job, independent of how fast either model scores one record
once loaded.

sail through generate_analysis() unreviewed and get masked wrong, or not masked at all.


Compliance angle. A masking gate applied per-column at batch scale changes what an
audit has to check. Day 1-3 asked "was this string ever un-redacted" about one document;
a batch/tabular job raises "was every row of this column redacted, or did the column-level
inference miss one value that didn't match its neighbors" — a single mismatched cell (a
national ID formatted with dashes when the rest of the column has none) can silently skip
the column's chosen operator for just that row. verify_fde_track.py-style row-count and
null-rate assertions after every batch masking run, not just after the code review that
approved the entity_mapping, are what actually catches that.


What breaks in production. Concept 3's measured finding — en_core_web_sm produces
roughly double the false-positive ORGANIZATION rate of en_core_web_lg on repeated
text — is a real production risk if this sandbox's model substitution is ever mistaken
for a deployment decision rather than a documented environment constraint. A team that
prototypes a masking gate against en_core_web_sm because that is what installed easily,
measures acceptable-looking precision on a small hand-picked sample, and ships the same
model to production because "it worked in dev," inherits a higher false-positive rate at
real volume without ever having measured it against the model the rest of the org
assumed was in use. The fix is not "always use the larger model" — it is recording, in
the same place requirements.txt records the dependency itself, which model a
measurement was taken against, so a later model swap is a decision someone makes on
purpose rather than a silent substitution nobody notices until precision drops.

Concept 1 — A fail-closed gate between chunking and embedding


Claims


    

  • Every concept in Days 1-4 called AnalyzerEngine/AnonymizerEngine directly inside a
concept's own example. A real pipeline needs exactly one place where every chunk headed
to Week 11's embedding step passes through masking first — not a convention every
caller has to remember, but a single function on the only path from "chunked text" to
"embedding API call," matching Week 12's own parse→chunk→embed→upsert stage boundaries.
    • 

  • "Fail-closed" means: if the masking gate itself cannot complete — the analyzer raises,
times out, or returns something the caller can't trust — the chunk is quarantined, not
embedded anyway with a warning. The alternative, "fail-open" (embed the raw, unmasked
chunk and log a warning), is worse than doing nothing: it sends exactly the PII this
whole week exists to keep out of the vector store, silently, on the one path (an
unexpected input, a transient error) that was never exercised by a normal-case test.
    • 

  • A quarantined chunk is not a deleted one. The gate's job is to stop that specific
chunk from reaching the embedder — what happens to it next (retry, dead-letter queue,
a human review step) is a pipeline-operations decision, not this gate's job to make.
    • 

  • Logging why a chunk was quarantined (the actual exception, not just "masking
failed") is what turns "the pipeline embedded fewer chunks than expected today" from a
silent drop into a diagnosable, residual-risk-tracked event — the same audit-trail
argument Day 3's Reality Check made about encryption key custody applies here to
masking-gate failures.
    • 



Example:


# EXECUTED
import logging
from presidio_analyzer import AnalyzerEngine
from presidio_analyzer.nlp_engine import NlpEngineProvider
from presidio_anonymizer import AnonymizerEngine
from presidio_anonymizer.entities import OperatorConfig

nlp_config = {"nlp_engine_name": "spacy", "models": [{"lang_code": "en", "model_name": "en_core_web_sm"}]}
analyzer = AnalyzerEngine(nlp_engine=NlpEngineProvider(nlp_configuration=nlp_config).create_engine())
anonymizer = AnonymizerEngine()

residual_risk_log = []

def mask_before_embed(chunk_text, chunk_id):
    """Gate between Week 09's chunker and Week 11's embedder. Returns the
    masked text to embed, or None if masking could not be trusted -- a None
    return means the caller MUST NOT embed chunk_text, fail-closed rather
    than fail-open."""
    try:
        results = analyzer.analyze(text=chunk_text, language="en")
        return anonymizer.anonymize(
            text=chunk_text, analyzer_results=results,
            operators={"DEFAULT": OperatorConfig("replace")},
        ).text
    except Exception as exc:
        residual_risk_log.append({"chunk_id": chunk_id, "error": repr(exc)})
        logging.error("masking gate failed for chunk %s: %r -- quarantined, NOT embedded", chunk_id, exc)
        return None

def embed_pipeline(chunks):
    """Stands in for Week 11's embed step -- it only ever receives what the gate approved."""
    embedded, quarantined = [], []
    for i, chunk in enumerate(chunks):
        masked = mask_before_embed(chunk, chunk_id=i)
        if masked is None:
            quarantined.append(i)
            continue
        embedded.append((i, masked))
    return embedded, quarantined

# One normal chunk, one chunk that is not a string at all -- a realistic real-world
# shape (a None value slipping through an upstream parsing bug), not a contrived
# crash: analyzer.analyze(text=None, ...) genuinely raises inside Presidio's own
# type check, no mocking needed to produce this failure.
chunks = [
    "Adjuster spoke with Dana Cohen about claim CLM-2291.",
    None,
    "Routine status update, no PII.",
]

embedded, quarantined = embed_pipeline(chunks)
print("embedded chunk ids:   ", [i for i, _ in embedded])
print("quarantined chunk ids:", quarantined)
print("residual_risk_log:    ", residual_risk_log)
print()
for i, text in embedded:
    print(f"  chunk {i} sent to embedder: {text!r}")

Concept 2 — Measuring detection recall and precision against a labelled set


Claims


    

  • Every score/threshold claim in Days 1-4 was about individual examples. A masking gate
actually deployed needs an aggregate number: across a labelled set of realistic inputs,
what fraction of real PII does the gate catch (recall), and what fraction of what it
flags is actually PII (precision) — neither number is knowable from reading example
output one string at a time.
    • 

  • A labelled synthetic set is a list of (text, ground_truth_spans) pairs, built by hand
for exactly this purpose — not scraped from real customer data, which would itself be
the PII exposure this week exists to prevent.
    • 

  • Overlap-based matching (a predicted span counts as correct if it overlaps a ground-truth
span of the same entity type at all, not only on an exact character-for-character match)
is the standard relaxation for this kind of evaluation — Presidio's own span boundaries
routinely differ by a character or two from a hand-labelled boundary (a leading/trailing
space, a possessive 's) without that being a real detection failure.
    • 

  • score_threshold is a precision/recall dial, not a fixed correctness setting: raising it
trades recall for precision (fewer, more-confident matches; more real PII slips through
unflagged) and lowering it does the reverse. Day 1's Concept 2 already showed the raw
match-count effect of moving this threshold; this concept measures what that trade
actually costs against ground truth.
    • 



Example:


# EXECUTED
from presidio_analyzer import AnalyzerEngine
from presidio_analyzer.nlp_engine import NlpEngineProvider

nlp_config = {"nlp_engine_name": "spacy", "models": [{"lang_code": "en", "model_name": "en_core_web_sm"}]}
analyzer = AnalyzerEngine(nlp_engine=NlpEngineProvider(nlp_configuration=nlp_config).create_engine())

# Small labelled synthetic set: (text, ground-truth [(entity_type, start, end), ...])
LABELLED_SET = [
    ("Dana Cohen filed claim CLM-2291 for water damage.",
     [("PERSON", 0, 10)]),
    ("Card 4111111111111111 was charged for the deductible.",
     [("CREDIT_CARD", 5, 21)]),
    ("Refund wired to IBAN IL620108000000099999999 yesterday.",
     [("IBAN_CODE", 21, 45)]),
    ("No customer information appears in this maintenance log entry.",
     []),
    ("Avi Levy and Dana Cohen are both listed as co-policyholders.",
     [("PERSON", 0, 8), ("PERSON", 13, 23)]),
]

def spans_overlap(a_start, a_end, b_start, b_end):
    return a_start < b_end and b_start < a_end

def score(labelled_set, entities, score_threshold):
    tp = fp = fn = 0
    for text, truth in labelled_set:
        preds = analyzer.analyze(text=text, language="en", entities=entities, score_threshold=score_threshold)
        matched_truth, matched_pred = set(), set()
        for pi, p in enumerate(preds):
            for ti, (etype, ts, te) in enumerate(truth):
                if p.entity_type == etype and spans_overlap(p.start, p.end, ts, te):
                    matched_truth.add(ti)
                    matched_pred.add(pi)
        tp += len(matched_truth)
        fn += len(truth) - len(matched_truth)
        fp += len(preds) - len(matched_pred)
    precision = tp / (tp + fp) if (tp + fp) else float("nan")
    recall = tp / (tp + fn) if (tp + fn) else float("nan")
    return tp, fp, fn, precision, recall

ENTITIES = ["PERSON", "CREDIT_CARD", "IBAN_CODE"]
for threshold in (0.5, 0.9):
    tp, fp, fn, precision, recall = score(LABELLED_SET, ENTITIES, threshold)
    print(f"score_threshold={threshold}  TP={tp} FP={fp} FN={fn}  precision={precision:.2f} recall={recall:.2f}")

Concept 3 — Over-masking is a retrieval-quality regression, not just noise


Claims


    

  • Days 1-4's false positives (ORGANIZATION on the word "PII" itself, NRP on a coded
claim ID, DATE_TIME on a day-of-week word) were framed as detection accuracy
problems. At the embedding stage they are something more specific: every word an
over-broad analyze() call masks is a word no downstream retrieval query can ever
match against again, because the vector store only ever saw the masked placeholder.
    • 

  • Scoping entities=[...] to only the types a chunk actually needs masked (PERSON and
the financial identifiers this week has focused on) versus leaving it unset (every
registered recognizer, including the noisier DATE_TIME/ORGANIZATION/NRP ones)
is the same "scoped vs broad" choice Day 1 Concept 2 already introduced — this concept
measures its downstream cost, not just its match count.
    • 

  • A simple word-overlap retrieval score (shared non-stopword tokens between a query and a
chunk) is not a real vector-similarity search, but it is enough to demonstrate the
mechanism: a query term that only exists in the masked-away portion of a chunk cannot
contribute to that chunk's score under ANY retrieval method, vector or lexical, because
the term is no longer in the text the retrieval system indexed.
    • 



Example:


# EXECUTED -- reuses analyzer, anonymizer from Concept 1
import re

chunks = [
    "Adjuster met the customer, Dana Cohen, on Tuesday at the downtown branch "
    "regarding water damage to the kitchen ceiling, claim CLM-5521.",
    "Routine policy renewal reminder sent, no claim activity this cycle.",
    "Customer Avi Levy reported a windshield crack on Monday, claim CLM-6002, "
    "repair scheduled at the north branch.",
]

def mask(text, entities):
    results = analyzer.analyze(text=text, language="en", entities=entities)
    return anonymizer.anonymize(
        text=text, analyzer_results=results,
        operators={"DEFAULT": OperatorConfig("replace")},
    ).text

SCOPED_ENTITIES = ["PERSON", "CREDIT_CARD", "IBAN_CODE", "US_BANK_NUMBER"]
scoped = [mask(c, SCOPED_ENTITIES) for c in chunks]
broad = [mask(c, None) for c in chunks]  # None = every registered recognizer

print("properly-scoped masking:")
for c in scoped:
    print(" ", c)
print()
print("broad/unscoped masking:")
for c in broad:
    print(" ", c)

def tokenize(text):
    return set(re.findall(r"[a-z0-9]+", text.lower())) - {"the", "on", "a", "at", "to", "of", "no"}

def retrieval_scores(query, corpus):
    q = tokenize(query)
    return [len(q & tokenize(c)) for c in corpus]

query = "What happened on Monday?"
scoped_scores = retrieval_scores(query, scoped)
broad_scores = retrieval_scores(query, broad)
print()
print(f"query: {query!r}")
print("scoped-masked scores:", scoped_scores, "-> top chunk", scoped_scores.index(max(scoped_scores)))
print("broad-masked scores: ", broad_scores, "-> top chunk", broad_scores.index(max(broad_scores)))

BFSI Reality Check — Day 5


Legacy angle. Week 12's orchestration pipeline and Week 13's mainframe-sourced
records both feed into the same parse→chunk→embed→upsert path this week's gate now sits
inside. A legacy-sourced chunk is disproportionately likely to contain exactly the coded,
non-standard tokens (branch codes, product codes, fixed-width account numbers) that this
week has repeatedly shown trip false positives under broad masking — meaning the
retrieval-quality regression Concept 3 measured is not evenly distributed across the
corpus, it concentrates precisely in the legacy-sourced documents the business most needs
a working audit trail for.


Compliance angle. Concept 2's precision/recall measurement is not just an engineering
metric — it is the artifact a DPIA (data protection impact assessment) actually needs.
"We use Presidio to mask PII before embedding" is an unverifiable claim without a number
attached; "measured recall of 1.00 at score_threshold=0.5 against an N-example labelled
set, re-measured whenever the model or threshold changes" is a claim a regulator, an
auditor, or an internal risk committee can actually evaluate and re-check. Recording only
the threshold that was chosen, without the recall/precision trade it was chosen against,
leaves the actual residual risk undocumented.


What breaks in production. The three concepts compose into the real failure mode this
week has been building toward: an analyzer failure that fails open (not this file's
mask_before_embed, but a version of it someone wrote without Concept 1's try/except)
embeds raw PII silently; a threshold raised "for higher confidence" without Concept 2's
measurement silently drops recall on exactly the entity type (PERSON, at 0.85) this
whole week centers on; and broad, unscoped masking adopted "to be safe" silently deletes
the retrieval signal a real user's query depends on, discovered only when someone asks
the RAG system a perfectly reasonable question and it confidently retrieves the wrong
document. None of these three fail loudly. All three are exactly what this day's
residual_risk_log, labelled-set measurement, and scoped-entities discipline exist to
make visible instead of silent.




Architecture Decision — Week 14


Choosing between: masking every chunk with the broadest possible entities=None call
("catch everything, err on the side of caution") vs a deliberately scoped entities=[...]
list matched to what a chunk's source actually contains, backed by Concept 2's measured
precision/recall rather than an unmeasured assumption either way.


Rule of thumb: Scope the entity list to what the data source genuinely needs masked —
Days 1-2 built exactly this kind of source-specific knowledge (financial identifiers,
Teudat Zehut) precisely so a chunk's origin can drive its masking policy instead of a
one-size-fits-all default. Move to a broader entity list only for a data source whose
content is genuinely unpredictable (free-text customer complaints, unstructured call
transcripts) where a scoped list would risk missing a real category of PII — and even
then, pair the broader list with Concept 2's labelled-set measurement before trusting it,
because Concept 3 showed broad masking has a real, measured cost (retrieval-quality
regression) that "catch everything" does not make free. The gate itself (Concept 1) is
never optional regardless of which entity-list policy a source uses: fail-closed
quarantine-on-error is the one piece of this week that has no scoped/broad trade-off,
because the alternative to quarantining an unmaskable chunk is embedding it unmasked.
