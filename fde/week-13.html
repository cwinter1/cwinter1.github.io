Concept 1 — Level Numbers, and Group vs. Elementary Items

A copybook is COBOL's record-layout language, and its structure is a tree encoded purely through indentation and level numbers: 01 is the record's top-level group item, and subordinate items are numbered 05, 10, 15, and so on (the gaps are convention, not a rule — they leave room to insert a level between two existing ones later without renumbering everything). A group item has no PIC clause of its own and no storage of its own; its "value" is just the concatenation of whatever its subordinate items hold. An elementary item carries a PIC clause and is where the actual bytes live. Only elementary items ever get a byte offset — a group item's offset and length are derived entirely from its children.

The practical test for "is this a group or an elementary item" is not the level number in isolation, it is whether any later field in the copybook has a higher level number before the next field at the same or lower level. A 05 item followed immediately by another 05 item is elementary; a 05 item followed by a 10 item is a group, because that 10 item is subordinate to it.

Example:

import dataclasses

@dataclasses.dataclass
class CopybookField:
    level: int
    name: str
    pic: str
    usage: str = "DISPLAY"

# ACCOUNT-RECORD copybook (as it would appear in COBOL source):
# 01 ACCOUNT-RECORD.
#    05 ACCOUNT-ID        PIC X(10).
#    05 CUSTOMER-NAME     PIC X(20).
#    05 ACCOUNT-BALANCE   PIC S9(7)V99 COMP-3.
#    05 ACCOUNT-STATUS    PIC X(1).
#    05 TRANSACTION-COUNT PIC 9(3).
#    05 FILLER            PIC X(5).
account_record_fields = [
    CopybookField(1, "ACCOUNT-RECORD", None),
    CopybookField(5, "ACCOUNT-ID", "X(10)"),
    CopybookField(5, "CUSTOMER-NAME", "X(20)"),
    CopybookField(5, "ACCOUNT-BALANCE", "S9(7)V99", usage="COMP-3"),
    CopybookField(5, "ACCOUNT-STATUS", "X(1)"),
    CopybookField(5, "TRANSACTION-COUNT", "9(3)"),
    CopybookField(5, "FILLER", "X(5)"),
]

def group_items(fields):
    return [f for f in fields if f.level == 1]

def elementary_items(fields):
    return [f for f in fields if f.level != 1]

elems = elementary_items(account_record_fields)
print(f"group items (level 01): {[f.name for f in groups]}")
print(f"elementary items (level 05): {[f.name for f in elems]}")

Concept 2 — PIC Clauses and Byte-Length Arithmetic


PIC X(n) is straightforward: an alphanumeric field occupying exactly n bytes,
one character per byte. Numeric clauses need more care. PIC S9(7)V99 describes a signed
number with 7 integer digit positions and 2 decimal digit positions — the V marks an
implied decimal point that consumes no storage of its own, it only tells the reader
where to place the point when interpreting the digits. The S marks the field as signed;
an unsigned field simply omits it.


Storage cost depends on USAGE, not on the PIC clause alone. DISPLAY (the default,
also called zoned decimal) spends one full byte per digit, sign included — the sign rides
in the zone nibble of the last digit's byte at no extra cost (Day 3 covers exactly how).
COMP-3 (packed decimal) is denser: two decimal digits share one byte via nibbles, plus
one more nibble for the sign, so an n-digit COMP-3 field needs ceil((n + 1) / 2) bytes.
S9(7)V99 COMP-3 has 9 total digit positions (7 + 2), so ceil(10 / 2) = 5 bytes — a
number worth memorizing, because it is the single most common COMP-3 field size in a real
financial copybook.


Example:


import math
import re

_PIC_ALPHANUM = re.compile(r"^X\((\d+)\)$")
_PIC_NUMERIC = re.compile(r"^(S)?9\((\d+)\)(?:V9\((\d+)\)|V(9+))?$")

def pic_digit_counts(pic):
    """Return (integer_digits, decimal_digits, signed) for a numeric PIC clause."""
    m = _PIC_NUMERIC.match(pic)
    if not m:
        raise ValueError(f"not a numeric PIC clause: {pic}")
    signed = m.group(1) == "S"
    int_digits = int(m.group(2))
    if m.group(3) is not None:
        dec_digits = int(m.group(3))
    elif m.group(4) is not None:
        dec_digits = len(m.group(4))
    else:
        dec_digits = 0
    return int_digits, dec_digits, signed

def pic_length_bytes(pic, usage="DISPLAY"):
    """Byte length of a single PIC clause, given its USAGE."""
    m = _PIC_ALPHANUM.match(pic)
    if m:
        return int(m.group(1))
    int_digits, dec_digits, _signed = pic_digit_counts(pic)
    total_digits = int_digits + dec_digits
    if usage == "COMP-3":
        # packed decimal: one nibble per digit plus one nibble for the sign,
        # two nibbles per byte, rounded up.
        return math.ceil((total_digits + 1) / 2)
    if usage == "DISPLAY":
        # zoned decimal: one byte per digit; the sign rides in the zone
        # nibble of the last digit's byte, so it costs no extra bytes.
        return total_digits
    raise ValueError(f"unhandled usage: {usage}")

print(f"X(10)              -> {pic_length_bytes('X(10)')} bytes")
print(f"X(20)              -> {pic_length_bytes('X(20)')} bytes")
print(f"S9(7)V99 COMP-3    -> {pic_length_bytes('S9(7)V99', usage='COMP-3')} bytes")
print(f"X(1)               -> {pic_length_bytes('X(1)')} bytes")
print(f"9(3)                -> {pic_length_bytes('9(3)')} bytes")
print(f"X(5)               -> {pic_length_bytes('X(5)')} bytes")

Concept 3 — OCCURS, REDEFINES, and Offsets That Must Sum to LRECL


OCCURS n TIMES repeats an elementary or group item's storage n times in place — a
fixed-size array with no delimiter between elements, so its total length is simply its
single-element length times n. REDEFINES does the opposite of consuming new bytes: it
declares that a field occupies the same storage as an earlier field, interpreted
differently — the classic use is storing a date as PIC X(8) for display purposes while a
REDEFINES gives the same eight bytes a PIC 9(8) numeric view for arithmetic. A
redefining field's start offset equals the start offset of the field it redefines, not the
running cursor position, and it must not advance the cursor for anything declared after it.


The check that catches almost every copybook-transcription mistake: every elementary
item's (start, end) offsets, laid end to end (skipping redefined bytes, which overlap
deliberately), must sum to exactly the record's declared LRECL. A copybook that is
off by even one byte here will silently misread every field after the error.


Example:


def layout_offsets(fields):
    """Assign (start, end) byte offsets to elementary items in declaration order.
    A REDEFINES field does not consume new bytes -- it starts back at the
    offset of the field it redefines. An OCCURS field's total length is its
    element length times its occurrence count."""
    offsets = []
    cursor = 0
    named_offsets = {}
    for f in fields:
        if f.level == 1:
            continue
        if f.redefines:
            start = named_offsets[f.redefines]
        else:
            start = cursor
        length = pic_length_bytes(f.pic, usage=f.usage) * f.occurs
        end = start + length
        offsets.append((f.name, start, end, length))
        named_offsets[f.name] = start
        if not f.redefines:
            cursor = end
    return offsets, cursor

@dataclasses.dataclass
class LayoutField:
    level: int
    name: str
    pic: str
    usage: str = "DISPLAY"
    occurs: int = 1
    redefines: str = None

# POLICY-RECORD copybook, illustrating OCCURS and REDEFINES together:
# 01 POLICY-RECORD.
#    05 POLICY-ID              PIC X(9).
#    05 PREMIUM-HISTORY OCCURS 3 TIMES PIC 9(5)V99.
#    05 LAST-CLAIM-DATE        PIC X(8).
#    05 LAST-CLAIM-DATE-R REDEFINES LAST-CLAIM-DATE PIC 9(8).
#    05 FILLER                 PIC X(3).
policy_record_fields = [
    LayoutField(1, "POLICY-RECORD", None),
    LayoutField(5, "POLICY-ID", "X(9)"),
    LayoutField(5, "PREMIUM-HISTORY", "9(5)V99", occurs=3),
    LayoutField(5, "LAST-CLAIM-DATE", "X(8)"),
    LayoutField(5, "LAST-CLAIM-DATE-R", "9(8)", redefines="LAST-CLAIM-DATE"),
    LayoutField(5, "FILLER", "X(3)"),
]

offsets, lrecl = layout_offsets(policy_record_fields)
for name, start, end, length in offsets:
    print(f"{name:<20} start={start:>3} end={end:>3} length={length:>3}")
print(f"computed LRECL (cursor after last non-redefining field): {lrecl}")

BFSI Reality Check — Day 1


Legacy angle: The copybook is usually the only documentation of a mainframe record's
shape that still exists, and it belongs to the mainframe application team, not to whoever
is building the DataPrep pipeline. A copybook change (a new field, a widened PIC clause)
is a COBOL recompile on their side that silently breaks every downstream offset table that
was hand-derived from an older version.


Compliance angle: ACCOUNT-BALANCE, CUSTOMER-NAME, and similar fields are exactly
the same regulated customer data whether they live in a modern Postgres row or a COMP-3
byte range on a mainframe. A data-subject access or erasure request scoped only to the
"modern" systems and blind to the mainframe copybook record has not actually covered the
data.


What breaks in production: A copybook is updated to insert one new field in the middle
of a record (not appended at the end), and nobody regenerates the downstream offset table
from it. Every field after the insertion point is read from the wrong byte range — not an
error, a silently wrong value, for every record in the file.

Concept 1 — Colspecs Generated From the Copybook, Not Hand-Typed


pandas.read_fwf's colspecs argument is exactly the (start, end) offset table Day 1
built — and it should always be generated from a parsed copybook layout, never
hand-typed against the raw text. A hand-typed colspec list is a second, independent place
the same arithmetic can go wrong, with no automatic check that it still agrees with the
copybook it is supposed to describe. This concept's record — TRANSACTION-RECORD — is
deliberately all DISPLAY/alphanumeric fields with no COMP-3; a packed-decimal field is
binary, not text, and pandas.read_fwf cannot parse it as a string column at all (Day 3
handles those fields by raw byte slicing instead).


Example:


# TRANSACTION-RECORD copybook, DISPLAY-only fields (COMP-3/binary fields need
# raw byte slicing instead of text colspecs -- Day 3 covers that; this record
# is deliberately all zoned/alphanumeric so pandas.read_fwf applies cleanly).
# 01 TRANSACTION-RECORD.
#    05 TRAN-ID       PIC X(8).
#    05 ACCOUNT-ID    PIC X(10).
#    05 TRAN-DATE     PIC X(8).
#    05 TRAN-AMOUNT   PIC 9(9)V99.
#    05 TRAN-TYPE     PIC X(1).
#    05 FILLER        PIC X(6).
transaction_record_fields = [
    LayoutField(1, "TRANSACTION-RECORD", None),
    LayoutField(5, "TRAN-ID", "X(8)"),
    LayoutField(5, "ACCOUNT-ID", "X(10)"),
    LayoutField(5, "TRAN-DATE", "X(8)"),
    LayoutField(5, "TRAN-AMOUNT", "9(9)V99"),
    LayoutField(5, "TRAN-TYPE", "X(1)"),
    LayoutField(5, "FILLER", "X(6)"),
]

def colspecs_from_layout(fields):
    offsets, lrecl = layout_offsets(fields)
    names = [name for name, _s, _e, _l in offsets]
    colspecs = [(s, e) for _n, s, e, _l in offsets]
    return names, colspecs, lrecl

tran_names, tran_colspecs, TRAN_LRECL = colspecs_from_layout(transaction_record_fields)
print(f"field names: {tran_names}")
print(f"colspecs:    {tran_colspecs}")
print(f"LRECL:       {TRAN_LRECL}")

Concept 2 — RECFM=FB Blocking and Record-Length Validation


RECFM=FB (fixed-block) is the defining trait of a classic mainframe sequential extract:
there is no line terminator anywhere in the file. A record's boundary is purely a byte
count — after LRECL bytes, the next record starts, with nothing to search for. That means
the very first thing any parser must do is validate that the raw stream's total length is
an exact multiple of LRECL; if it is not, the extract is truncated or the wrong copybook
is being used against it, and guessing where record boundaries fall from that point on
would silently misalign every field in every following record.


Example:


import io

def make_transaction_record(tran_id, account_id, tran_date, amount_cents, tran_type):
    """Build one 44-byte FB record by hand, DISPLAY (zoned) encoding throughout."""
    amount_str = str(amount_cents).zfill(11)  # 9(9)V99 = 11 total digit positions
    row = (tran_id.ljust(8) + account_id.ljust(10) + tran_date.ljust(8)
           + amount_str + tran_type.ljust(1) + "".ljust(6))
    assert len(row) == TRAN_LRECL, f"record is {len(row)} bytes, expected {TRAN_LRECL}"
    return row

records = [
    make_transaction_record("TXN00001", "ACC0000001", "20260301", 123456, "D"),
    make_transaction_record("TXN00002", "ACC0000002", "20260301", 500000, "C"),
    make_transaction_record("TXN00003", "ACC0000001", "20260302", 7500, "D"),
]

# RECFM=FB: fixed-block, no line terminators at all -- the raw stream is one
# unbroken run of LRECL-byte records. Simulate that raw stream, then deblock
# it by slicing every LRECL bytes rather than by looking for a delimiter.
raw_fb_stream = "".join(records)
print(f"raw FB stream length: {len(raw_fb_stream)} bytes, no separators present")

def validate_and_deblock(raw_stream, lrecl):
    if len(raw_stream) % lrecl != 0:
        raise ValueError(
            f"stream length {len(raw_stream)} is not a multiple of LRECL {lrecl} "
            "-- truncated or misconfigured extract, refuse to guess record boundaries"
        )
    return [raw_stream[i:i + lrecl] for i in range(0, len(raw_stream), lrecl)]

deblocked = validate_and_deblock(raw_fb_stream, TRAN_LRECL)
print(f"deblocked into {len(deblocked)} records of {TRAN_LRECL} bytes each")

try:
    validate_and_deblock(raw_fb_stream[:-1], TRAN_LRECL)
except ValueError as e:
    print(f"truncated stream correctly rejected: {e}")

import pandas as pd
# Deblocking already split the stream on real byte boundaries, so joining the
# fixed-length records with '\n' for read_fwf is safe -- it adds no ambiguity,
# every record is already exactly LRECL characters wide.
buf = io.StringIO("\n".join(deblocked))
df = pd.read_fwf(buf, colspecs=tran_colspecs, names=tran_names, dtype=str, keep_default_na=False)
print(df.to_string(index=False))

Concept 3 — Trailing Filler and Zero-Padded Numerics


Two habits carry over from every mainframe extract. First, a DISPLAY numeric field is
always written zero-padded to its full declared width — 9(9)V99 storing the value
1234.56 is the literal text 00000123456, never 123456 with leading spaces, because
a numeric PIC clause has no concept of a variable-width representation. Decoding it means
placing the implied decimal point (from the V's position) after stripping nothing.
Second, FILLER fields exist purely to pad a record out to its declared LRECL — they
carry no business meaning and no field name a downstream consumer should ever reference;
the correct handling is to parse past them and discard the result, never to try to make
sense of what is in them.


Example:


from decimal import Decimal

def decode_zoned_unsigned(raw_digits, decimal_digits):
    """9(n)V9(m) DISPLAY, unsigned: strip nothing, just place the implied
    decimal point -- the zero padding on the left is exactly how a mainframe
    writes a fixed-width unsigned numeric, never stripped before parsing."""
    scale = Decimal(10) ** decimal_digits
    return Decimal(raw_digits) / scale

df["TRAN-AMOUNT-DECIMAL"] = df["TRAN-AMOUNT"].apply(lambda s: decode_zoned_unsigned(s, 2))
df["FILLER"] = df["FILLER"].apply(lambda s: s.rstrip())
print(df[["TRAN-ID", "TRAN-AMOUNT", "TRAN-AMOUNT-DECIMAL", "FILLER"]].to_string(index=False))
print(f"FILLER column after stripping trailing spaces: {df['FILLER'].tolist()} "
      f"(all blank -- filler carries no data, only reserved padding to hit LRECL)")

Concept 1 — cp037 vs. cp500, and the Wrong-Code-Page Trap


EBCDIC is not one fixed byte-to-character mapping — it is a family of code pages, and the
two most commonly met in BFSI mainframe extracts are cp037 (US/Canada EBCDIC) and cp500
(International EBCDIC). Python's bytes.decode() handles both for real, with no external
library needed. The two code pages agree on letters and digits, which is exactly what makes
the trap dangerous: a file transcoded with the wrong one of the two still looks mostly
right — names and account numbers decode correctly — while a handful of punctuation
characters silently come out as the wrong character, an error easy to miss in a spot check
that only glances at the alphanumeric fields.


Example:


# cp037 (US/Canada EBCDIC) and cp500 (International EBCDIC) agree on letters
# and digits but disagree on a handful of punctuation code points -- exactly
# the trap: a file transcoded with the wrong one of the two still "works"
# for names and amounts, and only the punctuation-bearing fields come out
# corrupted, which is easy to miss in a spot check.
text = "REF[07]!"
ebcdic_bytes = text.encode("cp037")
print(f"'{text}' encoded as cp037: {ebcdic_bytes.hex()}")
print(f"decoded correctly as cp037:  {ebcdic_bytes.decode('cp037')!r}")
print(f"decoded WRONGLY as cp500:    {ebcdic_bytes.decode('cp500')!r}")
print(f"decoded WRONGLY as latin-1: {ebcdic_bytes.decode('latin-1')!r}")

Concept 2 — COMP-3 Packed-Decimal Nibble Unpacking


Packed decimal (COMP-3) stores two decimal digits per byte as nibbles, with one final
nibble reserved for the sign — 0xC or 0xF for positive, 0xD (or 0xB) for negative.
Unpacking means splitting every byte into its high and low nibble, reading all nibbles but
the last as decimal digits, and reading the last nibble as the sign. A worked example
grounds this precisely: PIC S9(7)V99 COMP-3 holding the value -1234.56 has 9 total
digit positions, so its zero-padded digit string is "000123456". Appending the negative
sign nibble D gives ten nibbles — 0 0 0 1 2 3 4 5 6 D — which pack two-per-byte into
five bytes: 0x00 0x01 0x23 0x45 0x6D.


Example:


def unpack_comp3(raw, scale):
    """raw: packed-decimal bytes. scale: digits after the implied decimal
    point (the PIC clause's V position). Last nibble is the sign: C/F =
    positive, D/B = negative."""
    nibbles = []
    for byte in raw:
        nibbles.append((byte >> 4) & 0xF)
        nibbles.append(byte & 0xF)
    sign_nibble = nibbles[-1]
    digit_str = "".join(str(n) for n in nibbles[:-1])
    magnitude = Decimal(digit_str)
    if scale:
        magnitude = magnitude / (Decimal(10) ** scale)
    sign = -1 if sign_nibble in (0xD, 0xB) else 1
    return sign * magnitude

def pack_comp3(value, total_digits, scale, negative_nibble=0xD, positive_nibble=0xC):
    """Inverse of unpack_comp3 -- builds packed-decimal bytes from a Decimal."""
    scaled = int((abs(value) * (Decimal(10) ** scale)).to_integral_value())
    digit_str = str(scaled).zfill(total_digits)
    sign_nibble = negative_nibble if value < 0 else positive_nibble
    nibbles = [int(c) for c in digit_str] + [sign_nibble]
    if len(nibbles) % 2 != 0:
        nibbles.insert(0, 0)
    raw = bytearray()
    for i in range(0, len(nibbles), 2):
        raw.append((nibbles[i] << 4) | nibbles[i + 1])
    return bytes(raw)

# Hand-worked example: PIC S9(7)V99 COMP-3, value -1234.56.
# Digit string (7 integer + 2 decimal = 9 digits): "000123456".
# Nibbles: 0 0 0 1 2 3 4 5 6 D  -> bytes 00 01 23 45 6D (5 bytes).
worked_example_bytes = bytes.fromhex("00012345") + bytes([0x6D])
print(f"worked-example packed bytes: {worked_example_bytes.hex()}")
unpacked = unpack_comp3(worked_example_bytes, scale=2)
print(f"unpacked value (scale=2):    {unpacked}")

repacked = pack_comp3(Decimal("-1234.56"), total_digits=9, scale=2)
print(f"repacked bytes match hand-worked bytes: {repacked == worked_example_bytes}")
print(f"round trip: unpack(pack(-1234.56)) == -1234.56 -> "
      f"{unpack_comp3(repacked, scale=2) == Decimal('-1234.56')}")

positive_example = pack_comp3(Decimal("789.01"), total_digits=9, scale=2)
print(f"positive value 789.01 packed: {positive_example.hex()}  "
      f"unpacked back: {unpack_comp3(positive_example, scale=2)}")

Concept 3 — Zoned-Decimal Sign Overpunch, and the Implied Decimal From V


Zoned decimal (plain DISPLAY usage) uses a different sign convention than COMP-3: every
digit still occupies its own full byte, but the zone nibble (the top four bits) of only
the last digit's byte carries the sign — 0xC for positive, 0xD for negative — while
every other digit's byte uses zone 0xF. This is called sign overpunch because, on an
actual EBCDIC terminal, that last byte's character glyph visibly changes (a 0-9 digit
becomes one of a handful of alternate symbol characters) to show the sign is folded in.
Combined with Concept 2's V-position scale, decoding any signed numeric field — COMP-3
or zoned — always comes down to the same two steps: recover the unscaled integer, then
divide by 10 ** decimal_digits from the PIC clause's V position.


Example:


def pack_zoned(value, digits):
    """Zoned decimal: each digit occupies a full byte, one byte per digit.
    The sign is folded into the zone nibble (top 4 bits) of the LAST digit's
    byte: 0xC = positive, 0xD = negative. Every other digit uses zone 0xF."""
    scaled = abs(value)
    digit_str = str(scaled).zfill(digits)
    raw = bytearray()
    for i, ch in enumerate(digit_str):
        d = int(ch)
        is_last = (i == len(digit_str) - 1)
        zone = (0xD if value < 0 else 0xC) if is_last else 0xF
        raw.append((zone << 4) | d)
    return bytes(raw)

def unpack_zoned(raw):
    digits = []
    sign = 1
    for i, byte in enumerate(raw):
        zone = (byte >> 4) & 0xF
        digit = byte & 0xF
        digits.append(str(digit))
        if i == len(raw) - 1 and zone in (0xD, 0xB):
            sign = -1
    return sign * int("".join(digits))

positive_zoned = pack_zoned(123, digits=3)
negative_zoned = pack_zoned(-123, digits=3)
print(f"+123 zoned bytes: {positive_zoned.hex()}  unpacked: {unpack_zoned(positive_zoned)}")
print(f"-123 zoned bytes: {negative_zoned.hex()}  unpacked: {unpack_zoned(negative_zoned)}")

def decode_field(pic, usage, raw):
    int_digits, dec_digits, _signed = pic_digit_counts(pic)
    if usage == "COMP-3":
        return unpack_comp3(raw, scale=dec_digits)
    if usage == "ZONED":
        value = unpack_zoned(raw)
        return Decimal(value) / (Decimal(10) ** dec_digits)
    raise ValueError(usage)

account_balance_raw = worked_example_bytes  # S9(7)V99 COMP-3, -1234.56
print(f"ACCOUNT-BALANCE PIC S9(7)V99 COMP-3 decoded: "
      f"{decode_field('S9(7)V99', 'COMP-3', account_balance_raw)}")

Concept 1 — Page Headers and Footers Stripped by Position


A mainframe batch report — the kind a COBOL report-writer program spools to JES2 output —
is plain fixed-width text, but it is not a data file: it repeats a page header (title,
running page number) and a page footer (a page-level total) at a fixed line position
within every page, because the report program's line-count logic, not the report's
content, decides where each page breaks. That means header and footer lines must be
identified and stripped by their position in the page, never by matching their text — the
same header line's page number changes every page, and the footer's total changes every
page, so text-matching would have to special-case exactly the parts of the line that most
need to be excluded from that comparison in the first place.


Example:


# A synthetic mainframe spool report: DAILY BRANCH TRANSACTION REPORT.
# Each page is exactly 6 lines: 2 header lines, 3 data lines, 1 page-total
# footer line -- fixed by the report program's line count, not by content.
LINES_PER_PAGE = 6
report_lines = [
    "DAILY BRANCH TRANSACTION REPORT           PAGE 1",
    "BRANCH   ACCOUNT-ID   AMOUNT",
    "100      ACC0000001   1500.00",
    "100      ACC0000002    250.75",
    "200      ACC0000003   4000.00",
    "PAGE TOTAL:                   5750.75",
    "DAILY BRANCH TRANSACTION REPORT           PAGE 2",
    "BRANCH   ACCOUNT-ID   AMOUNT",
    "200      ACC0000004    999.99",
    "300      ACC0000005   2200.00",
    "300      ACC0000006    100.00",
    "PAGE TOTAL:                   3299.99",
]

def split_pages(lines, lines_per_page):
    return [lines[i:i + lines_per_page] for i in range(0, len(lines), lines_per_page)]

def strip_headers_and_footers(lines, lines_per_page, header_lines=2, footer_lines=1):
    """Header/footer lines are identified by their fixed POSITION within each
    page -- not by matching text -- because report text (page numbers,
    running totals) changes page to page while the position never does."""
    data_lines = []
    for page in split_pages(lines, lines_per_page):
        data_lines.extend(page[header_lines: lines_per_page - footer_lines])
    return data_lines

data_lines = strip_headers_and_footers(report_lines, LINES_PER_PAGE)
print(f"{len(report_lines)} raw lines across {len(report_lines)//LINES_PER_PAGE} pages "
      f"-> {len(data_lines)} data lines after stripping headers/footers")
for line in data_lines:
    print(f"  {line!r}")

Concept 2 — Column Offsets and Control-Break Grouping


Report text is parsed by fixed column offsets exactly like a data record — there is no
delimiter, just position — but a report additionally carries an implicit grouping that a
data file's colspecs never need: a control break. The report's rows are already sorted
by branch code, and the "group boundary" is nothing more than the point where the leading
column's value changes from the row immediately before it. There is no explicit marker for
where one branch's rows end and the next begins; the change in that column's value is
the marker.


Example:


REPORT_COLSPECS = {"branch": (0, 9), "account_id": (9, 22), "amount": (22, 32)}

def parse_report_line(line):
    branch = line[REPORT_COLSPECS["branch"][0]:REPORT_COLSPECS["branch"][1]].strip()
    account_id = line[REPORT_COLSPECS["account_id"][0]:REPORT_COLSPECS["account_id"][1]].strip()
    amount = Decimal(line[REPORT_COLSPECS["amount"][0]:REPORT_COLSPECS["amount"][1]].strip())
    return branch, account_id, amount

parsed_rows = [parse_report_line(l) for l in data_lines]
for row in parsed_rows:
    print(f"  branch={row[0]:<5} account={row[1]:<12} amount={row[2]}")

def control_break_groups(rows):
    """Group consecutive rows by branch code -- there is no explicit grouping
    structure in the report text, the group boundary IS the point where the
    leading column's value changes from the row before it."""
    groups = []
    current_branch = None
    current_group = []
    for branch, account_id, amount in rows:
        if branch != current_branch and current_group:
            groups.append((current_branch, current_group))
            current_group = []
        current_branch = branch
        current_group.append((account_id, amount))
    if current_group:
        groups.append((current_branch, current_group))
    return groups

groups = control_break_groups(parsed_rows)
for branch, rows in groups:
    subtotal = sum(amount for _acct, amount in rows)
    print(f"  control break: branch {branch} -> {len(rows)} row(s), subtotal={subtotal}")

Concept 3 — Trailer Totals Reused as a Parse Checksum


Every page's footer total is not just something to strip and discard — it is a free
correctness check the report-writer program already computed, from data this parser cannot
independently trust yet. Summing the parsed amount column for a page and comparing it
against that page's own trailer total catches exactly the class of bug a truncated LRECL
validation (Day 2) does not: a report where every individual line parses without error, but
one line was silently dropped or double-counted somewhere in the pipeline before this
check ever ran.


Example:


def page_trailer_total(page_lines):
    trailer = page_lines[-1]
    return Decimal(trailer.replace("PAGE TOTAL:", "").strip())

def verify_pages_against_trailers(lines, lines_per_page, header_lines=2, footer_lines=1):
    results = []
    for page in split_pages(lines, lines_per_page):
        data = page[header_lines: lines_per_page - footer_lines]
        parsed = [parse_report_line(l) for l in data]
        computed_total = sum(amount for _b, _a, amount in parsed)
        trailer_total = page_trailer_total(page)
        results.append((computed_total, trailer_total, computed_total == trailer_total))
    return results

for i, (computed, trailer, ok) in enumerate(
        verify_pages_against_trailers(report_lines, LINES_PER_PAGE), start=1):
    print(f"  page {i}: computed={computed} trailer={trailer} match={ok}")

grand_total_computed = sum(amount for _b, _a, amount in parsed_rows)
print(f"grand total across both pages (computed from data lines): {grand_total_computed}")

Concept 1 — Rendering Copybook Records Into Narrative Before Embedding

Example:


def render_account_narrative(account_id, customer_name, balance, status, tran_count):
    status_word = {"A": "active", "C": "closed", "D": "delinquent"}.get(status, status)
    return (f"Account {account_id} held by {customer_name.strip()} is {status_word} "
            f"with a current balance of ${balance} across {tran_count} recorded "

Concept 2 — Short Structured Records vs. Long Report Pages Need Different Chunking


A single copybook record's narrative (Concept 1) is already a short, self-contained
unit — chunking it further would only fragment one account's facts across multiple
vectors for no benefit. A multi-page mainframe report (Day 4) is the opposite case: one
embedding call over the whole thing would blur one branch's transactions into another's
inside a single vector, exactly the retrieval-quality problem Week 09's chunking-strategy
week exists to avoid. The natural chunk boundary for a report is its own page boundary,
since that is already how the report itself organizes its control-break groups.


Example:


def chunk_lines(lines, size):
    return [lines[i:i + size] for i in range(0, len(lines), size)]

# A single ACCOUNT-RECORD narrative is already one short, self-contained
# unit -- it is its own chunk, never split further.
account_chunks = [account_narrative]

# The 12-line report from Day 4 is long enough that one embedding call over
# the whole thing would blur page 1's branch-100 rows into page 2's
# branch-300 rows in a single vector; chunk it by page instead.
report_chunks = chunk_lines(report_lines, LINES_PER_PAGE)
print(f"account narrative -> {len(account_chunks)} chunk(s) (short structured record, no split)")
print(f"12-line mainframe report -> {len(report_chunks)} chunk(s) of {LINES_PER_PAGE} lines each "
      f"(chunked by page, matching the report's own page boundary)")

Concept 3 — Provenance and Idempotent Upsert Keyed by Record ID Plus Extract Date


Week 12's idempotent-pipeline pattern (a deterministic key so re-running a batch is a
no-op) needs one adjustment for mainframe-sourced records: the key must include the
extract date, not just the record's own ID. A mainframe record has no reliable
"modified at" timestamp of its own the way a modern database row does — the whole record
is simply re-extracted in full on every batch run, whether or not anything in it actually
changed — so re-running the same day's extract must collapse to the same key (a
genuine no-op), while a later day's extract for the same record is a legitimately new
key, because the underlying mainframe record may have changed in the interim. Every
provenance record also carries source_system and copybook_version alongside the
record's own ID — exactly the fields Week 07's unified-record provenance design used for
CDC-sourced records, reused here for a batch-sourced one instead.


Example:


import hashlib

@dataclasses.dataclass
class LegacyVectorRecord:
    record_id: str
    source_system: str
    copybook_version: str
    extract_date: str
    narrative: str
    upsert_key: str = dataclasses.field(init=False)

    def __post_init__(self):
        # Deterministic key: same record_id re-extracted on the same date
        # collapses to the same key -- re-running a day's load is a no-op,
        # not a duplicate. A later extract_date is a genuinely new key,
        # because the mainframe record may have changed since.
        basis = f"{self.record_id}|{self.extract_date}"
        self.upsert_key = hashlib.sha256(basis.encode()).hexdigest()[:16]

def upsert_batch(index, records):
    for r in records:
        index[r.upsert_key] = r
    return index

index = {}
batch_1 = [
    LegacyVectorRecord("ACC0000001", "mainframe_policy_core", "COPYBOOK-V3",
                        "2026-03-01", account_narrative),
]
upsert_batch(index, batch_1)
print(f"after first load: {len(index)} record(s) in the index")

# Re-run the exact same extract (same record_id, same extract_date) -- this
# must be a no-op, not a duplicate.
upsert_batch(index, batch_1)
print(f"after re-running the same extract: {len(index)} record(s) in the index "
      f"(unchanged -- idempotent on record_id + extract_date)")

# A genuinely new day's extract for the same account IS a new key.
batch_2 = [
    LegacyVectorRecord("ACC0000001", "mainframe_policy_core", "COPYBOOK-V3",
                        "2026-03-02", account_narrative),
]
upsert_batch(index, batch_2)
print(f"after the next day's extract for the same account: {len(index)} record(s) "
      f"(a new extract_date is a genuinely new key, not an overwrite)")

BFSI Reality Check — Day 5


Legacy angle: There is frequently no per-record change indicator on the mainframe side
at all — the daily extract is a full re-dump of every record in scope, whether or not it
changed, which is exactly why the upsert key must be built from the extract date rather
than assuming an incremental, changed-rows-only feed the way Week 11's incremental
embedding update week could.


Compliance angle: The rendered narrative is a new representation of the same regulated
customer data the copybook record always held — a deletion request honored against the
mainframe source but never propagated to this narrative's vector-store entry has not
actually deleted the customer's data, it has only deleted one of its two copies.


What breaks in production: A batch is accidentally re-run twice for the same extract
date after a scheduling retry, and the upsert key correctly absorbs the duplicate — but a
different, more subtle bug ships alongside it unnoticed: the extract date is read from the
job's run timestamp instead of the mainframe's own as-of date for the data, so a job
that runs late (after midnight) silently starts keying every record under the next
calendar day, splitting one logical daily extract's records across two different
provenance dates.




Architecture Decision — Week 13


Choosing between: treating a COBOL/mainframe source as a special case handled outside
the DataPrep pipeline Weeks 08-12 built, vs. treating it as one more parser stage feeding
the same parse→chunk→embed→upsert shape everything else in Phase 2 already uses.


Rule of thumb: A mainframe copybook record is not a fundamentally different kind of
DataPrep input, it is a differently-encoded one — the parse stage is genuinely
different (Days 1-4's byte-offset arithmetic, EBCDIC decode, packed/zoned-decimal
unpacking, report control-break logic all exist because nothing about a mainframe extract
resembles a modern document format), but everything from "a fully-decoded record exists as
Python values" onward is identical to Week 08's document pipeline: render to narrative,
chunk at the boundary that matches the record's own natural shape (never split a short
structured record, always chunk a long report by its own page boundary), embed, and upsert
with a deterministic key. Build one COBOL-aware parser stage that emits the same shape
Week 08's parser already emits, rather than building a second, parallel pipeline for
mainframe sources — the tax of a parallel pipeline is every downstream fix (a chunking
tweak, an upsert-key change) having to be made twice and kept in sync forever, exactly the
kind of drift this track's own copy-in-not-cross-reference convention exists to avoid
internally.


The one genuine divergence from Week 08-12's contract is the upsert key: a mainframe batch
source has no reliable per-record change timestamp the way a modern database row does, so
the key must fold in the extract date (Day 5) rather than relying on a content hash or
a change-log offset the way Weeks 06, 07, and 11's sources could. Get this key wrong — key
on record_id alone, say — and a same-record, same-day reprocessing pass looks
indistinguishable from a genuinely new day's data; key on record_id plus a naive
wall-clock run timestamp instead of the batch's own as-of date, and a late-running job
silently splits one logical day's extract across two provenance dates, exactly the failure
this week's Day 5 Reality Check names.


Taken together, Phase 2 (Weeks 08-13) closes with the same lesson Phase 1 closed with in
Week 07, from the opposite direction: Week 07 showed that a beautifully engineered
streaming pipeline is worthless fed by a source whose real floor is a nightly batch window;
this week shows that a beautifully engineered parse→chunk→embed→upsert pipeline is
worthless if it cannot actually read the bytes its most important source hands it in the
first place. A DataPrep pipeline for a BFSI organization is not done when it handles PDFs
and scanned forms — it is done when it can also read the copybook-defined, EBCDIC-encoded,
packed-decimal record that is often the single most authoritative source of truth the
organization has.
