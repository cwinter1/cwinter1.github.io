Concept 1 — IngestionPipeline With an Ordered transformations List

IngestionPipeline(transformations=[...]) runs a Document through each transformation in order — a SentenceSplitter first, then any embedding model or metadata extractor after it — producing TextNode objects that each carry a ref_doc_id pointing back to the source Document they came from. This is the same "parse, then chunk, then embed" shape every earlier week built by hand; IngestionPipeline is LlamaIndex's own name for formalizing it as one composable, reusable object.

Example:

from llama_index.core.ingestion import IngestionPipeline
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core import Document

docs = [Document(text=("This policy covers named perils including fire, theft, and water damage. " * 20), doc_id="POL-1001")]

pipeline = IngestionPipeline(transformations=[SentenceSplitter(chunk_size=200, chunk_overlap=20)])
nodes = pipeline.run(documents=docs)
print(f"node count: {len(nodes)}")
print(f"each node carries a ref_doc_id back to the source document: {nodes[0].ref_doc_id == 'POL-1001'}")

Concept 2 — IngestionCache So an Expensive Parse Is Not Repeated


IngestionCache keys its cache entries on a hash of the transformation's own
configuration plus the input node content — the same document (or an unchanged node
already produced by an earlier transformation in the pipeline) run through the SAME
transformation a second time is served from cache instead of recomputed, while a
genuinely different document still triggers a real, uncached call. This is directly
useful the moment any transformation in the chain is expensive (a layout-aware PDF parse,
an LLM-based metadata extractor) rather than cheap sentence splitting.


Example:


from llama_index.core.ingestion import IngestionPipeline, IngestionCache
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core.schema import TransformComponent
from llama_index.core import Document

call_count = {"n": 0}

class ExpensiveTransform(TransformComponent):
    def __call__(self, nodes, **kwargs):
        call_count["n"] += 1
        for node in nodes:
            node.metadata["expensive_field"] = "computed"
        return nodes

docs = [Document(text="Claimant reports water damage to the kitchen ceiling from a burst pipe. " * 20, doc_id="CLM-2001")]

cache = IngestionCache()
pipeline = IngestionPipeline(
    transformations=[SentenceSplitter(chunk_size=200, chunk_overlap=20), ExpensiveTransform()],
    cache=cache,
)
pipeline.run(documents=docs)
print(f"first run called the expensive transform: {call_count['n']} time(s)")

# A second pipeline instance, same cache, same input -- the cache should short-circuit
# re-running the transform entirely.
pipeline2 = IngestionPipeline(
    transformations=[SentenceSplitter(chunk_size=200, chunk_overlap=20), ExpensiveTransform()],
    cache=cache,
)
pipeline2.run(documents=docs)
print(f"cache prevented re-running the expensive transform: {call_count['n'] == 1}")

Concept 3 — docstore Plus DocstoreStrategy.UPSERTS for Incremental Re-Ingestion


DocstoreStrategy.UPSERTS compares each incoming document's content hash against what
its docstore already has on record for that doc_id: an unchanged document produces NO
new nodes at all (a genuine no-op, not a re-embed); a changed document under the same
doc_id produces new nodes and replaces the old ones. This needs a real vector_store
attached to actually apply the delete-and-replace side of the upsert — without one,
LlamaIndex logs a warning and quietly falls back to DUPLICATES_ONLY (skip exact
repeats, but never detect a change), a real, checked distinction worth knowing before
relying on UPSERTS in a pipeline missing a vector store.


Example:


from llama_index.core.ingestion import IngestionPipeline, DocstoreStrategy
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.core.vector_stores import SimpleVectorStore
from llama_index.core.embeddings import MockEmbedding
from llama_index.core import Document

pipeline = IngestionPipeline(
    transformations=[SentenceSplitter(chunk_size=100, chunk_overlap=10), MockEmbedding(embed_dim=8)],
    docstore=SimpleDocumentStore(),
    vector_store=SimpleVectorStore(),
    docstore_strategy=DocstoreStrategy.UPSERTS,
)

doc_v1 = Document(text="Policy POL-4001 covers fire damage only.", doc_id="POL-4001")
pipeline.run(documents=[doc_v1])

# re-running the SAME unchanged document is a true no-op
nodes_unchanged = pipeline.run(documents=[doc_v1])
print(f"unchanged doc re-run produces nodes: {len(nodes_unchanged)}")

# the SAME doc_id with CHANGED content -- upsert replaces, doesn't duplicate
doc_v2 = Document(text="Policy POL-4001 covers fire AND water damage, updated terms.", doc_id="POL-4001")
nodes_changed = pipeline.run(documents=[doc_v2])
print(f"changed doc re-run produces nodes: {len(nodes_changed)}")
print(f"docstore still has exactly one document entry: {len(pipeline.docstore.docs) == 1}")

Concept 4 — num_workers Parallelism, and Where It Stops Helping


IngestionPipeline.run(documents=..., num_workers=N) for N > 1 parallelizes
transformation work across separate OS processes via Python's multiprocessing — real
parallelism, not threads, since chunking/embedding are CPU-bound. Checked directly in
this sandbox: num_workers=1 runs correctly and deterministically, but num_workers>1
hangs indefinitely here, blocked by this sandbox's multiprocessing restrictions — a real,
disclosed environment limitation, not a code bug, and consistent with this same
IngestionPipeline code path logging real "Removing unpickleable private attribute"
warnings when it tries to hand a SentenceSplitter's internal tokenizer closures across
the process boundary. That pickling/IPC overhead is exactly why parallelism "stops
helping" past a certain point even where it DOES run: for many small, cheap-to-chunk
documents, the cost of serializing each one across a process boundary can exceed the
compute saved, while parallelism keeps paying off for genuinely expensive per-document
work (OCR, layout-aware parsing) where each unit of work is large.


Example:


from llama_index.core.ingestion import IngestionPipeline
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core import Document

docs = [Document(text=f"Claim CLM-{5000 + i} narrative text repeated. " * 30, doc_id=f"CLM-{5000 + i}") for i in range(8)]
pipeline = IngestionPipeline(transformations=[SentenceSplitter(chunk_size=150, chunk_overlap=15)])

nodes_serial = pipeline.run(documents=docs, num_workers=1)
print(f"serial (num_workers=1) node count: {len(nodes_serial)}")

# REAL MODE -- not executed (num_workers>1 hangs under this sandbox's multiprocessing
# restrictions, confirmed by direct test rather than assumed):
#   nodes_parallel = pipeline.run(documents=docs, num_workers=4)
#   # in an unrestricted environment, this produces the SAME node count as num_workers=1,
#   # just distributed across worker processes -- correctness is identical, only wall-clock
#   # time differs, and only for CPU-heavy-enough transformations to outweigh IPC overhead.

BFSI Reality Check — Day 1


Legacy angle: IngestionCache matters most for exactly the kind of document a
twenty-year-old core produces without a matching AI-ready pipeline — a scanned form
needing OCR, or a mainframe report needing Week 13's copybook-driven parsing — where the
parse itself, not the embedding call, is the expensive step worth never repeating on an
unchanged input.


Compliance angle: DocstoreStrategy.UPSERTS's content-hash comparison is itself an
audit-relevant fact: a document that produces zero new nodes on re-ingestion is
provably unchanged since its last ingestion, without needing a separate change-tracking
system layered on top.


What breaks in production: A team configures docstore_strategy= DocstoreStrategy.UPSERTS but never attaches a vector_store to the pipeline — the
pipeline still runs, still produces nodes, and the silent fallback to
DUPLICATES_ONLY means a document that changes in place is never detected as changed;
stale content sits in the index indefinitely, with nothing about the pipeline's own
successful-looking run indicating anything went wrong.

Concept 1 — StorageContext Backed by PGVectorStore, Including Hybrid Search


StorageContext.from_defaults(docstore=..., index_store=..., vector_store=...) bundles
the three storage backends an index actually needs into one object passed to
VectorStoreIndex.from_documents() — swapping SimpleVectorStore (in-memory, this
sandbox) for PGVectorStore (a live Postgres/pgvector table) changes nothing about the
rest of the code, only which backend actually persists the data. PGVectorStore's real
hybrid_search=True constructor argument combines dense vector search with Postgres
full-text search server-side — the same fusion idea Week 05 built by hand with rank_bm25
and reciprocal rank fusion, offered here as one config flag on a real vector store.


Example:


from llama_index.core import StorageContext, VectorStoreIndex, Document, Settings
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.core.storage.index_store import SimpleIndexStore
from llama_index.core.vector_stores import SimpleVectorStore
from llama_index.core.embeddings import MockEmbedding

Settings.embed_model = MockEmbedding(embed_dim=8)

storage_context = StorageContext.from_defaults(
    docstore=SimpleDocumentStore(),
    index_store=SimpleIndexStore(),
    vector_store=SimpleVectorStore(),
)

docs = [Document(text="Auto policy claim narrative.", doc_id="CLM-8001")]
index = VectorStoreIndex.from_documents(docs, storage_context=storage_context)
print(f"storage_context.docstore has the document: {len(storage_context.docstore.docs) == 1}")
print(f"storage_context.vector_store has the embedded node: {len(storage_context.vector_store.data.embedding_dict) == 1}")

Concept 2 — MetadataFilters and FilterOperator for Tenant, Product Line, and Date Scoping


MetadataFilters(filters=[MetadataFilter(key=..., value=..., operator=...)], condition=FilterCondition.AND) narrows a retrieval to only nodes whose metadata satisfies
EVERY listed condition — FilterOperator.EQ for an exact tenant or product-line match,
FilterOperator.GTE/LTE for a date range. This runs entirely client-side against
SimpleVectorStore's stored metadata here, and server-side (as a real SQL WHERE clause)
against PGVectorStore — same filter object, same result semantics either way.


Example:


from llama_index.core import VectorStoreIndex, Document, Settings
from llama_index.core.embeddings import MockEmbedding
from llama_index.core.vector_stores import MetadataFilters, MetadataFilter, FilterOperator, FilterCondition

Settings.embed_model = MockEmbedding(embed_dim=8)

docs = [
    Document(text="auto policy claim CLM-9001", metadata={"tenant_id": "acme-insurance", "product_line": "auto", "effective_date": "2025-01-01"}, doc_id="d1"),
    Document(text="auto policy claim CLM-9002", metadata={"tenant_id": "acme-insurance", "product_line": "auto", "effective_date": "2026-06-01"}, doc_id="d2"),
    Document(text="home policy claim CLM-9003", metadata={"tenant_id": "acme-insurance", "product_line": "home", "effective_date": "2026-06-01"}, doc_id="d3"),
    Document(text="auto policy claim CLM-9004", metadata={"tenant_id": "other-insurer", "product_line": "auto", "effective_date": "2026-06-01"}, doc_id="d4"),
]
index = VectorStoreIndex.from_documents(docs)

filters = MetadataFilters(
    filters=[
        MetadataFilter(key="tenant_id", value="acme-insurance", operator=FilterOperator.EQ),
        MetadataFilter(key="product_line", value="auto", operator=FilterOperator.EQ),
        MetadataFilter(key="effective_date", value="2026-01-01", operator=FilterOperator.GTE),
    ],
    condition=FilterCondition.AND,
)
retriever = index.as_retriever(similarity_top_k=10, filters=filters)
results = retriever.retrieve("claim")
print(f"matched doc ids: {sorted(r.node.ref_doc_id for r in results)}")
print(f"excludes other tenant, wrong product line, and stale effective_date: {sorted(r.node.ref_doc_id for r in results) == ['d2']}")

Concept 3 — Separate Collections Versus Metadata Filters as a Tenant-Isolation Decision


A tenant_id metadata filter and a genuinely separate per-tenant index are NOT
equivalent in practice, even though both correctly scope a query when used correctly: a
shared index's isolation depends entirely on every single retrieval call remembering to
attach the filter — proven directly below by simply omitting it — while a per-tenant
index has structurally nothing else in it to leak, filter or no filter. The tradeoff is
real in the other direction too: a separate collection per tenant means N times the index
management overhead for N tenants, which a shared, correctly-filtered index avoids
entirely.


Example:


from llama_index.core import VectorStoreIndex, Document, Settings
from llama_index.core.embeddings import MockEmbedding
from llama_index.core.vector_stores import MetadataFilters, MetadataFilter, FilterOperator

Settings.embed_model = MockEmbedding(embed_dim=8)

docs = [
    Document(text="auto policy claim CLM-9001", metadata={"tenant_id": "acme-insurance"}, doc_id="d1"),
    Document(text="auto policy claim CLM-9004", metadata={"tenant_id": "other-insurer"}, doc_id="d4"),
]

# Shared-index approach: isolation depends entirely on remembering the filter.
shared_index = VectorStoreIndex.from_documents(docs)
leaked_results = shared_index.as_retriever(similarity_top_k=10).retrieve("claim")
print(f"forgetting the tenant filter on a shared index leaks cross-tenant results: {len(leaked_results) == 2}")

filtered_retriever = shared_index.as_retriever(
    similarity_top_k=10,
    filters=MetadataFilters(filters=[MetadataFilter(key="tenant_id", value="acme-insurance", operator=FilterOperator.EQ)]),
)
scoped_results = filtered_retriever.retrieve("claim")
print(f"with the filter applied, only the correct tenant comes back: {[r.node.ref_doc_id for r in scoped_results] == ['d1']}")

# Separate-collection approach: isolation is structural, nothing to forget.
acme_only_index = VectorStoreIndex.from_documents([d for d in docs if d.metadata["tenant_id"] == "acme-insurance"])
acme_results = acme_only_index.as_retriever(similarity_top_k=10).retrieve("claim")
print(f"a per-tenant index has no cross-tenant document to leak, filter or no filter: {[r.node.ref_doc_id for r in acme_results] == ['d1']}")

Concept 4 — SentenceSplitter and SemanticSplitterNodeParser, Carried Forward From Week 09


SentenceSplitter(chunk_size=..., chunk_overlap=...) is Week 09's fixed/recursive
chunking, now as one reusable LlamaIndex class; SemanticSplitterNodeParser(embed_model= ..., buffer_size=..., breakpoint_percentile_threshold=...) is Week 09's
embedding-similarity breakpoint chunking, genuinely executable with MockEmbedding for
the MECHANISM (it runs, it calls the embed model, it produces nodes) — but checked
directly, MockEmbedding returns the exact same fixed vector for every input text
regardless of content, so every sentence looks identically similar to every other one,
and the semantic splitter correctly finds zero real breakpoints, collapsing the whole
document into a single node. This is an honest, checked limitation of using a mock
embedder for THIS specific splitter, not a bug in SemanticSplitterNodeParser itself —
demonstrating genuine semantic breakpoints needs a real embedding model, the same REAL
MODE boundary Week 09 Day 3 already disclosed for its own semantic-chunking concept.


Example:


from llama_index.core.node_parser import SentenceSplitter, SemanticSplitterNodeParser
from llama_index.core.embeddings import MockEmbedding
from llama_index.core import Document

text = ("This policy covers fire damage to the dwelling. Fire damage includes smoke and soot. "
        "Separately, this policy also covers theft of personal property. Theft coverage requires a police report. "
        "Water damage from burst pipes is covered under a separate endorsement. Flood damage is explicitly excluded.")
doc = Document(text=text)

sentence_splitter = SentenceSplitter(chunk_size=50, chunk_overlap=0)
sentence_nodes = sentence_splitter.get_nodes_from_documents([doc])
print(f"SentenceSplitter (fixed size) node count: {len(sentence_nodes)}")

mock_embed = MockEmbedding(embed_dim=8)
print(f"MockEmbedding returns an identical vector for different text: {mock_embed.get_text_embedding('hello world') == mock_embed.get_text_embedding('a completely different sentence')}")

semantic_splitter = SemanticSplitterNodeParser(embed_model=mock_embed, buffer_size=1, breakpoint_percentile_threshold=95)
semantic_nodes = semantic_splitter.get_nodes_from_documents([doc])
print(f"SemanticSplitterNodeParser node count with a mock (content-blind) embedder: {len(semantic_nodes)}")

BFSI Reality Check — Day 2


Legacy angle: PGVectorStore's hybrid_search=True is a genuinely low-friction
upgrade path for a BFSI team that already runs Postgres for its transactional systems —
the same adoption argument Week 19 Day 2 made for PostgresSaver, extended here to vector
search itself needing no new database technology introduced.


Compliance angle: Concept 3's structural isolation (separate collections) is the
answer a data-residency or per-customer-contract requirement usually needs — "our data
never lives in the same table as another customer's" is a much easier claim to defend
under audit than "our application code always remembers to filter correctly."


What breaks in production: A tenant-isolation bug ships not because the filter logic
is wrong, but because ONE retrieval call site — a new feature, an admin debugging tool, a
batch job written by someone unfamiliar with the multi-tenancy convention — forgets to
attach the filter at all. Concept 3's own unfiltered-retrieval line is exactly that
missing call, made deliberately visible rather than accidentally shipped.

Concept 1 — RouterQueryEngine Selecting Between a Policy Index and a Claims Index


RouterQueryEngine(selector=..., query_engine_tools=[...]) picks exactly ONE tool
(query engine) to answer a given query, based on whatever selector decides. LlamaIndex's
built-in LLMSingleSelector needs a real LLM to return valid structured JSON — checked
directly, MockLLM's echo response fails that parser against its own default few-shot
example. BaseSelector is a small, real, pluggable interface (_select/_aselect
returning a SelectorResult), so a hand-written deterministic selector genuinely
demonstrates RouterQueryEngine's actual routing mechanism without needing that live LLM
call — production would use LLMSingleSelector or PydanticSingleSelector instead of
this stand-in.


Example:


from llama_index.core import VectorStoreIndex, Document, Settings
from llama_index.core.embeddings import MockEmbedding
from llama_index.core.llms import MockLLM
from llama_index.core.query_engine import RouterQueryEngine
from llama_index.core.tools import QueryEngineTool
from llama_index.core.base.base_selector import BaseSelector, SelectorResult, SingleSelection

Settings.embed_model = MockEmbedding(embed_dim=8)
Settings.llm = MockLLM()

class KeywordSelector(BaseSelector):
    def _select(self, choices, query):
        text = query.query_str.lower()
        if "claim" in text:
            return SelectorResult(selections=[SingleSelection(index=1, reason="mentions a claim")])
        return SelectorResult(selections=[SingleSelection(index=0, reason="defaults to policy coverage")])

    async def _aselect(self, choices, query):
        return self._select(choices, query)

    def _get_prompts(self):
        return {}

    def _update_prompts(self, prompts):
        pass

policy_index = VectorStoreIndex.from_documents([Document(text="Policy POL-1 covers fire and theft.", doc_id="POL-1")])
claims_index = VectorStoreIndex.from_documents([Document(text="Claim CLM-1 was filed for water damage.", doc_id="CLM-1")])
policy_tool = QueryEngineTool.from_defaults(query_engine=policy_index.as_query_engine(), description="Answers questions about policy coverage terms.")
claims_tool = QueryEngineTool.from_defaults(query_engine=claims_index.as_query_engine(), description="Answers questions about filed claims.")

router = RouterQueryEngine(selector=KeywordSelector(), query_engine_tools=[policy_tool, claims_tool])

Concept 3 — CitationQueryEngine for Node-Level References an Audit Can Follow


CitationQueryEngine.from_args(index, citation_chunk_size=...) prefixes every retrieved
chunk with a real "Source N:\n" label before it ever reaches the LLM prompt — checked
directly on the actual node text sent — so a genuinely citation-capable LLM's answer can
reference [1]/[2], and those numbers map directly back to resp.source_nodes[N-1].
This is the mechanism itself, provable without a real LLM's generated prose: the labelling
happens at retrieval time, before generation, which is exactly what makes an answer's

Concept 4 — Response Synthesizer Modes: compact, refine, and tree_summarize


The three modes make a genuinely different number of LLM calls for the same retrieved
chunks, not just a different prompt template: refine calls the LLM once per chunk,
sequentially updating one running answer — the most calls, but the closest to a plain
top-to-bottom read; compact packs as many chunks as fit into each call before calling
the LLM, cutting the call count when chunks are small enough to combine; tree_summarize
recursively combines chunks in a binary/n-ary tree, which can need the FEWEST calls
overall for enough input, at the cost of a summary-of-summaries structure that can lose
detail a single chunk-level answer would have kept. Counting REAL LLM calls per mode
(via a counting wrapper around MockLLM, with the model's context_window deliberately
lowered so 6 chunks cannot all fit in one call) makes the actual cost difference direct
and measured, not asserted.


Example:

    @property
    def metadata(self):
        return LLMMetadata(context_window=900, num_output=50)

    def complete(self, prompt, **kwargs):

        return super().complete(prompt, **kwargs)

Concept 1 — Workflow With @step, Event, and Context


A Workflow is built from @step-decorated async methods, each declaring which Event
subclass it consumes and which it produces via its own type annotations — a step runs
automatically the moment an event of its declared input type becomes available, with no
explicit edge list the way StateGraph.add_edge() requires. StartEvent/StopEvent mark
the workflow's real entry and exit; Context (passed to every step) is where any data
that needs to survive ACROSS steps, beyond what travels inside an event, actually lives.


Example:


from llama_index.core.workflow import Workflow, step, Event, StartEvent, StopEvent, Context
import asyncio

class ParsedEvent(Event):
    doc_id: str

class ChunkedEvent(Event):
    doc_id: str
    chunk_count: int

class DataPrepWorkflow(Workflow):
    @step
    async def parse(self, ctx: Context, ev: StartEvent) -> ParsedEvent:
        return ParsedEvent(doc_id=ev.doc_id)

    @step
    async def chunk(self, ctx: Context, ev: ParsedEvent) -> ChunkedEvent:
        return ChunkedEvent(doc_id=ev.doc_id, chunk_count=3)

    @step
    async def embed(self, ctx: Context, ev: ChunkedEvent) -> StopEvent:
        return StopEvent(result=f"{ev.doc_id}: embedded {ev.chunk_count} chunks")

async def main():
    wf = DataPrepWorkflow(timeout=10)
    result = await wf.run(doc_id="CLM-1001")
    print(f"result: {result}")

asyncio.run(main())

Concept 2 — Shared-State Control Flow Versus Event Emission and Subscription


This is the real structural difference, not just a syntax difference: a LangGraph node
function receives the FULL shared state dict by default (established since Week 19 Day


    

  1. — any node can read anything any earlier node wrote, whether or not that was
intentional. A Workflow step receives ONLY the specific Event type it declared as
input; a value another step computed and never put into an Event field or ctx.store
is simply invisible to it, not just conventionally private but structurally
unreachable. ctx.store is where a Workflow opts INTO LangGraph-style shared state
when a value genuinely needs to reach a step further downstream than the very next one.
    2. 



Example:


from langgraph.graph import StateGraph, START, END
from typing import TypedDict
from llama_index.core.workflow import Workflow, step, Event, StartEvent, StopEvent, Context
import asyncio

class PipelineState(TypedDict):
    doc_id: str
    parse_timestamp: str

def parse_node(state):
    return {"parse_timestamp": "T0"}

def chunk_node(state):
    return {}

def embed_node(state):
    return {"parse_timestamp": state["parse_timestamp"]}

g = StateGraph(PipelineState)
g.add_node("parse", parse_node)
g.add_node("chunk", chunk_node)
g.add_node("embed", embed_node)
g.add_edge(START, "parse")
g.add_edge("parse", "chunk")
g.add_edge("chunk", "embed")
g.add_edge("embed", END)
graph = g.compile()
result = graph.invoke({"doc_id": "CLM-1001", "parse_timestamp": ""})
print(f"LangGraph: every node saw the shared state dict implicitly: {result}")

class ParsedEvent(Event):
    doc_id: str

class EmbeddedEvent(Event):
    doc_id: str

class DataPrepWorkflow(Workflow):
    @step
    async def parse(self, ctx: Context, ev: StartEvent) -> ParsedEvent:
        await ctx.store.set("parse_timestamp", "T0")
        return ParsedEvent(doc_id=ev.doc_id)

    @step
    async def chunk(self, ctx: Context, ev: ParsedEvent) -> EmbeddedEvent:
        return EmbeddedEvent(doc_id=ev.doc_id)

    @step
    async def embed(self, ctx: Context, ev: EmbeddedEvent) -> StopEvent:
        parse_ts = await ctx.store.get("parse_timestamp", default=None)
        return StopEvent(result={"doc_id": ev.doc_id, "parse_timestamp_visible_here": parse_ts})

async def main():
    wf = DataPrepWorkflow(timeout=10)
    result = await wf.run(doc_id="CLM-1001")
    print(f"Workflows: only ctx.store-shared data crossed steps, everything else was event-scoped: {result}")

Concept 3 — Checkpointing and Human-in-the-Loop, Compared Honestly


Context.to_dict()/Context.from_dict(workflow, data) genuinely serialize and restore a
paused workflow's state across a real Python object boundary — checked directly, the
result is a plain, JSON-round-trippable dict. ctx.wait_for_event(EventType, requirements=...) genuinely pauses a step until a matching event arrives, the same
pause-and-resume shape as Week 19's interrupt(). Compared honestly rather than by
feature-list alone: LangGraph's checkpointing is a pluggable, DEDICATED interface
(BaseCheckpointSaver) with InMemorySaver/SqliteSaver/PostgresSaver all
implementing the SAME contract, proven genuinely durable across a real process restart
in Week 19 Day 2; Context.to_dict()/from_dict() gives the raw serialization primitive,
but persisting that dict anywhere durable (a file, a database) and reloading it on restart
is work the calling application must do itself, with no equivalent built-in
BaseCheckpointSaver-style abstraction shipped for it.


Example:


from llama_index.core.workflow import Workflow, step, StartEvent, StopEvent, Context, InputRequiredEvent, HumanResponseEvent
import asyncio
import json

class ApprovalWorkflow(Workflow):
    @step
    async def request_approval(self, ctx: Context, ev: StartEvent) -> StopEvent:
        ctx.write_event_to_stream(InputRequiredEvent(prefix="approve claim?"))
        response = await ctx.wait_for_event(HumanResponseEvent, requirements={"user_name": "reviewer"})
        return StopEvent(result=f"decision: {response.response}")

async def main():
    wf = ApprovalWorkflow(timeout=30)
    handler = wf.run()
    ctx_dict = None
    responded = False
    async for event in handler.stream_events():
        if isinstance(event, InputRequiredEvent) and not responded:
            ctx_dict = handler.ctx.to_dict()
            responded = True
            handler.ctx.send_event(HumanResponseEvent(response="approved", user_name="reviewer"))
    result = await handler
    print(f"context serialized while paused, is a plain dict: {isinstance(ctx_dict, dict)}")
    print(f"round-trips through json (a real durability primitive, not a mock): {isinstance(json.loads(json.dumps(ctx_dict)), dict)}")
    print(f"original run result: {result}")

    wf2 = ApprovalWorkflow(timeout=30)
    restored_ctx = Context.from_dict(wf2, ctx_dict)
    print(f"restored context is a real Context instance: {isinstance(restored_ctx, Context)}")

asyncio.run(main())

Concept 4 — Choosing Between Workflows and LangGraph: An Architecture Decision


Neither framework is strictly better — the choice tracks what this week's own three
concepts actually measured: LangGraph's mature, pluggable, genuinely-proven-durable

Concept 1 — Exposing a LlamaIndex Retriever as a Single LangGraph Tool


Nesting two frameworks' internals together — a LangGraph node reaching directly into a
LlamaIndex query engine's response-synthesis machinery, or vice versa — creates exactly
the kind of coupling this track has warned against since Week 12's "pass object keys, not
payloads" principle. The fix is the same one: wrap the retriever behind ONE plain
function LangGraph calls as a tool. LangGraph never needs to know a VectorStoreIndex
exists at all; it only ever sees a function taking a query string and returning doc ids.


Example:


from llama_index.core import VectorStoreIndex, Document, Settings
from llama_index.core.embeddings import MockEmbedding
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
import operator

Settings.embed_model = MockEmbedding(embed_dim=8)

docs = [Document(text="Policy POL-1 covers fire and theft.", doc_id="POL-1"), Document(text="Policy POL-2 covers water damage.", doc_id="POL-2")]
index = VectorStoreIndex.from_documents(docs)
retriever = index.as_retriever(similarity_top_k=2)

def retrieve_policy_clauses(query: str) -> list[str]:
    # The one tool boundary: LangGraph calls this plain function, backed by a
    # LlamaIndex retriever, without ever importing LlamaIndex's own query-engine or
    # response-synthesis machinery into the graph itself.
    results = retriever.retrieve(query)
    return [r.node.ref_doc_id for r in results]

class AgentState(TypedDict):
    query: str
    retrieved_doc_ids: Annotated[list[str], operator.add]

def retrieve_node(state):
    return {"retrieved_doc_ids": retrieve_policy_clauses(state["query"])}

g = StateGraph(AgentState)
g.add_node("retrieve", retrieve_node)
g.add_edge(START, "retrieve")
g.add_edge("retrieve", END)
graph = g.compile()
result = graph.invoke({"query": "fire damage", "retrieved_doc_ids": []})
print(f"LangGraph node retrieved via the LlamaIndex-backed tool: {sorted(result['retrieved_doc_ids'])}")

Concept 2 — MCP as the Standard Client/Server Tool Boundary


The Model Context Protocol standardizes exactly the boundary Concept 1 built by hand:
instead of every framework inventing its own tool-calling convention (LangChain's
@tool, LlamaIndex's QueryEngineTool, a bespoke function signature), an MCP server
registers tools ONCE and any MCP-compatible client — regardless of which agent framework
it's built on — can discover and call them the same way. The installed SDK here is
mcp 2.x, where the old FastMCP class was renamed MCPServer (a real, checked
version-specific finding, not assumed from older tutorials); its server.tool() decorator
and server.call_tool() genuinely register and invoke tools IN-PROCESS, with no live
stdio/SSE transport needed to prove the registration-and-invocation mechanism itself.


Example:


from mcp.server.mcpserver import MCPServer
import asyncio

server = MCPServer("claims-retrieval")

@server.tool()
def retrieve_policy_clauses(query: str, top_k: int = 3) -> list[str]:
    """Retrieve policy clauses relevant to a query."""
    corpus = ["fire damage clause", "theft clause", "water damage clause", "liability clause"]
    return corpus[:top_k]

async def main():
    tools = await server.list_tools()
    print(f"registered tools: {[t.name for t in tools]}")
    result = await server.call_tool("retrieve_policy_clauses", {"query": "fire", "top_k": 2})

Concept 3 — QueryFusionRetriever With Reciprocal Rank Fusion Behind One Tool Boundary


QueryFusionRetriever(retrievers=[...], mode=FUSION_MODES.RECIPROCAL_RANK) is Week 05's
reciprocal rank fusion, now fusing results across MULTIPLE LlamaIndex retrievers (the
Phase 1 pgvector/Milvus/Qdrant stores this week's README explicitly calls out) into one
ranked list — genuinely useful as exactly ONE tool behind the MCP/LangGraph boundary
Concepts 1-2 built, rather than exposing each underlying store as its own separate tool a
calling agent has to reason about individually. num_queries=1 disables the
default LLM-based query-expansion step (which needs a real LLM this sandbox doesn't have
for its own separate reason), isolating the fusion mechanism itself.


Example:


from llama_index.core import VectorStoreIndex, Document, Settings
from llama_index.core.embeddings import MockEmbedding
from llama_index.core.llms import MockLLM
from llama_index.core.retrievers import QueryFusionRetriever
from llama_index.core.retrievers.fusion_retriever import FUSION_MODES

Settings.embed_model = MockEmbedding(embed_dim=8)
Settings.llm = MockLLM()

docs_a = [Document(text="Policy POL-1 covers fire and theft.", doc_id="POL-1")]
docs_b = [Document(text="Policy POL-2 covers water damage.", doc_id="POL-2")]
index_a = VectorStoreIndex.from_documents(docs_a)
index_b = VectorStoreIndex.from_documents(docs_b)

fusion_retriever = QueryFusionRetriever(
    retrievers=[index_a.as_retriever(similarity_top_k=2), index_b.as_retriever(similarity_top_k=2)],
    mode=FUSION_MODES.RECIPROCAL_RANK,
    num_queries=1,
    use_async=False,
)
results = fusion_retriever.retrieve("policy coverage")
print(f"fused result count: {len(results)}")
print(f"doc ids present: {sorted(r.node.ref_doc_id for r in results)}")

Concept 4 — Node Postprocessors, Where Reranking Belongs, and the Cost of Each Hop


A BaseNodePostprocessor runs AFTER retrieval and BEFORE synthesis — exactly where Week
25's dedicated reranking-layer content will later put a real cross-encoder. Checked
directly: MockEmbedding's content-blind vectors (Day 2 Concept 4's finding) mean a
similarity-based postprocessor cannot demonstrate real discrimination here, so a
hand-written KeywordOverlapReranker (a real BaseNodePostprocessor implementation,
genuinely re-ranking by query/text word overlap) proves the mechanism instead. Measuring
actual wall-clock time across the call chain — a raw retriever call, the same call
wrapped through MCPServer.call_tool(), and reranking added on top — shows each
abstraction layer genuinely adds SOME latency, even measured purely in-process with no
real network transport (which would add strictly more on top of what's measured here).


Example:


from llama_index.core import VectorStoreIndex, Document, Settings
from llama_index.core.embeddings import MockEmbedding
from mcp.server.mcpserver import MCPServer
from llama_index.core.postprocessor.types import BaseNodePostprocessor
from llama_index.core.schema import NodeWithScore, QueryBundle
import asyncio
import time

Settings.embed_model = MockEmbedding(embed_dim=8)

class KeywordOverlapReranker(BaseNodePostprocessor):
    def _postprocess_nodes(self, nodes, query_bundle=None):
        query_words = set((query_bundle.query_str if query_bundle else "").lower().split())
        rescored = [NodeWithScore(node=n.node, score=float(len(query_words & set(n.node.text.lower().split())))) for n in nodes]
        return sorted(rescored, key=lambda n: n.score, reverse=True)

    @classmethod
    def class_name(cls):
        return "KeywordOverlapReranker"

docs = [Document(text="Policy POL-1 covers fire and theft.", doc_id="POL-1")]
index = VectorStoreIndex.from_documents(docs)
retriever = index.as_retriever(similarity_top_k=1)

server = MCPServer("claims-retrieval")

@server.tool()
def retrieve_policy_clauses(query: str) -> list[str]:
    return [r.node.ref_doc_id for r in retriever.retrieve(query)]

async def main():
    n = 200
    t0 = time.monotonic()
    for _ in range(n):
        retrieve_policy_clauses("fire")
    direct_elapsed = time.monotonic() - t0

    t0 = time.monotonic()
    for _ in range(n):
        await server.call_tool("retrieve_policy_clauses", {"query": "fire"})
    mcp_elapsed = time.monotonic() - t0

    print(f"MCP call_tool hop measurably slower than a direct call: {mcp_elapsed > direct_elapsed}")

asyncio.run(main())

Exact millisecond figures are hardware-dependent and not presented as fixed — only the
direction of the effect (each layer adds time, never subtracts it) is genuinely stable.

BFSI Reality Check — Day 5


Legacy angle: MCP's standard boundary matters most exactly where Phase 1's real
constraint lives — a BFSI team running pgvector, Milvus, AND a legacy keyword search
side by side has no reason to expose three framework-specific tool conventions to every
agent that needs them, when one MCP server can front all three behind one discovery
mechanism.


Compliance angle: A single, narrow tool boundary (Concept 1's plain function, or
Concept 2's MCP tool) is also the natural place to enforce Week 22's coming
least-privilege pattern — the calling agent only ever sees "retrieve policy clauses,"
never the underlying store's full query surface.


What breaks in production: A team measures Concept 4's real latency overhead once,
concludes "MCP adds negligible latency," and never re-measures once the MCP server moves
from in-process (this week's genuinely-executed setup) to a real stdio or network
transport in production — where process-boundary serialization and IPC cost strictly
more than the in-process call overhead measured here. The honest caveat this concept
already states (a real transport "would add strictly more on top of what's measured
here") is exactly the gap a one-time benchmark taken during development and never
revisited would miss.




Architecture Decision — Week 20


Choosing between: letting two AI frameworks' internals interpenetrate a single
pipeline (a LangGraph node reaching into LlamaIndex's query engine, or vice versa) vs. a
single narrow tool boundary (a plain function, or an MCP server) between them vs.
standardizing on one framework for the whole system and accepting whatever gaps it has.


Rule of thumb: never let two frameworks' internals interpenetrate — Concept 1's
"LangGraph never needs to know a VectorStoreIndex exists" rule holds regardless of
which two frameworks are involved, because the coupling cost (a change to LlamaIndex's
internals breaking LangGraph code that reached past the boundary) is the same cost Week
12 already named for a DAG task passing a payload instead of a reference. Between a plain
function boundary and an MCP server: use a plain function when only one framework, in one
codebase, ever calls the tool; reach for MCP the moment more than one AGENT or framework
needs to discover and call the SAME tool, since that is exactly the discovery problem MCP
solves and a plain function does not. Standardizing on one framework for an entire system
is rarely the right call once Day 4's own measurement stands: LangGraph's proven
durability and LlamaIndex's retrieval-composition strength are not a single framework's
strengths, so a system with both a durable-approval-workflow need (Week 19's domain) and a
retrieval-composition need (this week's Days 1-3) is better served by both, meeting at
exactly the tool boundary this closing day built.
