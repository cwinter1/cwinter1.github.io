Week 08 turned a scanned form or a PDF into clean text and structured elements. Before any of that text can be embedded and searched, it has to be split into pieces small enough for an embedding model's context window and a retrieval system's relevance granularity — that splitting decision is this week's whole subject. Four strategies are covered, in order of increasing structural awareness: fixed-size splitting (Day 1), which knows nothing about the document's structure; recursive splitting (also Day 1), which respects separators but still doesn't understand meaning; structure-aware splitting (Day 2), which uses the document's own headings and clause boundaries; and embedding-similarity breakpoint chunking (Day 3), which finds topic boundaries the document's formatting doesn't mark at all. Day 4 covers what travels with a chunk besides its text, and Day 5 measures which strategy actually wins on a real retrieval task rather than assuming one does.

Concept 1 — Token-Based Sizing Is Not Character Counting

An embedding model's context window and a chat model's usable input are both measured in tokens — the sub-word units a tokenizer produces — not characters or words. A chunk sized by character count can silently exceed a model's real token budget on text with lots of short, common words (each pulling only fractional-token weight in a real BPE vocabulary is not how it works — the actual effect runs the other way just as often: uncommon words, numbers, and punctuation each cost more than one token per character-run). The only sizing measurement that reflects what a model actually sees is a token count from the tokenizer that model uses.

This sandbox cannot reach tiktoken's real vocabulary file over the network here (its cl100k_base encoding is fetched from Microsoft Blob Storage on first use, and this environment's egress proxy blocks that host), so the token counts below use a simplified stand-in tokenizer — a regex that splits on letter-runs, digit-runs, and individual punctuation/symbol characters — instead of real BPE. It is not accurate at the sub-word level a real tokenizer operates at, but it demonstrates the same point real BPE tokenization makes: a token count is a different number from a character count and from a word count, and chunk-size budgets stated in "tokens" have to be measured with a real tokenizer, not approximated by dividing character count by four.

Example:

    """Stand-in tokenizer, NOT real BPE -- see prose above. Splits on
    letter-runs, digit-runs, and individual non-alphanumeric characters."""
    return re.findall(r"[A-Za-z]+|[0-9]+|[^\sA-Za-z0-9]", text)

Concept 2 — Recursive Splitting Respects Separators, Fixed-Size Splitting Doesn't


A fixed-size splitter cuts every N characters regardless of what's at that boundary — it
can land inside a word, a number, or a policy clause with equal indifference. LangChain's
RecursiveCharacterTextSplitter fixes this by trying a list of separators in order (by
convention ["\n\n", "\n", ". ", " ", ""] — paragraph, then line, then sentence, then
word, then character as the last resort), merging small pieces back together up to the
target chunk size, and recursing into the next separator only when a piece produced by the
current one is still too big to fit.


Example:


def recursive_split(text, size, overlap, separators):
    """Simplified RecursiveCharacterTextSplitter. Tries separators[0] first;
    merges split pieces back together up to `size`; recurses into any piece
    still too big using separators[1:]; falls back to a hard character slice
    once separators run out."""
    if len(text) <= size:
        return [text] if text else []
    if not separators:
        chunks = []
        start = 0
        step = size - overlap
        while start < len(text):
            chunks.append(text[start:start + size])
            start += step
        return chunks

    sep = separators[0]
    pieces = list(text) if sep == "" else text.split(sep)

    result = []
    buf = ""
    for piece in pieces:
        candidate = buf + (sep if buf else "") + piece
        if len(candidate) <= size:
            buf = candidate
        else:
            if buf:
                result.append(buf)
            if len(piece) > size:
                result.extend(recursive_split(piece, size, overlap, separators[1:]))
                buf = ""
            else:
                buf = piece
    if buf:
        result.append(buf)
    return result


def fixed_size_chunks(text, size, overlap=0):
    chunks = []
    start = 0
    step = size - overlap
    while start < len(text):
        chunks.append(text[start:start + size])
        start += step
    return chunks

Concept 3 — Overlap Is a Fraction of Chunk Size, and It Duplicates Storage


Overlap re-includes the tail of one chunk at the head of the next, so a fact stated right
at a chunk boundary isn't lost to whichever chunk doesn't get retrieved. It is usually
expressed as a fraction of the chunk size (a common default is 10-20%), and every
character of overlap is a character stored twice — once in each of the two chunks it
appears in.


Example:


def fixed_size_chunks(text, size, overlap=0):

    step = size - overlap
    while start < len(text):
        chunks.append(text[start:start + size])
        start += step
    return chunks

Concept 4 — Mid-Sentence Truncation Is the Concrete Damage Fixed-Size Splitting Causes


Concept 2 measured that fixed-size splitting cuts mid-word; the same indifference to
structure also cuts mid-sentence and mid-clause, which is the damage that actually matters
for retrieval — a chunk ending "the policy excludes losses caused by" carries none of the
information a reader (or a retrieval system) needs, and the chunk that continues "flood,
earth movement, or war" is equally useless without the clause it's completing.


Example:


def fixed_size_chunks(text, size, overlap=0):
    chunks = []
    start = 0
    step = size - overlap
    while start < len(text):
        chunks.append(text[start:start + size])
        start += step
    return chunks

doc = (
"The policy excludes losses caused by flood, earth movement, or war, regardless of "
"any other cause or event contributing concurrently or in any sequence to the loss. "
"The policy also excludes losses caused by neglect, wear and tear, or gradual "
"deterioration, and losses that occur while the dwelling has been vacant for more "
"than sixty consecutive days."
)

for size in (80, 120, 160):
    chunks = fixed_size_chunks(doc, size)
    # a chunk "ends mid-sentence" if its last character isn't sentence-ending
    # punctuation and it isn't the final chunk.
    mid_sentence_endings = sum(
        1 for c in chunks[:-1] if c.rstrip()[-1] not in ".!?"
    )
    print(f"size={size:>3}  chunks={len(chunks)}  "
          f"mid-sentence endings={mid_sentence_endings}/{len(chunks)-1}")
    print(f"    chunk 0 ends: ...{chunks[0][-45:]!r}")

here, which is exactly why Concept 2's recursive approach exists.




BFSI Reality Check — Day 1


Legacy angle: A batch DataPrep job re-chunking a whole claims-document archive after a
chunking-strategy change is a full re-embed of every chunk, not an incremental update —
this is exactly the "full reindex" cost Week 11's incremental-embedding economics were
built to avoid, and it recurs every time the chunking strategy itself changes, not just
when source documents change.


Compliance angle: A chunk boundary that splits an exclusion clause from the condition
that limits it (for example, "flood is excluded" landing in one chunk, "unless caused by a
covered peril" landing in the next) is not just a quality problem — a chatbot that
retrieves only the first chunk and states the exclusion as absolute is giving a materially
wrong answer about coverage, which is a real E&O and consumer-protection exposure, not an
abstract retrieval-quality metric.


What breaks in production: A chunking pipeline tuned and validated against long-form
policy wording gets pointed at short customer-service call transcripts without
re-validation, because "it already works." Fixed-size and even recursive splitting behave
very differently on a document made of many short speaker turns than on a document made of
long formal paragraphs — the failure is silent, since the pipeline still runs and produces
chunks, they are just badly shaped for the new document type.

Concept 1 — Splitting on Section and Clause Headings, Not Paragraphs


Policy wording (and most formal legal/financial documents) has an explicit structure the
document itself declares — ALL-CAPS section titles (DECLARATIONS, COVERAGE A,
EXCLUSIONS), numbered clauses, or markdown headers in a digitized version. Splitting on
those headings, rather than on paragraph breaks the way Day 1's recursive splitter does,
means every chunk boundary coincides with a boundary the document's own author already
drew — a section is never split mid-way through by an algorithm that doesn't know what the
section is about.


Example:


import re

def split_on_headings(text, heading_pattern=r"^[A-Z][A-Z0-9 /&\-]{3,60}$"):
    """Split on ALL-CAPS section-title lines -- a real, simple structural
    heuristic that works because policy wording conventionally uses
    ALL-CAPS section headers."""
    lines = text.split("\n")
    sections = []
    current_heading = None
    current_body = []
    for line in lines:
        stripped = line.strip()
        if stripped and re.match(heading_pattern, stripped):
            if current_heading is not None:
                sections.append((current_heading, "\n".join(current_body).strip()))
            current_heading = stripped
            current_body = []
        else:
            current_body.append(line)
    if current_heading is not None:
        sections.append((current_heading, "\n".join(current_body).strip()))
    return sections

Named insured: Jane Doe. Policy period: 12 months from inception date.

COVERAGE A -- DWELLING

This policy covers the dwelling on the residence premises against direct physical loss,
subject to the exclusions below. Coverage extends to attached structures.

"Dwelling" means the residence structure, including attached structures, used principally
for residential purposes. "Residence premises" means the one-family dwelling shown in the

Concept 2 — A Table or Definitions List Stays in One Chunk, Even Past the Target Size


A rate table, a limits schedule, or a definitions list is only useful to a reader (or a
retrieval system) as a whole — a chunk containing "Coverage A Dwelling: $350,000" without
the rest of the limits table around it has lost the very thing that made the row
meaningful. Structure-aware chunking treats a table or list as one atomic unit and lets it
exceed the target chunk size rather than split it, on the reasoning that an oversized but
coherent chunk beats an undersized but broken one.


Example:

Concept 3 — Endorsements and Exclusions Are Atomic Units, Never Split or Merged


An endorsement modifies the base policy as one indivisible unit — its sublimit, its
deductible, and its scope only make sense read together. The same heading-based split from
Concept 1 keeps an endorsement's full body in one section even when it is the single
longest section in the document, and — just as importantly — never silently merges it with
the section that follows.

Concept 4 — The Chunk-Size Variance This Deliberately Accepts


Fixed-size and recursive splitting both produce chunks clustered fairly close to the
target size. Structure-aware splitting gives that up on purpose: a one-line
DECLARATIONS section and a long DEFINITIONS section are both exactly one chunk each,
regardless of how different their sizes are, because the document's own structure — not a
size target — is what decides where a boundary goes.


Example:


import re
import statistics

def split_on_headings(text, heading_pattern=r"^[A-Z][A-Z0-9 /&\-]{3,60}$"):
    lines = text.split("\n")
    sections = []
    current_heading = None
    current_body = []
    for line in lines:
        stripped = line.strip()
        if stripped and re.match(heading_pattern, stripped):
            if current_heading is not None:
                sections.append((current_heading, "\n".join(current_body).strip()))
            current_heading = stripped
            current_body = []
        else:
            current_body.append(line)
    if current_heading is not None:
        sections.append((current_heading, "\n".join(current_body).strip()))
    return sections

Concept 1 — Sentence Embeddings and Cosine-Distance Breakpoints


Neither Day 1's separator-based splitting nor Day 2's heading-based splitting can find a
boundary that the document's own formatting doesn't mark — a call-transcript topic change
mid-conversation, with no blank line, no heading, nothing but the words themselves
changing subject. Embedding-similarity chunking finds this kind of boundary directly:
embed each sentence, measure the cosine distance between consecutive sentences, and treat
an unusually large jump in distance as a breakpoint — a real topic change, not a
formatting artifact.


This sandbox has no live embedding API, so the examples below use a deterministic
stand-in embedder — a bag-of-words hash into a fixed-size vector, not a real
transformer-based embedding model. It is accurate enough to demonstrate that distance
jumps when vocabulary changes (which is what a topic change usually looks like at the
word level), but it does not capture the semantic/contextual understanding a real
embedding model provides — two sentences using entirely different words for the same
concept would show high distance here despite meaning the same thing, which a real model
would not do.


Example:


import numpy as np
import re
import zlib

def stand_in_embed(text, dim=64):
    """Deterministic stand-in embedder -- NOT a real model. Hashes each
    lowercased word into a fixed-dim vector via a seeded random projection
    (bag-of-words style), then L2-normalizes. Sentences sharing more
    topical words land closer in cosine distance."""
    vec = np.zeros(dim)
    words = re.findall(r"[a-z]+", text.lower())
    for w in words:
        h = zlib.crc32(w.encode())
        rng = np.random.default_rng(h)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

def cosine_distance(a, b):
    return 1 - float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

Concept 2 — buffer_size and breakpoint_percentile_threshold


Two parameters control real semantic-breakpoint implementations (LlamaIndex's
SemanticSplitterNodeParser among them). buffer_size combines each sentence with its
immediate neighbors before embedding, smoothing out single-sentence noise so a breakpoint
reflects a sustained topic change rather than one unusual sentence.
breakpoint_percentile_threshold sets the cutoff as a percentile of the observed distance
distribution (rather than a fixed number), so the same threshold logic adapts to how
volatile a particular document's sentence-to-sentence distances happen to be.


Example:


import numpy as np
import re
import zlib

def stand_in_embed(text, dim=64):
    vec = np.zeros(dim)
    words = re.findall(r"[a-z]+", text.lower())
    for w in words:
        h = zlib.crc32(w.encode())
        rng = np.random.default_rng(h)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

def cosine_distance(a, b):
    return 1 - float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

sentences = [
    "Hi, I'm calling about my homeowners policy renewal.",
    "I wanted to check if my dwelling coverage limit went up this year.",
    "The declarations page shows three hundred fifty thousand for coverage A.",
    "Okay that makes sense, thank you for confirming that.",
    "Actually I also had a question about my payment method on file.",
    "Can you tell me if my autopay is set up with the checking account ending in 4821.",
    "I want to switch my payment method to a different card before next month.",

def buffered_embed(sentences, idx, buffer_size):
    lo = max(0, idx - buffer_size)
    hi = min(len(sentences), idx + buffer_size + 1)
    return stand_in_embed(" ".join(sentences[lo:hi]))

for buffer_size in (0, 1):

    distances = [cosine_distance(embeds[i], embeds[i + 1]) for i in range(len(embeds) - 1)]
    threshold = np.percentile(distances, 75)
    breakpoints = [i for i, d in enumerate(distances) if d > threshold]
    print(f"buffer_size={buffer_size}  distances={[round(d, 3) for d in distances]}")
    print(f"  threshold(p75)={threshold:.4f}  breakpoints={breakpoints}")

Concept 3 — The Embedding Calls This Adds at Ingest Time


Day 1 and Day 2's splitters find their boundaries for free — a separator or a heading
match costs nothing but string comparison. Embedding-similarity chunking has to embed
every sentence just to find its boundaries, before any of the resulting chunks are
embedded again for retrieval — a real, per-document cost that scales with sentence count,
not chunk count.

Concept 4 — Where This Beats Recursive Splitting on Call Transcripts


A call transcript typically has no blank lines between speaker turns and no headings —
just one line per turn. Recursive splitting's separator hierarchy has nothing structural
to grab onto beyond individual lines, so where its boundaries land relative to a real topic
change is governed entirely by the size parameter — a coincidence of where size
happens to divide the text, not an actual read of the content.


Example:


def recursive_split(text, size, overlap, separators):
    if len(text) <= size:
        return [text] if text else []
    if not separators:
        chunks = []
        start = 0
        step = size - overlap
        while start < len(text):
            chunks.append(text[start:start + size])
            start += step
        return chunks
    sep = separators[0]
    pieces = list(text) if sep == "" else text.split(sep)
    result, buf = [], ""
    for piece in pieces:
        candidate = buf + (sep if buf else "") + piece
        if len(candidate) <= size:
            buf = candidate
        else:
            if buf:
                result.append(buf)
            if len(piece) > size:
                result.extend(recursive_split(piece, size, overlap, separators[1:]))
                buf = ""
            else:
                buf = piece
    if buf:
        result.append(buf)
    return result

    "Hi, I'm calling about my homeowners policy renewal.",
    "I wanted to check if my dwelling coverage limit went up this year.",
    "The declarations page shows three hundred fifty thousand for coverage A.",
    "Okay that makes sense, thank you for confirming that.",
    "Actually I also had a question about my payment method on file.",
    "Can you tell me if my autopay is set up with the checking account ending in 4821.",
    "I want to switch my payment method to a different card before next month.",
]
transcript = "\n".join(sentences)

center's transcripts (short, terse turns) gets reused unchanged for a different line of
business's transcripts (longer, more discursive turns) — the same percentile-based
threshold logic adapts to within-document distance variance, but a percentile computed
per-document does not generalize a specific numeric sensitivity across document
populations with very different baseline verbosity, so breakpoint quality quietly
degrades on the new population.

Concept 1 — Parent Document ID, Section Path, and Effective/Expiry Dates


A chunk's text is only half of what needs to be stored. parent_doc_id traces a chunk
back to the document it came from, section_path records where inside that document, and
effective_date/expiry_date record which policy version the chunk describes — a limits
figure from last year's renewal and this year's renewal can both exist in the same index,
and only the metadata tells them apart.


Example:


import hashlib

def build_chunk_record(text, parent_doc_id, section_path, effective_date, expiry_date,
                        page_anchor, chunk_index):
    """Real chunk metadata a production pipeline would attach -- every field
    here is something a later retrieval filter or citation needs, not
    decoration."""
    chunk_id = hashlib.sha256(
        f"{parent_doc_id}:{chunk_index}:{text}".encode()
    ).hexdigest()[:16]
    return {
        "chunk_id": chunk_id,
        "parent_doc_id": parent_doc_id,
        "section_path": section_path,
        "effective_date": effective_date,
        "expiry_date": expiry_date,
        "page_anchor": page_anchor,
        "chunk_index": chunk_index,
        "text": text,
    }

record = build_chunk_record(

    section_path="COVERAGE > EXCLUSIONS",

    expiry_date="2026-12-31",

Concept 2 — A Contextual Header Prepended Before Embedding


A chunk read in isolation often loses the context that made it unambiguous in the source
document — "coverage does not apply to loss caused by flood" doesn't say which coverage.
Prepending a short contextual header (document name, section path) to the text actually
embedded — while keeping the original, unprefixed text as what's shown to a reader — lets
the embedding capture context the bare chunk text alone doesn't carry.


Example:


import numpy as np
import re
import zlib

    words = re.findall(r"[a-z]+", text.lower())
    for w in words:
        h = zlib.crc32(w.encode())
        rng = np.random.default_rng(h)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

def cosine_sim(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

Concept 3 — Page Anchors, and Metadata Designed to Become a Retrieval Filter


A page_anchor lets a retrieval-backed answer cite exactly where its claim came from — not
"the policy says X" but "policy POL-8842-C, Exclusions, page 4." And a field like
expiry_date isn't just descriptive: it's designed from the start to become a filter
condition a retrieval query applies, deciding which chunks are even eligible to be ranked
in the first place.

BFSI Reality Check — Day 4


Legacy angle: parent_doc_id and section_path are only as reliable as whatever

when someone tries to use exactly those capabilities on it.

Concept 1 — One Fixed Query Set, Run Across Every Chunking Strategy


Every strategy this week covered is a genuine engineering choice, not an obviously correct
default — the only way to know which one actually wins for a given corpus is to run the
same fixed set of test queries against each strategy's output and measure recall@k, the
fraction of queries whose correct answer appears in the top-k retrieved chunks. "Fixed"
matters: comparing strategies against different queries, or against queries added or
tweaked between runs, measures the queries changing, not the strategies.


Example:


import numpy as np
import re
import zlib

def stand_in_embed(text, dim=64):
    vec = np.zeros(dim)
    words = re.findall(r"[a-z]+", text.lower())
    for w in words:
        h = zlib.crc32(w.encode())
        rng = np.random.default_rng(h)
        vec += rng.normal(size=dim)
    norm = np.linalg.norm(vec)
    return vec / norm if norm > 0 else vec

def cosine_sim(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

def fixed_size_chunks(text, size, overlap=0):
    return [text[i:i + size] for i in range(0, len(text), size - overlap)]

def recursive_split(text, size, overlap, separators):
    if len(text) <= size:
        return [text] if text else []
    if not separators:
        return fixed_size_chunks(text, size, overlap)
    sep = separators[0]
    pieces = list(text) if sep == "" else text.split(sep)
    result, buf = [], ""
    for piece in pieces:
        candidate = buf + (sep if buf else "") + piece
        if len(candidate) <= size:
            buf = candidate
        else:
            if buf:
                result.append(buf)
            if len(piece) > size:
                result.extend(recursive_split(piece, size, overlap, separators[1:]))
                buf = ""
            else:
                buf = piece
    if buf:
        result.append(buf)
    return result

def split_on_headings(text, heading_pattern=r"^[A-Z][A-Z0-9 /&\-]{3,60}$"):
    lines = text.split("\n")
    sections, current_heading, current_body = [], None, []
    for line in lines:
        stripped = line.strip()
        if stripped and re.match(heading_pattern, stripped):
            if current_heading is not None:
                sections.append(f"{current_heading}\n{chr(10).join(current_body).strip()}")
            current_heading = stripped
            current_body = []
        else:
            current_body.append(line)
    if current_heading is not None:
        sections.append(f"{current_heading}\n{chr(10).join(current_body).strip()}")
    return sections

policy = """DECLARATIONS

Named insured: Jane Doe. Policy period: 12 months from inception date.

COVERAGE A -- DWELLING

This policy covers the dwelling on the residence premises against direct physical loss,
subject to the exclusions below. Coverage extends to attached structures. The dwelling
limit of liability is three hundred fifty thousand dollars.

DEFINITIONS

"Dwelling" means the residence structure, including attached structures, used principally
for residential purposes. "Residence premises" means the one-family dwelling shown in the
Declarations. "Other structures" means structures separated from the dwelling by clear
space.

EXCLUSIONS

Flood, earth movement, and war are excluded regardless of any other cause or event
contributing concurrently or in any sequence to the loss. Losses caused by neglect are
also excluded.

ENDORSEMENT HO-321 -- WATER BACKUP COVERAGE

This endorsement adds coverage for water that backs up through sewers or drains, subject
to a ten thousand dollar sublimit and a separate five hundred dollar deductible for this
coverage only."""

queries = [
    ("what is excluded from coverage", "flood"),
    ("what is the water backup sublimit", "ten thousand"),
    ("what does dwelling mean", "residence structure"),
    ("what is the dwelling limit of liability", "three hundred fifty thousand"),
]

def recall_at_k(chunks, queries, k=1):
    chunk_embeds = [stand_in_embed(c) for c in chunks]
    hits = 0
    for q, answer_keyword in queries:
        sims = [cosine_sim(stand_in_embed(q), ce) for ce in chunk_embeds]
        top_k_idx = np.argsort(sims)[::-1][:k]
        hits += any(answer_keyword in chunks[i] for i in top_k_idx)
    return hits / len(queries)

strategies = {
    "fixed(120)": fixed_size_chunks(policy, 120),
    "recursive(120)": recursive_split(policy, 120, 0, ["\n\n", "\n", ". ", " ", ""]),
    "structure-aware": split_on_headings(policy),
}

for name, chunks in strategies.items():
    r1 = recall_at_k(chunks, queries, k=1)
    r2 = recall_at_k(chunks, queries, k=2)
    print(f"{name:16} chunks={len(chunks):>2}  recall@1={r1:.2f}  recall@2={r2:.2f}")

Concept 2 — Context-Sufficiency: A Recall Hit Isn't the Same as a Complete Answer


Recall@k asks whether a chunk containing the right keyword was retrieved — it says
nothing about whether that chunk contains the whole answer. A chunk can score a hit while
still truncating the very list or clause the query asked about, if the chunk boundary
happened to fall in the middle of it.

Concept 3 — A Chunk-Size Sweep Curve, Not a Single Guess


Concepts 1-2 both used one hand-picked size per strategy. The only way to know whether a
chosen size is actually good, rather than merely not-obviously-bad, is to sweep a range of
sizes and look at the resulting recall curve — a single size, chosen once and never
revisited, is a guess wearing a specific number.


Example:

Concept 4 — Tokens-Per-Answer as the Tiebreaker


When two strategies score the same recall, they are not necessarily equally good — one may
retrieve much larger chunks to get there, which costs more in embedding compute at ingest
and more in prompt tokens at answer time. Token cost per correctly-answered query is the
tiebreaker recall@k alone can't provide.


Example:


def approx_bpe_tokens(text):
    import re
    return re.findall(r"[A-Za-z]+|[0-9]+|[^\sA-Za-z0-9]", text)

# (strategies, queries, stand_in_embed, cosine_sim as defined in Concept 1)
for name, chunks in strategies.items():
    chunk_embeds = [stand_in_embed(c) for c in chunks]
    tokens_per_hit = []
    for q, answer_keyword in queries:
        sims = [cosine_sim(stand_in_embed(q), ce) for ce in chunk_embeds]
        top1_idx = int(np.argmax(sims))
        top1_chunk = chunks[top1_idx]
        if answer_keyword in top1_chunk:
            tokens_per_hit.append(len(approx_bpe_tokens(top1_chunk)))
    avg_tokens = sum(tokens_per_hit) / len(tokens_per_hit) if tokens_per_hit else float("nan")
    print(f"{name:16} correct={len(tokens_per_hit)}/{len(queries)}  "
          f"avg tokens per correct top-1 chunk={avg_tokens:.1f}")

BFSI Reality Check — Day 5


Legacy angle: A chunking-strategy evaluation run once at launch, on the document types
available at launch, does not automatically transfer when a new document type (a different
line of business's policy template, a new call-center vendor's transcript format) is
onboarded later — the same discipline Day 1's warm-up caveat and Week 01's benchmarking
practice both established: re-measure on the actual corpus in front of you, not the one you
validated against originally.


Compliance angle: A documented recall@k, context-sufficiency, and token-cost comparison
across chunking strategies is exactly the kind of evidence an internal model-risk review
or an EU AI Act Article 15 accuracy claim wants for a retrieval-backed system — a chunking
strategy picked "because it seemed more sophisticated" with no measurement behind it is not
defensible evidence, whatever intuition motivated the choice.


What breaks in production: A chunking strategy's evaluation numbers from the design
phase get treated as a permanent property of the strategy rather than a snapshot of one
corpus, one query set, one embedding model at one point in time — exactly the same failure
mode Week 01 and Week 04 both closed on for vector-index benchmarks, now recurring one
layer up the pipeline at the chunking-strategy level.




Architecture Decision — Week 09


Choosing between: fixed-size, recursive, structure-aware, and embedding-similarity
breakpoint chunking, per document type rather than one strategy for the whole pipeline.


Rule of thumb: default to recursive splitting (Day 1) for anything without more
specific structure to exploit — it costs nothing extra over fixed-size splitting and never
does worse. Move to structure-aware chunking (Day 2) for documents with real, detectable
structure (policy wording, contracts, anything with section headings or clause
boundaries) — it costs the effort of writing a structure detector, and Concept 4's own
measurement shows that cost is not automatically repaid by better recall or lower token
cost on every corpus, so validate it against the fixed query set (Day 5 Concept 1) rather
than assuming semantic sophistication implies retrieval quality. Reach for
embedding-similarity breakpoint chunking (Day 3) specifically for unstructured
conversational text (call transcripts, chat logs) where no separator or heading exists to
detect a topic boundary at all — and budget for its real, per-sentence embedding cost at
ingest time (Day 3 Concept 3), which the other three strategies don't pay. Layer chunk
metadata and context injection (Day 4) on top of whichever splitting strategy is chosen;
it is not a competing strategy, it is a requirement for citation, staleness detection
(feeding directly into Week 11's incremental-embedding economics), and safe retrieval
filtering regardless of how the chunk boundaries themselves were decided. Whatever
combination is chosen, re-run Day 5's evaluation whenever the document population changes
meaningfully — a chunking strategy's measured recall is a property of the corpus and query
set it was measured against, not a permanent property of the strategy itself.
